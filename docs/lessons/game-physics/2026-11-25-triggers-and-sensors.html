Triggers and sensors

How a trigger notices bodies without blocking them, and how comparing this step's overlap with the last one gives clean enter, stay and exit events.

Your hero steps on a spike trap that should take 10 hit points, and is dead before the sprite has finished one frame of the hurt animation. A checkpoint chimes sixty times a second. A door opens when you walk up to it and never closes again.

All three are the same bug. The code asks "is the player touching this?" when it should ask "did the player just start touching this?"

A shape that notices but does not block

A trigger, also called a sensor, is a collision shape that is tested for overlap like any other, but is never pushed out of. Bodies walk straight through it. Its only job is to report who is inside. Spike traps, healing pools, checkpoints and door sensors are all triggers.

The overlap test itself is the AABB test from earlier in this track: two boxes overlap when their intervals overlap on both axes. The hard part is not the test. It is deciding when to act on it.

The bug: acting on every step

The first version most people write looks like this:

if overlaps(player, spikes) then
  player.hp = player.hp - 10    -- runs on every step you stand there
end

In words: as long as the player is inside, take 10 hit points. But the physics runs 60 steps per second, so ten steps, one sixth of a second, empties a 100 hit point bar.

This check is not wrong. It is the right answer to a different question. A healing pool that gives 20 hit points per second should act every step, adding 20 × STEP each time. What is missing are the two moments in between: the step the body arrives and the step it leaves.

The fix: compare with the last step

Give each trigger a memory: the set of bodies that were inside it on the previous step. Then every step, for every body, you have two yes-or-no answers, "was it inside?" and "is it inside now?". Four combinations give four results:

Was insideInside nowEventTypical use
nononothing
noyesenterdamage once, ring a checkpoint, open a door
yesyesstayheal or burn over time, show a prompt
yesnoexitclose the door, hide the prompt

An enter event fires once, on the first step of an overlap. An exit event fires once, on the first step without it. A stay event fires on every step in between. After deciding, the trigger writes "inside now" into its memory, ready for the next step.

One step by hand

In the demo the player is a 24 px box walking right at 200 px/s, so it moves 200 / 60 = 3.33 px per step. Say its right edge is at 118 and the spikes start at x = 120.

  1. Step 1: the right edge moves to 121.33, past 120. Was inside: no. Inside now: yes. Enter: hit points go from 100 to 90.
  2. Step 2: was inside: yes. Inside now: yes. Stay. The spikes have no stay action, so nothing happens. Hit points stay at 90.
  3. With the naive check, step 2 would also take 10, and so would every step after it: 0 hit points after 10 steps.

The healing pool has only a stay action: 20 × (1/60) = 0.33 hit points per step, so 30 steps, half a second, give back 10.

Correct versus good

Real spikes would hurt every time you push down on them. Games pick one hit on entry, often followed by a short spell of invulnerability, because that reads clearly to the player. A trigger is a game rule wearing a collision shape.

Try it

The demo starts with the naive check. Walk into the spikes and watch the log flood and the hit points vanish. Cross the checkpoint line and it rings on every step. Walk into the light zone and out again: the light never turns off. Now switch to Enter, stay and exit, press Reset, and repeat: each zone fires once on the way in and once on the way out.

The code

The demo's step in Lua, with the same zones and numbers. Each zone keeps a table inside of the bodies that overlapped it on the last step, so one trigger can track many bodies at once.

local STEP, RUN = 1 / 60, 200           -- fixed step (s), walking speed (px/s)
local HP_MAX, SPIKE_DAMAGE, HEAL_RATE = 100, 10, 20

local player = { x = 48, y = 138, w = 24, h = 24, hp = HP_MAX }
local checkpoints, lightOn = 0, false

-- A trigger is a box with up to three callbacks. It never blocks anything.
local zones = {
  { name = "spikes", x = 120, y = 30, w = 100, h = 80,
    onEnter = function (b) b.hp = math.max(b.hp - SPIKE_DAMAGE, 0) end },
  { name = "pool", x = 120, y = 190, w = 120, h = 80,
    onStay = function (b) b.hp = math.min(b.hp + HEAL_RATE * STEP, HP_MAX) end },
  { name = "checkpoint", x = 296, y = 0, w = 8, h = 300,
    onEnter = function (b) checkpoints = checkpoints + 1 end },
  { name = "light", x = 390, y = 30, w = 170, h = 90,
    onEnter = function (b) lightOn = true end,
    onExit = function (b) lightOn = false end },
}
for _, z in ipairs(zones) do z.inside = {} end  -- bodies inside last step

local function overlaps(a, b)
  return a.x < b.x + b.w and b.x < a.x + a.w
     and a.y < b.y + b.h and b.y < a.y + a.h
end

local function updateTriggers(bodies)
  for _, z in ipairs(zones) do
    for _, b in ipairs(bodies) do
      local was = z.inside[b] == true
      local now = overlaps(b, z)
      if now and not was then
        if z.onEnter then z.onEnter(b) end
      elseif now and was then
        if z.onStay then z.onStay(b) end
      elseif was and not now then
        if z.onExit then z.onExit(b) end
      end
      z.inside[b] = now or nil              -- remember for the next step
    end
  end
end

local function physicsStep(dx, dy)
  player.x = math.max(0, math.min(player.x + dx * RUN * STEP, 600 - player.w))
  player.y = math.max(0, math.min(player.y + dy * RUN * STEP, 300 - player.h))
  updateTriggers({ player })                -- after moving, never before
end

local accumulator = 0
function love.update(dt)
  local dx, dy = 0, 0
  if love.keyboard.isDown("right", "d") then dx = dx + 1 end
  if love.keyboard.isDown("left", "a") then dx = dx - 1 end
  if love.keyboard.isDown("down", "s") then dy = dy + 1 end
  if love.keyboard.isDown("up", "w") then dy = dy - 1 end
  if dx ~= 0 and dy ~= 0 then dx, dy = dx * 0.7071, dy * 0.7071 end
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    physicsStep(dx, dy)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  for _, z in ipairs(zones) do
    love.graphics.rectangle("line", z.x, z.y, z.w, z.h)
  end
  love.graphics.rectangle("fill", player.x, player.y, player.w, player.h)
  love.graphics.print("HP " .. math.floor(player.hp) .. "  checkpoints " .. checkpoints, 10, 310)
end
# Godot 4: an Area2D is a trigger. It emits body_entered and body_exited.
# There is no stay signal: ask for the overlapping bodies each physics step.
extends Area2D

@export var damage := 10
@export var heal_rate := 0.0     # hit points per second, 0 for spikes

func _ready() -> void:
    body_entered.connect(_on_body_entered)
    body_exited.connect(_on_body_exited)

func _on_body_entered(body: Node2D) -> void:
    if damage > 0 and body.has_method("take_damage"):
        body.take_damage(damage)

func _on_body_exited(body: Node2D) -> void:
    pass   # close a door, hide a prompt

func _physics_process(delta: float) -> void:
    if heal_rate > 0.0:
        for body in get_overlapping_bodies():
            if body.has_method("heal"):
                body.heal(heal_rate * delta)
using UnityEngine;

// Unity 2D: tick Is Trigger on this object's Collider2D. Trigger messages
// are only sent if at least one of the two objects has a Rigidbody2D.
public class Zone : MonoBehaviour
{
    public int damage = 10;
    public float healRate = 0f;   // hit points per second, 0 for spikes

    void OnTriggerEnter2D(Collider2D other)
    {
        if (damage > 0 && other.TryGetComponent(out Health health))
            health.Damage(damage);
    }

    void OnTriggerStay2D(Collider2D other)
    {
        if (healRate > 0f && other.TryGetComponent(out Health health))
            health.Heal(healRate * Time.fixedDeltaTime);
    }

    void OnTriggerExit2D(Collider2D other)
    {
        // close a door, hide a prompt
    }
}

In the GDScript and C# tabs, take_damage, heal and the Health component are your own code, not engine API. The engines keep the "inside last step" memory for you; you choose which event each action belongs to. In LÖVE's own love.physics, a fixture marked with setSensor(true) plays the same role, and the world's begin and end contact callbacks are its enter and exit.

Pitfalls

  • A one-shot action in a stay handler. Damage, score and sounds in a stay handler, or in an "is overlapping" check, run on every step. Put them in enter. Keep stay for things measured per second, and multiply them by the step.
  • Thin triggers and fast bodies. A trigger is tested at the end of each step, just like a wall, so it can tunnel. In the demo, drag the player fast across the 8 px checkpoint line and it may never ring. Make goal lines thicker than a body moves in one step, or sweep the path from the previous position as in the swept AABB lesson.
  • Exit that never comes. If a body is deleted, disabled or teleported while inside, some code paths never see it leave. Engines differ on whether they report an exit in these cases, so test yours. In your own code, remove deleted bodies from every inside table and decide whether that counts as an exit.
  • Checking before moving. Update triggers after the step's movement, in the fixed step, not in the draw function. Otherwise events depend on the frame rate or arrive a step late.
  • Changing the world inside a callback. Deleting bodies while the engine is still reporting events can break its loop over contacts. Record what to do and do it after the step.

In real games

Every major engine has this idea built in. Godot has Area2D and Area3D with body_entered and body_exited signals. Unity has the Is Trigger checkbox on colliders and the OnTriggerEnter, OnTriggerStay and OnTriggerExit messages, with 2D versions for 2D physics. Box2D calls them sensors, and LÖVE exposes them through Fixture:setSensor.

Typical uses: checkpoints, pickups, hazard and kill zones, camera zones, "press E" prompts, and areas that start a cutscene the first time you enter.

Your turn (15 minutes)

Add a "press E to talk" prompt to your game. Put a trigger around a sign or a character. Show the prompt on enter, hide it on exit, and only accept the E key while the player is inside.

You are done when the prompt appears exactly once each time you walk in, disappears as you walk out, and pressing E outside does nothing.

Takeaways

  • A trigger is a collision shape that reports overlap but never blocks or pushes.
  • "Is it overlapping?" alone is the stay event. Acting on it for one-shot actions repeats them every step.
  • Remember who was inside last step. Not before and yes now is enter; yes before and no now is exit.
  • Damage, score and sounds go in enter. Things measured per second go in stay, multiplied by the step.

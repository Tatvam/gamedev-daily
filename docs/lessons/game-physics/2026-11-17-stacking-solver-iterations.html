Stacking and solver iterations

Why a tower of boxes sinks into itself or shivers, and how running the contact solver several times per step makes it stand still.

You stack ten crates. Each pair collides correctly, yet the tower squashes until the top crate sits two crates lower than it should. Put a heavy crate on top and the tower shivers.

The collision test is fine. Every contact is fixed once per step, and fixing one breaks its neighbour.

One pass is not enough

The solver is the part of a physics step that changes velocities so that no touching pair keeps moving into each other. It fixes contacts one at a time with the impulse from earlier lessons, sharing each push by inverse mass.

One box on the floor is fixed in one go. In a stack, every box sits in two contacts. Follow three equal boxes through one step: gravity has just given each 1000 × 1/60 ≈ 16.7 pixels per second downward, and the solver walks up from the floor.

Each fix was right for its own pair and undid part of the fix below it.

Run it again

So go over the whole list again, starting from the velocities the last pass left. One trip through the list is a pass, or iteration. Each pass carries the support of the floor a little further up. For three boxes, each pass removes a quarter of the leftover speed:

PassesTop box still falling at
112.5 px/s
29.4 px/s
45.3 px/s
81.7 px/s
200.05 px/s

Solving contacts one at a time, over and over, is called sequential impulses. It never reaches the exact answer, but each pass gets closer, and you choose when it is close enough.

Why leftover speed becomes sinking

Speed the solver fails to remove moves the boxes into each other. As in the lesson on resolving penetration, overlap is removed a fraction at a time, with a strength and a slop. Here the solver asks for a small push-out speed:

push = STRENGTH * (depth - SLOP) / dt

In words: remove a fifth (STRENGTH = 0.2) of the overlap beyond half a pixel of slop during this step. Then each contact gets the impulse that leaves the pair separating at exactly that speed:

j = (closing + push) / (a.inv + b.inv)

In words: the speed change needed, shared by inverse mass. With too few passes, the stack stops sinking only once overlaps are deep enough for their push to cover what the passes missed. It rests squashed. In the demo, ten boxes with one pass sink about 67 pixels; with twenty passes, about 7.5 pixels, most of which is the allowed slop.

Tall stacks and heavy tops

Taller stacks need more passes for the support to reach the top. A heavy box on a light one is worse: the impulse is shared by inverse mass, so the light box takes almost every correction while the heavy one barely changes speed. With few passes the light box is shoved down and pushed back up over and over, and the tower shivers.

Game answer, not physics answer

Real crates never overlap, but a game stack only has to look still. Every pass costs time on every contact, so use the fewest passes that make your tallest stack look solid.

The code

This is the right tower of the demo, with the same numbers. A quick check by hand: a resting box overlaps the floor by 3 pixels. Gravity gives it 16.7 px/s downward. The push is 0.2 × (3 − 0.5) × 60 = 30 px/s, so j = 16.7 + 30 = 46.7 and the box leaves the step rising at 30 px/s. That moves it up 0.5 pixels, a fifth of the 2.5 pixels beyond the slop.

local GRAVITY    = 1000    -- pixels per second squared, +y is down
local STEP       = 1 / 60  -- fixed timestep in seconds
local ITERATIONS = 10      -- solver passes per step
local STRENGTH   = 0.2     -- share of the overlap pushed out per step
local SLOP       = 0.5     -- pixels of overlap left alone
local SIZE       = 30      -- box height in pixels

local function newBody(y, h, mass)
  local inv = 0
  if mass > 0 then inv = 1 / mass end
  return { y = y, h = h, vy = 0, inv = inv }
end

-- stack[1] is the floor, top edge at y = 400. Then ten boxes,
-- bottom first, each starting 2 px above the one below.
local stack = { newBody(420, 40, 0) }
for i = 1, 10 do
  stack[i + 1] = newBody(400 - (i - 0.5) * SIZE - i * 2, SIZE, 1)
end

local function step(dt)
  for i = 2, #stack do
    stack[i].vy = stack[i].vy + GRAVITY * dt
  end
  -- Collision detection: once per step.
  local contacts = {}
  for i = 2, #stack do
    local a, b = stack[i - 1], stack[i]
    local depth = (b.y + b.h / 2) - (a.y - a.h / 2)
    if depth > 0 then
      local push = STRENGTH * math.max(depth - SLOP, 0) / dt
      contacts[#contacts + 1] = { a = a, b = b, push = push }
    end
  end
  -- The solver: the whole list, ITERATIONS times over.
  for pass = 1, ITERATIONS do
    for _, c in ipairs(contacts) do
      local closing = c.b.vy - c.a.vy      -- b moving down into a
      local j = (closing + c.push) / (c.a.inv + c.b.inv)
      if j > 0 then                        -- only ever push apart
        c.a.vy = c.a.vy + j * c.a.inv
        c.b.vy = c.b.vy - j * c.b.inv
      end
    end
  end
  for i = 2, #stack do
    stack[i].y = stack[i].y + stack[i].vy * dt
  end
end

local accumulator = 0
function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    step(STEP)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  love.graphics.line(100, 400, 300, 400)
  for i = 2, #stack do
    local b = stack[i]
    love.graphics.rectangle("line", 174, b.y - b.h / 2, 52, b.h)
  end
end

The floor has an inverse mass of 0, so the same two lines that move a box leave the floor where it is. Set ITERATIONS to 1 to get the left tower.

Engines expose the same number. In Unity's 2D physics it is Velocity Iterations and Position Iterations under Project Settings > Physics 2D (8 and 3 by default), or Physics2D.velocityIterations and Physics2D.positionIterations from a script. Unity's 3D physics has Physics.defaultSolverIterations for the whole world and Rigidbody.solverIterations for one body. Godot's built-in 2D physics reads the project setting physics/2d/solver/solver_iterations.

Pitfalls

  • Raising STRENGTH instead of passes. A stronger push hides the sinking but turns overlap into upward speed nothing earned. With this code at 20 passes, a box dropped on a ten-box stack throws boxes up at about 14 px/s with STRENGTH = 0.2 and 53 px/s with 0.8: the stack pops and bounces.
  • Detecting contacts inside the loop. Finding contacts is the expensive part. Do it once per step and repeat only the cheap fix. Solver time is passes × contacts: 500 crates at 20 passes is 10 000 fixes per step.
  • Large mass ratios. A crate ten times heavier than the one under it needs many more passes. Keep touching bodies within a few times each other's mass, or put heavy things at the bottom.
  • Only-add clamping. The code above never takes push back. For a straight stack that gives the same result, but engines keep a running total of push per contact and clamp the total at zero, so a later pass can undo too much push from an earlier one.

In real games

Box2D, the engine behind Unity's 2D physics, popularised this approach. Its version 2 manual suggests 8 velocity and 3 position iterations, Unity's 2D defaults. Box2D version 3 instead splits each step into smaller substeps.

Engines also use warm starting: each contact begins the step with the push it needed last step, so a still stack starts nearly solved and needs fewer passes than this lesson's code. They also put bodies that stopped moving to sleep, skipping them until something touches them. Both are why crates in shipped games stay put.

Build a stack of ten equal boxes, with the code above in LÖVE or with physics bodies in your engine. Set the solver passes to 1 and measure how far the top box sinks after five seconds. Raise the passes one at a time and write down the smallest number at which the top box ends within 1 pixel per box of where it should be.

Now make the top box ten times heavier and find the new number. You are done when you have both numbers and can say why the second one is larger.

Takeaways

  • In a stack every box sits in two contacts, so fixing one contact disturbs its neighbour.
  • Running the whole contact list several times per step lets the support of the floor travel up the stack.
  • Speed the solver fails to remove becomes overlap, and the stack comes to rest squashed.
  • Tall stacks and heavy boxes on light ones need more passes. Detect contacts once and repeat only the cheap fix.
  • Choose the smallest number of passes that looks still, not the one that is physically exact.

Verlet integration

How storing the previous position instead of a velocity gives a stable integrator that you can constrain just by moving points.

You want a lantern on a rope, so you write the obvious thing: let gravity pull the lantern, then snap it back to the length of the rope. The lantern does not swing. It drops to the bottom and lies there, dead, while its velocity grows larger every frame.

The snapping was right. The problem is that you moved the lantern and forgot to tell its velocity. Verlet integration has no velocity to forget.

Remember where it was, not how fast it goes

The Euler methods from the last two lessons store a position and a velocity. Verlet integration (position Verlet, also called Störmer–Verlet) stores the current position and the previous position instead. The velocity is never stored. It is implied by the gap between the two.

One step is a single line:

next = current + (current - previous) + acceleration * dt * dt

In words: move the same distance you moved last step, then add the nudge that acceleration gives over one step. After that, the current position becomes the previous one, and the next becomes the current one.

Units: current - previous is in pixels, and px/s² times s² is also pixels.

Without constraints, it is semi-implicit Euler

Take the jump from earlier lessons: launch at 600 px/s, gravity 1800 px/s², 60 steps per second, height measured upward. To start Verlet with a velocity, set previous = current - velocity * dt, so previous is −10 px.

StepVerletSemi-implicit Euler
10 + 10 − 0.5 = 9.5 pxv = 570, y = 9.5 px
29.5 + 9.5 − 0.5 = 18.5 pxv = 540, y = 18.5 px
Peak95.0 px95.0 px

The two methods produce exactly the same positions. That is not a coincidence: semi-implicit Euler's velocity is always the last move divided by dt. So Verlet is just as stable, but not more accurate. (Start it with previous = current - velocity * dt + ½ · acceleration · dt² instead and the jump peaks at exactly 100 px, because Verlet is exact for constant acceleration when it starts on the true curve.)

The real difference appears when something moves a point directly.

One rope step by hand

The demo's pendulum: pivot at the origin, screen y pointing down, rope 150 px, gravity 1000 px/s², step 1/60 s. The bob hangs at (0, 150) and moved 5 px right last step, so previous is (−5, 150). That is 300 px/s.

  • Coast and fall: (0 + 5, 150 + 0 + 1000/3600) = (5, 150.278). That is 150.361 px from the pivot, too long.
  • Pull it back to 150 px along the line to the pivot: (4.988, 149.917).
  • The implied velocity is now (4.988 − 0, 149.917 − 150) × 60 = (299.3, −5.0) px/s.

The velocity has turned upward to follow the circle, and we never touched a velocity. With Euler, the stored velocity would still be (300, 16.7), pointing out of the circle, and gravity would add another 16.7 px/s to it every step. That is the dead lantern from the opening.

Stable is not the same as lossless

Snapping a point back onto a rope throws away a little of its motion every step, and more when it moves far per step. In the demo a 60° swing shrinks to about 28° after ten seconds at 60 steps per second, 15° at 30, and 48° at 240. A real pendulum would keep swinging. For ropes, chains and cloth in a game, settling down is usually what you want. If you need a pendulum that swings forever, use more steps.

Try it

Three pendulums start at the same angle and all use the same rope rule: after each step, put the bob back at 150 px from the pivot. Watch the two Euler bobs fall to the bottom and stay there while their energy shoots off the graph. The Verlet bob swings.

Then switch on Euler: also fix velocity, which removes the part of the velocity pointing along the rope after each snap. Now all three swing. Finally, drag in any picture to grab the bobs, and let go while moving. Only the Verlet bob keeps your throw, because its velocity is simply the distance your drag moved it.

The code

The Verlet pendulum as a LÖVE program, with the demo's numbers. Hold the left mouse button to drag the bob and release to throw it.

local G = 1000              -- gravity, px/s^2 (screen y points down)
local ROPE = 150            -- rope length, px
local STEP = 1 / 60         -- fixed step, seconds
local PX, PY = 400, 250     -- pivot on screen
local start = math.rad(60)  -- 60 degrees out, at rest
local bob = { x = PX + ROPE * math.sin(start), y = PY + ROPE * math.cos(start) }
bob.px, bob.py = bob.x, bob.y   -- previous = current: not moving yet
local accumulator = 0

local function verlet(b, dt)
  local mx, my = b.x - b.px, b.y - b.py   -- the last move
  b.px, b.py = b.x, b.y                   -- current becomes previous
  b.x = b.x + mx                          -- same move again
  b.y = b.y + my + G * dt * dt            -- plus the nudge from gravity
end

local function keepRopeLength(b)
  local dx, dy = b.x - PX, b.y - PY
  local d = math.sqrt(dx * dx + dy * dy)
  if d > 0 then
    b.x = PX + dx / d * ROPE              -- move it back onto the rope;
    b.y = PY + dy / d * ROPE              -- there is no velocity to fix
  end
end

local function hold(b, tx, ty, dt)        -- follow the mouse
  local follow = math.min(1, 30 * dt)
  b.px, b.py = b.x, b.y
  b.x, b.y = b.x + (tx - b.x) * follow, b.y + (ty - b.y) * follow
end

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    if love.mouse.isDown(1) then
      hold(bob, love.mouse.getX(), love.mouse.getY(), STEP)
    else
      verlet(bob, STEP)
    end
    keepRopeLength(bob)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  love.graphics.line(PX, PY, bob.x, bob.y)
  love.graphics.circle("fill", bob.x, bob.y, 10)
end
# Godot 4. Attach to a Node2D placed at the pivot.
extends Node2D

const G := 1000.0     # px/s^2, Godot's 2D y also points down
const ROPE := 150.0
var bob := Vector2.ZERO        # relative to the pivot
var previous := Vector2.ZERO

func _ready() -> void:
    var a := deg_to_rad(60.0)
    bob = Vector2(sin(a), cos(a)) * ROPE
    previous = bob

func _physics_process(delta: float) -> void:
    var moved := bob - previous
    previous = bob
    bob += moved + Vector2(0, G) * delta * delta
    bob = bob.normalized() * ROPE   # keep the rope length
    queue_redraw()

func _draw() -> void:
    draw_line(Vector2.ZERO, bob, Color.WHITE, 2.0)
    draw_circle(bob, 10.0, Color.WHITE)
// Unity works in metres and its y axis points UP, so gravity is negative y.
using UnityEngine;

public class VerletPendulum : MonoBehaviour
{
    public float gravity = 9.81f;   // m/s^2
    public float rope = 1.5f;       // m
    Vector2 bob, previous;          // relative to this object, the pivot

    void Start()
    {
        float a = 60f * Mathf.Deg2Rad;
        bob = new Vector2(Mathf.Sin(a), -Mathf.Cos(a)) * rope;
        previous = bob;
    }

    void FixedUpdate()
    {
        float dt = Time.fixedDeltaTime;
        Vector2 moved = bob - previous;
        previous = bob;
        bob += moved + Vector2.down * gravity * dt * dt;
        bob = bob.normalized * rope;   // keep the rope length
    }

    void OnDrawGizmos()
    {
        Gizmos.DrawLine(transform.position, transform.position + (Vector3)bob);
    }
}

The rigid bodies built into Godot and Unity store a velocity, and you do not choose their integrator. Verlet is what you write yourself for ropes, chains, cloth and particles, drawn with Line2D in Godot or LineRenderer in Unity.

Pitfalls

  • Teleporting only the current position. Moving a body to a spawn point without moving previous as well gives it a velocity equal to the whole jump. It will shoot off. Move both by the same offset.
  • Changing the step size. The stored gap was made with the old dt. With a new one it means a different speed, so the body speeds up or slows down. Use a fixed step. If you must change it, scale the gap: previous = current - (current - previous) * newDt / oldDt. The demo does this when you move the slider.
  • Setting a velocity. There is no velocity variable. To launch at speed v, set previous = current - v * dt.
  • Forces that need the velocity. Drag and damping read the velocity. Use (current - previous) / dt, which describes the last step rather than this one. A common shortcut for damping is to multiply the last move by a number just under 1, such as 0.99. That number is tied to your step rate.

In real games

Thomas Jakobsen's GDC 2001 paper Advanced Character Physics describes the system he built at IO Interactive for Hitman: Codename 47: particles moved with Verlet integration, then pushed around directly to satisfy stick constraints and collisions. That approach became a standard recipe for cloth, ropes and ragdolls in games.

Position Based Dynamics (Müller and colleagues, 2007) is a close relative: it corrects positions to satisfy constraints, then sets each velocity to the corrected move divided by the step.

Takeaways

  • Verlet stores the current and previous positions. One step is: repeat the last move, add acceleration times dt squared.
  • Without constraints it traces the same positions as semi-implicit Euler, so it is just as stable.
  • Its strength is constraints and collisions: move a point and its velocity follows by itself.
  • Snapping points back bleeds energy, more at low step rates. Ropes settle instead of exploding.
  • Use a fixed step, and move previous along with current when you teleport.

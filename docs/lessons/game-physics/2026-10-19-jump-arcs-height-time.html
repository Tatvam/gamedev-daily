Jump arcs from height and time

How to calculate gravity and launch speed from the jump height and time to peak you want, and why a stepped jump falls a few pixels short.

You raise the jump speed until the hero just reaches a three-tile ledge. The jump feels floaty, so you raise gravity. Now the hero misses the ledge, so you raise the jump speed again, and now the jump feels too fast. Two knobs, and every turn of one undoes the other.

This lesson replaces those two knobs with the two numbers a designer actually cares about: how high, and how long.

Two knobs that pull on each other

A jump is free fall that starts with an upward speed. Call that the launch speed, v0, in pixels per second. Gravity, g in pixels per second squared, takes g off the upward speed every second until it reaches zero at the top. The time that takes is the time to peak, T:

T = v0 / g

In words: the launch speed divided by how fast gravity eats it. The height reached by then is the jump height, h:

h = v0 * v0 / (2 * g)

In words: height grows with the square of the launch speed and shrinks as gravity grows. Both answers contain both knobs, so you cannot change the height without also changing the timing.

Turn the formulas around

Decide h and T first, then solve for the knobs. From the first line, v0 = g * T. Put that into the second line and the height becomes h = g * T * T / 2. Solve for g:

gravity = 2 * h / (T * T)

In words: twice the height, divided by the time to peak squared. The units work: px divided by s² is px/s². Then put that gravity back into v0 = g * T:

jumpSpeed = 2 * h / T

In words: twice the height, divided by the time to peak, in px/s.

One jump by hand

Tiles are 32 px. The hero should clear three tiles, so h = 96, and reach the top in T = 0.4 s:

  • gravity = 2 * 96 / (0.4 * 0.4) = 192 / 0.16 = 1200 px/s²
  • jumpSpeed = 2 * 96 / 0.4 = 480 px/s
  • Check: 480 * 480 / (2 * 1200) = 96 px, and 480 / 1200 = 0.4 s.
  • Running at 200 px/s, the jump spans 2 * 0.4 * 200 = 160 px, exactly five tiles.

Now the knobs are separate: a shorter T gives a snappier jump of the same height.

Correct is not the same as good

The 1200 px/s² this produces has nothing to do with real gravity at your pixel scale, and it does not need to. Pick the arc that feels right, and let the gravity be whatever that requires.

The catch: the game is a few pixels short

Type those numbers into the semi-implicit Euler step from earlier lessons (velocity first, then position) and print the peak. At 60 steps per second you get 92 px, not 96. Your three-tile ledge is missed by 4 px.

The reason is the order of the two lines. The first step takes 20 px/s of gravity off the launch speed before the body moves. Every stepped position is then where a body launched at 470 px/s would be, half a step of gravity slower. The peak falls short by:

shortfall = jumpSpeed * STEP / 2

In words: the launch speed times half a step. With 480 px/s and 1/60 s that is 4 px. It depends on the step size, so it changes with the physics rate:

Physics rateStepPeak as writtenWith the fix
30 per second33.3 ms88.0 px96.0 px
60 per second16.7 ms92.0 px96.0 px
120 per second8.3 ms94.0 px96.0 px

The fix is to give that half step back. Launch with:

vy = -(jumpSpeed + gravity * STEP / 2)

In words: the planned speed, plus half a step of gravity, pointing up (negative, because screen y grows downward). The first step removes a full step of gravity, so the body moves at v0 - g * STEP / 2, and every stepped position after that lands exactly on the planned parabola. Check step one: the body rises (480 - 10) / 60 = 7.83 px, and the formula 480 * t - 1200 * t * t / 2 at t = 1/60 gives 8 − 0.167 = 7.83 px. When T is a whole number of steps, the peak is exactly 96.

The code

The demo as a LÖVE program, with the same numbers. Press Space to jump. It uses the fixed step from the first lesson, because the fix relies on knowing the step size.

local JUMP_HEIGHT = 96     -- px the feet rise at the peak
local TIME_TO_PEAK = 0.4   -- s from take-off to the top
local RUN_SPEED = 200      -- px/s sideways while in the air
local STEP = 1 / 60        -- fixed physics step, s
local FLOOR_Y = 240        -- y of the feet when standing (y grows down)

-- Two design numbers in, two physics numbers out.
local gravity = 2 * JUMP_HEIGHT / (TIME_TO_PEAK * TIME_TO_PEAK)  -- 1200 px/s^2
local jumpSpeed = 2 * JUMP_HEIGHT / TIME_TO_PEAK                 -- 480 px/s

local player = { x = 40, y = FLOOR_Y, vx = 0, vy = 0, onGround = true }
local accumulator = 0

local function jump(p)
  -- Half a step of gravity extra puts every stepped position on the planned arc.
  p.vy = -(jumpSpeed + gravity * STEP / 2)   -- negative is up
  p.vx = RUN_SPEED
  p.onGround = false
end

local function step(p, dt)
  if p.onGround then return end
  p.vy = p.vy + gravity * dt       -- velocity first (semi-implicit Euler)
  p.x = p.x + p.vx * dt
  p.y = p.y + p.vy * dt
  if p.y >= FLOOR_Y then
    p.y, p.vx, p.vy = FLOOR_Y, 0, 0
    p.onGround = true
  end
end

function love.keypressed(key)
  if key == "space" and player.onGround then jump(player) end
end

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    step(player, STEP)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  love.graphics.rectangle("fill", player.x - 10, player.y - 28, 20, 28)
end
# Godot 4. +y is down, as in LÖVE.
extends CharacterBody2D

@export var jump_height := 96.0    # px
@export var time_to_peak := 0.4    # s
@export var run_speed := 200.0     # px/s

var gravity := 0.0
var jump_speed := 0.0

func _ready() -> void:
    gravity = 2.0 * jump_height / (time_to_peak * time_to_peak)
    jump_speed = 2.0 * jump_height / time_to_peak

func _physics_process(delta: float) -> void:
    if not is_on_floor():
        velocity.y += gravity * delta
    if is_on_floor() and Input.is_action_just_pressed("ui_accept"):
        # Gravity was skipped on this step, so the half step is subtracted.
        velocity.y = -(jump_speed - gravity * delta / 2.0)
    velocity.x = Input.get_axis("ui_left", "ui_right") * run_speed
    move_and_slide()
// Unity: +y is up and one unit is meant to be one metre.
using UnityEngine;

public class JumpArc : MonoBehaviour
{
    public float jumpHeight = 3f;     // units
    public float timeToPeak = 0.4f;   // s
    Rigidbody2D body;
    float gravity, jumpSpeed;
    bool jumpRequested;

    void Start()
    {
        body = GetComponent<Rigidbody2D>();
        gravity = 2f * jumpHeight / (timeToPeak * timeToPeak);
        jumpSpeed = 2f * jumpHeight / timeToPeak;
        // Scale the project gravity so this body feels exactly our gravity.
        body.gravityScale = gravity / Mathf.Abs(Physics2D.gravity.y);
    }

    void Update()
    {
        if (Input.GetButtonDown("Jump")) jumpRequested = true;   // add a ground check
    }

    void FixedUpdate()
    {
        if (!jumpRequested) return;
        jumpRequested = false;
        Vector2 v = body.linearVelocity;   // body.velocity before Unity 6
        v.y = jumpSpeed + gravity * Time.fixedDeltaTime / 2f;   // measure the peak to confirm
        body.linearVelocity = v;
    }
}

The Godot tab follows the order of Godot's CharacterBody2D script template, which adds gravity only off the floor. The take-off step gets no gravity, so the jump would overshoot instead, and the half step is subtracted. In Unity the physics engine applies gravity after FixedUpdate. I expect it to update velocity before position like the Lua code, but have not measured it, so print the peak once and flip the sign if it overshoots.

Pitfalls

  • Ignoring the half step, or applying it with the wrong sign. Velocity-first code falls short by jumpSpeed * STEP / 2. Position-first code, or code that skips gravity on the take-off step, overshoots by about the same amount. Measure the peak once and you will know which you have.
  • A variable timestep. The shortfall depends on the step, so with a variable step the jump height changes with the frame rate.
  • Getting the sign wrong. In LÖVE and Godot 2D, up is negative y, so the launch velocity is negative and gravity is positive. In Unity it is the other way round.
  • No margin. h is how far the feet rise. To land on a 96 px ledge, plan a little more than 96 px.
  • Sharing the jump gravity with everything. A good jump gravity may be too strong for crates and debris. Keep it on the character.

In real games

Kyle Pittman's GDC talk "Building a Better Jump" (2016) presents this same derivation for platformers: choose the height and the time or distance to the peak, and calculate gravity and launch speed from them. It also covers a stronger gravity on the way down.

Godot's CharacterBody2D script template starts you with a speed and a jump velocity constant, and Unity's Rigidbody2D has a gravity scale. These are the raw knobs from the start of this lesson; the formulas set them from a design.

Your turn (15 minutes)

In your platformer, replace the jump velocity and gravity settings with a jump height and a time to peak, and calculate the old two from them. Print the highest point of each jump, at the feet.

If the printed height is short or long by about jumpSpeed * step / 2, add the half-step correction with the right sign. You are done when the printed peak matches the height you typed to within one pixel, and changing the time to peak changes the feel without changing the peak.

Takeaways

  • Gravity and launch speed each change both the height and the timing of a jump, so tune height and time to peak instead.
  • gravity = 2 * h / (T * T) and jumpSpeed = 2 * h / T.
  • On flat ground the jump lasts 2T and covers 2T times the run speed.
  • A velocity-first step makes the jump fall short by jumpSpeed * STEP / 2; launching half a step of gravity faster puts every step on the planned arc.
  • The gravity a good jump needs is a design choice, not a physical constant.

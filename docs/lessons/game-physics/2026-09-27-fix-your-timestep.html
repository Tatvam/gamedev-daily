Fix your timestep

Why physics tied to the frame rate behaves differently on every machine, and how a fixed timestep with an accumulator makes it the same everywhere.

On your computer the hero's jump just reaches the ledge. On a friend's older laptop the same jump falls short, and the level cannot be finished. Nobody changed the code. The only difference is how many frames per second each machine draws.

If the frame rate can change what happens in your game, the frame rate is part of your game rules. This lesson takes it back out.

Multiplying by delta time is not enough

A game advances in small jumps of time. Each jump is a step, and its length in seconds is the timestep, usually written dt. The common approach is to measure how long the last frame took and use that as the timestep:

velocity += gravity * dt;
position += velocity * dt;

This is a variable timestep: a fast machine takes many small steps, a slow machine takes a few large ones. For an object moving at constant speed the result is the same either way, which is why this looks correct at first.

It stops being the same as soon as the speed changes during the step. Under gravity the velocity changes continuously, but the code only updates it once per step and then treats it as constant until the next one. Every step is a small approximation, and the size of the error depends on the size of the step.

The numbers

Take a jump with a launch speed of 600 pixels per second and gravity of 1800 pixels per second squared. On paper the peak is exactly 100 pixels. Here is what the two lines of code above produce:

Jump height is only the visible symptom. With large steps, fast objects move further per step and skip through thin walls, and stiff springs overshoot and explode. All of these come from the same cause: the step size is decided by the machine, not by you.

The fix: choose the step yourself

With a fixed timestep the simulation always advances by the same amount, for example one sixtieth of a second. The frame rate no longer decides how big a step is. It only decides how many steps to run before drawing.

The bookkeeping is done with an accumulator: a number holding time that has passed in the real world but has not been simulated yet.

  1. At the start of each frame, add the frame's duration to the accumulator.
  2. While the accumulator holds at least one step's worth of time, run one step and subtract the step from the accumulator.
  3. Draw. Whatever is left in the accumulator stays there for the next frame.

Two details that make it production ready

Cap the frame time. If one frame takes a full second, the loop will try to run 60 steps in the next frame. If those steps are slow, that frame takes even longer, and the next one needs even more steps. This is often called the spiral of death. Capping the time added to the accumulator, for example at a quarter of a second, means the game slows down briefly instead of freezing.

Interpolate when drawing. The leftover time in the accumulator means the screen is drawn somewhere between two steps. If you draw the latest step as it is, motion shows a small stutter whenever the frame rate and the step rate do not line up. The cure is to remember the previous state and blend: alpha = accumulator / step, then draw at previous + (current - previous) * alpha.

The code

The whole pattern is one loop. If you write your own engine or use a framework that only gives you a per-frame callback, this is what you add. Godot and Unity already contain this loop, so there the job is to put your physics code in the callback that it drives.

const STEP = 1 / 60;        // seconds per simulation step
const MAX_FRAME = 0.25;     // never simulate more than this per frame
let accumulator = 0;
let last = performance.now();

function frame(now) {
  const frameTime = Math.min((now - last) / 1000, MAX_FRAME);
  last = now;

  accumulator += frameTime;
  while (accumulator >= STEP) {
    previous = copy(current);   // kept for interpolation
    simulate(current, STEP);    // always the same step
    accumulator -= STEP;
  }

  const alpha = accumulator / STEP;
  draw(blend(previous, current, alpha));
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
# Godot runs the accumulator loop for you.
# _physics_process is called at a fixed rate: 60 times per second by default
# (Project Settings > Physics > Common > Physics Ticks per Second).

func _physics_process(delta: float) -> void:
    velocity.y += gravity * delta   # delta is the fixed step here
    move_and_slide()

# _process(delta) runs once per drawn frame. Keep visuals and UI there,
# and keep anything that affects gameplay out of it.
// Unity runs the accumulator loop for you.
// FixedUpdate is called at a fixed rate: every 0.02 s (50 per second) by default
// (Project Settings > Time > Fixed Timestep).

void FixedUpdate()
{
    body.AddForce(Vector2.down * extraGravity);   // physics goes here
}

void Update()
{
    // Runs once per drawn frame. Read input here and remember it
    // until the next FixedUpdate uses it.
    if (Input.GetButtonDown("Jump")) jumpRequested = true;
}

Both engines can also interpolate for you. In Unity, set Interpolate on the Rigidbody. Godot 4.3 and later have a physics interpolation option in the project settings.

Pitfalls

  • Reading button presses inside the fixed step. A "was pressed this frame" check is true for one drawn frame. On a fast machine some frames run no step at all, so the press is never seen. Read input every frame, store it, and let the next step consume it.
  • Using the frame time inside the fixed step. Inside the step, the timestep is the fixed step. Mixing in the frame's own duration brings the original bug straight back.
  • No cap on frame time. Switching windows, hitting a breakpoint or loading a level produces one huge frame. Without a cap the game tries to simulate all of it at once.
  • Steps that cost more than they simulate. If one step of 16 ms takes 20 ms to compute, the simulation can never catch up. Make the step cheaper or the step size larger.
  • Expecting identical results on every machine. A fixed step makes the game behave the same at every frame rate. Bit-for-bit identical results across different processors is a harder problem, and a fixed step is only its first requirement.

In real games

Both engines used in these lessons are built this way. Godot calls _physics_process on a fixed tick, 60 per second by default. Unity calls FixedUpdate on a fixed tick, 50 per second by default, and its built-in physics advances on the same tick.

The pattern is also the foundation of multiplayer techniques such as lockstep and rollback, which need every player's simulation to take the same steps in the same order.

You can recognise games that skipped this lesson: when players remove the frame rate limit, physics speeds up, jumps change height, or objects start to shake.

Open a project where a character jumps. Print the highest point of each jump. Limit the game to 30 frames per second and write the number down, then remove the limit and compare.

If the two numbers differ, find the movement code that runs once per drawn frame and move it into the fixed callback (_physics_process or FixedUpdate), or wrap it in the accumulator loop above. You are done when both frame rates print the same peak.

Takeaways

  • Multiplying by delta time only makes constant motion independent of frame rate. Anything that accelerates still depends on the step size.
  • A fixed timestep makes the step size your decision. The frame rate only changes how many steps run per frame.
  • The accumulator carries unsimulated time from one frame to the next, so no time is lost or invented.
  • Cap the frame time to survive long frames, and interpolate between the last two states to draw smoothly.
  • Gameplay belongs in the fixed step. Visuals and input reading belong in the frame.

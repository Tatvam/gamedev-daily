Static, kinematic and dynamic bodies

How static, kinematic and dynamic bodies differ, which one to pick for floors, platforms, players and crates, and why a kinematic body must move by velocity.

You build a moving platform by changing its position a little every frame. The crate on top does not ride along: the platform slides out from under it and the crate drops.

Then you make the hero a rigid body, and the first crate that lands on him knocks him over. Both bugs have the same cause: the wrong kind of body, or the right kind moved the wrong way.

One question: who moves this body?

A physics engine sorts every body into one of three kinds, by who may change where it goes.

  • A static body never moves. Floors, walls and level geometry.
  • A kinematic body moves only at the velocity your code gives it. Gravity and collisions do not change that velocity. Moving platforms, doors, elevators, and often the player.
  • A dynamic body is moved by the simulation: gravity, forces and collisions all change its velocity. Crates, balls, debris.

The solver only sees inverse mass and velocity

In the earlier lessons on impulses, a collision changed each body's velocity like this:

v = v + j * inv

In words: the push j changes the velocity in proportion to the inverse mass inv, which is 1 divided by the mass. Give a body an inverse mass of 0 and no push can ever change its velocity. That is how both static and kinematic bodies get their infinite mass, with no special case in the solver.

So what separates them? Only the velocity. A static body's velocity is always 0. A kinematic body's velocity is whatever your code set, and the solver uses it when it works out how fast two bodies close in on each other. That is how a platform shoves a crate and carries it by friction.

One more rule follows. When both bodies in a pair have inverse mass 0, the push formula divides by 0 + 0. Neither body could move anyway, so engines skip those pairs: a kinematic body passes straight through walls, floors and other kinematic bodies.

The teleport bug

Because the solver reads a kinematic body's velocity, you must move it by velocity. If you write its position directly, it teleports: it arrives at the new place, but its velocity is still 0. The solver thinks it is standing still. A crate on top feels no friction, so the platform slides out from under it. A crate in its way is not shoved, only pushed out of the overlap bit by bit.

The fix: set the velocity that reaches the target in one step:

vx = (targetX - x) / dt

In words: the gap to the target, divided by the step time. With the target 10 pixels to the right and a step of 1/60 s, vx = 10 × 60 = 600 px/s. The integrator then moves the body exactly those 10 pixels, and the solver knows it was moving at 600 px/s while it did.

Game answer, not physics answer

A real person is a dynamic body: pushed by crates, toppled by a hit. Players rarely want that. Platformer heroes are usually kinematic, so speed and jump arc are exactly what the designer chose. Make something dynamic when you want the simulation to surprise you.

The code

This is the demo's physics with the same numbers, minus the walls, the keys, throwing and the mouse spring. The body kind is used in three places only: whether gravity applies, which pairs are tested, and whether position is integrated. Everything else follows from the inverse mass.

A check by hand for one step: a dynamic crate at rest gains 1000 × 1/60 ≈ 16.7 px/s downward; a kinematic box gains nothing. A crate resting on top gets a normal push of about 16.7 per step, so friction changes its speed by at most 0.6 × 16.7 ≈ 10 px/s per step: it catches a box moving at 100 px/s in about 10 steps. When a crate thrown at 600 px/s hits the dynamic box of mass 4, the push is 600 / (1 + 1/4) = 480. The box gains 480 × 1/4 = 120 px/s and the crate keeps 600 − 480 = 120 px/s (floor friction on the box then cuts that; in the demo it peaks near 70). Against the kinematic box the push is 600 / (1 + 0) = 600, so the crate stops and the box gains 600 × 0 = 0.

local GRAVITY    = 1000    -- pixels per second squared, +y is down
local STEP       = 1 / 60
local ITERATIONS = 8
local FRICTION   = 0.6
local STRENGTH   = 0.2     -- share of the overlap pushed out per step
local SLOP       = 0.5     -- pixels of overlap left alone

local function newBody(kind, x, y, w, h, mass)
  local b = { kind = kind, x = x, y = y, w = w, h = h, vx = 0, vy = 0 }
  b.inv = 0                                   -- static and kinematic: infinite mass
  if kind == "dynamic" then b.inv = 1 / mass end
  return b
end

local function findContact(a, b)
  local dx, dy = b.x - a.x, b.y - a.y
  local ox = (a.w + b.w) / 2 - math.abs(dx)
  local oy = (a.h + b.h) / 2 - math.abs(dy)
  if ox <= 0 or oy <= 0 then return nil end
  local c = { a = a, b = b, nx = 0, ny = 0, depth = oy, jn = 0, jt = 0 }
  if ox < oy then
    c.depth = ox
    if dx < 0 then c.nx = -1 else c.nx = 1 end
  else
    if dy < 0 then c.ny = -1 else c.ny = 1 end
  end
  return c
end

local function applyPush(c, j, ux, uy)      -- j along direction (ux, uy)
  c.a.vx = c.a.vx - j * c.a.inv * ux
  c.a.vy = c.a.vy - j * c.a.inv * uy
  c.b.vx = c.b.vx + j * c.b.inv * ux
  c.b.vy = c.b.vy + j * c.b.inv * uy
end

local function solve(c, dt)
  local inv = c.a.inv + c.b.inv
  -- Normal: uses the kinematic body's velocity, which is why it shoves.
  local vn = (c.b.vx - c.a.vx) * c.nx + (c.b.vy - c.a.vy) * c.ny
  local push = STRENGTH * math.max(c.depth - SLOP, 0) / dt
  local old = c.jn
  c.jn = math.max(old + (push - vn) / inv, 0)
  applyPush(c, c.jn - old, c.nx, c.ny)
  -- Friction along the surface: this is what carries a rider.
  local tx, ty = -c.ny, c.nx
  local vt = (c.b.vx - c.a.vx) * tx + (c.b.vy - c.a.vy) * ty
  local limit = FRICTION * c.jn
  old = c.jt
  c.jt = math.min(math.max(old - vt / inv, -limit), limit)
  applyPush(c, c.jt - old, tx, ty)
end

local function step(bodies, dt)
  for _, b in ipairs(bodies) do
    if b.kind == "dynamic" then b.vy = b.vy + GRAVITY * dt end
  end
  local contacts = {}
  for i = 1, #bodies do
    for j = i + 1, #bodies do
      local a, b = bodies[i], bodies[j]
      if a.inv + b.inv > 0 then               -- two unmovable bodies never collide
        local c = findContact(a, b)
        if c then contacts[#contacts + 1] = c end
      end
    end
  end
  for pass = 1, ITERATIONS do
    for _, c in ipairs(contacts) do solve(c, dt) end
  end
  for _, b in ipairs(bodies) do
    if b.kind ~= "static" then               -- kinematic bodies move too
      b.x = b.x + b.vx * dt
      b.y = b.y + b.vy * dt
    end
  end
end

-- Kinematic: choose the velocity that reaches the target in one step.
-- Never write box.x directly: that is the teleport bug.
local function driveKinematic(b, targetX, targetY, dt)
  b.vx = (targetX - b.x) / dt
  b.vy = (targetY - b.y) / dt
end

local floor = newBody("static", 320, 330, 800, 60, 0)     -- top edge at y = 300
local box   = newBody("kinematic", 320, 200, 100, 40, 4)
local crate = newBody("dynamic", 320, 163, 30, 30, 1)
local bodies = { floor, box, crate }
local accumulator = 0

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    local mx, my = love.mouse.getPosition()
    driveKinematic(box, mx, my, STEP)
    step(bodies, STEP)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  for _, b in ipairs(bodies) do
    love.graphics.rectangle("line", b.x - b.w / 2, b.y - b.h / 2, b.w, b.h)
  end
end
# Godot 4 gives each kind its own node type:
#   StaticBody2D      static
#   AnimatableBody2D  kinematic, for platforms and doors moved by code or animation
#   CharacterBody2D   kinematic, moved with move_and_slide()
#   RigidBody2D       dynamic (set freeze and freeze_mode to make it static or kinematic)
extends AnimatableBody2D

@export var target := Vector2(400, 200)

func _physics_process(delta: float) -> void:
    # Moved inside the physics step, so Godot works out its velocity
    # and bodies it touches are pushed and carried.
    position = position.move_toward(target, 100.0 * delta)
// Unity 2D: one component, three body types.
// A Collider2D with no Rigidbody2D at all also counts as static.
using UnityEngine;

public class Platform : MonoBehaviour
{
    public Vector2 target = new Vector2(4f, 2f);
    Rigidbody2D body;

    void Awake()
    {
        body = GetComponent<Rigidbody2D>();
        body.bodyType = RigidbodyType2D.Kinematic;   // or Dynamic, Static
    }

    void FixedUpdate()
    {
        // MovePosition gives the body the velocity that reaches the point
        // during the next physics step. Writing transform.position teleports it.
        Vector2 next = Vector2.MoveTowards(body.position, target, 1f * Time.fixedDeltaTime);
        body.MovePosition(next);
    }
}

In Godot, moving a StaticBody2D by changing its position is the teleport bug; that is what AnimatableBody2D is for. In Unity 3D the same three choices are a Rigidbody with isKinematic off, a Rigidbody with isKinematic on, and a collider with no Rigidbody.

Pitfalls

  • Teleporting a kinematic or static body. Writing the position leaves the velocity at 0, so riders are left behind. Move it by velocity, or with the engine call made for it.
  • Expecting a kinematic body to stop at walls. It has no contact with static bodies, so it walks through them. A kinematic character needs its own collision code.
  • Crushing. A kinematic body pushes with infinite strength. Pin a crate between it and a wall and the solver cannot satisfy both contacts: the crate jitters, squeezes through, or is flung out.
  • Making everything dynamic. Every dynamic body costs solver time and can be knocked around. Level geometry should be static, which engines never integrate.

In real games

Box2D, the engine under Unity's 2D physics and LÖVE's love.physics, has exactly these three kinds. In LÖVE you pass "static", "kinematic" or "dynamic" to love.physics.newBody. The Box2D manual states that kinematic bodies do not collide with static or other kinematic bodies.

Godot splits the kinematic idea in two: CharacterBody2D for things you steer, and AnimatableBody2D for platforms and doors that push whatever is in the way.

Your turn (15 minutes)

Make a platform that moves left and right between two points, and put a crate on it. First move it by writing its position every frame and watch the crate get left behind. Then move it by velocity: driveKinematic in LÖVE, AnimatableBody2D in Godot, MovePosition on a kinematic Rigidbody2D in Unity.

You are done when the crate rides back and forth without sliding off.

Takeaways

  • Static never moves, kinematic moves at the velocity your code sets, dynamic is moved by the simulation.
  • Static and kinematic bodies both have inverse mass 0, so no collision can change their velocity. The only difference is that a kinematic body can have one.
  • Pairs where both bodies have inverse mass 0 are never solved, so kinematic bodies pass through walls.
  • Move kinematic bodies by velocity, never by writing the position, or they cannot push or carry anything.

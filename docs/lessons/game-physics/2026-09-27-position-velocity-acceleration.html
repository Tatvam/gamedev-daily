Position, velocity and acceleration

How acceleration changes velocity, velocity changes position, and how two lines of code per step turn that chain into motion.

You add gravity to a thrown rock and it does not arc. It drops as if yanked to the floor, and throwing harder barely matters. Or your spaceship is at full speed the moment you press a key and dead still the moment you let go.

Both come from changing the wrong number, or the right number by the wrong amount. This lesson sorts out which is which.

Three numbers, each one changing the next

Every moving thing in a 2D game carries three pairs of numbers, one for x and one for y.

  • Position is where the object is, in pixels.
  • Velocity is how fast the position changes, in pixels per second. It has a direction and a size, and the size is the object's speed.
  • Acceleration is how fast the velocity changes, in pixels per second, per second. That is written px/s² and said "pixels per second squared".

They form a chain. To make something move, set a velocity and let it move the position. To make something fall, set an acceleration and let it bend the velocity.

The two lines

The game advances in fixed steps of dt seconds, as set up in the previous lesson. Each step runs two lines. The first one:

velocity = velocity + acceleration * dt

In words: during this step, the velocity changes by the acceleration times the length of the step. With gravity of 400 px/s² and steps of one sixtieth of a second, the ball gains 6.67 px/s of downward speed every step.

The second one:

position = position + velocity * dt

In words: during this step, the object moves by its velocity times the length of the step. A ball moving at 200 px/s moves 3.33 pixels per step.

Check the units, because they catch real bugs. (px/s²) × s = px/s, a velocity, so it can be added to a velocity. (px/s) × s = px, which can be added to a position. Leave out dt in the first line and you add px/s² to px/s: the units do not match, and at 60 steps per second the acceleration comes out 60 times too strong.

With dt, the upward speed shrinks a little each step and the ball keeps rising for 0.75 seconds. Without it, the very first step flips the ball's velocity to downward. That is the rock that refuses to arc.

Mind the sign of y

In LÖVE and in Godot 2D, y grows downwards, so gravity is a positive y acceleration and an upward throw has a negative y velocity. In Unity y grows upwards and gravity is negative.

Reading a path from two arrows

Draw the velocity and the acceleration as arrows and you can predict the path before it happens:

  • No acceleration: a straight line at constant speed.
  • Acceleration pointing the same way as the velocity: a straight line that speeds up.
  • Acceleration pointing against the velocity: the object slows, stops for an instant, and comes back.
  • Acceleration at an angle: the path bends towards the acceleration. With constant acceleration the bend is a parabola.

Feel beats realism

A real object can never change its velocity instantly. Many games do it anyway for the player, setting velocity straight from input, because instant response feels better than realistic weight. That is a fine choice for a character. For a rock, a car or a spaceship, let acceleration do the work, or it will feel like a cursor instead of an object.

Note the order: velocity first, then position with the new velocity. Swapping the lines behaves worse; a later lesson explains why.

The code

The demo's default throw as a complete LÖVE program. The two lines live in step, inside the fixed timestep loop from the previous lesson.

local STEP = 1 / 60

local ball = {
  x = 120, y = 220,     -- position, pixels
  vx = 200, vy = -300,  -- velocity, pixels per second (negative y is up)
  ax = 0, ay = 400,     -- acceleration, pixels per second squared
}
local accumulator = 0

local function step(b, dt)
  b.vx = b.vx + b.ax * dt   -- acceleration changes velocity
  b.vy = b.vy + b.ay * dt
  b.x = b.x + b.vx * dt     -- velocity changes position
  b.y = b.y + b.vy * dt
end

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    step(ball, STEP)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  love.graphics.circle("fill", ball.x, ball.y, 10)
  -- debug drawing: where the ball would be in 0.25 s at this velocity
  love.graphics.line(ball.x, ball.y, ball.x + ball.vx * 0.25, ball.y + ball.vy * 0.25)
end
# Godot 4, on a CharacterBody2D. y grows downwards, as in LÖVE.
extends CharacterBody2D

var acceleration := Vector2(0, 400)

func _ready() -> void:
    velocity = Vector2(200, -300)

func _physics_process(delta: float) -> void:
    velocity += acceleration * delta
    move_and_slide()   # moves by velocity * delta and handles collisions
// Unity: y grows upwards and units are usually metres, so gravity is negative.
using UnityEngine;

public class Mover : MonoBehaviour
{
    public Vector2 velocity = new Vector2(2f, 3f);        // metres per second
    public Vector2 acceleration = new Vector2(0f, -4f);   // metres per second squared

    void FixedUpdate()
    {
        velocity += acceleration * Time.fixedDeltaTime;
        transform.position += (Vector3)(velocity * Time.fixedDeltaTime);
    }
}

In Godot, move_and_slide does the position line for you. In Unity, a Rigidbody2D runs both lines itself every physics step, gravity included; you steer it with its velocity or AddForce instead of moving its transform.

The demo's dashed path runs the same step ahead on a copy of the ball, so the preview cannot disagree with the real flight:

local function predict(b, seconds)
  local ghost = { x = b.x, y = b.y, vx = b.vx, vy = b.vy, ax = b.ax, ay = b.ay }
  local points = {}
  for i = 1, math.floor(seconds / STEP) do
    step(ghost, STEP)
    points[#points + 1] = ghost.x
    points[#points + 1] = ghost.y
  end
  return points   -- love.graphics.line(points) draws it
end

Pitfalls

  • Forgetting dt on the acceleration. The demo's bug toggle. Gravity becomes 60 times stronger at 60 steps per second, and changes again if the step rate changes. Every line should add like units to like.
  • Speeds measured per frame. Write every speed in pixels per second and multiply by dt. 5 pixels per frame at 60 frames per second is 300 px/s.
  • Mixing up which way y points. Code copied from a y-up engine into a y-down one makes gravity push upwards. Write the direction in a comment next to your gravity constant.
  • Moving objects by setting their position. Teleporting a body throws away its velocity, so it carries no momentum into a jump or a collision. Give it a velocity instead.

In real games

Godot's CharacterBody2D stores a velocity in pixels per second, and move_and_slide turns it into movement each physics tick. Unity's Rigidbody2D keeps a velocity and adds gravity to it every fixed step, with gravity set in the project's 2D physics settings.

An aiming line for a thrown object can be drawn the way the demo draws its dashed path: step a copy forward with the same code, and the line matches the real flight.

Takeaways

  • Acceleration changes velocity, and velocity changes position. Each step: v = v + a * dt, then p = p + v * dt.
  • Check units: px/s² times s gives px/s, and px/s times s gives px. A line that adds different units is a bug.
  • Constant acceleration makes velocity change in a straight line and position follow a parabola.
  • The path bends towards the acceleration. Drawing both arrows makes motion bugs easy to see.
  • Know which way y points in your engine before you pick the sign of gravity.

Semi-implicit Euler integration

Why updating velocity before position keeps orbits, springs and swings stable, for exactly the same cost as explicit Euler.

In the last lesson a moon on a perfect circular orbit spiralled away from its planet, pushed by nothing but the order of two lines of code. At 60 steps per second it had gained half the energy it needed to escape after ten orbits.

Swap those two lines and the same moon, at the same step size, stays on its circle for as long as you care to watch.

Turn first, then move

Explicit Euler moved the body with the velocity it had at the start of the step, then updated the velocity. Semi-implicit Euler does the same two things in the other order:

velocity = velocity + acceleration * dt

In words: first let the forces change the velocity, using the acceleration at the start of the step.

position = position + velocity * dt

In words: then move with the velocity you have just updated, the one from the end of the step.

It is "semi" implicit because only half of the update looks ahead: the position uses the new velocity, but the acceleration still comes from the old position. You will also see it called symplectic Euler or the Euler-Cromer method. Same idea, three names.

The cost is identical: one force calculation and four multiply-adds per body in 2D. Only the order changes.

Why the order matters

On a curve, explicit Euler steps along the old velocity, which points along the tangent, so it lands outside the circle. Its speed also grows, because the gravity nudge arrives at a right angle. Both errors push the energy up.

Semi-implicit Euler bends the velocity toward the planet before moving. The step now cuts slightly inside the circle. The speed still grows by the same tiny amount, but the moon is also a little closer to the planet, deeper in the gravity well. The extra speed adds energy and the lower position removes almost exactly the same amount.

One step by hand

The demo's numbers again: GM = 1,000,000 px³/s², the moon 100 px right of the planet, moving 100 px/s straight down the screen, one step of 1/60 s. The pull at 100 px is 1,000,000 / 100² = 100 px/s², toward the planet.

The velocity update is the same in both. The only difference is the x position: semi-implicit Euler moved by the new x velocity, −1.667 × 1/60 = −0.028 px, so it ends 0.0139 px inside the circle instead of 0.0139 px outside. Energy, as before, is E = ½ · speed² − GM / r. The speed part rose by about 1.39. The height part fell by about GM / r² × 0.0139 = 100 × 0.0139 = 1.39. They cancel.

Wobble instead of drift

Semi-implicit Euler is not more accurate per step. Its position is still off by about the same amount; the orbit becomes a slightly squashed circle. What changes is that the error does not pile up. Here is the worst energy error over ten orbits, starting 100 px out:

The semi-implicit energy rises a little and falls back every orbit. After a hundred orbits at 60 steps per second the worst error is still 0.03%. Explicit Euler would have long since left the screen.

Feel beats realism

A game rarely needs the exact position of a moon. It needs the moon to keep orbiting, the spring to keep bouncing at the same height, the rope to stop swinging instead of whipping harder. Semi-implicit Euler gives up nothing in cost to get that, which is why it is the default in most game physics code.

The same swap on a spring and a jump

A spring that swings once per second, started 100 px from rest and stepped at 60 per second, swings out to about 2,570 px after ten seconds with explicit Euler. With semi-implicit Euler it is still swinging to about 100 px.

The jump from the timestep lesson (launch 600 px/s, gravity 1800 px/s²) peaks at 95 px instead of the designed 100 px: 5 px low, where explicit Euler was 5 px high. For straight-line motion under constant gravity, neither order is exact; they are wrong by the same amount in opposite directions. The 5 px is fixed for a given step, so you can tune around it.

The code

The right-hand moon as a LÖVE program, with the demo's constants. Compare the highlighted function with explicitEuler from the previous lesson: the same four lines, in a different order.

local GM = 1000000          -- planet strength, px^3/s^2
local STEP = 1 / 60         -- fixed step, seconds
local CX, CY = 400, 300     -- planet position on screen
local moon = { x = 100, y = 0, vx = 0, vy = 100 }   -- relative to the planet
local accumulator = 0

local function gravity(x, y)
  local r = math.sqrt(x * x + y * y)
  local pull = GM / (r * r)              -- px/s^2, toward the planet
  return -x / r * pull, -y / r * pull
end

local function energy(b)
  local r = math.sqrt(b.x * b.x + b.y * b.y)
  return 0.5 * (b.vx * b.vx + b.vy * b.vy) - GM / r
end

local function semiImplicitEuler(b, dt)
  local ax, ay = gravity(b.x, b.y)       -- acceleration at the start of the step
  b.vx = b.vx + ax * dt                  -- change the velocity FIRST
  b.vy = b.vy + ay * dt
  b.x = b.x + b.vx * dt                  -- then move with the NEW velocity
  b.y = b.y + b.vy * dt
end

local startEnergy = energy(moon)         -- -5000

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    semiImplicitEuler(moon, STEP)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  love.graphics.circle("fill", CX, CY, 16)
  love.graphics.circle("fill", CX + moon.x, CY + moon.y, 5)
  local gained = (energy(moon) - startEnergy) / -startEnergy * 100
  love.graphics.print(string.format("energy gained: %.3f%%", gained), 10, 10)
end
# Godot 4, hand-written movement on a Node2D.
extends Node2D

const GM := 1000000.0
var planet := Vector2(400, 300)
var velocity := Vector2(0, 100)

func _physics_process(delta: float) -> void:
    var offset := position - planet
    var accel := -offset.normalized() * GM / offset.length_squared()
    velocity += accel * delta      # velocity first
    position += velocity * delta   # then position, with the new velocity

# The usual CharacterBody2D pattern is already in this order:
#   velocity.y += gravity * delta
#   move_and_slide()   # moves using the velocity you just changed
// Unity, hand-written movement in FixedUpdate.
public float gm = 1000000f;
public Vector2 planet = Vector2.zero;
Vector2 velocity = new Vector2(0f, 100f);

void FixedUpdate()
{
    float dt = Time.fixedDeltaTime;
    Vector2 offset = (Vector2)transform.position - planet;
    Vector2 accel = -offset.normalized * gm / offset.sqrMagnitude;
    velocity += accel * dt;                           // velocity first
    transform.position += (Vector3)(velocity * dt);   // then position
}

// A Rigidbody2D does this for you: add forces with AddForce
// and the physics engine integrates them.

Unity works in metres, so a real scene would use a much smaller gm. In both engines, a body driven by the physics engine is integrated for you; the order only becomes your job when you write the movement yourself.

Pitfalls

  • Computing the force after moving. The acceleration must come from the position at the start of the step. If you move first and then sample the force, you have quietly written a different method.
  • Mixing orders in one game. If the player uses one order and enemies use the other, the same jump numbers give peaks 10 px apart at 60 steps per second. Write the step in one function and call it everywhere.
  • Expecting it to be stable at any step. Bounded energy holds only while the step is small next to the fastest motion. A spring stepped with semi-implicit Euler stays stable only while its angular frequency times the step is below 2, about three steps per swing. Very stiff springs still explode.
  • Forces that depend on velocity. Drag and damping read the velocity. Use the velocity from the start of the step when computing them, before you overwrite it.

In real games

Box2D updates every body's velocity from its forces first and then moves it with the new velocity; its author, Erin Catto, describes this as symplectic Euler. Unity's 2D physics is built on Box2D.

Hand-written character code usually lands on this order by habit: add gravity to the velocity, then move. Godot's CharacterBody2D pattern of changing velocity and then calling move_and_slide() is the same order.

Takeaways

  • Semi-implicit Euler updates velocity first, then moves with the new velocity. Same cost as explicit Euler.
  • Its per-step error is about the same size, but on orbits and springs the energy wobbles around the right value instead of climbing.
  • For a jump it lands as far below the designed peak as explicit Euler lands above it.
  • It is stable only while the step is small compared with the fastest motion. Stiff springs still need small steps.
  • Pick one order, put it in one function, and use it for every body.

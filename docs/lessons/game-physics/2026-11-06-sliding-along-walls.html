Sliding along walls

How removing only the part of a velocity that points into a surface lets a body glide along a wall instead of stopping dead or sticking.

You hold up and right, the character walks diagonally into a wall, and it freezes. You are still pushing up, there is nothing above you, yet the character will not move until you let go of right. The wall feels like glue.

The collision code threw away the whole velocity when it only needed to throw away part of it. This lesson shows which part.

The bug: stopping on contact

The simplest collision response is "if I hit something, stop": set the velocity to zero, or undo the move. Both throw away the motion that was heading somewhere free, so diagonal movement into a wall dies and a jump that brushes a wall stops in mid-air.

The wall only blocks motion into it. Motion along it is none of the wall's business.

Split the velocity in two

Every contact comes with a contact normal n: a vector of length 1 that points out of the surface, towards the body. Any velocity v can be split into two parts that add back up to v:

  • The normal part, which points straight along n, into or out of the wall.
  • The tangent part, which runs along the surface.

The dot product measures the first one:

into = vx * nx + vy * ny      -- v · n

In words: into is how fast the body moves in the direction the wall faces. Negative means it is moving into the wall. Positive means it is moving away. Zero means it moves exactly along the surface.

The normal part is that speed along the normal direction, (v · n) n. Subtract it and what remains is the tangent part:

vx = vx - into * nx
vy = vy - into * ny           -- v - (v · n) n

In words: take away the motion that points into the wall, keep everything else. The result is the velocity that slides.

One step by hand

A ball moves at v = (200, -150) pixels per second. Screen y grows downwards, as in LÖVE, so the ball is heading right and up. Its speed is 250. It hits a vertical wall on its right, whose normal points left: n = (-1, 0).

  1. into = 200 × -1 + -150 × 0 = -200. Negative, so it is moving into the wall.
  2. vx = 200 - (-200 × -1) = 0 and vy = -150 - (-200 × 0) = -150.

The ball now moves straight up at 150 pixels per second, 2.5 pixels per step at 60 steps per second. The 200 pixels per second into the wall are gone; the 150 along it are untouched.

Only when moving into the surface

The check into < 0 matters. Without it, a body standing against a wall that tries to walk away would have its "away" speed removed too, and it could never leave. The wall would be glue again, from the other side.

Sliding is a bounce with no bounce

The restitution lesson reflected the normal part: v - (1 + e)(v · n) n. Set the restitution e to 0 and you get exactly the slide formula. With e = 1 it is a perfect mirror bounce. A frictionless, non-bouncy wall in real physics does the same thing, so here the physics answer and the game answer agree.

Where games part from physics: keeping the speed

Sliding loses speed: a shallow hit barely slows you, a nearly head-on hit almost stops you. That is physically right, but some games rescale the slid velocity back to the original speed so brushing a wall never feels sluggish. It is a design choice with a sharp edge, which the demo lets you find.

The code

A ball against one wall, stepped with a fixed timestep. The wall is a point on its surface and a unit normal, so it can face any direction. The numbers match the demo's starting setup.

local STEP = 1 / 60
local RADIUS = 14
local wall = { x = 400, y = 170, nx = -1, ny = 0 }   -- a point on the wall, unit normal
local ball = { x = 240, y = 270, vx = 200, vy = -150 }
local accumulator = 0

-- Remove the part of (vx, vy) that points into a surface with normal (nx, ny).
local function slide(vx, vy, nx, ny)
  local into = vx * nx + vy * ny          -- v . n
  if into >= 0 then
    return vx, vy                          -- moving away or along: leave it
  end
  return vx - into * nx, vy - into * ny
end

local function step(dt)
  ball.x = ball.x + ball.vx * dt
  ball.y = ball.y + ball.vy * dt
  local d = (ball.x - wall.x) * wall.nx + (ball.y - wall.y) * wall.ny
  if d < RADIUS then
    ball.x = ball.x + wall.nx * (RADIUS - d)   -- push out of the wall
    ball.y = ball.y + wall.ny * (RADIUS - d)
    ball.vx, ball.vy = slide(ball.vx, ball.vy, wall.nx, wall.ny)
  end
end

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    step(STEP)
    accumulator = accumulator - STEP
  end
end

function love.draw()
  local tx, ty = -wall.ny, wall.nx                 -- direction along the wall
  love.graphics.line(wall.x - tx * 1000, wall.y - ty * 1000,
                     wall.x + tx * 1000, wall.y + ty * 1000)
  love.graphics.circle("fill", ball.x, ball.y, RADIUS)
end
# CharacterBody2D.move_and_slide() moves by velocity, and on each hit
# removes the part of the motion that points into the surface.
extends CharacterBody2D

func _physics_process(delta: float) -> void:
    velocity = Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down") * 250.0
    move_and_slide()

# By hand: Vector2.slide(n) returns v - (v . n) n.
# It does not check the sign, so check it yourself.
func slide_velocity(v: Vector2, n: Vector2) -> Vector2:
    if v.dot(n) < 0.0:
        return v.slide(n)
    return v
// CharacterController.Move already slides along the colliders it hits.
// For your own movement code, the same rule in 2D:
Vector2 Slide(Vector2 v, Vector2 n)
{
    float into = Vector2.Dot(v, n);
    if (into >= 0f) return v;      // moving away or along: leave it
    return v - into * n;
}

// In 3D, Vector3.ProjectOnPlane(v, n) gives v - (v . n) n for a unit n,
// also without the sign check.

The "keep full speed" variant from the demo is a few more lines. It needs a dead zone, because a nearly head-on hit leaves a tiny slide vector whose direction is mostly rounding noise:

local function slideKeepSpeed(vx, vy, nx, ny)
  local speed = math.sqrt(vx * vx + vy * vy)
  local sx, sy = slide(vx, vy, nx, ny)
  local len = math.sqrt(sx * sx + sy * sy)
  if len < 0.0001 then
    return 0, 0
  end
  return sx * speed / len, sy * speed / len
end

The demo uses this exact dead zone, which is why 36° and 37° behave so differently: the slide part is less than 4 pixels per second there, well above 0.0001, so it gets blown up to 250. A practical game would use a much bigger dead zone, or only keep speed when the hit is shallow.

Pitfalls

  • Zeroing the whole velocity on contact. This is the sticky wall. Any code that says "collided, so velocity = 0" or "collided, so go back to the old position" should be replaced with the slide.
  • Forgetting the sign check. Removing the normal part when v · n is positive pulls a body that is leaving back onto the wall. Godot's slide and Unity's ProjectOnPlane do not check for you.
  • A normal that is not length 1. The formula assumes a unit normal. With n = (-2, 0) in the worked example, into becomes -400 and the "slide" gives (-600, -150): the ball is flung away from the wall. Normalise normals that you build from edge vectors.
  • Keeping full speed head-on. As the demo shows, rescaling a tiny slide vector turns a near miss of the normal into a full-speed shot in a random-looking direction. Use a dead zone or blend towards the plain slide as the hit gets more direct.
  • Corners. In a corner, sliding along one wall can push the body into the other. Fixing one contact at a time may need several passes, which is what move_and_slide does internally. One wall, as here, needs one pass.

In real games

Godot's CharacterBody2D and CharacterBody3D have move_and_slide(), which moves the body and slides it along what it hits, and Godot's vectors have a slide(n) method for doing it by hand. Unity's CharacterController.Move slides along colliders in the same way, and Vector3.ProjectOnPlane is the plain formula.

The player movement in id Software's Quake III Arena, whose source code was released, does this in a function called PM_ClipVelocity. It multiplies the removed part by a factor slightly above 1 (1.001), so the player ends up moving very slightly away from the surface instead of exactly along it, which keeps rounding errors from pushing the player back into the wall.

Takeaways

  • A wall only blocks the part of the velocity that points into it. Stopping completely is the sticky-wall bug.
  • into = v · n measures that part; v - into * n removes it and leaves the slide.
  • Only remove it when into is negative, and only with a unit-length normal.
  • Sliding is the same as a bounce with restitution 0.
  • Keeping full speed along the wall is a design choice; guard it against near head-on hits.

Tunnelling

Why fast or small objects skip through thin walls between two steps, how to predict when it happens, and three ways to stop it.

You fire a rocket at a closed door and it explodes in the next room. A player falls from a great height and drops straight through a thin floor, but only sometimes. The collision code is correct; it just never looked where the object passed through.

A step only checks where the object lands

The overlap tests from the last few lessons ask: do these two shapes overlap right now? A game moves the object, then asks once per step. This is discrete collision detection: the object is checked at separate moments and nowhere in between.

Between two steps the object teleports. If the old position is in front of a wall and the new one behind it, neither test sees an overlap. That is tunnelling.

The window rule

Take a bullet moving right at speed v, checked every dt seconds. In one step it moves:

d = v * dt

In words: the distance between two checked positions is the speed times the step. At 1800 pixels per second and 60 steps per second, that is 1800 × 1/60 = 30 pixels per step.

Now look at where a check would catch it. Call the bullet's left edge x, its size s, the wall's left edge W and its thickness T. The bullet overlaps the wall when x is between W - s and W + T. That range is the hit window, and its length is:

window = T + s

In words: the wall's thickness plus the bullet's own size. A wall 8 pixels thick and a bullet 6 pixels wide give a window of 14 pixels.

The checked positions are spaced d apart. If d is smaller than the window, one of them must land inside it: the bullet is always caught. If d is larger, whether one lands inside depends on where the shot started. Over many shots the share that are caught is:

hit chance = (T + s) / d

In words: the window as a fraction of one step. Here 14 / 30, so about 47% of shots hit. This is why tunnelling bugs are reported as "sometimes".

Anything that lengthens the step makes tunnelling more likely: more speed, a slower physics rate, a long frame with a variable timestep. So does anything that shortens the window: thinner walls, smaller objects.

Three fixes

1. Keep the step inside the window. Turn the rule around and you get the fastest safe speed: v below (T + s) / dt. For the numbers above that is 14 × 60 = 840 pixels per second. Cap the speed, or make walls and objects thicker.

2. Substeps. Split each step into n substeps and check after each, so each check moves only d / n. Three substeps turn 30 pixels into 10, which fits a 14 pixel window. The cost is n times the tests, and a big enough speed beats any fixed n.

3. Test the path, not the point. During one step the bullet covers everything from its old position to its new one. Test that whole swept region against the wall. If it overlaps, the bullet hit, and you can place it where it first touched: x = W - s when moving right. Testing the motion instead of the end point is continuous collision detection, or CCD. For a bullet treated as a point, the swept test is the raycast from the last lesson, with maximum length d.

The game answer is often the cheap one

The physically correct fix is a swept test for everything. Games rarely do that. Bullets are often not simulated at all: a raycast from the gun decides the hit. Walls get a collision shape thicker than their art, which nobody sees. CCD is switched on only for the few fast objects that still need it.

Then fix it four ways: lower the speed below the safe speed, raise the wall thickness to 25 pixels, set substeps to 3, or switch on the swept test and push the speed to the top. A physics rate of 30 makes it worse. Any change, or Reset, restarts the same sequence of shots.

The code

A small LÖVE program with the demo's numbers. Press space to fire again; with SUBSTEPS = 1 and SWEPT = false roughly half the shots pass through. Set either and they all hit.

-- A bullet flies right towards a thin wall, checked on a fixed step.
-- Lengths in pixels, speeds in pixels per second, y grows downwards.
local STEP = 1 / 60      -- seconds per physics step
local SUBSTEPS = 1       -- checks per step; 3 is enough for these numbers
local SWEPT = false      -- true: test the whole path of each check
local START, GONE = 20, 620

local wall = { x = 380, w = 8 }            -- left edge and thickness
local bullet = { size = 6, speed = 1800 }
local accumulator = 0

local function fire()
  -- start somewhere within one step of START, like a shot fired at any moment
  bullet.x = START - math.random() * bullet.speed * STEP
  bullet.hit = false
end

-- The bullet spans x .. x + size, the wall spans wall.x .. wall.x + wall.w.
local function overlaps(x)
  return x + bullet.size > wall.x and x < wall.x + wall.w
end

local function check(h)
  local prev = bullet.x
  local x = prev + bullet.speed * h
  if SWEPT then
    -- moving right, the box covered prev .. x + size during this check
    if prev < wall.x + wall.w and x + bullet.size > wall.x then
      bullet.x = wall.x - bullet.size      -- stop where it first touches
      bullet.hit = true
      return
    end
  elseif overlaps(x) then
    bullet.hit = true                      -- caught, but already inside the wall
  end
  bullet.x = x
end

local function physicsStep()
  local h = STEP / SUBSTEPS
  for i = 1, SUBSTEPS do
    if bullet.hit then return end
    check(h)
  end
end

function love.load()
  math.randomseed(11)
  fire()
end

function love.keypressed(key)
  if key == "space" then fire() end
end

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    if not bullet.hit and bullet.x < GONE then physicsStep() end
    accumulator = accumulator - STEP
  end
end

function love.draw()
  love.graphics.rectangle("fill", wall.x, 50, wall.w, 110)
  love.graphics.rectangle("line", bullet.x, 105 - bullet.size / 2, bullet.size, bullet.size)
  local status = "flying"
  if bullet.hit then status = "hit" elseif bullet.x >= GONE then status = "passed through" end
  local safe = (wall.w + bullet.size) * SUBSTEPS / STEP
  love.graphics.print(status, 10, 10)
  love.graphics.print(string.format("%.1f px per check, safe below %.0f px/s",
    bullet.speed * STEP / SUBSTEPS, safe), 10, 30)
end
# fast_body.gd: a fast RigidBody2D. Ask Godot to sweep it between steps.
extends RigidBody2D

func _ready() -> void:
    continuous_cd = RigidBody2D.CCD_MODE_CAST_SHAPE
    # CCD_MODE_CAST_RAY is cheaper and treats the body as a point.


# bullet.gd: a bullet you move yourself. Cast a ray along this step's motion.
extends Node2D

var velocity := Vector2(1800, 0)   # pixels per second

func _physics_process(delta: float) -> void:
    var from := global_position
    var to := from + velocity * delta
    var space := get_world_2d().direct_space_state
    var hit := space.intersect_ray(PhysicsRayQueryParameters2D.create(from, to))
    if hit.is_empty():
        global_position = to
    else:
        global_position = hit["position"]
        queue_free()
// In the script of a fast Rigidbody2D: ask Unity to sweep it between steps.
void Awake()
{
    GetComponent<Rigidbody2D>().collisionDetectionMode = CollisionDetectionMode2D.Continuous;
}


// In the script of a bullet you move yourself: cast a ray along this step's motion.
public Vector2 velocity = new Vector2(30f, 0f);   // units per second
public LayerMask wallMask;

void FixedUpdate()
{
    Vector2 from = transform.position;
    Vector2 step = velocity * Time.fixedDeltaTime;
    RaycastHit2D hit = Physics2D.Raycast(from, step.normalized, step.magnitude, wallMask);
    if (hit.collider != null)
    {
        transform.position = hit.point;
        Destroy(gameObject);
    }
    else
    {
        transform.position = from + step;
    }
}

Raising the physics rate is the engines' version of substeps (Physics Ticks per Second in Godot, Fixed Timestep in Unity), but it makes every body cost more. In LÖVE's own love.physics, which wraps Box2D, Body:setBullet(true) asks for the same continuous treatment.

Pitfalls

  • Only thinking about speed. A slow but tiny object against a one-pixel wall tunnels too. Check your smallest object against your thinnest wall.
  • Long frames with a variable timestep. A 100 millisecond hitch makes one step six times longer. Use a fixed step and cap the frame time.
  • Caught, but too deep. A discrete hit can leave the object far inside the wall. If it is past the middle, pushing it out the shortest way pushes it out of the far side, and it tunnels anyway.
  • Two moving objects. Two bullets flying at each other close the gap at the sum of their speeds, so use that in d. Some engines only sweep fast bodies against static walls by default; Box2D, for example, reserves continuous tests between two moving bodies for bodies marked as bullets.
  • Teleporting a body. Setting the position directly skips the engine's sweep. Move bodies through velocity or the engine's move functions.

In real games

Many shooters treat ordinary bullets as hitscan, a raycast from the gun, so they cannot tunnel. Slower projectiles such as rockets or grenades are often real bodies, and these are the ones that get CCD.

The common engines ship the fix as a per-body switch: continuous_cd on Godot's RigidBody2D, collisionDetectionMode on Unity's Rigidbody2D, and the bullet flag in Box2D. Godot's CharacterBody2D tests its whole motion when you call move_and_slide, which is part of why a character moved that way stops at thin walls.

Takeaways

  • Discrete collision checks only where an object lands, never the path in between.
  • An object can skip a wall when it moves further per step than the hit window: v * dt larger than T + s.
  • Past that point a hit is a matter of luck, with a chance of (T + s) / d. That is why the bug appears "sometimes".
  • Fixes: keep the step inside the window, use substeps, or test the swept path (continuous collision detection).
  • Games often use the cheap answer: raycast bullets, thicker invisible walls, and CCD only where it is needed.

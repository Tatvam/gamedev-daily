Forces and mass

How force, mass and acceleration connect, why the same push moves a heavy box less, and how to sum forces each step without letting them pile up.

You add a wooden crate and an iron safe to your level. The player shoves both, and both shoot off at exactly the same speed. The safe feels like painted cardboard.

The code set a velocity or an acceleration directly, so mass never had a say. This lesson puts it back, and shows the one bookkeeping mistake that makes forces run away.

Force divided by mass gives acceleration

So far we set acceleration by hand. Forces give us a better source for it.

A force is a push or a pull on a body. Like velocity, it has a direction and a size. Mass is how strongly a body resists having its velocity changed. It is not the same as weight; a safe floating in space is still hard to get moving.

The two meet in one equation, often called Newton's second law:

acceleration = force / mass

In words: the harder you push, the faster the velocity changes, and the heavier the body, the slower it changes. Double the force and the acceleration doubles. Double the mass and it halves.

Units

Force is mass times acceleration, so its unit is the mass unit times the acceleration unit. In a game measured in pixels and kilograms that is kg·px/s². In Unity, which works in metres, it is kg·m/s², the newton. A force of 400 means nothing until you know the mass it acts on.

One push by hand

The demo below pushes each box with 400 units of force for 15 steps of one sixtieth of a second, which is a quarter of a second. Each step runs the two lines from the previous lesson, with the acceleration now coming from force over mass:

1 kg400 px/s²6.67 px/s100 px/s
2 kg200 px/s²3.33 px/s50 px/s
4 kg100 px/s²1.67 px/s25 px/s

Step 1 for the 1 kg box: 400 × (1/60) = 6.67 px/s gained. Fifteen such steps give 100 px/s. The heavier boxes get the same push and leave slower, in exact proportion to their mass.

Several forces: collect, use once, clear

A body is often pushed by several things at once. It only cares about the net force, the sum of all of them, with directions taken into account: a push to the right of 400 and a wind to the left of 100 add up to 300 to the right.

Game code handles this with a force accumulator: one number per body (two, for x and y) that collects every force during a step. Every step then goes through the same three stages:

  1. Collect. Anything that pushes the body adds its force to the accumulator.
  2. Use. Divide the sum by the mass to get the acceleration, then update velocity and position.
  3. Clear. Set the accumulator back to zero, ready for the next step.

Forces describe what is happening right now. A force that is still pushing next step must be added again next step.

The bug: forgetting to clear

Leave out stage three and every step's forces stay in the sum. During the push, the 1 kg box receives 400, then 800, then 1200, and so on. After 15 steps it is moving at 800 px/s instead of 100, and because the 6000 left in the accumulator never goes away, it gains another 100 px/s every step after the push has ended. A slow push becomes a rocket. You can switch this bug on in the demo.

Feel beats realism

Gravity is the exception to "heavier moves less". The pull of gravity grows with mass, so the mass cancels out and everything falls with the same acceleration. That is why engines apply gravity as an acceleration, not as a force. If you add gravity as a fixed force instead, heavy things fall slowly and look like balloons.

For the player character, many games skip mass altogether and tune acceleration directly, because "reaches full speed in 0.2 seconds" is easier to design than "weighs 70 kg". Mass earns its place on the things the player pushes, throws and gets hit by.

The code

The demo as a LÖVE program, with the same masses, force and push length. The stages are marked: addForce collects, step uses and clears.

local STEP = 1 / 60
local PUSH_FORCE = 400   -- kg·px/s², to the right
local PUSH_STEPS = 15    -- one push lasts 15 steps = 0.25 s
local WIND = 0           -- kg·px/s², to the left
local LEFT, RIGHT = 14, 626

local boxes = {
  { mass = 1, x = 60, vx = 0, force = 0 },
  { mass = 2, x = 60, vx = 0, force = 0 },
  { mass = 4, x = 60, vx = 0, force = 0 },
}
local pushLeft = 0
local accumulator = 0

local function size(box) return 16 + 5 * box.mass end

local function addForce(box, f)
  box.force = box.force + f            -- collect
end

local function step(box, dt)
  local ax = box.force / box.mass      -- a = F / m
  box.vx = box.vx + ax * dt
  box.x = box.x + box.vx * dt
  box.force = 0                        -- clear for the next step
  if box.x > RIGHT - size(box) then box.x = RIGHT - size(box); box.vx = 0 end
  if box.x < LEFT then box.x = LEFT; box.vx = 0 end
end

function love.keypressed(key)
  if key == "space" then pushLeft = PUSH_STEPS end
end

function love.update(dt)
  accumulator = accumulator + math.min(dt, 0.25)
  while accumulator >= STEP do
    for i = 1, #boxes do
      if pushLeft > 0 then addForce(boxes[i], PUSH_FORCE) end
      addForce(boxes[i], -WIND)
      step(boxes[i], STEP)
    end
    if pushLeft > 0 then pushLeft = pushLeft - 1 end
    accumulator = accumulator - STEP
  end
end

function love.draw()
  for i, box in ipairs(boxes) do
    local s = size(box)
    love.graphics.rectangle("fill", box.x, 100 * i - s, s, s)
  end
end
# Godot 4, on a RigidBody2D. The engine keeps the force accumulator:
# it sums the forces, divides by mass and clears them each physics step.
extends RigidBody2D

const PUSH_FORCE := 400.0   # Godot 2D works in pixels: kg·px/s²
var push_steps_left := 0

func _ready() -> void:
    mass = 2.0

func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed("ui_accept"):
        push_steps_left = 15

func _physics_process(delta: float) -> void:
    if push_steps_left > 0:
        apply_central_force(Vector2(PUSH_FORCE, 0))   # for this step only
        push_steps_left -= 1
// Unity works in metres, so forces are in newtons and much smaller numbers
// feel right: 4 N on a 2 kg body gives 2 m/s².
using UnityEngine;

public class Pushable : MonoBehaviour
{
    public float pushForce = 4f;
    Rigidbody2D body;
    int pushStepsLeft;

    void Awake()
    {
        body = GetComponent<Rigidbody2D>();
        body.mass = 2f;
    }

    void Update()
    {
        if (Input.GetKeyDown(KeyCode.Space)) pushStepsLeft = 15;
    }

    void FixedUpdate()
    {
        if (pushStepsLeft > 0)
        {
            body.AddForce(new Vector2(pushForce, 0f), ForceMode2D.Force);
            pushStepsLeft--;
        }
    }
}

In both engines a force applied in the fixed callback lasts for that one step, just like the accumulator above. Unity's default fixed step is 0.02 s, so 15 steps there last 0.3 s, not 0.25 s. Engines also add their own damping and friction, so their numbers will not match the demo exactly.

Pitfalls

  • Never clearing the accumulator. The body speeds up forever and each new push stacks on the old ones. Clear it right after it is used, in one place, so no code path can skip it.
  • A one-step force for a sudden hit. A force applied for a single step changes the velocity by force × dt / mass, which is tiny and depends on the step size. For jumps, explosions and bullet hits you want an instant change of velocity instead, called an impulse. Both engines have a separate call for it, and a later lesson covers it properly.
  • A mass of zero. Dividing by it breaks the simulation. Many engines store the inverse mass, 1 / mass, and multiply by it. An immovable wall then gets an inverse mass of 0, and no force can move it.
  • Gravity as a plain force. Add gravity as mass × g, or straight to the acceleration. A fixed gravity force makes heavy objects fall slower than light ones.

In real games

Godot's RigidBody2D and Unity's Rigidbody2D both have a mass property and both keep a force accumulator for you. In Godot you add to it with apply_central_force, or apply_force at a point, which also makes the body spin. In Unity you call AddForce. For instant changes Godot has apply_central_impulse and Unity has ForceMode2D.Impulse.

Both engines apply gravity so that it does not depend on mass: a heavy and a light rigid body dropped together land together. Unity's 3D ForceMode even has Acceleration and VelocityChange modes that ignore mass on purpose, for cases where a designer wants every body to respond the same.

Your turn (15 minutes)

Start from the Lua program above and move all three boxes to x = 300. Give each box a second force: a spring pulling it back towards 300, addForce(boxes[i], (300 - boxes[i].x) * 2), added every step next to the wind. Push the boxes and watch them swing back and forth.

You are done when you can explain, before running it, which box swings back and forth fastest, and why. Then comment out the line that clears the force and see what happens to the swing.

Takeaways

  • Acceleration equals force divided by mass. Same push, twice the mass, half the acceleration.
  • Add every force into one net force first, then divide once.
  • Clear the force accumulator after each step. A force that keeps acting is added again every step.
  • Gravity is applied as an acceleration, so mass does not change how fast things fall.
  • Use mass where weight should be felt. For the player character, tuning acceleration directly is often the better game choice.

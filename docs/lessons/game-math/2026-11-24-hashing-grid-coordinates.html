Hashing coordinates: how does an endless star field stay the same?

How a hash turns a seed and a grid cell's coordinates into a repeatable random number, so an endless world can be rebuilt anywhere without storing it.

Your space game scrolls forever. The player flies far left, turns round, and expects the same stars on the way back. You cannot store an endless sky, and last lesson's seeded generator hands out numbers in a fixed order, while the player visits places in any order.

Ask the place, not the sequence

Cut the world into a grid of square cells, say 48 pixels wide. Every cell has whole-number coordinates: cell (0, 0), cell (3, −2), and so on. To find the cell under a world position, divide by the cell size and round down: a point at x = 100 pixels is in column floor(100 / 48) = 2.

Now we want a function that takes a seed and a cell's x and y and returns a number that looks random but is always the same for the same inputs. That is a hash function: a formula that scrambles its input into a number where nearby inputs give unrelated outputs. Its result is the hash.

A generator answers "what is the next number?". A hash answers "what is the number for this place?". No state, no order: cell (900, 12) can be worked out before, after or without cell (0, 0).

What scrambling means

Our hash repeats two simple moves on a whole number. Here they are on an 8-bit number (0 to 255) so you can follow them by hand.

  • Multiply and keep the remainder. Multiply by an odd number and keep the remainder after dividing by 256. This pushes changes in the low bits up into the high ones.
  • Fold. Shift the number right by some bits and combine it with itself using XOR ("exclusive or"): compare the two numbers bit by bit and write 1 where they differ, 0 where they match. This pulls the well-mixed high bits back down into the low ones.

Take 6. Multiply by 37: 222, which is 11011110 in binary. Shift right 4 bits: 00001101, which is 13. XOR them: 11010011 = 211. Now take 7. Multiply by 37: 259, keep the remainder after 256: 3. Shifted right 4 bits it is 0, so the fold leaves 3. Neighbours 6 and 7 landed on 211 and 3. That spreading is the whole job.

The real version works on 32-bit numbers, from 0 to 4,294,967,295 (232 − 1), and does fold, multiply, fold, multiply, fold. We call that scramble.

Feeding in the seed and both coordinates

Scramble the seed, add x, scramble, add y, scramble again. Every input is scrambled after it goes in, so changing any one changes everything. Divide the hash by 232 to get a fraction r from 0 up to, but never reaching, 1.

A worked cell

With seed 2, cell (0, 0) gives the hash 580,596,747. Divide by 4,294,967,296 and r = 0.135. Our rule is "a star if r is below 0.35", so this cell has a star.

A star also needs a position and a size. Scramble the hash again for each extra number: the cell's next three values are 0.703, 0.449 and 0.934. Keeping the star 10% away from each edge, its x inside the cell is (0.1 + 0.8 × 0.703) × 48 = 31.8 pixels, its y is (0.1 + 0.8 × 0.449) × 48 = 22.0 pixels, and its radius is 1 + 3 × 0.934 = 3.8 pixels. Ask again a million cells later and you get the same star.

Rule of thumb

Use a generator when you build something once, in order. Use a hash when you need the answer for a place, in any order, again and again.

The code

LÖVE runs on LuaJIT, which has a bit library for XOR and shifts. Lua numbers are only exact up to 253, and two 32-bit numbers multiplied together go past that, so mul32 multiplies in two halves. The names and numbers match the demo: seed 2 and cell (0, 0) give 580,596,747.

local bit = require("bit")    -- LuaJIT's bit library, built into LÖVE
local M = 4294967296          -- 2^32
local CELL, SEED, STAR_CHANCE = 48, 2, 0.35

local function mul32(a, k)    -- (a * k) mod 2^32, exact in Lua numbers
  local hi, lo = math.floor(a / 65536), a % 65536
  return ((hi * k) % 65536 * 65536 + lo * k) % M
end

local function fold(h, n)     -- h XOR (h shifted right by n bits)
  return bit.bxor(h, bit.rshift(h, n)) % M
end

local function scramble(h)
  h = mul32(fold(h, 16), 0x7feb352d)
  h = mul32(fold(h, 15), 0x846ca68b)
  return fold(h, 16)
end

local function hash(seed, x, y)
  local h = scramble((seed + 0x9e3779b9) % M)
  h = scramble((h + x) % M)
  return scramble((h + y) % M)
end

local function starInCell(cx, cy)
  local h = hash(SEED, cx, cy)
  if h / M >= STAR_CHANCE then return nil end
  local hx = scramble(h)      -- more numbers for this cell
  local hy = scramble(hx)
  local hs = scramble(hy)
  return { x = (cx + 0.1 + 0.8 * hx / M) * CELL,
           y = (cy + 0.1 + 0.8 * hy / M) * CELL,
           r = 1 + 3 * hs / M }
end

local camX, camY = -400, -300 -- world position of the screen's top-left

function love.draw()
  local w, h = love.graphics.getDimensions()
  for cy = math.floor(camY / CELL), math.floor((camY + h) / CELL) do
    for cx = math.floor(camX / CELL), math.floor((camX + w) / CELL) do
      local s = starInCell(cx, cy)
      if s then love.graphics.circle("fill", s.x - camX, s.y - camY, s.r) end
    end
  end
end

Move camX and camY in love.update and the sky scrolls forever. In Lua 5.3 and later you can write h ~ (h >> n) instead of the bit calls. Godot has a built-in hash() that accepts any value, such as hash(Vector2i(x, y)). Unity's Mathematics package has math.hash. Neither promises to match the numbers on this page.

Pitfalls

  • Combining coordinates with x + y. Cells (1, 2), (2, 1) and (3, 0) all add up to 3, so they get the same value. You see repeating diagonal lines. Multiplying, x × y, is worse: the whole row y = 0 and column x = 0 share one value. Scramble after adding each coordinate, as hash does.
  • Too little scrambling. If neighbouring inputs give neighbouring outputs, you get stripes, as the demo's "No scramble" option shows. Test a new hash by shading a few hundred cells by r and looking for lines.
  • Zero goes in, zero comes out. scramble(0) is 0, because folding and multiplying 0 always gives 0. Without the constant added to the seed, seed 0 at cell (0, 0) would always give r = 0. Adding a large odd constant first avoids that.
  • Rounding negative positions towards zero. The cell for x = −10 pixels is −1, not 0. Lua's math.floor gets this right. Casting to an integer in C# or GDScript rounds towards zero, which merges two columns into one double-width column at the origin. Use a floor function.
  • Precision in plain Lua. (h * 0x7feb352d) % M looks fine but loses the low bits, because the product passes 253. Use mul32.
  • Using the same hash for different jobs. If trees and stars both use hash(seed, x, y), every star cell also gets a tree in the same spot. Give each job its own seed, for example seed + 1 for trees.

In real games

Ken Perlin's reference code for gradient noise picks a random direction for each grid corner by passing the corner's whole-number coordinates through a shuffled table, which is a hash of coordinates. We build that noise in Track 5.

Shaders hash pixel or cell coordinates all the time, because a pixel shader cannot keep a generator running between pixels.

In Minecraft Java Edition, whether a chunk can spawn slimes is decided from the world seed and the chunk's coordinates alone, which is why players can calculate slime chunks without visiting them.

Take a tiled map in your project and add decoration from a hash: for each grass tile, use hash(seed, tileX, tileY) / M to decide whether it gets a flower, and a second scramble to pick one of three flower types. You are done when the flowers stay put as you scroll away and back, and changing only the seed rearranges all of them.

Takeaways

  • A hash turns inputs into a number that looks random but is always the same for the same inputs.
  • Hash the seed and a cell's coordinates to get a value for that place, in any order, with nothing stored.
  • Scramble after adding each input. Plain sums or products of coordinates repeat along lines.
  • Scramble the hash again to get more numbers for the same cell, such as a position and a size.
  • Find cells with floor, so negative coordinates land in the right cell.

Moving towards a target: why does my unit shake when it arrives?

How direction times speed times delta time moves an object towards a point, and how one distance check stops it overshooting and shaking on arrival.

You click on the map and your unit walks there. It walks well, but when it gets there it never stops: it shakes on the spot, forwards and back, forever. This lesson adds the one missing line.

Three questions every frame

As in the last lessons, positions are measured in grid squares and y grows downwards, as on a screen. Our chaser starts at (1, 1) and the target is at (4, 5).

Each frame, the chaser asks three questions.

  1. Which way? Subtract: to = target − position = (4 − 1, 5 − 1) = (3, 4). This is the arrow from the chaser to the target. Its length is the distance: √(3² + 4²) = √25 = 5. Normalising it (dividing by 5) gives the direction (0.6, 0.8), an arrow of length 1, as in the last lesson.
  2. How far? The speed is how many squares the chaser covers per second. The time since the last frame is called delta time, written dt, in seconds. The distance for this frame is speed × dt. To keep the numbers easy, pretend the game runs at 2 frames per second, so dt = 0.5. With a speed of 4 the step is 4 × 0.5 = 2 squares.
  3. Where to? Multiply the direction by the step and add it: (0.6 × 2, 0.8 × 2) = (1.2, 1.6), so the new position is (1 + 1.2, 1 + 1.6) = (2.2, 2.6). The chaser is now 3 squares from the target.

Written as one line, that is position = position + direction × speed × dt. Because of dt, a game at 30 frames per second takes bigger steps than one at 120, and both cover 4 squares per second.

The overshoot

Run the next frame. The distance is 3, the step is 2, so the chaser reaches (3.4, 4.2), 1 square short. Now the frame after: the distance is 1 but the step is still 2. The chaser moves 2 squares along the direction and ends up at (4.6, 5.8), 1 square past the target.

On the next frame the arrow to the target points backwards, so the chaser steps 2 squares back to (3.4, 4.2). Then forwards again. It never lands: it is always 1 square away, on one side or the other. That is the shaking unit from the start of the lesson.

The fix: land if you can reach it

Before moving, compare the distance with the step. If the distance is not more than the step, the chaser could reach the target this frame, so put it exactly on the target and stop. Otherwise take the normal step.

if dist <= step then
  pos = target                -- close enough: arrive exactly
else
  pos = pos + dir * step      -- still far: take a full step
end

In the example the third frame has distance 1 and step 2. 1 ≤ 2, so the chaser goes to (4, 5) and stays there. The check also handles the case where the chaser already sits on the target: the distance is 0, the check passes, and we never divide by 0 to normalise.

Rule of thumb

Moving at a fixed speed towards a point? Compare the distance with speed × dt first. If it is smaller or equal, snap to the target.

Try it

Click or tap anywhere on the grid to place the target, or drag it. With the canvas focused, the arrow keys move the target one square and P switches the protection. The chaser runs at the frame rate you choose and leaves one dot per frame.

With protection off, watch the chaser shake across the target while the overshoot count climbs. Raise the speed or lower the frame rate: the shaking grows, because it is one step wide. Then switch protection on. Press Reset and set the frame rate to 2 to replay the worked example.

The code

The same numbers as the worked example and the demo. A square is 40 pixels. Click to move the target, press P to switch protection.

-- Positions are in grid squares. y grows downwards, like LÖVE's screen.
local UNIT = 40                    -- pixels per grid square
local SPEED = 4                    -- squares per second
local chaser = { x = 1, y = 1 }
local target = { x = 4, y = 5 }
local protect = true               -- overshoot protection

local function moveTowards(pos, goal, step)
  local toX = goal.x - pos.x       -- the vector to the goal
  local toY = goal.y - pos.y
  local dist = math.sqrt(toX * toX + toY * toY)
  if protect and dist <= step then  -- can reach it this frame: land
    return { x = goal.x, y = goal.y }
  end
  if dist == 0 then                -- no direction to move in
    return { x = pos.x, y = pos.y }
  end
  return {                         -- direction times step
    x = pos.x + toX / dist * step,
    y = pos.y + toY / dist * step
  }
end

function love.mousepressed(x, y, button)
  target = { x = x / UNIT, y = y / UNIT }
end

function love.keypressed(key)
  if key == "p" then
    protect = not protect
  end
end

function love.update(dt)
  chaser = moveTowards(chaser, target, SPEED * dt)
end

function love.draw()
  love.graphics.circle("line", target.x * UNIT, target.y * UNIT, 10)
  love.graphics.circle("fill", chaser.x * UNIT, chaser.y * UNIT, 8)
  love.graphics.print("protect: " .. tostring(protect), 10, 10)
end

Check it by hand: moveTowards({ x = 1, y = 1 }, { x = 4, y = 5 }, 2) returns (2.2, 2.6), as in the diagram. At a real 60 frames per second the step is only 4 × (1/60), about 0.07 squares, so the shaking without protection is small but it is still there.

Built-in versions: Godot has Vector2.move_toward(to, delta) and Unity has Vector2.MoveTowards(current, target, maxDistanceDelta). Both include the landing check.

Pitfalls

  • No landing check. The chaser shakes across the target by up to one step forever. The shaking gets worse with higher speed or a lower frame rate, so it can look fine on your machine and bad on a slow one.
  • An arrival radius instead of a snap. if dist < 0.1 then stop works only while the step is smaller than 0.2. At high speed or a low frame rate the chaser can step over the whole circle and shake again. Comparing with the step itself always works.
  • Forgetting to normalise. pos + to * speed * dt moves fast when the target is far and slow when it is near. With speed 4 and dt 0.5 the example jumps from (1, 1) to (7, 9) and back forever.
  • Forgetting dt. Moving SPEED squares per frame instead of per second makes the chaser twice as fast on a 120 Hz screen as on a 60 Hz one.
  • Distance exactly 0. Without protection, a chaser that lands exactly on the target divides 0 by 0. In Lua that gives NaN (not a number), and the chaser vanishes. The landing check catches this for free; without it you need the separate dist == 0 test.
  • Negative speed. A negative step moves the chaser away and the landing check never fires. Keep speed at 0 or above.

In real games

Click-to-move units in strategy games and action RPGs, moving platforms and lifts that travel between two points, and patrols that walk from waypoint to waypoint all need "move at this speed towards that point and stop there". Godot's move_toward and Unity's MoveTowards exist because the pattern is so common.

The same idea works on single numbers, such as a health bar sliding towards the real health value at a fixed rate.

Takeaways

  • To move towards a point: subtract to get the vector to it, normalise it, multiply by speed × dt and add.
  • speed × dt is the distance you can travel this frame. In the example, 4 × 0.5 = 2 squares.
  • If the distance to the target is not more than that step, snap to the target. Otherwise the object overshoots and shakes.
  • The same check stops you dividing by zero when the object is already on the target.
  • Godot's move_toward and Unity's MoveTowards do all of this for you.

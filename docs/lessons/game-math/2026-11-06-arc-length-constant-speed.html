Arc length and constant speed: why does my drone rush the bends?

Why equal steps of t are not equal distances on a curve, and how a small table of distances lets a drone fly along it at a steady speed.

Your patrol drone follows a Bezier curve, and you move it by adding a fixed amount to t every second. It shoots off the start, crawls over the top of the arc, then speeds up again before the end. Your code never changes its speed.

The fix is to measure the curve once, keep the measurements in a short list, and move by distance instead of by t.

t is not distance

We use the cubic curve from the Bezier lessons: start P0 = (0, 6), handles P1 = (2, 0) and P2 = (6, 0), end P3 = (8, 4). Positions are in grid squares and y grows downwards, as on screen and in LÖVE.

The number t (from 0 at the start to 1 at the end) says how far through the recipe of lerps we are, not how far along the curve. Cut t into four equal quarters and work out the points: (0, 6), (1.81, 2.59), (4, 1.25), (6.19, 1.78), (8, 4). Now measure the straight line between each pair with Pythagoras. The first one goes 1.81 across and 3.41 up, so its length is √(1.81² + 3.41²) ≈ √14.9 ≈ 3.86 squares.

Equal steps of t, unequal distances. If t grows at a steady rate, the drone covers 3.86 squares in the first quarter of the time and only 2.25 in the third. That is the rush and the crawl.

The Bezier lesson already gave us the numbers for this. The velocity 3 × (E − D) is how far the point moves per unit of t, and its length changes along the curve: 18.97 at t = 0, but only 9.12 at t = 0.5. On a 3 second trip that is 6.3 squares per second at the start and 3.0 in the middle.

Measure the curve once

The arc length is the distance along the curve itself. There is no neat formula for it on a cubic Bezier, so games estimate it: cut the curve into small straight pieces, called chords, and add up their lengths.

Write the running total down after every piece and you have a lookup table: a list that says "at this t, the drone has travelled this far". With four pieces the total is 11.54. The true length is 11.71, because a straight chord is always a little shorter than the bend it cuts across. With 16 pieces the estimate is 11.70; more pieces, smaller error.

Read the table backwards

The table answers "how far at this t?" We want the opposite: "the drone has flown 5 squares, so what t do I feed the curve?" Read it backwards:

  1. Find the two rows whose distances surround 5. That is 3.86 (t = 0.25) and 6.43 (t = 0.5).
  2. Work out how far 5 lies between them. This is the inverse lerp from an earlier lesson: f = (5 − 3.86) / (6.43 − 3.86) = 1.14 / 2.57 ≈ 0.44.
  3. Go that far between the two t values with lerp: t = 0.25 + 0.44 × (0.5 − 0.25) ≈ 0.36.

Now the drone keeps a distance, adds speed × dt to it each frame, looks up t, and only then asks the curve for a point. Equal steps of distance, equal distances: a steady speed.

The lookup is only as good as the table. Between two rows it assumes distance grows evenly with t, which is not quite true, so with four pieces the answer t ≈ 0.36 actually lands 5.16 squares along, not 5. A bigger table makes those straight bits shorter and the error smaller.

Rule of thumb

Build the table once, when the curve is made or changed, never every frame. A few dozen rows per curve is usually plenty for movement; the demo lets you see where the error stops being visible.

The code

The two drones from the demo: the same curve, 40 pixels per grid square, a 3 second trip and a table of 16 pieces. buildLengthTable measures the curve once; tAtDistance reads the table backwards.

-- Points are tables { x, y }. y grows downwards, like LÖVE's screen.
local function vec(x, y) return { x = x, y = y } end

local function lerpPoint(p, q, t)
  return vec(p.x + (q.x - p.x) * t, p.y + (q.y - p.y) * t)
end

local function bezier3(c, t)                    -- c = { p0, p1, p2, p3 }
  local a, b = lerpPoint(c[1], c[2], t), lerpPoint(c[2], c[3], t)
  local d, e = lerpPoint(a, b, t), lerpPoint(b, lerpPoint(c[3], c[4], t), t)
  return lerpPoint(d, e, t)
end

-- lengths[i] = distance travelled at t = (i - 1) / pieces
local function buildLengthTable(c, pieces)
  local lengths, prev, total = { 0 }, c[1], 0
  for i = 1, pieces do
    local p = bezier3(c, i / pieces)
    local dx, dy = p.x - prev.x, p.y - prev.y
    total = total + math.sqrt(dx * dx + dy * dy)
    lengths[i + 1] = total
    prev = p
  end
  return lengths
end

-- The t at which the curve has covered distance d.
local function tAtDistance(lengths, d)
  local pieces = #lengths - 1
  local total = lengths[#lengths]
  if total <= 0 or d <= 0 then return 0 end     -- no curve, or not started
  if d >= total then return 1 end
  for i = 1, pieces do
    if d < lengths[i + 1] then                  -- so lengths[i + 1] > lengths[i]
      local f = (d - lengths[i]) / (lengths[i + 1] - lengths[i])
      return (i - 1 + f) / pieces
    end
  end
  return 1
end

local UNIT = 40                                 -- pixels per grid square
local function grid(x, y) return vec(x * UNIT, y * UNIT) end
local curve = { grid(0, 6), grid(2, 0), grid(6, 0), grid(8, 4) }
local lengths = buildLengthTable(curve, 16)
local totalLength = lengths[#lengths]
local TRIP_SECONDS = 3
local time = 0

function love.update(dt)
  time = time + dt
  if time > TRIP_SECONDS then time = time - TRIP_SECONDS end
end

function love.draw()
  love.graphics.push()
  love.graphics.translate(40, 60)
  local tOrange = time / TRIP_SECONDS                     -- steady t
  local distance = totalLength * time / TRIP_SECONDS      -- steady distance
  local tGreen = tAtDistance(lengths, distance)
  local a, b = bezier3(curve, tOrange), bezier3(curve, tGreen)
  love.graphics.setColor(1, 0.6, 0.1)
  love.graphics.circle("fill", a.x, a.y, 8)
  love.graphics.setColor(0.2, 0.75, 0.35)
  love.graphics.circle("fill", b.x, b.y, 8)
  love.graphics.pop()
  love.graphics.setColor(1, 1, 1)
  love.graphics.print(string.format("length %.2f squares  orange t %.2f  green t %.2f",
    totalLength / UNIT, tOrange, tGreen), 10, 10)
end

The printed length is 11.70 squares. At 1.5 seconds the orange drone is at t = 0.50, the point (4, 1.25), while the green one is at t = 0.43, about (3.38, 1.43): exactly halfway along the curve, and slightly behind, because the first half of t covers 6.50 of the 11.70 squares.

Built-in versions: Godot 4's Curve2D bakes a table like this for you, with get_baked_length() and sample_baked(offset). LÖVE's BezierCurve:evaluate(t) takes t, so it has the same uneven speed as the orange drone. Unity's core API has no curve type to compare.

Pitfalls

  • Using t as "how far along". A progress bar, a "50 percent of the way" checkpoint or evenly spaced fence posts placed at equal t all come out uneven. Convert distance to t first.
  • A stale table. Move a control point and the old table describes a different curve. Rebuild it whenever the points change.
  • Distance outside the curve. Past the end, a raw lookup has no row to land between, and t outside 0 to 1 sends the curve formula off into space. tAtDistance clamps to 0 and 1; to loop, subtract the total length, as love.update does with the time.
  • A curve of zero length. If all four points are the same, every row is 0 and step 2 would divide by zero. The total <= 0 check returns t = 0 first. Inside the loop the division is safe: the row it divides by is always longer than the one before.
  • Several curves in one path. Give the drone one distance for the whole path: keep each curve's total length, subtract them in turn to find which curve the distance falls on, then look up t in that curve's table. This also fixes the short curve that took as long as a long one in the Bezier path lesson.
  • Performance. The loop in tAtDistance walks the table from the start. For a few dozen rows that is nothing; for thousands, use a binary search or remember the row you used last frame.

In real games

Anything that follows a curve at a steady pace needs this, or something like it: patrol routes, enemies walking a tower-defence path, cameras on a rail, trains and conveyor belts. The same table spaces things evenly along a curve, such as road markings, fence posts or a line of coins.

Engines often hide it. Godot's Curve2D and Curve3D store baked points spaced by a bake_interval, and a PathFollow2D node moves by distance along them, through its progress property.

Takeaways

  • t says how far through the recipe you are, not how far along the curve. Equal steps of t give unequal distances.
  • Estimate the arc length by adding up the lengths of many short chords, and record the running total as a table of t and distance.
  • To move at a steady speed, keep a distance, look up the two rows around it, inverse lerp between them and lerp the t values.
  • A bigger table means a smaller error; build it once and rebuild it only when the curve changes.
  • Clamp the distance, and guard against a curve of zero length.

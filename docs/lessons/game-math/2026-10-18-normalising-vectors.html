Normalising a vector: why is diagonal movement faster?

How dividing a vector by its own length gives a pure direction of length 1, and how that stops diagonal movement from being 41 percent faster.

You make a top-down game where the hero walks 4 squares per second. Hold right: 4 squares per second. Hold right and down together and the hero crosses the room noticeably faster. Where does the extra speed come from, and how do you take it away?

Where the extra speed comes from

As in the last lessons, a vector is a pair (x, y) drawn as an arrow, and y grows downwards, as on a screen. So the up key means y = −1.

Most movement code turns the keys into an input vector: −1, 0 or 1 for each axis. Right gives (1, 0). Right and down gives (1, 1). Then it moves the hero by input * speed * dt.

Last lesson gave us the length of a vector: √(x² + y²). For (1, 0) that is √1 = 1. For (1, 1) it is √(1 + 1) = √2, about 1.41. So the diagonal move is 1.41 times as long, and the hero walks 1.41 × 4 = 5.66 squares per second. That is 41 percent too fast.

Draw all eight key combinations as arrows from one point. Their tips sit on a square, not a circle, and the corners stick out.

Unit vectors: direction with the size taken out

A vector holds two things: which way it points, and how long it is. Often you only want the first. A unit vector is a vector of length exactly 1. It is pure direction: multiply it by a speed and you get a move of exactly that speed.

To normalise a vector means to find the unit vector that points the same way. You divide both components by the vector's length. The result is often written v̂, said "v hat".

-- v-hat = v divided by its length |v|
local len = math.sqrt(v.x * v.x + v.y * v.y)
local dir = { x = v.x / len, y = v.y / len }
-- v = (3, 4): len = 5, dir = (3/5, 4/5) = (0.6, 0.8)

Why does this work? Last lesson showed that multiplying a vector by a number k multiplies its length by k. Dividing by the length is multiplying by k = 1 / |v|. The new length is |v| × (1 / |v|) = 1. The direction does not change, because k is positive. Check it: √(0.6² + 0.8²) = √(0.36 + 0.64) = √1 = 1.

Now the diagonal key input: (1, 1) has length √2, so its unit vector is (1 / √2, 1 / √2), about (0.71, 0.71). Each axis moves only 71 percent as fast, but the total move has length 1, like moving straight. Straight input such as (1, 0) already has length 1, so normalising leaves it unchanged.

The one vector you cannot normalise

When no key is pressed, or left and right are both held, the input is (0, 0). Its length is 0, and dividing by 0 is not allowed. In Lua, 0 / 0 gives "not a number" (NaN), and that value then spreads into the position and the hero vanishes. The zero vector has no direction. Check for it first and return (0, 0).

Rule of thumb

Want a direction? Normalise. Want a movement? Normalise, then multiply by the speed you chose. Always check for length 0 before you divide.

The code

The same hero as the demo: it starts at (5, 4), walks 4 squares per second, and a square is 40 pixels. Press N to switch normalising on and off.

-- Vectors are tables { x = ..., y = ... }. y grows downwards, like LÖVE's screen.
local function length(v)
  return math.sqrt(v.x * v.x + v.y * v.y)
end

local function normalise(v)
  local len = length(v)
  if len == 0 then                  -- (0, 0) has no direction
    return { x = 0, y = 0 }
  end
  return { x = v.x / len, y = v.y / len }
end

local UNIT = 40                     -- pixels per grid square
local SPEED = 4                     -- squares per second
local player = { x = 5, y = 4 }
local useNormalise = true
local currentSpeed = 0

function love.keypressed(key)
  if key == "n" then
    useNormalise = not useNormalise
  end
end

function love.update(dt)
  local input = { x = 0, y = 0 }
  if love.keyboard.isDown("left")  then input.x = input.x - 1 end
  if love.keyboard.isDown("right") then input.x = input.x + 1 end
  if love.keyboard.isDown("up")    then input.y = input.y - 1 end
  if love.keyboard.isDown("down")  then input.y = input.y + 1 end

  local dir = input
  if useNormalise then
    dir = normalise(input)
  end
  player.x = player.x + dir.x * SPEED * dt
  player.y = player.y + dir.y * SPEED * dt
  currentSpeed = length(dir) * SPEED
end

function love.draw()
  love.graphics.circle("fill", player.x * UNIT, player.y * UNIT, 12)
  love.graphics.print(string.format("normalise: %s   speed: %.2f squares/s",
    tostring(useNormalise), currentSpeed), 10, 10)
end

Hold right and down: the top line reads speed: 4.00 squares/s. Press N and it reads 5.66 for the same keys.

Built-in versions: Godot has Vector2.normalized() and Unity has the Vector2.normalized property. Both return (0, 0) for a vector too short to normalise instead of failing, but a hand-written version like the one above needs its own check.

Pitfalls

  • Forgetting the zero check. Normalising (0, 0) divides 0 by 0. In Lua that gives NaN, not an error, so nothing crashes: the hero's position quietly becomes NaN and it disappears from the screen.
  • Normalising analogue stick input. A gamepad stick gives values between −1 and 1, and a gentle push gives a short vector such as (0.2, 0). Normalising turns it into (1, 0), so the slightest touch means full speed. For sticks, only shrink the vector when its length is more than 1, and leave shorter ones alone. Godot's limit_length() and Unity's Vector2.ClampMagnitude do this.
  • Normalising after multiplying by speed. normalise(input * speed) throws the speed away again, because the result always has length 1. Normalise first, then multiply.
  • Expecting the components to stay whole numbers. (0.71, 0.71) times 4 is about (2.83, 2.83) squares per second. If your game snaps positions to whole pixels, a slow diagonal can stall or wobble. Keep positions as decimals and round only when drawing.
  • Tiny lengths. Rounding errors make very short vectors unreliable, so engines treat anything below a small threshold as zero. Comparing with exactly 0 is fine for key input, which is always whole numbers.
  • Performance. One square root and two divisions per character per frame is nothing to worry about. If you normalise the same direction many times, store the result.

In real games

Any game with eight-way movement from keys or a d-pad has to make this choice: normalise the input, or accept that diagonals are faster. Either can be right for a game, as long as it is a decision and not an accident. Godot's Input.get_vector builds the input vector from four actions and limits its length to 1.

Unit vectors are also how engines store pure directions: a camera's forward direction, a bullet's direction before it is multiplied by its speed, and the surface direction used to bounce a ball off a wall.

Takeaways

  • Raw key input (1, 1) has length √2, about 1.41, so un-normalised diagonal movement is 41 percent faster.
  • A unit vector has length 1. It is a pure direction, ready to be multiplied by a speed.
  • To normalise, divide each component by the length: (3, 4) ÷ 5 = (0.6, 0.8).
  • The zero vector has no direction. Check for length 0 before dividing.
  • For analogue sticks, limit the length to 1 instead of normalising.

Inverse lerp and remap: how wide is the health bar?

How inverse lerp turns a value such as health into a fraction t, and how remap carries that fraction into a new range such as a bar width or a colour.

The hero has 30 health out of 120, and the health bar on screen is 200 pixels wide when full. How many pixels should be filled? And the bar should turn from green to red as health drops, so what colour is 30 health?

Yesterday's lerp answered "I know t, where am I?". Today we ask the opposite question, "I know where I am, what is t?", and then use the answer to jump from one range to another.

Lerp, run backwards

Recall lerp(a, b, t) = a + (b - a) * t. You give it a start a, an end b and a fraction t, and it gives you a value.

Inverse lerp does the reverse. You give it the start a, the end b and a value v somewhere in that range, and it tells you the fraction t: how far along from a to b the value sits. Its answer is 0 when v equals a, 1 when v equals b, and 0.5 halfway.

The formula

Ask two distances. How far is v past the start? That is v − a. How long is the whole range? That is b − a. The fraction is one divided by the other:

inverseLerp(a, b, v) = (v - a) / (b - a)

Worked example, the hero with v = 30 health in the range a = 0 to b = 120:

  1. Distance past the start: 30 − 0 = 30.
  2. Length of the range: 120 − 0 = 120.
  3. The fraction: 30 / 120 = 0.25.

Check the ends. With v = 0 the top is 0, so t = 0. With v = 120 the top equals the bottom, so t = 1. When a is 0 this is just v / b, the familiar health divided by max health.

Remap: inverse lerp, then lerp

To remap a value is to move it from one range to another while keeping its place. Inverse lerp finds the place as a fraction; lerp puts that fraction into the new range, from c to d:

remap(v, a, b, c, d) = lerp(c, d, inverseLerp(a, b, v))

The health bar: t = 0.25 from above, and the bar goes from c = 0 to d = 200 pixels. lerp(0, 200, 0.25) = 0 + 200 × 0.25 = 50 pixels. The colour is a second lerp with the same t, from red at t = 0 to green at t = 1, so one t feeds as many outputs as you like.

A range that does not start at zero: a sound should play at full volume up to 20 metres away and be silent from 60 metres. At 30 metres, t = (30 − 20) / (60 − 20) = 10 / 40 = 0.25. The volume goes from 1 down to 0, so c = 1 and d = 0: lerp(1, 0, 0.25) = 1 + (0 − 1) × 0.25 = 0.75. Nothing special is needed for a range that runs downwards; the minus sign in d − c takes care of it.

Outside the range, and a range of zero length

Overheal the hero to 150 and t = 150 / 120 = 1.25, so the bar is 250 pixels and spills out of its frame. At −12 health, t = −0.1 and the width is −20 pixels. If you want the output to stay inside c to d, clamp t to 0 to 1 between the two steps. And if a equals b, then b − a is 0 and the division has no answer, so check for it before dividing.

The code

A health bar in LÖVE with the same numbers as the demo: range 0 to 120, a 200 pixel bar, red to green. Press the left and right arrow keys to change health by 10. inverseLerp holds the line that matters.

-- Screen coordinates: x grows right, y grows down, as in LÖVE.
local BAR_X, BAR_Y = 20, 20
local BAR_WIDTH, BAR_HEIGHT = 200, 16
local RED, GREEN = { 0.85, 0.2, 0.15 }, { 0.2, 0.75, 0.25 }

local function lerp(a, b, t)
  return a + (b - a) * t
end

-- Where does v sit between a and b? 0 at a, 1 at b.
local function inverseLerp(a, b, v)
  if a == b then return 0 end              -- no range: avoid dividing by 0
  return (v - a) / (b - a)
end

local function clamp01(t)
  return math.max(0, math.min(1, t))
end

-- Move v from the range a..b to the range c..d.
local function remap(v, a, b, c, d)
  return lerp(c, d, inverseLerp(a, b, v))
end

local health, maxHealth = 30, 120

-- Check: prints 0.25, then 50, then 0.75
print(inverseLerp(0, maxHealth, 30))
print(remap(30, 0, maxHealth, 0, BAR_WIDTH))
print(remap(30, 20, 60, 1, 0))           -- volume at 30 m

function love.keypressed(key)
  if key == "left" then health = health - 10 end
  if key == "right" then health = health + 10 end
end

function love.draw()
  local t = clamp01(inverseLerp(0, maxHealth, health))
  local width = lerp(0, BAR_WIDTH, t)
  love.graphics.setColor(lerp(RED[1], GREEN[1], t), lerp(RED[2], GREEN[2], t), lerp(RED[3], GREEN[3], t))
  love.graphics.rectangle("fill", BAR_X, BAR_Y, width, BAR_HEIGHT)
  love.graphics.setColor(1, 1, 1)
  love.graphics.rectangle("line", BAR_X, BAR_Y, BAR_WIDTH, BAR_HEIGHT)
  love.graphics.print(string.format("HP %d / %d", health, maxHealth), BAR_X, BAR_Y + 24)
end

Built-in versions: Godot has inverse_lerp(from, to, weight) and remap(value, istart, istop, ostart, ostop), which do not clamp. Unity has Mathf.InverseLerp, which clamps its result to 0 to 1; combine it with Mathf.Lerp for a clamped remap.

Pitfalls

  • A range of zero length. If a equals b, (v - a) / (b - a) divides by zero. In Lua that gives infinity, or "not a number" when v also equals a, and that value then poisons every lerp after it: the bar disappears or fills the screen. Guard it, as inverseLerp above does by returning 0.
  • Whole-number division. In Lua every number can hold a fraction, so 30 / 120 is 0.25. In C# and GDScript, dividing two whole numbers (ints) throws the fraction away: 30 / 120 is 0, and your bar is always empty until health is full. Convert one side to a float first.
  • Forgetting to clamp. Overheal, negative health and anything else outside a to b give t outside 0 to 1, so the output leaves c to d. Clamp t when the output must stay in range, such as a bar width or a volume.
  • Clamping the output with min and max. math.max(c, math.min(d, x)) only works when c is less than d. For a range that runs downwards, like volume 1 to 0, it returns the wrong value. Clamping t instead works in both directions.
  • Arguments in the wrong order. Is it (v, a, b) or (a, b, v)? Engines differ. Test once with the numbers from this page: the answer for 30 in 0 to 120 must be 0.25.

In real games

Any bar in a user interface is a remap: health, stamina, experience to the next level, a loading bar. So is a stick dead zone. An analogue stick rarely rests at exactly zero, so games ignore small tilts; remapping the tilt from the dead zone edge to 1 onto 0 to 1 removes the jump that a plain cut-off leaves. Fading sound or fog with distance uses the same shape as the volume example.

Shaders use it too. The GLSL specification defines smoothstep(edge0, edge1, x) as starting with clamp((x - edge0) / (edge1 - edge0), 0.0, 1.0), which is a clamped inverse lerp, before bending the result into an S shape.

Your turn (15 minutes)

Add a dead zone to stick or mouse-drag input in your own project. Take the input's length, call it m, from 0 to 1. Set DEAD = 0.2, compute t = clamp01(inverseLerp(DEAD, 1, m)), and scale your movement speed by t instead of by m.

You are done when m = 0.1 gives t = 0, m = 0.6 gives t of about 0.5, and m = 1 gives t = 1, and a character no longer creeps along when you let go of the stick. For a bonus, also set DEAD to 1 and confirm that your guard stops the division by zero.

Takeaways

  • inverseLerp(a, b, v) = (v - a) / (b - a) tells you how far along from a to b the value v sits.
  • remap is inverse lerp then lerp: find the fraction in the old range, then use it in the new one.
  • One t can drive many outputs at once, such as a width and a colour.
  • Clamp t, not the output, when the result must stay in range. This works for ranges that run downwards too.
  • Guard against a equal to b, and against whole-number division in C# and GDScript.

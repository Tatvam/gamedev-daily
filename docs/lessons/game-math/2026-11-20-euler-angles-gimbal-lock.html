Euler angles and gimbal lock: why did my plane stop turning?

How yaw, pitch and roll describe a 3D rotation, why their order matters, and why pitching 90 degrees makes yaw and roll turn about the same axis.

Your flight game stores the plane's rotation as three numbers: yaw, pitch and roll. It works until the player dives straight down. Now the yaw keys and the roll keys both spin the plane like a drill, and nothing turns the nose sideways. Your code is fine: three angles simply behave like this, and the problem is called gimbal lock.

Three turns, one after another

In 2D one angle says which way something faces. In 3D you need three. The most common way to store them is as Euler angles (named after the mathematician Leonhard Euler): three turns, each about one axis, done in a fixed order. For planes, cameras and characters they are called:

  • Yaw: turning the nose left or right, about the up axis (y).
  • Pitch: tipping the nose up or down, about the wing axis (x).
  • Roll: spinning around the nose, about the forward axis (z).

In this lesson x points right, y points up and z points forward, away from you, the same axes Unity uses. Before any rotation the plane's nose points along +z and its right wing along +x. Positive yaw turns the nose right, positive pitch tips it down, and positive roll lifts the right wing.

Each turn is a 2D rotation

A turn about one axis is the 2D rotation you already know, applied to the other two coordinates; the coordinate along the axis does not change. With a for the angle, c for cos a and s for sin a:

yaw   (about y):  x' = x·c + z·s     z' = z·c − x·s     y stays
pitch (about x):  y' = y·c − z·s     z' = y·s + z·c     x stays
roll  (about z):  x' = x·c − y·s     y' = x·s + y·c     z stays

Worked example. Yaw the plane 90° to the right. cos 90° = 0 and sin 90° = 1. The right wingtip starts at (1, 0, 0):

x' = 1·0 + 0·1 = 0
z' = 0·0 − 1·1 = −1          right wingtip → (0, 0, −1)

The nose now points right, so the right wing points backwards, as you would expect.

The order matters

Our order is: roll first, then pitch, then yaw, for every point of the model. Roll goes first, while the nose still lies along z, so it spins the plane around its own nose. Pitch then tips the nose about x. Yaw comes last and swings everything round the world's up axis.

Swap the order and the result changes. Take the right wingtip (1, 0, 0), roll 90° and yaw 90°. Roll first lifts it to (0, 1, 0), and yaw about the up axis leaves it there. Yaw first sends it to (0, 0, −1), and a turn about z cannot move a point on z. Same angles, different plane.

Gimbal lock

A gimbal is a set of rings, each hinged inside the next, like the mount of a ship's compass. The demo below draws one: the outer yaw ring turns about the world's up axis and carries the pitch ring, which carries the roll ring, which carries the plane. That nesting is exactly our order of turns.

Now pitch 90°. The nose (0, 0, 1) goes to y' = 0·0 − 1·1 = −1 and z' = 0·1 + 1·0 = 0, so it points straight down, (0, −1, 0). Roll spins the plane around its nose, and the nose is now the world's up–down line. Yaw spins the plane around the world's up–down line too. Two of the three sliders do the same job, and one kind of turn has gone missing: with roll at 0, no slider can swing the nose towards a wingtip. Losing a turn like this is gimbal lock. In the demo you will see the pitch ring lie flat inside the yaw ring.

You can check it with numbers. At pitch 90°, (yaw 30°, roll 0°) and (yaw 0°, roll −30°) and (yaw 40°, roll 10°) put every point of the plane in exactly the same place. Only yaw − roll matters. At pitch −90° (nose straight up) only yaw + roll matters.

What is actually locked

The plane can still face any way you like. What breaks is the description: near 90° a small, smooth turn can need huge, sudden changes in yaw and roll. That is why animations that blend Euler angles sometimes whip round in a spin nobody asked for.

The code

The three rotations, their order, and the demo's dart-shaped plane, steered with the keyboard and seen from 4 units behind.

-- x right, y up, z forward. Angles in degrees.
local yaw, pitch, roll = 0, 0, 0

local function rotateX(p, a)   -- pitch: positive tips the nose down
  local c, s = math.cos(a), math.sin(a)
  return { x = p.x, y = p.y * c - p.z * s, z = p.y * s + p.z * c }
end

local function rotateY(p, a)   -- yaw: positive turns the nose right
  local c, s = math.cos(a), math.sin(a)
  return { x = p.x * c + p.z * s, y = p.y, z = p.z * c - p.x * s }
end

local function rotateZ(p, a)   -- roll: positive lifts the right wing
  local c, s = math.cos(a), math.sin(a)
  return { x = p.x * c - p.y * s, y = p.x * s + p.y * c, z = p.z }
end

-- Roll first, then pitch, then yaw.
local function eulerRotate(p, yawDeg, pitchDeg, rollDeg)
  local q = rotateZ(p, math.rad(rollDeg))
  q = rotateX(q, math.rad(pitchDeg))
  return rotateY(q, math.rad(yawDeg))
end

-- Nose, right tip, tail, left tip, fin top, fin front.
local PLANE = { {x=0, y=0, z=1.1}, {x=0.9, y=0, z=-0.45}, {x=0, y=0, z=-0.7},
                {x=-0.9, y=0, z=-0.45}, {x=0, y=0.45, z=-0.75}, {x=0, y=0, z=-0.25} }
local EDGES = { {1,2}, {2,3}, {3,4}, {4,1}, {3,5}, {5,6} }

function love.update(dt)
  local turn = 60 * dt
  if love.keyboard.isDown("d") then yaw = yaw + turn end
  if love.keyboard.isDown("a") then yaw = yaw - turn end
  if love.keyboard.isDown("s") then pitch = pitch + turn end
  if love.keyboard.isDown("w") then pitch = pitch - turn end
  if love.keyboard.isDown("e") then roll = roll + turn end
  if love.keyboard.isDown("q") then roll = roll - turn end
  pitch = math.max(-90, math.min(90, pitch))
end

function love.draw()
  local w, h = love.graphics.getDimensions()
  local f = h                                  -- focal length in pixels
  local pts = {}
  for i, p in ipairs(PLANE) do
    local r = eulerRotate(p, yaw, pitch, roll)
    local depth = r.z + 4                      -- viewer is 4 units behind
    pts[i] = { w / 2 + f * r.x / depth, h / 2 - f * r.y / depth }   -- minus: y up
  end
  for _, e in ipairs(EDGES) do
    local a, b = pts[e[1]], pts[e[2]]
    love.graphics.line(a[1], a[2], b[1], b[2])
  end
  love.graphics.print(string.format("yaw %.0f  pitch %.0f  roll %.0f", yaw, pitch, roll), 10, 10)
end

A and D yaw, W and S pitch, Q and E roll. Hold S until pitch reads 90, then try A and E: they spin the dart the same way. No point comes closer than about 2.9 units to the viewer, so dividing by depth is safe.

Built-in versions: Unity's Quaternion.Euler(x, y, z) and transform.eulerAngles take pitch, yaw and roll in degrees, applied about z, then x, then y, the same order as here. Godot's Node3D.rotation_degrees holds the same three angles, but Godot's forward is −z, so some signs differ: test one known turn first.

Pitfalls

  • Mixing conventions. Engines and tools disagree on the order, on which axis is up, and on which way is positive. Three angles copied from a modelling program can give a different pose. Check one simple case, such as yaw 90°, by hand.
  • Degrees into sine. math.sin and math.cos want radians. Convert with math.rad, as eulerRotate does.
  • Angles wrap, and triples repeat. Yaw 190° is the same as yaw −170°. Worse, different triples can give the same pose: pitch 100° with yaw 20° and roll 10° equals pitch 80° with yaw 200° and roll 190°. That is why pitch is usually limited to −90° to 90°, and why an engine may give back different numbers from the ones you set.
  • Exactly 90° is not the only problem. Near the lock, small turns need large jumps in yaw and roll, so blending Euler angles can spin the long way round. First-person cameras usually clamp pitch to about ±89° and use no roll.
  • Adding to the angles. Adding to yaw turns about the world up axis, not the plane's own up. A ship that can loop needs another form; the next lesson shows one.

In real games

Engine editors show rotations as Euler angles because three numbers in degrees are easy to type: the rotation fields of a Unity Transform and a Godot Node3D work this way. Unreal Engine's FRotator stores pitch, yaw and roll.

Mouse-look cameras are the classic good use: yaw from sideways mouse movement, pitch from up and down, pitch clamped short of 90°, no roll. The name comes from real mechanical gimbals, as in compass mounts and navigation instruments, which can lock in the same way.

Your turn (15 minutes)

Make a mouse-look camera in LÖVE. Call love.mouse.setRelativeMode(true) in love.load. In love.mousemoved(x, y, dx, dy) add dx * 0.2 to yaw and dy * 0.2 to pitch, then clamp pitch to −89 to 89. Each frame compute forward = eulerRotate({x=0, y=0, z=1}, yaw, pitch, 0) and print it.

You are done when moving the mouse right makes forward.x grow, and moving it down stops at pitch 89 with forward.y at about −1.00. Check by hand: forward = (cos pitch · sin yaw, −sin pitch, cos pitch · cos yaw).

Takeaways

  • Euler angles store a 3D rotation as three turns: yaw about y, pitch about x, roll about z.
  • Each turn is a 2D rotation of the other two coordinates.
  • The order is part of the definition. Here it is roll, then pitch, then yaw, the same order Unity documents.
  • At pitch ±90° the roll axis lies on the yaw axis, so one kind of turn is lost: gimbal lock.
  • Euler angles suit typed-in numbers and cameras with clamped pitch, not free rotation or blending.

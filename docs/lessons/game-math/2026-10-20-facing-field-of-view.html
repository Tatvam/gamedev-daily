Field of view: can the guard see the player?

How comparing the dot product of two unit vectors with the cosine of half the view angle, plus a range check, gives a guard a real view cone.

In the last lesson the guard could tell "in front" from "behind". But a guard that spots you anywhere in the front half of the map, even far off to its side or a whole level away, has eyes no stealth game wants. Real guards see a narrow wedge: perhaps 90 degrees wide and 6 squares deep.

That wedge is called a view cone, and it takes one dot product, one cosine and one distance check.

What a view cone is

A view cone is the slice of space a character can see. In 2D it is a pie slice with its point on the guard. Three numbers describe it:

  • f, the facing: the direction down the middle of the slice.
  • The field of view (FOV): the full angle of the slice, from one edge to the other. We use 90°.
  • The view range: how far the guard can see. We use 6 squares.

The key number is half the field of view. A 90° cone reaches 45° to each side of the facing. So the question "is the player inside the slice?" becomes "is the angle between f and b, the arrow from guard to player, at most 45°?"

Angles into cosines

From the last lesson: when both arrows have length 1, their dot product is cos θ, the cosine of the angle between them. Making an arrow length 1 is normalising it: divide each part by the length.

Worked through for player A. The arrow from the guard is b = (4, −3). Its length is √(4² + 3²) = √25 = 5, so the unit arrow is (4 ÷ 5, −3 ÷ 5) = (0.8, −0.6). The facing f = (1, 0) already has length 1. The dot product is 1 × 0.8 + 0 × (−0.6) = 0.8.

For player B, b = (3, 4), also length 5, unit (0.6, 0.8), and the dot product is 1 × 0.6 + 0 × 0.8 = 0.6.

Now the trick. The cosine gets smaller as the angle grows: 1 at 0°, about 0.71 at 45°, 0 at 90°, −1 at 180°. So "the angle is at most 45°" means exactly the same as "the cosine is at least cos 45°". Written as a test:

unit f · unit b  ≥  cos(FOV ÷ 2)

Read it as: "the dot product of the two unit arrows is at least the cosine of half the field of view". The right-hand side is the threshold, the number the dot product has to reach. For a 90° cone it is cos 45° ≈ 0.71. A's 0.8 reaches it: seen. B's 0.6 does not. No arccos is needed, only one cosine for the cone itself.

Two thresholds to remember: FOV 180° gives cos 90° = 0, which is exactly yesterday's "dot product is positive" test, and FOV 360° gives cos 180° = −1, which every direction passes.

Range comes first

The angle test ignores distance: a player 50 squares away straight ahead passes it. So the guard also checks range, first, because it is cheaper. As in the length lesson, compare squared values and skip the square root. A's distance squared is 4² + 3² = 25, the range squared is 6² = 36, and 25 ≤ 36, so A is in range. Note that the dot product of a vector with itself, b · b, is its length squared; the code uses that.

Rule of thumb

Seen means two tests: distance squared ≤ range squared, and unit f · unit b ≥ cos(FOV ÷ 2). Use half the field of view, and give the cosine radians.

Flipping y in both arrows leaves their dot product unchanged, so the test works the same in a y-up world.

The code

The same guard and the same numbers. The player starts at guard + (4, −3), so the first frame says "Seen!"; then the player follows the mouse.

-- Positions are in grid squares. y grows downwards, like LÖVE's screen.
local UNIT = 40               -- pixels per grid square
local FOV_DEGREES = 90        -- the whole cone, edge to edge
local VIEW_RANGE = 6          -- in grid squares
local EDGE = 1e-9             -- lets points exactly on the edge count (see pitfalls)

local guard = { x = 5, y = 5, facing = { x = 2, y = 0 } }
local player = { x = 9, y = 2 }   -- guard + (4, -3)

local function dot(a, b)
  return a.x * b.x + a.y * b.y
end

local function normalise(v)
  local len = math.sqrt(dot(v, v))
  if len == 0 then
    return nil                -- a zero vector has no direction
  end
  return { x = v.x / len, y = v.y / len }
end

local function canSee(viewer, target, fovDegrees, range)
  local toTarget = { x = target.x - viewer.x, y = target.y - viewer.y }
  if dot(toTarget, toTarget) > range * range then
    return false              -- too far: skip the angle test
  end
  local f = normalise(viewer.facing)
  local b = normalise(toTarget)
  if not b then
    return true               -- standing on the viewer
  end
  if not f then
    return false              -- facing nowhere
  end
  local fov = math.max(0, math.min(fovDegrees, 360))
  local threshold = math.cos(math.rad(fov / 2))
  return dot(f, b) >= threshold - EDGE
end

function love.mousemoved(x, y)
  player = { x = x / UNIT, y = y / UNIT }
end

function love.draw()
  local gx, gy = guard.x * UNIT, guard.y * UNIT
  local seen = canSee(guard, player, FOV_DEGREES, VIEW_RANGE)
  local look = math.atan2(guard.facing.y, guard.facing.x)
  local half = math.rad(FOV_DEGREES / 2)
  if seen then
    love.graphics.setColor(0.2, 0.8, 0.3)
  else
    love.graphics.setColor(0.6, 0.6, 0.6)
  end
  love.graphics.arc("line", gx, gy, VIEW_RANGE * UNIT, look - half, look + half)
  love.graphics.setColor(1, 1, 1)
  love.graphics.circle("fill", gx, gy, 12)
  love.graphics.circle("line", player.x * UNIT, player.y * UNIT, 8)
  love.graphics.print(seen and "Seen!" or "Not seen", 10, 10)
end

Check it by hand: the facing (2, 0) normalises to (1, 0), and the player at (9, 2) gives toTarget = (4, −3), 25 is under 36, and dot(f, b) = 0.8 is above 0.707. At (8, 9) the dot product is 0.6: not seen.

Built-in versions: Godot has Vector2.normalized and Vector2.dot, Unity has Vector2.normalized and Vector2.Dot. In Unity, Vector2.Angle(facing, toTarget) <= fov / 2 does the angle test in degrees.

Pitfalls

  • Using the whole field of view. Forgetting the / 2 makes the cone twice as wide: a 90° setting sees 90° to each side.
  • Degrees into math.cos. Lua's math.cos takes radians. math.cos(45) is about 0.53, not 0.71, and nothing warns you. Convert with math.rad.
  • Forgetting to normalise. With f = (2, 0) and b = (4, −3), the raw dot product is 8, which passes any threshold. The comparison with a cosine only means something when both arrows have length 1.
  • Zero-length vectors. A player standing on the guard gives b = (0, 0), which has no direction; normalising would divide by 0. The code counts it as seen, and a facing of (0, 0) as seeing nothing. Choose on purpose.
  • Points exactly on the edge. Arithmetic rounds. At FOV 90° the player at (1, 1) is exactly on the edge, but its dot product comes out 0.7071067811865475, a hair under cos 45° = 0.7071067811865476. At 360° a player straight behind can score −1.0000000000000004. Subtracting the tiny EDGE lets the edge count as inside.
  • A field of view above 360°. The cosine wraps round: FOV 400° gives a half angle of 200°, and cos 200° ≈ −0.94, which is a narrower cone than 360°. Clamp to 0 to 360, as the code does.
  • Comparing angles from atan2 instead. A guard at 170° and a player at −170° differ by 340° if you subtract, but the real gap is 20°. The dot product has no such wrap problem.
  • The cone ignores walls. This test sees through rock. Games usually add a line-of-sight check (a ray cast against the level) only after the cone test passes, because ray casts cost more.

In real games

Stealth games are the obvious home: a guard that notices you only inside its cone, often drawn on screen, is this test plus a line-of-sight check. The same idea works unchanged in 3D with three-part vectors. An angle test like this one is also a common way to limit lock-on and aim assist to targets within some angle of where you are aiming, or to let a turret fire only once its target is nearly straight ahead.

Takeaways

  • A view cone is a facing, a field of view and a range.
  • Inside the angle means unit f · unit b ≥ cos(FOV ÷ 2). Bigger dot product, smaller angle.
  • Use half the field of view, in radians, and normalise both arrows first.
  • Check range first with squared distances; it is cheaper and rules out most targets.
  • Decide what zero-length arrows mean, clamp the FOV to 360°, and allow a tiny tolerance at the edge.

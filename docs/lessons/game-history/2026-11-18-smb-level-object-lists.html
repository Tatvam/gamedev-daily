Super Mario Bros.: a level is a list, not a picture

How Super Mario Bros. fitted its levels in a 40 KB cartridge by storing short lists of two-byte objects instead of full tile grids.

Super Mario Bros. (1985) has 32 levels, plus its music, its graphics and all of its code, on a cartridge of 40 kilobytes. A single photo on a phone is usually far bigger than that.

The levels fit because the cartridge does not store what they look like. It stores short instructions for building them, such as "a row of five bricks here" or "a pipe there".

The constraint: 40 kilobytes for everything

The cartridge holds two memory chips. One has 32 KB of program: the code, the music and the level data. The other has 8 KB of graphics: the 8 by 8 pixel tiles that every picture on screen is made from. The levels have to share the 32 KB with everything else in the game.

The game builds its world from metatiles: 16 by 16 pixel blocks, each made of four tiles. A brick, a question block or a piece of ground is one metatile. A level is a grid of these blocks, 13 rows tall in the play area below the score line.

The obvious way: store the grid

The simplest format is a tile grid: one byte per cell, naming the block in that cell. A screen is 16 blocks wide, so each screen-wide slice of the level costs 16 × 13 = 208 bytes. A level a dozen screens long would cost about 2.5 KB, and 32 such levels would need about 80 KB. That is more than twice the whole cartridge, before a single line of code.

Most of those bytes just say "sky" or "ground".

The trick: store objects

Super Mario Bros. stores each area as an object list: a short header, then a run of objects, then an end marker. As the community disassembly of the game describes it, every object takes two bytes, holding its position, its type and, for things that come in rows or columns, a length. The game's code then draws each object into the grid.

So "eight bricks in a row" is not eight bytes. It is two bytes: "bricks, here, length 8". A pipe is two bytes however tall it is. The ground is not stored cell by cell at all: the header describes it, and gaps are objects that remove it.

Pages keep the numbers small

Four bits can only count to 15, but a level is hundreds of columns long. The answer is pages: the level is cut into screen-wide pieces of 16 columns. Objects are listed from left to right, and each one stores only its column inside the current page. One bit in the second byte says "this object is on the next page". The decoder keeps a page counter and adds 16 columns each time that bit is set.

The demo on this page uses its own simplified version of this idea, so that you can read every bit. The real game's format has more types and uses some row values as special commands, for example to change the scenery or to mark where a pipe leads. Enemies are kept in a separate list.

The trade

An object list is tiny on disk but must be run through code before it is a level. A grid is large but ready to use. Super Mario Bros. paid in code and processor time to save storage, which on a 1985 cartridge was the scarcest resource.

The code

This decoder reads the same format as the demo, with the same type numbers. It starts with sky and ground, then reads two bytes at a time until it meets the end marker 0xFD. Rows and columns are stored from 0 and turned into Lua's 1-based indexes.

-- Tile ids in the decoded grid
local SKY, GROUND, BRICK, QBLOCK, COIN, PIPE, BLOCK = 0, 1, 2, 3, 4, 5, 6
local ROWS = 13

local function set(grid, r, c, v)
  if grid[r] and grid[r][c] then grid[r][c] = v end   -- ignore cells off the map
end

local function placeObject(grid, kind, col, row, len, floorRow)
  for k = 0, len - 1 do
    local c = col + k
    if kind == 0 then set(grid, row, c, BRICK)
    elseif kind == 1 then set(grid, row, c, QBLOCK)
    elseif kind == 2 then set(grid, row, c, COIN)
    elseif kind == 4 then                                -- stairs rise to the right
      for r = floorRow - k, floorRow do set(grid, r, c, BLOCK) end
    elseif kind == 5 then                                -- gap: remove the ground
      for r = floorRow + 1, ROWS do set(grid, r, c, SKY) end
    end
  end
  if kind == 3 then                                      -- pipe: 2 wide, down to the floor
    for r = row, floorRow do set(grid, r, col, PIPE); set(grid, r, col + 1, PIPE) end
  end
end

function decodeArea(bytes)
  local pages, groundRows = bytes[1], bytes[2]           -- the 2-byte header
  local floorRow = ROWS - groundRows
  local grid = {}
  for r = 1, ROWS do
    grid[r] = {}
    for c = 1, pages * 16 do
      if r > floorRow then grid[r][c] = GROUND else grid[r][c] = SKY end
    end
  end
  local page, i = 0, 3
  while bytes[i] and bytes[i] ~= 0xFD do
    local b1, b2 = bytes[i], bytes[i + 1]
    if b2 >= 128 then page = page + 1 end                -- the "next page" bit
    local col = page * 16 + math.floor(b1 / 16) + 1
    local row = b1 % 16 + 1
    local kind = math.floor(b2 / 16) % 8
    local len = b2 % 16 + 1
    placeObject(grid, kind, col, row, len, floorRow)
    i = i + 2
  end
  return grid
end

-- The demo's starting level: 21 bytes instead of 416
local level = decodeArea({ 0x02, 0x02,
  0x47, 0x10,  0x87, 0x04,  0xA7, 0x10,  0xA3, 0x10,  0xE9, 0x30,
  0x16, 0xA3,  0x3B, 0x51,  0x78, 0x30,  0xAA, 0x43,  0xFD })

Pitfalls

  • Order matters. Later objects overwrite earlier ones. In the demo the bricks at column 8 come first, so the question block at column 10 can replace one of them. If the bricks came after it, the question block would vanish under them.
  • The list must be sorted. Pages only work if objects are listed left to right. An object that belongs on an earlier page cannot be reached once the page counter has moved on.
  • Random access is slow. To know what is in column 200 you must read the list up to it. Decode into a grid (all at once, or a few columns ahead of the camera) before the game needs to check collisions.
  • Small fields set hard limits. With four bits a row of bricks can be at most 16 long. A longer run needs two objects. Choose field sizes from the levels you actually want to build.

In real games

Describing a level as placed objects instead of cells is how most modern engines save scenes. A Godot .tscn file or a Unity scene lists objects with their positions and settings; it does not store every point in space.

The constraint itself returns wherever size matters. Web games pay for every byte the player downloads before playing. Games that let players share their own levels often turn them into short codes or small files, and an object list is far smaller than a grid. Shared editors can send "placed a pipe at column 14" rather than the whole map.

Takeaways

  • A level grid spends the same space on empty sky as on content. An object list spends space only on things that are there.
  • Super Mario Bros. stores each object in two bytes: position, type and length.
  • Pages let a 4-bit column cover a long level: objects go left to right, and one bit says "next page".
  • The cost is decoding: the list must be run through code, in order, before the game can use it.

Crash Bandicoot: a level bigger than memory, read one page at a time

How Crash Bandicoot ran levels far bigger than the PlayStation's 2 MB: cut them into 64 KB pages and read the next ones from the disc as you run.

In Crash Bandicoot you run down a long jungle path with no loading screen until the end of the level. The PlayStation could not hold that whole level in memory. The part of the path in front of you was still on the disc a few seconds earlier, and the part behind you has already been thrown away.

The constraint: 2 MB of memory, 650 MB of disc

The original PlayStation (1994) has 2 MB of main memory, plus 1 MB of video memory and 512 KB for sound. Its CD-ROM drive holds about 650 MB and, at double speed, reads about 300 KB per second. So the console has a lot of storage, very little memory, and a slow pipe between them.

Naughty Dog's Crash Bandicoot (1996) wanted detailed levels. By co-founder Andy Gavin's own account, the data for one level was far larger than the memory left over once the game code, sound and other systems had taken their share. Loading the whole level before play, the usual approach, could not work.

The trick: fixed-size pages and a path you can predict

Gavin describes a system that cut each level's data into pages, fixed-size blocks of 64 KB each. Memory held a small set of page slots. As Crash moved along the level, the game read the pages he would need soon from the disc into free slots, and freed the slots holding pages he had left behind. Programmers call this paging or streaming: only a moving window of the data is in memory at any moment.

Two things made it work.

  • Fixed-size pages. Every page fits every slot, so freeing one page always makes room for the next. Memory never breaks into odd-sized gaps that are too small to use.
  • A predictable route. Crash levels are mostly corridors that you run along in one direction. If you know where the player is on the path, you know which pages come next, so the disc can start reading them early.

The race between the runner and the disc

Streaming turns the level into a race. Each 64 KB page takes about 64 ÷ 300 ≈ 0.21 seconds to read at 300 KB/s, so the disc can deliver at most about 4.7 pages per second. If the player crosses pages faster than that, the window of loaded pages shrinks until the player reaches a page that is not there yet. Then the game must wait, which the player sees as a freeze or hitch.

More memory does not change that speed limit. It only gives a bigger head start. Memory decides how long you can survive a burst of fast movement; disc speed decides how fast you can move forever.

Rule of thumb

A stream keeps up when the data the player uses per second is less than the data the disc delivers per second. Memory is the buffer that covers the moments when it is not.

The code

The same rules as the demo, with the same names and numbers. The disc reads one page at a time into a free slot, freeing the page furthest behind the player when memory is full. The runner moves only onto pages that are already in memory. Drawing is left out.

local PAGE_KB = 64
local LEVEL_PAGES = 40
local slots = 6          -- memory for level pages: 6 x 64 KB
local discKBps = 300     -- double-speed CD
local runSpeed = 2       -- pages per second
local lookahead = true   -- false: read a page only when the player needs it

local pos, waited, finished = 0, 0, false
local resident, count = {}, 0   -- resident[page] = true once it is in memory
local loading, progress = nil, 0

local function wanted(page, p)
  if lookahead then return page >= p - 1 and page <= p + slots - 2 end
  return page == p
end

local function nextToLoad(p)
  local last = p
  if lookahead then last = math.min(p + slots - 2, LEVEL_PAGES - 1) end
  for page = p, last do
    if not resident[page] then return page end
  end
  return nil
end

local function freeSlot(p)
  if count < slots then return true end
  local oldest = nil                 -- the unwanted page furthest behind
  for page in pairs(resident) do
    if not wanted(page, p) and (oldest == nil or page < oldest) then oldest = page end
  end
  if oldest == nil then return false end
  resident[oldest] = nil
  count = count - 1
  return true
end

function love.update(dt)
  if finished then return end
  local step = runSpeed * dt
  local p = math.floor(pos + step)   -- the page the player is about to stand on
  if p >= LEVEL_PAGES then finished = true return end

  if loading == nil then             -- the disc: start the next read
    local page = nextToLoad(p)
    if page and freeSlot(p) then loading, progress = page, 0 end
  end
  if loading then
    progress = progress + dt
    if progress >= PAGE_KB / discKBps then
      resident[loading] = true
      count = count + 1
      loading = nil
    end
  end

  if resident[p] then                -- the player: only onto loaded pages
    pos = pos + step
  else
    waited = waited + dt
    pos = math.max(pos, p - 0.0001)  -- stop at the border and wait
  end
end

function love.draw()
  love.graphics.print(("page %d, waited %.2f s"):format(math.floor(pos), waited), 10, 10)
end

Only one read runs at a time, and freeSlot makes room before it starts, so the pages in memory plus the one being read never exceed slots. A real engine would read on a background thread and hand the finished page over; the timing logic stays the same.

Pitfalls

  • Treating memory as the cure for hitches. If the player uses data faster than the disc supplies it, a bigger buffer only moves the hitch later. Fix the rate: smaller pages for the fast sections, compression, or a slower path through them.
  • Forgetting the seek. On an optical disc the read head has to move to the data before it can read, and that move costs far more than reading the next block in line. Pages that are read one after another should sit one after another on the disc.
  • Dropping a page the player can return to. The demo keeps one page behind the runner. If players can turn round, the window must reach backward too, and that memory is not available for reading ahead.

In real games

Crash Bandicoot is the case told here, from Andy Gavin's recollections. The general idea, keeping a window of the world in memory and reading the rest as the player moves, is now standard. Unreal Engine has level streaming and World Partition, which load and unload regions around the player. Unity can load scenes in the background with SceneManager.LoadSceneAsync, and Godot can load resources on a background thread with ResourceLoader.load_threaded_request.

The constraint is back on the web and on phones: a browser game that downloads its first level and fetches the rest while you play is paging over a network, and the network plays the part of the slow disc.

Takeaways

  • Crash Bandicoot's levels were larger than the PlayStation's memory, so they were cut into fixed 64 KB pages and read from the disc during play.
  • A predictable path lets the game read the next pages before the player needs them.
  • Fixed-size pages mean any freed slot can take any new page.
  • Disc speed sets how fast a player can move for ever; memory only sets how long a burst can last.
  • Modern engines stream the same way, from SSDs, discs and networks.

Donkey Kong Country: 3D renders squeezed into Super Nintendo sprites

How Donkey Kong Country put 3D-looking characters on a 2D console: render on a workstation, shrink, cut to hard edges and 15 colours, store as tiles.

In 1994 Donkey Kong Country looked like nothing else on the Super Nintendo. Its characters had soft shading, shiny highlights and round, solid forms. Yet it ran on the same console as every other game, and unlike Star Fox, the cartridge had no extra graphics chip. Every frame of every character was a flat sprite, made in advance on a far more powerful computer and squeezed into the console's rules.

The constraint: small, flat pictures with 15 colours each

The Super Nintendo draws characters as sprites: small pictures it can place anywhere on screen. A sprite is built from tiles, blocks of 8 by 8 pixels. One sprite can be at most 64 by 64 pixels, so a large character is put together from several.

Each sprite pixel is stored as a 4-bit number, an index into a palette (a short list of colours). A palette has 16 entries, and entry 0 always means "transparent". That leaves 15 real colours per sprite. The console knows 32,768 colours (5 bits each for red, green and blue), but all sprites on screen share just 8 such palettes.

At 4 bits per pixel, one tile takes 32 bytes. Everything the picture chip draws from, the tiles of sprites and backgrounds and the maps that place them, must fit in 64 KB of video memory.

The console cannot rotate or light a model, so every pose and angle must be its own stored picture. And a sprite pixel is either fully drawn or fully transparent, with nothing in between to smooth an edge.

A picture rendered by 3D software has any size, millions of colours, and anti-aliased edges, where pixels the shape only partly covers are stored as partly transparent so the outline looks smooth.

The trick: render on a workstation, then convert

Rare, the British studio that made the game, built and animated its characters as 3D models. Development accounts agree that this was done on Silicon Graphics workstations, and several name Alias PowerAnimator as the software. Nintendo marketed the result as ACM, Advanced Computer Modeling.

The models never reach the console. Each frame of each animation is rendered at high quality, then pushed through a conversion that turns it into something the sprite hardware can show:

  1. Render the frame on the workstation, in full colour with smooth edges.
  2. Shrink it to sprite size. Each small pixel becomes the average of a block of big ones, which keeps the shading smooth.
  3. Harden the edges. Every pixel becomes either solid or transparent, because the sprite hardware has nothing in between.
  4. Reduce the colours to 15 chosen for this picture, each rounded to the console's 5 bits per channel. Every pixel is then replaced by the index of its nearest palette colour.
  5. Cut into tiles of 8 by 8 and store them in the cartridge. Tiles that are entirely transparent need not be stored at all.

Why does the shading survive with only 15 colours? Because the palette is chosen for the picture. A model made of a few materials, each lit from one direction, contains a few hues in many brightnesses. Fifteen well-chosen steps of those hues still read as a rounded surface.

The reduction method used here is median cut, a standard technique: put all the picture's colours in one box, split the box across its widest colour channel at the middle value, and repeat until there are 15 boxes. The average of each box becomes a palette colour. Rare's own conversion tools are not described in the sources behind this page, so treat median cut as a stand-in, not as what Rare used. Retrospectives also say Rare wrote its own compression to fit all these frames on the cartridge; how it worked is not covered here.

The idea in one line

Do the expensive work where you have power and time, then bake the result into the exact format the weak machine already knows how to show.

The lesson for today

Baking is everywhere. Games render distant trees from 3D into flat impostors, pictures on a card that stand in for the model. Lighting is calculated in advance into textures. 2D games such as Dead Cells animate 3D models and render them to pixel-art frames. The questions are the same as Rare's: what size, how many colours, how many frames, and what happens at the edges.

The code

This is the conversion as an offline tool. A render is a list of pixels {r, g, b, a} from 0 to 1, with colour already multiplied by coverage a (premultiplied), so averaging a block gives correct edge colours. loadRender is your own image loader. The sizes and the 0.5 edge threshold match the demo.

local HI, SIZE, COLOURS = 192, 48, 15   -- render, sprite, colours besides transparent

local function shrink(img)               -- average each f by f block
  local f, out = HI / SIZE, {}
  for y = 0, SIZE - 1 do
    for x = 0, SIZE - 1 do
      local s = {0, 0, 0, 0}
      for sy = 0, f - 1 do
        for sx = 0, f - 1 do
          local p = img[(y * f + sy) * HI + x * f + sx + 1]
          for c = 1, 4 do s[c] = s[c] + p[c] / (f * f) end
        end
      end
      out[y * SIZE + x + 1] = s
    end
  end
  return out
end

local function medianCut(colours, k)     -- split the widest box at its middle
  local boxes = {colours}
  while #boxes < k do
    local best, range, ch = nil, 0, 1
    for i, box in ipairs(boxes) do
      for c = 1, 3 do
        local lo, hi = 1, 0
        for _, p in ipairs(box) do lo, hi = math.min(lo, p[c]), math.max(hi, p[c]) end
        if hi - lo > range then best, range, ch = i, hi - lo, c end
      end
    end
    if not best then break end           -- fewer distinct colours than k
    local box = table.remove(boxes, best)
    table.sort(box, function (a, b) return a[ch] < b[ch] end)
    local low, high = {}, {}
    for i, p in ipairs(box) do
      if i <= #box / 2 then low[#low + 1] = p else high[#high + 1] = p end
    end
    boxes[#boxes + 1] = low
    boxes[#boxes + 1] = high
  end
  local palette = {}
  for i, box in ipairs(boxes) do
    local s = {0, 0, 0}
    for _, p in ipairs(box) do for c = 1, 3 do s[c] = s[c] + p[c] / #box end end
    for c = 1, 3 do s[c] = math.floor(s[c] * 31 + 0.5) / 31 end  -- 5 bits a channel
    palette[i] = s
  end
  return palette
end

local function nearest(palette, p)
  local best, bestD = 1, math.huge
  for i, q in ipairs(palette) do
    local d = (p[1] - q[1]) ^ 2 + (p[2] - q[2]) ^ 2 + (p[3] - q[3]) ^ 2
    if d < bestD then best, bestD = i, d end
  end
  return best
end

local function convert(render)
  local pixels, opaque = shrink(render), {}
  for i = 1, SIZE * SIZE do
    local p = pixels[i]
    if p[4] >= 0.5 then                  -- hard edge: solid or nothing
      pixels[i] = {p[1] / p[4], p[2] / p[4], p[3] / p[4]}
      opaque[#opaque + 1] = pixels[i]
    else
      pixels[i] = false
    end
  end
  local palette = medianCut(opaque, COLOURS)
  local indices = {}                     -- 0 = transparent, 1 to 15 = palette
  for i = 1, SIZE * SIZE do
    indices[i] = pixels[i] and nearest(palette, pixels[i]) or 0
  end
  return indices, palette
end

function love.load()

end

Packing the indices into 8 by 8 tiles at 32 bytes each is bookkeeping on top.

Pitfalls

  • A palette per frame. The demo picks fresh colours for each angle, so they shift as you turn it. Sprites on screen share 8 palettes, so a real character needs one palette chosen from all its frames together, or it flickers between colour sets as it animates.
  • Rendering over a background colour. Render onto a coloured backdrop and the edge pixels mix in that colour, leaving a halo around the sprite in game. Render with transparency, as the demo does.
  • Shrinking by skipping pixels. Taking every fourth pixel instead of averaging gives jagged, noisy shading.
  • Losing the highlight. Keeping only the most common colours drops small bright spots, the very thing that makes a surface look shiny. Median cut splits on range, so highlights tend to keep a colour.
  • Memory grows with frames times angles. A 48 by 48 sprite is under a kilobyte, but twenty animations of a dozen frames is hundreds. Budget frames before rendering them.

In real games

Rare used the same approach for Donkey Kong Country 2 and 3 and for Donkey Kong Land on the Game Boy, and for the arcade fighter Killer Instinct, whose fighters were pre-rendered models. On PC, Diablo and StarCraft drew their units as sprites rendered from 3D models. More recently, Dead Cells animates 3D models and renders them to low-resolution frames.

Your turn (15 minutes)

Change convert so it takes a list of renders, all the frames of one animation, collects the opaque colours of every frame into one list, and builds a single shared palette from it. You are done when every frame comes out as indices into the same 15 colours, and the animation no longer changes colour from frame to frame.

Takeaways

  • Donkey Kong Country's characters were 3D models rendered on workstations, not drawn by the console.
  • Each render was shrunk, given hard edges and reduced to 15 colours plus transparent, the rules of a Super Nintendo sprite.
  • A palette chosen for the picture keeps smooth shading with very few colours.
  • Every pose and angle is a separate stored frame, so memory, not drawing speed, is the limit.
  • Baking expensive results offline into the target's native format is still a core technique.

Quake's lightmaps: light and shadow baked into a grid of bytes

How Quake lit its world: a tool stored one brightness byte every 16 texels on each surface, and the game multiplied that grid over the textures.

In Quake a lamp throws a soft pool of light on the floor, and a pillar casts a shadow across it. The floor may be one large polygon, and the game does no lighting maths for that shadow while you play. The light was worked out before the level shipped and stored in a small grid of numbers.

The constraint: light that lives on the corners

Quake (1996) drew its world in software, in 256 colours, on the processor of mid-1990s PCs such as the Pentium. Michael Abrash, who worked on the engine with John Carmack, writes that the game was meant to run on a machine with 8 MB of memory.

The early engine used Gouraud shading: work out the brightness at each corner (vertex) of a polygon and blend it across the inside. That ties light to geometry. A pool of light under a lamp needs a vertex under the lamp, and a sharp shadow edge needs many small polygons. Abrash also describes floors whose lighting "would shimmy and shift" as the player turned. More polygons meant a bigger level and a slower game.

The trick: a separate grid of light for every surface

Abrash credits Carmack with the fix: split lighting from geometry. Every wall, floor and ceiling polygon gets a lightmap, a grid of brightness values with one value every 16 texels (texture pixels) in each direction, about two feet in Quake's world. Each value is one byte of brightness, with no colour.

Baking: done once, by a tool

Baking means calculating something slow ahead of time and saving the answer. In the released source, Quake's light tool does this for every sample point and every light:

  1. Trace a line from the light to the point. If geometry blocks it, the point is in shadow.
  2. Otherwise add light value − distance, so brightness falls in a straight line to zero. The default light value is 300.
  3. Scale that by 0.5 + 0.5 × cos of the angle, so grazing light counts less.

The sum is halved and capped at 255. An -extra option averages four samples per point to soften jagged shadow edges, filtering Abrash says Billy Zelsnack suggested.

Drawing: the surface cache

Before a surface is drawn, the engine tiles its texture into a buffer and multiplies each texel by the light there, blended from the four nearest lightmap values (bilinear blending). The lit surface is then drawn with no lighting work and kept in a cache while it stays in view. Abrash reports 2.25 cycles per lit texel, and 600 KB of cache being enough at 320 by 200.

Flickering lights without re-baking

A surface can carry up to four lightmaps, each tagged with a light style: a string of letters played at ten a second, where a is dark, m normal and z double. Style 1, the flicker, is mmnmmommommnonmmonqnmmo. The engine turns the current letter into a scale for that lightmap:

local function styleScale(style, time)
  local k = math.floor(time * 10) % #style + 1
  return (string.byte(style, k) - string.byte("a")) * 22 / 256
end

The bake stays fixed; only the scale moves. But each change forces the surfaces using it to be rebuilt, and Abrash warns that lighting changing everywhere at once defeats the cache.

The lesson for today

Bake what does not move. A phone or browser pays for every real-time light every frame; a baked lightmap costs one texture read per pixel however many lights went into it, and can be small because light changes slowly across a surface.

The code

The same bake and the same surface build as the demo, with the same numbers. bake runs once; buildSurface runs again only when the lighting changes; love.draw just draws the cached image. Any 64 by 64 texture tile will do.

local SPACING, W, H = 16, 256, 160   -- one sample every 16 texels; floor is 256 by 160
local LIGHT_HEIGHT = 48              -- lamps hang 48 units above the floor
local lights  = { { x = 60, y = 44, power = 300 }, { x = 204, y = 120, power = 300 } }
local pillars = { { x = 112, y = 56, w = 24, h = 24 }, { x = 176, y = 24, w = 16, h = 40 },
                  { x = 40, y = 104, w = 32, h = 12 } }
local lightmap, cols, rows, texture, surface

local function inShadow(L, sx, sy)   -- walk from lamp to sample in 1-texel steps
  local dx, dy = sx - L.x, sy - L.y
  local steps = math.ceil(math.sqrt(dx * dx + dy * dy))
  for k = 1, steps - 1 do
    local px, py = L.x + dx * k / steps, L.y + dy * k / steps
    for _, b in ipairs(pillars) do
      if px > b.x and px < b.x + b.w and py > b.y and py < b.y + b.h then return true end
    end
  end
  return false
end

local function bake()                -- Quake did this offline, once per level
  cols, rows = W / SPACING + 1, H / SPACING + 1
  lightmap = {}
  for j = 0, rows - 1 do
    for i = 0, cols - 1 do
      local sx, sy, sum = i * SPACING, j * SPACING, 0
      for _, L in ipairs(lights) do
        if not inShadow(L, sx, sy) then
          local dx, dy = sx - L.x, sy - L.y
          local dist = math.sqrt(dx * dx + dy * dy + LIGHT_HEIGHT * LIGHT_HEIGHT)
          local angle = 0.5 + 0.5 * LIGHT_HEIGHT / dist
          sum = sum + math.max(0, (L.power - dist) * angle)
        end
      end
      lightmap[j * cols + i + 1] = math.min(255, math.floor(sum * 0.5))  -- one byte
    end
  end
end

local function sample(i, j) return lightmap[j * cols + i + 1] end

local function lightAt(x, y)         -- blend the four nearest samples
  local fx, fy = x / SPACING, y / SPACING
  local i = math.min(math.floor(fx), cols - 2)
  local j = math.min(math.floor(fy), rows - 2)
  local u, v = fx - i, fy - j
  local top = sample(i, j) * (1 - u) + sample(i + 1, j) * u
  local bottom = sample(i, j + 1) * (1 - u) + sample(i + 1, j + 1) * u
  return top * (1 - v) + bottom * v
end

local function buildSurface()        -- the surface cache: texture times light
  local img = love.image.newImageData(W, H)
  for y = 0, H - 1 do
    for x = 0, W - 1 do
      local r, g, b = texture:getPixel(x % 64, y % 64)
      local k = math.min(2, lightAt(x + 0.5, y + 0.5) / 128)
      img:setPixel(x, y, math.min(1, r * k), math.min(1, g * k), math.min(1, b * k), 1)
    end
  end
  surface = love.graphics.newImage(img)
end

function love.load()
  texture = love.image.newImageData("bricks64.png")
  bake()
  buildSurface()
end

function love.draw()
  love.graphics.setColor(1, 1, 1)
  love.graphics.draw(surface, 0, 0, 0, 3, 3)   -- no lighting maths per frame
end

The bake casts a line from every lamp to every sample. The draw does no lighting at all. Rebuilding the surface costs one blend per texel, which is why it is cached. The demo also multiplies each lightmap by its style scale; for the steady style m that is 264/256, just over 1.

Pitfalls

  • Samples inside walls. Some sample points fall inside solid geometry, come out black and bleed into the floor beside them. Quake's tool nudges them towards the middle of the face, and a comment there admits this does not always work. Try 32 texels and look at the pillar edges.
  • Choosing the spacing. Coarse grids blur shadows; fine grids cost memory and bake time, growing with the square of the resolution.
  • Moving things get no lightmap. Abrash describes Quake lighting each monster from how bright the floor is where it stands. Modern engines use baked light probes.
  • Changing lights force rebuilds. Light styles and dynamic lights, such as a flying rocket's glow, invalidate cached surfaces. Keep them few.
  • Seams. Each surface has its own grid, so neighbours can disagree along a shared edge.

In real games

Quake's light tool, the surface builder and the light style strings are all in id Software's released source. GLQuake, the OpenGL version, skipped the surface cache: it packs lightmaps into 128 by 128 textures and draws them as a second pass that multiplies the colour already on screen. Abrash writes that Quake 2 added radiosity to the preprocessor, letting light bounce. Unity, Unreal Engine and Godot all ship lightmap bakers today.

Take a static room in your own project with two or three lights. You are done when you can say how many bytes each spacing stores and point at one place where the coarse version shows a shadow leak.

Takeaways

  • Gouraud shading tied light to vertices, so detailed light needed more polygons; Quake gave each surface its own light grid instead.
  • A tool traced every light to a sample every 16 texels and stored one byte per sample, shadows included.
  • At run time the texture was multiplied by the blended lightmap into a cached surface, with no per-pixel lighting while drawing.
  • Light styles scale whole lightmaps for flicker and pulses, at the cost of rebuilding surfaces.
  • The grid is coarse on purpose: light changes slowly, so a few hundred bytes can light a whole wall.

Resident Evil's doors: a loading screen you watch on purpose

How Resident Evil hid each room's load from the CD behind a slow door animation, and why the animation must wait for the load to finish.

In the first Resident Evil, released by Capcom for the PlayStation in 1996, every new room begins the same way. The screen goes dark, a door fills the view, and it creaks open slowly while you wonder what is on the other side. Players remember those few seconds as some of the tensest in the game. They are also a loading screen.

The constraint: every room comes off a CD

The PlayStation had 2 MB of main memory and a double-speed CD-ROM drive that reads about 300 KB per second. Resident Evil shows its rooms from fixed camera angles over pre-rendered backgrounds: pictures drawn in advance, with the 3D characters placed on top. Each room needs its own pictures, models and sounds.

The whole mansion could not fit in memory at once, so the game loads one room at a time. When the player leaves a room, the next one has to be read from the disc. A read like that is not instant. Before any data flows, the drive must move its read head to the right place on the disc, which is called a seek. Then the bytes arrive at the drive's transfer rate. A room of several hundred kilobytes therefore takes a few seconds.

Something has to be on screen during those seconds. A black screen with a progress bar works, but it stops the game cold.

The trick: make the wait part of the game

Resident Evil shows a short scene of a door opening instead. The scene is small, one door and a moving camera, so it can stay in memory and needs nothing from the disc. While it plays, the drive reads the next room.

The scene is a masking transition: an animation whose real job is to cover work the player should not see. Two details make it work.

  1. It starts the load first. The disc read begins the moment the player touches the door, and the animation plays on top of it. Nothing waits for the animation to start.
  2. It finishes only when both are done. The door scene has a set length, but the next room cannot appear until its data is in memory. If the load is slower than the animation, the game has to hold on the last moment, usually a dark doorway, until the read completes.

The animation sets a minimum wait and the disc sets the rest. A designer picks a door length that covers most rooms and accepts a short hold for the largest.

Where the idea came from

Director Shinji Mikami has said in interviews that the door scenes came from Sweet Home, a 1989 Capcom horror game for the Famicom that also showed doors opening between areas. In a translated interview reported by fan sites, he describes the PlayStation leaving the screen black while it loaded a room, and realising that a door scene would hide that and build tension at the same time. I could not open the original interview, so treat that account as reported, not quoted. That the doors cover loading is not in doubt; it is how the scenes behave on the hardware.

Rule of thumb

Start the slow work first, then play something worth watching on top of it. Finish when both are done, not when either one is.

The code

The demo's door logic in Lua, with the same rooms and numbers on the 2x drive. The disc read is simulated by a timer here. In a real LÖVE game you would start the read on a background thread with love.thread and check whether it has finished.

local SEEK_S = 0.2              -- move the read head
local DISC_KB_PER_S = 300       -- double-speed CD drive
local DOOR_S = 3.0              -- length of the door scene

local ROOMS = {
  { name = "Hall", kb = 520 },   { name = "Library", kb = 760 },
  { name = "Gallery", kb = 420 }, { name = "Cellar", kb = 900 },
}
local current, door = 1, nil    -- door is the transition in progress

local function openNextDoor()
  local target = current % #ROOMS + 1
  local load = SEEK_S + ROOMS[target].kb / DISC_KB_PER_S  -- read starts
  door = { target = target, t = 0, load = load }
end

local function drawDoor(p)      -- p goes from 0 to 1
  local s = math.max(0, math.min(1, (p - 0.2) / 0.5))
  local angle = s * s * (3 - 2 * s) * math.rad(80)
  love.graphics.setColor(0.42, 0.37, 0.32)
  love.graphics.rectangle("fill", 300, 150, 200 * math.cos(angle), 300)
  love.graphics.setColor(1, 1, 1)
end

function love.keypressed(key)
  if key == "space" and door == nil then openNextDoor() end
end

function love.update(dt)
  if door == nil then return end
  door.t = door.t + dt
  if door.t >= DOOR_S and door.t >= door.load then  -- both
    current = door.target
    door = nil
  end
end

function love.draw()
  if door then
    drawDoor(math.min(door.t / DOOR_S, 1))
  else
    love.graphics.print("Room: " .. ROOMS[current].name, 10, 10)
  end
end

The load times come out at 2.7 seconds for the Library, 1.6 for the Gallery, 3.2 for the Cellar and 1.9 for the Hall. Only the Cellar is slower than the 3 second door, so only the Cellar holds, for 0.2 seconds.

Pitfalls

  • Ending on the animation, not the load. If the room appears when the door finishes, a slow disc shows a half-loaded room or crashes. The finish condition must check both.
  • Starting the load after the animation. Then the player watches the door and the bar, one after the other, and the trick costs time instead of hiding it.
  • A door that is too long. On fast storage the animation becomes pure waiting. The door length is a floor on every transition, so set it from your slowest common case, not your worst one.
  • Loading the animation itself from disc. The masking scene must already be in memory.

In real games

Capcom kept the door scenes in Resident Evil 2 (1998) and in the 2002 GameCube remake of the first game, where they had become part of the series' identity as much as a technical need.

The pattern appears wherever loading hides inside the world. Long elevator rides in the first Mass Effect (2007) are widely reported to have covered loading, and in Metroid Prime (2002) doors are commonly described as waiting to open until the next room has streamed in.

The lesson for today: on the web and on phones, the network is the slow disc. Start fetching the next screen as soon as the player shows intent, play a short transition that is already in memory, and end it when both are ready. Keep it short, so fast connections do not pay for slow ones.

Then add a cached table: after a room has been loaded once, its load time becomes zero, and the door plays at half length when the room is cached. You are done when walking the loop twice is visibly faster the second time, and you can say which room still holds and why.

Takeaways

  • Resident Evil loaded each room from the PlayStation's CD while a door-opening scene played.
  • A masking transition starts the load first and ends only when both the load and the animation are done.
  • The player waits for the longer of the two, so the animation length is a minimum wait on every door.
  • The idea survives in elevators, squeeze-through gaps and web page transitions: hide latency behind something worth watching.

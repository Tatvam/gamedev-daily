Another World: a whole game drawn from lists of points

How Another World fit cinematic animation on two floppy disks: shapes stored as a few points and filled row by row at play time, not as pixels.

Another World (Eric Chahi, published by Delphine Software in 1991, and sold in North America as Out of This World) opens like a film, with camera cuts and close-ups. Stored as pictures, that would have filled a stack of floppy disks. The game stores almost none of it as pictures.

The constraint: pictures are expensive

The game draws a 320 by 200 pixel screen in 16 colours. Sixteen colours need 4 bits a pixel, so one full screen is 320 × 200 ÷ 2 = 32,000 bytes. The English Amiga version is two floppy disk images of 901,120 bytes (880 KB) each.

One minute of full-screen animation at 12 pictures a second is 720 pictures: 23,040,000 bytes, over twelve times what both disks hold.

The trick: store the outline, fill it at play time

Instead of pixels, the game stores polygons: flat shapes described by their corner points. A hill is not 7,200 bytes of pixels but a box size and six points, filled row by row as the scene plays. A scene is a draw list: an ordered list of "draw this shape here" commands, painted back to front so later shapes cover earlier ones.

In the open-source reimplementation of the engine, each shape is stored as:

  • one byte for the width of its bounding box and one for the height,
  • one byte for the number of points, which is always even,
  • two bytes per point, x and y, measured from the box's top-left corner.

The order of the points is the clever part. The first half go down the right side; the second half come back up the left. Point 1 and the last point sit at the same height, as do point 2 and the second to last, and so on. So the filler never sorts edges: it walks one edge down each side together and, for every row, fills the span (the run of pixels on one row) from the left edge to the right edge.

The price: every row of a shape must be one unbroken span. A "U" or a two-peaked ridge must be built from several shapes, which is why the demo's peak and hill are separate.

Two details stretch the data further. A draw command carries a zoom value, where 64 means full size, so one shape can be drawn larger or smaller with no extra data. And a group is a shape made of other shapes, each with an offset. A character is a group: the torso and head are stored once, and each animation frame only needs new legs.

A small machine inside the game

The draw lists are instructions for a virtual machine: a made-up processor, implemented in software. In the reimplementation it has 256 variables, up to 64 threads that take turns, 27 ordinary instructions (set a variable, jump, fill a screen page, copy a page, play a sound) and two drawing instructions marked by the top bits of the instruction byte. There are four screen pages. In the Amiga data each palette holds 16 colours, with 4 bits each for red, green and blue.

Gameplay and cutscenes are both this bytecode, so porting the game meant rewriting only the interpreter.

Fact and legend

The format, instruction counts and disk sizes were checked in Gregory Montoir's and Fabien Sanglard's reimplementations, which read the original data files. They are reconstructions, not Chahi's source. That Chahi built the game mostly alone over about two years, with music by Jean-François Freitas, is often repeated and comes from his own retellings; I could not check it in this session. Figures you may see for how much of the game is polygon data were not checked and are left out.

The idea in one line

Store the description of a picture, not the picture, and pay a little CPU time at play time to turn the description into pixels.

The lesson for today

The trade is everywhere now. Fonts store each letter as an outline, filled at any size. SVG icons, vector animation on phones and the web, and GPU triangle meshes work the same way. When a download or memory budget is tight, ask whether the art can be a description instead of pixels.

The code

The demo's filler in LÖVE, drawing the hill at the same place, size and palette entry. Add more entries to drawList to build a scene.

-- A shape in a format modelled on Another World's: a bounding box, then an even
-- number of points. Points 1..n/2 go down the right side, the rest come back up
-- the left, and point k is at the same height as point n + 1 - k.
local hill = { w = 160, h = 90, color = 5,
  pts = { {84, 0}, {120, 40}, {160, 90}, {0, 90}, {50, 40}, {76, 0} } }

local palette = { [5] = {0.33, 0.27, 0.47} }   -- 16 entries (0 to 15) in the demo
local drawList = { { shape = hill, x = 200, y = 115, zoom = 64 } }

local function span(y, x1, x2, color)
  if y < 0 or y > 199 then return end
  x1, x2 = math.max(x1, 0), math.min(x2, 319)
  if x1 > x2 then return end
  love.graphics.setColor(palette[color])
  love.graphics.rectangle("fill", x1, y, x2 - x1 + 1, 1)
end

local function fillShape(shape, cx, cy, zoom)
  local s = zoom / 64                            -- 64 means full size
  local left = cx - math.floor(shape.w * s / 2)
  local top = cy - math.floor(shape.h * s / 2)
  local p, n = shape.pts, #shape.pts
  for k = 1, n / 2 - 1 do
    local r1, r2 = p[k], p[k + 1]                -- right edge, going down
    local l1, l2 = p[n + 1 - k], p[n - k]        -- left edge, going down
    local y1 = top + math.floor(r1[2] * s)
    local y2 = top + math.floor(r2[2] * s)
    for y = y1, y2 - 1 do
      local t = (y - y1) / (y2 - y1)
      local xl = left + math.floor((l1[1] + (l2[1] - l1[1]) * t) * s)
      local xr = left + math.floor((r1[1] + (r2[1] - r1[1]) * t) * s)
      span(y, xl, xr, shape.color)
    end
  end
end

function love.draw()
  love.graphics.scale(3, 3)                      -- 320 x 200 screen, 3 times larger
  for _, cmd in ipairs(drawList) do
    fillShape(cmd.shape, cmd.x, cmd.y, cmd.zoom)
  end
end

When y1 == y2 the inner loop does not run, so nothing divides by zero. Each shape's bottom row is left unfilled, as in the demo.

Pitfalls

  • Two spans on one row. A ring cannot be one shape here. Split it into pieces with one span per row.
  • Pairs at different heights. The filler takes row counts from the right side only, so if point k and point n + 1 - k are not level the left edge goes wrong. Check data when you build it.
  • Overdraw. Every shape fills all its pixels, even ones a later shape covers. The virtual machine can fill, copy and show whole pages, so a script can paint a still background into a page once and copy it each frame.
  • Seams. Neighbouring shapes need one rounding rule for edges, or gaps appear where they meet.
  • Division per edge. Each edge needs a slope, and divides were slow on 1990s processors. The reimplementation looks reciprocals up in a 1,024-entry table.

In real games

Because the game is data for an interpreter, the reimplementation rawgl runs the original files from the Amiga, Atari ST, DOS, Windows 3.1 and 3DO releases and the 15th and 20th anniversary editions. Even the copy-protection screen and the password screen are bytecode, which is why the known cracks work by patching a few bytes of it.

Your turn (15 minutes)

Add a letter "U", about 40 by 50 pixels, to the Lua scene. Its upper rows have two spans, so build it from three shapes: two uprights and a bottom bar, with every pair level. Add up its bytes (3 + 2 per point, per shape) and compare with a 16-colour bitmap of its box (width × height ÷ 2). You are done when the letter draws with no gaps and you have both numbers.

Takeaways

  • A 16-colour 320 by 200 screen is 32,000 bytes; a polygon scene can be a few hundred.
  • Each shape is a box size and an even list of points that pair up by height.
  • Filling walks one edge down each side together and fills one span per row, with no sorting.
  • Zoom and groups let one stored shape serve many sizes and frames.
  • A virtual machine runs the draw lists, so porting the game meant porting the interpreter.

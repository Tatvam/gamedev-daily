NES bank switching: a big cartridge through a small window

How mapper chips in NES cartridges swapped 16 KB banks into the console's 32 KB view of the cartridge, so games could grow far past that limit.

Super Mario Bros. fits in about 40 kilobytes. Games released a few years later on the same console held several times that much, yet the processor could still see only 32 KB of the cartridge at once. The extra room came from chips inside the cartridge that change which 32 KB it sees.

The constraint: 64 KB of addresses, half for the cartridge

The NES processor is a version of the 6502. It names every byte it can read or write with a 16-bit address, a number from $0000 to $FFFF (the $ marks hexadecimal). That gives 64 KB of address space, the full list of addresses, and the whole machine has to share it.

The bottom half belongs to the console: 2 KB of working memory, the graphics chip's registers, and the sound and controller ports. The top half, $8000 to $FFFF, is wired to the cartridge's program ROM (read-only memory). So the processor can see at most 32 KB of game code and data. Graphics live on a second bus with an 8 KB slot of their own.

A cartridge with exactly 32 KB of program and 8 KB of graphics needs no extra parts. Fans call that board NROM, and Super Mario Bros. uses it. Anything bigger has nowhere to go.

The trick: a window and a switch

The fix is to put more ROM on the cartridge than the console can address, cut it into equal pieces called banks, and add a small chip that decides which bank answers when the processor reads a given address. That chip is called a mapper.

The simplest common layout, used by the board known as UxROM, splits the cartridge's 32 KB slot in two:

  • $8000–$BFFF is a 16 KB switchable window. Any bank can be placed there.
  • $C000–$FFFF is fixed to the last bank of the cartridge and never changes.

To choose a bank, the game writes its number to an address in the ROM area. ROM cannot be written, so the write would normally do nothing, but the mapper catches the number and holds it in its register, a tiny one-value memory. From the next read on, the window shows the new bank. A switch costs one store instruction.

Why one bank must stay fixed

The processor reads its instructions from the same address space. If the code that performs a switch sits in the window, the switch pulls that code out from under the processor, and its next instruction comes from another bank's data.

So switching code and the main loop go in the fixed bank. It sits at the top for a second reason: on power-on or an interrupt, the 6502 reads where to jump from the last six bytes, $FFFA–$FFFF, which must exist whatever the window holds.

Graphics too

Many UxROM games have RAM instead of ROM in the 8 KB graphics slot and copy tiles into it from the program banks. Other mappers switch graphics banks directly.

The code

A small UxROM-style mapper in Lua, with the same numbers as the demo: eight 16 KB banks, bank 7 fixed, a map in bank 3 and music in bank 5. Each bank is filled with its own number, so a read shows which bank answered.

-- A UxROM-style mapper: 16 KB banks, the last one fixed at $C000.
local BANK_SIZE  = 16384
local BANK_COUNT = 8                    -- 128 KB of ROM
local FIXED      = BANK_COUNT - 1       -- bank 7

local rom = {}                          -- rom[bank][offset], counted from 0
for b = 0, BANK_COUNT - 1 do
  rom[b] = {}
  for i = 0, BANK_SIZE - 1 do rom[b][i] = b end
end

local selected = 0                      -- the mapper's one register

local function cpuRead(addr)
  if addr >= 0xC000 then return rom[FIXED][addr - 0xC000] end
  if addr >= 0x8000 then return rom[selected][addr - 0x8000] end
  return 0                              -- console RAM and ports: not modelled
end

local function cpuWrite(addr, value)
  if addr >= 0x8000 then
    selected = value % BANK_COUNT       -- a write to "ROM" picks the bank
  end
end

-- On real hardware this routine lives in the fixed bank,
-- so switching never removes it from under the processor.
local function loadFromBank(bank, first, count)
  local previous = selected
  cpuWrite(0x8000, bank)
  local out = {}
  for i = 0, count - 1 do
    out[#out + 1] = cpuRead(0x8000 + first + i)
  end
  cpuWrite(0x8000, previous)            -- put the window back
  return out
end

local map, music = {}, {}

function love.load()
  map   = loadFromBank(3, 0, 16)
  music = loadFromBank(5, 0, 16)
end

function love.keypressed(key)
  local n = tonumber(key)
  if n and n >= 0 and n < BANK_COUNT then cpuWrite(0x8000, n) end
end

function love.draw()
  love.graphics.print("Window $8000 shows bank " .. selected, 10, 10)
  love.graphics.print("Byte at $8000: " .. cpuRead(0x8000), 10, 30)
  love.graphics.print("Byte at $C000: " .. cpuRead(0xC000), 10, 50)
  love.graphics.print("Map came from bank " .. map[1] ..
                      ", music from bank " .. music[1], 10, 70)
end

The program keeps its own copy of the register in selected. On the real boards the register cannot be read back, so games kept that copy in RAM for the same reason: to know what to restore.

Pitfalls

  • Switching away your own code. As the demo shows, code that changes the window must not live in the window.
  • Interrupts in the middle. The NES fires an interrupt at the start of every vertical blank. Its handler must be in the fixed bank, and if it switches banks it must put back the bank it found, or the main program resumes reading the wrong data.
  • Bus conflicts. On the original UxROM boards, a write to the ROM area also makes the ROM put its own byte on the data bus. If that byte differs from the bank number being written, the two collide. Games avoided this by writing each bank number to an address in ROM that already holds that same number, usually a small table of 0, 1, 2 and so on.
  • Data across a bank edge. A level that runs from bank 3 into bank 4 cannot be read in one pass, because the two are never in the window together. Keep each asset inside one bank.

In real games

Fan documentation of NES boards lists Mega Man, Castlevania, Contra, DuckTales and Metal Gear among the games on UxROM boards. Nintendo's MMC1 chip, used in The Legend of Zelda, Metroid and Mega Man 2, offered finer control, including switching graphics and choosing which half of the slot stays fixed. The MMC3, introduced in 1988 and used in Super Mario Bros. 3, switched smaller 8 KB program banks and added a counter that can interrupt the processor at a chosen scanline, which is how that game keeps its status bar still while the level scrolls.

The Game Boy uses the same idea with chips called memory bank controllers, but it fixes the first bank at the bottom of its cartridge area and switches the one above it. Expanded memory on DOS PCs did the same with a 64 KB page frame filled by 16 KB pages.

The window never went away. Operating systems map pages of virtual memory into a process, games stream textures through a fixed memory pool, and audio middleware loads and unloads sound banks to fit a budget. The rules stay the same: a fixed core that is always present, a window filled on purpose, and care that nothing in use is swapped out.

Takeaways

  • The NES processor sees only 32 KB of cartridge program ROM, at $8000–$FFFF.
  • A mapper chip cuts a larger ROM into banks and connects a chosen bank to a window of addresses.
  • The game selects a bank by writing its number to the ROM area; the mapper catches the write.
  • Switching code, interrupt handlers and the start-up addresses live in a bank that never moves.
  • Modern streaming follows the same pattern: a fixed core plus a window whose contents you manage.

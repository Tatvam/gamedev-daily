Donkey Kong's level 22: a timer that wraps to almost nothing

Why Donkey Kong ends at level 22: the bonus timer is worked out in one byte, 260 wraps to 4, and the cap that should catch it checks too late.

In the 1981 Donkey Kong arcade game, each stage starts with a bonus timer in the corner. If it reaches zero, Mario loses a life. On level 22 the timer starts so low that he dies a few seconds in, long before anyone could climb to the top.

Nobody chose that ending. It comes from the order of two lines of arithmetic, and the same mistake still turns up in code written today.

The constraint: every number fits in one byte

The Donkey Kong board runs on a Z80, an 8-bit processor. Its working unit is the byte: eight bits, which hold whole numbers from 0 to 255. When a sum needs a ninth bit, the processor keeps the low eight bits and drops the ninth. This is wrap-around, or overflow: 250 + 10 gives 4, not 260, and no error is raised. The processor does set a carry flag to say a bit fell off, but only code that checks the flag will notice.

Programmers of the time lived inside this limit. Scores were split across several bytes, and anything that fitted in one byte was kept in one byte.

The formula: more levels, more time, up to a cap

The bonus timer is stored in hundreds of points. A widely cited disassembly of the game by Don Hodges describes how its starting value is worked out from the level number:

  1. Multiply the level by 10 and add 40.
  2. If the result is more than 80, use 80.
  3. Show it multiplied by 100 on screen.

So level 1 gets 50 (shown as 5000), level 2 gets 60, level 3 gets 70, and from level 4 on the cap holds the timer at 80, or 8000. The cap is there so the timer stops growing, and for eighteen levels it does its job.

The bug: the cap checks a number that has already wrapped

On level 21 the sum is 21 × 10 + 40 = 250. That fits in a byte, it is more than 80, and the cap turns it into 80. Normal.

On level 22 the sum is 22 × 10 + 40 = 260. That needs nine bits. The processor keeps the low eight, and 260 − 256 = 4. Now the cap asks "is 4 more than 80?" The answer is no, so 4 goes through untouched. The stage starts with a timer of 400 points instead of 8000, and the timer runs out in a few seconds.

A level that can't be finished is called a kill screen. Donkey Kong's is the first stage of level 22, often written 22-1. It became the end point of competitive play: top scores are measured by what a player collects before reaching it.

The levels after 22

The wrap does not last forever. Each later level adds 10 to the wrapped value: 14 on level 23, 24 on level 24, up to 74 on level 29, and on level 30 the result is 84, which the cap pulls back to 80. Those later timers are still short. The table shows the values the formula gives.

The idea in one line

A limit checked after the arithmetic can't catch an overflow. Clamp the input, or check the carry, before the result is trusted.

The lesson for today

Bytes are still everywhere: colour channels in images, packed save files, sequence numbers in network packets, small integer types chosen to save memory on mobile or in large arrays. C# in Unity wraps integers silently unless you ask for checked arithmetic. Lua in LÖVE stores numbers as 64-bit floats, so they don't wrap, but the moment you write a value into a byte (an image pixel, a binary file) the old edge returns. Whenever a result is clamped, ask whether the value being clamped could already be wrong.

Try it

Drag the level from 21 to 22 and watch the bits: the ninth bit lights up, falls off, and the cap lets the small leftover through. Press Climb to send the climber up a toy stage with that much time. You can also click or tap a bar in the chart at the bottom to jump to that level. Then turn on the fix and try level 22 again.

The code

Lua numbers don't wrap, so toByte imitates an 8-bit register with % 256. The buggy version adds first and caps afterwards, as the game effectively does. The fixed version caps the level before the sum can grow too big. The numbers match the demo.

-- Bonus timer in hundreds of points, worked out like an 8-bit machine would.
local TIMER_CAP = 80               -- 80 hundreds = 8000 points

local function toByte(n)
  return n % 256                   -- keep the low 8 bits, drop the carry
end

local function bonusBuggy(level)
  local t = toByte(level * 10 + 40)  -- level 22: 260 becomes 4
  if t > TIMER_CAP then t = TIMER_CAP end   -- too late: 4 is not > 80
  return t
end

local function bonusFixed(level)
  local l = math.min(level, 4)       -- clamp the input first
  local t = toByte(l * 10 + 40)      -- now at most 80, can never wrap
  if t > TIMER_CAP then t = TIMER_CAP end
  return t
end

local lines = {}

function love.load()
  for level = 20, 30 do
    lines[#lines + 1] = string.format("level %2d   buggy %4d   fixed %4d",
      level, bonusBuggy(level) * 100, bonusFixed(level) * 100)
  end
end

function love.draw()
  for i, text in ipairs(lines) do
    love.graphics.print(text, 20, 20 + (i - 1) * 18)
  end
end

Run it and the buggy column drops from 8000 to 400 at level 22, then climbs back by 1000 a level until 30. The fixed column stays at 8000.

Pitfalls

  • Clamping the output instead of the input. A cap after the sum can only catch values that are still correct. Clamp the inputs so the sum can't overflow, or do the sum in a wider type and clamp that.
  • Ignoring the carry. In assembly the processor tells you a bit fell off. Checking the carry flag after the addition, and treating a set flag as "too big", would have caught this one. In high-level code the equivalent is a checked or saturating add.
  • Testing only the levels people reach. Level 22 takes a skilled player a long time to reach. A test that loops the formula over every level from 1 to 255 shows the dip at once. Cheap exhaustive tests beat long play sessions for this kind of bug.
  • A wider type only moves the edge. A 16-bit timer would have pushed the wrap out to level 6,550. That is safe in practice, but clamping the input is safe for every level.

In real games

The level 22 kill screen is part of arcade history. It is the finish line in the 2007 documentary The King of Kong: A Fistful of Quarters, and record scores are set by players who reach it. Don Hodges disassembled the timer routine, explained the overflow and published a patch that removes it.

Donkey Kong Jr. is often reported to have a kill screen at level 22 from a similar timer overflow. I could not check that against a primary source, so treat it as often repeated, not confirmed.

In 2025 news sites reported that a player called Kosmic had found a way to finish the level 22 stage despite the tiny timer, using precise inputs on an emulator. I could not open those reports, so the details are not confirmed here.

Takeaways

  • Donkey Kong works out the bonus timer as level × 10 + 40 in one byte, capped at 80 (8000 points).
  • On level 22 the sum is 260, which wraps to 4, and the cap lets 4 through because it is smaller than 80.
  • The stage starts with 400 points on the timer, too little to climb, so level 22 is a kill screen.
  • Clamp inputs, or check for overflow, before you clamp results. A limit placed after the arithmetic can't see a wrap.

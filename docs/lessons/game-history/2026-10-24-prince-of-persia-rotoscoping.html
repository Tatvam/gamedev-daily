Prince of Persia: a run cycle traced from film

How Prince of Persia got lifelike running: poses traced from video of a real runner, each with its own step, then reused for the shadow double.

In many 1980s games a running character has two or three poses, and the feet slide across the floor while the legs scissor. The hero of Prince of Persia (Broderbund, 1989) leans into a run, shifts his weight and plants each foot where it lands. He ran on the same Apple II as everyone else.

The difference was not a faster machine. It was where the poses came from, and how much data each one carried.

The constraint

The Apple II's high-resolution screen is 280 by 192 pixels, its 6502 processor runs at about 1 MHz, and the models of the late 1980s had 64 or 128 kilobytes of memory. Every pose of every character is a small image that has to sit in that memory alongside the levels, the code and the sound.

So frames are expensive, and each is drawn by hand. Guessed motion tends to look stiff: limbs swing evenly and the body glides at a constant speed.

The trick: film first, trace second

Rotoscoping means tracing over filmed footage, one frame at a time, to get an animation. It is far older than video games. Jordan Mechner, who wrote Prince of Persia in 6502 assembly between 1985 and 1989, videotaped his younger brother David running, jumping and climbing, then traced the figure from chosen frames into small images and cleaned them up by hand.

  1. Tracing is choosing. Video has far more frames than a game can store. Keeping a handful is sampling: each kept frame is a real moment, so even a few carry real weight and timing.
  2. The film says how far to move. While a foot is planted, the body travels as far as the foot slides back relative to the hips. Store that distance with each frame and the foot stays put.

The released source code shows the second point directly. Each frame table entry is five bytes: image number, sword image, two drawing offsets and floor-check flags, with room for 240 frames in 1,200 bytes. A sequence table scripts each move as a list of frames. The running loop is eight frames, and between them the kid moves by these amounts, in the game's position units:

Run step12345678
Move51245234
Footstep soundyesyes

The steps are uneven on purpose. A constant speed would make the feet skate. Today this idea is called root motion: the animation, not a speed variable, decides how far the character travels.

One set of frames, two characters

The hero meets a shadow double of himself. In the routine that picks frames, the shadow uses the kid's own frame set, except for the sword-fighting frames 150 to 189, which come from the guards' set. That set holds the sword in the other hand, so a mirrored fighter still holds it correctly.

What makes the shadow look different is how it is drawn. The kid and guards use a mask: clear the shape's area, then put the image in. The shadow uses XOR (exclusive or, the 6502's EOR instruction): every image pixel flips the screen pixel under it. On empty space the shadow is a figure; over a wall it becomes a hole. Drawing it twice restores the screen.

When the two merge, the kid flashes between mask and XOR drawing on alternate frames. Guards get the same frugality: some are drawn one pixel to the side, under a flag named GuardColor. On the Apple II a pixel's colour depends on its column, so the shift recolours a guard with no new images.

What is checked and what is story

The frame table, run cycle, shadow frames and XOR drawing come from the source code, which I read. The filming comes from Mechner's own accounts, which I could not open this session. Retellings disagree on details such as David's age, so those are left out.

The code

The demo's runner in LÖVE. leg is the "film", a smooth function of phase. The loop building FRAMES is the tracing: it keeps eight phases and, from the planted foot, how far to move after each (6, 2, 2, 6, 6, 2, 2, 6). Two runners share the table.

-- Eight poses traced from a smooth run, shared by a runner and its double.
local TAU, R = 2 * math.pi, math.pi / 180
local THIGH, SHIN, TORSO, UPPER, FORE = 8, 8, 11, 6, 5
local LEAN, FPS, SCALE, FLOOR = 12 * R, 10, 4, 47

local function dir(a) return math.sin(a), math.cos(a) end   -- 0 = straight down

local function leg(q)            -- the "film": knee and foot at phase q
  local th = (30 * math.sin(TAU * q) + 5) * R
  local kn = (15 + 60 * math.max(0, math.cos(TAU * q))) * R
  local kx, ky = dir(th)
  local sx, sy = dir(th - kn)
  return THIGH * kx, THIGH * ky, THIGH * kx + SHIN * sx, THIGH * ky + SHIN * sy
end

-- Tracing: keep 8 phases, and how far the planted foot moves the body.
local FRAMES = {}
for k = 0, 7 do
  local p = k / 8
  local _, _, _, ya = leg(p)
  local _, _, _, yb = leg(p + 0.5)
  local st = (ya >= yb) and 0 or 0.5               -- the lower foot is planted
  local _, _, f1 = leg(p + st)
  local _, _, f2 = leg((k + 1) / 8 + st)
  FRAMES[k + 1] = { p = p, dx = math.floor(f1 - f2 + 0.5), hipY = 38 - math.max(ya, yb) }
end

local runners = { { x = 0, f = 1, dir = 1 }, { x = 104, f = 5, dir = -1 } }
local acc = 0

function love.load() love.window.setMode(128 * SCALE, 56 * SCALE) end

function love.update(dt)
  acc = acc + dt
  while acc >= 1 / FPS do
    acc = acc - 1 / FPS
    for _, r in ipairs(runners) do
      r.x = r.x + r.dir * FRAMES[r.f].dx            -- the frame says how far
      r.f = r.f % 8 + 1
      if r.x > 128 then r.x = -24 elseif r.x < -24 then r.x = 128 end
    end
  end
end

local function drawRunner(r)
  local fr = FRAMES[r.f]
  love.graphics.push()
  love.graphics.translate(r.x + 12, FLOOR - 40 + fr.hipY)
  love.graphics.scale(r.dir, 1)                    -- mirror, not a new image
  local lx, ly = dir(LEAN)
  local shx, shy = TORSO * lx, -TORSO * ly
  love.graphics.line(0, 0, shx, shy)
  love.graphics.circle("fill", shx + 4 * lx, shy - 4 * ly, 3)
  for _, q in ipairs({ fr.p, fr.p + 0.5 }) do
    local kx, ky, fx, fy = leg(q)
    love.graphics.line(0, 0, kx, ky, fx, fy)
    local ua = 35 * math.sin(TAU * (q + 0.5)) * R  -- arm swings against its leg
    local ux, uy = dir(ua)
    local hx, hy = dir(ua + 80 * R)
    local ex, ey = shx + UPPER * ux, shy + UPPER * uy
    love.graphics.line(shx, shy, ex, ey, ex + FORE * hx, ey + FORE * hy)
  end
  love.graphics.pop()
end

function love.draw()
  love.graphics.scale(SCALE, SCALE)
  love.graphics.setLineWidth(2)
  love.graphics.setColor(0.92, 0.92, 0.92)
  drawRunner(runners[1])
  love.graphics.setColor(0.45, 0.45, 0.6)          -- the double: same FRAMES
  drawRunner(runners[2])
  love.graphics.setColor(0.92, 0.92, 0.92)
  love.graphics.rectangle("fill", 0, FLOOR, 128, 2)
end

The window is the demo's 128 by 56 screen scaled four times. LÖVE has no XOR blend mode, so here the double gets another colour instead; the demo draws on a one-bit screen where it can flip pixels.

Pitfalls

  • Keeping every film frame. Pick the poses that define the motion, such as contact, push-off and flight, and let timing do the rest.
  • Moving at a constant speed. Traced frames over a constant speed make the feet skate. Store a distance per frame.
  • Boiling outlines. Raw tracing wobbles between frames. Clean each frame by hand so still parts stay still.
  • Mirroring swaps hands. A mirrored fighter holds the sword in the other hand, which is why Prince of Persia keeps a separate enemy set.
  • XOR depends on the background. On busy scenery an XOR sprite is hard to read. Fine for a ghost, bad for a hero.

In real games

Delphine Software's Flashback (1992) is another well-known rotoscoped platformer. Today the same pipeline is motion capture, cleaned up by animators. Unity, Godot and Unreal Engine all support root motion, where movement stored in the animation moves the character. Sharing animations between characters on one skeleton, recoloured with a tint, is the modern shadow double.

Takeaways

  • Rotoscoping traces chosen frames of real footage, so even a few poses carry real weight and timing.
  • Prince of Persia's run cycle is eight frames, each with its own move distance, which keeps the feet planted.
  • The shadow double reuses the kid's frames and differs only in being drawn with XOR instead of a mask.
  • Today's equivalents are motion capture, root motion and animations shared across characters.

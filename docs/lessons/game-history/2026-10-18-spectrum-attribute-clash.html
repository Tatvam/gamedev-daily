ZX Spectrum attribute clash: two colours per 8 by 8 block

Why ZX Spectrum sprites stain the scenery: colour is stored once per 8 by 8 block, so a moving sprite repaints every block it touches.

Watch footage of a colourful ZX Spectrum game and you will see a strange smear. When a character walks past a tree, a square patch of the tree changes to the character's colour, then snaps back once they have passed. The patch is always a neat block, never the shape of the character.

This is attribute clash. It is not a bug in one game but a result of how the machine stores its screen.

The constraint: a whole screen in under 7 KB

The ZX Spectrum, launched by Sinclair Research in 1982, was sold first with 16 KB or 48 KB of memory. Its screen is 256 by 192 pixels and can show eight colours (black, blue, red, magenta, green, cyan, yellow and white), each in a normal and a bright version.

Storing a colour for every pixel would need at least 4 bits per pixel: 256 × 192 × 4 ÷ 8 = 24,576 bytes. That is more than the whole memory of the 16 KB model. So the screen is split into two parts:

  • The bitmap: 1 bit per pixel, saying only "on" or "off". 256 × 192 ÷ 8 = 6,144 bytes.
  • The attributes: one byte for each 8 by 8 block of pixels, called a cell. The screen is 32 cells wide and 24 tall, so 768 bytes.

Together that is 6,912 bytes. Colour costs about an eighth of what the bitmap costs, instead of three times as much.

What one attribute byte holds

Each attribute byte gives its cell exactly two colours. INK is the colour of every "on" pixel in the cell. PAPER is the colour of every "off" pixel. One more bit, BRIGHT, picks the bright version of both, and the top bit, FLASH, makes the cell swap ink and paper a couple of times a second.

Why a moving sprite stains its surroundings

A sprite is a small moving picture, such as the player's character. The Spectrum has no sprite hardware, so games draw sprites into the bitmap by hand. Drawing the shape is fine: the bitmap can hold any pattern of bits. The trouble comes with colour.

Say a magenta character walks in front of a green hill. The cells it overlaps contain both hill pixels and character pixels, and all of those "on" pixels share one INK. The game has two choices:

  1. Write the sprite's colour into the cell. The character is magenta, but so is every hill pixel in the same cell. A square magenta stain follows the character around. This is the clash.
  2. Leave the cell's colour alone. The scenery stays correct, but the character turns green over the hill, white over a cloud, yellow over the sun. It has no colour of its own.

There is no third option inside one cell. Because a sprite almost never lines up exactly with the 8 by 8 grid, a 16 by 16 character usually touches 9 cells, not 4, which makes the stain bigger than the character.

The idea in one line

When colour is stored at a lower resolution than shape, anything that moves must either borrow the colour of the block it is in or overwrite it for everything else in that block.

How games lived with it

Each game chose its compromise. Some drew the play area in one ink on one paper, so there was nothing to clash with, and kept colour for the score panel. Some used plain black scenery and spaced sprites apart. Some built characters from whole cells and moved them a cell at a time. Others simply accepted the clash as the price of a colourful screen.

The lesson for today

Storing colour more coarsely than detail is still everywhere. JPEG images and most video keep brightness for every pixel but colour for groups of pixels, called chroma subsampling, because eyes notice fine detail in brightness more than in colour. Texture formats such as BC1 store two colours per 4 by 4 block. Both save memory or bandwidth, and both show a small "clash" when a sharp coloured edge falls inside a block.

The code

A tiny attribute screen in LÖVE. The bitmap is a table of true and false, the attributes are one table per cell, and the colour of any pixel comes from its cell. The demo's sprite, mask, sizes and the "sprite sets the ink" rule are the same; the background is a simple pattern here to keep the code short. Move the sprite with the arrow keys.

-- 1 bit per pixel, 1 INK/PAPER pair per 8x8 cell, 16 x 10 cells.
local CELLS_X, CELLS_Y, SCALE = 16, 10, 4
local W, H = CELLS_X * 8, CELLS_Y * 8
local PALETTE = { [0] = {0, 0, 0}, {0, 0, 0.84}, {0.84, 0, 0}, {0.84, 0, 0.84},
  {0, 0.84, 0}, {0, 0.84, 0.84}, {0.84, 0.84, 0}, {0.84, 0.84, 0.84} }
local SPRITE_INK = 3                  -- magenta
local sx, sy = 20, 30                 -- sprite position in pixels
local bitmap, attr = {}, {}

local function dist(px, py, x, y) return math.sqrt((px - x) ^ 2 + (py - y) ^ 2) end
local function spriteBit(px, py)      -- 16x16 disc with two eye holes
  return dist(px, py, 7.5, 7.5) < 7 and dist(px, py, 5, 6) > 1.5 and dist(px, py, 10, 6) > 1.5
end
local function maskBit(px, py) return dist(px, py, 7.5, 7.5) < 8 end

function love.load()
  for y = 0, H - 1 do
    bitmap[y] = {}
    for x = 0, W - 1 do bitmap[y][x] = (x + y) % 5 == 0 end      -- diagonal stripes
  end
  for cy = 0, CELLS_Y - 1 do
    attr[cy] = {}
    for cx = 0, CELLS_X - 1 do attr[cy][cx] = { ink = 4 + cx % 3, paper = 1 } end
  end
end

function love.keypressed(key)
  if key == "left" then sx = math.max(0, sx - 1) end
  if key == "right" then sx = math.min(W - 16, sx + 1) end
  if key == "up" then sy = math.max(0, sy - 1) end
  if key == "down" then sy = math.min(H - 16, sy + 1) end
end

local function pixelColour(x, y)
  local cx, cy = math.floor(x / 8), math.floor(y / 8)
  local ink, paper = attr[cy][cx].ink, attr[cy][cx].paper
  local on, px, py = bitmap[y][x], x - sx, y - sy
  if px >= 0 and px < 16 and py >= 0 and py < 16 then
    if maskBit(px, py) then on = false end
    if spriteBit(px, py) then on = true end
  end
  if cx * 8 < sx + 16 and cx * 8 + 8 > sx and cy * 8 < sy + 16 and cy * 8 + 8 > sy then
    ink = SPRITE_INK                  -- the clash: the whole cell takes the sprite's ink
  end
  if on then return PALETTE[ink] end
  return PALETTE[paper]
end

function love.draw()
  for y = 0, H - 1 do
    for x = 0, W - 1 do
      love.graphics.setColor(pixelColour(x, y))
      love.graphics.rectangle("fill", x * SCALE, y * SCALE, SCALE, SCALE)
    end
  end
end

Delete the highlighted if block and you get the other compromise: the sprite keeps the shape but takes each cell's own ink. There is no line you can write that gives both, because each cell has only one ink.

Pitfalls

  • Forgetting to restore the attributes. When the sprite moves on, the cells it leaves must get their old colour back. A game has to keep a copy of the background attributes, or redraw them, or the stain stays behind as a trail.
  • Counting 4 cells for a 16 by 16 sprite. Only when it sits exactly on the grid. At any other position it overlaps 6 or 9 cells, so the stain and the work of colouring it both grow.
  • Drawing a monochrome sprite with no mask. If the sprite is simply OR'd into the bitmap, it merges with any scenery of the same ink and disappears. Clearing a slightly larger outline first, as the demo does, keeps it readable.

In real games

Ultimate Play the Game's isometric adventure Knight Lore (1984) is the example most often given of the monochrome approach: its play area uses one colour pair at a time, so its detailed characters never clash. Accounts I found disagree on whether that colour changes from room to room, so this page does not say.

Attribute clash is not unique to the Spectrum. Other machines of the era that stored colour per block, such as the MSX and the Commodore 64 in some of their screen modes, had related limits, though the details differ by mode.

Run the Lua above. Then add a second table, savedInk, filled in love.load with a copy of every cell's ink. You are done when the sprite leaves no trail, and you have seen the trail once by skipping the restore.

Takeaways

  • The Spectrum stores shape per pixel (6,144 bytes) but colour per 8 by 8 cell (768 bytes), one INK and one PAPER each.
  • A sprite in a cell must either set that cell's ink, staining the scenery, or take the cell's ink and lose its own colour.
  • Off-grid sprites touch more cells, so the stain is usually bigger than the sprite.
  • Games hid clash with one-colour play areas, plain backgrounds, or characters built around the grid.
  • Low-resolution colour lives on in chroma subsampling and block texture compression, with the same trade-off at sharp coloured edges.

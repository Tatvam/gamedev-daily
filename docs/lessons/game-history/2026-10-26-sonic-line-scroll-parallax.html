Sonic the Hedgehog: many layers of parallax from one background

How Sonic's backgrounds slide at many speeds on a chip with two layers: a table gives every screen line of one background its own scroll value.

Run right in the first zone of Sonic the Hedgehog (Sega, 1991) and the world comes apart into layers: clouds drift, far mountains creep, hills slide past and the water speeds up towards the bottom of the screen. It looks like five or six layers stacked up. The Mega Drive's video chip has two, and the level itself uses one of them.

The constraint: two layers, one scroll each

Parallax is the train-window effect: near things rush past, far things barely move. Games fake it by scrolling pictures at different speeds.

The Mega Drive (sold as the Genesis in North America) draws with a video chip, the VDP (video display processor). In the 40-column mode Sonic uses, the screen is 320 by 224 pixels. It has two layers built from 8 by 8 pixel tiles, plane A and plane B, plus sprites, all in 64 KB of video memory.

Normally a plane scrolls as one piece. The level Sonic runs on takes plane A, leaving plane B for everything behind it. One value per plane gives two depths: the level and one flat backdrop.

What the chip offers: a scroll value per line

The VDP reads its horizontal scroll values from a scroll table in video memory. Two bits in register $0B choose how it reads that table:

  • Whole screen: one entry for the whole frame.
  • Per row: a new entry every 8 lines, 28 entries for 224 lines.
  • Per line: a new entry for every line.

(A fourth setting, which MAME's source calls broken, repeats the first eight entries down the screen.) Each entry is two 16-bit values, one for plane A and one for plane B, so a full per-line table is 224 × 4 = 896 bytes. That is the whole cost: under a kilobyte, and no extra drawing.

The trick: cut one picture into bands

Sonic's background is one picture laid out in horizontal strips: clouds, mountains, hills, water. Each frame the game writes the table so that every line of a strip gets that strip's value. Each strip, or band, slides at its own speed, and the eye reads the bands as separate layers.

The table is built in ordinary memory while the frame runs, then copied into video memory by DMA (direct memory access, a hardware copy that does not need the processor) during the vertical blank, the pause between two frames.

The numbers come from the zone's scroll routine. The mountains move 0.375 pixels for every pixel the camera moves, and the hills 0.5. In the water, the top line moves with the hills, and each line below adds 1/104 of the gap between the hills and the camera. So the band speeds up down the screen, the way a flat surface moves beside you. The game keeps these positions in fixed point, whole numbers with a fractional part stored in the low bits, so slow bands creep smoothly instead of jumping.

Fact and legend

Sonic did not invent line scrolling. The hardware feature was there for every Mega Drive game, and per-line effects were already in use on other machines, such as the Amiga with its copper. The figures above come from the Sonic Retro disassembly, whose labels and comments are written by fans, not Sega. It has two versions of this routine: in the earlier one, the clouds and mountains share one value across the top 112 lines; the separate cloud drift appears in a later revision.

The idea in one line

Instead of drawing more layers, give one layer a small table of offsets, one per line, and paint the art so that each band of lines is one depth.

The lesson for today

Stacked full-screen see-through layers are still costly on phones and in browsers, because every pixel is drawn once per layer. One picture with a per-row offset draws each pixel once; in a shader, shift the texture coordinate by a value looked up from the row. As with Mode 7, the processor fills a tiny table each frame and simple hardware applies it.

The code

The demo's background in LÖVE, with the same bands and speeds. love.update builds the scroll table, as the game does each frame. tableEntry plays the video chip: it picks which entry each line uses. love.draw draws the picture one line at a time, shifted by that entry.

-- Line scrolling: one background picture, one scroll value per screen line.
local SW, SH, PLANE_W = 320, 224, 512
local BANDS = 88            -- speeds in each gradient, 1 to 88
local MODE = "line"         -- "line", "cell" (8-line rows) or "full"
local RUN = 120             -- camera speed in pixels per second
local camX = 0
local hscroll = {}          -- the scroll table, entries 0 to 223
local planeB, lineQuads

local function gradient(line, first, count, from, to)
  local n = math.min(BANDS, count)
  local band = math.floor((line - first) * n / count)
  return from + (to - from) * (band + 0.5) / n
end

local function speedForLine(line)
  if line < 48 then return gradient(line, 0, 48, 0.40, 0.20)   -- cloud ceiling
  elseif line < 104 then return 0.125                          -- far mountains
  elseif line < 136 then return 0.25                           -- hills
  end
  return gradient(line, 136, 88, 0.30, 1.00)                   -- water
end

local function tableEntry(line)     -- which entry the video chip reads
  if MODE == "full" then return hscroll[0] end
  if MODE == "cell" then return hscroll[line - line % 8] end
  return hscroll[line]
end

function love.load()
  love.graphics.setDefaultFilter("nearest", "nearest")
  planeB = love.graphics.newImage("plane_b.png")   -- your own 512 x 224 picture
  lineQuads = {}
  for line = 0, SH - 1 do
    lineQuads[line] = love.graphics.newQuad(0, line, PLANE_W, 1, PLANE_W, SH)
  end
end

function love.update(dt)
  camX = camX + RUN * dt
  for line = 0, SH - 1 do                          -- build the table every frame
    hscroll[line] = -math.floor(camX * speedForLine(line))
  end
end

function love.draw()
  love.graphics.scale(3, 3)
  for line = 0, SH - 1 do
    local x = tableEntry(line) % PLANE_W
    love.graphics.draw(planeB, lineQuads[line], x, line)
    love.graphics.draw(planeB, lineQuads[line], x - PLANE_W, line)
  end
end

Set the window to 960 by 672 in conf.lua. Each line is drawn twice, 512 pixels apart, so the picture wraps around like a hardware plane. Lua's % always returns a positive result for a positive divisor, so negative scroll values work. The demo draws a foreground layer on top at speed 1, which is plane A's job on the real machine.

Pitfalls

  • Shearing solid scenery. A mountain that spans two bands, or sits in a gradient, leans over as you run. Keep solid objects inside one band and save gradients for flat things: water, floors, cloud ceilings. The demo's clouds sit in a gradient and lean slightly; set Speeds in each gradient to 1 and they stay round.
  • Bands cannot overlap. Each line of the plane shows one strip at one offset, so a near tree in front of far mountains on the same lines needs sprites or the other plane.
  • Vertical scrolling moves the bands. Bands are rows of the picture, but the table is indexed by screen line. When the background scrolls vertically the table must shift too; Sonic's routine trims the top band and lengthens the water.
  • Writing the table while it is being read. Change it mid-frame and the top and bottom of the screen disagree. Build it in a buffer and copy it between frames.

In real games

In Sonic the Hedgehog every zone has its own routine that fills the scroll table, picked from a list by zone number. In the later revision, Labyrinth Zone uses the same table for a different effect: every line below the water surface gets a small extra offset from a wave table, on both planes, so the scene ripples underwater. On the Super Nintendo, games get per-line scrolling by having HDMA (covered in the F-Zero lesson) write a scroll register before each line.

Your turn (15 minutes)

Give the clouds a drift of their own, as Sonic's later revision does. Add local cloudDrift = 0, increase it by 20 * dt in love.update, and for lines below 48 write hscroll[line] = -math.floor(camX * speedForLine(line) + cloudDrift). Then make each third of the cloud band drift at a different rate. You are done when the clouds keep moving with RUN set to 0, and the top third moves fastest.

Takeaways

  • The Mega Drive has two scrolling planes, but each can take a new horizontal scroll value on every line.
  • A per-line table costs 4 bytes per line, 896 bytes for the screen, and is copied in between frames.
  • Painting the background in horizontal bands lets one plane look like many layers.
  • Solid scenery gets one value per band; flat surfaces get a value that grows line by line.
  • The modern form is a per-row offset in a shader: one draw instead of many stacked layers.

Quake's potentially visible set: deciding what to draw before the game ships

Quake worked out in advance which parts of a level can ever see each other, stored it as one bit per area, and skipped the rest of the map every frame.

Stand in a small room in a big level. Almost everything sits behind solid walls, yet a naive renderer still examines every hidden wall each frame before deciding not to draw it. Quake moved that decision out of the game: a tool made it once, before the level shipped.

The constraint: true 3D on a mid-1990s PC

Quake shipped in the summer of 1996 with fully 3D levels, drawn in software on the processor. The hard part, as Michael Abrash described it, is visible surface determination: working out which polygons the camera can see. The methods tried first did more work in complicated scenes, and Abrash recalls one spot where the frame rate fell into single digits.

Leaves: the level is already cut into pieces

Like Doom, a Quake level is compiled into a binary space partitioning tree (see the Doom BSP lesson), here with 3D planes. The empty space ends up cut into convex pieces called leaves, each holding the polygons on its boundary. The released map format allows up to 8192 leaves.

The trick: a lookup table of what can ever be seen

For every leaf, the tools work out which other leaves can be seen from anywhere inside it. That list is the leaf's potentially visible set, or PVS. It is stored as a row of bits, one bit per leaf in the level: 1 means "might be visible from here", 0 means "can never be seen from here, whatever you do".

Building the table, slowly

A separate tool called vis does the work after the BSP is built. The level must be sealed, so the outside can be thrown away. The openings between neighbouring leaves are portals. In the released source, vis first makes a rough guess for each portal by flooding through the portals in front of it, then refines it by following chains of portals: if no straight line can thread the whole chain, the leaf at the end is not visible.

Abrash wrote that processing a level took 10 to 30 minutes on a four-processor Alpha, a figure that includes building the BSP and the lighting. A -fast option keeps only the rough guess.

Making it small

Abrash says the first uncompressed tables were several megabytes. But from any one leaf most of the level is hidden, so most bytes in a row are zero: a non-zero byte is stored as it is, and a run of zero bytes becomes a zero followed by a count. The row 03 00 00 00 00 00 10 is stored as 03 00 05 10. With that, fewer leaves and the sealed outside removed, Abrash puts the table at about 20 KB for a good-size level.

Using it, cheaply

Each frame the game finds the camera's leaf by walking down the BSP tree. When that leaf changes, it unpacks the row and marks every visible leaf, and the nodes above it, with a frame number. The BSP walk then skips unmarked branches.

The price is extra work. The set holds what is visible from anywhere in the leaf, not from your exact spot, so it includes more than is really in view: Abrash says two or three times as many polygons as are actually visible.

The lesson for today

Abrash quotes Terje Mathisen: "almost all programming can be viewed as an exercise in caching." Baked occlusion data, lighting and navigation meshes make the same trade: build time and a little memory so that a phone or browser does less work every frame, and the worst frame is not much worse than the best.

The code

A slow bake and a cheap lookup. Rooms are numbered from 0 so room j is bit j, as in the demo strip; rows are plain numbers read with division, since Lua 5.1 has no bit operators. clearLine is your own grid ray test, like the one in the Wolfenstein lesson.

local COLS, NUM_ROOMS = 4, 12           -- 4 by 3 rooms, each 8 by 5 tiles
local pvs = {}                          -- pvs[room] = one bit per room
local usePVS = true
local player = { x = 2.5, y = 2.5 }     -- in tiles

local function roomAt(x, y)
  local c = math.min(COLS - 1, math.floor((x - 1) / 8))
  local r = math.min(2, math.floor((y - 1) / 5))
  return r * COLS + c
end

local function hasBit(row, j)
  return math.floor(row / 2 ^ j) % 2 == 1
end

local function anyLine(a, b, clearLine) -- any point in a sees any point in b?
  for _, p in ipairs(a) do
    for _, q in ipairs(b) do
      if clearLine(p.x, p.y, q.x, q.y) then return true end
    end
  end
  return false
end

-- Offline, once per level. samples[i] lists points spread over room i.
local function bakePVS(samples, clearLine)
  for i = 0, NUM_ROOMS - 1 do
    local row = 2 ^ i                   -- a room always sees itself
    for j = 0, NUM_ROOMS - 1 do
      if j ~= i and anyLine(samples[i], samples[j], clearLine) then
        row = row + 2 ^ j
      end
    end
    pvs[i] = row
  end
end

local function drawRoom(j)              -- stand-in for sending room j to the renderer
  local c, r = j % COLS, math.floor(j / COLS)
  love.graphics.rectangle("fill", (1 + c * 8) * 16, (1 + r * 5) * 16, 7 * 16, 4 * 16)
end

-- In love.load, call bakePVS(samples, clearLine) or load a table your build tool saved.
function love.draw()
  local row = pvs[roomAt(player.x, player.y)]
  for j = 0, NUM_ROOMS - 1 do
    if not usePVS or hasBit(row, j) then drawRoom(j) end
  end
end

The bake may test thousands of lines per pair of rooms. The draw is one read and twelve bit tests.

Pitfalls

  • Open spaces defeat it. It only helps when walls block sight, as the hall map shows.
  • Moving things are not in the table. The bake sees only fixed geometry. A closed door does not hide the room behind it unless you add a separate run-time test.
  • A bake that samples can miss. The demo tests lines between sample points and could miss a thin gap, making a room pop in. Quake's vis works with exact portal shapes. If you sample, use many points and lean towards "visible".
  • Leaks. The method assumes a sealed level, so the tools can throw the outside away. A hole to the outside breaks that assumption.
  • Long builds. Minutes per level slow designers down. Keep a rough mode for test builds, like -fast.
  • Unpacking every frame. The row only changes when the camera moves to a new area. Cache it, as Quake did.

In real games

Quake's vis tool and the engine code that reads the table are in id Software's released source. GLQuake's console variable r_novis marks every leaf visible, like the demo's toggle. Abrash describes the PVS also limiting which models were drawn and which entities were sent over the network, and a QuakeWorld version using a wider "potentially hearable set" to pick which sounds to send, which he credits with raising the player limit from 16 to 32. Valve's Source engine compiles maps with a tool named VVIS, and Unity offers baked occlusion culling for the same reason.

Your turn (15 minutes)

Take a level in your own project and give every area a zone number. Write an editor or start-up step that casts rays between points spread over each pair of zones and stores one visibility row per zone, saved to a file. At run time, look up the row for the player's zone and switch off drawing for every object in a zone whose bit is 0. You are done when an on-screen counter of drawn objects drops sharply as you walk into a closed room, and a key that ignores the table brings the count back.

Takeaways

  • Quake's tools split each level into convex leaves and stored, for every leaf, one bit per leaf saying whether it could ever be seen from there.
  • Building the table took minutes per level; using it took one lookup when the camera changed leaf.
  • Rows are mostly zeros, so runs of zero bytes were packed into a zero and a count.
  • The set is conservative: it holds everything visible from anywhere in the leaf, so some hidden polygons still get drawn.
  • It works when walls block sight, and moving objects need their own test.

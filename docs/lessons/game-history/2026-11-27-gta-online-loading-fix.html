GTA Online: the six-minute load a player fixed

How two hidden loops made GTA Online load for minutes, how a player found them without source code, and how to spot quadratic work in your own loader.

For years, PC players of GTA Online sat through loading screens that could run for several minutes before they reached the game. Faster computers barely helped. In early 2021 a player who goes by t0st took the game apart to see why, and found that most of the wait came from two small loops working against each other in the worst possible way.

The constraint: nothing, at first

Earlier pages in this series were about hardware limits. Here the PC had plenty of memory and a fast drive. The limit was the shape of the code, and it only showed up once the data grew large.

t0st did not have the game's source code. He used a profiler, a tool that samples what a program is doing many times a second, and saw that during loading one processor core stayed fully busy for minutes. He then read the machine code of the busy functions, a process called disassembly, to work out what they were doing. On his own PC, an older AMD FX-8350 machine, getting into GTA Online took about six minutes.

The two loops

The busy code was reading a text file of about 10 megabytes in JSON, a common text format for structured data. It listed the items players can buy in the online mode, about 63,000 of them. Two things went wrong.

Loop one: measuring the text again and again. The reader pulled values out of the text with sscanf, a standard C function that reads values from a string. The version of sscanf the game used first measured the whole remaining string with strlen, which walks byte by byte until it finds the end. So every small read near the start of the file walked through nearly 10 megabytes just to learn where the text ended, and then read a few bytes. The next read did it again.

Loop two: checking for duplicates one by one. Each item that was read was stored in a plain list, and before storing it the code compared it with every item already in the list to make sure it was not a duplicate. The last item needs about 63,000 comparisons. Added up, that is roughly 63,000 × 63,000 ÷ 2, close to two billion comparisons.

Both loops have the same shape. The work for one item grows with the number of items, so the total grows with the square of the number of items. This is called quadratic time. Twice the items means about four times the work.

The fix

t0st wrote a small patch, a proof of concept, that changed the game's code as it ran. It measured the text once and remembered the length, so the reader stopped walking to the end each time. It also worked around the slow duplicate check. On his machine, by his own measurements as reported in the press, removing the duplicate check alone took loading from about six minutes to about four and a half, fixing the length measurement alone brought it to about two minutes fifty, and both together brought it to about one minute fifty seconds.

The proper repair for loop two is a hash table: a structure that turns each key into a slot number, so checking "have I seen this item?" takes one quick look instead of a walk through the whole list. Once both loops are fixed, the work for each item stays the same no matter how many items there are. That is linear time.

Rockstar confirmed to PC Gamer that he had found a real problem in the PC loading code, and shipped its own fix in a GTA Online update in March 2021. t0st said Rockstar paid him $10,000 through its bug bounty program, which he described as an exception, since the program normally rewards security reports.

Rule of thumb

If the work you do for each item depends on how many items there are, your loop is quadratic. Look for a scan, a search or a copy hiding inside a loop, including inside a library call.

The code

A small catalogue loader in Lua with both fixes as switches, using the demo's names. Lua strings know their own length, so Lua does not have the strlen trap itself. It has a close cousin: cutting off the part you have read with rest:sub(...) copies all the text that is left, every time. That is the same walk to the end. Start with N = 12, then try 5,000 and 20,000 with the fixes on and off.

-- Load "name,price" lines, with the two fixes as switches
local FIX_LENGTH = true  -- fix 1: never re-walk the text that is left
local FIX_HASH = true    -- fix 2: find duplicates with a hash set
local N = 12             -- items in the file

local function makeCatalog(n)
  local lines = {}
  for i = 1, n do
    lines[i] = "item_" .. i .. "," .. (i * 7 % 1000)
  end
  return table.concat(lines, "\n") .. "\n"
end

local function loadCatalog(text)
  local items, seen = {}, {}
  local pos, rest = 1, text
  while true do
    local name, price, nextPos
    if FIX_LENGTH then
      name, price, nextPos = text:match("^([^,\n]+),(%d+)\n()", pos)
      pos = nextPos
    else
      name, price = rest:match("^([^,\n]+),(%d+)\n")
      if name then
        rest = rest:sub(#name + #price + 3)  -- copies all that is left
      end
    end
    if not name then break end

    local dup = false
    if FIX_HASH then
      dup = seen[name] == true             -- one look, any size
      seen[name] = true
    else
      for i = 1, #items do                 -- compare with every stored item
        if items[i].name == name then dup = true end
      end
    end
    if not dup then
      items[#items + 1] = { name = name, price = tonumber(price) }
    end
  end
  return items
end

local result, seconds
function love.load()
  local text = makeCatalog(N)
  local start = love.timer.getTime()
  result = loadCatalog(text)
  seconds = love.timer.getTime() - start
end

function love.draw()
  love.graphics.print(#result .. " items in " .. string.format("%.3f", seconds) .. " s", 20, 20)
end

The fixed parser keeps a position number, pos, and asks match to start there; the () at the end of the pattern returns the position just after the line. A Lua table is a hash table, so seen[name] is the hash set.

Pitfalls

  • Testing only with small data. At 1,000 items the second demo needs about a million steps, a blink for a computer. Test loaders with ten times the data you expect.
  • Loops hidden in library calls. sscanf walking to the end of its input surprised many programmers. In Lua, string.sub copies, and table.insert(t, 1, x) and table.remove(t, 1) shift every element. Inside a loop, each becomes quadratic.
  • Data that grows after release. A live game's catalogues and save files get longer with every update. Code that was fine at launch can be slow years later.
  • Fixing by deleting a check. A patch that skips a duplicate check is fine for an experiment, but the check may exist for a reason. Make it fast instead of removing it.
  • Guessing instead of measuring. t0st found the problem with a profiler. Profile before you rewrite.

In real games

This is the rare story in this series where the fix came from a player. t0st published his write-up on his blog and shared the patch's source on GitHub.

The lesson for today: the constraint here was not the hardware but the growth of the data, and that constraint is everywhere now. A web game that parses a large JSON file on every start, a mobile game that searches thousands of owned items each frame, or a server that checks every player against every other player all hit the same wall. The repair is usually the same: remember what you already measured, and use a hash table instead of a search.

Your turn (15 minutes)

Find one loader or start-up routine in your own project, or use the Lua code above. Time it with your real data, then with ten times as much (copy the data or generate fake entries). If the time grows about ten times, it is linear. If it grows about a hundred times, find the hidden loop and fix it. You are done when ten times the data costs about ten times the time.

Takeaways

  • GTA Online's PC loading spent minutes reading one 10 MB JSON file of about 63,000 items.
  • Two loops were quadratic: sscanf measured the rest of the text on every read, and each item was checked against every stored item for duplicates.
  • A player found both with a profiler and disassembly, and on his PC a patch cut loading from about six minutes to under two.
  • Rockstar confirmed the problem, shipped a fix in March 2021 and, by t0st's account, paid him a $10,000 bounty.
  • Remember lengths and positions instead of re-measuring, use hash tables for "have I seen this?", and test with ten times the data.

Out Run: a 3D road drawn one line at a time

How Out Run's road looks 3D with no polygons: each screen line is one flat strip at one depth, shifted and sized from a table built every frame.

In Sega's Out Run (1986, directed by Yu Suzuki) the road bends away into the distance, climbs over hills and drops out of sight behind crests, and the kerb stripes rush towards you. It looks 3D. There is not a single polygon on the screen.

The constraint: no hardware for 3D

Arcade boards of the mid-1980s were good at scrolling tile backgrounds and drawing sprites, small pictures placed anywhere on screen. Filling a full 3D scene, triangle by triangle, every frame was beyond affordable hardware. A winding, climbing road had to be made from what the hardware did quickly: copying rows of pixels.

The trick: one screen line sees one depth

Below the horizon, every row of the picture shows the ground at one distance: far just under the horizon, close at the bottom. If the eye is at height h and the screen is d pixels from the eye (the focal distance), the ground seen on a line n pixels below the horizon is at depth

depth = h * d / n

and anything at that depth appears scaled by d / depth. So the road on that line is a flat strip: a centre and a half width, both known as soon as you know the depth. Stack the strips and you have a road shaped like a triangle pointing at the horizon.

Now bend and lift the strips. For a curve, shift each strip's centre sideways, a little more for every step into the distance. For a hill, give the ground a height at each depth: higher ground lands higher on the screen, and road behind a crest lands on lines nearer road already covers, so it is not drawn. For speed, colour the strips by light and dark bands fixed to the ground; as the car moves, the bands slide down the screen.

Trees, signs and cars are sprites scaled by the same d / depth and drawn far to near, so near objects cover far ones.

How Out Run split the work

Out Run's board, a successor to Sega's Hang-On hardware, has two Motorola 68000 processors and a Z80 for sound, plus hardware that scales sprites. It also has a dedicated road generator. Emulator and reverse-engineering source code shows how it works:

  • The road graphics live in ROM as 256 stored rows of road pixels for each road, each pixel one of a few values: road, inner stripe, outer stripe, outside.
  • Road memory holds a line table: for each screen line, which stored row to use (or a solid colour), a horizontal scroll value, and colour choices for the stripes.
  • The chip copies the chosen row onto the screen line, shifted by the scroll value. Nothing is computed per pixel.

The second 68000 builds that table every frame from the track data: it interpolates the curve into one horizontal position per line, works out the height of the road and where the horizon sits, and writes the result. The table is double buffered, so the chip draws from one copy while the processor fills the other. The hardware can also draw two roads with a priority between them, which suits the places where the road splits in two.

Fact and legend

The game is often called "fake 3D". The depth is real perspective arithmetic; only the drawing is done line by line instead of with polygons. That the road's width comes from which stored row a line picks is our reading of the emulation code, which copies one stored pixel per screen pixel. The rebuild below draws each strip directly.

The idea in one line

Do the 3D maths once per screen line, not once per pixel, and let a simple drawer turn the table into a picture.

The lesson for today

Retro-style racers on phones and the web still draw roads this way, because a few hundred strips cost almost nothing. The deeper pattern is everywhere: work out a small table per row, per tile or per object, then let fast, simple code apply it. A shader that computes floor depth from the pixel's row is the same rule. Scaled flat pictures survive as billboards: distant trees drawn as one image facing the camera.

The code

The demo's road in LÖVE, with the same numbers. buildTable walks into the distance in steps of 20 units, bends and lifts the road, and fills any new screen lines with that step's entry. love.draw paints each line as flat strips.

-- Out Run style road: one table entry per screen line, then flat strips.
local SW, SH, HORIZON = 320, 200, 100
local DIST, CAM_H, ROAD_W = 160, 1000, 700
local STEP, FAR, STRIPE = 20, 30000, 400
local CURVE, HILL, SPEED = 6, 500, 3000
local SKY, LINE = {0.5, 0.72, 0.9}, {0.95, 0.95, 0.95}
local GRASS = { [0] = {0.29, 0.62, 0.26}, [1] = {0.25, 0.56, 0.23} }
local KERB  = { [0] = {0.85, 0.85, 0.85}, [1] = {0.75, 0.22, 0.17} }
local ROAD  = { [0] = {0.45, 0.45, 0.45}, [1] = {0.42, 0.42, 0.42} }
local pos = 0

local function bend(zw) return math.sin(zw * 2 * math.pi / 12000) end
local function terrain(zw) return HILL * math.sin(zw * 2 * math.pi / 20000) end

local function buildTable()
  local lines, maxY, x, dx = {}, SH, 0, 0
  local camY = CAM_H + terrain(pos)
  for z = STEP, FAR, STEP do
    local zw = pos + z
    dx = dx + CURVE * 1e-5 * bend(zw) * STEP        -- the road turns a bit more
    x = x + dx * STEP
    local scale = DIST / z
    local yi = math.floor(HORIZON + (camY - terrain(zw)) * scale)
    if yi < maxY then                                -- not hidden behind a crest
      local entry = { z = z, cx = SW / 2 + x * scale, hw = ROAD_W * scale,
                      stripe = math.floor(zw / STRIPE) % 2 }
      for line = math.min(maxY, SH) - 1, math.max(yi, 0), -1 do lines[line] = entry end
      maxY = yi
    end
    if maxY <= 0 then break end
  end
  return lines
end

local function strip(y, x1, x2, c)
  love.graphics.setColor(c[1], c[2], c[3])
  love.graphics.rectangle("fill", x1, y, x2 - x1, 1)
end

function love.load()
  love.window.setMode(SW * 3, SH * 3)
end

function love.update(dt)
  pos = (pos + SPEED * dt) % 120000
end

function love.draw()
  local lines = buildTable()
  love.graphics.scale(3, 3)
  for y = 0, SH - 1 do
    local e = lines[y]
    if not e then strip(y, 0, SW, SKY)
    else
      strip(y, 0, SW, GRASS[e.stripe])
      strip(y, e.cx - e.hw * 1.2, e.cx + e.hw * 1.2, KERB[e.stripe])
      strip(y, e.cx - e.hw, e.cx + e.hw, ROAD[e.stripe])
      if e.stripe == 0 then strip(y, e.cx - e.hw * 0.03, e.cx + e.hw * 0.03, LINE) end
    end
  end
end

The window is 960 by 600, the demo's 320 by 200 screen scaled three times, showing the demo's default road. The 3D lives entirely in buildTable; love.draw knows nothing about depth, just as Out Run's road chip knew nothing about the track.

Pitfalls

  • Dividing by zero at the horizon. The depth formula divides by the distance below the horizon. Walk forward in depth and project to lines instead, as the code does.
  • Stripes that crawl and shimmer. Fix bands to the ground (pos + z), not the screen. Far away a band is thinner than a line and flickers; use wide bands.
  • Sprites popping through hills. A sign behind a crest must be cut off by the nearer road. The demo clips each sprite at the highest road line nearer than it.
  • Curves that swing the camera. The sideways shift must start at zero at the car and grow with depth, or the bottom of the road slides sideways.

In real games

Sega's Hang-On (1985) ran on the earlier hardware in the same family. Line-by-line roads also appear on machines with no road chip, where the processor shifts each line, as in Activision's Enduro for the Atari 2600, which Louis Gorenfeld analyses on his pseudo 3D page. The Cannonball project rewrote Out Run's 68000 code in C++ and still emulates the road chip, because the game's logic is built around that line table.

Takeaways

  • Below the horizon, each screen line shows the ground at one depth: depth = height × focal ÷ lines below horizon.
  • A road is a stack of flat strips; curves shift the strips, hills move them up or down, and ground-fixed colour bands sell the speed.
  • Out Run's processor built a per-line table every frame, and a road chip turned each entry into a line of pixels.
  • Do expensive maths per row or per object, not per pixel, and hand the result to a simple drawer.

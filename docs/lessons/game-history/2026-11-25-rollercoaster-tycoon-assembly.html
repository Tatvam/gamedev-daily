RollerCoaster Tycoon: a thousand guests on a 1999 PC

Why Chris Sawyer wrote RollerCoaster Tycoon in assembly, and how cutting the work done per guest lets a simulation hold far more of them.

Zoom out over a busy park in RollerCoaster Tycoon and you see crowds: hundreds, often more than a thousand small people walking the paths, queuing, eating, getting lost and complaining about the price of umbrellas. Every one of them is simulated, not painted on. The game ran on ordinary home PCs of 1999, which were many times slower than a cheap phone today.

The constraint: cost per guest times the number of guests

A crowd simulation has one simple cost formula. If each guest takes some amount of work per frame, the whole park takes that amount multiplied by the number of guests. Double the crowd and you double the bill. The computer has a fixed amount of time to pay that bill before the next frame is due: the frame budget, about 16.7 milliseconds at 60 frames per second.

That means a small waste per guest is never small. An extra hundred instructions per guest does not matter with ten guests. With two thousand guests it is two hundred thousand extra instructions, every frame. Home PCs of the late 1990s ran at a few hundred megahertz at best, so a designer who wanted big crowds had to make each guest very cheap.

The trick: write it close to the machine

Chris Sawyer designed and programmed RollerCoaster Tycoon, released for Windows in 1999, almost entirely in x86 assembly language. Assembly is a text form of the processor's own instructions: one line is roughly one instruction, such as "add these two registers" or "load this byte from memory". There is no compiler deciding things for you. The programmer chooses which values live in the processor's fast registers, how many bytes each field takes and in what order data sits in memory.

Sawyer's own FAQ, as reported by search summaries I could read in this session, describes the game as about 99 percent assembly, with a small amount of C to talk to Windows and DirectX. He had already written Transport Tycoon (1994) the same way. In later interviews he is reported to have said that a higher-level language would have made the game slower or forced him to simplify the simulation. I could not open those pages, so treat the exact wording as reported, not quoted.

Assembly does not make code fast by magic; a slow idea in assembly is still slow. What it gives is total control and a habit: you see every instruction you spend, so you notice when a guest does work it does not need.

Rebuilding the idea: do not think every frame

We cannot rebuild hand-written x86 in a web page, and this page does not claim to show RollerCoaster Tycoon's own pathfinding. What we can rebuild is the arithmetic that drove the whole design. Take one common guest task, walking to a ride, and write it two ways.

  • Wasteful: every frame, every guest searches the paths from scratch to find its route. On our small park that search checks over 30 tiles per guest on average.
  • Cheap: once, for each ride, the game builds a direction table: for every path tile, which neighbouring tile is one step closer to that ride. A guest only decides anything when it arrives at a new tile, and then it reads one entry from the table. The rest of the time it just walks.

The table costs something too: building it for four rides checks 324 tiles. But that happens once, not once per guest per frame. Moving work out of the loop that runs most often is the single most useful optimisation habit there is.

Rule of thumb

Find the loop that runs once per entity per frame. Every unit of work you remove there is multiplied by the size of your crowd.

The code

The demo's cheap mode in Lua, with the same park, the same four rides and the same walking speed of 2 tiles per second. buildDirections runs once per ride. updateGuest runs once per guest per frame, and on most frames it only adds to a timer.

local MAP = {
  "........................", ".A#######....#######B...",
  "........#....#......#...", "........#....#......#...",
  "..#############.....#...", "..#.....#.....#######...",
  "..#.....#.......#.......", "..#.....#.......#.......",
  "..########......#####...", "..#......#..........#...",
  ".C#......#######....#D..", ".........#..............",
  ".........#..............", ".........E..............",
}
local W, H, SPEED, TILE = 24, 14, 2, 20   -- SPEED in tiles per second
local DIRS = { { 1, 0 }, { -1, 0 }, { 0, 1 }, { 0, -1 } }
local rides, guests, entrance = {}, {}, nil

local function walkable(x, y)
  return x >= 1 and y >= 1 and x <= W and y <= H and MAP[y]:sub(x, x) ~= "."
end

-- Runs once per ride: step[i] is the next tile toward the ride
local function buildDirections(tx, ty)
  local step, queue, head = { [ty * W + tx] = { tx, ty } }, { { tx, ty } }, 1
  while head <= #queue do
    local x, y = queue[head][1], queue[head][2]
    head = head + 1
    for _, d in ipairs(DIRS) do
      local nx, ny = x + d[1], y + d[2]
      if walkable(nx, ny) and not step[ny * W + nx] then
        step[ny * W + nx] = { x, y }
        queue[#queue + 1] = { nx, ny }
      end
    end
  end
  return step
end

-- Runs once per guest per frame
local function updateGuest(g, dt)
  g.t = g.t + SPEED * dt
  if g.t < 1 then return end              -- still walking: no decision
  g.t = g.t - 1
  g.x, g.y = g.nx, g.ny
  if g.x == g.ride.x and g.y == g.ride.y then
    g.ride = rides[love.math.random(#rides)]
  end
  local nxt = g.ride.step[g.y * W + g.x]  -- one table lookup
  g.nx, g.ny = nxt[1], nxt[2]
end

function love.load()
  love.math.setRandomSeed(7)
  for y = 1, H do
    for x = 1, W do
      local ch = MAP[y]:sub(x, x)
      if ch == "E" then entrance = { x, y } end
      if ch:match("%u") and ch ~= "E" then
        rides[#rides + 1] = { x = x, y = y, step = buildDirections(x, y) }
      end
    end
  end
  for i = 1, 1000 do
    local ex, ey = entrance[1], entrance[2]
    local g = { x = ex, y = ey, t = -love.math.random() * 10,
                ride = rides[love.math.random(#rides)] }
    local nxt = g.ride.step[ey * W + ex]
    g.nx, g.ny = nxt[1], nxt[2]
    guests[i] = g
  end
end

function love.update(dt)
  for _, g in ipairs(guests) do updateGuest(g, dt) end
end

function love.draw()
  for _, g in ipairs(guests) do
    local u = math.max(0, math.min(1, g.t))
    local px = (g.x + (g.nx - g.x) * u) * TILE
    local py = (g.y + (g.ny - g.y) * u) * TILE
    love.graphics.rectangle("fill", px, py, 3, 3)
  end
end

A guest with a negative t is still waiting at the entrance, so the crowd leaves over five seconds. The wasteful version replaces the highlighted lookup with a full search, run every frame.

Pitfalls

  • Reaching for assembly, or any clever trick, before measuring. Modern compilers write better machine code than most people do by hand. The large wins come from doing less work, which you find by timing the per-entity loop, not by guessing.
  • Hidden per-frame work. Searches, sorts, string building and allocating new tables inside the per-entity update look harmless with ten entities. Ask of every line: does this have to happen every frame, for every one?
  • A stale table. When the player builds or deletes a path, the direction tables are wrong until you rebuild them. Rebuild on the edit, not every frame.
  • Memory for speed. One table per destination costs one entry per tile per ride. On a large map with hundreds of destinations, build tables only for popular targets.

In real games

Sawyer used the same approach for Transport Tycoon and for RollerCoaster Tycoon 2 (2002). Much of what players know about the sequel's internals comes from OpenRCT2, an open-source project that rewrote the original assembly routines one by one in C, and later C++, while keeping the game's behaviour. It still needs the original game's data files to run.

Assembly was common in 1990s PC games for the hottest loops, such as drawing sprites; a PC Gamer report quotes an Age of Empires developer saying that game leaned on it to scroll and fill the screen quickly. RollerCoaster Tycoon stands out for using it for nearly everything.

The lesson for today: the per-entity multiplication never went away. Phone games pay for wasted work in battery and heat, browser games in one busy thread, and servers in how many players one machine holds. Data-oriented engine designs, which pack each kind of entity data together and update it in tight loops, answer the same question Sawyer answered in assembly.

You are done when you can name the guest count at which the wasteful version passes 16 milliseconds on your machine, and how many guests the cheap version handles in the same time.

Takeaways

  • A crowd costs the work per member times the number of members, so per-guest waste is multiplied by the whole park.
  • Chris Sawyer wrote RollerCoaster Tycoon almost entirely in x86 assembly, which gave him control over every instruction spent per guest.
  • Assembly helps only when the work itself is lean; the biggest wins come from doing less, less often.
  • Move expensive work out of the per-entity loop: build a shared table once and let each entity read it.

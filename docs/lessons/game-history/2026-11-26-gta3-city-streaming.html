Grand Theft Auto III: a city that only exists around you

How GTA III kept a whole city playable on a PS2 by streaming blocks from the disc around the player, and why driving too fast breaks the illusion.

In Grand Theft Auto III (2001) you can steal a car and drive from one end of Liberty City to the other without a single loading screen. It feels as if the whole city is there, all the time. It is not. Most of it is sitting on the disc, and only a small patch around you is in memory at any moment.

The constraint: a city bigger than the memory

The PlayStation 2 has 32 megabytes of main memory, shared by the code, the cars, the people, the sound and the city. Obbe Vermeij, a technical director on the game, has said in posts reported by several outlets that there was no way the whole map of GTA III could fit in PS2 memory.

The disc holds all of it, but a disc is slow. Reading takes time, and moving the read head to a new place on the disc, a seek, takes time too, even before any data arrives.

The trick: stream a ring around the player

Streaming means loading data while the game keeps running, a piece at a time, instead of stopping for a loading screen. GTA III streams its city. The idea, in the simplified form this page rebuilds, has four parts:

  1. Cut the city into pieces. Here they are square blocks, each with its own size in megabytes.
  2. Keep a load ring: every block within a set distance of the player should be in memory. The ring is wider than what the player can see, so new blocks arrive before they are needed.
  3. Keep a queue of missing blocks in the ring and read them from the disc one at a time, nearest first.
  4. When memory is full, evict (throw away) the block farthest from the player that is outside the ring. It is still on the disc and can be read again later.

Where it breaks: speed

Streaming is a race. Each block the player moves brings a new strip of blocks into the ring. If the disc fetches that strip before the player crosses the margin, nobody notices. If not, the player reaches a place that is not loaded yet, which games show as missing buildings, blurry stand-ins or a sudden pause.

This turned into design. In Vermeij's reported account, the Dodo, the only plane the player can fly, was kept from going too fast or too far because, in his reported words, "the streaming couldn't keep up" if it went too fast or too far. Coverage of his posts also says vehicles were tuned slower for the same reason, and that streaming was harder on older PS2 models and older discs. I could not open his original posts, so treat this wording as reported.

He is also reported to have said that models placed close together on the DVD load faster, and that a programmer, Adam Fowler, wrote code that kept moving loaded models around in memory so that freed gaps could be reused. Those gaps are called fragmentation: free memory split into pieces too small for the next block. The demo below keeps memory packed tight for free; the real game had to work for that.

Rule of thumb

Streaming keeps up when the disc can load a new strip of the world faster than the player crosses the margin between the load ring and the view. If it cannot, widen the margin, shrink the data, speed up the reads or slow down the player.

Try it

A car drives a loop around a city of 16 by 16 blocks. The drive starts after a short loading screen that fills the first ring. At the default settings the disc keeps up. Now raise Car speed to 2 blocks per second: red holes start to appear inside the solid circle, which is what the player can see, and at 3 or 4 they hardly ever go away. Then lower Disc speed, or drop Memory to 4 MB, where the ring no longer fits at all. Switch Show to What the player sees to hide everything the player never knows about.

The code

The demo's streaming rules in Lua, with the same grid, radii, seek time and default speeds. Block sizes come from a different random generator, so they will not match the demo block for block. updateStreaming gives the disc a slice of time each frame; calling it once with 10 seconds before the drive is the loading screen.

local GRID, LOAD_R, VIEW_R = 16, 2.5, 1.5  -- radii in blocks
local SEEK = 0.05                 -- seconds to move the read head
local discSpeed, memory = 4, 12   -- MB per second, MB
local speed = 1                   -- car speed, blocks per second
local ROUTE = { {1,1}, {14,1}, {14,6}, {4,6}, {4,11}, {14,11}, {14,14}, {1,14} }
local blocks, used, reading, leg = {}, 0, nil, 1
local car = { x = 1, y = 1 }

local function dist(b)
  return math.sqrt((b.cx - car.x)^2 + (b.cy - car.y)^2)
end

-- Free memory by dropping the farthest loaded block outside the ring
local function evictFor(size)
  while used + size > memory do
    local worst = nil
    for _, b in ipairs(blocks) do
      if b.loaded and dist(b) > LOAD_R and (not worst or dist(b) > dist(worst)) then
        worst = b
      end
    end
    if not worst then return false end   -- the ring itself does not fit
    worst.loaded = false
    used = used - worst.size
  end
  return true
end

local function startNextRead()
  local best = nil
  for _, b in ipairs(blocks) do
    if not b.loaded and dist(b) <= LOAD_R and (not best or dist(b) < dist(best)) then
      best = b
    end
  end
  if best and evictFor(best.size) then
    used = used + best.size              -- reserve the memory now
    reading = best
    reading.timeLeft = SEEK + best.size / discSpeed
  end
end

local function updateStreaming(dt)
  local t = dt
  while t > 0 do
    if reading and dist(reading) > LOAD_R then   -- left the ring: cancel
      used = used - reading.size
      reading = nil
    end
    if not reading then startNextRead() end
    if not reading then return end               -- nothing to read
    local step = math.min(t, reading.timeLeft)
    reading.timeLeft = reading.timeLeft - step
    t = t - step
    if reading.timeLeft <= 0 then
      reading.loaded = true
      reading = nil
    end
  end
end

local function moveCar(dt)
  local left = speed * dt
  while left > 0 do
    local target = ROUTE[leg % #ROUTE + 1]
    local dx, dy = target[1] - car.x, target[2] - car.y
    local d = math.sqrt(dx * dx + dy * dy)
    if d <= left then
      car.x, car.y = target[1], target[2]
      leg = leg % #ROUTE + 1
      left = left - d
    else
      car.x, car.y = car.x + dx / d * left, car.y + dy / d * left
      left = 0
    end
  end
end

function love.load()
  love.math.setRandomSeed(3)
  for j = 0, GRID - 1 do
    for i = 0, GRID - 1 do
      blocks[#blocks + 1] = { i = i, j = j, cx = i + 0.5, cy = j + 0.5,
                              size = 0.2 + 0.4 * love.math.random(), loaded = false }
    end
  end
  updateStreaming(10)                    -- the loading screen
end

function love.update(dt)
  moveCar(dt)
  updateStreaming(dt)
end

function love.draw()
  local S = 30                           -- pixels per block
  for _, b in ipairs(blocks) do
    if b.loaded then
      love.graphics.setColor(0.5, 0.6, 0.8)
    elseif dist(b) <= VIEW_R then
      love.graphics.setColor(0.9, 0.2, 0.2)  -- a hole the player can see
    else
      love.graphics.setColor(0.15, 0.15, 0.15)
    end
    love.graphics.rectangle("fill", b.i * S + 2, b.j * S + 2, S - 4, S - 4)
  end
  love.graphics.setColor(1, 1, 1)
  love.graphics.circle("fill", car.x * S, car.y * S, 5)
end

The car drives on the roads between blocks, so its position is measured at block corners and a block's distance is taken to its centre.

Pitfalls

  • A ring with no margin. If the load radius equals the view radius, every new block is needed the moment it is requested. The margin is what buys the disc its time.
  • Loading in the wrong order. Reading the queue in the order blocks were added, rather than nearest first, spends disc time on blocks behind the player. Many engines also load ahead in the direction of travel.
  • Forgetting the seek. Each read pays the seek again, so store things that load together, together.
  • Fragmentation. Loading and freeing blocks of different sizes leaves gaps. Total free memory can be enough while no single gap is.
  • Waiting on the main thread. If the game stops to wait for a read, streaming becomes a stutter. Read in the background.

In real games

Streaming around the player was not new in 2001. Crash Bandicoot (1996) paged its levels from the disc as the player moved along a mostly fixed path, which we covered earlier in this series. GTA III's challenge was that the player could go in any direction, at the speed of whatever car they stole. Its sequels Vice City and San Andreas used the same kind of engine.

The lesson for today: the constraint moved, it did not vanish. Open-world engines still stream; Unreal Engine 5's World Partition, for example, splits a map into a grid of cells and loads the cells near the player. A web game streams over the network, where a "seek" is a round trip to a server. Online maps load image tiles around what you are looking at, and blur or blank the ones that have not arrived when you pan too fast. Same race, same four answers.

Takeaways

  • GTA III's city did not fit in the PS2's 32 MB of memory, so the game streamed it from the disc around the player.
  • Streaming keeps a load ring wider than the view, reads missing pieces nearest first and evicts the farthest pieces when memory is full.
  • Each read costs a seek plus size divided by disc speed, so the player's top speed is limited by the disc.
  • That limit reached the design: by the developers' reported account, vehicles and the Dodo plane were kept slow enough for streaming to keep up.
  • The same race runs today in open-world engines, web games and map apps.

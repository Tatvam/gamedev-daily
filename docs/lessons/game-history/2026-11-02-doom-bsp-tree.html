Doom: walls in the right order from a tree built in advance

How Doom drew walls at any angle nearest first without sorting: a binary space partitioning tree, built before the game ships, walked once per frame.

Wolfenstein 3D could only build mazes from square blocks. A year later, in 1993, id Software's Doom had walls at any angle, rooms of different shapes and floors at different heights, on the same kind of PC with no 3D hardware. Every frame the game has to know which walls are in front of which. Doom does not work that out while you play. The answer is stored in the map file.

The constraint: what hides what?

Seen from above, a Doom level is flat: a set of lines on a 2D plan, each line a wall, with floor and ceiling heights attached to the areas between them. The renderer turns these lines into columns on the screen, much as Wolfenstein 3D did. But with walls at any angle there is no grid to step through, so the renderer needs another way to decide which wall covers which.

The obvious answer is to sort the walls by distance every frame. That costs time for every wall in the level, every frame, and it can still be wrong: a long wall can have its middle further away than a short wall that it hides. A depth value stored for every pixel would solve it, but that means extra memory and an extra test on every pixel the processor writes. Doom avoids both.

The trick: split the map once, ahead of time

Take any wall and extend its line across the whole map. This is a partition line. Every other wall is now on one side of it or the other. A wall that crosses the line is cut into two pieces; Doom calls each piece of wall a seg (short for segment).

Now repeat on each side separately, with a new partition line, and keep going until every group of segs encloses a convex area: one with no dents, where no wall can block your view of another wall in the same area. Doom calls such an area a subsector.

The splits form a binary space partitioning tree, or BSP tree. Each inner node holds one partition line and two children, the front side and the back side. Each leaf is a subsector with its list of segs.

Why the tree gives the drawing order

One fact makes it work: a wall on your side of a line can never be hidden by a wall on the far side of that line. So at every node the renderer asks one question, "which side of this line is the player on?", walks that side's branch first and the other branch second. Done from the root down, this visits every subsector from nearest to furthest. Inside a subsector the order does not matter, because the walls of a convex area that face you never overlap on screen.

The released source shows exactly this. The function R_RenderBSPNode calls R_PointOnSide to find the player's side of a node's line, recurses into that child, then into the other one. No list of walls is ever sorted.

Stopping early

Front to back has a bonus. Doom keeps a short list, solidsegs, of the screen column ranges that solid walls have already covered. A new wall only draws in the columns still open, so each wall pixel is written once. Each node also stores a bounding box for each child. Before entering the far branch, R_CheckBBox checks whether that box would land in any open column; if it is out of view or fully covered, the whole branch is skipped. In a room with solid walls on all sides, most of the level is never visited.

Floors and ceilings are filled in after the walls, and sprites last. Things that can be seen through, like monsters, still need sorting; the tree only orders the fixed walls.

Built before shipping

The tree is made by a separate tool called a node builder, run when a map is finished. id's own builder, DoomBSP, was written for the NeXTSTEP computers the team developed on, and its source survives. It tries seg lines as partitions (on a large group, a sample of about 40 of them) and scores each one: the size of the larger side, plus 8 for every seg it would cut. Lowest score wins. A balanced tree stays shallow, and every cut adds a seg the game must store and process, so cuts are punished hard. A line with nothing behind it is not a candidate, and a group in which every line is like that is convex: a leaf.

The price

The tree describes walls that never move sideways. Doom's doors and lifts move up and down by changing a floor or ceiling height, which leaves the 2D plan, and so the tree, unchanged. Change a wall's position and the nodes must be rebuilt.

The method was not invented for Doom. Henry Fuchs, Zvi Kedem and Bruce Naylor described BSP trees for finding visible surfaces in a 1980 paper. Doom put it to work in a game that ran on a home PC. In his 1997 notes for the source release, John Carmack wrote: "I used the BSP tree for rendering things".

The lesson for today

Anything that never changes can have its hard questions answered before the game ships. Modern engines still bake static geometry into spatial trees for visibility, collision and ray queries, and still pay the same price: what moves has to be handled another way.

The code

The builder and the walk in plain Lua, using the demo's walls, its tolerance EPS and DoomBSP's score of 8 per cut, so it builds the same tree. A two-sided wall is two segs facing opposite ways. love.draw numbers the walls that face the player in the order they come out.

local EPS = 1e-4
local function seg(name, x1, y1, x2, y2) return { name = name, x1 = x1, y1 = y1, x2 = x2, y2 = y2 } end
local walls = {
  seg("A", 1, 1, 15, 1), seg("B", 15, 1, 15, 11), seg("C", 15, 11, 1, 11), seg("D", 1, 11, 1, 1),
  seg("E", 10, 3, 10, 5), seg("F", 10, 5, 12, 5), seg("G", 12, 5, 12, 3), seg("H", 12, 3, 10, 3),
  seg("I", 3, 8, 7, 5), seg("I", 7, 5, 3, 8), seg("J", 8, 9, 12, 8), seg("J", 12, 8, 8, 9),
}
local player = { x = 8, y = 3 }

-- Signed distance from the line of s. Positive = front (right-hand side, y down).
local function side(s, px, py)
  local dx, dy = s.x2 - s.x1, s.y2 - s.y1
  return (dx * (py - s.y1) - dy * (px - s.x1)) / math.sqrt(dx * dx + dy * dy)
end

local function classify(div, s)
  local a, b = side(div, s.x1, s.y1), side(div, s.x2, s.y2)
  if math.abs(a) < EPS and math.abs(b) < EPS then        -- on the line itself
    local same = (div.x2 - div.x1) * (s.x2 - s.x1) + (div.y2 - div.y1) * (s.y2 - s.y1) > 0
    if same then return "front" else return "back" end
  end
  if a > -EPS and b > -EPS then return "front" end
  if a < EPS and b < EPS then return "back" end
  return "split", a, b
end

local function cut(s, a, b)                 -- returns the front piece, then the back piece
  local t = a / (a - b)
  local mx, my = s.x1 + (s.x2 - s.x1) * t, s.y1 + (s.y2 - s.y1) * t
  local p1, p2 = seg(s.name, s.x1, s.y1, mx, my), seg(s.name, mx, my, s.x2, s.y2)
  if a > 0 then return p1, p2 else return p2, p1 end
end

local function grade(div, segs)             -- DoomBSP's score: lower is better
  local f, b, cuts = 0, 0, 0
  for _, s in ipairs(segs) do
    local c = "front"
    if s ~= div then c = classify(div, s) end
    if c == "front" then f = f + 1
    elseif c == "back" then b = b + 1
    else f, b, cuts = f + 1, b + 1, cuts + 1 end
  end
  if b == 0 then return nil end             -- nothing behind it: not a useful split
  return math.max(f, b) + 8 * cuts
end

local function buildBSP(segs)
  local best, bestGrade = nil, math.huge
  for _, s in ipairs(segs) do
    local g = grade(s, segs)
    if g and g < bestGrade then best, bestGrade = s, g end
  end
  if not best then return { leaf = true, segs = segs } end   -- convex: a subsector
  local front, back = {}, {}
  for _, s in ipairs(segs) do
    local c, a, b = "front", 0, 0
    if s ~= best then c, a, b = classify(best, s) end
    if c == "front" then table.insert(front, s)
    elseif c == "back" then table.insert(back, s)
    else
      local f, k = cut(s, a, b)
      table.insert(front, f)
      table.insert(back, k)
    end
  end
  return { div = best, front = buildBSP(front), back = buildBSP(back) }
end

local function walk(node, px, py, visit)    -- nearest leaf first
  if node.leaf then visit(node) return end
  local near, far = node.front, node.back
  if side(node.div, px, py) < 0 then near, far = node.back, node.front end
  walk(near, px, py, visit)
  walk(far, px, py, visit)                  -- Doom checks far's bounding box first
end

local tree = buildBSP(walls)

function love.draw()
  local S, order = 40, 0
  walk(tree, player.x, player.y, function(leaf)
    order = order + 1
    for _, s in ipairs(leaf.segs) do
      if side(s, player.x, player.y) > EPS then   -- faces the player
        love.graphics.line(s.x1 * S, s.y1 * S, s.x2 * S, s.y2 * S)
        love.graphics.print(tostring(order), (s.x1 + s.x2) / 2 * S, (s.y1 + s.y2) / 2 * S)
      end
    end
  end)
end

Building is slow, since every seg is tried against every other at every level, which is why it runs once, offline. The walk is fast: one side test per node.

Pitfalls

  • Choosing partitions badly. Lines that cut many walls multiply the segs, and lopsided splits make deep trees. Score candidates, as DoomBSP did, rather than taking the first wall.
  • No tolerance for "on the line". After a cut, the new end points sit almost exactly on the partition line, and rounding can put them a hair on the wrong side. Treat values within a small EPS as on the line.
  • Moving walls. The tree is only valid for the walls it was built from. Keep moving objects out of it and handle them separately.
  • Forgetting the far branch check. The order alone saves sorting, but the real speed comes from skipping branches that are out of view or already covered.
  • Treating see-through things as solid. Only solid walls may mark columns as covered. Windows, fences and sprites have to be drawn without blocking what is behind them.

In real games

Every game on the Doom engine, including Doom II, Heretic and Hexen, ships its maps with prebuilt nodes, and fan-made node builders are still used to build them. Quake, also from id Software, moved the idea into full 3D: its map compiler splits levels with planes instead of lines. Valve's Source engine still names its map compiler VBSP. The pattern of building a spatial tree offline for static geometry remains standard in engines today.

Takeaways

  • Doom's maps are cut, before the game ships, into convex areas by a tree of partition lines.
  • At each node, visiting the player's side first gives a nearest-to-furthest order with no sorting.
  • Front to back lets Doom fill each screen column once and skip whole branches once they are hidden.
  • The node builder balances the tree and avoids cutting walls; DoomBSP added 8 to a split's score for every cut.
  • The tree only works for walls that never move sideways, which is why Doom's doors move vertically.

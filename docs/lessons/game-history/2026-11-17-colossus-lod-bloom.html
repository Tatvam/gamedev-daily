Shadow of the Colossus: far mountains and light brighter than white

How a PS2 game can show far mountains with fewer points and a sun brighter than white: distance-based level of detail and a bright-pass bloom.

In Shadow of the Colossus you can stand on a cliff and see mountains across the land, under a sky so bright it seems to spill over the rock. The PlayStation 2 could not draw all that land in full detail, and its screen could not show anything brighter than white. Both effects come from one habit: work out what the eye can tell apart, and fake the rest cheaply.

The constraint: a small machine and a white ceiling

Shadow of the Colossus was made by Sony's Team Ico, directed by Fumito Ueda, and released for the PlayStation 2 in 2005. The player rides across one large open land to find giant bosses, the colossi.

The PlayStation 2 has 32 MB of main memory, and its graphics chip, the Graphics Synthesizer, has 4 MB of its own. Screen images store each colour channel as a whole number from 0 to 255, so 255 is the brightest a pixel can be.

Two problems follow. A far mountain range can hold as many triangles as a nearby hill but covers a sliver of the screen. And a real sun is far brighter than a white wall, yet on screen both stop at 255.

Trick 1: spend fewer points on far land

Level of detail (LOD) means keeping several versions of the same object, from detailed to simple, and drawing the simple one when the object is small on screen. For terrain, a simple version can be made by keeping only every 2nd, 4th or 8th height point.

How far is far enough? A step of one metre at distance z covers focal ÷ z pixels on screen, where focal is the camera's scale in pixels. Pick the longest step that still stays under a few pixels:

level = math.floor(math.log(segmentPx * z / focal) / math.log(2))   -- step = 2 ^ level metres

Each time the distance doubles, the level goes up by one and the number of points halves, while the gap between points on screen stays about the same.

A Siliconera article on the game describes its distant land as low-resolution versions swapped for detailed ones as you ride closer. I saw that only in a search summary and could not open it, so treat it as often repeated, not confirmed. The demo rebuilds the general technique, not the game's code.

Trick 2: fake light brighter than white

High dynamic range (HDR) rendering keeps brightness values above 1.0 (screen white) and decides at the end how to show them. Modern chips use floating point images for this. The PlayStation 2's screen formats are 16, 24 or 32 bits of whole numbers, with no room above white.

Bloom imitates what an eye or a camera lens does with very bright light: it spreads into a glow around the bright object. The glow is what tells you "this is brighter than white", even though no pixel is. A bloom pass has four steps:

Step 3 blurs an image a quarter of the width and height: 16 times fewer pixels, and each blur step reaches four times as far. A glow is soft, so nobody sees the lost detail.

Without HDR images there is no light above 1.0 to keep, so on such hardware the usual approach is to set the threshold below white, for example at 80% brightness. That is the "fake" in fake HDR. The demo computes the sun's true brightness, which makes the idea easier to see.

Shadow of the Colossus is well known for this look: heavy bloom, with bright skies bleeding over cliff edges and the colossi's outlines. I could not confirm how the team built it on the PlayStation 2, so the rebuild uses the standard method.

Rule of thumb

Bloom makes nothing brighter than white. It spends the light that did not fit on the pixels around it, and the eye reads that glow as brightness.

Try it

Turn on Show terrain points, then turn Simplify far terrain off: the point count roughly quadruples, yet the picture does not change. Turn it back on, set Segment size on screen to 24 px and move Ride forward: far ridges now jump as they switch level.

Then toggle Bloom. Drag the sun (or focus the picture and use the arrow keys) just behind a ridge and watch the glow spill over the edge. Use View to see the hidden buffers.

The code

Both tricks in plain Lua, with the demo's numbers. glowBuffer takes a quarter-size table of light values (1.0 is white) and returns the glow to add on top. A real game does this on the graphics chip.

local FOCAL = 551        -- pixels: the demo's view is 380 px tall x 1.45
local segmentPx = 4      -- longest terrain segment allowed on screen
local MAX_LEVEL = 9
local THRESHOLD, BLUR_R, GLOW_GAIN = 1.0, 6, 1.5

-- 0 = every point, 1 = every 2nd, 2 = every 4th, ...
local function lodLevel(z)
  local level = math.floor(math.log(segmentPx * z / FOCAL) / math.log(2))
  return math.max(0, math.min(level, MAX_LEVEL))
end

-- heights[1..n]: one terrain height per metre along a ridge at distance z
local function ridgePoints(heights, z)
  local pts = {}
  for i = 1, #heights, 2 ^ lodLevel(z) do pts[#pts + 1] = heights[i] end
  return pts
end

local function blur(buf, w, h, dx, dy)  -- box blur along one direction
  local out = {}
  for y = 1, h do
    out[y] = {}
    for x = 1, w do
      local sum = 0
      for k = -BLUR_R, BLUR_R do
        local sx = math.min(w, math.max(1, x + k * dx))
        local sy = math.min(h, math.max(1, y + k * dy))
        sum = sum + buf[sy][sx]
      end
      out[y][x] = sum / (2 * BLUR_R + 1)
    end
  end
  return out
end

local function glowBuffer(light, w, h)
  local glow = {}
  for y = 1, h do                       -- bright pass
    glow[y] = {}
    for x = 1, w do
      glow[y][x] = math.max(0, light[y][x] - THRESHOLD)
    end
  end
  for pass = 1, 2 do                    -- two box blurs look nearly round
    glow = blur(glow, w, h, 1, 0)
    glow = blur(glow, w, h, 0, 1)
  end
  return glow  -- pixel = math.min(1, math.min(1, scene) + glow * GLOW_GAIN)
end

The first highlighted line turns "how far away" into "how many points to skip". The second keeps only the light the screen had to throw away.

Pitfalls

  • Popping between levels. When a ridge switches level, its outline jumps. Keep segments small, or blend heights between two levels over a short distance (geomorphing).
  • Cracks in 3D terrain. A detailed terrain patch next to a simple one can leave thin gaps along their shared edge. Engines stitch the edge or hang a short wall of triangles (a skirt) under each patch.
  • A threshold that is too low. If ordinary bright pixels pass, everything glows and the picture looks washed out.
  • Bloom without real brightness. If images stop at 1.0, the sun and a white shirt glow equally. With HDR images, give light sources values well above 1.0.

In real games

Large outdoor games routinely simplify distant terrain. Unity's terrain has a Pixel Error setting that plays the role of this demo's segment size. Bloom is a standard post effect: Unity's Bloom has a threshold and an intensity, Godot's Environment has Glow with an HDR threshold, and Unreal has bloom in its post process settings.

The old constraints return on phones and in browsers, where memory bandwidth is scarce: bloom there is still done on shrunken images, and distant terrain is kept simple.

Takeaways

  • Far terrain covers few pixels, so it can be drawn from every 2nd, 4th or 8th point without looking different.
  • Choose the level from the distance: floor(log2(segmentPx × z ÷ focal)) keeps segments a steady size on screen.
  • A screen cannot show anything brighter than white. Bloom spreads the extra light into a glow, which the eye reads as brightness.
  • Bloom is a bright pass, a blur on a shrunken image, and an add. Without HDR images, the threshold sits below white.

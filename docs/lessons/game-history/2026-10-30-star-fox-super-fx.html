Star Fox and the Super FX: a 3D chip hidden in the cartridge

How Star Fox drew polygons on a console built for tiles: a processor in the cartridge drew each picture, and the console copied it in as a background.

Star Fox (1993) flew solid 3D ships through space on a Super Nintendo, a console built to slide flat tiles and sprites around. It managed this by putting a second processor inside the cartridge. You can still see the price: the 3D view moves in visible steps, several times slower than the TV redraws the screen.

The constraint: a console that cannot draw a polygon

The Super Nintendo's main processor is a 65816-family chip that runs at 2.68 MHz for most work and 3.58 MHz at best. Its picture chip has no idea what a triangle is. It builds the screen from tiles (8 by 8 blocks of pixels) and sprites (small movable tiles), all read from 64 KB of video memory.

A 3D picture in software means rotating and projecting every corner (many multiplications), filling every pixel of every visible triangle, and storing the result in the console's tile format, where the bits of one pixel are spread across several bytes. Then it must be copied into video memory. The main processor can write there freely only during blanking, the short gap between one TV picture and the next. The 2.68 MHz processor could not do all of this fast enough for a playable game.

The trick: a second processor that draws, and a background that displays

Argonaut Software, a British studio known for 3D games on home computers such as Starglider, designed a chip for the job and worked with Nintendo on Star Fox. Nintendo sold it as the Super FX. The production chip is printed with the name MARIO; the acronym often given for it is not confirmed here.

The Super FX is a small, fast processor that sits in the cartridge beside the game ROM and its own RAM, about 10.7 MHz in Star Fox. The work is split like this:

  1. The chip transforms the models and fills triangles into a picture in cartridge RAM (32 KB in Star Fox). It has a plot instruction that writes pixels straight into the console's tile format, so no conversion step is needed afterwards.
  2. When a picture is finished, the main processor uses DMA (direct memory access, a fast hardware copy) to move it into video memory during blanking. A full picture can need more than one blank, so the copy may be spread over several TV frames.
  3. The picture chip shows those tiles as an ordinary background layer. The layer's tile map lists the tiles in order, row by row, so the layer behaves like a plain bitmap.

Two limits set the frame rate: the chip's cycles per picture (some per triangle, some per pixel), and the blanks needed for the copy, however simple the picture. So Star Fox's 3D view updates much less often than the TV's 60 frames per second. Technical write-ups usually put it somewhere around 10 to 15 pictures per second, lower in busy scenes. Those are estimates; this page found no official figure.

Shrinking the picture helps both limits at once, which is one reason Super FX games often drew their 3D view in a window smaller than the full screen. Fewer triangles helps only the first. That is why Star Fox's ships are built from a small number of large, flat-coloured faces.

The idea in one line

If the display hardware cannot draw what you need, draw it somewhere else into its native format, and hand it over as something it already knows how to show.

The lesson for today

This is the shape of every modern renderer: a separate processor, the GPU, draws into a buffer the display does not see, and the handover has a cost of its own. The polygon budget lives on as the triangle and pixel budget of a phone game. The small window lives on as dynamic resolution: drawing fewer pixels when a frame runs long, then scaling up.

The code

On a modern PC the drawing itself takes no time worth measuring, so the Lua keeps the Super FX timing as a budget. It draws the picture, works out how many cycles that would have cost, then spends that cost one TV frame at a time before copying. renderShip and drawPicture are your own functions: a triangle filler that returns how many triangles and pixels it handled, and a palette lookup that scales the picture up. The constants match the demo.

local CLOCK = 10740000            -- chip cycles per second (10.74 MHz)
local TICK = 1 / 60               -- one TV frame
local BW, BH = 160, 96            -- the chip's picture, in pixels
local BUFFER_BYTES = BW * BH / 2  -- 4 bits per pixel: 7680 bytes
local COPY_PER_BLANK = 6000       -- bytes copied per blank (assumed)
local CYCLES_PER_TRIANGLE = 400   -- invented costs, see the text
local CYCLES_PER_PIXEL = 4
local budget = 256                -- triangles in the model
local phase, work, clock, angle = "draw", 0, 0, 0
local ram, tv = {}, {}            -- cartridge RAM and video RAM

local function startPicture()
  local triangles, pixels = renderShip(ram, angle, budget)
  work = BW * BH + triangles * CYCLES_PER_TRIANGLE + pixels * CYCLES_PER_PIXEL
  phase = "draw"
end

function love.load()
  startPicture()
end

function love.update(dt)
  angle = angle + 0.9 * dt        -- the game itself never slows down
  clock = clock + dt
  while clock >= TICK do          -- one pass per TV frame
    clock = clock - TICK
    if phase == "draw" then
      work = work - CLOCK * TICK  -- the chip's share of this frame
      if work <= 0 then phase, work = "copy", BUFFER_BYTES end
    else
      work = work - COPY_PER_BLANK   -- DMA during the blank
      if work <= 0 then
        for i = 1, BW * BH do tv[i] = ram[i] end
        startPicture()
      end
    end
  end
end

function love.draw()
  drawPicture(tv)                 -- the TV only ever shows finished copies
end

The highlighted cost line is the polygon budget. angle moves every frame, but tv changes only when a copy finishes: the stepped motion in the demo.

Pitfalls

  • Forgetting the transfer. A faster chip does nothing for the copy: at 21.48 MHz the demo still cannot beat 20 pictures per second.
  • Counting only triangles. Fill cost grows with screen area; a few huge close triangles can cost more than many small ones.
  • Showing a half-drawn picture. Copy only finished pictures, or keep two buffers and swap them, or players see the pod being built.
  • Tying game logic to the picture rate. angle moves with real time, so the pod turns at the same speed at 5 or 20 pictures per second. Advance it once per picture and the whole game slows down.

In real games

Star Fox was the first Super FX game. Others using the chip include Stunt Race FX and Vortex. A later version, the Super FX 2, ran at about 21.4 MHz and powered the Super Nintendo port of Doom and parts of Super Mario World 2: Yoshi's Island, where it stretches and rotates sprites rather than drawing polygons.

Takeaways

  • Star Fox's cartridge carried the Super FX, a processor that drew 3D pictures into its own RAM.
  • It wrote pixels in the console's tile format, so a finished picture could be shown as an ordinary background layer.
  • Picture rate is limited by drawing cost and by the copy into video memory during blanking.
  • Fewer, larger flat faces and a smaller 3D window were how games stayed inside both limits.
  • Modern GPUs, resolution scaling and triangle budgets solve the same problem.

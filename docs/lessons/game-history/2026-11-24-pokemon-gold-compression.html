Pokemon Gold and Silver: compression, and the story of the second region

How an LZ-style command stream of fills, zero runs and copies shrinks game data, and what is fact and what is legend about Iwata's compression in Pokemon Gold.

Beat the Elite Four in Pokemon Gold or Silver and the game is not over: a whole second region, Kanto from the first games, opens up. Fans often say this was only possible because Satoru Iwata, then at HAL Laboratory, wrote compression that squeezed the game small enough. The real story is less tidy. This page rebuilds the kind of compression the game uses and separates the record from the retelling.

The constraint: everything in 2 megabytes

Pokemon Gold and Silver came out in Japan in 1999 for the Game Boy Color. Its ROM, the read-only game data on the cartridge, is 2 megabytes, seen by the console through 16 KB windows called banks (see the bank switching lesson).

Those 128 banks hold the program, maps, music, text and pictures of 251 Pokemon, front and back. Game Boy graphics are built from 8 by 8 pixel tiles with 2 bits per pixel, so every tile costs 16 bytes. A picture 7 tiles square is 49 tiles, or 784 bytes, before any compression.

The trick: describe the data instead of storing it

Compression means storing a shorter description that a program, the decompressor, can turn back into the exact original bytes. Game data is full of patterns that allow this.

Run-length encoding replaces a run such as "seven grass tiles" with a count and a value. Back-references, the idea behind Abraham Lempel and Jacob Ziv's LZ77 method of 1977, replace a repeated stretch with "copy n bytes from d bytes back". Formats that mix the two are called LZ-style.

Gold and Silver store much of their graphics this way. The fan-made disassembly, which turns the ROM back into readable source code, documents the format as a stream of commands. Each command starts with a header byte: the top 3 bits pick the command and the low 5 bits give a count, so one command covers 1 to 32 bytes (a long form allows longer runs). The commands are:

  • Literal: the next n bytes are copied as they are.
  • Iterate: repeat one byte n times.
  • Alternate: repeat a pair of bytes, a b a b, for n bytes.
  • Zero fill: write n zero bytes, with nothing else stored.
  • Repeat, flip and reverse: copy n bytes from earlier output, either as they were, with the bits of each byte reversed, or in backwards order.

A byte of FF ends the stream. Flip suits graphics: in a Game Boy tile each bit is one pixel, so reversing a byte's bits mirrors that row of pixels.

The demo and code use this simplified version on a tile map, a grid of tile numbers, because its patterns are easy to see. The game mainly compresses tile graphics, but the commands work on any bytes.

Fact and legend

Here is what can be pinned down. In Nintendo's Iwata Asks interview about the remakes HeartGold and SoulSilver, Game Freak's Shigeki Morimoto thanks Iwata for creating the tools for compressing the Pokemon graphics, and Iwata agrees that he did. The same conversation recalls him porting the battle program to Pokemon Stadium on the Nintendo 64 in about a week.

Often repeated, not confirmed

That this compression freed the room for Kanto is the popular version, but no primary source I know of says so. Fan researchers, and a widely reported 2023 video by Did You Know Gaming?, argue the main gain was speed: graphics unpacked faster, so battles appeared sooner. Treat "saved Kanto" as legend, and the speed account as better supported but still second-hand.

The code

The demo's format and encoder in plain Lua for LÖVE. Data is a table of byte values, indexed from 1. With every command allowed, the demo's Town map compresses from 240 bytes to 44; with only literals it grows to 249.

-- header byte = command * 32 + (count - 1), count is 1..32
local LIT, FILL, ALT, ZERO, COPY, MAXN, STOP = 0, 1, 2, 3, 4, 32, 255

function decompress(src)
  local out, p = {}, 1
  while src[p] ~= STOP do
    local cmd, n = math.floor(src[p] / 32), src[p] % 32 + 1
    p = p + 1
    for k = 0, n - 1 do
      if cmd == LIT then out[#out + 1] = src[p + k]
      elseif cmd == FILL then out[#out + 1] = src[p]
      elseif cmd == ALT then out[#out + 1] = src[p + k % 2]
      elseif cmd == ZERO then out[#out + 1] = 0
      else out[#out + 1] = out[#out + 1 - (src[p] + 1)] end  -- COPY
    end
    if cmd == LIT then p = p + n
    elseif cmd == FILL or cmd == COPY then p = p + 1
    elseif cmd == ALT then p = p + 2 end
  end
  return out
end

local function runLength(i, max, test)  -- bytes from i that pass test(j)
  local len = 0
  while len < max and test(i + len) do len = len + 1 end
  return len
end

-- on = { [FILL] = true, [ALT] = true, [ZERO] = true, [COPY] = true }
function compress(d, on)
  local out, lit, i = {}, {}, 1
  local function emit(...)                -- trailing nils are dropped
    for _, b in ipairs({ ... }) do out[#out + 1] = b end
  end
  local function flush()
    if #lit > 0 then emit(LIT * 32 + #lit - 1, unpack(lit)); lit = {} end
  end
  while i <= #d do
    local max, best, pick = math.min(MAXN, #d - i + 1), 0, nil
    local function try(cmd, len, cost, a, b)  -- keep the biggest saving
      if on[cmd] and len - cost > best then best, pick = len - cost, { cmd, len, a, b } end
    end
    try(ZERO, runLength(i, max, function (j) return d[j] == 0 end), 1)
    try(FILL, runLength(i, max, function (j) return d[j] == d[i] end), 2, d[i])
    try(ALT, runLength(i, max, function (j) return d[j] == d[i + (j - i) % 2] end), 3, d[i], d[i + 1])
    for dist = 1, math.min(256, i - 1) do
      try(COPY, runLength(i, max, function (j) return d[j] == d[j - dist] end), 2, dist - 1)
    end
    if pick then
      flush()
      emit(pick[1] * 32 + pick[2] - 1, pick[3], pick[4])
      i = i + pick[2]
    else
      lit[#lit + 1] = d[i]; i = i + 1
      if #lit == MAXN then flush() end
    end
  end
  flush(); emit(STOP)
  return out
end

A copy may overlap what it writes: with distance 2 and count 20 it keeps re-copying the pair it just wrote, because the decoder works one byte at a time.

Pitfalls

  • Compression can make data bigger. With only literals the 240-byte map becomes 249 bytes, and Noise barely shrinks. Store data raw when compressing does not help.
  • Decompression costs time. On a Game Boy, unpacking a picture before a battle is a visible pause. Measure decode time, not only size.
  • Greedy is not optimal. The best command now can block a better one two bytes later. Offline tools can search harder.
  • Trust no input. A copy distance pointing before the start of the output reads garbage, and one bad header shifts every command after it. Test that every packed asset unpacks to the exact original in your build.

In real games

The fan disassemblies of Pokemon Gold, Silver and Crystal document the command format described above for the games' compressed graphics. Fans have noted that it closely resembles the format in other HAL Laboratory games such as EarthBound; I could not confirm that from a primary source.

LZ-style compression never left. The Deflate method inside zip files and PNG images combines LZ77 back-references with Huffman coding, and the PlayStation 5 has a hardware decoder for Kraken, from RAD Game Tools' Oodle library, so streaming compressed data costs no processor time.

The lesson for today: the Gold and Silver debate, size or speed, is a choice engines still make. A web game wants a small download, so it picks a high ratio. An open world streaming data mid-play wants fast decoding, so it picks something like LZ4, which compresses less but unpacks very quickly. Pick the format for the bottleneck you actually have.

Takeaways

  • Gold and Silver fit 251 Pokemon into a 2 MB cartridge, with much of the graphics compressed.
  • Their format is a stream of commands: literal bytes, runs of one byte, alternating pairs, zero runs, and copies of earlier output.
  • Iwata did write compression tools for the games' graphics; that they freed the room for Kanto is legend, and the best-supported account says the gain was speed.
  • Compression only wins on data with patterns, and is paid for in decoding time.

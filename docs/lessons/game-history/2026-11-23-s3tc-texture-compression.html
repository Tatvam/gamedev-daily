S3 Texture Compression: sixteen pixels in eight bytes

How S3TC (DXT1, now BC1) stores each 4 by 4 block of a texture as two colours and sixteen 2-bit choices, and why graphics hardware can read it directly.

Zoom in close on a texture in almost any 3D game of the last twenty-five years and you may spot faint square smudges, four pixels wide, where a smooth gradient meets a sharp edge. Those squares are the fingerprints of a compression scheme designed in 1998 that is still inside every desktop graphics card today.

The constraint: textures fill the card

A texture is an image the graphics card wraps over a 3D surface. In the late 1990s consumer 3D cards commonly had somewhere between 4 and 16 megabytes of memory, and that memory also had to hold the screen images being drawn. One 256 by 256 texture at 24 bits per pixel is 192 KB. Add the smaller copies used at a distance, called mipmaps, and it grows by about a third. A few dozen of those and the card is full.

Memory size was only half the problem. Every textured pixel on screen reads texture data, often several texels at a time, so smaller textures also mean less traffic between the chip and its memory.

Ordinary image compression such as JPEG does not help here. A JPEG has to be decoded from the start, and each part of the file is a different length. The graphics chip needs the opposite: to jump straight to any texel, in any order, millions of times a second, and decode it in a few cheap steps.

The trick: two colours and a line between them

S3 Graphics introduced S3 Texture Compression, S3TC, with its Savage3D chip in 1998. Microsoft licensed it for DirectX 6.0, where the formats were named DXT1 to DXT5. Direct3D 10 later renamed them BC1 to BC3, for block compression. This page rebuilds DXT1, the basic colour format.

The texture is cut into blocks of 4 by 4 pixels. Each block is stored in exactly 8 bytes:

  1. Two colours, c0 and c1, each squeezed into 16 bits in a layout called RGB565: 5 bits of red, 6 of green and 5 of blue. Green gets the extra bit because eyes are most sensitive to it.
  2. Sixteen 2-bit indices, one per pixel. Each index picks one of four colours.

Only two of those four colours are stored. The other two are calculated by the decoder: one is two thirds of the way from c0 towards c1, the other is one third of the way. So every block has a tiny palette of four colours that all sit on one straight line through colour space, and each pixel snaps to the nearest of them.

Sixteen pixels at 24 bits are 48 bytes. Eight bytes is a ratio of 6 to 1, or 8 to 1 against 32-bit pixels. That is 4 bits per pixel, the same as a 16-colour image, but each block has its own four colours.

Why fixed-size blocks matter

Every block is exactly 8 bytes, so the chip can find the block holding any texel with one multiply and one add. Decoding is equally small: read two 16-bit colours, blend them, pick one with two bits. That is cheap enough to build into the texture unit itself, so the texture stays compressed in video memory and is only expanded at the moment a texel is sampled. Memory and bandwidth both shrink by the same ratio.

A free mode bit

DXT1 hides one more switch in the order of the two colours. Read c0 and c1 as 16-bit numbers. If c0 is greater, the block uses the four-colour palette above. If c0 is not greater, the block uses three colours (c0, c1 and their halfway point) and index 3 means black or fully transparent. The format gets one-bit transparency, used for leaves and fences, without spending a single extra bit. An encoder that wants four colours simply swaps the pair so the larger one comes first.

Rule of thumb

DXT1 is excellent when each 4 by 4 block holds shades along one colour direction, such as a gradient or a single edge between two colours. It struggles when one block contains three unrelated colours, because no single line passes near all of them.

The code

A complete DXT1 encoder and decoder for one block, in plain Lua that runs inside LÖVE. A block is a table of 16 pixels, row by row, each { r, g, b } from 0 to 255. Bit operations are written as arithmetic so the code needs no library.

local floor = math.floor

local function to565(c)          -- 24-bit colour to a 16-bit number
  local r5 = floor(c[1] * 31 / 255 + 0.5)
  local g6 = floor(c[2] * 63 / 255 + 0.5)
  local b5 = floor(c[3] * 31 / 255 + 0.5)
  return r5 * 2048 + g6 * 32 + b5
end

local function from565(v)        -- and back, repeating the top bits
  local r5, g6, b5 = floor(v / 2048), floor(v / 32) % 64, v % 32
  return { r5 * 8 + floor(r5 / 4), g6 * 4 + floor(g6 / 16), b5 * 8 + floor(b5 / 4) }
end

local function dist2(a, b)
  local dr, dg, db = a[1] - b[1], a[2] - b[2], a[3] - b[3]
  return dr * dr + dg * dg + db * db
end

local function mix(a, b, wa, wb)
  local out = {}
  for k = 1, 3 do out[k] = floor((wa * a[k] + wb * b[k]) / (wa + wb)) end
  return out
end

function palette(c0, c1)         -- palette[index + 1]
  local a, b = from565(c0), from565(c1)
  if c0 > c1 then return { a, b, mix(a, b, 2, 1), mix(a, b, 1, 2) } end
  return { a, b, mix(a, b, 1, 1), { 0, 0, 0 } }  -- 3 colours + transparent
end

function encodeBlock(px)
  local best, ia, ib = -1, 1, 1  -- endpoints: the two most different pixels
  for i = 1, 16 do
    for j = i + 1, 16 do
      local d = dist2(px[i], px[j])
      if d > best then best, ia, ib = d, i, j end
    end
  end
  local c0, c1 = to565(px[ia]), to565(px[ib])
  if c0 < c1 then c0, c1 = c1, c0 end   -- c0 > c1 selects four colours
  local pal, idx = palette(c0, c1), {}
  for i = 1, 16 do                -- each pixel keeps its nearest index
    local bestD = math.huge
    for k = 1, 4 do
      local d = dist2(px[i], pal[k])
      if d < bestD then bestD, idx[i] = d, k - 1 end
    end
  end
  return c0, c1, idx              -- 16 + 16 + 16 * 2 bits = 8 bytes
end

function decodePixel(c0, c1, idx, i)
  return palette(c0, c1)[idx[i] + 1]
end

function blockOffset(x, y, width) -- byte offset of the block holding texel x, y
  return (floor(y / 4) * (width / 4) + floor(x / 4)) * 8
end

In a real decoder the indices are packed into one 32-bit number: pixel i (counting from 0) uses bits 2i and 2i + 1, and the whole block is stored little-endian, low byte first. The demo shows those bytes for the selected block. LÖVE can load ready-made DXT1 files directly with love.image.newCompressedData, so in practice you compress with a tool and let the graphics card decode.

Pitfalls

  • Judging memory by file size. A 200 KB PNG is decompressed to full size in video memory. A DXT1 texture stays 4 bits per pixel on the card. Mobile games often run out of memory for exactly this reason.
  • Sizes that are not multiples of 4. The format works in whole blocks. Keep texture sizes divisible by 4 at every mipmap level you use, or the tools pad them for you.
  • Normal maps and smooth alpha. DXT1 bends normals and has only on-or-off transparency. Use DXT5 (BC3), which adds 8 bytes of alpha per block, or the two-channel BC5 for normal maps.
  • Weak encoders. Picking endpoints naively, as this demo does, leaves quality on the table. Good compressors fit a line through the block's colours and refine it. Compress offline with a good tool rather than at load time with a quick one.
  • Small text and pixel art. Hard multi-colour detail inside a block, like the stripes in the demo, is the worst case. Leave such textures uncompressed.

In real games

Once DXT was part of DirectX 6.0 and available in OpenGL through the EXT_texture_compression_s3tc extension, PC games adopted it widely. Unreal Tournament (1999) is often cited as an early showcase: its second CD is widely reported to have carried high-resolution S3TC textures for cards that supported the format. I could not check that claim against a primary source in this session.

S3's patent on the method kept it out of open-source graphics drivers for years; that patent has since expired. The formats themselves never left. Every PC graphics card still decodes BC1 to BC3 in hardware, and Direct3D 11 added BC6H for high dynamic range images and BC7 for higher-quality colour with alpha.

The lesson for today: the same constraint is back on phones and the web, where memory and bandwidth are tight and many formats exist. Mobile chips use ETC2 or ASTC rather than BC, which is why engines compress textures per platform at build time. ASTC keeps the fixed-size block idea but lets the block size vary, trading quality for bits. Whatever the format, the rule from 1998 holds: blocks of fixed size, decoded in the texture unit, so the data stays small all the way to the pixel.

Takeaways

  • DXT1 (BC1) stores every 4 by 4 block in 8 bytes: two RGB565 colours and sixteen 2-bit indices.
  • The decoder derives two more colours between the stored pair, so each block has four colours on one line.
  • Fixed-size blocks let the graphics chip find and decode any texel directly, so textures stay compressed in video memory.
  • The order of the two colours selects four-colour or three-colour-plus-transparent mode, at no cost in bits.
  • Blocks with three unrelated colours compress badly; modern formats such as BC7 and ASTC exist to soften that.

Space Invaders: the march that speeds up as you shoot

Space Invaders moves one invader per screen refresh, so the fewer are left, the faster the whole rack marches. Rebuild the schedule and see why.

In Taito's Space Invaders (1978) the rack of 55 invaders starts as a slow, heavy shuffle. Shoot them down and the survivors march faster and faster, until the last one races across the screen and is hard to hit.

Nobody wrote a line that says "speed up when there are fewer enemies". The speed-up comes from how the game schedules its drawing, and designer Tomohiro Nishikado kept it.

The constraint: one slow processor, one bitmap screen

The cabinet runs on an Intel 8080 processor at about 2 MHz. The picture is a bitmap: one bit per pixel, 256 by 224 pixels, about 7 KB of memory that the video hardware reads out to the monitor. To move an invader, the processor must copy its shape into that memory byte by byte.

The hardware sends two interrupts per screen refresh, signals that make the processor drop what it is doing and run a fixed routine: one near the middle of the screen, one at the bottom. At 60 refreshes per second, they are the game's heartbeat.

The trick: one invader per refresh

The game does not move the rack as a whole. It keeps a single reference invader, the bottom-left position of the rack, and works out every other invader from it: 16 pixels right per column, 16 pixels up per row. The disassembled program then works like this:

  1. At the end of each refresh, it draws one invader at its place relative to the reference.
  2. At the middle of the next refresh, a cursor steps to the next invader that is still alive, left to right along a row, then up to the next row. Dead invaders are skipped in the same pass, so they cost no refreshes.
  3. When the cursor runs off the end of the rack, the reference invader moves 2 pixels sideways (or drops 8 pixels and turns round at an edge) and the cursor starts again at the bottom.

Now count. With all 55 alive, one full pass takes 55 refreshes, so the rack takes one 2-pixel step a little less than once per second. With 10 alive, a pass takes 10 refreshes: six steps a second. With one alive, the pass is a single refresh and the invader steps 60 times a second. Same code, same frame rate, 55 times the speed.

Fact and legend

The story is often retold as "the processor ran faster when it had less to draw", as if the frame rate climbed. The commented disassembly is more precise: the game is locked to the 60 Hz interrupts, and the pace comes from the one-invader-per-refresh schedule. The code does not say why it was written this way. A likely reason is that redrawing all 55 in one refresh, plus the player, shots and shields, was too much for the processor, but that is an inference, not a documented fact.

That Nishikado noticed the speed-up during development and kept it as the difficulty curve is widely reported from his interviews.

The idea in one line

Give the work a fixed budget per frame instead of a fixed amount per frame, and anything that shrinks the work speeds up the result.

The code

The same schedule in LÖVE, with the demo's numbers: an 11 by 5 rack spaced 16 pixels apart, steps of 2, drops of 8, a 224-pixel field. tick runs once per 1/60 of a second, however fast your machine draws.

local COLS, ROWS, SPACING = 11, 5, 16
local COUNT = COLS * ROWS              -- 55 invaders
local STEP, DROP, FIELD_W = 2, 8, 224
local SCALE, TICK = 3, 1 / 60          -- one tick = one screen refresh
local FIXED = false                    -- true: dead slots still cost a tick

local alive, drawnX, drawnY = {}, {}, {}
local refX, refY, dir = 24, 96, 1      -- reference invader: bottom left
local cursor, living, acc = 0, COUNT, 0

local function place(i)                -- move ONE invader to its rack position
  drawnX[i] = refX + ((i - 1) % COLS) * SPACING
  drawnY[i] = refY - math.floor((i - 1) / COLS) * SPACING
end

local function hitsEdge()
  for i = 1, COUNT do
    if alive[i] and ((dir == 1 and drawnX[i] + SPACING > FIELD_W - 4)
                  or (dir == -1 and drawnX[i] < 4)) then return true end
  end
  return false
end

local function moveReference()
  if hitsEdge() then
    dir = -dir
    refY = refY + DROP
  else
    local step = STEP
    if living == 1 and dir == 1 then step = 3 end  -- the original's last-invader quirk
    refX = refX + dir * step
  end
end

local function nextSlot()
  cursor = cursor + 1
  if cursor > COUNT then cursor = 1; moveReference() end
end

local function tick()
  if living == 0 then return end
  nextSlot()
  if not FIXED then
    while not alive[cursor] do nextSlot() end      -- dead invaders cost nothing
  end
  if alive[cursor] then place(cursor) end
end

for i = 1, COUNT do alive[i] = true; place(i) end

function love.update(dt)
  acc = acc + dt
  while acc >= TICK do acc = acc - TICK; tick() end
end

function love.mousepressed(x, y)
  for i = 1, COUNT do
    local ix, iy = drawnX[i] * SCALE, drawnY[i] * SCALE
    if alive[i] and x >= ix and x < ix + SPACING * SCALE and y >= iy and y < iy + SPACING * SCALE then
      alive[i] = false
      living = living - 1
      break
    end
  end
end

function love.draw()
  for i = 1, COUNT do
    if alive[i] then
      love.graphics.rectangle("fill", (drawnX[i] + 2) * SCALE, (drawnY[i] + 4) * SCALE, 12 * SCALE, 8 * SCALE)
    end
  end
end

The highlighted lines are the whole trick. Set FIXED = true and the rack keeps one pace to the end.

Pitfalls

  • Hidden coupling. Any schedule that does a fixed number of things per frame ties the rate of each thing to how many there are. Space Invaders turned that into a feature. In your game it may be a bug: enemies that react faster when their friends die, by accident.
  • The ripple is real. Invaders move one at a time, so the rack briefly sits half in its old place and half in its new one. Collision code must use where an invader is drawn, not where the rack says it should be.
  • A curve you did not design. Steps per second are 60 divided by the invaders left: almost flat for most of the wave, then a sudden climb. For a gentler ramp, drive speed from the count on purpose.
  • This is a rebuild, not an emulator. The real game also pauses the march while an invader explodes, and its edge test reads screen memory directly.

In real games

In the original game, according to the commented disassembly:

  • The rack draws one invader per refresh, from the bottom-left reference, row by row upwards.
  • A lone last invader steps 3 pixels moving right but 2 moving left, which makes its timing harder to read.
  • The rack turns round when anything appears in a line of screen memory at the edge of the playfield.

The lesson for today

Games with hundreds of agents often update only some of them each frame, taking turns, so expensive work such as path searches never blows the frame budget. This time slicing is the Space Invaders schedule, with the same side effect: with fewer agents, each is updated more often.

If you do not want that side effect, give each agent the real time since its own last update, so its speed does not depend on how often its turn comes:

local BUDGET, turn = 4, 0   -- agents updated per frame

local function updateSome(agents, now)
  for n = 1, math.min(BUDGET, #agents) do
    turn = turn % #agents + 1
    local a = agents[turn]
    a:update(now - a.lastTime)   -- elapsed time, not "one step"
    a.lastTime = now
  end
end

Phones that throttle when hot and servers with many players make the old question matter again: is your game's speed set by the clock, or by how much work there is?

Takeaways

  • Space Invaders runs on an Intel 8080 with a one-bit bitmap screen, and redraws just one invader per screen refresh.
  • Every invader is placed relative to one reference position, which only moves after each living invader has been redrawn once.
  • Fewer invaders means shorter passes, so the rack speeds up from about 1 step per second to 60, with no change in frame rate.
  • Fixed work budgets per frame (time slicing) still couple speed to count today. Use elapsed time when you do not want that.

Palette cycling: a waterfall that moves while its pixels stay still

How 256-colour artists animated water, fire and light by rotating a few palette entries, so the picture moved while no pixel in it changed.

In many PC and Amiga games of the late 1980s and early 1990s, waterfalls pour and lamps glow inside a single painted background, on machines that could barely afford to redraw the screen. The shapes of the water never change; only the colours travel through them.

The constraint: a screen of colour numbers

The common 256-colour mode on VGA PCs, often called mode 13h, is 320 by 200 pixels with one byte per pixel: 64,000 bytes for one screen. That byte is not a colour. It is a colour number, an index into a palette: a table of 256 entries, each holding a real colour as red, green and blue values of 6 bits each. The display hardware looks up every pixel's entry as it draws the picture.

Animate a waterfall with frames and ten full-screen frames are 640,000 bytes, nearly all of the 640 KB of conventional memory a DOS program could normally use. Even a small animated patch must be copied into screen memory every time it changes, by a processor that also runs the game.

The palette is tiny: 256 entries of 3 bytes is 768 bytes. Changing an entry recolours every pixel that uses it, at once, with no pixel copied.

The trick: paint with numbers in order, then rotate the colours

Palette cycling (also called colour cycling) sets aside a run of palette entries, called a range, for one moving thing. Say entries 16 to 23 belong to the waterfall.

  1. The artist paints the waterfall with those numbers in order along the direction of flow: a row of 16, then 17, and so on to 23, then 16 again.
  2. The range is filled with a little ramp of colours: one bright foam colour, a few that fade, and some plain water blue.
  3. Several times a second the program rotates the range: every colour moves up one entry and the last one wraps round to the first.

The bright colour that sat in entry 16 now sits in 17. Every pixel numbered 17 lights up and every 16 goes dark, so the bright band appears to move one row down. Repeat, and the water flows forever. A step costs 8 entries times 3 bytes: 24 bytes written, against thousands for redrawing the waterfall.

The layout of numbers is where the artistry lives. Stripes give flowing water, rings around a lamp give pulsing light, scattered dots give sparkle or rain. A scene can have several ranges, each with its own speed, while the rest of the palette stays still. The related palette shifting fades colours gradually instead, for example from day to dusk.

Fact and legend

Mark Ferrari, an artist whose credits include Lucasfilm Games' Loom and The Secret of Monkey Island and, much later, Thimbleweed Park, is the name most tied to this technique. His colour-cycled landscapes reached a new audience in 2010, when programmer Joseph Huckaby rebuilt them in a web page called Canvas Cycle. Ferrari taught his methods at GDC 2016 in a talk titled 8 Bit & '8 Bitish' Graphics: Outside the Box.

He did not invent colour cycling. Paint programs of the 1980s, Electronic Arts' Deluxe Paint among them, already let artists mark ranges to cycle. Ferrari is known for pushing it far beyond simple stripes. This page could not check which shipped games used his cycling art, so it names none.

The idea in one line

If an image stores numbers and a table turns them into colours, animating the small table can animate the large image.

The lesson for today

Modern hardware has no palette, but a shader rebuilds one in two lines: store colour numbers in a texture and look each up in a second texture one pixel tall, a palette lookup. Animating water then means rewriting a 1 KB strip, not uploading a full-size image every frame. The same lookup gives team colours and colour-blind friendly palettes from one set of art, and keeps downloads small on the web and phones.

Try it

The scene is stored as 160 by 100 colour numbers that never change; each frame they are only looked up again in the current palette, as VGA hardware did. The strip under the scene is the palette. Turn the three ranges on one by one, then switch on Show colour numbers to see what is really stored. Point at or touch the scene to read a number.

The code

LÖVE draws in full colour, so the Lua keeps its own colour numbers and does the lookup that VGA did in hardware. The rotation is the whole trick. buildScene is your own function that fills pixels and palette; colour numbers start at 0, as on VGA, which is fine for table keys.

local W, H = 160, 100
local pixels = {}    -- pixels[y][x] = colour number. Never changes.
local palette = {}   -- palette[n] = {r, g, b} from 0 to 1. This is what moves.
local ranges = {
  { low = 16, high = 23, rate = 12, timer = 0 },   -- waterfall
  { low = 24, high = 29, rate = 6,  timer = 0 },   -- river
  { low = 32, high = 37, rate = 4,  timer = 0 },   -- lantern
}
local imageData, image

local function rotate(low, high)    -- every colour moves up one entry
  local last = palette[high]
  for n = high, low + 1, -1 do
    palette[n] = palette[n - 1]
  end
  palette[low] = last                 -- the top colour wraps round
end

function love.load()
  love.graphics.setDefaultFilter("nearest", "nearest")
  buildScene(pixels, palette, W, H)
  imageData = love.image.newImageData(W, H)
  image = love.graphics.newImage(imageData)
end

function love.update(dt)
  for _, r in ipairs(ranges) do
    r.timer = r.timer + dt
    while r.timer >= 1 / r.rate do
      r.timer = r.timer - 1 / r.rate
      rotate(r.low, r.high)
    end
  end
end

function love.draw()
  for y = 1, H do                     -- the lookup VGA did in hardware
    for x = 1, W do
      local c = palette[pixels[y][x]]
      imageData:setPixel(x - 1, y - 1, c[1], c[2], c[3], 1)
    end
  end
  image:replacePixels(imageData)
  love.graphics.draw(image, 0, 0, 0, 4, 4)
end
// LÖVE pixel shader. The image stores colour numbers in its red channel,
// and palette is a 256 by 1 image you rotate on the CPU each step.
uniform Image palette;

vec4 effect(vec4 color, Image tex, vec2 uv, vec2 screen)
{
    float n = floor(Texel(tex, uv).r * 255.0 + 0.5);    // colour number
    return Texel(palette, vec2((n + 0.5) / 256.0, 0.5)) * color;
}

With the shader, the loop in love.draw disappears: after each rotate, write the palette into a 256 by 1 image and send it with shader:send("palette", paletteImage). Use nearest filtering on both images. The big image is uploaded once.

Pitfalls

  • Static art that borrows a cycling entry. A rock pixel using entry 19 flickers with the waterfall. Keep each range for its moving thing only.
  • Numbers out of order. Motion appears only when neighbouring pixels hold neighbouring numbers along the direction of travel. A jumble gives noise, not flow.
  • Ranges eat the palette. Every entry spent on cycling is one fewer shade for the rest of the scene.
  • Steppy motion. A short range moves in visible jumps. Longer ranges, slower rates or blending towards the next colour (try the toggle) smooth it.
  • CPU lookup at modern sizes. The Lua loop is fine for 16,000 pixels. For full HD, use the shader.
  • Flashing. Fast cycles of strongly contrasting colours can flash, which can harm players with photosensitive epilepsy. Keep bright, high-contrast cycles slow.

In real games

Colour cycling was common wherever the display used a palette, on PCs, the Amiga and consoles: shimmering water and lava, blinking lights, glowing logos. Deluxe Paint had cycling built in so artists could preview it while painting. Mark Ferrari's scenes are the best known showcase, now seen mostly through Joseph Huckaby's 2010 browser rebuild, and the idea lives on in palette-swap and gradient-map shaders.

Your turn (15 minutes)

Add a fourth range that runs backwards. Write rotateDown(low, high), which moves every colour down one entry and wraps the first round to the last, and give each range a reverse flag that picks which function love.update calls. Set it on the river. You are done when the ripples drift the other way, the waterfall still falls, and pixels is never written after buildScene.

Takeaways

  • In 256-colour modes each pixel stores a colour number, and a 768-byte palette turns numbers into colours as the screen is drawn.
  • Palette cycling rotates a small range of entries, so pixels painted with those numbers in order appear to move.
  • One step writes a few dozen bytes; redrawing would copy thousands.
  • The art is the layout of numbers: stripes flow, rings pulse, dots sparkle.
  • Today a shader palette lookup does the same job: animate a tiny strip, not the big image.

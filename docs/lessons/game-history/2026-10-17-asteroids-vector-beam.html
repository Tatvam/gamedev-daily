Asteroids: drawing with a vector beam

Asteroids has no pixels to fill: the screen is a list of beam moves that a small chip traces about 60 times a second. Rebuild the beam and see why.

In Atari's Asteroids (1979) the ship and the rocks are thin, bright lines on black, with no staircase steps on the diagonals. That is because the game does not draw into pixels at all: its monitor steers the electron beam along each line of each shape, and the game's job is to hand it a list of where to go.

The constraint: memory for a picture

A normal television picture is a raster: the beam sweeps every row of the screen, and memory called a frame buffer must say what each dot looks like, lit or not.

According to the MAME emulator's description of the hardware, the Asteroids board has a 6502 processor at about 1.5 MHz (a 12.096 MHz crystal divided by 8), 1 KB of working memory, 2 KB of vector RAM, 2 KB of vector ROM and 6 KB of program ROM. Its drawing space is 1024 by 1024 units, of which the game uses a 1024 by 768 area.

A frame buffer for 1024 by 768 dots at 1 bit per dot is 98,304 bytes, 48 times the vector RAM. That comparison is mine, not a documented reason for the design, but it shows why storing lines instead of dots pays.

The trick: the picture is a program

An X-Y monitor (or vector monitor) has no fixed scan pattern. Two inputs set where the beam points, a third sets its brightness. Between it and the processor sits Atari's Digital Vector Generator (DVG), a circuit that executes a display list: a short program of drawing commands in vector RAM and ROM. The community disassembly names them:

  • CUR puts the beam at a position and sets a scale.
  • VEC and the shorter SVEC move the beam by a relative amount at a brightness from 0 to 15. Brightness 0 moves it switched off.
  • JSR and RTS call a stored shape and return, up to four deep. JMP jumps. HALT ends the list.

How the beam draws a straight line

The DVG keeps the beam's position in an X counter and a Y counter, and steps both using chips called rate multipliers that spread the steps evenly, so both counters arrive together: a straight line at any angle. Lines running off the edge are cut off by the hardware.

One rock, three sizes

Shapes live in vector ROM as subroutines. The disassembly shows four rock outlines of about a dozen short vectors each, and the game draws all three rock sizes from them by changing only the scale before the call. A broken rock costs no new artwork, only a smaller number.

Two lists: one being drawn, one being written

The glow fades unless the beam keeps redrawing, so the list runs every frame. The processor builds the next list in one half of vector RAM while the DVG traces the other. A jump command at the start of RAM points at the half to draw; once the DVG reports it reached HALT, the game flips that jump. This is double buffering, applied to commands instead of an image. The disassembly's comments put the rate at 62.5 frames per second.

Fact and legend

The hardware facts above come from MAME's source and the commented disassembly. MAME runs Lunar Lander (1979) on the same driver and DVG, and the generator is usually said to have come to Asteroids from that game. The game is usually credited to Lyle Rains and Ed Logg; I could not check a primary source for that while writing.

The idea in one line

Store what to draw, not what the screen looks like, and the cost follows the number of lines instead of the number of dots.

The code

The demo's shapes and numbers in LÖVE; BEAM_SPEED is step 7 on the slider. buildList writes this frame's commands and love.draw walks them like the beam, timing each move. CUR jumps are instant, as in the DVG. The real DVG gives each line a time set by its scale rather than its length, so treat the milliseconds as illustrative.

-- Shapes as relative beam moves {dx, dy, brightness}. Brightness 0 = beam off.
local ROCK = { {0, 40, 0}, {25, -10, 7}, {15, -20, 7}, {-10, -25, 7}, {5, -15, 7}, {-25, -10, 7},
               {-25, 10, 7}, {-20, -5, 7}, {-5, 30, 7}, {15, 20, 7}, {-5, 15, 7}, {30, 10, 7} }
local SHIP = { {0, 24, 0}, {-14, -40, 12}, {14, 8, 12}, {14, -8, 12}, {-14, 40, 12} }
local SCALES = { 2, 1, 0.5 }            -- big, medium, small: one outline
local W, H, BEAM_SPEED = 1024, 768, 16000  -- units; units per second
local rocks = { { x = 200, y = 560, vx = 40, vy = -25, size = 1 },
                { x = 760, y = 200, vx = -30, vy = 35, size = 2 },
                { x = 600, y = 640, vx = 55, vy = 20, size = 3 } }

local function addShape(list, x, y, shape, scale)
  list[#list + 1] = { op = "cur", x = x, y = y }   -- jump with the beam off
  for _, v in ipairs(shape) do
    list[#list + 1] = { op = "vec", dx = v[1] * scale, dy = v[2] * scale, b = v[3] }
  end
end

local function buildList()               -- the end of the table plays the part of HALT
  local list = {}
  addShape(list, W / 2, H / 2, SHIP, 1)
  for _, r in ipairs(rocks) do addShape(list, r.x, r.y, ROCK, SCALES[r.size]) end
  return list
end

function love.update(dt)
  for _, r in ipairs(rocks) do r.x, r.y = (r.x + r.vx * dt) % W, (r.y + r.vy * dt) % H end
end

function love.draw()                      -- walk the list like the beam, timing every move
  local x, y, time = 0, 0, 0
  for _, c in ipairs(buildList()) do
    if c.op == "cur" then x, y = c.x, c.y else
      if c.b > 0 then                     -- 0.75 fits 1024 x 768 in 800 x 600; y points up
        love.graphics.setColor(1, 1, 1, 0.35 + 0.65 * c.b / 15)
        love.graphics.line(x * 0.75, (H - y) * 0.75, (x + c.dx) * 0.75, (H - y - c.dy) * 0.75)
      end
      time = time + math.sqrt(c.dx * c.dx + c.dy * c.dy) / BEAM_SPEED
      x, y = x + c.dx, y + c.dy
    end
  end
  love.graphics.setColor(1, 1, 1, 1)
  love.graphics.print(string.format("one pass: %.1f ms", time * 1000), 10, 10)
end

The highlighted lines are the whole display: a line exists only while the beam moves along it. LÖVE draws to a raster window, so this shows the list's logic, not a real beam.

Pitfalls

  • Every line costs time, every frame. A raster frame takes the same time however busy the scene; a vector pass grows with the lines, so a full screen flickers more than an empty one.
  • Unlit moves are not free. Brightness-0 moves still travel, so order shapes to avoid zigzagging across the screen.
  • Outlines only. Filling a shape takes many lines, so vector games mostly stay with outlines and dots.
  • Emulation loses the glow. On a raster screen a vector game becomes thin pixel lines; the monitor's glow has to be faked with shaders.

In real games

From the MAME source and the Asteroids disassembly:

  • Asteroids keeps its four rock outlines, the ship, the saucer and the letters as stored shapes in 2 KB of vector ROM, and builds each frame's list in 2 KB of double-buffered vector RAM.
  • Battlezone, Tempest and Star Wars run on Atari's later Analog Vector Generator in MAME.

The lesson for today

A modern renderer works the same way at a larger scale. Each frame the game records a command buffer, a list of draw calls, which the graphics card executes while the game records the next. Drawing one stored mesh many times with different transforms, instancing, is the rock outline at three scales. Fonts and SVG icons store outlines, not dots, so they stay sharp and small. And on a phone or in a browser, a budget of draw commands often bites before the pixel count does.

Run the Lua above in LÖVE. Add bullets: each is a CUR to its position plus one very short VEC at brightness 15, so it shows as a bright dot. Takeaways

  • Asteroids steers the beam along each line, so it needs no frame buffer and has no jagged diagonals.
  • The picture is a display list of commands that the Digital Vector Generator traces about 60 times a second.
  • Shapes are stored once and reused at different scales, and the next list is built while the current one is drawn.
  • Vector cost grows with the number of lines, as draw-call budgets do today.

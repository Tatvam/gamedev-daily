Amiga copper gradients: a new colour on every line

How Amiga skies got dozens of shades from a tiny palette: a coprocessor rewrites one colour register as the screen is drawn, line by line.

Many Amiga games show a sky that fades smoothly from deep blue to a glowing horizon, above a scene with only a handful of colours. Count the shades and you get more than the screen mode is supposed to hold. A small helper chip is changing what one colour means while the picture is drawn.

The constraint: a picture made of colour numbers

The Amiga (1985) stores its screen as bitplanes: separate layers of one bit per pixel. Stack the bits for one pixel and you get a colour number. Two planes give numbers 0 to 3, five planes give 0 to 31. A low-resolution screen of 320 by 200 pixels costs 8,000 bytes per plane, and every extra plane also costs time on the memory bus that the processor and the other chips share.

The colour number picks one of 32 colour registers, COLOR00 to COLOR31. Each holds a 12-bit colour, 4 bits each of red, green and blue: any of 4,096 colours. But a 4-colour screen can only address 4 registers, so it shows 4 colours. (Special modes such as Hold-And-Modify show more, with their own restrictions.) Paying for a smooth sky with extra bitplanes would cost memory, bus time and colours the rest of the scene needs.

The copper: a chip that waits and writes

The Amiga's custom chips include a tiny coprocessor, the copper, that runs in step with the video beam drawing the picture line by line. Every frame it runs a short program, the copper list, from the top.

It knows only three instructions, each stored as two 16-bit words (4 bytes):

  • WAIT stops until the beam reaches a given line and position. While it waits it does not use the memory bus.
  • MOVE writes a value into one of the chips' hardware registers. The colour registers are among them.
  • SKIP jumps over the next instruction if the beam has passed a position. Gradients do not need it.

The list ends with a WAIT for a position the beam never reaches.

The trick: change the meaning of colour 0 as the beam goes down

Paint every sky pixel with colour number 0. Then write a copper list: wait for line 0, set COLOR00 to dark blue; wait for line 26, set it lighter; and so on. The video chip looks up each pixel's register at the moment the beam draws it, so each line of sky shows whatever COLOR00 holds then.

You can rewrite a register on every line: 200 changes cost 200 WAIT and MOVE pairs, 1,600 bytes, and no work from the main processor. Several registers can change per line, so ground and water can get gradients too.

Fact and legend

You will read that the copper let the Amiga "show more colours than it had". True for the whole screen, not for one line: each line still uses only the registers it can address. The copper changes them between lines (mid-line changes exist but are coarse), which is why copper effects are horizontal stripes. Also, real WAIT line numbers count from the top of the beam's path, above the visible picture; in the rebuild, line 0 is the first visible line.

The idea in one line

If colour is looked up when a pixel is drawn, change the lookup table while drawing, and one stored number can mean many colours.

The lesson for today

Modern graphics cards do not draw in beam order, but the idea survives as small data looked up at draw time. A sky needs no full-screen image: a texture one pixel wide and a few hundred tall, stretched across the screen, gives the same gradient for a tiny fraction of the memory and download, which still matters on phones and the web. A gradient ramp, a strip of colours a shader indexes by height, is a direct descendant of the copper list.

Try it

The scene is 320 by 200 pixels with four colour registers: sky, far hills, near hills and sun. Turn Copper on off and the sky is flat. Then turn on Show what the bitplanes store: the stored picture never changes.

The code

The demo's scene and default numbers, in LÖVE. buildCopperList makes one WAIT and MOVE pair per band, rounding colours to 4 bits per channel. render plays the beam: load the palette at the top, then on each line do any MOVE whose WAIT has been reached before drawing the line.

-- Copper-style sky: rewrite one colour register at chosen lines.
local W, H, SCALE = 320, 200, 3
local palette = {                          -- 4 registers, 0..15 per channel
  [0] = {6, 4, 7}, [1] = {6, 3, 6},        -- COLOR00 sky, COLOR01 far hills
  [2] = {2, 1, 3}, [3] = {15, 13, 6},      -- COLOR02 near hills, COLOR03 sun
}
local TOP, HORIZON = {1, 1, 5}, {15, 8, 3}
local BANDS, START, STOP = 16, 0, 130
local image

local function colourNumber(x, y)          -- what the bitplanes store
  if y >= 150 + 10 * math.sin(x * 0.05 + 1) then return 2 end
  if y >= 120 - 14 * math.sin(x * 0.03) then return 1 end
  if (x - 230) ^ 2 + (y - 95) ^ 2 <= 18 * 18 then return 3 end
  return 0
end

local function buildCopperList()
  local list = {}
  for i = 0, BANDS - 1 do
    local t = 0
    if BANDS > 1 then t = i / (BANDS - 1) end
    local c = {}
    for k = 1, 3 do c[k] = math.floor(TOP[k] + (HORIZON[k] - TOP[k]) * t + 0.5) end
    list[#list + 1] = { wait = START + math.floor(i * (STOP - START) / BANDS), reg = 0, value = c }
  end
  return list
end

local function render(list)
  local data, regs, seen, count, nextOp = love.image.newImageData(W, H), {}, {}, 0, 1
  for r = 0, 3 do regs[r] = palette[r] end                  -- top of frame
  for y = 0, H - 1 do
    while list[nextOp] and list[nextOp].wait <= y do         -- WAIT reached...
      regs[list[nextOp].reg] = list[nextOp].value            -- ...so MOVE
      nextOp = nextOp + 1
    end
    for x = 0, W - 1 do
      local c = regs[colourNumber(x, y)]
      local key = c[1] * 256 + c[2] * 16 + c[3]
      if not seen[key] then seen[key] = true; count = count + 1 end
      data:setPixel(x, y, c[1] / 15, c[2] / 15, c[3] / 15, 1)
    end
  end
  print(count .. " colours on screen from 4 registers")
  return love.graphics.newImage(data)
end

function love.load()
  love.graphics.setDefaultFilter("nearest", "nearest")
  love.window.setMode(W * SCALE, H * SCALE)
  image = render(buildCopperList())
end

function love.draw()
  love.graphics.draw(image, 0, 0, 0, SCALE, SCALE)
end

With these numbers it prints 19 colours on screen from 4 registers, the same figure the demo shows with its default settings. Notice that colourNumber never mentions a colour, and the copper list never mentions a pixel.

Pitfalls

  • Forgetting the top of the frame. A register keeps its last value. If the list does not reset the sky colour each frame, the horizon colour leaks into the top of the next frame. The Lua reloads the palette for this reason.
  • Every pixel on the line shares the register. Anything else drawn with colour 0 changes too, such as a hole in a tree. Reserve the rewritten colour number for the sky.
  • More bands than colour steps. With 4 bits per channel a fade has at most 16 steps per channel. Extra bands repeat values and only lengthen the list.
  • The Lua is slow on purpose. It builds the picture pixel by pixel to show the mechanism. In a real game, draw a stretched gradient image or use a shader.

In real games

Copper skies were common in Amiga games, and in the demo scene full-width stripes of changing colour, called raster bars or copper bars, became a signature effect. The Workbench used the copper too: drag one screen down and another, with a different resolution and palette, shows above it on the same display.

Other machines did it by other means. The Commodore 64 used raster interrupts, where the processor is told when the beam reaches a line. The Super Nintendo's HDMA writes a table of values into registers line by line, used for gradients and for Mode 7 floors.

Takeaways

  • Amiga bitplanes store colour numbers; 32 colour registers turn them into 12-bit colours from 4,096.
  • The copper is a coprocessor with three instructions, WAIT, MOVE and SKIP, that runs in step with the beam every frame.
  • Rewriting a colour register at chosen lines gives a gradient with many colours from one palette entry, at no cost to the main processor.
  • The extra colours are spread down the screen; each line still uses only the registers it can address.
  • Today the same idea is a small gradient ramp or palette looked up at draw time instead of a big image.

Doom's visplanes: floors saved for later, in a table of 128

How Doom drew floors and ceilings: it saved them per column as visplanes, drew them later in rows, and quit when its table of 128 was full.

Doom level designers in the 1990s knew a crash that came with no warning. Build a detailed room, test it, walk to one particular spot, and the game stops with the message R_FindPlane: no more visplanes. The room was not too big. It had too many different-looking pieces of floor in view at once.

The constraint: walls go down, floors go across

Yesterday's lesson showed Doom walking its BSP tree and drawing walls nearest first, one screen column at a time. Columns suit walls: every pixel in one column of a wall is at the same distance, so the texture is stepped through at one fixed rate.

Floors are the opposite. Down a column of floor, every pixel is at a different distance. Along a screen row, a flat floor stays at the same distance all the way across. So floors are cheap to draw in rows and expensive in columns. But the wall pass discovers floor one column at a time. Doom's answer is to write the floor down during the walk and draw it afterwards.

The trick: a visplane per floor surface

A visplane (visible plane) is Doom's record of one floor or ceiling surface that is on screen this frame. It has three things that decide how it looks: a height, a flat (Doom's name for a floor or ceiling texture) and a light level. For each of the 320 screen columns it stores two bytes: the top row and the bottom row the surface covers in that column. That is all. One column can hold only one run of rows.

Filling the table

When the walk draws a wall, it also knows which rows below it show the floor in front of it. To record them it uses two functions from the released source file r_plane.c:

  • R_FindPlane, called once for each area the walk enters, returns the first entry in the table with the same height, flat and light, or adds a new one.
  • R_CheckPlane, called for each wall piece, checks whether that wall's columns are already used in the entry. If they are free, the entry grows to include them. If even one is taken, a new visplane with the same three values is added.

Neighbouring areas that look exactly alike cost nothing extra: when both sides of a line match, the wall code skips marking the floor there, so the two areas become one run in each column. All sky shares a single key; the source comment reads "all skys map together".

Drawing the table

Once every wall is done, R_DrawPlanes goes through the table. For each visplane, R_MakeSpans compares neighbouring columns to find where each row starts and ends, and R_MapPlane draws each row as one span, a horizontal strip of pixels, caching the distance for that row. Sprites come last.

The limit

The table is a fixed array. In r_plane.c it is declared with #define MAXVISPLANES 128, under a comment that sums up how the programmers felt: "Here comes the obnoxious "visplane"." Each entry carries 20 bytes of fields plus 644 bytes of per-column rows and padding, so the whole table is about 85,000 bytes, set aside for the life of the game.

When R_FindPlane needs a new entry and all 128 are taken, it stops the game with the error from the hook. In the released source, R_CheckPlane, the other place that adds entries, has no such check at all.

What fills the table is variety in view, not size. A huge plain courtyard is one visplane. A small floor of alternating flats is many, because each return to stone after a break needs another entry. Light changes and small steps count exactly as much as texture changes.

Why designers had to care

The count depends on where the player stands and looks. A map can be fine everywhere except one spot, and only playing it from that spot reveals the crash. Later source ports removed the limit; PrBoom-plus, for example, keeps visplanes in a hash table of linked lists, and its comment notes that MAXVISPLANES there is "no longer a limit on the number of visplanes".

The lesson for today

A visplane is a batch: surfaces that share drawing state are merged and drawn together. Modern renderers batch draw calls by material in the same spirit, and many small material changes cost more than one big plain surface for the same reason. Fixed-size pools are still everywhere too, from particle buffers to packet queues. Decide what happens when one is full, and test the worst view, not the average.

The code

The bookkeeping in plain Lua, with the same names as the demo. love.draw marks three floors in the order the walk would meet them, near stone, a strip of grate and stone again, and ends up with three visplanes. Rows and columns start at 1.

local MAX_VISPLANES, SCREEN_W, SCREEN_H = 128, 320, 200
local visplanes = {}

local function newPlane(height, flat, light)
  if #visplanes == MAX_VISPLANES then error("no more visplanes") end
  local pl = { height = height, flat = flat, light = light,
               minx = SCREEN_W + 1, maxx = 0, top = {}, bottom = {} }
  table.insert(visplanes, pl)
  return pl
end

local function findPlane(height, flat, light)   -- first entry that looks the same
  for _, pl in ipairs(visplanes) do
    if pl.height == height and pl.flat == flat and pl.light == light then return pl end
  end
  return newPlane(height, flat, light)
end

local function checkPlane(pl, start, stop)      -- a wall will mark columns start..stop
  for x = math.max(start, pl.minx), math.min(stop, pl.maxx) do
    if pl.top[x] then return checkPlane(newPlane(pl.height, pl.flat, pl.light), start, stop) end
  end
  pl.minx, pl.maxx = math.min(pl.minx, start), math.max(pl.maxx, stop)
  return pl
end

local function markRows(pl, x1, x2, top, bottom)
  for x = x1, x2 do pl.top[x], pl.bottom[x] = top, bottom end
end

local function drawPlanes(drawSpan)             -- read each visplane back out as rows
  for _, pl in ipairs(visplanes) do
    for y = 1, SCREEN_H do
      local start = nil
      for x = pl.minx, pl.maxx + 1 do
        local inside = pl.top[x] ~= nil and pl.top[x] <= y and y <= pl.bottom[x]
        if inside and not start then start = x end
        if not inside and start then drawSpan(pl, y, start, x - 1); start = nil end
      end
    end
  end
end

function love.draw()
  visplanes = {}                                -- the table is emptied every frame
  markRows(checkPlane(findPlane(0, "stone", 192), 1, SCREEN_W), 1, SCREEN_W, 151, 200)
  markRows(checkPlane(findPlane(0, "grate", 192), 1, SCREEN_W), 1, SCREEN_W, 131, 150)
  markRows(checkPlane(findPlane(0, "stone", 192), 1, SCREEN_W), 1, SCREEN_W, 111, 130)
  drawPlanes(function(pl, y, x1, x2)            -- one row: one distance, one texture step
    local v = pl.light / 255
    if pl.flat == "grate" then v = v * 0.5 end
    love.graphics.setColor(v, v, v)
    love.graphics.rectangle("fill", x1 - 1, y - 1, x2 - x1 + 1, 1)
  end)
  love.graphics.setColor(1, 1, 1)
  love.graphics.print("visplanes: " .. #visplanes, 8, 8)
end

The third call finds the first stone entry, sees that its columns are taken and makes a new one. A newly made entry starts with no columns, so the second checkPlane call always accepts it. Doom's own span builder is smarter than the triple loop in drawPlanes: it compares each column only with its neighbour, but it produces the same rows.

Pitfalls

  • Judging by size. A big plain area is one visplane. A small detailed floor with stripes, lights or little steps can be dozens. Count the breaks a single column of the view passes through.
  • Forgetting light is part of the key. A patch of dim floor with the same texture and height is a different visplane, exactly like a texture change.
  • Testing from one spot. The count changes with position and angle. In the demo, turn the view with Look and watch the same floor need a different number.
  • A pool with no plan for full. Doom's answer was to quit. If you keep a fixed pool, decide on a fallback, such as merging, skipping or drawing a cheaper version, and log how close you came.
  • Assuming merging is optimal. R_FindPlane only offers the first matching entry. If that one is busy a new one is made, even when a later entry with the same key has room.

In real games

Every game on the original Doom engine inherited this design. Chocolate Doom, a source port that aims to behave like the original executables, keeps MAXVISPLANES at 128. Ports aimed at mappers, such as Boom and its descendant PrBoom-plus, replaced the array with a structure that can grow, which is one reason large community maps name the port they need. Deferring surfaces and drawing them grouped by state lives on in modern renderers that batch by material.

Takeaways

  • Walls are cheap to draw in columns and floors in rows, so Doom recorded floors during the wall pass and drew them afterwards.
  • A visplane is one surface's height, flat and light level, plus one top and bottom row for each screen column.
  • Same-looking floors merge, unless they need the same column; then a new visplane is made.
  • Doom's table held 128, and running out stopped the game with "R_FindPlane: no more visplanes".
  • Variety in view, not size, uses up the table, which is the same reason modern renderers batch by material.

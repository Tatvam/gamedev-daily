NES sprite flicker: eight sprites per line, shared out by turns

Why NES sprites flicker: the chip draws only the first 8 sprites on each line, so games reshuffle the list every frame and let everyone take turns.

Play a busy Nintendo Entertainment System game and, when enemies and bullets line up across the screen, some of them start to shimmer as if they were half transparent. Nothing is wrong with your console or your television.

The flicker is a choice the programmers made. The hardware could not draw everything, and flickering was the least bad way to fail.

The constraint: eight sprites on any one line

The NES (sold as the Famicom in Japan from 1983) draws its picture with a graphics chip called the PPU, the Picture Processing Unit. The picture is 256 pixels wide and is built one horizontal line at a time, a scanline, about 60 times a second on North American and Japanese televisions.

Moving objects are made of sprites: small 8 by 8 pixel pictures (or 8 by 16, one setting for all of them) that the PPU can place anywhere on top of the background. Their positions live in a 256-byte memory inside the PPU called OAM, Object Attribute Memory. Each entry takes 4 bytes (Y position, tile number, attributes such as palette and flipping, and X position), so OAM holds 64 sprites.

The catch is what happens on each line. While one scanline is drawn, the PPU searches OAM for sprites that cover the next line. It always starts at entry 0, walks forwards, and keeps the first 8 it finds: it has only enough time between lines to fetch 8 sprites' pictures. A ninth sprite is simply not drawn on that line.

Eight sprites of 8 pixels cover a quarter of the line. And a character is rarely one sprite: in 8 by 8 mode a 16 by 16 character is four sprites, two side by side, so four characters in a row fill the line.

Why the same sprites vanish every frame

If the game writes its objects into OAM in the same order every frame, the same 8 sprites win every frame, and the rest stay missing for as long as they share the line. A bullet becomes invisible. Because sprites are dropped line by line, an enemy can even lose just the rows that overlap a crowded line.

The trick: change the order every frame

The PPU does not decide the order. The game does. Games keep their sprite list in ordinary memory and have it copied into OAM once per frame, so they can write the objects in a different order each time. This is called sprite cycling or OAM cycling. Two simple ways:

  • Rotate the start. Frame 1 starts writing from object 0, frame 2 from object 1, and so on, wrapping round. Who lands past eighth place changes every frame.
  • Reverse on alternate frames. Forwards on even frames, backwards on odd ones. With up to 16 sprites on a line, each is drawn at least every other frame; beyond 16, the middle ones never are.

Flicker is the visible result. At 60 frames a second the eye blends the frames, so a sprite drawn in half of them looks see-through rather than gone. "Some things are invisible" becomes "everything is a little faint", and a faint bullet is far better than an invisible one.

The idea in one line

When a fixed budget cannot fit everything, rotate who misses out, so the failure is shared, short and visible instead of permanent and silent.

The lesson for today

Hard per-frame budgets are still everywhere: lights per object, shadow-casting lights, AI agents that think this frame, objects per network packet. Fill the budget from the front of the same list every time and the items at the back starve. Round-robin order, or a priority that grows the longer an item waits, shares the budget out as sprite cycling did.

The code

The same scene in LÖVE, with the same numbers: 12 sprites, 10 on the row at y = 40, and the rule "first 8 in OAM order per scanline". Sprites are solid squares here. buildOam is the game's job; spritesOnLine is the PPU's. Set ROTATE to false to see sprites vanish instead.

-- The NES rule: on each scanline only the first 8 sprites in OAM order are drawn.
local SCREEN_W, SCREEN_H, SCALE = 256, 96, 3
local SIZE, MAX_PER_LINE = 8, 8
local ROTATE = true
local COLOURS = { {1, 0.42, 0.35}, {1, 0.7, 0.25}, {0.5, 0.88, 0.42}, {0.35, 0.66, 1} }
local objects = {}
local frame = 0

function love.load()
  love.window.setMode(SCREEN_W * SCALE, SCREEN_H * SCALE)
  for i = 0, 9 do                                   -- ten on one row
    objects[#objects + 1] = { x = 12 + i * 24, y = 40, colour = COLOURS[i % 4 + 1] }
  end
  objects[#objects + 1] = { x = 40, y = 12, colour = COLOURS[3] }
  objects[#objects + 1] = { x = 180, y = 70, colour = COLOURS[4] }
end

-- The game: copy objects into OAM, starting from a different one each frame.
local function buildOam()
  local oam, n, start = {}, #objects, 0
  if ROTATE then start = frame % n end
  for i = 0, n - 1 do
    oam[i + 1] = objects[(start + i) % n + 1]
  end
  return oam
end

-- The PPU: search OAM from the start, keep the first 8 that cover line y.
local function spritesOnLine(oam, y)
  local found = {}
  for i = 1, #oam do
    local s = oam[i]
    if y >= s.y and y < s.y + SIZE then
      if #found == MAX_PER_LINE then break end      -- the rest are dropped
      found[#found + 1] = s
    end
  end
  return found
end

function love.update(dt)
  frame = frame + 1                                 -- a new OAM order every frame
end

function love.draw()
  local oam = buildOam()
  for y = 0, SCREEN_H - 1 do
    local found = spritesOnLine(oam, y)
    for i = #found, 1, -1 do                        -- lower OAM index ends on top
      love.graphics.setColor(found[i].colour)
      love.graphics.rectangle("fill", found[i].x * SCALE, y * SCALE, SIZE * SCALE, SCALE)
    end
  end
end

With vertical sync on, one love.update is one displayed frame, so the order changes every frame. The drawing loop works scanline by scanline like the PPU, so a sprite partly over a crowded row loses only those rows.

Pitfalls

  • Rotating by a step that matches the pattern. If the list has 10 objects and you rotate by 5, the start only ever takes two values, so the losses always fall on the same few sprites while the rest are never touched. Rotating by 1, or by a step that shares no factor with the list length, visits every starting point.
  • Letting the player flicker too. Fair sharing is not always right. You can keep a few important sprites at the front of OAM every frame and cycle only the rest.
  • Forgetting that metasprites multiply the count. One 16 by 16 character costs two sprites on each of its lines. Count hardware sprites per line, not objects.
  • Flicker at a low frame rate. At 30 frames a second, a sprite shown in alternate frames blinks 15 times a second: hard to read and unpleasant for some players. Keep crowding rare.

In real games

Flicker is one of the most recognisable looks of NES games with crowded screens, and NES homebrew developers still write cycling routines today. Some emulators offer an option that removes the eight-per-line limit, which looks solid but is not how the console behaves.

The limit is not unique to the NES. The original Game Boy holds 40 sprites and draws at most 10 on one line, with the same choice between vanishing and flickering.

Takeaways

  • The NES PPU holds 64 sprites in OAM but draws only the first 8 it finds on each scanline.
  • With a fixed OAM order, the same sprites lose every frame and simply vanish.
  • Games change the order every frame, by rotating the start or reversing it, so the losers change and sprites flicker instead.
  • Rotation must reach every starting point, and important sprites can be kept at the front.
  • Any hard per-frame budget, from lights to network updates, can share its shortfall the same way.

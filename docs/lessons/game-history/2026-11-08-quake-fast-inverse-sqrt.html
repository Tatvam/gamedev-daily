Quake III's fast inverse square root: a guess from the bits, then one fix

How Quake III Arena estimated 1/√x with no division: read a float's bits as an integer, subtract from a magic number, then refine once.

Every time a game lights a surface, it needs the direction the surface faces as a vector of length exactly 1. Making a vector that length means dividing it by its length, which takes a square root and a division, for every vertex, every frame. When id Software released the source code of Quake III Arena in 2005, programmers found a short function that does this job with neither, using a hexadecimal number that nobody could explain at first.

The constraint: square roots and divisions were slow

To normalise a vector (x, y, z) you multiply each part by 1/√(x² + y² + z²). That value, one divided by a square root, is called the inverse square root. On the processors of the late 1990s, square root and division were among the slowest floating-point operations, many times slower than an addition or a multiplication. A 3D game that normalises thousands of vectors per frame pays that price thousands of times.

Quake III Arena (1999) contains a function, Q_rsqrt in the file q_math.c, that estimates the inverse square root using only an integer shift, an integer subtraction and a few multiplications. The answer is not exact, but it is close enough for lighting.

The trick, step 1: a float's bits are almost its logarithm

A 32-bit float stores a number as 1 sign bit, 8 exponent bits and 23 fraction bits. The value is (1 + fraction ÷ 2²³) × 2exponent − 127. The 127 is called the bias; it lets the exponent field hold negative powers.

Now forget that those 32 bits are a float and read them as a plain whole number, call it i. The exponent sits in the high bits, so i grows by 2²³ each time the number doubles. Between two powers of two, the fraction rises in a straight line. That is very nearly a logarithm in base 2, scaled up and shifted:

Exact at powers of two, a little low in between. Reading the bits as an integer gives you a rough logarithm for free.

Step 2: halve the logarithm, flip its sign

Logarithms turn powers into multiplication: log(1/√x) = −½ log x. So with a rough logarithm in hand, the inverse square root is "take minus half of it". On the integer that becomes: shift i right by one bit to halve it, and subtract it from a constant that puts the bias back. Working the algebra through with the table's straight-line logarithm gives the constant 1.5 × 127 × 2²³, which is 0x5F400000 in hexadecimal. Quake III uses 0x5F3759DF, slightly smaller, which spreads the error more evenly. Read the result back as a float and you have a first guess that is within about 3.5 percent.

Step 3: one step of Newton's method

Newton's method improves a guess at the root of an equation by following the slope of the equation towards zero. Applied to "find y so that 1/y² = x", the update works out to

y = y * (1.5 - 0.5 * x * y * y)

which, conveniently, has no division in it either. Each step roughly squares the relative error, so the error falls very fast: in the demo below, the worst case is about 3.4 percent for the raw guess, 0.18 percent after one step, and 0.0005 percent after two. Quake III does one step. A second step is in the source but commented out, with a note that it can be removed.

Pattern worth keeping

Get a cheap guess from the structure of the data, then refine it with a cheap correction. The guess does not need to be good; it needs to be close enough for the correction to finish the job.

Who wrote it: not settled, and probably not Carmack

The function is often credited to John Carmack, Quake III's lead programmer. In 2006 the hardware site Beyond3D, in articles by Ryszard Sommefeldt, went looking for the author. As those articles report, Carmack said it was not his work. Other well-known programmers who were asked, including Terje Mathisen and Gary Tarolli of 3dfx, said they had seen or used it but had not created it. The second article names Greg Walsh, who wrote it at Ardent Computer in the late 1980s, building on an idea from Cleve Moler. This page could not re-open those articles while it was written, so treat the chain of names as reported, not confirmed. How the exact value 0x5F3759DF was chosen is not explained in the Quake III source.

The code

A rebuild of the mechanism in plain Lua, written for this page. Lua numbers are 64-bit, and LuaJIT has no plain way to read a float's bits, so floatToBits and bitsToFloat build the 32-bit pattern by hand with math.frexp. That is far slower than the original; the point is to see each step. The numbers match the demo: for x = 4 with one step it prints 0.499154.

-- Fast inverse square root, rebuilt step by step. Positive numbers only.
local MAGIC = 0x5F3759DF

local function floatToBits(x)
  local m, e = math.frexp(x)               -- x = m * 2^e, with 0.5 <= m < 1
  local exponent = e - 1 + 127             -- stored with a bias of 127
  local fraction = math.floor((m * 2 - 1) * 2^23 + 0.5)
  return exponent * 2^23 + fraction        -- a rounding carry moves into the exponent
end

local function bitsToFloat(i)
  local exponent = math.floor(i / 2^23)
  local fraction = i - exponent * 2^23
  return (1 + fraction / 2^23) * 2^(exponent - 127)
end

local function fastInvSqrt(x, steps)
  local i = floatToBits(x)                 -- the bits: roughly log2(x), scaled
  i = MAGIC - math.floor(i / 2)            -- minus half the log, bias put back
  local y = bitsToFloat(i)                 -- first guess, within about 3.5%
  for n = 1, steps do
    y = y * (1.5 - 0.5 * x * y * y)        -- Newton step: no division, no root
  end
  return y
end

local x, steps = 4, 1

function love.keypressed(key)
  if key == "up" then x = x * 1.25 end
  if key == "down" then x = x / 1.25 end
  if key == "space" then steps = (steps + 1) % 3 end
end

function love.draw()
  local guess = fastInvSqrt(x, steps)
  local exact = 1 / math.sqrt(x)
  love.graphics.print(("x = %.4f  steps = %d"):format(x, steps), 10, 10)
  love.graphics.print(("estimate %.6f  exact %.6f  error %.4f%%"):format(
    guess, exact, 100 * (guess - exact) / exact), 10, 30)
end

The original is C and works on 32-bit floats throughout, reading the bits by pointing an integer pointer at the float. Here the Newton steps run in 64-bit numbers, which changes the last digits but not the shape of the error.

Pitfalls

  • Using it today for speed. Since 1999 x86 processors with SSE have had an instruction, rsqrtss, that returns an approximate inverse square root directly, and shader languages have inversesqrt. On current hardware the bit trick is usually slower than these. Write 1 / math.sqrt(x), measure, and only then look for something faster.
  • Feeding it the wrong numbers. The trick assumes a positive, normal float. Zero, negative numbers, infinity and the very tiny subnormal floats give nonsense, not an error message.
  • Copying the pointer cast. Reading a float through an integer pointer, as the 1999 C code does, breaks the type rules of modern C and C++, and an optimising compiler is allowed to produce wrong code. Copy the bytes instead.
  • Reusing the constant elsewhere. The magic number belongs to 32-bit floats and to the number of Newton steps that follow. A 64-bit double needs a different 64-bit constant, and a different step count favours a slightly different value.
  • Trusting 0.18 percent everywhere. That is fine for a lighting normal. In a value that is fed back into itself every frame, such as a physics state, small errors add up.

In real games

Quake III Arena's released source is the best-known home of the function, and its fame comes from that release and the debate about its author, not from Quake III being the first program to use it. Chris Lomont's 2003 paper analysed the constant and found that 0x5F375A86 is very slightly better after one Newton step; the demo includes it, and the difference is tiny.

The lesson for today is the pattern, not the constant. Graphics hardware still offers fast approximate functions, such as GLSL's inversesqrt, because games happily trade a little accuracy for speed in lighting. Mobile and web shaders often run at reduced precision for the same reason. And "read the bits of a float as an integer" is still a common tool: it sorts positive floats correctly as integers, and it gives quick logarithm and power estimates.

Takeaways

  • Read as an integer, a float's bits are a scaled, shifted, straight-line approximation of its base-2 logarithm.
  • In log space, 1/√x is "minus half", which becomes one shift and one subtraction from a magic constant.
  • One Newton step, with no division, cuts the worst error from about 3.4 to about 0.18 percent.
  • The function is often credited to John Carmack, but the reported history points elsewhere and is not fully settled.
  • Modern hardware has fast inverse square root built in, so keep the pattern (cheap guess, cheap fix) rather than the code.

Metroid's password: the save file you write down

How Metroid on the NES packed a player's progress into bits, guarded it with a checksum and printed it as a password, so the cartridge needed no save memory.

When you lost all your energy in the American and European release of Metroid, the game showed a screen of 24 strange characters and told you to write them down. Typing them back in later put you where you left off, with the items you had found.

Those characters were not a key to a save stored somewhere else. They were the save. This lesson rebuilds that trick on a small scale.

The constraint: nowhere to write

Metroid first came out in Japan in 1986 for the Famicom Disk System, an add-on that ran games from small writable disks. Saving progress there was simple: write it to the disk.

The version sold on cartridge in North America (1987) and Europe had no such option. A cartridge of that kind holds ROM, read-only memory: the console can read the game from it but cannot change it. Keeping a save needs extra memory chips on the board and a small battery to keep their contents alive when the power is off, which made each cartridge cost more. Metroid shipped without them. The only place left to keep the save was outside the machine: on paper, in the player's hand.

The trick: the save becomes text

A save file only has to remember what a game cannot work out again by itself. For Metroid that is mostly yes-or-no facts: has this item been picked up, has this door been opened, has this boss been beaten. Each fact fits in a single bit, a 0 or a 1. Counts such as the number of missiles take a few bits more.

The game lines those bits up into a row, then cuts the row into groups of 6 bits. Six bits can hold 64 different values, so each group is written as one character from a 64-symbol alphabet of digits, upper case letters, lower case letters and two punctuation marks. That gives a password with no wasted space: every character carries 6 bits of save data.

According to the fan-written technical guide to the format, Metroid's 24 characters hold 144 bits, which is 18 bytes. Sixteen bytes describe the player's progress. The other two do housekeeping, and they are the clever part.

The checksum: catching typing mistakes

People copy 24 characters badly. A checksum is an extra value calculated from the rest of the data and stored next to it. The guide describes Metroid's as simple: add up the first 17 bytes and keep only the lowest 8 bits of the total. When a password is typed in, the game does the same sum. If it does not match the stored byte, the password is rejected.

This catches nearly every slip of the pen. It is not a lock, though. A wrong password has about a 1 in 256 chance of passing by luck, because the check is only 8 bits.

The shift: scrambling the look

If the bits went straight into characters, collecting one item would change one character, and players would soon learn which character meant what. Metroid stores a shift value, and the progress bits are rotated by that many places before being written: every bit slides along, and the ones that fall off one end come back at the other. Typing the password in reverses the rotation using the stored shift. As fans describe it, this means the same save can be written as many different-looking passwords.

Fact and legend

The best known Metroid password begins with the words JUSTIN BAILEY and starts the game with many items. It is often said that this is a lucky string that happens to pass the checksum and decode into a strong save, not a cheat the developers planted. That explanation fits the format, but no developer statement confirming it was available to this page, and claims about who Justin Bailey was are unconfirmed.

Try it

Click or tap the squares to collect items, open doors and beat bosses, and move the sliders. With a keyboard, focus the save panel, use the arrow keys and press Enter or Space.

Change one item and see how few characters change. Move Shift and the same save becomes a different password. Then press Break one character and Load password to watch the checksum reject it.

The code

This is the demo's format in Lua: four data bytes, a shift byte and a checksum byte, written as 8 characters. It keeps the bits in a table of 0s and 1s, which is slower than bit operations but easy to follow and runs in plain Lua 5.1. Bit numbers in the comments count from 1.

local ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz?-"

local function pushBits(bits, value, count)        -- most significant bit first
  for i = count - 1, 0, -1 do
    bits[#bits + 1] = math.floor(value / 2 ^ i) % 2
  end
end

local function readBits(bits, first, count)
  local value = 0
  for i = first, first + count - 1 do value = value * 2 + bits[i] end
  return value
end

local function rotate(bits, first, count, shift)   -- rotate left by shift places
  local copy = {}
  for i = 0, count - 1 do copy[i] = bits[first + (i + shift) % count] end
  for i = 0, count - 1 do bits[first + i] = copy[i] end
end

local function dataSum(bits, shift)                -- four data bytes plus the shift
  local sum = shift
  for b = 0, 3 do sum = sum + readBits(bits, b * 8 + 1, 8) end
  return sum % 256
end

function encode(save)          -- save.shift must be 0 to 31
  local bits = {}
  pushBits(bits, save.items, 8);    pushBits(bits, save.doors, 8)
  pushBits(bits, save.missiles, 8); pushBits(bits, save.tanks, 3)
  pushBits(bits, save.bosses, 2);   pushBits(bits, save.area, 3)
  local check = dataSum(bits, save.shift)
  rotate(bits, 1, 32, save.shift)
  pushBits(bits, save.shift, 8);    pushBits(bits, check, 8)
  local out = {}
  for c = 0, 7 do
    local v = readBits(bits, c * 6 + 1, 6)
    out[#out + 1] = ALPHABET:sub(v + 1, v + 1)
  end
  return table.concat(out)
end

function decode(text)          -- returns a save table, or nil
  if #text ~= 8 then return nil end
  local bits = {}
  for c = 1, 8 do
    local pos = ALPHABET:find(text:sub(c, c), 1, true)
    if not pos then return nil end
    pushBits(bits, pos - 1, 6)
  end
  local shift = readBits(bits, 33, 8)
  rotate(bits, 1, 32, (32 - shift % 32) % 32)      -- undo the rotation
  if dataSum(bits, shift) ~= readBits(bits, 41, 8) then return nil end
  return { items = readBits(bits, 1, 8), doors = readBits(bits, 9, 8),
           missiles = readBits(bits, 17, 8), tanks = readBits(bits, 25, 3),
           bosses = readBits(bits, 28, 2), area = readBits(bits, 30, 3), shift = shift }
end

-- The demo's starting save. Items 1, 2 and 4 are bits 11010000.
print(encode({ items = 208, doors = 224, missiles = 15, tanks = 2,
               bosses = 0, area = 1, shift = 5 }))   --> 707eEWK5

The checksum is taken before the rotation and checked after it is undone, so it protects the save itself, not one particular spelling of it. In a LÖVE game, call encode on your game-over screen and draw the result with love.graphics.print.

Pitfalls

  • A checksum is not security. It stops typos, not people. Anyone who learns the format can build any save they like, and fans did exactly that for Metroid. If a code must not be forged, for example one that unlocks paid content or posts to a leaderboard, check it on a server or sign it with a secret key.
  • Passing the check does not make a save sensible. In the demo, area is 3 bits, so it can hold 0 to 7, but only areas 0 to 4 exist. About 1 in 256 random strings passes the checksum, and some of those name an area that is not there. Range-check every field after decoding. Loading nonsense is how odd glitch states are born.
  • Look-alike characters. An alphabet with both 0 and O, or l and 1, invites copying mistakes. If people write the code by hand, drop the confusable symbols, even if that costs a longer code.
  • Formats outlive versions. Add a field later and old codes decode wrongly. Reserve bits for a version number.

In real games

Password saves were common on consoles whose cartridges had no save memory, and they faded as battery-backed saves and memory cards became normal.

Packing state into a short string did not fade. Hearthstone deck codes are the deck itself, packed into bytes and written as base64 text that players paste into forums. Many browser games keep a puzzle in the page address, so sharing a link shares the state with no server involved. The check digit at the end of an ISBN is the same kind of guard as Metroid's checksum.

The constraint also returns at scale: a game storing millions of cloud saves pays less when yes-or-no facts are bits rather than text.

Paste the code into main.lua. Add a version field by taking one bit from missiles: store missiles in 7 bits, push a 1-bit version after them, update the positions in decode, and make it return nil when the version is not 1. Then add a range check that rejects any area above 4. You are done when your own saves round-trip through encode and decode unchanged and a hand-edited code with area 6 is refused.

Takeaways

  • A save only needs the facts the game cannot rebuild, and most of them are single bits.
  • Cut the bits into 6-bit groups and each group becomes one of 64 characters: a password with no wasted space.
  • A checksum catches typing mistakes. With 8 bits, about 1 in 256 wrong codes still slips through.
  • Rotating the bits by a stored shift hides the structure, but it is disguise, not protection.
  • Always range-check fields after decoding. A passing checksum does not mean the save makes sense.

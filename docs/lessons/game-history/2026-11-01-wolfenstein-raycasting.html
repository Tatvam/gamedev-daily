Wolfenstein 3D: a 3D view from a flat grid, one ray per column

How Wolfenstein 3D drew a 3D maze on a 1992 PC: cast one ray per screen column across a 2D grid and size each wall slice by its distance.

Wolfenstein 3D, released by id Software in 1992, let players run through corridors in first person on ordinary PCs with no 3D hardware. Yet the game never stores a 3D world. Its levels are flat grids of squares, and the 3D view is worked out from that grid one screen column at a time.

The constraint: the processor draws every pixel

A PC of the early 1990s had no chip to draw triangles or test depth. The graphics card showed whatever bytes the processor wrote into video memory, at 320 by 200 pixels with 256 colours. Every wall pixel was calculated and written by the main processor, which also ran the game. A general 3D renderer, with walls at any angle and height to sort and clip, was too much work. So the game shrank the problem.

The trick: make the world simple enough for rays

The released source code shows the rules. A map is a grid of at most 64 by 64 squares. Each square is either empty or a solid wall block (doors, which slide inside their square, are a special case). Every wall is a whole square, all walls are the same height, and the floor and ceiling are flat. The ceiling is filled with one colour per level and the floor with one fixed colour; neither is textured.

Those rules have a useful result: looking straight ahead, any column of the screen shows ceiling at the top, floor at the bottom, and at most one wall slice in between, centred on the horizon. To draw a column, the renderer only needs to know which wall that column sees and how far away it is.

Finding that is called raycasting: start at the player and follow a straight line, the ray, in the direction that column looks, until it enters a wall square. One ray per column, so a 320 pixel wide view costs 320 rays, whatever the size of the map.

Walking the grid

A ray can only enter a new square where it crosses a grid line, so the renderer jumps from crossing to crossing. It tracks how far along the ray the next vertical grid line is and how far the next horizontal one is, takes the nearer, moves into the square beyond, and checks whether it is a wall. This is a kind of DDA (digital differential analyser), a stepping method that only needs additions inside its loop.

In Wolfenstein 3D this loop is hand-written assembly, a routine called AsmRefresh, with one branch for vertical walls and one for horizontal walls. As it passes through an empty square it marks that square as seen in a 64 by 64 table. Later the game only considers drawing enemies and objects that stand in, or next to, a marked square, so the rays do double duty as a visibility test.

From distance to height

Perspective makes things shrink in proportion to distance. A wall twice as far away looks half as tall, so the slice height is a constant divided by the distance. That constant, the focal length, is set by the field of view: with a view w pixels wide and a field of view fov, it is (w / 2) / tan(fov / 2).

Which distance, though? The obvious answer, the length of the ray, is wrong. Rays at the edge of the screen travel further than the centre ray to reach the same flat wall, so a straight wall would bulge in the middle and curve away at the sides. This is the fisheye effect.

The fix is to measure distance along the direction the player faces. The game's CalcHeight function does the same thing by projecting the hit point onto the view direction, and it clamps very small distances to a minimum so the division cannot overflow.

The rays are also not spread at equal angles. They aim through equally spaced points on a flat screen, so each column's angle is the atan of its position across the screen. The source builds a table of these angles when the view size is set.

Texture and light for almost nothing

Where the ray hits inside a square also tells the renderer which column of the wall picture to draw: the fractional part of the hit coordinate picks one of the texture's 64 columns, which is then stretched to the slice height. And each wall type has two pictures, one for faces hit across a vertical grid line and one for horizontal lines, shaded differently, which gives the maze a sense of light without any lighting maths.

In his release notes for the source code, John Carmack wrote that "ray casting was a lot simpler to do at the time", compared with a renderer based on binary space partitioning, the method Doom would use. He also wrote that the wall-stretching routines were generated as machine code while the game ran, the fastest method on the machines without a memory cache that were the original target.

The idea in one line

Restrict the world until each screen column has one simple question, then answer it once per column.

The lesson for today

The same grid walk still finds which tiles a bullet crosses, whether an enemy can see the player, and which block a ray hits in voxel worlds. And the bargain remains: if you set the rules of your world, choose rules that make the expensive question cheap.

The code

A complete LÖVE program with the same map, field of view, column count and minimum distance as the demo. The map is a list of strings: 0 is empty and other digits are wall types. The demo moves in fixed steps; this version moves smoothly with the arrow keys.

local MAP = {
  "111111111111", "100000000001", "100000220001", "100000220001",
  "100000000001", "100300000001", "100300001111", "100000000001",
  "122200000001", "100000033001", "100000000001", "111111111111",
}
local FOV, COLUMNS, MIN_DIST = math.rad(60), 40, 0.05
local player = { x = 2.5, y = 10.5, angle = math.rad(300) }
local SHADE = { ["1"] = {0.35, 0.55, 0.9}, ["2"] = {0.3, 0.7, 0.4}, ["3"] = {0.9, 0.65, 0.25} }

local function tileAt(cx, cy)            -- outside the map counts as wall
  local row = MAP[cy + 1]
  if row == nil or cx < 0 or cx >= #row then return "1" end
  return row:sub(cx + 1, cx + 1)
end

local function castRay(px, py, angle)
  local dx, dy = math.cos(angle), math.sin(angle)
  local cellX, cellY = math.floor(px), math.floor(py)
  local stepX = dx < 0 and -1 or 1
  local stepY = dy < 0 and -1 or 1
  local deltaX = math.abs(1 / dx)        -- ray length from one vertical line to the next
  local deltaY = math.abs(1 / dy)        -- and from one horizontal line to the next
  local nextX = (dx < 0 and px - cellX or cellX + 1 - px) * deltaX
  local nextY = (dy < 0 and py - cellY or cellY + 1 - py) * deltaY
  for _ = 1, 64 do
    local dist, side
    if nextX < nextY then                -- the vertical line is nearer: cross it
      dist, side = nextX, "x"
      nextX = nextX + deltaX
      cellX = cellX + stepX
    else
      dist, side = nextY, "y"
      nextY = nextY + deltaY
      cellY = cellY + stepY
    end
    local tile = tileAt(cellX, cellY)
    if tile ~= "0" then return dist, side, tile end
  end
  return nil                             -- gave up: nothing within 64 crossings
end

function love.update(dt)
  local turn, move = 0, 0
  if love.keyboard.isDown("left") then turn = turn - 1 end
  if love.keyboard.isDown("right") then turn = turn + 1 end
  if love.keyboard.isDown("up") then move = move + 1 end
  if love.keyboard.isDown("down") then move = move - 1 end
  player.angle = player.angle + turn * 2 * dt
  local nx = player.x + math.cos(player.angle) * move * 2 * dt
  local ny = player.y + math.sin(player.angle) * move * 2 * dt
  if tileAt(math.floor(nx), math.floor(ny)) == "0" then
    player.x, player.y = nx, ny
  end
end

function love.draw()
  local w, h = love.graphics.getDimensions()
  local half = math.tan(FOV / 2)
  local focal = (w / 2) / half
  local colW = w / COLUMNS
  love.graphics.setColor(0.2, 0.2, 0.25)        -- ceiling: one flat colour
  love.graphics.rectangle("fill", 0, 0, w, h / 2)
  love.graphics.setColor(0.4, 0.4, 0.4)         -- floor: another
  love.graphics.rectangle("fill", 0, h / 2, w, h / 2)
  for i = 0, COLUMNS - 1 do
    local screenX = (2 * (i + 0.5) / COLUMNS - 1) * half  -- evenly spaced on the screen
    local rayAngle = player.angle + math.atan(screenX)
    local dist, side, tile = castRay(player.x, player.y, rayAngle)
    if dist then
      local perp = math.max(dist * math.cos(rayAngle - player.angle), MIN_DIST)
      local sliceH = focal / perp
      local c = SHADE[tile] or SHADE["1"]
      local k = (side == "y") and 0.65 or 1     -- darker face for horizontal lines
      love.graphics.setColor(c[1] * k, c[2] * k, c[3] * k)
      love.graphics.rectangle("fill", i * colW, (h - sliceH) / 2, colW + 1, sliceH)
    end
  end
end

To add a texture, take the hit point player.x + math.cos(rayAngle) * dist (or the y version when side is "x"), keep its fractional part with % 1, and multiply by the texture width to choose the column to stretch.

Pitfalls

  • Using the ray length as the distance. Straight walls bow outwards. Multiply by the cosine of the angle from the view direction, as the demo does when Correct fisheye is on.
  • Spreading rays at equal angles. It looks close, but walls stretch towards the screen edges. Aim the rays at equally spaced points across a flat screen and take the atan.
  • Dividing by a tiny distance. With the player pressed against a wall, the distance nears zero and the slice height explodes. Clamp it, as Wolfenstein 3D did, and keep the player a little away from walls.
  • A ray that never stops. If the map has a gap in its outer wall, a ray can run forever. Cap the number of crossings and treat outside the map as wall.
  • Forgetting the limits. No angled walls, no stairs, no rooms above rooms. That is the price of the speed.

In real games

id Software's earlier games Hovertank 3D and Catacomb 3-D were first-person maze games built on the same grid idea, and Wolfenstein 3D refined it. The engine was licensed to other studios, and Spear of Destiny, the follow-up, ran on it too. Today grid raycasting is a common first 3D project, and the same grid walk is used for line of sight and bullet tracing in tile-based games and for picking blocks in voxel games.

Takeaways

  • Wolfenstein 3D stores a flat grid, at most 64 by 64 squares, not a 3D world.
  • With equal-height walls and flat floors, each screen column shows at most one wall slice, so one ray per column is enough.
  • The ray jumps from grid line to grid line and checks each square it enters.
  • Slice height is focal length divided by the distance along the view direction; using the raw ray length gives fisheye.
  • Choosing strict world rules can turn an expensive general problem into a cheap special one.

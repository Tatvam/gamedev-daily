Myst and the slow CD-ROM: where files sit on the disc

Why early CD-ROM drives spent more time moving the read head than reading, and how grouping files that are read together cuts load times.

Myst, released by Cyan in 1993, is a world of still pictures: click, and the next view appears. Each click means a trip to the CD-ROM drive, and on the drives of the day that trip was slow. Much of the wait was not reading the picture. It was the drive moving to where the picture was stored.

The constraint: a fast-ish pipe with a slow tap

Brothers Rand and Robyn Miller built Myst on the Macintosh in HyperCard, Apple's card-based authoring tool, and shipped it on a CD-ROM. A CD held about 650 MB, far more than the floppy disks of the time, and Myst needed most of that space for its pictures, sounds and short films. Even so, the pictures were stored with 256 colours to keep them small.

Two numbers describe any drive. Transfer rate is how fast data flows once the drive is reading. A single-speed (1x) CD-ROM drive delivers about 150 KB per second, the rate fixed by the CD-ROM standard. Seek time is how long it takes to move the read head to a new place and start reading there. For early drives, the average access time was usually quoted in the hundreds of milliseconds.

At 150 KB per second, a 60 KB picture takes 0.4 seconds to read. A jump across the disc first can cost almost as much again.

Why jumps are slow on a CD

A CD has no rings of separate tracks. Its data is one long spiral, starting near the centre and winding outwards. The drive reads it at a constant linear speed, so the motor must turn faster near the centre and slower near the edge. A long jump means moving the head on its arm, finding the exact spot on the spiral again, and changing the motor's speed. Reading straight on needs none of that.

The trick: lay the disc out in the order it will be read

You cannot make the head move faster, but you can give it less distance to cover. Files that the player will want one after another should sit next to each other on the spiral. Then most reads begin exactly where the last one ended, and the drive simply keeps reading.

A game like Myst suits this well. The player moves through linked scenes, almost always to a neighbour, and stays on one island (one Age, in Myst's terms) for a long time. Group each Age's scenes together, in the order they connect, and a walk becomes mostly short reads with an occasional jump.

Coverage of Rand Miller's 2020 interview with Ars Technica reports that the team compressed images and sound to run on 1x drives, did not know until deep into development whether the game would run from a CD at all, and placed files carefully on the disc. I could not open the interview, so Myst's actual layout is not described here. The demo shows the general technique, not a copy of Myst's disc.

Latency versus bandwidth

Seek time is a kind of latency: a fixed delay before data starts to flow. Transfer rate is bandwidth. When latency is large, the number of separate requests matters more than their size.

Then set the drive to 4x: reading gets four times faster, but seeking does not, and the gap between the layouts grows. With the canvas focused, Space steps and R resets.

The code

The demo's cost model in Lua, with the same walk, the same layouts and the same numbers. A read that starts exactly where the head stopped costs no seek. Any other jump costs a fixed 120 ms plus up to 600 ms more in proportion to how far it goes.

local DISC_KB, SCENE_KB, KB_PER_SECOND = 600000, 60, 150
local SETTLE_MS, FULL_SEEK_MS = 120, 600

local WALK = { "A1","A2","A3","A4","A3","A4","A5","A6","A1",
  "B1","B2","B3","B4","B5","B4","B3","B2","B1","A1",
  "C1","C6","C5","C4","C3","C4","C5","C6","C1",
  "B1","B6","B5","B6","B1","A1","A6","A5" }

local ISLANDS = { "A", "B", "C" }
local GROUP_START = { A = 30000, B = 230000, C = 430000 }
local scattered, grouped = {}, {}          -- name -> start, in KB

for i, island in ipairs(ISLANDS) do
  for j = 1, 6 do
    local name = island .. j
    local slot = (((i - 1) * 6 + (j - 1)) * 7) % 18   -- spread out
    scattered[name] = math.floor((slot + 0.5) * DISC_KB / 18)
    grouped[name] = GROUP_START[island] + (j - 1) * SCENE_KB
  end
end

local function seekMs(from, to)
  if from == to then return 0 end           -- keep reading, no jump
  return SETTLE_MS + FULL_SEEK_MS * math.abs(to - from) / DISC_KB
end

local function walkCost(layout)
  local head, seek, read = 0, 0, 0
  for _, name in ipairs(WALK) do
    local start = layout[name]
    seek = seek + seekMs(head, start)
    read = read + SCENE_KB / KB_PER_SECOND * 1000
    head = start + SCENE_KB                  -- head ends after the file
  end
  return seek, read
end

function love.draw()
  local s1, r1 = walkCost(scattered)
  local s2, r2 = walkCost(grouped)
  love.graphics.print(string.format("Scattered: seek %.1f s, read %.1f s", s1 / 1000, r1 / 1000), 10, 10)
  love.graphics.print(string.format("Grouped:   seek %.1f s, read %.1f s", s2 / 1000, r2 / 1000), 10, 30)
end

It prints 13.6 seconds of seeking for the scattered layout and 3.9 for the grouped one, against 14.4 seconds of reading for both. Grouping removes 14 of the 36 jumps, and the remaining jumps are short.

Pitfalls

  • Grouping by type instead of by use. Putting all pictures in one folder and all sounds in another is tidy, but if every scene needs one of each, the head bounces between the two folders on every step. Group by what is loaded together.
  • Assuming the file system keeps your order. On a CD you build the image, so you can control the order. On a hard drive or a phone, the operating system decides where files go. There, the usual answer is one large package file whose inside you lay out yourself.
  • Forgetting the walk back. A layout ordered for walking forward still pays a seek when the player turns around. Small, frequently revisited files are better kept in memory once loaded.

In real games

Disc layout stayed a routine part of shipping console and PC games through the CD and DVD years. Microsoft, for example, published a technical article for Windows developers on optimizing DVD performance in games, which deals with the same seek problem.

Hard drives have the same problem with a moving head. In his 2020 talk The Road to PS5, Mark Cerny described how games for hard drives stored copies of the same data in several places so that each area could be read with few seeks, and presented the console's solid-state drive as a way to stop doing that.

The lesson for today: latency is still everywhere. A web game that loads 200 small images makes 200 requests, each with a network round trip, which is a seek by another name. Packing images into one sprite sheet, bundling scripts and grouping a level's assets into one download are Myst's disc layout in a new form. Count the round trips before you count the bytes.

Takeaways

  • Load time is roughly the number of jumps times the seek cost, plus the bytes divided by the transfer rate.
  • On a 1x CD-ROM drive, about 150 KB per second, a jump could cost as much as reading a whole picture.
  • Placing files in the order they are used turns many jumps into continuous reading.
  • Faster transfer makes layout matter more, because the seeks stay.
  • Today the same rule applies to network requests and package files: fewer, larger, well-ordered reads.

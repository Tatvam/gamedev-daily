Racing the beam: the Atari 2600 draws one line at a time

The Atari 2600 had no memory for a picture, so games rewrote the graphics chip between scanlines, inside a budget of 76 CPU cycles per line.

Today a game draws a whole frame into memory and then shows it. The Atari Video Computer System, released in 1977 and later renamed the Atari 2600, could not do that. It had 128 bytes of RAM in total. A picture 160 pixels wide and 192 lines tall needs 3,840 bytes even at one bit per pixel, which is thirty times more memory than the console had.

So the program drew the picture while the television was displaying it, a few pixels ahead of the beam. This is known as racing the beam.

The constraint: a chip that only knows the current line

An old television draws with an electron beam that sweeps left to right, one line at a time, top to bottom. Each line is a scanline. The beam's trip back to the left edge is the horizontal blank, and its trip back to the top is the vertical blank.

The 2600's graphics chip, the TIA (Television Interface Adaptor), has no frame buffer: no memory holding a whole picture. It has a handful of registers, small slots the program writes to, that describe a single line:

  • a background colour (COLUBK)
  • a coarse playfield: 20 bits spread across PF0, PF1 and PF2, each bit four pixels wide, covering the left half of the screen. The right half repeats or mirrors it.
  • two players, 8-pixel-wide sprites whose shape is one byte each (GRP0, GRP1), plus two one-pixel missiles and a ball

As the beam moves, the TIA turns those registers into a signal. If the program writes nothing, every line comes out the same and a sprite becomes a stripe from top to bottom. To draw a shape, the program must change the registers between lines, for the whole picture.

The numbers

The TIA counts in colour clocks, one per pixel position. A line lasts 228 colour clocks: 68 of horizontal blank and 160 visible. The processor, a 6507 at about 1.19 MHz, does one cycle per three colour clocks. That is 76 cycles per line, only about 22 of them inside the blank. A register write takes 3 cycles, so a line fits a couple of dozen instructions.

The trick: a kernel synchronised to the beam

The loop that runs during the 192 picture lines is called the kernel. Each pass writes the registers for this line, works out the values for the next, then writes to WSYNC, a register that stops the processor until the next line starts. That locks the loop to the television, one pass per line.

Three rules follow from the timing:

  1. Write first, think later. The writes have to happen in the blank at the start of the line. Anything computed for the next line comes after them.
  2. Never go over 76. If one pass takes longer than a line, the WSYNC wait releases on the line after next. Every pass now takes two lines, the picture stretches, and the frame has too many lines for the television to lock on to.
  3. Game logic lives in the blanks. Moving enemies and reading the joystick happen during the vertical blank and overscan.

Some effects write mid-line on purpose. Change the playfield after the left half is drawn and the right half no longer mirrors it. Even a sprite's horizontal position is set by timing: a write to RESP0 puts the sprite wherever the beam is at that moment.

The idea in one line

With no memory for the result, the program is the picture: each piece is produced exactly when it is needed.

The code

LÖVE has a frame buffer, so we pretend it does not. The table tia holds one line's settings. kernel rewrites it before each line, and drawLine plays the television, painting 160 pixels from whatever the registers hold. The numbers match the demo: sprite at x 76, top line 88, each sprite row on two lines.

-- A toy TIA: it holds the settings for ONE line, never a picture.
local tia = { colubk = { 0, 0, 0 }, grp0 = 0, p0x = 76 }

local LINES = 192                 -- visible lines in an NTSC frame
local SCALE = 3                   -- screen pixels per console pixel
local SPRITE = { 0x18, 0x3C, 0x66, 0xC3, 0xC3, 0x66, 0x3C, 0x18 }
local SPRITE_COLOUR = { 1, 0.9, 0.3 }
local spriteY = 88                -- first line of the sprite

local function skyColour(line)
  local t = line / (LINES - 1)
  local shade = 1
  if math.floor(line / 8) % 2 == 1 then shade = 0.85 end
  return { (0.1 + 0.8 * t) * shade, (0.15 + 0.35 * t) * shade, (0.45 - 0.25 * t) * shade }
end

local function bitIsSet(byte, n)  -- n = 7 is the leftmost pixel
  return math.floor(byte / 2 ^ n) % 2 == 1
end

-- The kernel: runs between lines and rewrites the registers.
local function kernel(line)
  tia.colubk = skyColour(line)
  local row = math.floor((line - spriteY) / 2) + 1  -- each row lasts 2 lines
  if row >= 1 and row <= #SPRITE then tia.grp0 = SPRITE[row] else tia.grp0 = 0 end
end

-- The television: read the registers as they are now and paint one line.
local function drawLine(line)
  for x = 0, 159 do
    local c = tia.colubk
    local bit = x - tia.p0x
    if bit >= 0 and bit < 8 and bitIsSet(tia.grp0, 7 - bit) then c = SPRITE_COLOUR end
    love.graphics.setColor(c[1], c[2], c[3])
    love.graphics.rectangle("fill", x * SCALE, line * SCALE, SCALE, SCALE)
  end
end

function love.draw()
  for line = 0, LINES - 1 do
    kernel(line)    -- comment this out and every line repeats the same settings
    drawLine(line)
  end
end

The demo adds the playfield the same way and adds the clock: each write happens at a particular cycle, and a write after the blank only affects pixels the beam has not reached yet.

Pitfalls

  • Thinking before writing. A kernel that computes first pushes its writes into the visible line. The damage is a one-line shear at the edge of a shape, easy to miss.
  • A path that is sometimes slow. On the 6502 family a taken branch costs an extra cycle, and another if it crosses a page boundary. A kernel that overflows on only a few lines gives a picture that shakes, so programmers counted cycles for every path through the loop.
  • Too many lines per frame. A frame that runs long or short can make the picture roll, so the blank periods are timed too, usually with the console's built-in timer.
  • This toy is not an emulator. The real TIA has small delays between a write and its effect, and stores playfield bits in an unusual order. The demo and the Lua ignore both. The Lua also calls rectangle 30,720 times a frame: fine for a toy, wasteful for a game.

In real games

Every 2600 game has a kernel, and most of the console's famous tricks are ways of getting more out of it:

  • Reusing sprites down the screen. Once a sprite has finished its lines, the kernel can move it and change its shape, so two sprites can show a column of objects, as long as no two share a line.
  • Flicker. When more objects share lines than there are sprites, games draw some on one frame and the rest on the next. The 2600 version of Pac-Man is well known for its flickering ghosts.
  • Wide graphics from mid-line writes. A well-known technique for six-digit scores places copies of both sprites side by side and rewrites their shapes while the beam crosses them, giving a 48-pixel-wide image.

The lesson for today

The 76-cycle line became the 16.7 millisecond frame at 60 frames per second, and 8.3 at 120. The rules still hold. Do the work with a deadline first and prepare the next frame afterwards, as engines do when they record the next frame's drawing commands while the graphics card draws this one. Treat the budget as a hard limit: a frame that runs over is a visible hitch. And move work that need not happen now out of the loop, into loading screens, precomputed tables, or spread over several frames.

Takeaways

  • The 2600 had 128 bytes of RAM and no frame buffer. Its graphics chip only describes the current line.
  • Games rewrote the registers before every line in a loop called the kernel, locked to the beam with WSYNC.
  • A line allows 76 cycles, about 22 in the blank, so writes come first and preparation second.
  • A kernel over budget stretches the picture and breaks the frame timing.
  • The modern frame budget is the same problem: deadlines first, heavy work out of the loop.

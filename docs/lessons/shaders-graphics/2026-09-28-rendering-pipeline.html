The rendering pipeline: from three vertices to pixels

Follow one triangle through the GPU: the vertex shader places its corners, the rasteriser finds the covered pixels, and the fragment shader colours each one.

Rotate a sprite by a few degrees and its clean edges turn into little stairs. Move one corner of a textured mesh and the whole texture stretches with it. Neither happens in your fragment shader. Both happen in the steps before it, where the GPU decides which pixels your shader runs on and what it is told about each one.

One triangle, six steps

Last lesson's sentence still holds: a fragment shader is a small function that runs once per pixel and returns a colour. This lesson asks: which pixels?

Everything a GPU draws is made of triangles: a sprite is two, a 3D character thousands. Their corners are vertices, and each carries data: a position, often a colour and a texture coordinate. The route from vertices to finished pixels is the rendering pipeline.

1. The vertex shader: once per corner

The vertex shader is the fragment shader's sibling: a small function that runs once per vertex and returns a position. It moves each corner from the object's own coordinates to where it should appear on screen. Rotating, following the camera and swaying grass happen here.

In GLSL it writes gl_Position, a position in clip space. The GPU divides x, y and z by the fourth component, w, giving normalised device coordinates: in WebGL, x and y run from -1 to 1 across the viewport with y up. Engines hide this: LÖVE lets you work in pixels from the top-left and applies a matrix for you, and Unity and Godot provide helpers.

The vertex shader can also pass extra values down the pipeline, such as a colour or a UV. These are varyings, because they vary across the triangle.

2. Primitive assembly: three dots become a shape

The GPU groups the vertices into triangles. In 3D, triangles facing away from the camera can be thrown out here: back-face culling.

3. Rasterisation: which pixels are inside?

A triangle has sharp edges; a screen is a grid of squares. The rasteriser bridges them with a blunt rule: a pixel belongs to the triangle if the pixel's centre is inside it. Each pixel that passes becomes a fragment, and only fragments get a call to your fragment shader.

The test uses an edge function: (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x) is positive on one side of the edge from a to b and negative on the other. A point is inside when it is on the inner side of all three edges.

4. Interpolation: blending the corner values

The three edge values, divided by the triangle's total, give barycentric weights: how close the pixel is to each corner. Inside the triangle they are never negative, and they always add up to 1. At corner A the weights are (1, 0, 0). At the centre of the triangle they are a third each.

Every varying reaches the fragment shader as a weighted blend of its three corner values. If A is red, B green and C blue, a pixel at the centre receives (0.33, 0.33, 0.33), a dark grey. This is why a texture stretches when you move a corner: the UVs are blended between wherever the corners are.

5 and 6. The fragment shader, then the merger

Your fragment shader runs once per fragment with the interpolated varyings as input and returns a colour. The output merger decides how it lands: the depth test can reject it if something nearer was drawn, and blending can mix it with what is on screen.

Rule of thumb

The vertex shader runs 3 times for a triangle. The fragment shader runs once for every pixel it covers, which can be tens of thousands. Work that gives the same answer across the triangle belongs in the vertex shader or on the CPU.

Try it

This triangle is rasterised by hand inside a fragment shader, with big pixels so you can see each decision. Set Stage to 1 and step forward to 5. Drag the coloured corners, or pick a vertex and use the sliders; on the focused canvas, arrow keys move the chosen corner and 1, 2 and 3 choose it.

At stage 3, drag a corner slowly: a big pixel switches on only when the edge passes its centre dot. Then change Rotation: the vertex shader moves just 3 points, yet every fragment is recomputed. Lower Pixel size and watch the fragment count climb while the vertex count stays at 3.

The code

In LÖVE a vertex shader is a function called position. It receives the vertex position in pixels (top-left origin, y down) and returns it multiplied by transform_projection, which converts it to clip space. The mesh is the demo's default triangle in an 800 by 600 window, with the same corner colours and UVs; the pixel stage is the demo's stage 5.

local angle = 0   -- degrees, the Rotation slider
local shader, mesh

local vertexcode = [[
uniform float u_angle;    // radians
uniform vec2 u_centre;    // rotate around this point, in pixels

vec4 position(mat4 transform_projection, vec4 vertex_position)
{
    vec2 p = vertex_position.xy - u_centre;
    float c = cos(u_angle);
    float s = sin(u_angle);
    p = vec2(p.x * c - p.y * s, p.x * s + p.y * c);
    return transform_projection * vec4(p + u_centre, 0.0, 1.0);
}
]]

local pixelcode = [[
uniform float u_checks;

vec4 effect(vec4 color, Image tex, vec2 texture_coords, vec2 screen_coords)
{
    // color and texture_coords arrive already interpolated
    vec2 cell = floor(texture_coords * u_checks);
    float checker = mod(cell.x + cell.y, 2.0);
    return vec4(color.rgb * (0.6 + 0.4 * checker), 1.0);
}
]]

function love.load()
  shader = love.graphics.newShader(pixelcode, vertexcode)
  -- x, y, u, v, r, g, b, a for each corner
  mesh = love.graphics.newMesh({
    { 160, 480, 0, 0, 1, 0, 0, 1 },   -- A, red
    { 640, 420, 1, 0, 0, 1, 0, 1 },   -- B, green
    { 360, 90, 0, 1, 0, 0, 1, 1 },    -- C, blue
  }, "triangles", "static")
end

function love.draw()
  local w, h = love.graphics.getDimensions()
  shader:send("u_angle", -math.rad(angle))   -- minus: y points down in LÖVE
  shader:send("u_centre", { w / 2, h / 2 })
  shader:send("u_checks", 4.0)
  love.graphics.setShader(shader)
  love.graphics.draw(mesh)   -- 3 vertex calls, one fragment call per covered pixel
  love.graphics.setShader()
end
#ifdef GL_FRAGMENT_PRECISION_HIGH
precision highp float;
#else
precision mediump float;
#endif

uniform vec2 u_resolution;
uniform vec2 u_a;        // vertex shader output for A, in pixels from the bottom-left
uniform vec2 u_b;
uniform vec2 u_c;
uniform float u_cell;    // size of one big demo pixel, in real pixels
uniform float u_stage;
uniform float u_grid;
uniform float u_sel;
uniform float u_dpr;
uniform vec3 u_bg;
uniform vec3 u_ink;
uniform vec3 u_topic;

// Edge function: positive on one side of the line from a to b, negative on the other.
float edge(vec2 a, vec2 b, vec2 p) {
  return (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x);
}

float segDist(vec2 p, vec2 a, vec2 b) {
  vec2 pa = p - a;
  vec2 ba = b - a;
  float h = clamp(dot(pa, ba) / max(dot(ba, ba), 0.0001), 0.0, 1.0);
  return length(pa - ba * h);
}

vec3 vertexDot(vec3 col, vec2 q, vec2 v, vec3 fill, float r, float px) {
  float d = length(q - v);
  col = mix(col, u_ink, 1.0 - smoothstep(r + px, r + 2.0 * px, d));
  return mix(col, fill, 1.0 - smoothstep(r - px, r, d));
}

void main() {
  float k = 1.0 / u_resolution.y;   // work in small numbers: 1.0 = canvas height
  vec2 frag = gl_FragCoord.xy;
  vec2 a = u_a * k;
  vec2 b = u_b * k;
  vec2 c = u_c * k;

  // Rasteriser: which big pixel is this, and is its centre inside all three edges?
  vec2 centre = (floor(frag / u_cell) + 0.5) * u_cell;
  vec2 p = centre * k;
  float area = edge(a, b, c);
  float solid = step(0.0001, abs(area));
  float safeArea = mix(1.0, area, solid);
  float wA = edge(b, c, p) / safeArea;
  float wB = edge(c, a, p) / safeArea;
  float wC = edge(a, b, p) / safeArea;
  float inside = step(0.0, wA) * step(0.0, wB) * step(0.0, wC) * solid;

  // Interpolation: one value per corner, blended by the weights.
  vec3 vcol = wA * vec3(1.0, 0.0, 0.0) + wB * vec3(0.0, 1.0, 0.0) + wC * vec3(0.0, 0.0, 1.0);
  vec2 uv = wA * vec2(0.0, 0.0) + wB * vec2(1.0, 0.0) + wC * vec2(0.0, 1.0);

  // Each stage adds one line.
  vec3 col = u_bg;
  if (u_stage > 2.5) col = mix(col, u_topic, 0.35 * inside);
  if (u_stage > 3.5) col = mix(col, vcol, inside);
  vec2 check = floor(uv * 4.0);
  if (u_stage > 4.5) col = mix(col, vcol * (0.6 + 0.4 * mod(check.x + check.y, 2.0)), inside);

  // Demo only: grid lines and a dot at each big pixel centre.
  float gridOn = u_grid * step(2.5, u_stage) * step(5.0 * u_dpr, u_cell);
  vec2 f = frag - floor(frag / u_cell) * u_cell;
  float gridLine = 1.0 - step(u_dpr, min(f.x, f.y));
  col = mix(col, u_ink, 0.18 * gridLine * gridOn);
  float centreDot = 1.0 - step(1.6 * u_dpr, length(frag - centre));
  col = mix(col, u_ink, centreDot * gridOn * mix(0.3, 0.9, inside));

  // Stage 2: the true edges of the triangle, drawn thin on top.
  vec2 q = frag * k;
  float d = min(segDist(q, a, b), min(segDist(q, b, c), segDist(q, c, a))) / k;
  col = mix(col, u_ink, (1.0 - smoothstep(0.5 * u_dpr, 1.5 * u_dpr, d)) * step(1.5, u_stage));

  // Stage 1: the three positions the vertex shader returned.
  float px = u_dpr * k;
  float r = 6.0 * px;
  col = vertexDot(col, q, a, vec3(1.0, 0.0, 0.0), r + 3.0 * px * (1.0 - step(0.5, abs(u_sel))), px);
  col = vertexDot(col, q, b, vec3(0.0, 1.0, 0.0), r + 3.0 * px * (1.0 - step(0.5, abs(u_sel - 1.0))), px);
  col = vertexDot(col, q, c, vec3(0.0, 0.0, 1.0), r + 3.0 * px * (1.0 - step(0.5, abs(u_sel - 2.0))), px);

  gl_FragColor = vec4(col, 1.0);
}
// Godot 4. Put this in a ShaderMaterial on a ColorRect.
// A ColorRect is a quad: 4 vertices, 2 triangles.
shader_type canvas_item;

uniform float angle = 0.0;        // radians
uniform vec2 pivot = vec2(0.0);   // in the rect's own pixels, e.g. its size / 2
uniform float checks = 4.0;

void vertex() {
    // Once per vertex. VERTEX is in local pixels, 0,0 at the top-left, y down.
    vec2 p = VERTEX - pivot;
    float c = cos(angle);
    float s = sin(angle);
    VERTEX = vec2(p.x * c - p.y * s, p.x * s + p.y * c) + pivot;
}

void fragment() {
    // Once per covered pixel. UV has been interpolated from the corners.
    vec2 cell = floor(UV * checks);
    float checker = mod(cell.x + cell.y, 2.0);
    vec3 col = vec3(UV.x, UV.y, 0.5);
    COLOR = vec4(col * (0.6 + 0.4 * checker), 1.0);
}
// Built-in render pipeline, unlit. Put it on a material and apply it to a Quad.
Shader "GameDevDaily/PipelineSpin"
{
    Properties
    {
        _Angle ("Angle (radians)", Float) = 0
        _Checks ("Checks", Float) = 4
    }
    SubShader
    {
        Tags { "RenderType" = "Opaque" }
        Pass
        {
            CGPROGRAM
            #pragma vertex vert
            #pragma fragment frag
            #include "UnityCG.cginc"

            float _Angle, _Checks;

            struct v2f
            {
                float4 pos : SV_POSITION;
                float2 uv : TEXCOORD0;   // a varying
            };

            v2f vert (appdata_base v)   // once per vertex
            {
                v2f o;
                float c = cos(_Angle);
                float s = sin(_Angle);
                float3 p = v.vertex.xyz;   // object space; the Quad is centred on 0,0
                p.xy = float2(p.x * c - p.y * s, p.x * s + p.y * c);
                o.pos = UnityObjectToClipPos(p);
                o.uv = v.texcoord.xy;
                return o;
            }

            fixed4 frag (v2f i) : SV_Target   // once per covered pixel
            {
                float2 cell = floor(i.uv * _Checks);
                float checker = fmod(cell.x + cell.y, 2.0);
                float3 col = float3(i.uv.x, i.uv.y, 0.5);
                return fixed4(col * (0.6 + 0.4 * checker), 1);
            }
            ENDCG
        }
    }
}

The engine versions draw a quad (two triangles), so the colour comes from the UV instead of vertex colours. Godot's canvas VERTEX has y down, like LÖVE, so a positive angle turns clockwise on screen; in the demo and Unity's object space y is up, so it turns anticlockwise. For URP, use Shader Graph: in the Vertex context, feed a Position node (Object space) through Rotate About Axis (axis 0, 0, 1) into the Position block, and build the checker from the UV node with Multiply, Floor and Modulo.

Pitfalls

  • Thin triangles that flicker. A triangle thinner than a pixel can miss every centre in one frame and hit some in the next. In the demo, drag a corner almost onto the opposite edge and watch the fragment count drop.
  • Interpolated directions get shorter. Blending two unit-length directions gives a shorter one. A normal passed as a varying must be normalised again in the fragment shader before lighting uses it.
  • A triangle that vanishes when its corners are reversed. Back-face culling tells front from back by whether the corners run clockwise or anticlockwise on screen. A hand-built mesh with its corners listed the wrong way round can be culled as a back face.

What it costs

Count the calls. A full-screen quad has 4 vertices and about 2 million fragments at 1080p, and overlapping objects each get their own fragments for the same pixel. On phones the fragment side is usually the bottleneck, so moving a calculation from per-pixel to per-vertex is a cheap win, as long as the value changes linearly across the triangle.

The other extreme costs too. GPUs shade fragments in blocks of 2 by 2 pixels, so a triangle covering one pixel still pays for a whole block. Dense meshes far from the camera waste work this way.

In real games

Every sprite in LÖVE, Godot or Unity reaches the GPU as triangles, usually a quad of two. Unity's sprite import settings have a Mesh Type option: Tight builds a mesh that follows the sprite's outline, so transparent corners are not rasterised; Full Rect uses a plain quad.

Vertex shaders are the usual place for cheap motion the CPU never sees: foliage swaying, flags rippling, water bobbing. Moving a few hundred vertices costs far less than recomputing thousands of pixels.

Takeaways

  • The vertex shader runs once per vertex and returns a position; the fragment shader runs once per covered pixel and returns a colour.
  • The rasteriser keeps a pixel when its centre is inside all three edges of the triangle. That rule causes jagged edges and vanishing thin triangles.
  • Varyings are blended between the corners with barycentric weights that add up to 1.
  • Fragment calls vastly outnumber vertex calls, so per-pixel work is what to watch, especially on phones.

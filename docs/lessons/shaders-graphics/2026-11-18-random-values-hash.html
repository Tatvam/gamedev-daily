Random values from a hash: same cell, same number

A shader has no random() and no memory. A hash turns a cell's coordinates into a number that looks random but is the same every frame.

Grass where every tile is the same green looks like wallpaper. On the CPU you would call math.random per tile and store the result. A shader has no random function and remembers nothing between pixels or frames. It has to compute a random-looking number from what it has: the pixel's position.

A hash: a number that only looks random

A fragment shader is a small function that runs once per pixel: the pixel's position and a few uniforms go in, a colour comes out. Any randomness has to come from those inputs.

A hash function scrambles an input so that nearby inputs give unrelated outputs. It is deterministic: the same input always gives the same output. That is exactly what a shader needs. Cell (3, 5) gets the same value on every frame and every pixel inside it, with nothing stored. math.random, by contrast, is a generator with hidden state, where each call depends on the one before. Pixels run in parallel and cannot share that state.

Step 1: one input per cell

As in the fract lesson, dividing by a cell size and taking floor gives each pixel the number of its cell.

vec2 id = floor(gl_FragCoord.xy / u_cell);   // (0, 0), (1, 0), (2, 0) ...

Every pixel in a cell shares the id, so it shares the random value. Hash the raw pixel position instead and you get film grain rather than tiles.

Step 2: squash, scramble, keep the tail

The classic shader hash is one line, copied so widely that its origin is hard to trace:

float r = fract(sin(dot(id, vec2(12.9898, 78.233))) * 43758.5453);

Read it from the inside out.

  • dot(id, K) squashes two numbers into one: 12.9898 × x + 78.233 × y. The constants are arbitrary uneven numbers, chosen so rows and columns do not line up.
  • sin folds that number into the range −1 to 1. Neighbours now differ, but still follow a wave: stage 3 of the demo shows stripes.
  • * 43758.5453 pushes the sine's fourth and fifth decimal places to the front. Those far digits change wildly from cell to cell.
  • fract keeps only those digits: a number from 0 to just under 1.

Why does that look random? One cell to the right, the sine shifts a little. Multiplied by about 44 thousand, that shift is thousands of units, and only its fractional part survives. With a multiplier of 1 you still see the wave, and small multipliers leave traces of it in the bar chart; try the demo's Multiplier menu.

More than one value per cell

Hashing the same id twice gives the same number twice. For a second value, shift the input: hash(id + vec2(0.5, 0.25)) falls between the integer ids, so it never repeats another cell's value.

Seeds

A seed picks which pattern you get: hash(id + seed * vec2(31.0, 17.0)). Step it several times a second for TV static.

Precision is part of the formula

The hash lives on the last few of the roughly seven digits a 32-bit float keeps. For cell (3, 5), double precision gives 0.810; the same sum rounded to 32-bit floats gives about 0.835. GPUs also compute sin slightly differently, so the pattern can change between devices. Under mediump, a 16-bit float on many phones, it turns into blotches and stripes. The demo asks for highp when the device has it.

Which corner is cell (0, 0)

WebGL's gl_FragCoord starts at the bottom-left with y up, so that is the demo's cell (0, 0). LÖVE's screen_coords start at the top-left with y down; the LÖVE code flips y to match. Godot's canvas UV starts at the top-left, Unity's mesh UVs at the bottom-left. The greys are output as written; in a linear-space project, such as Unity's Linear colour space, they display brighter.

Try it

Step through the Stage menu; each stage adds one line of the shader. On stage 4, set Multiplier to 1, 10, 100, 1000 and then 43758.5453, and watch the stripes break up, in the shader and in the bar chart of the bottom row. Then change the Seed and Cell size: a cell keeps its value until you do. Animate the seed re-rolls the grid six times a second.

The code

In LÖVE the shader is a string with the effect entry point, drawn over the window. The arrow keys double or halve the cell size; space changes the seed.

local cellSize = 24        -- cell size in screen units
local seed = 0             -- whole number: each seed is a different pattern
local shader

local pixelcode = [[
uniform vec2 u_resolution;
uniform float u_cell;
uniform float u_seed;
const vec2 K = vec2(12.9898, 78.233);
const vec2 SEED_STEP = vec2(31.0, 17.0);

float hash(vec2 p)
{
  return fract(sin(dot(p, K)) * 43758.5453);
}

vec4 effect(vec4 color, Image tex, vec2 texture_coords, vec2 screen_coords)
{
  // LÖVE's origin is the top-left: flip y so cell (0, 0) is bottom-left, as in the demo
  vec2 pos = vec2(screen_coords.x, u_resolution.y - screen_coords.y);
  vec2 id = floor(pos / u_cell);
  float r = hash(id + u_seed * SEED_STEP);
  return vec4(vec3(r), 1.0) * color;
}
]]

function love.load()
  shader = love.graphics.newShader(pixelcode)
end

function love.keypressed(key)
  if key == "up" then cellSize = math.min(cellSize * 2, 96) end
  if key == "down" then cellSize = math.max(cellSize / 2, 3) end
  if key == "space" then seed = (seed + 1) % 32 end
end

function love.draw()
  local w, h = love.graphics.getDimensions()
  local pw, ph = love.graphics.getPixelDimensions()
  shader:send("u_resolution", { pw, ph })
  shader:send("u_cell", cellSize * pw / w)   -- in real pixels on high-DPI screens
  shader:send("u_seed", seed)
  love.graphics.setShader(shader)
  love.graphics.rectangle("fill", 0, 0, w, h)
  love.graphics.setShader()
  love.graphics.print("cell " .. cellSize .. "  seed " .. seed, 10, 10)
end
#ifdef GL_FRAGMENT_PRECISION_HIGH
precision highp float;   // the hash needs 32-bit floats
#else
precision mediump float;
#endif

uniform vec2 u_resolution;
uniform float u_cell;    // cell size in device pixels
uniform float u_seed;    // whole number: each seed is a different pattern
uniform float u_mult;    // the big multiplier, 43758.5453 normally
uniform float u_stage;   // 0 raw UV ... 4 final colour

const vec2 K = vec2(12.9898, 78.233);
const vec2 SEED_STEP = vec2(31.0, 17.0);

float hash(vec2 p) {
  return fract(sin(dot(p, K)) * u_mult);
}

void main() {
  vec2 uv = gl_FragCoord.xy / u_resolution;     // 1. 0 to 1 across the canvas
  vec2 id = floor(gl_FragCoord.xy / u_cell);    // 2. which cell: 0, 1, 2 ...
  vec2 p = id + u_seed * SEED_STEP;
  float s = sin(dot(p, K));                     // 3. one number per cell, folded to -1..1
  float r = fract(s * u_mult);                  // 4. keep only the far digits: 0 to 1

  // 5. use it: r picks the shade of grass, a second hash puts a flower in about 1 cell in 5
  vec2 f = fract(gl_FragCoord.xy / u_cell);     // position inside the cell, 0 to 1
  float r2 = hash(p + vec2(0.5, 0.25));
  vec3 col = mix(vec3(0.16, 0.38, 0.16), vec3(0.36, 0.62, 0.24), r);
  float flower = step(r2, 0.2) * (1.0 - smoothstep(0.2, 0.26, length(f - 0.5)));
  col = mix(col, vec3(0.98, 0.84, 0.3), flower);

  if (u_stage < 3.5) col = vec3(r);
  if (u_stage < 2.5) col = vec3(s * 0.5 + 0.5);
  if (u_stage < 1.5) col = vec3(id * u_cell / u_resolution, 0.0);
  if (u_stage < 0.5) col = vec3(uv, 0.0);
  gl_FragColor = vec4(col, 1.0);
}
// Godot 4, a ShaderMaterial on a ColorRect.
shader_type canvas_item;

uniform vec2 rect_size = vec2(640.0, 360.0);  // set this to the ColorRect's size
uniform float cell_size = 24.0;
uniform float seed = 0.0;

float hash(vec2 p) {
    return fract(sin(dot(p, vec2(12.9898, 78.233))) * 43758.5453);
}

void fragment() {
    // UV starts at the top-left with y going down, so cell (0, 0) is the top-left cell.
    vec2 id = floor(UV * rect_size / cell_size);
    float r = hash(id + seed * vec2(31.0, 17.0));
    COLOR = vec4(vec3(r), 1.0);

            }
            ENDCG
        }

}

The highlighted lines are the whole idea: find the cell, hash it. HLSL spells fract as frac. In URP Shader Graph, chain UV, Multiply and Floor into the Random Range node; Unity's documentation for that node shows generated code using this same sine formula. The Godot and Unity versions count cells over the object's UVs, so the grid moves with the object.

Pitfalls

  • Hashing large numbers. A world position of 50 000, or u_time after an hour, has lost the digits the hash lives on, and the pattern turns blocky. Hash small numbers such as cell ids, and wrap seeds and time, as the demo does.
  • Low precision on phones. Under mediump the hash falls apart. Ask for highp, or use a hash without sin, such as Dave Hoskins' "Hash without Sine" family.
  • Trusting the GPU for gameplay. CPU and GPU, or two GPUs, can disagree in the last digits. If gameplay depends on which tile has a flower, decide it on the CPU and send it to the shader.
  • Hashing the same input twice. Then "random size" and "random colour" are the same number. Offset the input for each extra value.
  • Expecting smooth randomness. A hash is white noise: each cell is independent of its neighbours. Clouds and fire need values that change gradually, which is the next lesson.

What it costs

One dot product, one sin, one multiply and one fract: cheap even on a phone. sin is the dearest part, but most GPUs have dedicated hardware for it. The alternative, a noise texture, costs a texture read, memory bandwidth and an asset.

In real games

Per-cell hashes give games small variety: tiles shaded or rotated slightly differently, stars that twinkle at their own rate, grass with its own sway offset, film grain and dithering. The same hash, with the same constants give or take a few digits, appears in The Book of Shaders' chapter on randomness and in Unity's documentation for the Random Range node. Many shader writers now prefer hashes without sin.

Your turn (15 minutes)

Turn the LÖVE program into a star field.

  1. With f = fract(pos / u_cell), draw a disc in each cell: 1.0 - smoothstep(0.03, 0.06, length(f - 0.5)).
  2. Keep it only where hash(id) < 0.15.
  3. Move each star off-centre with two more hashes, offset by vec2(0.5, 0.25) and vec2(0.75, 0.5).
  4. Add uniform float u_time, fed from a timer you add dt to in love.update, and multiply the brightness by 0.6 + 0.4 * sin(u_time * 3.0 + 6.28 * hash(id + vec2(0.25, 0.75))).

You are done when the stars are scattered irregularly, stay put between runs, and twinkle out of step.

Takeaways

  • A shader has no random generator and no memory. A hash computes a random-looking number from its input, the same one every time.
  • Hash the cell id from floor for one value per cell.
  • fract(sin(dot(id, K)) * 43758.5453): squash to one number, fold with sin, push the far digits forward, keep them.
  • It depends on 32-bit precision: use highp, keep inputs small, and do not base gameplay on it.
  • Offset the input for extra values; add a seed for a different pattern.

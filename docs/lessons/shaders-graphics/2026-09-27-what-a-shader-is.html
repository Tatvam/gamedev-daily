What a shader is

A fragment shader is a small function that runs once for every pixel: it takes the pixel's position and returns a colour.

You pasted a water shader from the internet into your project. It shimmers, and you have no idea why. You change one number and the screen goes black.

Shaders feel like magic until someone tells you the one sentence that explains them: a shader is a small function that runs once per pixel and returns a colour.

One function, run for every pixel

In game code you write a loop to touch many things. A graphics card works the other way round: you hand it one small function, and it calls that function for every pixel of the shape being drawn, thousands of calls at the same time.

That function is a fragment shader. A fragment is one candidate pixel of a shape being drawn; for now you can read "fragment" as "pixel". Shaders are written in their own small languages. The one on this page is GLSL, the OpenGL Shading Language, which is also what LÖVE and WebGL use.

What goes in

Each call knows exactly one thing on its own: where its pixel is. In WebGL that is the built-in variable gl_FragCoord.xy, measured in pixels from the bottom-left corner, with y pointing up. The centre of the bottom-left pixel is (0.5, 0.5), not (0, 0).

Everything else arrives as a uniform: a value your game code sends in before drawing, which is the same for every pixel during that draw. The canvas size, the time, and the sliders in the demo below are all uniforms.

What comes out

The function returns one colour as four numbers: red, green, blue and alpha (opacity), each from 0.0 to 1.0. In WebGL you write it to gl_FragColor. vec4(1.0, 0.0, 0.0, 1.0) is solid red. Values outside the range are clamped when stored, so 1.7 shows as 1.0.

What it cannot do

A call cannot see what its neighbours returned, and it keeps nothing for the next frame. That is the price of running thousands of calls in parallel: every effect has to be computed from the position and the uniforms alone.

Building a picture in four lines

  1. Ignore the position and return the slider colour. Every pixel gets the same answer: a flat screen.
  2. Divide the position by the canvas size. The result, uv, runs from 0.0 to 1.0 across the canvas at any resolution. Show uv.x as grey and you see a ramp.
  3. Put uv.x in red and uv.y in green. Now each pixel's colour is its position, the most useful debugging view in shader work.
  4. Multiply by the sliders. Red scales the horizontal ramp, green the vertical one, blue is the same everywhere.

Rule of thumb

When a shader does something you do not understand, output the intermediate value as a colour. A number you can see is a number you can debug.

Try it

Use the Stage menu to walk through the four steps above. Then click or tap anywhere on the canvas, or focus it and use the arrow keys, to move the probe ring. The readout shows what goes into the function for that one pixel and what comes out.

On stage 3 the bottom-left is black and the top-right yellow: y grows upwards. On stage 4, drag Red to zero and watch the probe's red output drop to 0.00.

The code

In LÖVE the shader is a string compiled with love.graphics.newShader. LÖVE writes main for you and calls your effect function, which returns the colour. shader:send sets uniforms, and the shader runs for every pixel drawn while it is active. This is stage 4 of the demo, with the same names and starting values.

One difference matters: LÖVE's screen_coords start at the top-left and y points down, like the rest of LÖVE. The line uv.y = 1.0 - uv.y flips it so the result matches the demo.

local red, green, blue = 1.0, 1.0, 0.4   -- the three sliders
local shader

local pixelcode = [[
uniform vec2 u_resolution;
uniform float u_red;
uniform float u_green;
uniform float u_blue;

vec4 effect(vec4 color, Image tex, vec2 texture_coords, vec2 screen_coords)
{
    vec2 uv = screen_coords / u_resolution;   // 0.0 to 1.0 across the window
    uv.y = 1.0 - uv.y;                        // screen_coords start at the top-left
    return vec4(uv.x * u_red, uv.y * u_green, u_blue, 1.0);
}
]]

function love.load()
  shader = love.graphics.newShader(pixelcode)
end

function love.draw()
  local w, h = love.graphics.getPixelDimensions()   -- screen_coords are in pixels
  shader:send("u_resolution", { w, h })
  shader:send("u_red", red)
  shader:send("u_green", green)
  shader:send("u_blue", blue)
  love.graphics.setShader(shader)
  love.graphics.rectangle("fill", 0, 0, love.graphics.getDimensions())   -- effect() runs for each pixel of this
  love.graphics.setShader()
end
precision mediump float;

uniform vec2 u_resolution;
uniform float u_red;
uniform float u_green;
uniform float u_blue;
uniform float u_stage;
uniform vec2 u_probe;
uniform float u_dpr;

void main() {
  // What goes in: the position of this pixel, in pixels from the bottom-left corner.
  vec2 uv = gl_FragCoord.xy / u_resolution;

  // What comes out: one colour. Each stage replaces the line before it.
  vec3 col = vec3(u_red, u_green, u_blue);
  if (u_stage > 1.5) col = vec3(uv.x);
  if (u_stage > 2.5) col = vec3(uv.x, uv.y, 0.0);
  if (u_stage > 3.5) col = vec3(uv.x * u_red, uv.y * u_green, u_blue);

  // Demo only: a black and white ring around the probed pixel.
  float d = length(gl_FragCoord.xy - u_probe);
  col = mix(col, vec3(0.0), 1.0 - step(1.5 * u_dpr, abs(d - 9.0 * u_dpr)));
  col = mix(col, vec3(1.0), 1.0 - step(1.0 * u_dpr, abs(d - 7.0 * u_dpr)));

  gl_FragColor = vec4(col, 1.0);
}
// Godot 4. Put this in a ShaderMaterial on a ColorRect.
shader_type canvas_item;

uniform float u_red : hint_range(0.0, 1.0) = 1.0;
uniform float u_green : hint_range(0.0, 1.0) = 1.0;
uniform float u_blue : hint_range(0.0, 1.0) = 0.4;

void fragment() {
    // UV is 0 to 1 across the rectangle, with 0,0 at the top-left.
    vec2 uv = vec2(UV.x, 1.0 - UV.y);
    COLOR = vec4(uv.x * u_red, uv.y * u_green, u_blue, 1.0);
}
// Built-in render pipeline, unlit. Put it on a material and apply it to a Quad.
Shader "GameDevDaily/FirstShader"
{
    Properties
    {
        _Red ("Red", Range(0, 1)) = 1
        _Green ("Green", Range(0, 1)) = 1
        _Blue ("Blue", Range(0, 1)) = 0.4
    }
    SubShader
    {
        Tags { "RenderType" = "Opaque" }
        Pass
        {
            CGPROGRAM
            #pragma vertex vert
            #pragma fragment frag
            #include "UnityCG.cginc"

            float _Red, _Green, _Blue;

            struct v2f
            {
                float4 pos : SV_POSITION;
                float2 uv : TEXCOORD0;
            };

            v2f vert (appdata_base v)
            {
                v2f o;
                o.pos = UnityObjectToClipPos(v.vertex);
                o.uv = v.texcoord.xy;   // 0,0 is the bottom-left of the quad
                return o;
            }

            fixed4 frag (v2f i) : SV_Target
            {
                return fixed4(i.uv.x * _Red, i.uv.y * _Green, _Blue, 1);
            }
            ENDCG
        }
    }
}

The engine versions use the mesh's own UVs instead of the screen position, because they usually draw on an object. Godot's canvas UV starts at the top-left, so it is flipped; Unity's starts at the bottom-left, like WebGL. For URP, build it in an Unlit Shader Graph: UV node into Split, multiply R and G by Red and Green properties, join them with a Blue property in a Combine node, and connect that to Base Color.

Pitfalls

  • Writing 1 instead of 1.0. GLSL ES 1.0, used by WebGL 1, does not convert integers to floats for you. vec3(1, 0, 0) works because constructors convert, but uv.x * 2 is a compile error. Give every float a decimal point and the problem never comes up.
  • Forgetting which corner is zero. WebGL and Unity UVs put 0,0 at the bottom-left. LÖVE's screen_coords and Godot's canvas UV put it at the top-left. An effect that appears upside down after porting nearly always comes from this.
  • Sending a uniform the shader does not use. The compiler removes unused uniforms, and LÖVE's shader:send then raises an error because the name no longer exists. Comment out the send while you experiment.
  • Expecting 0.5 to look half as bright. The numbers you return go to the screen as they are, and screens do not show them as a straight line of light. In a Unity project set to Linear colour space the output is also converted before display, so the same shader looks lighter there than on this page. The gamma and linear colour lesson later in this topic covers why.

What it costs

The cost of a fragment shader is pixels drawn times work per pixel. A 1920 by 1080 screen has about 2.07 million pixels, so a full-screen shader at 60 frames per second runs about 124 million times a second. The shader on this page does a divide and a few multiplies per pixel, which any GPU, including a phone's, handles easily.

Loops, many texture reads and long chains of maths all get multiplied by those millions. Phones are usually limited by how many pixels they can fill, and their screens often have more pixels than a desktop monitor, so full-screen effects are the first suspect when a mobile game runs slowly.

In real games

Everything a modern engine draws goes through shaders. In Godot a ShaderMaterial lets you write your own fragment() function, as shown above. In Unity every material points at a shader, written by hand or built in Shader Graph.

The site Shadertoy is built around exactly the model in this lesson: one full-screen fragment shader that receives the resolution, time and mouse as uniforms and returns a colour for every pixel.

Your turn (15 minutes)

Put the Lua version into a new LÖVE project and run it. Then change the shader, one line at a time, so that:

  1. the gradient runs from top to bottom instead of left to right in the red channel (swap uv.x for uv.y),
  2. the left half of the window is one colour and the right half another (hint: uv.x > 0.5 in an if),
  3. the blue channel follows the mouse: send love.mouse.getX() / love.graphics.getWidth() as u_blue.

You are done when all three work and you can say, for each one, what goes in and what comes out.

Takeaways

  • A fragment shader is a function that runs once per pixel and returns one colour.
  • What goes in is the pixel's position plus uniforms, values that are the same for every pixel in a draw.
  • Pixels cannot see each other's results and nothing is remembered between frames.
  • Dividing the position by the resolution gives UVs from 0 to 1, and showing them as colour is the first debugging tool to reach for.
  • The cost is pixels times work per pixel, which matters most on high-resolution phone screens.

Variable jump height: hold for high, tap for low

How ending a jump's rise early when the button is released lets players choose the height of every jump, and how to tune and code it.

A small spike sits on the floor and a row of spikes hangs from the ceiling just above it. You only need a little hop, but every jump in this game is the same full leap, so you clear the floor spike and fly straight into the ceiling. The game gave you one jump and the level asked for two.

One button, many heights

With a fixed jump, pressing the button starts the same arc every time. The player chooses only when to jump, never how high. Jumps are easy to predict, but cannot adapt to what is ahead.

With variable jump height, the jump keeps rising while the button is held and ends its rise early when the button is let go. A quick tap gives a low hop, a long hold gives the full jump, and everything in between is available. The player now steers the height of each jump with their thumb.

How the rise is cut short

Two methods are common. Both take off at full speed and differ only in what happens on release.

  • Release gravity. While the character is rising and the button is up, multiply gravity by a number above 1, the release gravity multiplier. The upward speed drains faster, so the top of the arc comes sooner and lower. This lesson's demo and code use this method.
  • Velocity cut. On the frame the button is released, if the character is still rising, multiply its upward speed once by a number below 1, such as 0.5. The arc bends down at once.

Release gravity gives a softer, rounded top. A velocity cut gives a sharper one. Neither is correct; try both.

Starting points to tune

For release gravity, a multiplier of about 2 to 4 is a common range; this demo starts at 3. For a velocity cut, keeping about half the upward speed is a common start. Then test the shortest tap you can make: the lowest hop should be clearly lower than the full jump, often around a third to a half of its height, and still high enough to clear the smallest obstacle in your levels. These are starting points, not rules.

What the player feels

Without it, every jump is a commitment to one shape, and low obstacles under a ceiling feel unfair. With it, taps feel quick and light, holds feel strong, and the player senses that the character answers how they press, not only when.

Try it

The runner never stops. Tall pillars need a full jump, and low spikes under a spiked ceiling need a small hop. Play a few with variable jump height off: every jump is full height, so the ceilings cannot be passed. Then switch it on, hold for pillars and tap for ceilings.

Now move the release gravity slider. At ×1 letting go changes nothing, and the toggle might as well be off. Higher values make taps shorter. The graph at the top draws your last jump against a full one, so you can see the moment you let go bend the arc.

The code

This is the demo's runner in LÖVE, with the same numbers. Height y is measured upward from the ground and obstacles are left out. The marked lines are the technique.

local RUN_SPEED = 220        -- pixels per second, the runner never stops
local GRAVITY = 2200         -- pixels per second squared
local JUMP_SPEED = 700       -- pixels per second at take-off
local VARIABLE_JUMP = true   -- the demo's toggle
local RELEASE_GRAVITY = 3    -- the demo's slider: gravity multiplier after letting go

local player = { x = 0, y = 0, vy = 0, grounded = true }
local jumpHeld = false       -- true from take-off until the button comes up

local function isJumpKey(key)
  return key == "space" or key == "w" or key == "up"
end

function love.keypressed(key)
  if isJumpKey(key) and player.grounded then
    player.vy = JUMP_SPEED
    player.grounded = false
    jumpHeld = true
  end
end

function love.keyreleased(key)
  if isJumpKey(key) then
    jumpHeld = false           -- pressing again in the air does not undo this
  end
end

function love.update(dt)
  player.x = player.x + RUN_SPEED * dt
  if not player.grounded then
    local g = GRAVITY
    if VARIABLE_JUMP and player.vy > 0 and not jumpHeld then
      g = GRAVITY * RELEASE_GRAVITY  -- let go while rising: the rise ends sooner
    end
    player.vy = player.vy - g * dt
    player.y = player.y + player.vy * dt
    if player.y <= 0 then
      player.y, player.vy, player.grounded = 0, 0, true  -- landed
    end
  end
end

The check player.vy > 0 keeps the extra gravity to the rise. Once the character starts falling, normal gravity takes over, so a tap and a hold fall the same way. Making the fall itself faster is a separate choice, covered in the next lesson.

To try a velocity cut instead, drop the extra gravity and change the release handler:

function love.keyreleased(key)
  if isJumpKey(key) and jumpHeld and player.vy > 0 then
    player.vy = player.vy * 0.5   -- keep half the upward speed, once
  end
  if isJumpKey(key) then jumpHeld = false end
end

Pitfalls

  • Letting a second press restore the jump. If you test "is the button down right now" every frame, a player can release and press again in the air to get normal gravity back. Clear a flag on release and only set it on take-off, as above.
  • Cutting upward motion that was not a jump. A spring, a stomp bounce or a knock-back also moves the character up with the button released. These usually should not be cut, another reason to track jumpHeld instead of reading the button.
  • A shortest hop that is too short or too tall. A quick natural tap should still clear the smallest thing you ask players to hop over. If it is nearly full height, the feature is invisible.
  • Forgetting buffered and coyote jumps. A jump fired from the buffer may start after the player already let go. Check the button when the jump fires and start it already released if it is up, so an early tap gives a hop.
  • Levels that never ask for it. If every obstacle wants a full jump, players never learn that holding matters. Put a low ceiling or a small gap early, where a hop is the clear answer.

When not to use it. Some games are built on committed jumps, where the challenge is choosing when to leave the ground and then living with the arc. A fixed jump is easier to read and plan, which suits deliberate action and puzzle games where exact heights matter. It also frees the button for a "hold to charge" move.

In real games

In Super Mario Bros. (1985), holding the jump button longer makes Mario jump higher, and many later platformers follow this pattern, including Hollow Knight and Celeste. I have not checked which method each of these uses in code, so none is claimed here.

The original Castlevania (1986) is a well-known example of the opposite choice: a fixed jump arc that cannot be changed once it starts, which tends to be described as part of its deliberate, heavy feel.

Your turn (15 minutes)

In your own platformer, add jumpHeld and release gravity as above, and bind two keys that raise or lower the multiplier by 0.5 while you play.

Build one obstacle that needs a full jump and one low ceiling that needs a hop. Try the multiplier at 1, 2, 3 and 5. At each value, note your quickest tap's height and whether both obstacles can be cleared without thinking. You are done when you have picked a value and written one sentence on why.

Takeaways

  • Variable jump height lets the player choose the height of each jump by how long they hold the button.
  • Start every jump at full speed, then end the rise early on release, either with extra gravity while rising or a one-off cut to the upward speed.
  • Track a flag set on take-off and cleared on release, so a second press or a spring bounce does not get mixed up with the jump.
  • A release gravity of about 3, or keeping half the speed, is a common start. Tune it so the quickest tap still clears your smallest obstacle.
  • Fixed jumps are a valid choice for games about commitment and planning.

Corner correction: sliding past the edge you barely hit

How quietly nudging a rising player sideways around a ceiling corner they clipped by a few pixels saves jumps that should have worked.

You run at a narrow gap in the ceiling, jump, and stop dead in mid-air. The corner of your character's head caught the edge of the gap by two pixels. On screen it looked like you were through. The game was right by the numbers and wrong by the player.

Why near misses happen

Most 2D games test collisions with a hitbox: an invisible rectangle around the character. The test is exact: overlap a wall by a fraction of a pixel and the move is blocked.

Players do not see that precisely. They judge by eye, mid-jump, while the character moves several pixels per frame. Take the demo below: the player is 20 pixels wide and the gap is 24 pixels wide, so the player's centre must be inside a 4 pixel window when the head reaches the ceiling. Running at 160 pixels per second, the player crosses 4 pixels in 25 milliseconds, about one and a half frames at 60 frames per second. Almost every running jump will clip a corner.

When it happens, the player gets a bonk: upward speed drops to zero and the character falls back down. A bonk from a large overlap feels deserved; one from two pixels feels like cheating.

The fix: slide around small overlaps

Corner correction means that when a rising character would hit a ceiling, the game first checks whether shifting it sideways by a few pixels would clear the obstacle. If a small shift works, the character is moved over and keeps rising. If none does, it bonks as usual.

The limit on that shift is the forgiven overlap: the largest number of pixels the game will slide the character. The test tries 1 pixel left, 1 pixel right, 2 pixels left, and so on up to the limit, and takes the first spot that is free. Trying the smallest shift first keeps the correction as small as possible.

Rules that keep it honest

  • Only while moving up. The bonk is the problem being solved. Sliding a falling character sideways is a different feature with different risks.
  • Only small overlaps. The limit should be a fraction of the character's width, so a head that clearly hit the ceiling still bonks.
  • The new spot must be free. Test the shifted box against everything solid before moving it, or the fix will push the character into another wall.

Starting points to tune

For a character 16 to 20 pixels wide, try a limit of 2 to 4 pixels, about a fifth of the width or less. Scale it with your art: a 64 pixel character might take 8 to 12. Shift by whole pixels in pixel-art games. These are places to start, not rules.

The same idea is commonly applied sideways: a character dashing into the lip of a ledge a few pixels too high can be popped up onto it.

What the player feels

Without correction, near misses end in a sudden stop that reads as unfair, and players learn to slow down and line up every gap. With it, the player simply gets through. Done well, nobody notices it at all: the shift is a few pixels in one frame, too small to see at full speed.

The code

This is the demo's vertical movement in LÖVE, with the same sizes and numbers. Running and side walls are left out, and the demo runs this at a fixed 60 steps per second. The player starts at x = 205, 3 pixels past the window: it bonks with the correction off and slides through with it on. The marked lines are the technique.

local SIZE = 20             -- the player is a 20 by 20 box
local CORRECTION = 4        -- forgiven overlap in pixels, the demo's slider
local CORRECTION_ON = true  -- the demo's toggle
local GRAVITY, JUMP_SPEED = 1875, 750   -- 150 px high, 0.4 s to the top

-- Boxes: x, y is the bottom-left corner, y measured up from the ground.
local solids = {
  { x = 0,   y = 100, w = 188, h = 16 },  -- ceiling left of the gap
  { x = 212, y = 100, w = 188, h = 16 },  -- ceiling right of the gap
}
local player = { x = 205, y = 0, vy = 0 }  -- x is the centre, y the feet

local function hitAt(px, py)
  for _, s in ipairs(solids) do
    if px + SIZE / 2 > s.x and px - SIZE / 2 < s.x + s.w
      and py + SIZE > s.y and py < s.y + s.h then
      return s
    end
  end
  return nil
end

local function moveUp(p, newY)
  local hit = hitAt(p.x, newY)
  if not hit then
    p.y = newY
    return
  end
  if CORRECTION_ON then
    for d = 1, CORRECTION do
      if not hitAt(p.x - d, newY) then p.x = p.x - d; p.y = newY; return end
      if not hitAt(p.x + d, newY) then p.x = p.x + d; p.y = newY; return end
    end
  end
  p.y = hit.y - SIZE  -- no small slide clears it: bonk
  p.vy = 0
end

local function moveDown(p, newY)
  local hit = hitAt(p.x, newY)
  if newY <= 0 then newY = 0; p.vy = 0
  elseif hit then newY = hit.y + hit.h; p.vy = 0 end
  p.y = newY
end

function love.keypressed(key)
  if key == "space" and player.y == 0 then player.vy = JUMP_SPEED end
end

function love.update(dt)
  local oldVy = player.vy
  player.vy = math.max(player.vy - GRAVITY * dt, -900)
  local newY = player.y + (oldVy + player.vy) * 0.5 * dt
  if newY > player.y then moveUp(player, newY) else moveDown(player, newY) end
end

Notice that moveUp tests the shifted box with the same hitAt it uses for the bonk. That is what makes "the new spot must be free" automatic, whatever else is in the level.

In a full game, move horizontally first and vertically second in each step, as the demo does, so the gap's walls hold a running player in place while it rises through.

Pitfalls

  • A limit that is too large. At half the character's width, players slip through gaps you meant to block and visibly jump sideways around corners they plainly hit. That reads as a bug. Try 10 in the demo and watch for the jump.
  • Sliding into danger. The shifted spot may be free of walls but full of spikes. Either test hazards too, or skip the slide when the new spot would hurt.
  • Correcting against one-way platforms. Platforms you can jump up through should never cause a bonk, so they should not trigger a correction either. Leave them out of the upward test.
  • Pushing against the player's input. A slide away from the direction the player is holding can feel odd. Some games skip that side or prefer the side the player is moving toward. Test both in your own game.

When not to use it. If exact clearance is the puzzle, for example a gap that is deliberately one pixel too narrow until the character crouches, correction removes the rule the player was meant to learn. In a slow game with wide gaps the problem may never come up.

In real games

Maddy Thorson, one of Celeste's developers, lists jump corner correction among the game's forgiveness mechanics in a 2020 thread of design notes, later collected as an article called "Celeste & Forgiveness": if you bump your head on a corner, the game tries to move you sideways around it. I found this through search results and press write-ups of the thread; I could not open the original in this session.

Many 3D games get a similar effect from the shape of the collider. Unity's built-in CharacterController, for example, is a capsule, and a rounded top tends to glance off an edge instead of stopping dead on it.

Takeaways

  • Exact hitboxes plus fast movement turn narrow gaps into frame-perfect jumps, and small overlaps feel unfair.
  • Corner correction tries small sideways shifts, smallest first, when a rising character would hit a ceiling.
  • Each pixel of forgiven overlap widens the window by a pixel on both sides.
  • Keep the limit to about a fifth of the character's width, apply it only while rising, and test that the new spot is safe.
  • Leave it out where exact clearance is part of the challenge.

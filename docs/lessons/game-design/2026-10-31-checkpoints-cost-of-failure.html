Checkpoints and the cost of failure

How checkpoint spacing and respawn delay set the real price of a death, why long stretches between checkpoints compound, and how to tune both.

You die at the last jump of a hard section. The screen fades, a loading icon spins, and you walk back through three rooms you have already beaten to try that one jump again. On the fourth time you put the controller down. The jump was not the problem. The price of missing it was.

Every death has a price, paid in time

The cost of failure is everything a player loses when they fail. In most action games the biggest part is time, and it comes in two pieces:

  • Replay time: the stretch between the last checkpoint (the place the game puts you back after a death) and the spot where you died, which you have to play again.
  • Dead time: the death animation, fade, loading and any message before you can move again. You do nothing during it.

Lost items or currency can add a third piece; this lesson sticks to time. The price of one death is roughly replay time + dead time, multiplied by the number of deaths.

Why long gaps hurt more than they look

Doubling the distance between checkpoints does not just double the cost, because a stretch must be cleared in one go. A player who clears each obstacle 80 percent of the time clears a stretch of 2 in one go 64 percent of the time, a stretch of 4 only 41 percent, and a stretch of 8 only 17 percent. And each failure sends them back further.

The numbers use a standard result: the average number of tries to get k successes in a row, at chance p each, is (1 − pk) / ((1 − p) pk). Only its shape matters here.

What the player feels

When failure is cheap, a death works like a quick lesson: try, see what went wrong, try again a second later. Players experiment, and "one more go" comes easily. When failure is expensive, the first deaths raise the tension, which can be exciting. After that, each retry is mostly replay, attention goes to parts already mastered instead of the part being failed, and frustration tends to start.

Dead time tends to feel worse than replay time, second for second, because there is nothing to do.

Starting points to tune

For a game built on many attempts, aim for a respawn delay of 0.3 to 1 second and a replay of under 30 seconds before the hard part. For a slower game where each attempt is a big event, a replay of a minute or two can work if that part is quick or still interesting. Past 2 or 3 seconds of dead time, the delay itself starts to feel like a punishment. These are starting points to tune, not rules.

Spacing is not the only lever. Put each checkpoint right before a new challenge, and make the replay fast: skip cutscenes already seen and leave opened doors open.

The code

This is the demo's checkpoint and respawn logic in LÖVE, with the same numbers. Running, jumping and collisions are left as a stub called movePlayer; put your own movement there and have it return true when the player hits something deadly. The marked lines are the two costs: where you go back to, and how long you wait.

local RUN_SPEED = 150         -- pixels per second
local CHECKPOINT_EVERY = 4    -- obstacles between checkpoints
local RESPAWN_DELAY = 1.0     -- seconds of dead time
local START_X, FIRST_OBSTACLE, OBSTACLE_GAP = 60, 300, 230

local checkpoints = { START_X }
for i = 2, 16 do
  if (i - 1) % CHECKPOINT_EVERY == 0 then
    local obstacleX = FIRST_OBSTACLE + (i - 1) * OBSTACLE_GAP
    table.insert(checkpoints, obstacleX - 110)  -- just before it
  end
end

local player = { x = START_X, checkpoint = 1, dead = false, wait = 0 }
local furthest = START_X
local stats = { new = 0, replay = 0, waiting = 0, deaths = 0 }

local function movePlayer(p, dt)
  p.x = p.x + RUN_SPEED * dt  -- replace with your run, jump and collisions
  return false                -- true when the player touched a hazard
end

function love.update(dt)
  if player.dead then
    stats.waiting = stats.waiting + dt
    player.wait = player.wait - dt
    if player.wait <= 0 then
      player.dead = false
      player.x = checkpoints[player.checkpoint]
    end
    return
  end
  local hit = movePlayer(player, dt)
  local nextX = checkpoints[player.checkpoint + 1]
  if nextX and player.x >= nextX then player.checkpoint = player.checkpoint + 1 end
  if player.x > furthest then
    furthest = player.x
    stats.new = stats.new + dt
  else
    stats.replay = stats.replay + dt  -- ground already beaten
  end
  if hit then
    player.dead = true
    player.wait = RESPAWN_DELAY
    stats.deaths = stats.deaths + 1
  end
end

stats.replay + stats.waiting is the time lost to retries, the number the demo reports. Keep it as a debug readout in your real game.

Pitfalls

  • Tuning with your own skill. You rarely die in your own level. A new player dies far more, and because the cost compounds, a stretch that feels fine to you can be miserable for them. Watch someone else play.
  • Hidden dead time. A half-second fade, a death animation and a short load add up to seconds nobody decided on. Measure the time from death to control.
  • Checkpoints before the walk, not the fight. A checkpoint at the start of a long corridor that leads to a boss puts the whole corridor in the replay. Move it to the door.
  • Respawning into danger. If an enemy or hazard can reach the player in the first second after a respawn, one mistake becomes two deaths.
  • Saving a broken state. A checkpoint that saves the player with almost no health can trap them. Restore a fair state on respawn.

When not to make failure cheap. Some games are about the stakes. In a roguelike, losing the run is the point; in survival horror, the fear of losing progress is part of the fear; in an arcade score chase, a full restart is the challenge. Some players also argue that a long walk back gives time to calm down and plan. And when retrying is free, players tend to brute-force a section rather than learn it, so the win can feel smaller.

In real games

Celeste is built from short screens, and a death puts the player back at the start of the current screen almost immediately, so each screen works as a checkpoint. It also keeps a visible death count. Super Meat Boy uses short levels with a near-instant restart, and when a level is finished it replays every attempt at once, turning the pile of failures into a show.

Dark Souls goes the other way. Bonfires are spaced far apart, death costs the souls the player was carrying, and they get one chance to recover them by reaching the spot where they died. The walk back is part of its tension, and players still argue about it.

Takeaways

  • The price of a death is the replay time plus the dead time, multiplied by how often players die.
  • Long gaps between checkpoints compound: the stretch is harder to clear in one go, and each failure sends the player further back.
  • Dead time feels worse than replay time. Keep it short in any game built on many attempts.
  • Place checkpoints just before new challenges, make the replay fast, and respawn in a fair, safe state.
  • High stakes are a valid choice in some genres. Choose them on purpose, not by accident.

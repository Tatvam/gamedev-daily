Introduce, develop, twist, conclude

How to build a level around one idea in four steps borrowed from kishotenketsu, and why the order of those steps decides whether it teaches or punishes.

You add a moving platform to your game. It appears once, carries the player across a gap, and is never seen again. Or the opposite happens: the first moving platform the player meets hangs over spikes, and they die before they learn how it moves.

Both waste a good idea. This lesson is about giving one idea a whole level, in an order that lets the player grow with it.

One idea, four steps

Kishotenketsu (kishōtenketsu) is a four-part structure for short stories and poems. It is commonly traced to four-line Chinese poetry and is well known from Japanese four-panel comic strips. The parts are ki (introduction), shō (development), ten (twist) and ketsu (conclusion). The twist does not have to be a conflict. It is an unexpected turn that makes you see the first two parts differently.

Level designers borrow the shape and apply it to a gimmick: the one mechanic or object a level is built around, such as a moving platform, a switch block or a wind current.

  1. Introduce. Show the gimmick in its simplest form, where failure is cheap. The player learns what it does.
  2. Develop. Same rule, more demand: two of them, tighter timing, real danger. The player learns to use it well.
  3. Twist. Use the same gimmick in a way the player did not expect, so it means something new. The player learns what else it can do.
  4. Conclude. A last challenge that combines what came before, with nothing new to learn. The player shows they have mastered it.

Why the order matters

A useful way to check a sequence is to count, for every room, how many skills it asks for that no earlier room did. Call that its new skill count. In the intended order the counts are 1, 1, 1, 0: each room teaches one thing, and the last only tests. Put the twist first and its count becomes 2. The player has to learn to ride and to launch at once, over spikes, with nothing to build on. Put the conclusion first and it is 3, and the three rooms after it feel like a step backwards.

The count is a rough tool, since two small skills can be easier than one big one. But a room with a count above 1 is where to look first when testers struggle.

Making the twist fair

A good twist feels surprising and obvious at once. In the demo, every platform carries you, and hopping between two in the develop room lets you feel that momentum. The twist asks you to use it on purpose: jump while the platform moves toward the gap, and its speed adds to yours. Plain jumps cover about 92 pixels. With the platform's 140 pixels per second added, the same jump covers about 170, which is what the 120 pixel gap needs.

If the twist relies on something the player has never seen, it is not a twist. It is a second gimmick, and it deserves its own introduction.

Starting numbers

These are starting points to tune, not rules. In a short action level, each step commonly takes 15 seconds to a minute. A failure in the introduction should cost only a few seconds. The conclusion is usually a little harder than the develop step and shorter than you expect: a victory lap, not a final exam.

Rule of thumb

Give each room at most one new skill, make the twist a new use of something the player already holds, and end with a room that asks for nothing new.

The code

First, the order check from the strip. Each room lists the skills it asks for, and the function counts the new ones in each position.

-- The skills each room asks for. Same data as the demo.
local ROOMS = {
  introduce = { "ride" },
  develop   = { "ride", "hop" },
  twist     = { "ride", "launch" },
  conclude  = { "ride", "hop", "launch" },
}

-- For each position, how many skills that no earlier room asked for?
local function newSkillsPerRoom(order)
  local seen, counts = {}, {}
  for i, name in ipairs(order) do
    local n = 0
    for _, skill in ipairs(ROOMS[name]) do
      if not seen[skill] then seen[skill] = true; n = n + 1 end
    end
    counts[i] = n
  end
  return counts
end

print(table.concat(newSkillsPerRoom({ "introduce", "develop", "twist", "conclude" }), ", "))
--> 1, 1, 1, 0
print(table.concat(newSkillsPerRoom({ "twist", "introduce", "develop", "conclude" }), ", "))
--> 2, 0, 1, 0

Second, the mechanic behind the twist. The platform slides back and forth, carries the player while they stand on it, and hands its speed to them when they leave it. Collision with solid ground is left as your own function.

local GRAVITY, JUMP, RUN, PW, PH = 1800, 520, 160, 14, 20
local plat = { a = 124, b = 330, y = 170, w = 60, speed = 140, phase = 0, x = 124, dx = 0, vx = 0 }
local player = { x = 20, y = 150, vy = 0, carry = 0, on = nil, inputX = 0 }
local roomTime = 0

local function tri(u) return 1 - math.abs(u % 2 - 1) end  -- 0, 1, 0, 1 ...

local function movePlatform(p, t, dt)
  local newX = p.a + (p.b - p.a) * tri(t * p.speed / (p.b - p.a) + p.phase)
  p.dx, p.vx, p.x = newX - p.x, (newX - p.x) / dt, newX
end

function love.keypressed(key)
  if key == "space" and (player.on or onSolidGround(player)) then
    player.vy = -JUMP
    if player.on then player.carry = player.on.vx end  -- the twist: keep its speed
    player.on = nil
  end
end

function love.update(dt)
  roomTime = roomTime + dt
  movePlatform(plat, roomTime, dt)
  local wasOn = player.on
  if wasOn then player.x = player.x + wasOn.dx end         -- ride along
  local air = 0
  if not wasOn then air = player.carry end
  player.x = player.x + (player.inputX * RUN + air) * dt
  local prevBottom = player.y + PH
  player.vy = player.vy + GRAVITY * dt
  player.y = player.y + player.vy * dt
  player.on = nil
  if player.vy >= 0 and prevBottom <= plat.y + 0.5 and player.y + PH >= plat.y
     and player.x < plat.x + plat.w and player.x + PW > plat.x then
    player.y, player.vy, player.on, player.carry = plat.y - PH, 0, plat, 0
  elseif wasOn then
    player.carry = wasOn.vx                                  -- walked off the edge
  end
  collideWithGround(player)  -- your code: on landing, set player.carry = 0
end

Pitfalls

  • A twist that is really a new mechanic. If the third room needs something the first two never showed, players feel tricked. Plant the twist earlier, even if only as something they notice by accident.
  • Stopping after the develop step. A level that only gets harder tends to feel like a list. The twist is what players remember.
  • A conclusion that is a wall. Ending on the hardest moment of the game turns mastery into frustration. Commonly the conclusion is a little harder than the develop step, not far harder.
  • A long introduction. Experienced players get bored. Keep it short.
  • Every level in exactly this shape. After a few levels, players start expecting the twist in room three. Vary the length of each step, merge steps, or hide the twist in an optional route.

When not to use it

The structure suits short, hand-made levels with one clear gimmick, which is why it fits platformers and puzzle games. It fits less well in open worlds, in systemic games where players mix tools freely, and in procedurally generated levels where you cannot control the order. Late in a game, when players already know every mechanic, a level about how several of them combine can be better than a level about one.

In real games

The best-known link between kishotenketsu and level design is Koichi Hayashida, director of Super Mario 3D Land (2011). Reports of an interview he gave to Gamasutra (now Game Developer) say he described the structure as an inspiration for building levels around one core idea. I could not open the interview itself, so treat the wording as second hand.

Mark Brown's Game Maker's Toolkit video on Super Mario 3D World (2015) breaks many of that game's levels into four steps: introduce a gimmick, develop it, twist it and conclude. Not every level in those games follows the pattern neatly.

Your turn (15 minutes)

Pick one gimmick in your game that appears only once. On paper, write four rooms for it: introduce, develop, twist, conclude. Next to each room, list the skills it asks for, and count the new ones in each position as the code does.

You are done when the counts read 1, 1, 1, 0 (or close), the first room is safe to fail in, and you can point to the earlier room where the twist was hinted.

Takeaways

  • Build a level around one gimmick, in four steps: introduce, develop, twist, conclude.
  • Each room should ask for at most one new skill. Counting them shows why order matters.
  • A fair twist is a new use of something the player already knows, hinted earlier.
  • The conclusion combines and confirms. It adds nothing new.
  • Use the shape as a habit, not a formula, or players will start to predict it.

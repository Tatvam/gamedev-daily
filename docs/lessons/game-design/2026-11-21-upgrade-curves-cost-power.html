Upgrade curves: how cost and power set the wait between upgrades

How linear, exponential and diminishing curves for upgrade cost and power decide whether the wait between upgrades stays steady, stretches or collapses.

For the first half hour of an upgrade game, something new arrives every few seconds. Then each upgrade takes minutes, and the game seems to stop. Or the opposite happens: by upgrade 20 you buy something on every tap and none of it feels earned. Both came from two curves that were tuned on their own.

The player feels the wait, not the price

An upgrade game has two curves. The cost curve says what upgrade number n costs. The power curve says how fast the player earns after n upgrades: gold per tap, gold per second, damage per hit. The player never feels either curve alone. They feel the gap between them:

wait for the next upgrade = cost ÷ power

A price of a million gold feels like ten seconds if you earn a hundred thousand a second. Big numbers are decoration; the wait is the rhythm of the game.

Three shapes

Each curve usually takes one of three shapes. A linear curve adds the same amount every level. An exponential curve multiplies by the same factor every level: "15 percent growth" means each value is 1.15 times the one before. A diminishing curve adds less every level. In this lesson it grows with the square root of the level, so going from level 1 to 4 adds as much as going from 4 to 9.

The ratio decides the rhythm

What matters is which curve grows faster. The diagram below shows the wait for the first 14 upgrades under three pairings.

Some rules you can check with a calculator:

  • Both exponential. Each wait is (1 + cost growth) ÷ (1 + power growth) times the one before. With cost at 20 percent and power at 15 percent that is 1.2 ÷ 1.15, about 1.043, so the wait doubles roughly every 16 upgrades. Equal growth gives a perfectly steady wait.
  • Both linear. The wait levels off at the ratio of the two slopes. It never runs away.
  • Exponential cost, linear or diminishing power. Exponential always wins in the end, so the wait grows without limit. This is a wall: the point where progress stalls. In the demo's wall preset the wait goes from 10 taps to over 600 within 25 upgrades.
  • Linear cost, exponential power. The wait shrinks toward nothing and upgrades stop meaning anything.

What the player feels

A steady wait is reliable but tends to feel flat after a while. A gentle stretch is the most common choice in long progressions. Each upgrade feels slightly more earned, and the lengthening wait quietly tells the player it is time for something new: a new building, a new area, or a reset that trades progress for a permanent bonus. A wall feels like the game has stopped, and players tend to quit unless the wall is the signal for that new thing. A shrinking wait feels great for a minute and then trivial.

Starting points to tune

Make the first upgrade take 10 to 30 seconds (or taps). For long or endless progressions, let cost grow by a few percentage points more per level than power; the idle games mentioned below use cost growth of 7 to 15 percent per purchase. Then write down the wait at upgrades 1, 10, 25 and 50. If it grows by more than about ten times between 1 and 50, expect players to feel a wall. These are starting points, not rules.

Walls can be aimed at wallets

If your game sells a way to skip the wait, you can tune the curves so the wall arrives right when the offer appears. That is artificial scarcity: making the free path slow on purpose so paying feels necessary. It works, and it works against the player. If you sell boosts, make sure the free curve is one you would be happy to play.

When not to use a formula

An action game with eight weapon upgrades does not need a growth formula. Write the eight prices by hand. Formulas pay off with dozens of levels or no last level at all. And if upgrades do not raise income, for example sword damage in a game where gold per level is fixed, the "power" in the formula is your income curve, not the upgrade's effect. Check the ratio of cost to income instead.

The code

The demo's model in LÖVE, with the same names and numbers. Press Space to tap. The marked lines are the two curves and the ratio between them.

local BASE_COST = 100      -- gold for the first upgrade
local BASE_POWER = 10      -- gold per tap before any upgrade
local COST_SHAPE = "exponential"
local COST_GROWTH = 0.20   -- 20% per level
local POWER_SHAPE = "exponential"   -- or "linear" or "diminishing"
local POWER_GROWTH = 0.15  -- 15% per level

local function cost(level)
  if COST_SHAPE == "linear" then
    return BASE_COST * (1 + COST_GROWTH * level)
  end
  return BASE_COST * (1 + COST_GROWTH) ^ level
end

local function power(level)
  if POWER_SHAPE == "linear" then
    return BASE_POWER * (1 + POWER_GROWTH * level)
  elseif POWER_SHAPE == "diminishing" then
    return BASE_POWER * (1 + POWER_GROWTH * math.sqrt(level))
  end
  return BASE_POWER * (1 + POWER_GROWTH) ^ level
end

-- The number the player actually feels
local function tapsToNext(level)
  return cost(level) / power(level)
end

local level, gold, taps = 0, 0, 0

local function tap()
  gold = gold + power(level)
  taps = taps + 1
  if gold >= cost(level) then   -- buy automatically, at most once per tap
    gold = gold - cost(level)
    level = level + 1
    taps = 0
  end
end

function love.keypressed(key)
  if key == "space" then tap() end
end

function love.draw()
  love.graphics.print("Level " .. level, 20, 20)
  love.graphics.print("Gold " .. math.floor(gold) .. " / " .. math.floor(cost(level)), 20, 40)
  love.graphics.print("Taps this upgrade: " .. taps, 20, 60)
  love.graphics.print(string.format("Needs about %.1f taps", tapsToNext(level)), 20, 80)
end

Print tapsToNext for levels 1 to 50 before you play at all. That one column tells you more about your progression than the price list does.

Pitfalls

  • Tuning cost alone. A price list looks reasonable on its own. Divide it by power before you judge it.
  • Testing only the start. Exponential and linear curves look alike for the first few levels, as the shapes diagram shows. Check level 50 and level 200 on paper.
  • Hidden diminishing power. If bonuses add together (+10%, +10%, +10%), each one is a smaller share of the total than the last. Power that looks linear on the upgrade screen can feel diminishing in play.
  • Number overflow. Lua numbers are 64-bit floats that reach infinity near 1.8 × 10308. At 15 percent growth that is around level 5,000. Endless games either cap levels or store big numbers in their own format.
  • Many purchases in one frame. When power runs far ahead of cost, a while loop that buys "as many as affordable" can run millions of times. The demo and the code buy at most one upgrade per tap.

In real games

In Cookie Clicker, each extra building of the same type costs 15 percent more than the last, so price is the base price times 1.15 to the power of the number owned. Its ascension system is a reset that trades current progress for a permanent bonus, a common answer when the wait grows long.

Anthony Pecorella's series on the math of idle games, written while he worked at Kongregate, describes the usual pattern as costs growing exponentially while production grows linearly or polynomially. One of its examples is AdVenture Capitalist's lemonade stand, whose cost grows by a factor of 1.07 per purchase.

Takeaways

  • The wait between upgrades is cost divided by power, and the wait is what the player feels.
  • When both curves are exponential, each wait is (1 + cost growth) ÷ (1 + power growth) times the last.
  • Exponential cost against linear or diminishing power always ends in a wall; plan what the player does when they reach it.
  • A slow stretch is a common default for long progressions. Steady can feel flat, shrinking feels trivial.
  • A wall tuned to sell a skip is a pressure tactic. Make the free curve one you would play.

Acceleration, friction and top speed

How three numbers, acceleration, deceleration and top speed, decide whether a character feels tight, heavy or slippery, and how to tune them.

Two games can share the same top speed and feel nothing alike. In one, the hero stops on a coin-sized ledge the moment you let go. In the other, the hero slides past it every time, and you end up tapping in little pulses to creep into place. The difference is how each game gets to that speed and back to zero.

Movement is a curve, not a number

When you hold a direction, a character's speed does not have to jump straight to its maximum. It can rise over time. Three values describe that rise and fall:

  • Top speed: the fastest the character moves while you hold a direction, in pixels per second.
  • Acceleration: how quickly speed builds while you push, in pixels per second, per second. An acceleration of 2400 means the speed grows by 2400 px/s every second you hold, or 40 px/s each frame at 60 frames per second.
  • Deceleration: how quickly speed drains when you let go. Games often call this friction, even when no real friction is being simulated.

Plot speed against time for one press and release, and every movement style becomes a shape: a ramp up, a flat top, a ramp down.

Two numbers the player actually feels

Raw acceleration values are hard to picture. Two derived numbers are easier to reason about:

  • Time to top speed = top speed ÷ acceleration. At 240 px/s and 2400 px/s², that is 0.1 seconds, about six frames.
  • Stopping distance = top speed² ÷ (2 × deceleration). At 240 px/s and 3000 px/s², that is about 10 pixels, well under half of a 24 pixel character.

Stopping distance is the one that decides your level design. If the character slides 180 pixels after release, a 40 pixel ledge is a guessing game.

Turning around

A third case hides between the other two: pushing the opposite way while still moving. If you treat it as ordinary acceleration, a heavy character turns sluggishly. A common choice, and the one used here, is to brake at the deceleration rate until the speed reaches zero, then accelerate the new way. Some games brake even harder when turning, which reads as a skid.

Starting points to tune

For a precise platformer: reach top speed in about 0.05 to 0.1 seconds and stop within a quarter of the character's width. For a heavier, momentum-driven feel: 0.3 to 0.6 seconds to top speed and a stop of about one to two character widths. Ice or a vehicle can take a second or more. These are ranges to begin from, not rules. Tune them against your own levels and camera.

Try it

Start on Tight, run to the marked pad and stop on it. Then switch to Heavy and Ice and try the same thing. Watch the graph: the rising edge is your acceleration, the falling edge after release is your deceleration, and the step line below it shows exactly when you were pushing.

On Ice you start releasing well before the pad: you are no longer steering, you are planning. For a racing game that can be the fun. For a platformer with small ledges it usually is not.

The code

This is the demo's movement in LÖVE, with the Tight preset. The core is a small helper, approach, that moves a value toward a target by a fixed amount and never overshoots. Every case, speeding up, slowing down and braking, is a call to it with a different target and rate.

local ACCEL = 2400       -- px/s per second while pushing
local DECEL = 3000       -- px/s per second when released or braking
local TOP_SPEED = 240    -- px/s

local player = { x = 160, vx = 0 }

-- Move value toward target by at most amount, without overshooting.
local function approach(value, target, amount)
  if value < target then
    return math.min(value + amount, target)
  else
    return math.max(value - amount, target)
  end
end

function love.update(dt)
  local input = 0
  if love.keyboard.isDown("left", "a") then input = input - 1 end
  if love.keyboard.isDown("right", "d") then input = input + 1 end

  if input ~= 0 then
    if player.vx * input < 0 then  -- pushing against the motion
      player.vx = approach(player.vx, 0, DECEL * dt)
    else
      player.vx = approach(player.vx, input * TOP_SPEED, ACCEL * dt)
    end
  else
    player.vx = approach(player.vx, 0, DECEL * dt)
  end

  player.x = player.x + player.vx * dt
end

function love.draw()
  love.graphics.rectangle("fill", player.x - 12, 300 - 24, 24, 24)
end

Because approach stops exactly at its target, the character reaches exactly zero and exactly top speed, with no creeping and no overshoot. Run this inside the fixed timestep from the physics track and it behaves the same at any frame rate.

Pitfalls

  • Friction as a multiplier per frame. vx = vx * 0.9 every frame is a popular shortcut, but it slows down faster at high frame rates and never quite reaches zero, so the character drifts by fractions of a pixel. Subtract a rate times dt instead, as approach does.
  • Forgetting the turnaround. With low acceleration and no braking rule, reversing feels like wading through mud. Decide on purpose how turns work.
  • Tuning in an empty room. Values that feel great on a flat test floor can be miserable next to small ledges and spikes. Tune with a real piece of level on screen, and check stopping distance against your smallest platform.
  • One set of values for ground and air. Many platformers use weaker control in the air than on the ground, so a jump's direction partly commits. Too weak and the player feels locked in; too strong and jumps lose weight.
  • Using momentum to hide a slow character. Slow acceleration reads as weight, but a long ramp in every room becomes a tax on every input. As in the latency lesson, the first frame of a press should still visibly change something.

When not to use gradual acceleration

Grid-based and turn-based movement, menu cursors, and games built on exact positioning tend to feel best with instant start and stop. Momentum is a tool for games where carrying speed is part of the challenge or the fantasy: vehicles, heavy characters, ice, and games about speed itself.

In real games

The developers of Celeste released the source of the game's player class as a learning resource. Its running code uses the same pattern as the Lua above: an approach function moving speed toward the top running speed, or toward zero when no direction is held. In that code the top run speed is 90 (in the game's own pixel units) and the run acceleration is 1000 per second, so the character reaches full speed in under a tenth of a second and stops in about the same time. In the air the rate is multiplied by 0.65, which is exactly the weaker air control described above.

The early Super Mario Bros. games are well known for the opposite approach: Mario builds up to a run over time and skids when you reverse, and learning to handle that momentum is part of the skill.

Takeaways

  • Movement feel comes from the shape of the speed curve, not from top speed alone.
  • Think in time to top speed and stopping distance. They are easier to tune than raw acceleration values.
  • Decide how turning around works. Braking before reversing keeps heavy characters controllable.
  • Move speed toward a target by a fixed rate times dt, so it lands exactly on zero and on top speed.
  • Momentum suits vehicles, heavy characters and speed-focused games. Precise games tend to want near-instant control.

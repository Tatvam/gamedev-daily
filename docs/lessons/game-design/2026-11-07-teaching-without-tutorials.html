Teaching without tutorials: the safe first room

How a safe room whose only exit needs a new move teaches it better than a text box, and how to add hints only when the player is stuck.

The game pauses and a box says "Press X to dash. Dashing lets you cross wide gaps." You press a button to close it without really reading it. Two rooms later there is a wide gap over spikes, and the first time you ever dash is the moment it matters. You fall, lose a life, and blame the game.

The player was told about the dash, but never got to try it somewhere safe. This lesson is about building a room that lets them.

Doing beats reading

A tutorial here means any teaching that stops the game to explain: a text box, a pop-up, a page of controls. Text tutorials tend to fail in a few predictable ways:

  • They get skipped. Many players close the box before reading it.
  • They come too early. The rule arrives before the player needs it, and is forgotten by the time they do.
  • The first try happens under pressure. Reading "dash crosses gaps" does not tell you how far a dash goes. Only doing it does, and if the first attempt is over spikes, learning costs a life.

The alternative is a teaching room: a small, safe space built so that the only way out is to use the new mechanic. The player sees a problem, tries things, and finds the answer. A move you found yourself tends to stick better than one you were told about.

The parts of a teaching room

A good teaching room usually has five properties:

  1. One new thing. No enemies, no timer, nothing else to learn.
  2. A visible goal. The exit can be seen from the start.
  3. A gate that needs the mechanic. Check it with numbers, not by eye. In the demo a plain jump covers at most about 100 pixels and the gap needs 116.
  4. Cheap failure. A starting point is under about three seconds from a fall to the next attempt.
  5. The smallest hint that works. A picture of the button, a light, a shape. Words are the last resort.

Escalating hints

Some players will not find the answer. Instead of explaining to everyone up front, use an escalating hint: one that starts quiet and gets louder only when the player is stuck. First the sign, then a button prompt over the player's head. A common starting point is to show the prompt after about three failed tries or 20 to 30 seconds without progress. Players who solve it quickly never see it.

Then test, with stakes

Right after the teaching room, ask for the same move where failure matters: the same gap, now over spikes. The player has done it once already, so the test feels like a chance to show off rather than a trap.

Rule of thumb

Introduce a mechanic where failure is cheap, then test it where failure counts. Never let the first use and the first real stakes happen in the same place.

Try it

Play the "Text box first" run, then switch to "Teaching room" and play again. Both end in the same spike room. The timeline under the game records reading, dashes, safe falls and deaths: look at where your first dash lands in each run.

Your second run is easier simply because it is second. For a fairer test, hand the demo to someone who has not read this page, with the button prompt set to "Never", and watch without helping.

The code

The dash and the teaching room's bookkeeping, with the demo's numbers. Jumping and collision are left as your own functions. The highlighted lines record where the first dash happened and turn the prompt on after enough safe falls.

local GRAVITY    = 1800  -- px/s^2
local RUN_SPEED  = 160   -- px/s
local DASH_SPEED = 520   -- px/s
local DASH_TIME  = 0.15  -- s, so a dash covers 78 px
local HINT_AFTER = 3     -- safe falls before the button prompt appears

local player = { x = 24, y = 140, vx = 0, vy = 0, facing = 1, inputX = 0,
                 grounded = true, canDash = true, dashTimer = 0 }
local teach = { falls = 0, prompt = false, firstDashRoom = nil }
local currentRoom = "teach"     -- "teach" (safe pit) or "test" (spikes)

local function startDash()
  if not player.canDash then return end
  player.canDash = false        -- one dash until you land
  player.dashTimer = DASH_TIME
  if teach.firstDashRoom == nil then teach.firstDashRoom = currentRoom end
end

function love.keypressed(key)
  if key == "x" then startDash() end
end

-- Call this from your collision code when the player lands in the safe pit.
function onSafeFall()
  teach.falls = teach.falls + 1
  if teach.falls >= HINT_AFTER then teach.prompt = true end
end

function love.update(dt)
  if player.dashTimer > 0 then
    player.dashTimer = player.dashTimer - dt
    player.vx = player.facing * DASH_SPEED
    player.vy = 0               -- a dash ignores gravity
  else
    player.vx = player.inputX * RUN_SPEED
    player.vy = player.vy + GRAVITY * dt
  end
  moveAndCollide(player, dt)    -- your collision code, sets grounded
  if player.grounded and player.dashTimer <= 0 then player.canDash = true end
end

function love.draw()
  drawRoom(currentRoom)         -- includes the sign: a key picture, no words
  drawPlayer(player)
  if currentRoom == "teach" and teach.prompt then
    drawKeyPrompt("X", player.x, player.y - 30)
  end
end

Log teach.firstDashRoom in playtests. If many testers first dash in the test room, the teaching room is not working.

Pitfalls

  • A gate with a back door. If a running jump, coyote time or a lucky corner clears the gap, players skip the lesson. Work out the longest plain jump, forgiveness included, and make the gap clearly wider.
  • Hiding the button entirely. Players cannot discover a button they do not know exists. Show it somewhere: a sign, on-screen controls, a pause menu, using the player's own binding if they remapped it.
  • Expensive failure in the teaching room. A long climb back or a death screen turns experiments into punishments.
  • Teaching two things at once. With a new move and a new enemy in one room, you cannot tell which one confused the player.
  • No test afterwards. A move practised once and never asked for again is forgotten.

When not to use it

Rules that are invisible in the space, such as crafting menus or damage formulas, and large control schemes like a fighting game's move list, are usually better explained in words the player can look up again. Some players also need to be told: someone new to games, or with a cognitive disability, may find open-ended experiment stressful. An optional written explanation alongside the room costs little. And on a second playthrough a teaching room is just a delay, so keep it short.

In real games

The best-known example is World 1-1 of Super Mario Bros. (1985). In a 2015 video interview with Eurogamer, Shigeru Miyamoto described the level as designed so that players could learn how the game works by playing it, without a manual. You can see it in the layout: the first mushroom slides away from Mario, hits a pipe and comes back toward him, so many players collect it whether they meant to or not, and learn what it does.

Portal (2007) introduces its portal gun in stages. The player first gets a device that places only one colour of portal, in simple test chambers, and only later the full two-portal gun. Each new ability arrives in a small chamber where it is the only way forward.

A common middle ground is the contextual prompt: a button icon that appears only where and when it is needed, such as beside a climbable ledge.

Your turn (15 minutes)

Pick one mechanic in your game that is currently explained with text. Build a room with a visible exit that can only be reached by using it, with a cheap way to retry. Measure the gate: write down the longest distance the player can cover without the mechanic, and make sure the room needs clearly more.

Remove the text, add a sign with a picture of the button, and add a prompt that appears after three failures. You are done when the room cannot be finished without the mechanic and a tester who has never seen it gets through without you saying a word.

Takeaways

  • Players tend to remember what they did better than what they read, so teach with a problem that needs the mechanic.
  • A teaching room has one new thing, a visible goal, a gate that measurably needs the mechanic, and failure that costs seconds.
  • Start with the smallest hint and add louder ones only when the player is stuck.
  • Introduce where failure is cheap, then test the same move where it counts.
  • Keep a way to read the controls, and an optional explanation, for players who need it.

Jump arcs: height, hang time and fast fall

How to build a jump from its height and time to the top, then add a slower top and a faster fall so it is easier to aim.

You jump toward a small platform. The character rises, drifts over the top, and then sinks so slowly that you overshoot while waiting to come down. Nothing is broken, the jump is just a perfect physics arc, and a perfect physics arc is often not the jump players want.

Design the jump, then derive the physics

A jump in most 2D games is two numbers: a jump speed, the upward speed given on take-off, and gravity, which drains that speed every frame. Tuning them directly is awkward: raise gravity for a snappier jump and it also gets lower.

It is easier to choose what the player experiences: the jump height in pixels, which decides what can be reached, and the time to apex, how long it takes to reach the top, which decides whether the jump feels quick or floaty. The physics follows:

local GRAVITY = 2 * JUMP_HEIGHT / (TIME_TO_APEX * TIME_TO_APEX)
local JUMP_SPEED = 2 * JUMP_HEIGHT / TIME_TO_APEX

For 100 pixels in 0.42 seconds, gravity is about 1134 px/s² and jump speed about 476 px/s. Now you can make the jump quicker without changing its height, so without breaking your levels.

The trouble with a symmetric arc

With one gravity the whole way, the fall takes as long as the rise. That tends to feel floaty: half the jump is spent coming down, with nothing left to decide but where to land. Two changes, together or alone, reshape it.

  • Apex hang. While the vertical speed is below a small threshold (50 px/s here), multiply gravity by a hang gravity below 1, such as 0.5. The character lingers at the top, where the player lines up the landing.
  • Fast fall. While moving down, multiply gravity by a fall multiplier above 1. The jump lands sooner and with weight. A multiplier of m divides the fall time by the square root of m, so ×2 cuts it to about 71 percent.

The hang also raises the peak slightly (under a pixel here) and makes the real time to the top a little longer than the number you chose. Check your tightest ledge afterwards.

Starting points to tune

Pick the height from your level design first. A time to apex of roughly 0.3 to 0.45 seconds is a reasonable place to start for a platformer. Hang gravity of about 0.5 within a narrow speed band, and a fall multiplier of about 1.5 to 2.5. Add a cap on fall speed so long drops stay readable. These are starting points, not rules.

What the player feels

Without shaping, jumps feel like tossing a balloon: soft and hard to land precisely. With it, the character pauses for a moment at the top, the player sees the landing spot, and the character drops onto it. The jump feels more controllable and heavier, with the same height and take-off.

The code

This is the demo's jump in LÖVE, with the same numbers. Height y is measured upward from the ground, and running and platforms are left out. The demo runs this update at a fixed 60 steps per second. The marked lines are the technique.

local JUMP_HEIGHT = 100     -- pixels, the demo's slider
local TIME_TO_APEX = 0.42   -- seconds, the demo's slider
local SHAPED = true         -- the demo's "Hang and fast fall" toggle
local HANG_GRAVITY = 0.5    -- gravity multiplier near the top
local HANG_SPEED = 50       -- "near the top" means slower than this, px/s
local FALL_MULT = 2         -- gravity multiplier while falling
local MAX_FALL = 1000       -- cap on falling speed, px/s

local GRAVITY = 2 * JUMP_HEIGHT / (TIME_TO_APEX * TIME_TO_APEX)
local JUMP_SPEED = 2 * JUMP_HEIGHT / TIME_TO_APEX

local player = { y = 0, vy = 0, grounded = true, jumping = false }

local function gravityFor(p)
  if SHAPED and p.jumping and math.abs(p.vy) < HANG_SPEED then
    return GRAVITY * HANG_GRAVITY   -- linger at the top
  elseif SHAPED and p.vy < 0 then
    return GRAVITY * FALL_MULT      -- come down faster
  end
  return GRAVITY
end

function love.keypressed(key)
  if key == "space" and player.grounded then
    player.vy = JUMP_SPEED
    player.grounded = false
    player.jumping = true
  end
end

function love.update(dt)
  if player.grounded then return end
  local oldVy = player.vy
  player.vy = math.max(player.vy - gravityFor(player) * dt, -MAX_FALL)
  player.y = player.y + (oldVy + player.vy) * 0.5 * dt  -- average speed this step
  if player.y <= 0 then
    player.y, player.vy = 0, 0
    player.grounded, player.jumping = true, false
  end
end

The jumping flag limits the hang to real jumps, so walking off a ledge does not float. Moving by the average of the old and new speed makes the peak match the height you asked for; with the new speed alone it comes out a few pixels short.

This combines with variable jump height. Some games apply the hang only while the button is held, so a tap still gives a crisp hop.

Pitfalls

  • Tuning gravity and jump speed by hand. Each change breaks the other. Edit height and time to apex and derive the rest. Lock height early, since levels are built around it; time to apex is safe to tune later.
  • A hang band that is too wide. If "near the top" covers most of the jump, you have only made gravity weaker. Keep it narrow.
  • Fast fall with no cap. On long drops the player cannot react, and fast bodies can pass through thin floors in one step. Cap the falling speed.
  • Hang on things that are not jumps. Springs, knock-back and ledge drops usually should not float. Gate it on a flag set at take-off.
  • Step size changing the arc. With a frame-dependent dt, the peak varies between machines. A fixed timestep keeps the arc the same everywhere.

When not to use it. A slow, symmetric arc can be the point: low gravity levels, swimming, or a character whose charm is drifting. Games where players predict arcs from shared physics, such as thrown objects, may want one rule for everything. In a fast game a long hang slows the pace.

In real games

Maddy Thorson, one of Celeste's developers, described in a 2020 thread of Celeste design notes that the game halves gravity at the peak of a jump while the jump button is held, to give the player more time to adjust the landing. I found this through press write-ups that reproduce the thread, not the original posts.

Kyle Pittman's GDC 2016 talk "Building a Better Jump" presents the same derivation from height and time, and discusses stronger gravity on the way down.

In Super Smash Bros. Melee, pressing down while falling makes the character fall faster, turning fall speed into a choice the player makes.

Takeaways

  • Design a jump by height and time to apex, then derive gravity as 2h / t² and jump speed as 2h / t.
  • A single gravity gives a symmetric arc, which often feels floaty because half the jump is spent falling.
  • Weaker gravity near the top gives time to aim; stronger gravity on the way down gives weight and a quicker landing.
  • Keep the hang band narrow, cap fall speed, and apply the hang only to real jumps.
  • A plain floaty arc is still the right choice for some characters and settings.

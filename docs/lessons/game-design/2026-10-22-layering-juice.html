Layering juice on a plain game

How to add feedback effects to a plain game one layer at a time, give each one a job, and notice when polish starts to hide the action.

You add screen shake to your game, then particles, then a flash, then a sound. Each one felt better the day you added it. A week later a friend plays it and keeps losing the ball in the fireworks.

Earlier lessons each covered one effect. This one is about stacking them.

Juice is feedback, not decoration

Juice is the name developers commonly use for effects that answer the player's actions with more response than the rules need: the shake, the sparks, the squash, the rising pitch. None of it changes who wins. A brick that vanishes and a brick that flashes, bursts and falls away are worth the same points.

What juice changes is how clearly the game talks back. A useful way to judge an effect is to ask which question it answers for the player:

  • Did it count? A flash or a sound on the exact frame of contact.
  • Where? Particles that come from the brick that was hit, in its colour.
  • How hard, or how important? Shake and particle count that grow with the size of the event.
  • What is happening over time? A sound whose pitch rises as a combo grows.

An effect that answers none of these is decoration: sometimes worth having, but the first thing to cut when the screen gets busy.

Add one layer at a time

Effects interact. If you add five at once and the game feels worse, you cannot tell which one did it. A slow habit works better:

  1. Play the plain game for a minute, so you remember what plain feels like.
  2. Add one effect at a modest strength, play, and say what it tells you. Switch it off and on to compare.
  3. Keep it, tune it, or cut it. Only then add the next one.

The order matters less than doing it one at a time. A common habit is to save screen-wide effects such as shake for last, because they change how everything else reads.

Scale effects by importance

If every event gets the biggest reaction, nothing stands out. Give events a ranking and let the effects follow it. In the demo a normal brick adds 3 pixels of shake and 8 particles; the last brick of the wall gets three times as much. A paddle hit gets only a squash, a flash and a low note.

When polish starts to hide the action

Every effect spends some of the player's attention. The warning signs tend to be the same:

  • The important object gets lost. The ball disappears behind particles, or shake moves it more than its own motion does.
  • The game feels slower. Hit stop and long tweens delay the moment the player can read the result. In a fast game with many small hits, that delay repeats every second.
  • Effects stop meaning anything. When the screen shakes all the time, a shake no longer says "that was big".
  • Players get tired. Constant motion and flashing wear people out, and make some feel unwell.

Two cheap checks help. Squint at the screen during a busy moment: the things the player controls and tracks should still be the clearest shapes, so draw them last, on top of every effect. And watch someone new play. If they lose the ball, the effects are winning.

Starting points, not rules

At 100 percent strength: shake 3 px per brick, capped at 8, decaying with an 80 ms half-life (the time to lose half its size). 8 particles per brick living 0.5 s. A 60 ms flash, at most three a second. Ball stretch 20 percent, squash 30 percent for 0.1 s. Bricks ease in over 0.35 s. Hit stop: probably none in this genre.

When not to layer it on

Competitive and precision games tend to keep effects small, because players need exact positions more than spectacle. Calm puzzle games often suit soft, short effects. Hit stop suits melee combat but tends to fight a game like this one, where the player tracks one fast ball through many small hits. Whatever you keep, let players turn shake and flashing down or off.

The code

The rules call one function per event, and every effect sits behind a switch inside it. That makes A/B testing, a "reduce effects" option and the importance boost easy. Tweens, squash and the trail are drawn in drawWorld from the same switches. Names and numbers match the demo.

local juice = { tween = true, squash = true, flash = true, particles = true,
                trail = true, shake = true, sound = true, hitStop = false,
                intensity = 1 }
local fx = { shake = 0, freeze = 0, lastFlash = -1 }
local clock = 0

local SHAKE_PER_HIT, SHAKE_MAX, SHAKE_HALF_LIFE = 3, 8, 0.08
local PARTICLES_PER_HIT, PARTICLE_LIFE = 8, 0.5
local FLASH_TIME, FLASH_GAP = 0.06, 0.34   -- at most 3 flashes a second
local HIT_STOP = 0.04
local LAST_BRICK_BOOST = 3
local hitSound = love.audio.newSource("hit.wav", "static")

-- The rules call this once per brick hit. Nothing here changes the rules.
function onBrickHit(brick, combo, isLast)
  local k = juice.intensity
  local boost = isLast and LAST_BRICK_BOOST or 1
  if juice.shake then
    fx.shake = math.min(fx.shake + SHAKE_PER_HIT * k * boost, SHAKE_MAX * k)
  end
  if juice.particles then
    for i = 1, math.floor(PARTICLES_PER_HIT * k * boost + 0.5) do
      spawnParticle(brick, PARTICLE_LIFE)
    end
  end
  if juice.flash and clock - fx.lastFlash >= FLASH_GAP then
    brick.flash = FLASH_TIME
    fx.lastFlash = clock
  end
  if juice.hitStop then fx.freeze = HIT_STOP * k end
  if juice.sound then
    hitSound:stop()
    hitSound:setPitch(2 ^ (math.min(combo, 12) / 12))  -- a semitone per brick
    hitSound:play()
  end
end

function love.update(dt)
  clock = clock + dt
  fx.shake = fx.shake * 2 ^ (-dt / SHAKE_HALF_LIFE)
  updateParticles(dt)
  if fx.freeze > 0 then
    fx.freeze = fx.freeze - dt
  else
    updateBall(dt)      -- the rules; calls onBrickHit
  end
  updatePaddle(dt)      -- input never freezes
end

function love.draw()
  local s = fx.shake
  love.graphics.push()
  love.graphics.translate((love.math.random() * 2 - 1) * s, (love.math.random() * 2 - 1) * s)
  drawWorld()           -- draw the ball last, on top of every effect
  love.graphics.pop()
  drawHud()             -- the score does not shake
end

The other functions called here are your own; earlier lessons in this track show each effect alone.

Pitfalls

  • Effects that change the rules. If a tween moves a brick's collision box, or hit stop freezes the paddle, the polish has changed how the game plays. Keep juice in the drawing and leave the simulation alone.
  • Stacking without a cap. Five hits in a quarter second add five shakes. Cap the total, as SHAKE_MAX does, and cap particle counts too.
  • Tuning while tired of the game. After hours of testing you stop noticing effects and turn them up. Compare with the plain version.
  • Particle cost. Thousands of particles created and destroyed each second can cost frame time. Cap the count and reuse particle tables.

In real games

The approach in this lesson, taking a plain brick-breaking game and adding effects one at a time, is the format of Martin Jonasson and Petri Purho's 2012 talk Juice it or lose it, which helped popularise the word "juice" among developers. Jan Willem Nijman's talk The art of screenshake does something similar with a simple shooter.

Many modern games also offer settings to reduce screen shake or flashing: the right amount differs between players.

Your turn (15 minutes)

Pick one event in your game, such as a hit or a pickup. Route every effect for it through one function with a switch per effect, like onBrickHit. Play with all effects off for a minute, then add them back one at a time, writing one line for each saying which question it answers. Cut or shrink any effect without a line. You are done when every remaining effect has its line and you can still follow the important object in the busiest moment.

Takeaways

  • Juice is extra feedback that does not change the rules. Judge each effect by the question it answers for the player.
  • Add effects one at a time and compare with the plain game, so you know what each one does.
  • Scale effects by importance so big moments still stand out.
  • Polish has gone too far when the player loses the important object, the game feels slower, or effects stop meaning anything.
  • Route effects through one event function with switches, so they are easy to test and to turn down.

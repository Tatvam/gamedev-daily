Jump buffering: remembering the early press

How remembering a jump pressed just before landing stops the game ignoring inputs, how long to remember it, and how to code it.

You are bouncing over a row of spikes. You press jump again as you come down, the character lands, and simply stands there until the next spike hits. You pressed. The game saw it. It threw the press away because your feet were still a few pixels above the floor.

A press that arrives too early is thrown away

The usual rule is that a jump press only works while the character is grounded, standing on something solid in the current frame. A press in the air is checked once, fails, and is forgotten.

That is fine when the player is waiting on the ground. It fails when they chain moves. To jump again right on landing, a player aims at the landing frame, and human timing is not frame exact. Many presses arrive a few frames early, do nothing, and the surprised second press comes far too late.

The coyote time lesson fixed presses that arrive just after the edge. This is the mirror case: presses that arrive just before the ground.

The fix: remember the press for a moment

Jump buffering stores a jump press made in the air and carries it out on the first frame the character is grounded, as long as that happens within a short window. The stored press is the buffer, and the window is how long it stays valid.

How it works in code

Keep one number, the buffer timer. When jump is pressed on the ground, jump at once. When it is pressed in the air, set the timer to the full window. Each frame, after moving and checking for landing, jump if the character is grounded and the timer is above zero, then count the timer down. A jump always sets the timer to zero, so one press gives one jump.

As with coyote time, count in seconds or in fixed simulation steps, not in rendered frames, so the window stays the same length on every machine.

Starting points to tune

A window of about 100 ms (6 frames at 60 frames per second) is a common place to start, and values from roughly 50 to 150 ms are widely used. Too short and early presses still vanish. Too long and the character starts jumping when the player has changed their mind, which feels like the game acting on its own. These are starting points, not rules.

What the player feels

Without a buffer, chained jumps feel sticky: the controls seem to drop presses at random, and players often blame their controller. With one, pressing "on the landing" simply works and bouncing gets a steady rhythm.

The code

This is the demo's runner in LÖVE, with the same numbers. Height y is measured upward from the ground, and spikes are left out to keep the technique visible. The marked lines are the whole technique.

local RUN_SPEED = 260       -- pixels per second, the runner never stops
local GRAVITY = 2200        -- pixels per second squared
local JUMP_SPEED = 700      -- pixels per second at take-off
local BUFFER_TIME = 0.100   -- seconds; the demo's slider (0 turns it off)

local player = { x = 0, y = 0, vy = 0, grounded = true }
local jumpBuffer = 0        -- time left in which a stored press still counts

local function jump()
  player.vy = JUMP_SPEED
  player.grounded = false
  jumpBuffer = 0            -- spent: one press, one jump
end

function love.keypressed(key)
  if key ~= "space" and key ~= "w" and key ~= "up" then return end
  if player.grounded then
    jump()
  else
    jumpBuffer = BUFFER_TIME  -- too early: remember it
  end
end

function love.update(dt)
  player.x = player.x + RUN_SPEED * dt
  if not player.grounded then
    player.vy = player.vy - GRAVITY * dt
    player.y = player.y + player.vy * dt
    if player.y <= 0 then
      player.y, player.vy, player.grounded = 0, 0, true  -- landed
    end
  end
  if player.grounded and jumpBuffer > 0 then
    jump()                    -- the stored press fires on the landing frame
  end
  jumpBuffer = math.max(0, jumpBuffer - dt)
end

Order matters in love.update. Land first, then check the buffer, then count it down. If you count down before the check, a press made exactly one window before landing just misses, and the effective window is one frame shorter than the number you typed.

Pitfalls

  • Not clearing the buffer on a jump. If the timer survives a jump, a press used for one jump can fire a second one on the next landing. Set it to zero in the one function every jump goes through.
  • A window that is too long. A player who taps jump near the peak, perhaps hoping for a double jump that does not exist, gets an extra hop on landing they never wanted. That is the opposite of forgiving. Keep the window short, and test with a press at the top of a jump.
  • Buffering into the wrong move. In a game with a double jump, an early press while airborne should usually spend the air jump if one is left, and buffer only when it is not. Decide on purpose which one wins, then make it consistent.
  • Forgetting the other moves. Attacks, dashes and wall jumps drop early presses just as easily. If you buffer several actions, decide what happens when two are stored at once.
  • Buffering through a scene change. A press stored as the player dies or a menu opens can fire after the restart. Clear the buffer whenever control is taken away.

When not to use it. Buffering matters most where moves are chained quickly. In slow, deliberate games, or where committing to an exact input is the challenge, such as some rhythm games, it can remove skill the design depends on. In fighting games the window is also a balance decision.

In real games

Celeste uses jump buffering. Its director Maddy Thorson listed it in a 2020 thread about the game's forgiveness mechanics, next to coyote time and corner correction, and said the team did not invent these tricks. I could not confirm the exact window Celeste uses, so it is not given here.

Input buffering in general is common in action and fighting games, where a press made during the end of one move is held so the next move starts the moment it can. A well tuned buffer is invisible, so you usually cannot tell its length from playing.

Your turn (15 minutes)

In your own platformer, add a buffer timer as above with a window of 0.1 seconds, and make the window something you can change while playing, for example with two keys that add or remove 0.02 seconds.

Stand on flat ground and jump ten times in a row, pressing each new jump as you come down. Count the jumps that fired on landing at 0, 0.1 and 0.25 seconds. Then, at each value, press once at the top of a jump and note whether the extra hop feels wanted. You are done when you have picked a value between those two points and written down why.

Takeaways

  • Players aim chained jumps at the landing frame and often press a little early. A strict grounded check throws those presses away.
  • Jump buffering stores an airborne press and carries it out on the first grounded frame, within a short window.
  • Set a timer on an air press, check it right after landing, count it down after the check, and clear it on every jump.
  • About 100 ms is a common starting point. Too long and the game jumps when the player has changed their mind.

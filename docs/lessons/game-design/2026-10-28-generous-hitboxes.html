Generous hitboxes: small to hurt, big to collect

Why the box that hurts the player is usually smaller than the sprite, why pickups reach further than they look, and how to size both.

A bullet passes through the empty space beside your ship's wing, and you lose a life. Then you fly straight over a coin, and it stays there because your ship's box was one pixel short of it. Both times the game did exactly what its collision code said. Both times it felt like the game was against you.

The sprite is not the body

A sprite is the picture of the character. Collision code rarely tests the picture itself. It tests simple shapes: a hurtbox is the shape that takes damage when something touches it, and a pickup radius is how far from the character's centre an item can be and still be collected.

The easy first version uses the sprite's bounding box, the smallest rectangle around the picture, for everything. That box is almost always bigger than the drawn shape. The demo's ship is drawn as an arrow, and it fills only a little over a third of its box; the two top corners and the notch at the back are empty space. When a bullet touches an empty corner, the game counts a hit the player could not see.

Two shapes, pulled in opposite directions

The fix is to stop using one shape for two jobs.

  • The hurtbox shrinks. Put a small circle at the heart of the sprite. A bullet has to reach the solid middle of the character before it counts. Anything that only touches the edges, wings or hair passes harmlessly.
  • The pickup reach grows. Put a larger circle around the character for collecting coins, hearts and ammo. If the sprite came close, the item is taken.

Both changes push in the player's favour, and that is the point. Players judge contact by eye, at speed, from the middle of the shape. When the game errs, it should err toward what the player believes happened: "that missed me" and "I grabbed that".

Starting points to tune

For the hurtbox, try a circle whose radius is about an eighth of the sprite's width in a dense shooter (4 px on the demo's 32 px ship), and a quarter to a third of it in an action game with fewer, slower hazards. For pickups, try a radius around one sprite width from the centre. These are places to start, not rules; the right size depends on bullet speed, bullet count and how much space the screen leaves to dodge.

What the player feels

With the sprite box, dense patterns feel cheap. Players hit by corners they did not see learn to keep a wide berth, so the screen feels more crowded than it looks and threading a gap feels like luck. With a small hurtbox, the same pattern becomes something to read and slip through, and a close call feels like skill. With a wider pickup reach, players stop making careful passes over every coin and keep moving.

Try it

Play a 30 second round with "Generous hitboxes" off. The hurtbox and the pickup shape are both the sprite's box. Then switch it on and play another round. Both rounds use the same bullet rain, so the readouts compare fairly. Watch for the blue rings: each one is a bullet that touched the sprite box but missed the hurtbox, a hit that the old test would have counted.

Then push the hurtbox slider to 16 px, larger than the ship's body, to feel the game turn unfair, and down to 1 px to feel it stop mattering.

The code

This is the demo's collision code in LÖVE, with the same sizes. Spawning bullets and coins, removing bullets that leave the screen, and keeping the ship on screen are left out. Coordinates are in pixels with y pointing down, as in LÖVE. The marked lines are the technique: two circle tests with different radii instead of one box test.

local GENEROUS = true                 -- the demo's toggle
local SPRITE_W, SPRITE_H = 32, 26     -- the ship's bounding box
local HURT_RADIUS = 4                 -- the demo's sliders
local PICKUP_RADIUS = 28
local BULLET_RADIUS, COIN_RADIUS = 5, 6
local SPEED, MERCY = 190, 1.0

local player = { x = 180, y = 360, mercy = 0, hits = 0, coins = 0 }
local bullets = {}  -- { x, y, vx, vy }, filled by your pattern code
local coins = {}    -- { x, y }

local function circlesTouch(ax, ay, ar, bx, by, br)
  local dx, dy = ax - bx, ay - by
  return dx * dx + dy * dy < (ar + br) * (ar + br)
end

-- A circle against a box centred on (bx, by): the "use the sprite" test.
local function circleTouchesBox(cx, cy, r, bx, by, bw, bh)
  local nx = math.max(bx - bw / 2, math.min(cx, bx + bw / 2))
  local ny = math.max(by - bh / 2, math.min(cy, by + bh / 2))
  return (cx - nx) ^ 2 + (cy - ny) ^ 2 < r * r
end

local function bulletHits(p, b)
  if GENEROUS then
    return circlesTouch(p.x, p.y, HURT_RADIUS, b.x, b.y, BULLET_RADIUS)
  end
  return circleTouchesBox(b.x, b.y, BULLET_RADIUS, p.x, p.y, SPRITE_W, SPRITE_H)
end

local function coinTaken(p, c)
  if GENEROUS then
    return circlesTouch(p.x, p.y, PICKUP_RADIUS, c.x, c.y, COIN_RADIUS)
  end
  return circleTouchesBox(c.x, c.y, COIN_RADIUS, p.x, p.y, SPRITE_W, SPRITE_H)
end

function love.update(dt)
  local dx, dy = 0, 0
  if love.keyboard.isDown("left") then dx = dx - 1 end
  if love.keyboard.isDown("right") then dx = dx + 1 end
  if love.keyboard.isDown("up") then dy = dy - 1 end
  if love.keyboard.isDown("down") then dy = dy + 1 end
  player.x = player.x + dx * SPEED * dt
  player.y = player.y + dy * SPEED * dt
  player.mercy = math.max(0, player.mercy - dt)

  for i = #bullets, 1, -1 do
    local b = bullets[i]
    b.x = b.x + b.vx * dt
    b.y = b.y + b.vy * dt
    if player.mercy == 0 and bulletHits(player, b) then
      player.hits = player.hits + 1
      player.mercy = MERCY
      table.remove(bullets, i)
    end
  end

  for i = #coins, 1, -1 do
    if coinTaken(player, coins[i]) then
      player.coins = player.coins + 1
      table.remove(coins, i)
    end
  end
end

Both loops run backwards so that table.remove does not skip an item. The hurtbox and the pickup reach share a centre but are separate numbers, so each can be tuned without touching the other.

Pitfalls

  • A hurtbox the player cannot locate. If the safe area is tiny, players need to know where it is. Put the hurtbox under a clearly drawn core, such as a cockpit, a gem or the character's chest, or show it while the player moves slowly. A tiny hurtbox off to one side of the sprite feels as wrong as a large one.
  • Shrinking it so far that nothing matters. At 1 pixel almost every pattern can be ignored, and dodging stops being a skill. Shrink until hits feel fair, not until they stop.
  • Being strict when the player attacks. The same generosity applies the other way round to the player's attacks: shots that clip an enemy's edge should usually count. Being strict with the player and loose with enemies is the opposite of the goal.
  • Pickups that vanish too early. A big reach with no animation looks like a glitch: the coin disappears while still visibly away from the ship. Pulling the item toward the player for a few frames, like a magnet, makes a wide reach read as intentional.

When not to use it. In a game about precise contact, like a fighting game where players study every frame and every box, the boxes are part of the rules and players expect them to match the art closely. In a slow puzzle game where touching a hazard is the whole question, a hurtbox smaller than the art can make the answer unclear. When a pickup is a choice you might want to avoid, a large reach takes the choice away.

In real games

Bullet hell shooters, the genre of dense, patterned bullet storms, rely on this the most. In the Touhou Project shooters, holding the slow "focus" movement makes the player's hitbox visible as a small dot, and that dot is much smaller than the character's sprite. Fan wikis put it at around 4 to 5 pixels, varying by character; I found that figure in search results and could not open the pages to confirm it. The same games keep a "graze" counter that rewards bullets that pass close to the character, turning near misses into a score mechanic.

Pickup reach is often a stat the player can improve. In Vampire Survivors, for example, a passive item increases how far away experience gems are pulled in.

Your turn (15 minutes)

Draw your player's collision shapes on screen with a debug key. If you are using the sprite's bounding box, replace the hurtbox with a circle at the sprite's solid centre, radius about a quarter of the sprite's width, and give pickups their own circle one sprite width in radius. Play your hardest section three times with each setup and count hits that surprised you. You are done when every hit you take is one you can see coming, and coins you fly over are never left behind.

Takeaways

  • The sprite's bounding box is larger than the drawn shape, so using it as a hurtbox counts hits the player could not see.
  • Give damage and collection separate shapes: a small hurtbox at the solid centre and a larger pickup reach.
  • Both changes err toward what the player believes happened, which is what makes them feel fair.
  • Anchor a small hurtbox to something visible, and stop shrinking it before dodging stops mattering.
  • Leave the boxes honest where exact contact is the rule, as in fighting games and competitive play.

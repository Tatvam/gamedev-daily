Shading basic forms: sphere, cylinder and cube

How a sphere, a cylinder and a cube each catch one light differently, how many shades each needs, and how bigger sprites are built from the three.

You shade a crate the way you shaded your ball: light in the top-left corner, dark in the bottom-right, a soft blend between. The crate now looks like a cushion. The light was right. The form was wrong, because a box does not catch light the way a ball does.

Shade follows the way the surface faces

In the last lesson every pixel got its shade from one question: how directly does this bit of surface face the light? The answer depends on the form, the simple solid shape underneath the drawing. Three forms cover most of what you will ever draw: the sphere, the cylinder and the cube. Each changes its facing in a different way, so each gets a different shading pattern.

The sphere: changes in both directions

A sphere turns away from you whichever way you move across it, so the shade changes everywhere. The bands are curves that wrap around the brightest spot. A sphere can use every step of your ramp, and it usually looks better with more of them, because each extra step makes the curve feel smoother.

The cylinder: changes across, never along

An upright cylinder turns as you move across its width, but moving down its length changes nothing. Every row of the body is the same row repeated, so the bands are straight stripes that run the full length. The flat top is a separate surface that faces up and gets a single shade of its own.

The cube: one shade per face

A flat face points in one direction everywhere, so every pixel on it gets the same shade. A cube shows you at most three faces at once, so it uses at most three shades however long your ramp is. The form shows up as hard steps at the edges, not as a blend. With the light from the top left, the usual result is a light top, a middle front and a dark side.

No flat face points straight at the light, so on a ramp of four or more steps a cube usually leaves the lightest one unused. That step is a highlight, and highlights belong to curved surfaces.

Bigger sprites are stacks of forms

A head is roughly a sphere. An arm, a tree trunk, a barrel or a pipe is a cylinder. A crate, a house or a stone step is a cube. Before shading a complex sprite, decide which form each part is closest to, then shade each part by that form's rule with the same light. Where two parts meet, check that they do not end up in the same shade, or they merge into one blob.

Rule of thumb

Ask "which way does this part turn?" Both ways: shade it like a sphere. One way: stripes, like a cylinder. Not at all: one flat shade per face, like a cube.

The code

Each form is a small function that answers one question for a pixel: which way does it face? The shading function is the same for all three. This LÖVE program draws the demo's three 24 by 24 forms at 8x with the 4-step ramp and the same light.

local LIGHT_ANGLE, LIGHT_HEIGHT = 135, 20   -- from the top left, fairly low
local a, e = math.rad(LIGHT_ANGLE), math.rad(LIGHT_HEIGHT)
local LX, LY, LZ = math.cos(e) * math.cos(a), -math.cos(e) * math.sin(a), math.sin(e)

local function rgb(r, g, b) return { r / 255, g / 255, b / 255 } end
local RAMP = { rgb(29, 31, 58), rgb(48, 90, 96), rgb(94, 154, 112), rgb(198, 212, 142) }

-- Facing (a dot product from -1 to 1) turned into a ramp step 1..#RAMP.
local function step(nx, ny, nz)
  local d = nx * LX + ny * LY + nz * LZ
  local t = math.max(0, math.min(1, (d + 0.3) / 1.3))
  return math.min(#RAMP, math.floor(t * #RAMP) + 1)
end

-- Each form answers: which way does pixel (x, y) face? nil means empty.
local function sphere(x, y)
  local u, v = (x + 0.5 - 12) / 10.5, (y + 0.5 - 12) / 10.5
  local d2 = u * u + v * v
  if d2 <= 1 then return u, v, math.sqrt(1 - d2) end   -- turns both ways
end

local function cylinder(x, y)
  local px, py = x + 0.5, y + 0.5
  local u = (px - 12) / 8
  if math.abs(u) > 1 then return nil end
  if u * u + ((py - 5) / 3) ^ 2 <= 1 then return 0, -1, 0 end   -- flat top
  if py < 5 or (py > 20 and u * u + ((py - 20) / 3) ^ 2 > 1) then return nil end
  return u, 0, math.sqrt(1 - u * u)              -- turns across only
end

local function cube(x, y)                        -- one direction per face
  if y >= 3 and y <= 8 and x >= 12 - y and x <= 25 - y then return 0, -1, 0 end
  if x >= 3 and x <= 16 and y >= 9 and y <= 22 then return 0, 0, 1 end
  if x >= 17 and x <= 22 and y >= 25 - x and y <= 38 - x then return 1, 0, 0 end
end

function love.draw()
  for i, form in ipairs({ sphere, cylinder, cube }) do
    for y = 0, 23 do
      for x = 0, 23 do
        local nx, ny, nz = form(x, y)
        if nx then
          love.graphics.setColor(RAMP[step(nx, ny, nz)])
          love.graphics.rectangle("fill", (i - 1) * 216 + 24 + x * 8, 24 + y * 8, 8, 8)
        end
      end
    end
  end
end

The highlighted lines are the three rules. The sphere's direction depends on both u and v, the cylinder's only on u, and the cube's is a constant per face. The numbers 0.3 and 1.3 in step are my choice: they make anything facing a little away from the light fall into the darkest step. They are not a standard. In a real game you would bake this once into an image rather than redraw it every frame.

Pitfalls

  • Shading everything like a sphere. A blend from corner to corner on a box makes it look soft and swollen. Flat faces usually get flat shades, with the change at the edge.
  • Gradients across a flat face. Grading a face from light to dark tells the eye the face bends. At sprite sizes even a slight one usually reads as a curve.
  • Too few shades for the form. Two shades cannot separate three cube faces. Either add a step, or let an outline or a one-pixel edge highlight mark the missing edge.
  • Too many shades for the size. On a 16 pixel sprite, five steps on a sphere make bands only one or two pixels wide, which reads as noise. Three or four is the common range at that size.
  • Parts that merge. When two forms meet in the same shade, the edge between them disappears. Darken the contact with a pixel of shadow, or shift one part a step.

In real games

Look at the crates in almost any 2D game with shaded tiles: usually one flat colour per side. Pipes and pillars are usually vertical stripes, and orbs and bombs carry curved bands and a highlight.

Some games skipped hand shading entirely and built sprites from lit 3D models. Donkey Kong Country (Rare, 1994) is the famous example: its characters were rendered from 3D models and then reduced to sprites, so the shading follows the forms exactly as in the code above. Engines such as Godot and Unity can also light 2D sprites at runtime using a normal map, an image that stores the facing direction of each pixel.

Your turn (15 minutes)

Pick one sprite of 16 to 32 pixels, such as a character, a barrel or a lamp. On a copy, paint over each part in a flat colour coded by form: one colour for sphere parts, one for cylinders, one for cubes.

Then shade the sprite again with your ramp and your chosen light, following each form's rule: curved bands on spheres, stripes on cylinders, one shade per face on cubes. You are done when every flat face is a single shade, every cylinder has straight bands, and at 1x no two touching parts merge into one shape.

Takeaways

  • Shade comes from which way a surface faces, so the form decides the pattern, not the outline.
  • A sphere turns in both directions: curved bands, and it can use every step of the ramp.
  • A cylinder turns in one direction: straight stripes along its length, with a separate shade for a flat end.
  • A cube does not turn: one flat shade per face, at most three shades, and the form shows at the edges.
  • Complex sprites are built from these three; shade each part by its form with one shared light.

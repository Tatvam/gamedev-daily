Hue, saturation and value: three questions for every colour

How to describe any colour as hue, saturation and value, and why those three dials are easier to steer than red, green and blue numbers.

You draw a red potion and want its shadow a little darker. You nudge the red number down, and the shadow turns brown. You nudge green and blue as well, and now it looks purple. Then you want a blue potion and have to start over. You are steering with the wrong three dials.

Red, green and blue describe the screen, not the colour

A screen makes every colour by mixing red, green and blue light. A colour is stored as three numbers from 0 to 255, its RGB values. That is perfect for the hardware and awkward for a painter, because the questions you actually ask, such as "darker", "duller" or "more orange", each need all three numbers to move together, by different amounts.

Take the potion's red, RGB 191, 48, 72. Here is what three everyday changes do to those numbers:

Every RGB column changed, yet each wish was one idea. The right-hand column shows the same changes described with three different dials, where each wish moves exactly one number.

The three dials

HSV describes a colour with three numbers that match how painters talk about it:

  • Hue answers "which colour?" It is an angle on a colour wheel, from 0 to 360 degrees: 0 is red, 60 yellow, 120 green, 180 cyan, 240 blue and 300 magenta. Because it is a wheel, 360 is red again, so 350 is a red leaning towards pink.
  • Saturation answers "how much colour, and how much grey?" At 0% the colour is a pure grey. At 100% it is as vivid as that hue can be.
  • Value answers "how much light?" At 0% every colour is black. At 100% it is the brightest version of that hue the screen can show.

Under the hood, HSV is just RGB rearranged. Value is the largest of the three RGB channels, and saturation is the gap between the largest and the smallest channel, as a fraction of the largest. Every HSV colour converts to exactly one RGB colour; the code below does it.

Ask the three questions in order

When a colour in a sprite looks wrong, ask which dial is wrong before touching anything:

  1. Is it too light or too dark? Change value. This is the one that most often decides whether a sprite reads at all, which is why the next lesson is about value alone.
  2. Is it too loud or too grey? Change saturation. Large areas such as walls and skies usually sit at lower saturation, so small things such as pickups can be vivid and stand out.
  3. Is it the wrong colour family? Change hue. Small hue changes, 10 to 20 degrees, are also how shadows and highlights get their richness, a trick a later lesson covers in full.

HSB, HSV and HSL

Many editors label this model HSB, with B for brightness. HSB and HSV are the same thing. HSL is a different model: in it, lightness 100% is always white, while in HSV value 100% is the brightest version of the hue. Check which one your editor shows before copying numbers between tools.

Why this works so well for pixel art

A sprite usually stores palette indexes, small numbers that say "colour 3", rather than colours. Change palette entry 3 and every pixel that uses it changes at once. Combined with HSV, recolouring a whole object is one slider: shift the hue of the body colour and let its shadow and light keep their distance from it.

Try it

The potion uses six palette entries. With Liquid body selected, drag Hue all the way round and watch the whole liquid change family: its shadow and light follow, because they are stored as distances from the body. Then lower Saturation to 0 and the liquid turns to greys that still look shaded. Compare Original and Yours at 1x in the previews.

Then pick one entry, such as Cork, from the menu or by clicking its swatch, and watch the RGB readout: one slider moves, but two or three RGB numbers change. You can also drag in the square and on the hue strip.

The code

LÖVE wants colours as red, green and blue from 0 to 1, so the game can keep its palette in HSV and convert when drawing. This is the demo's potion with the same numbers. The arrow keys turn hue and value and Z and X change saturation, all for the liquid body; the shadow and light keep their offsets.

local SCALE = 16
local SPRITE = {
  "................", "......1111......", ".....166661.....", ".....166661.....",
  "......15.1......", "....115...11....", "...1.5......1...", "..154444444431..",
  "..154333333321..", ".15433333333321.", ".14333333333321.", ".13333333333221.",
  ".13333333333221.", "..133333332221..", "...1222222221...", "....11111111....",
}

-- Hue in degrees (0-360), saturation and value in percent (0-100).
local palette = {
  [1] = { h = 260, s = 40, v = 22 },   -- outline
  [5] = { h = 0,   s = 0,  v = 97 },   -- glass shine
  [6] = { h = 30,  s = 45, v = 65 },   -- cork
}
local liquid = { h = 350, s = 75, v = 75 }   -- entry 3, the body
local OFFSETS = {                            -- liquid entries, relative to the body
  [2] = { h = -20, s = 5,   v = -30 },  -- shadow
  [3] = { h = 0,   s = 0,   v = 0 },    -- body
  [4] = { h = 15,  s = -20, v = 20 },   -- light
}

local function clamp(x, lo, hi) return math.max(lo, math.min(hi, x)) end

local function hsvToRgb(h, s, v)
  s, v = s / 100, v / 100
  local c = v * s                          -- distance from grey to the pure colour
  local hp = (h % 360) / 60                -- which sixth of the wheel
  local x = c * (1 - math.abs(hp % 2 - 1))
  local r, g, b
  if hp < 1 then r, g, b = c, x, 0
  elseif hp < 2 then r, g, b = x, c, 0
  elseif hp < 3 then r, g, b = 0, c, x
  elseif hp < 4 then r, g, b = 0, x, c
  elseif hp < 5 then r, g, b = x, 0, c
  else r, g, b = c, 0, x end
  local m = v - c                          -- lift everything up to the value
  return r + m, g + m, b + m
end

local function colourOf(i)
  local o = OFFSETS[i]
  if o then
    return hsvToRgb(liquid.h + o.h, clamp(liquid.s + o.s, 0, 100), clamp(liquid.v + o.v, 0, 100))
  end
  local p = palette[i]
  return hsvToRgb(p.h, p.s, p.v)
end

function love.keypressed(key)
  if key == "right" then liquid.h = (liquid.h + 10) % 360 end
  if key == "left" then liquid.h = (liquid.h - 10) % 360 end
  if key == "up" then liquid.v = clamp(liquid.v + 5, 0, 100) end
  if key == "down" then liquid.v = clamp(liquid.v - 5, 0, 100) end
  if key == "x" then liquid.s = clamp(liquid.s + 5, 0, 100) end
  if key == "z" then liquid.s = clamp(liquid.s - 5, 0, 100) end
end

function love.draw()
  for y = 1, #SPRITE do
    for x = 1, #SPRITE[y] do
      local i = tonumber(SPRITE[y]:sub(x, x))   -- "." gives nil: leave it empty
      if i then
        love.graphics.setColor(colourOf(i))
        love.graphics.rectangle("fill", 20 + (x - 1) * SCALE, 20 + (y - 1) * SCALE, SCALE, SCALE)
        love.graphics.rectangle("fill", 300 + x, 20 + y, 1, 1)   -- real size
      end
    end
  end
end

In Lua, % always returns a result with the sign of the divisor, so (0 - 10) % 360 is 350 and the hue wraps round the wheel in both directions.

Pitfalls

  • Treating value as brightness. Pure yellow and pure blue both have value 100%, yet yellow looks far brighter. A common rough measure, luma, gives about 226 out of 255 for yellow and 29 for blue. Two colours with equal value can still be very different in lightness, so check with your eye, or in greyscale, which is the next lesson.
  • Darkening by value alone. Dropping only value works, but the result often looks muddy. Shadows usually look better when saturation and hue move a little too, which is why the potion's shadow is 20 degrees round the wheel and a bit more saturated.
  • Hue on greys does nothing. At saturation 0 the hue is ignored, and at value 0 everything is black. If dragging hue seems broken, check the other two dials.
  • Mixing up HSV and HSL numbers. The same three numbers give a different colour in each model. Copy hex codes or RGB between tools instead.

In real games

Common image editors, including Aseprite, Photoshop and GIMP, offer a hue, saturation and value (or brightness) view in their colour pickers next to RGB, so you can choose with one model and store the result in the other.

Shifting the hue of a sprite's colours is also a cheap way to make enemy variants and team colours from one drawing, an idea the later lesson on palette swapping builds on.

Your turn (15 minutes)

Open any small sprite you have made. For each colour in its palette, write down its hue, saturation and value from your editor's picker. Then make a second version of the sprite for a different team or element, such as a fire and an ice variant, by changing only the hue of the main colours. Keep saturation and value as they were.

You are done when both versions sit side by side at 1x, read as the same object, and you could describe the difference between them in one sentence about hue alone.

Takeaways

  • RGB is how screens store colour; HSV is a rearrangement that matches how painters think.
  • Hue is the colour family (an angle, 0 to 360), saturation is how far from grey, value is how much light.
  • When a colour looks wrong, decide which of the three dials is wrong before changing anything.
  • Value is not perceived brightness: yellow and blue at the same value look very different.
  • Storing palette entries as offsets from a base colour lets one hue change recolour a whole object.

Sharing colours between ramps

How one colour can be a step in several ramps at once, which steps are safe to share, and how four materials fit in 10 colours instead of 16.

You built a clean four-step ramp for wood, another for clay, another for stone and another for grass. That is 16 colours for one small courtyard, and the darkest step of each ramp is a near-black that nobody could tell apart from the others. You are paying four times for one colour.

A ramp is a list of pointers, not a list of colours

A ramp is an ordered run of colours from dark to light that shades one material. Earlier lessons built each ramp on its own, but a ramp does not have to own its colours. It only needs, at each step, a colour with the right value (lightness) and a hue that fits.

So think of a ramp as a list of choices from the palette: "for wood, step 1 is this colour, step 2 is that one". When two ramps make the same choice for a step, they share that colour. The palette gets shorter; the pixels barely change.

A palette map like this one, with ramps as rows, is the easiest way to see your sharing.

Which steps are safe to share

A colour can join a ramp only if it has the value that step needs. The rule the demo checks is simple: in every ramp, each step must still be clearly lighter than the one before. Break that and the ramp stops shading: a "shadow" pixel that is lighter than the mid-tone reads as a highlight, and the form turns inside out.

Within that rule, some steps share much more easily than others:

  1. The darkest step. Near the bottom of a ramp, colours lose most of their saturation (the lesson on saturation across a ramp showed why), so different materials end up with nearly the same dark. One shared dark, usually a slightly cool one, often doubles as the outline colour.
  2. The lightest step. Highlights are also low in saturation. Materials of similar hue, like wood and clay here, can share one.
  3. Shadows of neighbouring hues. The teal grey works for both stone and grass because its hue sits between the stone's blue-grey and the grass's green. It is also where hue shifting would push a green shadow anyway: towards blue.
  4. The mid-tone, rarely. The mid-tone is the most saturated step and covers the most pixels, so it is what says "this is wood" or "this is clay". It is usually the last step to share.

What sharing buys you

Fewer colours is the obvious gain. Two others matter as much. A scene where every material falls to the same dark looks lit by one light, because the shadows agree. And a shared colour is one palette entry, so changing it changes every ramp that uses it.

Rule of thumb

Share from the ends of the ramps inwards. Share the dark first, then the light, then the shadow steps between neighbouring hues. Keep each material's mid-tone its own.

This is a convention, not a law. A large palette with no sharing at all can look fine. What usually goes wrong is the opposite extreme: share so much that two materials have identical ramps, and the player can no longer tell the crate from the pot.

The code

In a game or a palette tool, store sharing the way the diagram draws it: one list of colours, and ramps that point into it by index. A sprite then stores a ramp and a step, and asks RAMPS[r].steps[s] for its palette index. This LÖVE program draws the demo's suggested palette map, counts the colours and runs the same ramp check, with the same minimum gap of 12.

-- One palette of 10 colours (0 to 255). Ramps point into it by index.
local PALETTE = {
  {46, 34, 51},    -- 1 shared dark (every ramp)
  {94, 58, 52},    -- 2 warm brown (wood and clay)
  {148, 96, 63},   -- 3 wood mid
  {201, 150, 95},  -- 4 tan light (wood and clay)
  {184, 87, 58},   -- 5 clay mid
  {71, 91, 90},    -- 6 teal grey (stone and grass)
  {125, 135, 150}, -- 7 stone mid
  {195, 200, 196}, -- 8 stone light
  {108, 148, 64},  -- 9 grass mid
  {182, 207, 106}, -- 10 grass light
}

local RAMPS = {
  { name = "Wood",  steps = {1, 2, 3, 4} },
  { name = "Clay",  steps = {1, 2, 5, 4} },
  { name = "Stone", steps = {1, 6, 7, 8} },
  { name = "Grass", steps = {1, 6, 9, 10} },
}

local MIN_GAP = 12
local SIZE = 32

local function luma(c)
  return 0.299 * c[1] + 0.587 * c[2] + 0.114 * c[3]
end

-- Every step must be clearly lighter than the step before it.
local function checkRamp(ramp)
  for i = 2, #ramp.steps do
    local darker = PALETTE[ramp.steps[i - 1]]
    local lighter = PALETTE[ramp.steps[i]]
    if luma(lighter) - luma(darker) < MIN_GAP then
      return "step " .. i .. " is not lighter than step " .. (i - 1)
    end
  end
  return "ok"
end

local function countColours()
  local used, n = {}, 0
  for _, ramp in ipairs(RAMPS) do
    for _, index in ipairs(ramp.steps) do
      if not used[index] then
        used[index] = true
        n = n + 1
      end
    end
  end
  return n
end

function love.draw()
  love.graphics.setColor(1, 1, 1)
  love.graphics.print("Colours: " .. countColours() .. " (16 without sharing)", 20, 12)
  for r, ramp in ipairs(RAMPS) do
    local y = 40 + (r - 1) * (SIZE + 8)
    love.graphics.setColor(1, 1, 1)
    love.graphics.print(ramp.name, 20, y + 8)
    for s, index in ipairs(ramp.steps) do
      local c = PALETTE[index]
      love.graphics.setColor(c[1] / 255, c[2] / 255, c[3] / 255)
      love.graphics.rectangle("fill", 80 + (s - 1) * (SIZE + 4), y, SIZE, SIZE)
    end
    love.graphics.setColor(1, 1, 1)
    love.graphics.print(checkRamp(ramp), 240, y + 8)
  end
end

The highlighted table is the whole idea. Sharing is a repeated number: the 1 in every ramp, the 2 and 4 in wood and clay, the 6 in stone and grass. Change PALETTE[1] and four materials change together. Try making the grass ramp {1, 6, 2, 10} to see the check report the broken step.

Pitfalls

  • Sharing by hue, not by value. A colour whose hue fits can still have the wrong value. Check every link against the steps on both sides of it, in greyscale if unsure.
  • Sharing the mid-tones. The mid-tone tells the player what a material is. Share it and the crate and the pot become the same object in two shapes.
  • Edges that vanish. Where two materials touch, a shared colour on both sides of the border erases the edge. If an edge matters, make sure different steps meet there.
  • Sharing by eyedropper. A colour that is merely close to one in another ramp is a near duplicate, not a shared colour. Use the exact palette entry.
  • Forgetting the link exists. Retune the shared dark for the stone and you have retuned the wood too. Check every ramp that uses it.

In real games

Hardware once forced sharing. On the NES, the four background palettes all share one common backdrop colour, and each sprite palette holds only three colours plus transparency, so artists reused the same few colours across many objects. The PICO-8 fantasy console gives every game the same fixed 16 colours, so every ramp in a PICO-8 game is built from shared entries.

Today it is a habit of palette designers. Small published palettes such as DawnBringer's 16 and 32-colour palettes are often studied for the way a few colours combine into many ramps.

Your turn (15 minutes)

Pick three materials from your project that each have their own ramp. Draw a palette map: one row per ramp, dark on the left.

Link the darkest steps into one colour. Then look for one more pair, a light or a shadow step between neighbouring hues, that can share. Repaint the sprites with the shared entries. You are done when the map has at least two fewer colours, every ramp still goes clearly from dark to light in greyscale, and each material is still recognisable at 1x.

Takeaways

  • A ramp is a list of choices from the palette. Two ramps that choose the same colour share it.
  • A shared colour must have the right value for its step in every ramp that uses it.
  • Share from the ends inwards: the darkest step first, then the lights, then shadows between neighbouring hues.
  • Keep each material's mid-tone its own, so materials stay distinct.
  • Store ramps as indexes into one palette, so changing a shared colour updates every ramp at once.

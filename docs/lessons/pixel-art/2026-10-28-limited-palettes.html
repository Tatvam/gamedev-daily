Limited palettes: fewer colours, one look

Why a small palette gives a whole scene one look and speeds up your choices, and how to decide which colours survive when you cut from 32 to 4.

You drew the grass on Monday and the tree on Thursday. Each got its own carefully built ramp, and side by side they look as if they come from two different games. The cause is not the shading: the scene has too many colours that almost match.

A palette is a promise

A palette is the fixed list of colours a piece of art is allowed to use. A limited palette is one you keep deliberately small, often somewhere from 4 to 32 colours for a whole game or scene. Every pixel must be one of those colours, and nothing else.

Old hardware forced such limits. Today a limit is usually a choice, and a good one for three reasons.

1. Shared colours tie the scene together

When the grass and the leaves draw from the same greens, and the pond reuses the sky's blues, the eye reads them as lit by the same light in the same world. Separate ramps for every object drift apart, each a little warmer or a little more saturated than its neighbour, and the scene looks pasted together.

2. Fewer colours means faster, firmer decisions

In the 32-colour scene below, the lightest grass and the lightest leaf differ by about 8 points on a 0 to 255 scale (the readout in the demo uses a simple weighted difference of red, green and blue). Nobody sees that at 1x, but you still had to choose between them for every pixel. With 8 colours the closest pair is about 38 apart. Every colour now does a job no other colour can, and choosing one takes a glance instead of a squint.

3. The limit pushes you towards value

When you cannot add a colour, you solve problems with value. At 4 colours the demo scene has no hue to spare: it is four values with a green tint, and the red flowers become pale flowers that stand out by brightness alone. If the values read, the picture reads.

Which colours survive?

Cutting a palette is a series of decisions. A useful order:

  1. Merge near duplicates first. Two greens 8 points apart are one colour pretending to be two. These cuts are free.
  2. Share ramps between materials. The pond can reuse the sky's blues. The leaves can reuse the grass. The next lesson covers this in depth.
  3. Protect the accents. An accent is a small, strong colour that marks something important: a flower, a gem, the player's scarf. It covers few pixels, so it looks cheap to cut. It is usually the last colour you should give up.
  4. Keep the value range. Whatever you cut, keep a clear dark, a clear light and steps between them.

An automatic tool that reduces colours does not know any of this. The one in the demo merges the pair of colours that adds the least error, weighted by how many pixels use each. It does well on step 1. Then it throws away the red flowers at 12 colours, because they cover only 7 pixels. At 6 it averages the sun into the light greens and the tree trunk into the dark ones.

Rule of thumb

Start a project with a small palette, around 8 to 16 colours, and add a colour only when you can name the job it does that no existing colour can do.

This is a convention, not a law. Large palettes are fine for, say, subtle skin tones or a painterly style. What usually breaks without a limit is the whole: near duplicates make edges mushy, and objects drawn on different days stop matching.

The code

Hand-picking is the goal, but an automatic merge is a good way to find your near duplicates. This LÖVE program does what the demo's Automatic merge does: it counts the colours of scene.png, then repeatedly merges the pair with the lowest cost until TARGET colours remain. Press up and down to change the target. It uses the same weights as the demo.

local TARGET = 8
local ZOOM = 6
local original, reduced

-- Weighted difference between two colours (0 to 255 per channel), squared.
local function dist2(a, b)
  local dr, dg, db = a[1] - b[1], a[2] - b[2], a[3] - b[3]
  return (2 * dr * dr + 4 * dg * dg + 3 * db * db) / 9
end

-- groups: { rgb = {r, g, b}, n = pixel count, keys = {colours merged into it} }
local function mergeClosest(groups, target)
  while #groups > target do
    local best, bi, bj = math.huge, 0, 0
    for i = 1, #groups - 1 do
      for j = i + 1, #groups do
        local A, B = groups[i], groups[j]
        local cost = A.n * B.n / (A.n + B.n) * dist2(A.rgb, B.rgb)
        if cost < best then best, bi, bj = cost, i, j end
      end
    end
    local A, B = groups[bi], groups[bj]
    local n = A.n + B.n
    for k = 1, 3 do
      A.rgb[k] = (A.rgb[k] * A.n + B.rgb[k] * B.n) / n
    end
    A.n = n
    for _, key in ipairs(B.keys) do table.insert(A.keys, key) end
    table.remove(groups, bj)
  end
end

local function keyOf(r, g, b)
  return math.floor(r * 255 + 0.5) .. "," .. math.floor(g * 255 + 0.5) .. "," .. math.floor(b * 255 + 0.5)
end

local function reduce(data, target)
  local w, h = data:getWidth(), data:getHeight()
  local byKey, groups = {}, {}
  for y = 0, h - 1 do
    for x = 0, w - 1 do
      local r, g, b = data:getPixel(x, y)
      local key = keyOf(r, g, b)
      if not byKey[key] then
        byKey[key] = { rgb = { r * 255, g * 255, b * 255 }, n = 0, keys = { key } }
        table.insert(groups, byKey[key])
      end
      byKey[key].n = byKey[key].n + 1
    end
  end
  mergeClosest(groups, target)
  local newColour = {}
  for _, group in ipairs(groups) do
    for _, key in ipairs(group.keys) do newColour[key] = group.rgb end
  end
  for y = 0, h - 1 do
    for x = 0, w - 1 do
      local r, g, b, a = data:getPixel(x, y)
      local c = newColour[keyOf(r, g, b)]
      data:setPixel(x, y, math.floor(c[1] + 0.5) / 255, math.floor(c[2] + 0.5) / 255, math.floor(c[3] + 0.5) / 255, a)
    end
  end
  return #groups
end

local count

local function rebuild()
  local data = love.image.newImageData("scene.png")
  count = reduce(data, TARGET)
  reduced = love.graphics.newImage(data)
  reduced:setFilter("nearest", "nearest")
end

function love.load()
  original = love.graphics.newImage("scene.png")
  original:setFilter("nearest", "nearest")
  rebuild()
end

function love.keypressed(key)
  if key == "up" and TARGET < 32 then TARGET = TARGET + 1; rebuild() end
  if key == "down" and TARGET > 2 then TARGET = TARGET - 1; rebuild() end
end

function love.draw()
  love.graphics.setColor(1, 1, 1)
  love.graphics.draw(original, 20, 40, 0, ZOOM, ZOOM)
  love.graphics.draw(reduced, 40 + original:getWidth() * ZOOM, 40, 0, ZOOM, ZOOM)
  love.graphics.print("Colours: " .. count .. " (up / down to change)", 20, 12)
end

The cost line is the whole idea: a merge is cheap when the two colours are close or when one of them covers few pixels. That second part is why the tool sacrifices small accents, and why you should treat its result as a list of suggestions, not a finished palette. The merged colour is the pixel-weighted average of the two, so after many merges it can be a colour nobody picked. In statistics this greedy merge is known as Ward's method.

Pitfalls

  • Limiting at the end. Reducing a finished 60-colour scene is painful and loses detail. Pick the palette first and draw with it.
  • A small palette with no value range. Eight mid-tones give you a flat, muddy scene. Check the palette in greyscale: you want a clear dark, a clear light and even steps between.
  • Cutting the accent. The colour with the fewest pixels is often the one the player needs to notice. Count it as a job, not as a cost.
  • Trusting automatic reduction. It counts pixels, not meaning. Use it to find near duplicates, then decide yourself.
  • Sneaking colours back in. Filtered scaling or semi-transparent overlays in the engine create new colours on screen. If the limit matters, check what the screen shows.

In real games

Some limits came from hardware. The original Game Boy screen shows four shades. The PICO-8 fantasy console is built around one fixed 16-colour palette, and its games still look distinct from each other because of how those colours are shared. Classic hardware palettes get their own lesson later in this track.

Other limits are a style choice. Downwell draws its default look with black, white and red, and Return of the Obra Dinn renders its whole 3D world in two colours. Many artists also start from shared palettes such as DawnBringer's 16 and 32-colour palettes, which are collected with many others on the Lospec palette list.

Your turn (15 minutes)

Take a scene or a busy sprite sheet from your project and count its colours. Write a list of the jobs those colours do: sky, ground dark, ground light, skin, outline, accent, and so on.

Make a copy and cut it to at most 12 colours, in the order from the lesson: merge near duplicates, share ramps, protect the accent, keep the value range. You are done when the copy uses 12 colours or fewer, every colour on your list has a job, and the copy still reads as well as the original at 1x and in greyscale.

Takeaways

  • A limited palette gives every object the same colours to share, which makes the scene look like one world.
  • Near duplicates cost you decisions and add nothing a player can see. Merge them first.
  • Fewer colours push you to solve problems with value, which is what makes art read.
  • Protect small accent colours. Automatic reduction cuts them first because they cover few pixels.
  • Choose the palette before you draw, and add a colour only when it has a job no other colour can do.

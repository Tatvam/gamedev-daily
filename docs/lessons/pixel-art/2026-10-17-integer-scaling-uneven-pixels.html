Integer scaling: why some pixels come out fat

Why scaling pixel art by whole numbers keeps every pixel the same size, why 2.5× makes fat and thin pixels, and how to letterbox the leftover space.

You switched your game to nearest neighbour filtering, so the edges are sharp. But in a full-screen window the character's eyes are different sizes, a straight diagonal outline has a kink in it, and when the camera scrolls the tiles seem to ripple.

Nothing is blurred this time. Some of your pixels are simply bigger than others. This lesson shows why, and the one rule that prevents it.

A screen cannot draw half a pixel

A scale factor is how many screen pixels each art pixel should cover. At 3×, one art pixel becomes a 3 by 3 block. Scaling by a whole number like 2, 3 or 4 is called integer scaling.

Now try 2.5×. Each art pixel should be two and a half screen pixels wide, but a screen pixel is the smallest thing a monitor can light up. With nearest neighbour filtering, every screen pixel shows the one art pixel its centre falls inside. Count it out for a row of four art pixels and you get widths of 2, 3, 2, 3. The total is right, 10 screen pixels, but the art pixels inside it are not equal.

We will call the wider ones fat pixels. Which art pixels come out fat depends on the scale and on where the sprite sits, but at any scale that is not a whole number some must.

Why it hurts pixel art in particular

  • Matching details stop matching. Two eyes drawn the same can land on different mixes of thin and fat columns. In the demo at 1.5×, one eye gets a wide white and a thin pupil and the other gets the reverse, so the slime looks in two directions at once.
  • Clean lines get kinks. A diagonal built from equal steps of two art pixels turns into steps of 4 and 5 screen pixels at 2.3×, so the line looks wobbly even though you drew it perfectly.
  • Motion shimmers. When the camera moves by one art pixel, every art pixel moves to a new screen position, and the pattern of fat and thin columns slides across the art. Shapes seem to swell and shrink as they scroll.

The damage shrinks as the scale grows

At 1.5× the widths are 1 and 2: a fat pixel is twice the size of a thin one, which is impossible to miss. At 5.5× they are 5 and 6, a 20 percent difference that many players will not notice in a still image. Fractional scales hurt most at low zoom.

What to do with the leftover space

Windows rarely divide evenly by your game's resolution. Say the game is drawn at 320 by 180 pixels, a common size because it fits many 16:9 screens exactly:

  • On a 1920 by 1080 monitor the largest scale that fits is exactly 6×. Perfect.
  • On a 1366 by 768 laptop screen it would be 4.27×. Use 4× instead: the game fills 1280 by 720, and the 43 pixels on the left and right and 24 at the top and bottom stay empty.

Filling that leftover space with plain bars is called letterboxing (or pillarboxing, when the bars are at the sides). It is the usual choice for pixel art. The alternatives are to show a little more of the game world in the gap, or to accept a fractional scale and smooth only the final step. More world can reveal things you did not plan to show, and smoothing brings back a little blur.

Rule of thumb

Take the window size, divide by your game resolution, round down to a whole number, and centre the result. Rounding up would push part of the picture off the screen.

The code

The usual setup in LÖVE: draw the whole game into a small canvas at its own resolution, then draw that canvas to the window at the largest whole-number scale that fits, centred, with black bars around it.

local GAME_W, GAME_H = 320, 180
local canvas

function love.load()
  love.graphics.setDefaultFilter("nearest", "nearest")
  canvas = love.graphics.newCanvas(GAME_W, GAME_H)
end

-- The largest whole number that fits the window, never below 1.
local function integerScale(windowW, windowH)
  local s = math.floor(math.min(windowW / GAME_W, windowH / GAME_H))
  return math.max(1, s)
end

local function drawGame()
  -- Draw your level and sprites here, in game pixels (0..320, 0..180).
end

function love.draw()
  love.graphics.setCanvas(canvas)
  love.graphics.clear(0.66, 0.81, 0.89)
  drawGame()
  love.graphics.setCanvas()

  local w, h = love.graphics.getDimensions()
  local scale = integerScale(w, h)
  -- Centre it, and keep the offset on whole screen pixels too.
  local x = math.floor((w - GAME_W * scale) / 2)
  local y = math.floor((h - GAME_H * scale) / 2)
  love.graphics.clear(0, 0, 0)            -- the letterbox bars
  love.graphics.draw(canvas, x, y, 0, scale, scale)
end

And here is how the demo works out the width of each art column, in the same plain Lua. Columns are counted from 0 in the maths, and the table index adds 1. The rows use the same function.

-- How many screen pixels each art column covers at a given scale.
-- Screen pixel sx shows the art column under its centre, sx + 0.5.
local function columnWidths(artWidth, scale)
  local widths = {}
  for i = 1, artWidth do
    widths[i] = 0
  end
  local sx = 0
  while true do
    local col = math.floor((sx + 0.5) / scale)
    if col >= artWidth then
      break
    end
    widths[col + 1] = widths[col + 1] + 1
    sx = sx + 1
  end
  return widths
end

print(table.concat(columnWidths(12, 2.5), ", "))  --> 2, 3, 2, 3, ... (uneven)
print(table.concat(columnWidths(12, 2), ", "))    --> 2, 2, 2, 2, ... (even)

Pitfalls

  • Scaling every sprite on its own. Sprites drawn straight to the window, each with its own scale and position, can land between screen pixels. Drawing into one small canvas first puts everything on the same grid.
  • Rounding up. math.ceil or math.floor(x + 0.5) on the scale gives a picture bigger than the window, and the edges of the level are cut off.
  • An offset that is not whole. Centring with (w - GAME_W * scale) / 2 can give a half pixel when the gap is odd. Floor it, as the code does.
  • Forgetting high-DPI screens. Some operating systems scale whole windows by 125 or 150 percent for readability. The game can then be rescaled after you have done everything right. Check that your window reports its real pixel size (in LÖVE, the highdpi window setting is part of this) and test on such a screen if you can.
  • A resolution with no good fit. 320 by 180 divides 1280 by 720, 1920 by 1080 and 2560 by 1440 exactly. An odd size like 300 by 200 fits few screens, so most players see wide bars.

In real games

Many pixel art games and most emulators of older consoles offer an integer scaling option, because those old resolutions rarely fit modern screens exactly.

The engines have built-in support for the idea. Godot has stretch settings for pixel art projects, and recent versions add an integer option to them; the Godot documentation page on multiple resolutions covers this. Unity's 2D tools include a Pixel Perfect Camera component made for this problem. Option names change between versions, so check the documentation.

Set up the canvas and integerScale from the code in your own project, with a 320 by 180 game resolution and a sprite in the middle. Make the window resizable (in LÖVE, t.window.resizable = true in conf.lua).

Drag the window edges slowly. You are done when the picture jumps between sizes in whole steps, stays centred with bars around it, and a screenshot opened in your pixel editor shows every art pixel as a square of exactly the same size.

Takeaways

  • A screen can only light whole pixels, so at a fractional scale some art pixels must come out wider than others.
  • Uneven pixels break matching details and clean lines, and they make scrolling shimmer.
  • The difference is worst at low scales: 1.5× makes pixels of 1 and 2, while 5.5× makes 5 and 6.
  • Round the scale down to a whole number, centre the picture on a whole pixel, and fill the rest with bars.

Classic hardware palettes: Game Boy, NES and PICO-8

What the Game Boy, NES and PICO-8 palettes allow, and how to move a scene onto a fixed palette with nearest colour matching and a few fixes by hand.

You want your game to look like it runs on a Game Boy, so you drop a four-colour green filter over your finished art. The hero's red hood comes out pale, lighter than the grass around it, and the character stops standing out. Every colour is a "correct" Game Boy colour, but the picture is wrong.

Old consoles did not let artists choose any colour they liked. This lesson shows what those fixed palettes were, and how to move art onto one without wrecking it.

Palettes you could not choose

A fixed palette is a set of colours built into the hardware. Every pixel on screen must be one of them, and the artist cannot add another. Three palettes are worth knowing:

  • Game Boy (1989). Each pixel stores 2 bits, so it can be one of 4 shades. The screen had a green tint, so they run from dark olive to pale yellow-green. Real screens vary, so the RGB values used by emulators and by this lesson are approximations.
  • NES (1983 in Japan as the Famicom). The picture chip has 64 colour entries, about 54 of them distinct, because several are duplicates of black. The NES sent a TV signal, not RGB numbers, so emulators each use their own approximation. The demo uses one widely shared one.
  • PICO-8 (2015). A fantasy console by Lexaloffle: a made-up console that runs on your computer. Its 16 colours are defined exactly. Newer versions can swap in 16 extra colours, but a screen still shows 16 at a time.

Fewer colours than the palette has

The NES palette looks generous, but a game could not use it freely. Each sprite (a moving object such as the player) picks one of four small palettes of 3 colours, plus transparent. The background is split into areas of 16 by 16 pixels, and each area picks one of four palettes of 3 colours plus one backdrop colour shared by the whole screen. Without tricks, that gives at most 25 colours on screen at once, and only 3 or 4 inside any one area.

This is why NES characters are usually drawn in three colours, often a dark, a mid-tone and a light, and why games sometimes stack two sprites to get more colours on a hero. Artists drew for the limits from the first pixel.

Moving art onto a fixed palette

If you already have art, the usual first step is nearest colour matching: for each colour in your art, find the closest palette colour and use that instead. Because the art stores palette indexes, you do this once per entry, not once per pixel: a small table that says "my colour 13 becomes palette colour 2".

The question is what "closest" means. Two measures cover most cases:

  • Nearest RGB colour. Treat red, green and blue as a position in space and pick the palette colour with the smallest distance. Good when the palette has many hues, like the NES or PICO-8.
  • Brightness only. Ignore hue and compare how light each colour is. First stretch both sets so that the darkest colour counts as 0 and the lightest as 1, then pick the nearest number. Good when the palette is a row of shades, like the Game Boy.

RGB distance looks for a similar colour, and a green palette has nothing like red. On a palette of shades, the thing worth keeping is value, how light or dark each colour is, which is what makes a sprite readable.

Then fix it by hand

Matching is a starting point. Usually two problems are left:

  • Merges. Two colours that must stay apart land on the same entry, such as the sun and the sky behind it.
  • Wrong hue. A colour lands in the wrong family, such as grass that turns grey because grey was slightly closer than any green.

Fix these by changing single entries in the table, not by repainting pixels. One change recolours every pixel with that index.

Rule of thumb

Match by brightness when the palette is a ladder of shades, and by RGB when it has many hues. Then look at the result at 1x and fix the few entries that merged or changed family.

Try it

Start on Game Boy with Nearest RGB colour. The hood turns light, lighter than the grass, and Brightness flips counts 3 pairs of colours whose dark-light order clearly reversed. Switch Match by to Brightness only: the flips drop to none and the hood reads as dark again.

Now press PICO-8 and keep Brightness only. The order is kept, but the sky turns grey-violet and the grass brown and pink, because hue was ignored. Go back to Nearest RGB colour: the sky is blue, but the grass is grey and the hood brown. Turn on Hand fixes to change five entries by hand.

The code

This is the demo's matching in Lua for LÖVE, cut down to six of the scene's colours. Outline and cloud are the darkest and lightest of the full set too, so the stretched brightness values match the demo. The result is a table from scene index to palette index; drawing looks each pixel up through it.

-- Scene colours as drawn. The level stores indexes into this table.
local source = {
  {90, 150, 220},   -- 1 sky
  {245, 245, 240},  -- 2 cloud
  {80, 160, 70},    -- 3 grass
  {205, 165, 110},  -- 4 path
  {205, 50, 55},    -- 5 red hood
  {30, 25, 40},     -- 6 outline
}
-- Game Boy shades, dark to light (one common approximation).
local GAMEBOY = { {15, 56, 15}, {48, 98, 48}, {139, 172, 15}, {155, 188, 15} }

local function luma(c) return 0.299 * c[1] + 0.587 * c[2] + 0.114 * c[3] end

local function rgbDistance(a, b)
  local dr, dg, db = a[1] - b[1], a[2] - b[2], a[3] - b[3]
  return dr * dr + dg * dg + db * db
end

-- Brightness from 0 (darkest in this palette) to 1 (lightest).
local function relativeLumas(pal)
  local lo, hi = math.huge, -math.huge
  for _, c in ipairs(pal) do lo = math.min(lo, luma(c)); hi = math.max(hi, luma(c)) end
  local out = {}
  for i, c in ipairs(pal) do out[i] = (luma(c) - lo) / math.max(hi - lo, 1) end
  return out
end

local function buildMap(src, target, byBrightness)
  local sv, tv = relativeLumas(src), relativeLumas(target)
  local map = {}
  for i, c in ipairs(src) do
    local best, bestD = 1, math.huge
    for j, t in ipairs(target) do
      local d = byBrightness and math.abs(sv[i] - tv[j]) or rgbDistance(c, t)
      if d < bestD then best, bestD = j, d end
    end
    map[i] = best
  end
  return map
end

local map = buildMap(source, GAMEBOY, true)
map[5] = 2   -- hand fix: keep the hood on shade 2 whichever way we matched
local level = { {1, 1, 2, 2}, {1, 5, 5, 1}, {3, 4, 4, 3} }
local Z = 8

function love.draw()
  for y, row in ipairs(level) do
    for x, index in ipairs(row) do
      local c = GAMEBOY[map[index]]
      love.graphics.setColor(c[1] / 255, c[2] / 255, c[3] / 255)
      love.graphics.rectangle("fill", (x - 1) * Z, (y - 1) * Z, Z, Z)
    end
  end
end

The and ... or line is safe because both distances are numbers, never nil. Brightness matching gives sky, grass and hood shade 2, path shade 3, cloud shade 4 and outline shade 1. A real game would draw tiles, and could do the lookup in a shader, as the later lesson on palette swapping shows.

Pitfalls

  • Treating RGB distance as what the eye sees. Plain RGB distance treats a step in blue the same as a step in green, though the eye is far more sensitive to green. Weighted formulas do better, but none replaces looking.
  • Remapping pixel by pixel. Matching every pixel of a painted image with soft gradients gives speckled noise where neighbours fall either side of a boundary. Match the entries of indexed art instead.
  • Forgetting the per-sprite limits. Matching a hero onto the NES palette can give it eight "NES colours". A real NES sprite shows 3 plus transparent. For the authentic look, respect the per-sprite and per-area limits too.
  • Copying one emulator's numbers as the truth. Game Boy and NES colours vary between screens, TVs and emulators. Pick one approximation and use it consistently.

In real games

The Game Boy Color could show original Game Boy games in colour by mapping their four shades to built-in colour sets, and the player could pick a set with a button combination at start-up. The game still thought in four shades; the hardware chose the colours.

PICO-8 shows that a fixed palette can be a style rather than a hardware limit. Celeste began as a PICO-8 game by Matt Thorson and Noel Berry in 2015 and is drawn entirely in the 16 PICO-8 colours. Many modern games pick a small published palette in the same spirit.

Your turn (15 minutes)

Take one sprite from your project in indexed colour mode. Make a copy and set each palette entry to the nearest Game Boy shade by eye, judging only brightness. Make a second copy and do the same with the 16 PICO-8 colours, keeping each colour in its own family.

Look at both at 1x next to the original. Change at most three entries in each to fix merges and wrong hues. You are done when each copy reads as clearly as the original at its real size.

Takeaways

  • A fixed palette is built into the hardware: every pixel must be one of its colours. The Game Boy has 4 shades, the NES about 54 colours with only 3 per sprite, PICO-8 exactly 16.
  • Game Boy and NES colours have no single true RGB value; use an approximation and say which.
  • Nearest colour matching moves art onto a palette one entry at a time. Match by brightness for a ladder of shades and by RGB for a palette of many hues.
  • Matching is a first pass. Fix the entries that merged or changed family, and judge at 1x.

Avoiding pillow shading: shade from the light, not the outline

Why shading inwards from the outline makes a sprite look flat and puffy, how to spot it, and how shading from one light direction fixes it.

You shade a rock with a dark ring inside the outline, a middle ring inside that, and a light blob in the centre. It uses your ramp, yet the rock looks like a stuffed cushion lit by a different world from your other sprites. The colours are fine. The bands follow the wrong thing.

Bands that copy the outline

Pillow shading is shading where the dark tones hug the outline on every side and the tones get lighter towards the middle, whatever direction the light comes from. The name comes from the result: a puffed-up shape like a pillow, stitched at the edges.

It is a natural mistake, because the outline is the only thing you can see on the canvas. The form underneath and the light have to be imagined. So the hand follows the outline, and every band becomes a smaller copy of it.

Why it looks wrong

Three things go wrong at once.

  • There is no light. It does not match the light you chose for the rest of the game, so the sprite looks pasted in.
  • The form goes flat. Shading should tell the eye which way the surface faces. Rings that copy the outline add nothing: a rock, a head and a barrel with the same silhouette get identical shading.
  • The edge gets heavy. A dark ring all the way round acts like a thick, smudged outline and eats pixels you need for detail.

A sphere lit from straight in front does get round bands centred in the middle. That is a real light behind the camera, and it still follows the form: a box lit the same way gets one flat shade on its front face, not rings.

The fix, step by step

  1. Decide where the light is before placing a shade. Top left is a common choice.
  2. Find the shadow side. Parts facing away from the light get the dark tones: a wide band there, none on the lit side.
  3. Let the light reach the edge. On the lit side the light tones usually run up to the outline. If that edge vanishes into the background, fix it with the outline, not a dark band.
  4. Move the brightest spot towards the light, where the surface faces it most directly. It is only centred if the light is in front.
  5. Shade each part by its form, as in the last lesson, with no dark ring around each part.

Rule of thumb

Hide the outline and look at the shading alone. If you cannot tell where the light comes from, it is pillow shading. If your darkest shade touches the outline all the way round, it almost certainly is.

Try it

The code

This LÖVE program builds the demo's gourd and shades it both ways. The pillow version only knows the distance to the nearest empty pixel; the lit version needs each pixel's facing and the light. BLEND is the slider. The shading is worked out once in love.load.

local SIZE, ZOOM, BLEND = 24, 8, 1.0       -- BLEND: 0 = pillow, 1 = lit
local a, e = math.rad(135), math.rad(20)   -- light from the top left, fairly low
local LX, LY, LZ = math.cos(e) * math.cos(a), -math.cos(e) * math.sin(a), math.sin(e)
local RAMP = { { 0.11, 0.12, 0.23 }, { 0.19, 0.35, 0.38 }, { 0.37, 0.60, 0.44 }, { 0.78, 0.83, 0.56 } }
local BALLS = { { 12, 15.5, 7.5 }, { 12, 7, 4.5 } }   -- two spheres: x, y, radius

-- Which way does pixel (x, y) face? Uses the sphere nearest the viewer. nil = empty.
local function normal(x, y)
  local best, bestZ
  for _, b in ipairs(BALLS) do
    local u, v = (x + 0.5 - b[1]) / b[3], (y + 0.5 - b[2]) / b[3]
    local d2 = u * u + v * v
    if d2 <= 1 and (not bestZ or math.sqrt(1 - d2) * b[3] > bestZ) then
      best, bestZ = { u, v, math.sqrt(1 - d2) }, math.sqrt(1 - d2) * b[3]
    end
  end
  return best
end

-- How far is pixel (x, y) from the nearest empty pixel?
local function edgeDistance(x, y)
  local best = math.huge
  for oy = -1, SIZE do
    for ox = -1, SIZE do
      if not normal(ox, oy) then best = math.min(best, (ox - x) ^ 2 + (oy - y) ^ 2) end
    end
  end
  return math.sqrt(best)
end

local shade = {}
function love.load()
  local dist, maxD = {}, 1
  for y = 0, SIZE - 1 do
    for x = 0, SIZE - 1 do
      if normal(x, y) then
        dist[y * SIZE + x] = edgeDistance(x, y)
        maxD = math.max(maxD, dist[y * SIZE + x])
      end
    end
  end
  for i, d in pairs(dist) do
    local n = normal(i % SIZE, math.floor(i / SIZE))
    local pillow = (d - 1) / (maxD - 1)                           -- follows the outline
    local lit = (n[1] * LX + n[2] * LY + n[3] * LZ + 0.3) / 1.3   -- follows the light
    local t = math.max(0, math.min(1, pillow + (lit - pillow) * BLEND))
    shade[i] = math.min(#RAMP, math.floor(t * #RAMP) + 1)
  end
end

function love.draw()
  for i, s in pairs(shade) do
    love.graphics.setColor(RAMP[s])
    love.graphics.rectangle("fill", (i % SIZE) * ZOOM, math.floor(i / SIZE) * ZOOM, ZOOM, ZOOM)
  end
end

The highlighted lines are the whole lesson. pillow is 0 on the outline and 1 at the deepest point, and the light appears nowhere in it. lit is the facing test from the last two lessons (the 0.3 and 1.3 are my choice, not a standard). Set BLEND to 0 and change the light angle: nothing changes. That is pillow shading, written as code.

Pitfalls

  • Darkening the lit edge "so it shows up". That is the outline's job, or the background's, not a dark band on the side facing the light.
  • A highlight in the dead centre. Moving the bands but leaving the brightest spot in the middle keeps half the pillow look.
  • Rings around every part. A character can be pillow shaded part by part: a ring round the head, one round each arm. Shade every part from the same light, then add contact shadows where parts overlap.
  • Over-correcting. A shadow half in one flat dark colour flattens the form a new way and vanishes on dark backgrounds. Keep a mid-tone between light and darkest.
  • Equal bands side by side. Bands of the same width running in parallel show the pixel grid. That is banding, the next lesson.

In real games

"Pillow shading" is a term from pixel art critique rather than from game studios. You mostly meet it in tutorials and in forum feedback on beginners' sprites.

Glowing things, such as a fireball, a magic orb or a lamp, are the usual exception: they give off their own light, so they are usually brightest in the core and darker at the edge. That is also why pillow shading looks wrong on solid objects: it makes them look as if they glow.

Engines can light sprites at runtime with a normal map, an image that stores which way each pixel faces. Godot and Unity both support this for 2D sprites. The lighting maths they run is the same idea as the lit line above: the shade comes from the stored facing and the light, not from the outline. If the base colours are already pillow shaded by hand, though, that dark ring is still painted in and the engine light is added on top of it.

Your turn (15 minutes)

Take your oldest shaded sprite, or quickly pillow shade a 16 to 24 pixel rock on purpose. On a copy, paint the outline in the background colour and ask a friend where the light comes from. Then reshade it with your chosen light: a wide dark band on the far side only, light tones up to the lit edge, the brightest pixels moved towards the light.

You are done when the darkest shade no longer touches the outline on the lit side, and someone who sees only the shading can point to the light.

Takeaways

  • Pillow shading darkens every edge and lightens the middle, so the bands copy the outline instead of the form.
  • It reads as puffy and flat, it ignores the game's light, and the dark ring makes the edge heavy.
  • The test: hide the outline and see whether the light direction is still clear, or check whether the darkest shade rings the whole sprite.
  • The fix: shade from one light, keep the dark tones on the far side, let the light reach the near edge and move the highlight towards the light.
  • Glowing objects are the usual exception, because they really are brightest at the core.

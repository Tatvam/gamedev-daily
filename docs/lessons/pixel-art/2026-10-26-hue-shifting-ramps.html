Hue shifting: warm lights, cool shadows

How turning the hue of a ramp towards yellow in the lights and towards blue in the shadows makes shading richer than changing brightness alone.

You built a tidy ramp: one hue, even value steps, every band visible at 1x. Yet the sprite looks like plastic. The shadows are the same green with the lights turned down. Nothing is wrong with the values. The hue never moves, and that is what makes it look flat.

Let the hue travel along the ramp

Hue shifting means changing the hue a little at each step of a ramp, instead of keeping it fixed. The usual convention is simple: as the ramp gets lighter, turn the hue towards yellow, the warmest-looking hue; as it gets darker, turn it towards blue, the coolest-looking one. People call yellows, oranges and reds warm and blues and blue-greens cool, and that is all "temperature" means here.

The values stay where the last lesson put them. Only the hue of each step changes; the ladder of greys that shapes the form is untouched.

Why it looks better

There are two reasons, one from the world and one from the eye.

  • Outdoor light is often warm, and shadow is often cool. The lit side of an object is lit by the yellowish sun. The shadow side gets no direct sun; it is lit mostly by the blue sky. Painters used this long before pixel art existed.
  • A change of hue is extra information. In a straight ramp, neighbouring steps differ only in value. In a shifted ramp they differ in value and hue, so bands separate a little more clearly and the colours feel varied instead of tinted.

It is a convention, not a law. Under a cool light, such as moonlight or a blue neon sign, it flips. What matters is that every ramp in a scene agrees on the direction, because the shift tells the viewer what colour the light is.

Which way round the wheel

Hue is an angle on the colour wheel, from 0° to 359°. Yellow sits at 60° and blue at 240°, exactly opposite each other. For any base hue, move the lights towards 60° and the shadows towards 240°, each by the shorter way round the wheel.

Some examples of the shorter way round:

  • Green (130°): lights go down towards yellow-green, shadows go up through teal.
  • Orange-red (15°): lights go up towards orange and gold, shadows go down through red into crimson and purple.
  • Blue (240°): the shadows are already at the cool end and stay put. Yellow is exactly opposite, so the lights could go either way; the demo sends them towards cyan.

How much to shift

A common starting point is around 10° to 20° per step. Below about 5° is hard to see. At 30° per step the ends of a five-step ramp are 120° apart and stop reading as one material. Two more rules:

  • Stop at the target. If the base is already close to yellow, the lights reach 60° after one step and should stay there instead of sailing past into green.
  • Keep the greys. Yellow is much brighter than blue at the same HSV value. Rotate the hue and leave V alone, and a light step turned towards yellow gets brighter, breaking your even ladder. Adjust each shifted step's value until its grey matches the straight ramp's.

Rule of thumb

Build the straight ramp first and write down its greys. Then turn each step's hue a fixed amount per step, lights towards yellow and shadows towards blue, and nudge each step's value until its grey is back where it was.

Try it

Both slimes use the same base colour, the same five greys and the same pixels. The left one uses a straight ramp; the right one shifts its hue. Look at the 1x previews first, then try:

  • Turn on Show in greyscale. The two slimes become identical, proving that only hue changed.
  • Set Base hue to 15 (clay) and then 240 (blue) and watch which way the markers on the hue strip travel.
  • Turn off Keep greys equal. The grey difference climbs and the lights glow brighter than the form deserves.
  • Push Hue shift to 30. The ramp becomes a rainbow.

The code

A hue shifted ramp is still just five colours, so it costs nothing at run time. This LÖVE program builds both ramps with the demo's starting numbers and draws the same slime at 8x. Press space to swap ramps; the sprite stores step numbers, not colours, so swapping is a palette swap by index.

local WARM, COOL = 60, 240                 -- yellow and blue, in degrees
local BASE_VALUE, STEP, STEPS = 0.65, 0.14, 5
local ZOOM = 8
local OUTLINE = { 0.12, 0.10, 0.14 }

local SLIME = {
  "................", "................", "................", "................",
  "......oooo......", "....oo5544oo....", "...o55544443o...", "..o5554444433o..",
  "..o5544444333o..", ".o544o444o3332o.", ".o444o443o3322o.", ".o444444333322o.",
  ".o444433333221o.", ".o433333222211o.", "o33332222221111o", ".oooooooooooooo.",
}

-- h in degrees, s and v from 0 to 1. Returns r, g, b from 0 to 1.
local function hsvToRgb(h, s, v)
  local c = v * s
  local hp = (h % 360) / 60
  local x = c * (1 - math.abs(hp % 2 - 1))
  local r, g, b = 0, 0, 0
  if hp < 1 then r, g = c, x
  elseif hp < 2 then r, g = x, c
  elseif hp < 3 then g, b = c, x
  elseif hp < 4 then g, b = x, c
  elseif hp < 5 then r, b = x, c
  else r, b = c, x end
  local m = v - c
  return r + m, g + m, b + m
end

local function luma(r, g, b)
  return 0.299 * r + 0.587 * g + 0.114 * b
end

-- Turn hue h up to `amount` degrees towards `target`, the short way round.
local function hueToward(h, target, amount)
  local d = (target - h + 540) % 360 - 180       -- -180 .. 179
  if math.abs(d) <= amount then return target end  -- stop at the target
  if d < 0 then amount = -amount end
  return (h + amount) % 360
end

local function buildRamp(hue, sat, shift)
  local ramp = {}
  local baseIndex = math.floor(STEPS / 2) + 1
  for i = 1, STEPS do
    local k = i - baseIndex                       -- -2 .. 2, 0 is the base
    local grey = luma(hsvToRgb(hue, sat, BASE_VALUE + k * STEP))
    local h = hue
    if k > 0 then h = hueToward(hue, WARM, k * shift) end
    if k < 0 then h = hueToward(hue, COOL, -k * shift) end
    -- same grey as the straight ramp, new hue
    local v = math.min(1, grey / luma(hsvToRgb(h, sat, 1)))
    ramp[i] = { hsvToRgb(h, sat, v) }
  end
  return ramp
end

local straight, shifted, current

function love.load()
  straight = buildRamp(130, 0.6, 0)
  shifted = buildRamp(130, 0.6, 15)
  current = shifted
end

function love.keypressed(key)
  if key == "space" then
    if current == shifted then current = straight else current = shifted end
  end
end

function love.draw()
  for y, row in ipairs(SLIME) do
    for x = 1, #row do
      local c = row:sub(x, x)
      if c ~= "." then
        if c == "o" then
          love.graphics.setColor(OUTLINE)
        else
          love.graphics.setColor(current[tonumber(c)])
        end
        love.graphics.rectangle("fill", 40 + (x - 1) * ZOOM, 40 + (y - 1) * ZOOM, ZOOM, ZOOM)
      end
    end
  end
end

Value scales red, green and blue together, so grey scales in proportion. That is why one division, grey / luma(hsvToRgb(h, sat, 1)), finds the value that puts a new hue at the old grey. The math.min catches the rare hue that cannot get that bright; that step comes out a little darker.

Pitfalls

  • Shifting hue without checking value. The most common mistake. The even steps quietly become uneven. Check the ramp in greyscale after every shift.
  • Too much shift. A rainbow ramp stops reading as one material: a green slime with blue shadows looks like it stands in a puddle. Pull back until the base still names the colour.
  • Ramps shifting different ways. If grass shadows go blue and rock shadows go red, the scene has no single light. Shift every ramp in the same direction.
  • Expecting it to work on greys. At low saturation hue barely shows, so a 15° shift does almost nothing. Near-grey materials usually need a touch of saturation too, which is the next lesson.
  • Pure black and white at the ends. They have no hue, so the ramp loses its shift exactly where it should be strongest.

In real games

Hue shifting is taught in the pixel art guides listed below, and many palettes shared online are laid out as hue shifted ramps. I will not claim from memory which game used which exact ramp.

You can check for yourself: open a screenshot of a pixel art game you like, pick three colours along one shaded surface from shadow to light, and read their hues. Often the hue moves across the ramp, and its direction tells you which way the artist decided the light leans.

Your turn (15 minutes)

Take the straight ramp from the last lesson, or any ramp from your game, and write down each step's hue, value and grey. In a copy, turn each light step 12° towards yellow per step away from the base, and each shadow step 12° towards blue. Adjust each step's value until its grey matches the original.

Recolour one sprite with the new ramp and put it beside the original at 1x. You are done when both look identical in greyscale and the shifted one looks less flat in colour. If it looks like a different material, halve the shift.

Takeaways

  • Hue shifting turns each step's hue a little: usually lights towards yellow and shadows towards blue.
  • Go the shorter way round the colour wheel, and stop when you reach the target hue.
  • Around 10° to 20° per step is a common start; much more and the ramp stops reading as one material.
  • Keep the greys of the straight ramp. Hue shifting should change colour, not form.
  • It follows the light: under a cool light, flip the direction, and keep every ramp in a scene consistent.

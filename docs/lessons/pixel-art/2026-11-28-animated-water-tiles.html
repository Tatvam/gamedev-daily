Animated tiles: looping water that stays seamless

How to build a water tile from a few looping frames that stay seamless at the edges and at the loop, and drive every copy from one clock.

Your pond is one water tile repeated fifteen times. In motion it is a sheet of blue glass. So you animate it, and now every tile ripples on its own schedule, the tile grid shows up as seams, and once a second the whole pond hitches.

An animated tile is a short loop of tiles

An animated tile has several frames, slightly different versions of the same tile, shown one after another and repeated. The map still stores one tile number per cell; only the picture behind that number changes.

For the loop to read as moving water, it has to be seamless in two directions:

  • In space. Every frame must tile on its own, with its left edge matching its right edge and its top matching its bottom, exactly as in seamless tiling.
  • In time. The last frame must lead into the first as smoothly as frame 1 leads into frame 2. Otherwise the loop has a visible restart, a hitch the eye catches every cycle.

The shift trick: one tile, shifted with wrap-around

The easiest way to get both: draw one seamless tile and make the other frames by shifting its content sideways, so what falls off one edge comes back on the other. Shifting with wrap-around keeps a seamless tile seamless.

Choose the shift so that the frames add up to exactly one tile width. With a 16 pixel tile and 4 frames, each frame moves 4 pixels: 0, 4, 8, 12. The next step would be a shift of 16, which is the same picture as a shift of 0, so the loop closes by itself.

Water looks livelier if two parts move in opposite directions: light highlights drift right, dark ripples drift left. Both move a whole tile per loop, so both close it. In code the frame f pixel at column x reads from the base tile like this (Lua's % always gives a result from 0 up, even for negative numbers):

local shift = (f - 1) * TILE / FRAMES   -- 0, 4, 8, 12 when FRAMES is 4
local hx = (x - shift) % TILE           -- highlight column: drifts right
local rx = (x + shift) % TILE           -- ripple column: drifts left

In an editor, use a wrap-around offset: GIMP has Layer, Transform, Offset; Photoshop has Filter, Other, Offset; many pixel editors have a similar command.

Frame count and frame time

The frame count sets the step size: 16 pixels divided by the number of frames. The frame time, how long each frame is held, sets how fast the steps come.

  • 2 frames means an 8 pixel step, half the tile. A shift of +8 looks identical to a shift of -8, so the eye cannot tell which way the water moves. It reads as blinking.
  • 4 frames gives 4 pixel steps. The direction is clear and it is little work, which is why short loops are common for water.
  • 8 frames gives 2 pixel steps: smoother, but twice the hand cleanup.

Pick a frame count that divides the tile width. With 3 frames on 16 pixels the step is 5.33, which rounds to 5, 5 and 6, and the uneven step stumbles every loop.

For calm water, 150 to 250 milliseconds per frame is a good start. Shorter times look like rushing or boiling, which can suit a river or lava.

One clock for the whole pond

The highlights cross tile edges: a wavelet leaving one tile continues in its neighbour. That only lines up if both show the same frame, so every copy should read its frame from one shared clock:

local frame = math.floor(timer / FRAME_TIME) % FRAMES + 1

Give each tile its own random start frame and the wavelets break at every edge: the grid comes back. For small things that stay inside one tile, such as flowers or torches, the convention is usually reversed. Perfect sync looks mechanical there, and different start frames look natural.

Rule of thumb

If the pattern crosses tile edges, share the clock. If each tile is a separate object, offset it.

The code

The four frames sit side by side in water.png, 64 by 16 pixels, like the demo's strip. Each frame gets a quad, a rectangle that picks part of an image, and one timer picks the frame for every water tile. Written for LÖVE 11, with the demo's default numbers.

-- water.png: four 16x16 frames side by side, 64x16 pixels
local TILE, FRAMES, FRAME_TIME = 16, 4, 0.15   -- 150 ms per frame
local POND_W, POND_H, BANK, SCALE = 5, 3, 4, 4
local sheet
local quads = {}
local timer = 0

function love.load()
  love.graphics.setDefaultFilter("nearest", "nearest")
  sheet = love.graphics.newImage("water.png")
  for f = 1, FRAMES do
    quads[f] = love.graphics.newQuad((f - 1) * TILE, 0, TILE, TILE, sheet:getDimensions())
  end
end

function love.update(dt)
  timer = timer + dt   -- one clock for every water tile
end

function love.draw()
  local frame = math.floor(timer / FRAME_TIME) % FRAMES + 1   -- 1 .. FRAMES
  love.graphics.scale(SCALE)
  -- draw the bank around the pond here, as a normal static tile layer
  for ty = 0, POND_H - 1 do
    for tx = 0, POND_W - 1 do
      love.graphics.draw(sheet, quads[frame], BANK + tx * TILE, BANK + ty * TILE)
    end
  end
end

For tiles that should not be in sync, such as flowers, store a start offset per tile and add it before the wrap: (math.floor(timer / FRAME_TIME) + offset[i]) % FRAMES + 1. With offset[i] set to 0 for every tile you are back to the shared clock.

Pitfalls

  • A loop with a restart. If the last frame does not lead into the first, the water jumps once per cycle. Judge the loop playing, several times in a row.
  • Frames that are not seamless. Check every frame in a 3 by 3 repeat. A hand fix on one frame can break its edge.
  • Random start frames on water. They break every edge, as the demo shows. Keep offsets for self-contained tiles.
  • Moving too much per frame. When a step is half the spacing of the pattern or more, the direction becomes ambiguous and the water flickers. Add frames or make the step smaller.
  • Too much contrast in the moving part. Bright foam crawling across a large lake pulls the eye away from the player. Keep it subtle.
  • Per-tile timers. They cost memory and drift apart. One timer per tile type is enough.

In real games

On tile-based consoles such as the NES and SNES, the map holds tile numbers that point at tile graphics. Replacing the graphics behind one number changes every copy at once: a shared clock built into the hardware.

Modern tools work the same way. The Tiled map editor lets you give a tile a list of frames, each with its own duration. In Godot 4 a tile in a TileSet atlas can have several animation frames, and its animation mode can be set to give each placed tile a random start time. Unity's 2D Tilemap Extras package includes an Animated Tile with a list of sprites and a speed setting. These options have moved between releases, so check the documentation for your version.

Your turn (15 minutes)

  1. Draw one seamless 16 by 16 water tile in four colours (deep, mid, light, foam), with short highlight dashes, one crossing the right edge.
  2. Duplicate it three times and offset the copies by 4, 8 and 12 pixels with wrap-around.
  3. Play the loop at 150 to 200 ms per frame, in a 3 by 3 repeat.
  4. Optional: shift only the dark ripples the other way on each frame.

You are done when the 3 by 3 repeat moves at real size with no visible tile edges and no hitch when the loop restarts.

Takeaways

  • An animated tile has to be seamless in space (every frame tiles) and in time (the last frame leads into the first).
  • Shifting one seamless tile with wrap-around by tile width divided by frame count gives frames that are both.
  • Frame count sets the step size and frame time sets the speed. Two frames of half a tile only blink.
  • Tiles whose pattern crosses edges, like water, must share one clock. Self-contained tiles usually look better offset.

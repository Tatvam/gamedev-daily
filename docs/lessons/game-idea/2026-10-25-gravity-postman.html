Gravity Postman: aim once, let the planets finish the route

A slingshot delivery game where you choose only the direction and power of each letter and gravity bends the rest, with a playable prototype and the flight code in Lua.

You are the only postman on a tiny planet, and the post goes out by slingshot. Pull back, let go, and watch your letter curve around heavy worlds you can never move. The first second of the flight is shown to you in advance. After that, it is down to your judgement.

The core loop: aim, send, watch, adjust

Gravity Postman is a trajectory puzzle: a puzzle where the player sets up a single launch and then cannot touch anything while the simulation plays out. Each route has a home planet, a target planet with a mailbox, and three gravity wells, which are heavy planets that pull the letter towards them. The straight line to the target is always blocked by a well or its pull, so every route needs a curve.

The player chooses two numbers, angle and power, and that is the whole control scheme. The letter then flies on its own.

The rules

  • Aiming. Drag back from anywhere, like pulling a slingshot. The direction of the pull sets the angle, and its length sets the power, from 60 to 240 units per second.
  • Gravity. Each well pulls the letter with a strength that falls off with the square of the distance. A small softening number is added to the distance so the pull never becomes infinite. Every well pulls everywhere on the map, not only nearby.
  • The one-second preview. While aiming, a dotted line shows exactly where the letter will be for the first second of flight, and no further. It is the real simulation run ahead, so it never lies.
  • Losing a letter. The letter is lost if it hits a well, flies off the map, comes back to the home planet, or is still flying after 8 seconds (stuck in an orbit). Its path stays as a faint ghost trail, and your aim stays where it was.
  • Score. Deliver to three targets. The score is the number of letters sent. Fewer is better.

Why only one second of preview

A full preview line would turn the game into tracing a line onto a target. No preview at all would turn it into guessing. One second sits between them: you see the launch direction and the first bend, and you have to imagine the rest. The skill the player builds is reading the map, knowing that a fast letter skims past a well and a slow one gets bent sharply.

What makes it different

The player fantasy is the postman who knows the neighbourhood so well they can thread a letter between planets. The constraint is the single decision before launch. Nothing can be saved in the air, so all the tension sits in the moment before letting go.

The hardest part to build is the set of routes. Gravity paths are very sensitive, so each map needs a script that tries every angle and power and counts how many win, rather than tuning by eye.

Try it

Send the first letter straight at the target and watch a well swallow it. Then aim to one side, note where the preview ends, and send again, changing one thing at a time.

The code

The heart of the mechanic in LÖVE: summing the pulls, stepping the letter at a fixed rate, and running the same step ahead of time for the one-second preview. The numbers are those of the first route. checkHits() is your own function for the target, the edges, the home planet and the 8 second limit.

local SOFT, STEP, PREVIEW = 24, 1 / 120, 1.0
local home = { x = 70, y = 250, r = 20 }
local wells = { { x = 300, y = 190, r = 34, gm = 1600000 },
  { x = 180, y = 90, r = 18, gm = 500000 }, { x = 430, y = 290, r = 20, gm = 600000 } }
local letter, acc = nil, 0
local function checkHits() end                -- yours: target, edges, home, time

local function step(p, h)                     -- p is any { x, y, vx, vy }
  for _, w in ipairs(wells) do
    local dx, dy = w.x - p.x, w.y - p.y
    local d2 = dx * dx + dy * dy
    local d = math.sqrt(d2)
    local a = w.gm / (d2 + SOFT * SOFT)
    p.vx, p.vy = p.vx + a * dx / d * h, p.vy + a * dy / d * h
  end
  p.x, p.y = p.x + p.vx * h, p.y + p.vy * h
  for _, w in ipairs(wells) do                -- touching a well loses the letter
    if (p.x - w.x) ^ 2 + (p.y - w.y) ^ 2 < (w.r + 4) ^ 2 then p.dead = true end
  end
end

local function launch(angle, power)
  local c, s = math.cos(angle), math.sin(angle)
  return { x = home.x + c * (home.r + 6), y = home.y + s * (home.r + 6), vx = c * power, vy = s * power }
end

local function preview(angle, power)          -- dots for the first second only
  local p, dots = launch(angle, power), {}
  for i = 1, PREVIEW / STEP do
    step(p, STEP)
    if p.dead then break end
    if i % 6 == 0 then dots[#dots + 1] = { p.x, p.y } end
  end
  return dots
end

function love.update(dt)
  acc = acc + math.min(dt, 0.1)
  while letter and acc >= STEP do
    step(letter, STEP); acc = acc - STEP
    if letter.dead then letter = nil else checkHits() end
  end
end

The preview and the flight share one step function and one fixed step size, so the dotted line is not a guess: it is the first 120 steps of the real flight. To send a letter, set letter = launch(angle, power). Because the letter dies on touching a well, it can never reach a well's centre, so d is never zero.

Pitfalls

  • Too sensitive to aim. If a winning shot is a single degree wide, the game feels like luck. Test early: for each route, try every whole degree and every power in steps of 5 and print the winning bands. The prototype's routes have winning bands many degrees wide, and 2 to 6 percent of all settings win. If a band is narrower than about 3 degrees, move a well.
  • The preview gives it away. At high power, one second covers most of the map and the puzzle disappears. That is why the prototype caps power at 240 units per second on a map 600 wide. Watch testers: if they win by lining the dots up with the target, shorten the preview or lower the cap.
  • Orbits that never end. A letter can loop around a well for a long time, and the player sits waiting. The 8 second limit ends that. If testers wait often, show a countdown on the letter.
  • Frame rate changes the answer. Without a fixed step, a shot that wins on one computer misses on another, and your winning-band script is wrong for everyone. Step at 120 per second no matter how fast the screen draws.
  • Unreadable pull. Size alone does not show weight. The dashed ring at a fixed pull strength makes heavy wells visibly reach further.

In real games

Launching something once and letting physics finish the job is a large family of games, often called slingshot or artillery games. In Angry Birds (Rovio, 2009) you pull back a slingshot to set angle and power under ordinary downward gravity. Artillery games such as Worms (Team17, 1995) add wind to a similar shot. Kerbal Space Program (Squad, 2015) is built around planning orbits between planets, though there you also fly the ship yourself.

Gravity Postman differs in two ways: the pull comes from several points at once rather than from below, so curves wrap around obstacles, and the partial preview is a designed limit rather than a difficulty setting. The delivery theme also keeps the mood calm.

Your turn: the first playtest

In one sitting, build the Lua above with circles for everything, a slingshot drag with love.mousepressed and love.mousereleased, and the preview dots. Make one route by hand, then add a loop that tries every angle and power and prints the winning bands.

Hand it to a friend and say only "drag back and let go to post the letter". The one question to answer: after a miss, does their next shot move in the right direction? If their aim changes in a sensible way, the gravity is readable. If they jump between wildly different shots, the wells are too strong or the preview too short.

Takeaways

  • Weekend version: the prototype above with ten routes, a par number of letters per route, and a small stamp animation on delivery.
  • One-month version: forty routes, with new pieces added one at a time: a moon that orbits a well, a planet that pushes instead of pulls, a second mailbox that must be hit by the same letter, and a short post office story between chapters.
  • Cut first: moving moons. They make every map change over time, which breaks the solver script and makes the ghost trail misleading. Static pieces give more puzzles for less work.
  • The partial preview is the design. Tune its length before anything else.

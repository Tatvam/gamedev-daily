River Numbers: steer a river by nudging the land

A calm logic puzzle on a grid of heights: water takes the lowest way down, and you raise or lower a few tiles to bring the river to every field.

A spring bubbles out on a hilltop, and the river it feeds runs straight past three thirsty fields. You cannot dig a canal. You can only lift or sink a few patches of ground by one step each, and the water does the rest.

The core loop: read the slope, nudge a tile, watch the water

River Numbers is played on a six by six grid. Every tile shows its height, a whole number from 0 to 9. One tile is the spring, where water starts. Some tiles are fields, and the level is solved when water reaches all of them.

The player never moves the water. They spend changes: each raises or lowers one tile by one step, from a budget of five at most. Moving a tile back refunds the change, so trying things is free.

Every ten seconds the player reads the numbers around the river, nudges a tile, and watches the water rush along its new course. Every minute a field turns green. Every session brings bigger valleys where one change has to serve two fields.

The rules

  • Lowest way down. From each wet tile, water moves to the lowest of its four neighbours, but only if that neighbour is strictly lower than the tile itself.
  • A tie splits the river. If two or more neighbours share the lowest height, water goes to all of them.
  • No way down makes a pond. If no neighbour is lower, the water stops there. Flat ground does not carry water.
  • The spring is fixed. Every other tile, fields included, can be changed. Heights stay between 0 and 9.

What makes it different

The player fantasy is the patient landscaper: you shape a valley by hand and let nature carry the water. Nothing chases you and every move can be undone. The constraint is the budget of changes, which turns a sandbox into a puzzle: you can see a dozen ways to bend the river, but only a few fit in five steps.

The two levers feel different. Lowering a tile invites water in, often through a tie, so the river forks and keeps its old course. Raising a tile pushes water away, like a small dam. Good levels make the obvious lever fail: lowering an entrance can leave it level with the tile behind, and level ground makes a pond.

The hardest part to build is not the flow, which is a short search. It is making thirty-six numbers readable at a glance and designing levels with one clean answer. The demo shades tiles by height so the valley shows before you read a digit, and a small program that tried every set of changes within budget confirmed each level has exactly one solution.

The code

The heart of the mechanic in LÖVE: the flow search and a budgeted change, using level 2 of the demo. Call nudge(r, c, 1) or nudge(r, c, -1) from your input code, then flow() to get the wet tiles. Drawing is left out.

local N, budget, spring = 6, 2, { 1, 1 }
local rows = { "998987", "899998", "798889", "654329", "387789", "210899" }
local DIRS = { { -1, 0 }, { 1, 0 }, { 0, -1 }, { 0, 1 } }
local start, h = {}, {}
for r = 1, N do
  start[r], h[r] = {}, {}
  for c = 1, N do start[r][c] = tonumber(rows[r]:sub(c, c)); h[r][c] = start[r][c] end
end
local function key(r, c) return (r - 1) * N + c end

local function flow()                    -- returns wet[key] = true
  local wet, queue, head = { [key(spring[1], spring[2])] = true }, { spring }, 1
  while head <= #queue do
    local r, c = queue[head][1], queue[head][2]
    head = head + 1
    local low, outs = h[r][c], {}
    for _, d in ipairs(DIRS) do
      local nr, nc = r + d[1], c + d[2]
      local nh = h[nr] and h[nr][nc]       -- nil off the edge
      if nh and nh < low then low, outs = nh, { { nr, nc } }
      elseif nh and nh == low and #outs > 0 then outs[#outs + 1] = { nr, nc } end
    end
    for _, o in ipairs(outs) do
      if not wet[key(o[1], o[2])] then wet[key(o[1], o[2])] = true; queue[#queue + 1] = o end
    end
  end
  return wet
end

local function nudge(r, c, step)         -- step is 1 (raise) or -1 (lower)
  local new, used = h[r][c] + step, 0
  if (r == spring[1] and c == spring[2]) or new < 0 or new > 9 then return false end
  for i = 1, N do for j = 1, N do used = used + math.abs(h[i][j] - start[i][j]) end end
  used = used + math.abs(new - start[r][c]) - math.abs(h[r][c] - start[r][c])
  if used > budget then return false end
  h[r][c] = new
  return true
end

The highlighted lines are the game. A strictly lower neighbour replaces the list; an equal one joins it, but only once something lower than the tile itself has been found, so flat ground never carries water. The cost of a change is how far the tile moves from its starting height, which is why moving it back is a refund. Field (4, 5) is watered when flow()[key(4, 5)] is true; on this level, nudge(5, 1, 1) twice does it.

Pitfalls

  • Numbers as homework. Thirty-six digits are tiring to read. If testers scan every digit before each move, the shading is not doing its job: fix that before adding levels.
  • Surprise forks. Ties are the richest rule and the easiest to miss, because two equal numbers do not look special. If players are puzzled when the river splits, mark tie tiles or teach the split alone in the first level, as the demo does.
  • Ponds that feel like bugs. Players expect water to fill a hollow and spill over. The demo's water simply stops. Test whether that reads as a rule or as a mistake. Filling basins is a fine later rule, but it changes every level, so decide early.
  • Loose budgets. With one spare change, many levels fall to random poking. Set each budget to the smallest one that works, found by a solver, and check how many answers remain. The demo's levels have exactly one each.

In real games

Shaping land to move water has been explored from several sides. Where's My Water? (Creature Feep, published by Disney, 2011) has players dig through dirt so falling water reaches a goal, with physics-style liquid rather than a grid rule. God games let the player reshape terrain: in Populous (Bullfrog, 1989) you raise and lower land, though there the aim is flat ground for your followers, not rivers. From Dust (Ubisoft Montpellier, 2011) lets the player carry earth and water to protect villages, as a real-time simulation.

River Numbers makes the flow a turn-based rule on visible numbers, closer to a pencil puzzle than a simulation. Something like it may well exist among grid puzzles I have not played; the change budget with free refunds is the part to test.

Your turn: the first playtest

In one sitting, build the Lua above with level 3 of the demo typed in, numbers drawn on plain squares, wet tiles coloured blue, and fields outlined. Skip the flow animation and the shading.

Give it to a friend with only the four rules and the controls. The one question: before they make each change, can they point to where the water will go next? If they are mostly right by the third field, the rule is readable. If not, note whether ties or ponds fooled them: that rule needs a teaching level.

Takeaways

  • Weekend version: the demo's four rules, fifteen hand-made levels with budgets set by a solver, height shading, and a gentle splash when a field turns green.
  • One-month version: larger maps that scroll, villages that must stay dry, basins that fill and spill, and a level editor that runs the solver as you paint heights.
  • Cut first: extra tile types such as rocks or bridges. Heights, a spring and fields already make a full puzzle language.
  • Hardest part: readability and level design, not code. Build the solver before the tenth level.

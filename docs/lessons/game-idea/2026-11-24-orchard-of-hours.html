Orchard of Hours: borrow time from one tree to ripen another

A calm puzzle where three trees share one fixed pool of hours, and you move hours between them until all three bear fruit at once.

You keep an orchard where time is not shared out fairly: each tree is exactly as old as the hours you give it, and every hour you give one tree has to come from another. The market wants cherries, apples and pears on the same morning, so you must make three clocks that run at different speeds all land on fruit together.

The core loop: take an hour, give an hour, watch the season turn

Each tree has an age in hours, and that age decides what it looks like. Each tree also has its own cycle, a short year that repeats: some hours in leaf, then blossom, then fruit, then bare branches, then leaf again. The cherry's year is 6 hours long, the apple's 9 and the pear's 7.

You never set an age directly. You carry a lantern that holds loose hours. Taking an hour from a tree makes it one hour younger and puts that hour in the lantern. Giving an hour makes a tree one hour older and empties the lantern by one. The total of all ages plus the lantern never changes.

Every ten seconds you move one hour and watch a tree scrub forward or back through its year: fruit shrinks back into blossom, or bare branches burst into leaf. Every minute you solve one order, a new total of hours and a new starting orchard. Every session is a season of orders, each scored by how few hours you moved.

The rules

  • Hours are conserved. Ages plus the lantern always equal the order's total. A tree's age cannot go below zero.
  • Seasons repeat. A tree's season is its age counted within its own year. An apple aged 15 is in its second year, at hour 6, so it is in fruit.
  • The harvest. The order is done when all three trees are in fruit and the lantern is empty. Every hour must be spent.
  • The score. Each hour given counts as one hour moved. The game knows the smallest possible number and shows it as the target.
  • No clock and no loss. Nothing happens until you act. You can undo any move by moving the hour back.

What makes it different

The player fantasy is the patient gardener who bends time, not the farmer who waits for it. The constraint is conservation: you cannot add time, only move it. That turns a garden into a balancing puzzle. Ripening the slow apple always costs the cherry or the pear something, and often pushes one of them past its fruit into bare branches.

The different year lengths are what keep it from being simple arithmetic. When the obvious answer does not add up, the way out is often to push one tree through a whole extra year, so a tree that looks finished may need to grow nine more hours. The third order in the demo works that way.

The hardest part to build is not the code, which is tiny. It is generating orders that have a solution, a clear best answer, and at least one tempting wrong path. A brute-force search over every split of the total does all three for three trees; the demo uses one to compute the target score.

The code

The heart of the mechanic in LÖVE: each tree's year is a list of seasons, the season is the age wrapped into that list, and taking and giving move single hours through the lantern. Drawing and the order list are left out. The trees, numbers and first order are the demo's.

local TREES = {
  { name = "Cherry", year = { "leaf", "leaf", "blossom", "fruit", "fruit", "bare" } },
  { name = "Apple",  year = { "leaf", "leaf", "leaf", "leaf", "blossom", "blossom", "fruit", "fruit", "bare" } },
  { name = "Pear",   year = { "leaf", "leaf", "leaf", "blossom", "fruit", "fruit", "bare" } },
}
local ages = { 5, 5, 5 }               -- order 1: 15 hours in total
local lantern, moved, selected = 0, 0, 1

local function season(i)               -- the age wrapped into the tree's own year
  local year = TREES[i].year
  return year[ages[i] % #year + 1]
end

local function harvestReady()          -- every hour spent, every tree in fruit
  if lantern > 0 then return false end
  for i = 1, #TREES do
    if season(i) ~= "fruit" then return false end
  end
  return true
end

local function take(i)
  if ages[i] == 0 then return end      -- a tree cannot be younger than zero
  ages[i], lantern = ages[i] - 1, lantern + 1
end

local function give(i)
  if lantern == 0 then return end
  ages[i], lantern = ages[i] + 1, lantern - 1
  moved = moved + 1
end

function love.keypressed(key)
  if key == "left" then selected = math.max(1, selected - 1) end
  if key == "right" then selected = math.min(#TREES, selected + 1) end
  if key == "down" then take(selected) end
  if key == "up" then give(selected) end
  if harvestReady() then print("Harvest! Hours moved: " .. moved) end
end

The + 1 in season is there because Lua tables start at index 1 while ages start at 0. The best possible score comes from trying every split of the total, keeping the splits where season says fruit for all three trees, and counting how many hours each one needs to move.

Pitfalls

  • It becomes a sum on paper. Some players will write the fruit hours down and solve it with arithmetic, and then it is homework. If testers stop looking at the trees, hide the exact numbers and show only the trees and strips.
  • Hour by hour is too slow. Moving nine hours one at a time is tedious once you know the plan. If testers sigh during the third order, add a drag that moves several hours at once.
  • The lantern hides the rule. Carrying loose hours makes the conservation rule softer, because a player can hold hours for a while. If testers do not understand why the harvest does not trigger, show the total of trees plus lantern on screen, as the demo does.
  • Three trees is a small space. With three trees and short years, every order has only a few answers, and a player may stumble on them by poking. If solving does not feel earned, add a fourth tree before adding new rules.

In real games

Games that let the player control time usually make it a single dial for the whole world. Braid by Jonathan Blow rewinds everything at once, and some of its worlds change how time relates to the player, such as one where time moves forward and back as you walk right and left. Orchard of Hours splits time into separate pieces and makes them compete for a shared budget.

Farming games, such as Stardew Valley, give each crop a number of days to grow, and planning around those timers is part of their appeal. There the clock runs for every crop together and the player waits. Here the player is the clock, and the puzzle is only the timing.

I have not surveyed every puzzle game with conserved resources, so I will not claim this idea is the first of its kind.

Your turn: the first playtest

In one sitting, build the Lua above with three circles for trees, coloured by season, and each tree's age printed under it. Write five orders by hand, or generate them with a brute-force search that rejects any order without a solution.

Give it to three people without explaining the years. The one question: do players discover the year wrap on their own? If someone pushes a tree past its fruit, sees it come round to fruit again and smiles, the idea has its hook. If everyone stays inside the first year and finds it flat, give the years stronger visual rhythm before adding anything else.

Takeaways

  • Weekend version: three trees with different year lengths, take and give, twenty hand-checked orders, and a target score from brute force.
  • One-month version: five tree types, orders that ask for mixed seasons (two in blossom, one in fruit), animated trees that scrub smoothly through the year, and a calm sound for each season change.
  • Cut first: weather, pests and story. They add rules around the edge but do not make the one choice, which tree pays for this hour, any more interesting.
  • Hardest part: making good orders. Generate many, rank them by how far the start is from the nearest answer and by how many near misses there are, then pick by hand.

Gravity Painter: down is free, every other way costs paint

A grid puzzle where you paint cells with a direction of gravity, then drop a ball that falls whichever way the paint under it points. Prototype and Lua.

You hold a brush loaded with gravity. Paint a cell orange and anything in it falls left; paint it violet and it falls up. With three drops of paint, get the ball past the spikes and into the cup.

The core loop: paint, drop, read the trail

Gravity Painter is a puzzle on a seven by seven grid with a ball, a cup (the goal), walls and spikes. Before the ball moves, you paint cells left, up or right. Each painted cell costs one unit of the level's paint supply, a small fixed budget.

Then you press Drop. Each step, the ball moves one cell the way the paint under it points. A cell with no paint pulls it down. That gives the game its one line of advice: down is free, every other way costs paint.

Every ten seconds the player paints a stroke and drops the ball. Every minute they read the trail it left, see where it went wrong, and fix a cell. Every session brings levels where the obvious route runs out of paint and the cheap one uses free falls.

The rules

  • Blocked means rest. If the next cell is a wall or the edge, the ball stops and the run is over.
  • Spikes pop, the cup wins. Entering a spike cell ends the run. Entering the cup clears the level.
  • Paint is a budget. Painting a bare cell costs one unit, recolouring costs nothing, erasing gives the unit back. Any open cell takes paint, even the ball's starting cell.
  • Loops end the run. A ball that returns to a cell it visited would circle forever, so the run stops.

What makes it different

The player fantasy is the painter who rewrites the laws of the world instead of pushing the ball. You never touch it. The constraint is the paint supply, and because down is free, the puzzle is about economy: where can ordinary gravity carry the ball for nothing, and where must you pay?

Two surprises carry the early levels. Paint works in mid-air, so one stroke can turn a ball halfway down a shaft. And up paint only lifts while there is paint: paint one cell up with open air above it, and the ball rises, falls back, and rises again. Climbing means painting the whole column and a sideways stroke at the top.

The hardest part to build is the levels. The rules are tiny, so a level's quality depends on how many paint plans solve it. I checked each demo level with a small search that tries every plan within the budget, painting only cells on the ball's current path, since paint anywhere else cannot change the run.

Try it

Level 1 teaches that paint turns the ball. Level 2 has exactly one solution: drop once and look at where the ball passes. On level 3, paint the ball's cell up and drop it to see the loop, then climb for real with six paint.

The code

The heart of the mechanic in LÖVE: painting with a budget, and one step of the fall, using level 2 of the demo. Call setPaint(row, col, "l") from your mouse code (nil erases) and drop() from love.keypressed. Drawing is left out.

local N, STEP = 7, 0.14                -- seconds per cell
local level = { supply = 3, map = { "...S...", ".......", "###.###", "G......",
                                    "###.###", "...^...", "^^^^^^^" } }
local DIR = { l = { 0, -1 }, r = { 0, 1 }, u = { -1, 0 } }
local paint, used = {}, 0              -- paint[key] is "l", "r" or "u"
local ball, seen, running, timer, result = { r = 1, c = 4 }, {}, false, 0, nil
local function tile(r, c) return level.map[r]:sub(c, c) end
local function key(r, c) return (r - 1) * N + c end

local function setPaint(r, c, dir)     -- dir = nil erases
  local t, k = tile(r, c), key(r, c)
  if t ~= "." and t ~= "S" then return false end
  local cost = (dir and 1 or 0) - (paint[k] and 1 or 0)
  if used + cost > level.supply then return false end
  paint[k], used = dir, used + cost
  return true
end

local function fall()                  -- one cell; returns how the run ended, or nil
  local d = DIR[paint[key(ball.r, ball.c)]] or { 1, 0 }   -- no paint means down
  local r, c = ball.r + d[1], ball.c + d[2]
  if r < 1 or r > N or c < 1 or c > N or tile(r, c) == "#" then return "rest" end
  ball = { r = r, c = c }
  if tile(r, c) == "G" then return "goal" end
  if tile(r, c) == "^" then return "spikes" end
  if seen[key(r, c)] then return "loop" end
  seen[key(r, c)] = true
end
local function drop()
  ball, seen = { r = 1, c = 4 }, { [key(1, 4)] = true }
  running, timer, result = true, 0, nil
end
function love.update(dt)
  timer = timer + dt
  while running and timer >= STEP do
    timer = timer - STEP
    result = fall()
    running = (result == nil)
  end
end

The highlighted line is the game. With no paint, DIR[nil] is nil (reading a nil key is allowed in Lua), so the or falls back to down. The cost line covers painting (1), recolouring (0) and erasing (-1) at once.

Pitfalls

  • Paint everything, think nothing. With a generous supply, the player paints arrows straight to the cup and the puzzle disappears. Keep the supply at, or one above, the smallest number that solves the level, found by a solver. Level 2 of the demo has one solution at three paint; level 3 has four at six.
  • Trial and error instead of planning. Dropping is free, so players may paint at random. The trail turns that into learning for a while; if testers still guess after several levels, add a drop counter and a star for solving in one.
  • Loops that feel like bugs. A ball bobbing between two cells looks broken unless the game says what happened. Name it on screen, as the demo does, and teach it on purpose in an early level.
  • Colour alone. Draw an arrow on every painted cell so colour-blind players can read the board, and keep the trail thin enough not to hide it.

In real games

Gravity puzzles where the player tilts or flips the whole world are a well-explored area. In VVVVVV (Terry Cavanagh, 2010) the player flips gravity instead of jumping, and many puzzle games rotate the whole level so everything falls a new way. Arrow tiles that redirect a moving object are another common family: ChuChu Rocket! (Sonic Team, 1999) has players place arrows on the floor to steer running mice. Lemmings (DMA Design, 1991) shares the idea of setting up the world for characters you do not control directly.

Gravity Painter sits between those: gravity is set cell by cell, and ordinary gravity is the free default you pay to override. I have not surveyed every grid puzzle, and some game has likely used painted gravity before; the paint budget is the part to build and test.

Your turn: the first playtest

In one sitting, build the Lua above with levels 2 and 3 typed in, coloured squares for paint, a circle for the ball, and a dotted line through the last run's cells. Skip animation and drag painting.

Give it to a friend with only the controls and the rule "no paint means down". The one question: on level 2, after the ball first hits the spikes, does your friend paint a cell the ball passed through in mid-air, or only cells where it came to rest? If they find the mid-air stroke within a few drops, the rule is readable and the trail is doing its job. If they never try it, the game needs a level that teaches it more gently before this one.

Takeaways

  • Weekend version: the demo's rules, twelve hand-made levels whose supplies come from a solver, the trail of the last drop, and a satisfying sound when the ball drops into the cup.
  • One-month version: two balls sharing one painted grid with different cups, paint that fades after the ball passes, and a level editor that runs the solver as you place walls.
  • Cut first: extra paint types such as sticky or bouncy paint. Three directions and free down already make a full puzzle language.
  • Hardest part: the levels, not the code. Budget a solver from day one.

Next

Twist to try: give the ball momentum, so on an unpainted cell it keeps going the way it last moved instead of falling, and paint becomes a set of turns rather than a field of gravity.

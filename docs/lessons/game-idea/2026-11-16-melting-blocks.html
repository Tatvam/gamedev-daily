Melting Blocks: shrink to fit, grow to press

A block-pushing puzzle where heaters shrink the ice and freezers grow it back, so you manage its size to fit gaps and press buttons.

The door only opens for a heavy block of ice, and the only way to the door is a crack in the wall no wider than an ice cube. So you push the block across a heater, watch it shrink to fit, squeeze it through, then roll it over the freezers until it is big enough again.

The core loop: plan the route, push, watch the size

Melting Blocks is played on a small grid room. You walk a worker one tile at a time. Walk into the block of ice and you push it one tile, as long as the tile behind it is free. That much is a classic block-pushing puzzle.

The new part is that the ice has a size: small, medium or large. Two kinds of floor change it. A heater shrinks the ice by one size each time the ice is pushed onto it. A freezer grows it by one size, up to large. The worker can walk over both without effect.

Every ten seconds the player plans a few pushes, makes them, and checks the size readout. Every minute a gap is squeezed through and the ice is fattened back up. Every session brings new rooms.

The rules

  • Push, never pull. The worker pushes the ice one tile by walking into it. Ice against a wall stays put.
  • Every entry counts. The ice changes size when it is pushed onto a heater or freezer, every time. Push it off and back on, and it changes again.
  • Small ice melts away. Pushing small ice onto a heater melts it, and the room is lost until you undo.
  • Narrow gaps. Only small ice fits through a gap in the wall. The worker always fits.
  • The heavy button. Only large ice is heavy enough to press it. Pressing it solves the room.

What makes it different

The player fantasy is the careful ice carrier who knows exactly how much heat a block can take. The constraint is that size is a resource you spend and earn by where you push, so the route through the room is the whole puzzle. A tile you would happily cross in a normal pushing puzzle becomes expensive here.

The second idea hides in the rule "every entry counts". A single heater can be used twice by pushing the ice off it and back on, as long as there is room for the worker to get to the other side. Discovering that is the first real insight.

The code is small. The hardest part to build is level design: block-pushing puzzles are full of dead ends, and it is hard to tell by eye whether a room can be solved at all. A breadth-first search (trying every reachable state, nearest first) over the worker's tile, the ice's tile and its size checked each level in the demo. The shortest solutions are 8, 33 and 33 moves.

Try it

Level 1 is a straight line that teaches the sizes. Level 2 has one heater too few on the obvious path. Level 3 asks you to think about where the worker will stand after the gap.

The code

The heart of the mechanic in LÖVE: one step of the worker, including the push and the size change, using level 1 of the demo. Rows are strings, so tile(x, y) reads one character. Drawing is left out.

local map = {
  "##########",
  "#....#...#",
  "#....#...#",
  "#..HH|FFB#",                       -- H heater, F freezer, | gap, B button
  "#....#...#",
  "##########",
}
local player = { x = 3, y = 3 }
local ice = { x = 3, y = 4, size = 3 }   -- 1 small, 2 medium, 3 large
local state = "playing"                  -- "playing", "melted" or "won"

local function tile(x, y) return map[y]:sub(x, x) end

local function step(dx, dy)
  if state ~= "playing" then return end
  local nx, ny = player.x + dx, player.y + dy
  if tile(nx, ny) == "#" then return end
  if nx == ice.x and ny == ice.y then      -- walking into the ice pushes it
    local ix, iy = nx + dx, ny + dy
    local t = tile(ix, iy)
    if t == "#" then return end
    if t == "|" and ice.size > 1 then return end   -- too big for the gap
    ice.x, ice.y = ix, iy
    if t == "H" then ice.size = ice.size - 1 end
    if t == "F" then ice.size = math.min(3, ice.size + 1) end
    if ice.size == 0 then state = "melted" end
    if t == "B" and ice.size == 3 then state = "won" end
  end
  player.x, player.y = nx, ny
end

function love.keypressed(key)
  if key == "left" then step(-1, 0) end
  if key == "right" then step(1, 0) end
  if key == "up" then step(0, -1) end
  if key == "down" then step(0, 1) end
end

The highlighted lines are the game. The gap test sits before the move, so medium ice bumps against the gap instead of being crushed into it. On this map, pressing left, down and then right six times solves the room. For undo, copy player, ice and state into a list before each step and pop the last copy back.

Pitfalls

  • Dead ends with no warning. Ice pushed into a corner can never come out, and the player may spend minutes before noticing. Undo is not optional here. Test whether players recognise a stuck block; if not, grey the ice out when no push can move it.
  • Pumping solves everything. Because every entry counts, a heater with space around it is unlimited shrinking. If most of your rooms fall to pushing back and forth, size stops being a plan and becomes a chore. Count how often your solver's solutions re-enter the same tile, and wall off space where you want a single pass.
  • Sizes that do not read. Players must see at a glance that medium ice will not fit the gap. Draw every size and the gap opening to the same scale, as the demo does, and ask a tester to predict a bump before they push.
  • Melting far from the start. A melt after thirty careful moves feels unfair. Keep rooms short, and let undo step back from a melt, not only restart.

In real games

Block pushing is old ground. Sokoban (Hiroyuki Imabayashi, Thinking Rabbit, 1982) set the rules most players know: push, never pull, and crates stuck in corners stay stuck. Stephen's Sausage Roll (Increpare, 2016) is a close neighbour in spirit: you push and roll sausages over grills, so where an object travels changes its state, not only its position. There each side of a sausage must be cooked once, and overcooking it ruins it.

Melting Blocks puts the changing state into a single number that blocks or opens parts of the room, so size works like a key that you have to keep reshaping. Grid puzzles with shrinking or growing pieces surely exist that I have not played; the part to test is whether a three-step size ladder alone is enough for twenty rooms.

Your turn: the first playtest

In one sitting, build the Lua above with level 2 of the demo typed in, coloured squares for each tile, the ice drawn at three sizes, and undo. Skip animation and level select.

Give it to a friend with only the five rules. The one question: do they discover on their own that the same heater can be used twice? If they do within a few minutes, the rule is clear enough to build levels on. If they give up, the rule needs a teaching room of its own before level 2.

Takeaways

  • Weekend version: the demo's five rules, ten hand-made rooms checked by a solver, undo, and a short squash-and-stretch on every size change.
  • One-month version: two blocks at once, a medium-only gap, heaters that switch on and off with the worker's steps, and a level editor that runs the solver while you build.
  • Cut first: extra sizes. Three are enough; a fourth makes the readout harder to read and the solver slower without adding new ideas.
  • Hardest part: making rooms that are solvable and have one clear insight. Build the solver before the fifth room.

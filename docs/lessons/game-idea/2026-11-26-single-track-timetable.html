Single Track Timetable: four trains, one line, one place to pass

A planning game where four trains share one track with a single passing loop, and you write the departure times before watching the day play out.

You are the dispatcher of a country railway with one track, four trains and a single short stretch where two trains can pass. You write the timetable at your desk, press Play, and then you can only watch: the drivers will leave exactly when you told them, whatever is coming the other way.

The core loop: write the times, watch the day, read the chart

The line is 10 km long, with West station at one end and East station at the other. Most of it is single track: one rail line used by trains in both directions. From km 6 to km 7 there is a passing loop, a short second track where an eastbound and a westbound train can stand side by side and pass each other.

Your only tool is the timetable: the minute each train leaves its station. Each train has a window its passengers will accept, so you cannot simply send them one at a time all day.

Every ten seconds you nudge one departure and watch how its line moves on the chart. Every minute you press Play and watch one day run, ending in a collision, a day with some waiting, or a perfect day. Every session is a week of days, each adding trains, loops or tighter windows.

The rules

  • The timetable is law. A train leaves its station at its set minute, even if another train is coming straight at it.
  • One signal. At each end of the loop a signal holds a train that is about to leave the loop while a train going the other way is on the single track ahead. That is the only safety on the line.
  • The loop holds one train each way. Two trains going the same way share a track everywhere, so a fast train that catches a slow one hits it.
  • Collisions end the day. Two trains on the same track closer than 0.2 km have collided.
  • The score is waiting. A train's delay is its arrival time minus its departure time minus its normal running time. A perfect day has no collision and zero total delay.

The train graph

The game shows the plan on a train graph, the chart railways have long used to plan single lines: distance runs across, time runs down, and each train is a line. A steep line is a slow train. Where two lines cross, two trains are at the same place at the same time, which is only safe inside the shaded loop.

What makes it different

The player fantasy is the calm planner whose work is judged later, not the signalman pulling levers in a panic. The constraint is that you act only before the day starts. Every decision is a prediction, and the chart is how you make it.

The one loop is what makes the times interact. It sits off-centre, so two trains leaving at the same minute do not meet in it. A slow freight occupies the line for twenty minutes and an express covers it in five, so the trains' lines have different slopes, and the place where two lines cross moves whenever you change one time.

The hardest part to build is not the simulation, which is under forty lines. It is the puzzle design: choosing windows so that at least one perfect day exists, the obvious first timetable fails, and the near misses are close enough to tempt. A brute-force search over every combination of departure minutes handles all three, and that is how the demo's windows were chosen.

Try it

The goal is a perfect day with no collision and no waiting; there are ten of them among about fourteen thousand timetables.

The code

The whole day in LÖVE: trains leave on time, move along the line, stop at the loop signal if something is coming, and the pair check finds collisions. Drawing is left out. The trains, numbers and draft timetable are the demo's.

local LINE, LOOP_A, LOOP_B, CRASH, STEP = 10, 6, 7, 0.2, 0.02   -- km, km, km, km, minutes
local EXIT, AHEAD = { [1] = LOOP_B, [-1] = LOOP_A }, { [1] = "east", [-1] = "west" }
local trains = {                               -- speed in km per minute, dep in minutes
  { name = "Express", dir =  1, speed = 2,   dep = 4 },
  { name = "Local W", dir = -1, speed = 1,   dep = 0 },
  { name = "Local E", dir =  1, speed = 1,   dep = 0 },
  { name = "Freight", dir = -1, speed = 0.5, dep = 2 },
}
local function section(p) return p < LOOP_A and "west" or (p > LOOP_B and "east" or "loop") end
local function oncoming(tr, sec)               -- anyone heading the other way there?
  for _, o in ipairs(trains) do
    if o.state == "running" and o.dir ~= tr.dir and section(o.pos) == sec then return true end
  end
end
local function step(t)                         -- returns two trains if they collide
  for _, tr in ipairs(trains) do
    if not tr.state and t >= tr.dep then tr.state, tr.pos = "running", tr.dir == 1 and 0 or LINE end
    if tr.state == "running" then
      local nx, exit = tr.pos + tr.dir * tr.speed * STEP, EXIT[tr.dir]
      if (tr.pos - exit) * tr.dir <= 0 and (nx - exit) * tr.dir > 0
         and oncoming(tr, AHEAD[tr.dir]) then nx = exit end   -- the loop signal holds it
      tr.pos = nx
      if nx <= 0 or nx >= LINE then tr.state = "arrived" end
    end
  end
  for i = 1, #trains do for j = i + 1, #trains do
    local a, b = trains[i], trains[j]
    local sec = a.state == "running" and b.state == "running" and section(a.pos)
    if sec and sec == section(b.pos) and (sec ~= "loop" or a.dir == b.dir)
       and math.abs(a.pos - b.pos) < CRASH then return a, b end
  end end
end
local n, hitA, hitB = 0, nil, nil
function love.update(dt)
  local target = n * STEP + dt * 2             -- two minutes of the day per second
  while not hitA and n * STEP < target do
    hitA, hitB = step(n * STEP)
    n = n + 1
  end
end

The highlighted lines are the whole safety system: a train about to cross the loop exit checks the section ahead, and if a train going the other way is on it, it stops exactly at the exit. EXIT and AHEAD are looked up by direction, 1 for east and -1 for west. The loop's two tracks are why section returns "loop" and the collision test ignores trains passing each other there. Stepping the day in fixed steps of 0.02 minutes keeps every run identical, which a planning game needs: the same timetable must always give the same day.

Pitfalls

  • Watching is boring. Twenty seconds of trains you cannot touch feels long on the tenth try. If testers drum their fingers, add a fast-forward and let them skip straight to the result once they have seen a day play out.
  • The chart solves it for them. A good train graph shows every conflict before Play, and then the day is only a confirmation. That may be fine for a calm puzzle. If it feels flat, show only the plan lines for the first few days and hide them later, or add a train whose departure you do not control.
  • Trial and error wins. With four sliders a player can poke until it works. Watch whether testers predict outcomes out loud. If they never do, give each day a limited number of Plays.
  • Tiny timing ties. Two trains reaching a signal in the same step is decided by the order of the loop. Keep that order fixed, and design windows that do not depend on a tie; the brute-force search can flag those.

In real games

Railway management games usually let the player build the network and run trains continuously. OpenTTD has signals and a timetable for each vehicle, and players often build single lines with passing places. Factorio gives players rail signals and chain signals to keep trains apart on networks they build themselves. In Mini Metro the player draws lines and the trains run by themselves, with no timetable at all.

Single Track Timetable removes the building and the live control and keeps only the plan. It is closer to a logic puzzle than to a sandbox. Real single lines are worked with passing loops and with rules that allow only one train at a time on each section; this game deliberately keeps that rule only at the loop, so the timetable has to do the rest.

I have not played every railway puzzle game, so I will not claim no one has built this exact idea.

Your turn: the first playtest

In one sitting, build the Lua above and draw only the train graph: a vertical line per train from its departure point, extended down the screen as the day runs, with the loop as a shaded column. Use the four trains and windows from the demo, and keys to change one departure at a time.

Give it to three people with one sentence of rules. The one question: do players start reading the chart to predict a crash before they press Play? If you hear "these two will meet here", the chart is the game. If players only press Play and react, the planning is not visible enough yet; draw the lines larger and highlight crossings outside the loop before adding anything.

Takeaways

  • Weekend version: one line, one loop, four trains, the train graph, and ten hand-checked days, each with at least one perfect timetable found by brute force.
  • One-month version: two and three loops, stations in the middle where passengers board, trains that must turn round and come back, and a week structure where each day reuses the previous day's trains.
  • Cut first: money, buying trains and building track. They turn a sharp puzzle into a tycoon game and dilute the one decision, which train goes first.
  • Hardest part: puzzle generation. Search every timetable, count perfect and near-perfect ones, and keep days where few are perfect and the earliest times fail.

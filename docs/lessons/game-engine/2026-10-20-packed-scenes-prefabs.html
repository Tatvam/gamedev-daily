Packed scenes in Godot, prefabs in Unity

How Godot and Unity store a reusable template object, why each instance saves only its overrides, and what happens when the game loads one.

You built an enemy, copied it thirty times across five levels, and then decided it should be a little bigger. Now you have thirty edits to make, and you will miss one. Or you made all thirty enemies from one template, changed the template once, and one enemy stayed small anyway, because months ago someone nudged its size by hand.

A template and its instances

A template is a saved object you can stamp out many times: its nodes or components, and the values on them. Godot calls it a packed scene: any scene saved as a .tscn file, loaded as a PackedScene resource. Unity calls it a prefab: a GameObject with its children and components, saved as a .prefab asset.

Each copy you place in a level is an instance: the template's whole tree, hung under one node of another tree.

An instance stores only its differences

The level file does not hold thirty full enemies. For each instance it holds a reference to the template plus the values that instance changed. A value an instance sets for itself is an override. Reading any property follows one rule:

  1. If the instance has an override for it, use that.
  2. Otherwise use the template's value.

That rule gives both behaviours from the hook. Change the template and every instance that does not override that property follows. An instance that overrides it keeps its own value, whether you meant it to or not. Position is the everyday override: each placed enemy has its own.

What happens when the game loads one

When a level loads, or your code spawns an instance, the engine:

  1. reads the template,
  2. builds a complete new copy of its objects with the template's values,
  3. writes the overrides on top,
  4. adds the copy to the running scene, and starts calling its scripts.

Ownership changes along the way. On disk, the template owns the defaults and the level owns the overrides. In memory, every instance owns a full set of its own values, so changing one enemy while the game runs touches nothing else. The template link is what lets the editor push your edits into every level; it is not checked each frame.

The engines differ on step 4. In Godot, instantiate() returns the new nodes without adding them to the scene tree; their _ready runs only when you add_child them. In Unity, Instantiate adds the copy to the scene straight away, and an active copy's Awake has already run before the call returns. So in Godot you can set values before the instance's setup code runs; in Unity it has already run.

Templates inside templates

Both engines let a template contain instances of other templates, and let one template extend another: an inherited scene in Godot, a prefab variant in Unity. A variant is a reference to the base plus its overrides, the same rule again.

Both editors mark overrides. Unity shows them in bold with a blue bar in the margin, and the Overrides menu in the Inspector applies or reverts them. Godot shows a revert arrow next to a changed property, and Editable Children lets you change nodes inside an instance.

Rule of thumb

Put a value in the template if it should be the same everywhere. Override it only where one instance has a reason to differ.

The code

LÖVE has no templates, so the Lua builds one with a metatable, which tells Lua where to look for keys a table lacks. An instance holds only its overrides, and __index sends every other lookup to the template: the override rule in one line. instantiate is steps 2 and 3 of loading. Keys: T edits the template, O overrides Enemy2, R reverts it, Space spawns a copy of Enemy3.

-- The template: the values every enemy starts from.
local enemy = { hue = 10, size = 1.0 }

-- An instance stores only its overrides and asks the template for the rest.
local function place(template, overrides)
  return setmetatable(overrides or {}, { __index = template })
end

-- Loading: a full, independent copy with the overrides written on top.
local function instantiate(instance)
  local copy = {}
  for key, value in pairs(getmetatable(instance).__index) do copy[key] = value end
  for key, value in pairs(instance) do copy[key] = value end
  return copy
end

local level = { place(enemy), place(enemy), place(enemy, { size = 1.6 }), place(enemy) }

local function hueToRgb(h)
  local function f(n)
    local k = (n + h / 60) % 6
    return 1 - math.max(0, math.min(k, 4 - k, 1))
  end
  return f(5), f(3), f(1)
end

function love.keypressed(key)
  if key == "t" then enemy.hue = (enemy.hue + 30) % 360 end  -- every instance follows
  if key == "o" then level[2].hue = 200 end                   -- Enemy2 stops following
  if key == "r" then level[2].hue = nil end                   -- revert: back to the template
  if key == "space" then
    local spawned = instantiate(level[3])
    print(spawned.hue, spawned.size, getmetatable(spawned))  -- 10 1.6 nil: no link left
  end
end

function love.draw()
  for i, e in ipairs(level) do
    love.graphics.setColor(hueToRgb(e.hue))
    local half = 20 * e.size
    love.graphics.rectangle("fill", 100 * i - half, 200 - half, half * 2, half * 2)
  end
end
# level.gd (Godot 4). Attach to a Node2D in a new scene and run.
# The template is built in code so the script runs on its own. In a real project you
# save it as res://enemy.tscn and write: const ENEMY = preload("res://enemy.tscn")
extends Node2D

func make_template() -> PackedScene:
    var root := Node2D.new()
    root.name = "Enemy"
    var body := Polygon2D.new()
    body.name = "Body"
    body.polygon = PackedVector2Array([Vector2(-20, -20), Vector2(20, -20), Vector2(20, 20), Vector2(-20, 20)])
    body.color = Color.from_hsv(10.0 / 360.0, 0.65, 0.9)   # hue 10
    root.add_child(body)
    body.owner = root            # only nodes owned by the root are packed
    var scene := PackedScene.new()
    scene.pack(root)
    root.free()
    return scene

func _ready() -> void:
    var enemy_scene := make_template()
    for i in 4:
        var enemy := enemy_scene.instantiate() as Node2D   # a full copy, not in the tree yet
        enemy.name = "Enemy%d" % (i + 1)
        enemy.position = Vector2(100 * (i + 1), 200)
        if i == 2:
            enemy.scale = Vector2(1.6, 1.6)   # set before add_child, so its _ready sees it
        add_child(enemy)                       # _ready runs here
    # At run time there is no link: this recolours Enemy2 only.
    var body2 := get_node("Enemy2/Body") as Polygon2D
    body2.color = Color.from_hsv(200.0 / 360.0, 0.65, 0.9)
// Spawner.cs (Unity 6 or 2022 LTS). Setup: GameObject > 3D Object > Cube, drag the cube into
// the Project window to make a prefab, delete it from the scene. Add this script to an empty
// GameObject, drag the prefab into Enemy Prefab, press Play.
using UnityEngine;

public class Spawner : MonoBehaviour
{
    public GameObject enemyPrefab;   // the template: an asset, not an object in the scene
    readonly GameObject[] enemies = new GameObject[4];

    void Start()
    {
        for (int i = 0; i < 4; i++)
        {
            // A full copy, already in the scene. Awake on its scripts has run by now.
            enemies[i] = Instantiate(enemyPrefab, new Vector3(1.5f * i, 0f, 0f), Quaternion.identity);
            enemies[i].name = "Enemy" + (i + 1);
        }
        enemies[2].transform.localScale = Vector3.one * 1.6f;   // this copy only

        // .material gives this renderer its own copy of the material, so only Enemy2 changes.
        enemies[1].GetComponent<Renderer>().material.color = Color.HSVToRGB(200f / 360f, 0.65f, 0.9f);

        // Writing to enemyPrefab here would change the asset, not an instance.
    }
}

Godot 3 named this method instance(); Godot 4 renamed it instantiate().

Pitfalls

  • Accidental overrides. Nudge a value on an instance and put it back by eye, and it may now be stored as an override that blocks template edits. Look for the bold property or the revert arrow.
  • Shared sub-resources. A resource inside the template, such as a material or a collision shape, can be one object shared by all instances. In Godot it stays shared unless you enable Local to Scene on it or duplicate it. In Unity, renderer.sharedMaterial changes every enemy, while renderer.material makes a private copy that your code is responsible for destroying.
  • Editing the template instead of the instance. In Unity, a prefab field points at the asset. Changing it at run time changes future spawns, and in the Editor the change can outlive Play mode. Change the object Instantiate returned.
  • Setting values too late. In Unity, code in Awake sees the template's values, because it ran inside Instantiate. Read them in Start instead. In Godot, set values between instantiate() and add_child.
  • Renaming inside a template. Rename a child node in a Godot scene, or a serialized field in a Unity script, and existing overrides can silently stop applying. Unity's [FormerlySerializedAs] attribute helps with fields.
  • Spawning cost. Every instantiation builds a full copy. Spawning many bullets per second can cause hitches; object pooling, a later lesson, is the fix.

In real games

In both engines, almost everything spawned at run time comes from a template: bullets, pickups, enemies, damage numbers, menu rows. In Godot a level, a character and a menu are all scenes, so a game is scenes instancing scenes. Unity's current workflow, with nested prefabs and variants, arrived in Unity 2018.3.

The idea is older than both engines: the prototype pattern. Lua's metatables, used above, are the standard way Lua programs share defaults between tables.

Your turn (15 minutes)

In your own project, make a template for something you place more than twice, such as a coin or a crate. Place three instances. Override one property on one instance, then change that property and one other in the template.

Predict which instances change before you look, then revert the override. You are done when your predictions were right and you can point to where your engine shows the override.

Takeaways

  • A packed scene in Godot and a prefab in Unity are saved templates. Each placed copy is an instance.
  • A scene file stores each instance as a reference to its template plus its overrides. Anything not overridden comes from the template.
  • When the game runs, every instance is a full, independent copy. The template link is used by the editor and at load time, not every frame.
  • Godot runs _ready when you add the instance to the tree; Unity runs Awake inside Instantiate.
  • Watch for accidental overrides and for resources that are still shared between instances.

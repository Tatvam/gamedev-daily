Polling versus event-driven input

Why asking every frame whether a key is down can miss quick taps, how input events catch every press, and how Godot and Unity offer both.

On a fast machine the jump button always works. During a heavy scene, when the game drops to 15 frames per second, some quick taps do nothing at all. The player is sure they pressed it, and they are right. The game simply never looked at the key while it was down.

Two ways to learn about a key

The operating system notices each key change and puts a message about it in a queue for your window. The engine reads that queue, usually once per frame, and offers you two ways to find out what happened.

Polling: ask about the state now

Polling means asking "is this key down at this moment?" once per frame. The engine keeps a table of which keys are held, updates it from the queued messages, and answers from the table. In LÖVE that question is love.keyboard.isDown("space").

Polling suits things that last, such as walking or charging a shot, and keeps all input code in your update, in a known order.

To get a one-off action such as a jump from polling, you compare this frame's answer with the last one. "Down now, up last frame" is a new press. This is called edge detection, and it is where polling breaks.

The gap between two looks

A poll is a sample: it sees the state at one instant per frame. At 60 frames per second the samples are 16.7 milliseconds apart. At 10 per second they are 100 milliseconds apart. A quick tap can easily be shorter than 100 milliseconds, and a key pressed and released entirely between two samples is up at both of them. As far as polling can tell, it never happened.

Events: be told about every change

An input event is one of those queued messages, handed to your code: "space went down", then later "space came up". Instead of asking, you write a function, a callback, that the engine calls once for each event. In LÖVE that is love.keypressed(key).

Events are not faster than polling: the engine still hands them over at the next frame. But they are not lost. A tap between two frames arrives as a press and a release, both delivered at the next frame. The price is that your code runs in a callback, outside your update, so it usually just records what happened for the update to act on.

What the engines do with this

Godot 4. Polling: Input.is_key_pressed(KEY_SPACE) or Input.is_action_pressed("jump"). Events: override _unhandled_input(event) (or _input) on a node, which is called once per event. The edge check Input.is_action_just_pressed is recorded when the press event arrives, not sampled. The Godot 4.5 documentation says it still returns true for an action that was pressed and released again in the same frame, "so as not to miss input". A project setting, input_devices/compatibility/legacy_just_pressed_behavior, brings back the old behaviour that missed such taps. It is off by default.

Unity 6 and 2022 LTS, Input System package. Polling: Keyboard.current.spaceKey.isPressed, or IsPressed() on an input action. Edge checks: wasPressedThisFrame on a control and WasPressedThisFrame() on an action. Events: subscribe to an action's performed callback, which runs as the Input System processes queued input. The older Input Manager has Input.GetKey for polling and Input.GetKeyDown for edges. I could not confirm whether these "this frame" checks report a press released inside the same frame, so when every tap matters, use the callback.

Rule of thumb

Poll for things that last, such as movement. Use events, or the engine's event-built "just pressed" check, for things that happen once, such as jumping, shooting or opening a menu.

The code

This LÖVE program counts space presses in both ways, like the demo's counters. It sleeps in every update to fake a game running at 10 frames per second. Tap space quickly and the polling count falls behind the event count.

local FRAME_RATE = 10        -- slow frames make the gaps between polls wide
local polledPresses = 0
local eventPresses = 0
local wasDown = false

-- Event: LÖVE calls this once for every press, before love.update runs.
function love.keypressed(key, scancode, isrepeat)
  if key == "space" and not isrepeat then
    eventPresses = eventPresses + 1
  end
end

function love.update(dt)
  -- Poll: is the key down at this moment?
  local isDown = love.keyboard.isDown("space")
  if isDown and not wasDown then          -- edge: down now, up last frame
    polledPresses = polledPresses + 1
  end
  wasDown = isDown
  love.timer.sleep(1 / FRAME_RATE)        -- pretend the game is busy
end

function love.draw()
  love.graphics.print("polling saw " .. polledPresses, 20, 20)
  love.graphics.print("events saw  " .. eventPresses, 20, 40)
end
# tap_counter.gd, on any Node in the main scene. Godot 4.
extends Node

var polled_presses := 0
var event_presses := 0
var just_pressed_count := 0
var was_down := false

func _ready() -> void:
    Engine.max_fps = 10    # slow frames make the gaps between polls wide

# Event: called once for every input event that nothing else handled.
func _unhandled_input(event: InputEvent) -> void:
    if event is InputEventKey and event.pressed and not event.echo \
            and event.keycode == KEY_SPACE:
        event_presses += 1

func _process(_delta: float) -> void:
    # Poll: is the key down at this moment?
    var is_down := Input.is_key_pressed(KEY_SPACE)
    if is_down and not was_down:
        polled_presses += 1
    was_down = is_down
    # Built from events by the engine. ui_accept includes Space by default.
    if Input.is_action_just_pressed("ui_accept"):
        just_pressed_count += 1
    if Input.is_action_just_pressed("ui_cancel"):
        print("polling ", polled_presses, ", events ", event_presses,
                ", just pressed ", just_pressed_count)
// TapCounter.cs. Unity 6 or 2022 LTS with the Input System package installed.
using UnityEngine;
using UnityEngine.InputSystem;

public class TapCounter : MonoBehaviour
{
    int polledPresses, eventPresses;
    bool wasDown;
    InputAction jump;

    void Awake()
    {
        QualitySettings.vSyncCount = 0;
        Application.targetFrameRate = 10;   // slow frames, wide gaps
        jump = new InputAction("Jump", InputActionType.Button, "<Keyboard>/space");
        jump.performed += ctx => eventPresses++;   // event: once per press
    }

    void OnEnable()  { jump.Enable(); }
    void OnDisable() { jump.Disable(); }

    void Update()
    {
        // Poll: is the key down at this moment?
        bool isDown = Keyboard.current != null && Keyboard.current.spaceKey.isPressed;
        if (isDown && !wasDown) polledPresses++;
        wasDown = isDown;
    }

    void OnGUI()
    {
        GUILayout.Label("polling saw " + polledPresses);
        GUILayout.Label("events saw " + eventPresses);
    }
}

In Godot, press Escape (ui_cancel) to print the three counts. The third, built by the engine from events, should match the event count, not the polling count.

Pitfalls

  • Building one-off actions from your own polling. Comparing isDown with last frame works at 60 frames per second and quietly fails during a slowdown. Use an event, or the engine's own just-pressed check.
  • Reading "pressed this frame" in the fixed step in Unity. FixedUpdate can run zero or several times in one frame, so a one-frame flag can be missed or seen twice. Read it in Update, store it, and let the next fixed step use it. Godot tracks physics ticks separately, and its documentation says is_action_just_pressed works per physics tick inside _physics_process.
  • Doing gameplay inside the callback. It runs at a different point in the frame from your update. Record the event, such as jumpQueued = true, and act on it in the update.
  • Counting key repeat as presses. Holding a key makes the operating system send repeated press events. Skip them with isrepeat in LÖVE and event.echo in Godot.
  • Keeping your own held state from events. If the window loses focus while a key is down, the release may never reach you and the key stays "held". Clear your state when focus is lost (love.focus in LÖVE), or poll for held keys instead.

In real games

LÖVE is built on the SDL library, which offers both styles at the bottom layer: an event queue and a keyboard state array. Godot and Unity both expose both styles. Godot's source shows its just-pressed check being recorded as each event is parsed, and Unity's Input System is also fed by a queue of input events. Browsers offer only events (keydown and keyup), so browser games that poll, like this page's demo, fill their own table of held keys from those events.

Your turn (15 minutes)

In your own project, cap the frame rate at 10 (Engine.max_fps in Godot, Application.targetFrameRate with QualitySettings.vSyncCount = 0 in Unity). Tap jump twenty times as quickly as you can and count the jumps. If any were lost, move the press detection to an event callback or the engine's just-pressed check, store it in a jumpQueued flag, and consume the flag in your update. You are done when twenty quick taps give twenty jumps at 10 frames per second.

Takeaways

  • Polling asks "is it down now?" once per frame. It cannot see anything that starts and ends between two frames.
  • Events report every change. They are handled at the next frame, so they are not faster, but they are never lost.
  • Poll for held actions such as movement. Use events or the engine's just-pressed check for one-off actions such as jumping.
  • Godot 4.5's is_action_just_pressed is built from events and catches a press and release inside one frame by default.

The game loop: input, update, render

Every engine repeats three jobs each frame: read input, update the world, draw it. Learn the order, who owns each piece of data, and where your code runs.

You move the player in one script and the camera in another, and the camera wobbles a pixel behind the player on some frames. Or a button press registers one frame late, or not at all.

Bugs like these are about order: which code ran first inside a frame, and which copy of the data it saw.

One loop, three jobs

A game is a program that never finishes its main loop until the player quits. That loop is the game loop. One pass through it is a frame. At 60 frames per second one pass has about 16.7 milliseconds to do everything.

Every engine, from a hand-written LÖVE game to Godot and Unity, does the same three jobs in each pass:

  1. Input. Collect what happened since the last frame (keys, mouse, touch, gamepad) into a snapshot of the input state.
  2. Update. Advance the world by a small slice of time. Game code reads the snapshot and changes positions, health and timers. Nothing is drawn yet.
  3. Render. Read the world state and turn it into pixels. Rendering should only read the world, never change it.

Then the loop goes around again. Each job writes one kind of data and only reads what came before it.

Why the order matters

Because the jobs run one after another, the same fact can have three different values at the same moment. The key on your keyboard is up, but this frame's snapshot still says it is down. The ball in memory has moved, but the screen still shows the old position until Render runs. That is not a bug; it is how every frame works.

It also explains the classic "one frame late" bug. If the camera reads the player's position during Update before the player script has moved, the camera follows last frame's position. On the screen that looks like a small jitter.

Who owns the loop

In LÖVE, the loop is a Lua function called love.run. A simplified version of the default reads like the three jobs above:

-- simplified from LÖVE 11's default love.run, one frame
love.event.pump()                      -- 1. input: ask the OS for events
local dt = love.timer.step()           -- time since the last frame
love.update(dt)                        -- 2. update: your game code
love.graphics.clear()
love.draw()                            -- 3. render: your drawing code
love.graphics.present()                -- show the finished frame

Godot and Unity own the loop completely. You never write it. Instead you write callbacks: functions with special names that the engine calls at a fixed point in its loop. Both engines also add a fourth job that the simple loop above does not have: a fixed step for physics, which runs zero, one or several times per frame so that physics advances in equal slices of time.

Notice the Render row. In LÖVE you issue every draw call yourself, every frame. In Godot and Unity you mostly do not draw at all. You change data the engine owns, such as a node's position or a GameObject's transform, and the engine's renderer reads that data after your Update code has finished. The engine owns the pixels. You own the world state that feeds them.

Rule of thumb

Ask two questions about any line of game code: in which job does it run, and which data does it read? If it reads data that a later job in the same frame writes, it is looking at last frame.

The code

The Lua version makes the three jobs visible by giving each one its own function, with the same names and numbers as the demo. LÖVE calls love.update and then love.draw once per frame, so the order is fixed by the loop, not by luck.

local SPEED = 120            -- world units per second
local WIDTH = 300            -- the world is 0..300 wide
local RADIUS = 10
local ball = { x = 150, vx = 0 }
local input = { dir = 0 }    -- snapshot, written once per frame

local function readInput()   -- 1. input: only writes the snapshot
  input.dir = 0
  if love.keyboard.isDown("left") then input.dir = input.dir - 1 end
  if love.keyboard.isDown("right") then input.dir = input.dir + 1 end
end

local function updateWorld(dt)   -- 2. update: reads the snapshot, writes the world
  ball.vx = input.dir * SPEED
  ball.x = ball.x + ball.vx * dt
  ball.x = math.max(RADIUS, math.min(WIDTH - RADIUS, ball.x))
end

function love.update(dt)
  readInput()
  updateWorld(dt)
end

function love.draw()         -- 3. render: only reads the world
  love.graphics.circle("fill", ball.x, 100, RADIUS)
end
# Godot 4. Attach to a Node2D in a new scene and run it.
extends Node2D

const SPEED := 120.0

func _ready() -> void:
    position = Vector2(150, 100)

# Called once per frame, after Godot has collected this frame's input.
func _process(delta: float) -> void:
    var dir := Input.get_axis("ui_left", "ui_right")
    position.x += dir * SPEED * delta
    position.x = clamp(position.x, 10.0, 290.0)

# Called when the node first appears and after queue_redraw(), not every frame.
# The engine keeps the result and draws it at the node's new position.
func _draw() -> void:
    draw_circle(Vector2.ZERO, 10.0, Color.WHITE)
// Unity 6 or 2022 LTS. Put on a GameObject with a SpriteRenderer.
// Uses the legacy Input Manager. In Unity 6 projects set Player Settings >
// Active Input Handling to "Both", or read the keyboard through the Input System.
using UnityEngine;

public class BallMover : MonoBehaviour
{
    // 1.2 units is about 120 pixels at the default 100 pixels per unit.
    const float Speed = 1.2f;

    // Called once per frame, after Unity has read this frame's input.
    void Update()
    {
        float dir = Input.GetAxisRaw("Horizontal");
        transform.position += new Vector3(dir * Speed * Time.deltaTime, 0f, 0f);
    }

    // No draw code: Unity renders every camera after Update and LateUpdate.
}

All three read input, then move by speed times the frame's duration. Only the Lua version draws by hand, because in LÖVE you are the renderer.

Pitfalls

  • Reading data before it is written. A camera that follows the player during Update may run before the player moved, so it follows last frame's position. In Unity, move followers in LateUpdate, which runs after every Update. In Godot, a node's process_priority controls the order of _process calls (lower runs first), or the follower can be placed later in the scene tree.
  • Assuming an order between objects. Within one job, the engine decides which object goes first. Godot processes nodes in scene tree order unless priorities say otherwise. Unity does not promise an order between scripts unless you set one in Project Settings under Script Execution Order. Design so that the order does not matter, or make it explicit.
  • Blocking the loop. A slow file load or long search inside Update also delays input and drawing, so the game freezes. Spread long work over several frames or move it off the main thread.
  • Expecting changes to appear immediately. Setting a position draws nothing. The change becomes visible at the next Render.

In real games

Every real-time game has this loop somewhere. LÖVE exposes it as love.run, which you can replace entirely. Godot's loop is driven by a MainLoop object, and the SceneTree you work with every day is the default one. Unity exposes the order of its internal systems through the PlayerLoop API, which advanced users can inspect and extend.

Your turn (15 minutes)

In your own project, add one print line to each callback on a single object, including the frame number: Engine.get_process_frames() in Godot, Time.frameCount in Unity. Use _input, _physics_process and _process in Godot, or FixedUpdate, Update and LateUpdate in Unity. Run for a second and read three frames of output.

Write the order down as a timeline. You are done when you can say, for one object that follows another (a camera, a health bar, a pet), which callback moves the leader, which moves the follower, and whether the follower sees this frame's position or last frame's.

Takeaways

  • A game loop repeats three jobs every frame: input, update, render.
  • Each job owns one kind of data: input writes a snapshot, update writes the world, render writes pixels.
  • Data flows forward inside a frame. Code that reads something written later in the frame sees last frame's value.
  • LÖVE lets you own the loop. Godot and Unity own it and call your code through callbacks at fixed points.
  • In Godot and Unity you rarely draw. You change world data, and the engine draws it after your update code finishes.

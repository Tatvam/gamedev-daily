Frame pacing and vsync

Why evenly spaced frames feel smoother than a higher but uneven frame rate, what vsync does to frame times, and how Godot and Unity set it.

The counter in the corner says 50 frames per second, yet the camera pan hitches every few frames. Lock the same game to 30 and it suddenly looks calmer, even though fewer pictures reach the screen. The counter was telling the truth about the average and nothing about the spacing.

Frame rate is an average, frame time is what you see

Frame time is how long one frame takes, in milliseconds. 60 frames per second means 16.7 ms per frame on average. The word "average" hides a lot:

RunFrame times (ms)Counter showsLooks
A16.7, 16.7, 16.7, 16.760 fpssmooth
B8.3, 25, 8.3, 2560 fpsshaky
C16.7, 16.7, 33.3, 16.7, 16.7, 33.345 fpsstutters
D33.3, 33.3, 33.3, 33.330 fpssteady

Your eye expects a moving object to cover equal distances in equal times. When one picture stays up twice as long as its neighbours, the object seems to stop, then jump. Frame pacing is how evenly frames are spaced when they reach the screen. Run D has worse frame rate than C and better pacing, and many players prefer it.

The screen has its own clock

A typical monitor redraws itself at a fixed rate, for example 60 times per second. Each refresh reads a picture from memory and sends it out line by line, top to bottom. The short gap before the next refresh starts is the vertical blank.

The game never draws straight into the picture being shown. It draws into a hidden back buffer, then hands it over with a swap, which makes it the front buffer the display reads from. Until the swap the game owns the picture; after it, the display does. The only question is when the swap may happen.

  • Vsync off. The swap happens the moment the frame is ready, even halfway through a refresh. The top of the screen shows the old frame and the bottom the new one, split at a visible line: tearing.
  • Vsync on. Vsync (vertical synchronisation) makes the swap wait for the vertical blank. No tearing, but a frame that misses the deadline by 1 ms waits for the next refresh. The old picture is shown twice, and that frame takes 33.3 ms on screen.

So with vsync on, frame times snap to whole refreshes: 16.7, 33.3, 50 ms. A game whose frames take 15 to 20 ms does not run at a smooth 55. It flips between 60 and 30 from one frame to the next, which is run C in the table. In the simple model drawn here, where the game waits for each swap before starting the next frame, a game that always takes 18 ms drops straight to 30. Real drivers often queue an extra frame (triple buffering), which raises the average but adds delay.

How to get even spacing

  • Fit the budget with room to spare. If your worst frames stay under 16.7 ms, vsync gives you a perfectly flat 60.
  • Cap at a rate that divides the refresh. 30 on a 60 Hz screen, 40 or 60 on 120 Hz. Every picture then stays up for the same number of refreshes.
  • Variable refresh rate. Displays with VRR (sold as G-Sync, FreeSync or Adaptive-Sync) wait for the game instead, within a range, so a 20 ms frame is shown for 20 ms.

Try it

A tiny model of a game and a 60 Hz display. The game draws frames back to back, each taking the render time plus a random jitter. The top panel is the screen, the graph shows how long each new picture stayed up. Red bars differ from the bar before them: those are the hitches you feel.

Start at 15 ms with vsync on: the graph is flat. Raise the jitter to 6 ms and watch bars jump to 33.3 while the average falls to about 45 per second. Now pick the 30 per second cap: lower, but flat again. Finally switch vsync off and look for the red tear marks at the screen edges. Quarter speed and Step one refresh help you see each picture.

The model leaves out the GPU working in parallel with the CPU, driver frame queues and compositors. It treats each refresh of your own screen as one 60 Hz refresh, so on a 120 Hz screen it runs twice as fast.

The code

The most useful pacing tool is a frame time graph you can switch on in any build. This LÖVE version uses the demo's numbers: it burns 15 ms plus or minus 6 ms per frame to stand in for rendering, keeps the last 48 frame times and draws them as bars. Press V to toggle vsync and watch the bars change.

-- conf.lua: function love.conf(t) t.window.vsync = 1 end
local RENDER_MS = 15   -- pretend cost of one frame
local JITTER_MS = 6    -- random change in that cost, plus or minus
local SPEED, SPACING = 240, 40
local HISTORY = 48     -- frame times kept for the graph
local times = {}       -- ring buffer, milliseconds
local head, scroll, vsync = 0, 0, 1

function love.load()
  math.randomseed(7)
  love.window.setVSync(vsync)
end

local function burn(ms)   -- stands in for real rendering work
  local stop = love.timer.getTime() + ms / 1000
  while love.timer.getTime() < stop do end
end

function love.update(dt)
  head = head % HISTORY + 1
  times[head] = dt * 1000   -- includes any wait for vsync
  scroll = (scroll + SPEED * dt) % SPACING
end

function love.draw()
  for x = -SPACING, love.graphics.getWidth(), SPACING do
    love.graphics.rectangle("fill", x + scroll, 0, 14, 130)
  end
  local n, sum, worst = #times, 0, 0
  for i = 1, n do
    local ms = times[(head + i - 1) % n + 1]   -- oldest first
    sum = sum + ms
    worst = math.max(worst, ms)
    love.graphics.rectangle("fill", 10 + (i - 1) * 6, 300 - ms * 2, 4, ms * 2)
  end
  if sum > 0 then
    love.graphics.print(string.format("avg %.1f fps  worst %.1f ms  vsync %d (V)",
      1000 * n / sum, worst, vsync), 10, 310)
  end
  burn(math.max(2, RENDER_MS + JITTER_MS * (2 * math.random() - 1)))
end

function love.keypressed(key)
  if key == "v" then
    vsync = 1 - vsync
    love.window.setVSync(vsync)
  end
end
# Godot 4. Attach to a Node2D in a new scene. Press V to toggle vsync.
extends Node2D

const RENDER_MS := 15.0
const JITTER_MS := 6.0
const SPEED := 240.0
const SPACING := 40.0
const HISTORY := 48

var times: Array[float] = []
var scroll := 0.0
var last_usec := 0
var rng := RandomNumberGenerator.new()

func _ready() -> void:
    rng.seed = 7
    DisplayServer.window_set_vsync_mode(DisplayServer.VSYNC_ENABLED)
    Engine.max_fps = 0   # no cap; try 30
    last_usec = Time.get_ticks_usec()

func _process(delta: float) -> void:
    # Measure real time between frames rather than trusting delta,
    # which Godot may smooth while vsync is on.
    var now := Time.get_ticks_usec()
    times.append((now - last_usec) / 1000.0)
    last_usec = now
    if times.size() > HISTORY:
        times.pop_front()
    scroll = fmod(scroll + SPEED * delta, SPACING)
    var cost := maxf(2.0, RENDER_MS + JITTER_MS * rng.randf_range(-1.0, 1.0))
    var stop := Time.get_ticks_usec() + int(cost * 1000.0)
    while Time.get_ticks_usec() < stop:   # stands in for rendering work
        pass
    queue_redraw()

func _draw() -> void:
    var x := -SPACING
    while x < get_viewport_rect().size.x:
        draw_rect(Rect2(x + scroll, 0, 14, 130), Color.WHITE)
        x += SPACING
    var sum := 0.0
    var worst := 0.0
    for i in times.size():
        var ms := times[i]
        sum += ms
        worst = maxf(worst, ms)
        draw_rect(Rect2(10 + i * 6, 300 - ms * 2, 4, ms * 2), Color.ORANGE)
    if sum > 0.0:
        var on := DisplayServer.window_get_vsync_mode() == DisplayServer.VSYNC_ENABLED
        draw_string(ThemeDB.fallback_font, Vector2(10, 330),
            "avg %.1f fps  worst %.1f ms  vsync %s (V)" % [1000.0 * times.size() / sum, worst, on])

func _unhandled_input(event: InputEvent) -> void:
    if event is InputEventKey and event.pressed and event.keycode == KEY_V:
        var on := DisplayServer.window_get_vsync_mode() == DisplayServer.VSYNC_ENABLED
        DisplayServer.window_set_vsync_mode(
            DisplayServer.VSYNC_DISABLED if on else DisplayServer.VSYNC_ENABLED)
// Unity 6 or 2022 LTS. Put on an empty GameObject and test in a build:
// the Editor's own timing is not representative.
using UnityEngine;

public class FramePacing : MonoBehaviour
{
    const float RenderMs = 15f, JitterMs = 6f, Speed = 240f, Spacing = 40f;
    const int History = 48;
    readonly float[] times = new float[History];
    readonly System.Random rng = new System.Random(7);
    int head, count;
    float scroll;

    void Start()
    {
        QualitySettings.vSyncCount = 1;     // 0 off, 1 every refresh, 2 every second
        Application.targetFrameRate = -1;   // only used when vSyncCount is 0
    }

    void Update()
    {
        times[head] = Time.unscaledDeltaTime * 1000f;
        head = (head + 1) % History;
        count = Mathf.Min(count + 1, History);
        scroll = (scroll + Speed * Time.unscaledDeltaTime) % Spacing;

        float cost = Mathf.Max(2f, RenderMs + JitterMs * (float)(rng.NextDouble() * 2.0 - 1.0));
        var watch = System.Diagnostics.Stopwatch.StartNew();   // stands in for rendering
        while (watch.Elapsed.TotalMilliseconds < cost) { }
    }

    void OnGUI()
    {
        if (GUI.Button(new Rect(10, 340, 160, 30), "Toggle vsync"))
            QualitySettings.vSyncCount = QualitySettings.vSyncCount == 0 ? 1 : 0;
        if (Event.current.type != EventType.Repaint) return;

        for (float x = -Spacing; x < Screen.width; x += Spacing)
            GUI.DrawTexture(new Rect(x + scroll, 0, 14, 130), Texture2D.whiteTexture);
        float sum = 0f, worst = 0f;
        for (int i = 0; i < count; i++)
        {
            float ms = times[(head - count + i + History) % History];   // oldest first
            sum += ms;
            worst = Mathf.Max(worst, ms);
            GUI.DrawTexture(new Rect(10 + i * 6, 300 - ms * 2, 4, ms * 2), Texture2D.whiteTexture);
        }
        if (sum > 0f)
            GUI.Label(new Rect(10, 310, 400, 24),
                $"avg {1000f * count / sum:F1} fps  worst {worst:F1} ms  vSyncCount {QualitySettings.vSyncCount}");
    }
}

Pitfalls

  • Judging by the frame rate counter. An average over a second hides single long frames. Look at a frame time graph and at the worst frame, not the mean.
  • A cap that does not divide the refresh. 50 per second on a 60 Hz screen with vsync on means a mix of 16.7 and 33.3 ms pictures: the worst of both. Read the real refresh rate instead of assuming 60; 120 and 144 Hz screens are common.
  • Expecting targetFrameRate to work with vsync on. On desktop Unity ignores it unless vSyncCount is 0. Unity's documentation also notes that the software cap is less precise than vsync and can cause small stutters.
  • Pacing the start, not the arrival. A software cap times when frames begin. If their cost varies, they still reach the screen unevenly. Try the 30 cap with vsync off in the demo to see it.
  • Measuring in the editor. Editor windows, tool panels and desktop compositors all change timing. Judge pacing in an exported build, ideally full screen.

In real games

Console games commonly offer a "quality" mode locked at 30 and a "performance" mode at 60 rather than an unlocked rate in between, because both divide a 60 Hz TV evenly. Insomniac's Ratchet & Clank: Rift Apart added a 40 per second mode for 120 Hz displays, where 40 divides the refresh into three.

The Steam Deck's performance menu lets players set both a frame limit and the screen refresh rate, so the two can be matched. On Android, Google's Frame Pacing library (also called Swappy) lines up when a game submits frames with when the display uses them, and Unity exposes it as the Optimized Frame Pacing option in the Android player settings.

Takeaways

  • Frame pacing is how evenly pictures reach the screen. Even spacing matters more than a high average.
  • Vsync stops tearing by waiting for the refresh, so frame times snap to whole refreshes: 16.7, 33.3, 50 ms at 60 Hz.
  • A frame rate between 30 and 60 on a 60 Hz screen with vsync is a stutter of mixed 16.7 and 33.3 ms frames.
  • Fit the budget, cap at a divisor of the refresh rate, or use a VRR display.
  • Godot uses V-Sync Mode and Engine.max_fps; Unity uses vSyncCount and targetFrameRate, which do not combine on desktop.

Entity component system: data in tables, logic in systems

How an ECS keeps components in tables keyed by entity id and runs systems over every entity that has the right set, and how Unity and Godot relate to it.

A bullet-hell scene has 5,000 bullets. Each is a node or GameObject with its own update script, so every frame the engine visits 5,000 objects and runs the same few lines on each in turn. The work is identical for every bullet. Only the numbers differ.

An entity component system turns that around: one function, one loop, all the bullets.

Turning objects inside out

Yesterday's component pattern built an object from parts, and each part carried its own data and its own update code. An entity component system (ECS) splits those two apart into three pieces:

  • An entity is only an id, a number. It has no code and no data of its own.
  • A component is plain data with no code: a Position is an x and a y, Gravity is one number.
  • A system is a function that runs over every entity that has a certain set of components. The set it asks for is its query.

Picture the components as a table: a row per entity, a column per component type, and each cell filled or empty. A system only asks: does this row have every column I need?

What happens, in what order

The world holds the table and the list of systems. Each frame it runs the systems in a fixed order, here Gravity, Movement, Draw: Gravity changes the speed, Movement uses it, Draw shows the result. The outer loop is over systems, not objects:

-- Objects: for each object, do all of its work.
for _, obj in ipairs(objects) do obj:update(dt) end

-- ECS: for each system, do one job for every match.
for _, sys in ipairs(systems) do
  for id = 1, nextId do
    if matches(id, sys.needs) then sys.run(id, dt) end
  end
end

That swap is the whole idea. Order stops depending on where an object sits in a tree and becomes one list you can read top to bottom.

Who owns the data

The world owns every component. An entity owns nothing; it is the row number that ties cells together. A system owns logic but no per-entity state. So behaviour changes by data alone: give the tree a Velocity and Gravity starts pulling it down, with no code edited.

Why it can be fast

Real ECS libraries store the table compactly. Some keep each component type in its own packed array. Others group entities with exactly the same set of components, an archetype, and store each group side by side. Either way a system walks memory in order instead of hopping between objects, which processors handle very well. And because a query says what it reads and writes, systems that touch different data can run on different cores at once.

How the engines express it

Unity has a full ECS in the separate com.unity.entities package, part of DOTS, its Data-Oriented Technology Stack. The code below targets Entities 1.x on Unity 2022.3 LTS or Unity 6. A component is a struct implementing IComponentData. A system is a partial struct implementing ISystem that loops over SystemAPI.Query<RefRW<A>, RefRO<B>>() (read-write and read-only). Entities are stored by archetype in 16 KB blocks called chunks, so adding or removing a component moves the entity, a structural change. Order comes from system groups and [UpdateBefore] / [UpdateAfter]. You usually author GameObjects in a subscene and a step called baking converts them into entities.

Godot 4 has no built-in ECS. Its nodes update themselves, a design the Godot team has explained (see Further reading). For thousands of identical things, Godot's answer is to skip nodes and drive the low-level servers, such as RenderingServer and PhysicsServer2D, from one manager script. Community ECS add-ons exist. The GDScript tab writes the idea by hand, one Dictionary per component.

Rule of thumb

Reach for ECS when you have many things that share the same few behaviours: bullets, crowds, particles, units. For a few dozen unique, hand-built objects such as a player, a door and a menu, nodes and GameObjects are easier to build and debug.

The trade-off cuts both ways. ECS gives explicit order and fast loops, but behaviour is spread over systems, so "why did this entity do that?" takes more digging. Nodes and GameObjects keep everything about one thing in one place, at the cost of visiting objects one by one.

The code

A complete LÖVE program with the demo's six entities and numbers: a 400 by 180 world, gravity 300 px/s², bounces at y = 165 and y = 10, wrapping at the sides. It draws every sprite as a circle.

-- A tiny ECS. Keys 1-3 switch Gravity, Movement, Draw. T toggles the tree's Velocity.
local W, FLOOR, CEILING = 400, 165, 10
local nextId = 0
local position, velocity, gravity, sprite = {}, {}, {}, {}  -- one table per component

local function spawn(p, v, g, s)
  nextId = nextId + 1
  local id = nextId                        -- an entity is only this number
  position[id], velocity[id], gravity[id], sprite[id] = p, v, g, s
  return id
end

local function matches(id, needs)          -- the query
  for _, store in ipairs(needs) do
    if store[id] == nil then return false end
  end
  return true
end

local function runSystem(sys, dt)
  for id = 1, nextId do
    if matches(id, sys.needs) then sys.run(id, dt) end
  end
end

local Gravity = { on = true, needs = { velocity, gravity }, run = function(id, dt)
  velocity[id].y = velocity[id].y + gravity[id] * dt
end }

local Movement = { on = true, needs = { position, velocity }, run = function(id, dt)
  local p, v = position[id], velocity[id]
  p.x = p.x + v.x * dt
  p.y = p.y + v.y * dt
  if p.x > W then p.x = p.x - W end
  if p.x < 0 then p.x = p.x + W end
  if p.y > FLOOR then p.y, v.y = FLOOR, -math.abs(v.y) end
  if p.y < CEILING then p.y, v.y = CEILING, math.abs(v.y) end
end }

local Draw = { on = true, needs = { position, sprite }, run = function(id)
  local p, s = position[id], sprite[id]
  love.graphics.setColor(s.r, s.g, s.b)
  love.graphics.circle("fill", p.x, p.y, s.size)
end }

local ORDER = { Gravity, Movement }        -- update order; Draw runs in love.draw

function love.load()
  spawn({ x = 60, y = 150 }, { x = 50, y = 0 }, nil, { size = 8, r = 0.2, g = 0.45, b = 0.85 })   -- 1 hero
  spawn({ x = 150, y = 40 }, { x = 30, y = 0 }, 300, { size = 8, r = 0.9, g = 0.6, b = 0.1 })     -- 2 ball
  spawn({ x = 250, y = 150 }, nil, 300, { size = 12, r = 0.2, g = 0.6, b = 0.3 })                -- 3 tree
  spawn({ x = 320, y = 60 }, { x = -40, y = 20 }, nil, nil)                                      -- 4 ghost
  spawn({ x = 200, y = 30 }, { x = -15, y = 0 }, nil, { size = 10, r = 0.7, g = 0.7, b = 0.7 })  -- 5 cloud
  spawn({ x = 340, y = 20 }, { x = 0, y = 0 }, 300, { size = 6, r = 0.8, g = 0.2, b = 0.2 })     -- 6 apple
end

function love.keypressed(key)
  local sys = ({ Gravity, Movement, Draw })[tonumber(key) or 0]
  if sys then sys.on = not sys.on end
  if key == "t" then
    if velocity[3] then velocity[3] = nil else velocity[3] = { x = 0, y = 0 } end
  end
end

function love.update(dt)
  for _, sys in ipairs(ORDER) do
    if sys.on then runSystem(sys, dt) end
  end
end

function love.draw()
  love.graphics.scale(2)
  love.graphics.setColor(1, 1, 1)
  love.graphics.line(0, 173, W, 173)
  if Draw.on then runSystem(Draw, 0) end
end
# Godot 4. Attach to a Node2D in a new scene and run it.
# Godot has no built-in ECS, so this writes the idea by hand.
extends Node2D

const W := 400.0
const FLOOR := 165.0
const CEILING := 10.0
var next_id := 0
var positions := {}    # id -> Vector2, one Dictionary per component
var velocities := {}   # id -> Vector2
var gravities := {}    # id -> float
var sprites := {}      # id -> Color

func spawn(p, v, g, s) -> int:
    next_id += 1
    if p != null: positions[next_id] = p
    if v != null: velocities[next_id] = v
    if g != null: gravities[next_id] = g
    if s != null: sprites[next_id] = s
    return next_id

func query(stores: Array) -> Array:
    var ids := []
    for id in range(1, next_id + 1):
        var ok := true
        for store in stores:
            if not store.has(id):
                ok = false
        if ok:
            ids.append(id)
    return ids

func _ready() -> void:
    scale = Vector2(2, 2)
    spawn(Vector2(60, 150), Vector2(50, 0), null, Color.ROYAL_BLUE)    # 1 hero
    spawn(Vector2(150, 40), Vector2(30, 0), 300.0, Color.ORANGE)       # 2 ball
    spawn(Vector2(250, 150), null, 300.0, Color.FOREST_GREEN)          # 3 tree
    spawn(Vector2(320, 60), Vector2(-40, 20), null, null)              # 4 ghost
    spawn(Vector2(200, 30), Vector2(-15, 0), null, Color.LIGHT_GRAY)   # 5 cloud
    spawn(Vector2(340, 20), Vector2(0, 0), 300.0, Color.CRIMSON)       # 6 apple

func _process(delta: float) -> void:
    for id in query([velocities, gravities]):        # Gravity system
        var v: Vector2 = velocities[id]
        v.y += gravities[id] * delta
        velocities[id] = v
    for id in query([positions, velocities]):        # Movement system
        var p: Vector2 = positions[id]
        var v: Vector2 = velocities[id]
        p += v * delta
        if p.x > W: p.x -= W
        if p.x < 0.0: p.x += W
        if p.y > FLOOR:
            p.y = FLOOR
            v.y = -absf(v.y)
        if p.y < CEILING:
            p.y = CEILING
            v.y = absf(v.y)
        positions[id] = p
        velocities[id] = v
    queue_redraw()

func _draw() -> void:
    draw_line(Vector2(0, 173), Vector2(W, 173), Color.WHITE)
    for id in query([positions, sprites]):           # Draw system
        draw_circle(positions[id], 8.0, sprites[id])
// Needs the Entities package (com.unity.entities 1.x), Unity 2022.3 LTS or Unity 6.
// Put this in one .cs file. The systems are created automatically in the default world.
// y points down here to match the demo's numbers. Drawing needs the separate
// Entities Graphics package, so inspect the entities in the editor's Entities windows.
using Unity.Entities;
using Unity.Mathematics;

public struct Position : IComponentData { public float2 Value; }
public struct Velocity : IComponentData { public float2 Value; }
public struct Gravity  : IComponentData { public float Value; }

public partial struct SpawnSystem : ISystem
{
    public void OnCreate(ref SystemState state)
    {
        var em = state.EntityManager;
        var ball = em.CreateEntity();                        // an entity is only an id
        em.AddComponentData(ball, new Position { Value = new float2(150, 40) });
        em.AddComponentData(ball, new Velocity { Value = new float2(30, 0) });
        em.AddComponentData(ball, new Gravity  { Value = 300f });
        var tree = em.CreateEntity();                        // no Velocity: Gravity skips it
        em.AddComponentData(tree, new Position { Value = new float2(250, 150) });
        em.AddComponentData(tree, new Gravity  { Value = 300f });
    }
}

[UpdateBefore(typeof(MovementSystem))]
public partial struct GravitySystem : ISystem
{
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;
        foreach (var (vel, g) in SystemAPI.Query<RefRW<Velocity>, RefRO<Gravity>>())
            vel.ValueRW.Value.y += g.ValueRO.Value * dt;
    }
}

public partial struct MovementSystem : ISystem
{
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;
        foreach (var (pos, vel) in SystemAPI.Query<RefRW<Position>, RefRW<Velocity>>())
        {
            pos.ValueRW.Value += vel.ValueRO.Value * dt;
            if (pos.ValueRO.Value.y > 165f)
            {
                pos.ValueRW.Value.y = 165f;
                vel.ValueRW.Value.y = -math.abs(vel.ValueRO.Value.y);
            }
        }
    }
}

In all three, whether an entity falls depends only on its components. The Gravity system never names the ball or the tree.

Pitfalls

  • Adding or removing components while a system is looping. As in the freeing objects lesson, the set you are walking changes under you. Record the change and apply it after the loop; in Unity, that is what an EntityCommandBuffer is for.
  • A query that silently matches nothing. The tree has Gravity and does not fall, and nothing reports an error. When an entity does nothing, check its components first.
  • Systems in the wrong order. If Draw ran before Movement, everything would be drawn a frame late. Set the order on purpose, in one place.
  • Holding on to an entity id after it is destroyed. Many ECS libraries reuse ids, so an old id can quietly point at a new entity. Store a generation counter that changes on each reuse, or check the entity still exists.
  • Making everything an ECS. A menu or a single boss gains little from queries and loses the editor's usual tools. Many projects use ECS only for the crowded parts.

In real games

Unity's Entities package serves projects with very large numbers of objects. Bevy, an open source engine written in Rust, is built around an ECS. EnTT (C++) and Flecs (C and C++) are widely used standalone ECS libraries. Blizzard's Timothy Ford described Overwatch's ECS-based gameplay architecture in a GDC 2017 talk. Godot takes the other path: nodes for most code, servers where one object per thing costs too much.

Takeaways

  • An entity is an id, a component is plain data, and a system is a function that runs over every entity matching its query.
  • The world owns all the data. Behaviour changes by adding and removing components, not by editing classes.
  • The outer loop is over systems, so the frame order is one explicit list you can read.
  • Packed storage makes system loops fast; change components only between loops.
  • Unity offers ECS in its Entities package; Godot uses nodes, with servers for crowds.

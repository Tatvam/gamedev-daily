Hierarchical and pushdown state machines

How superstates share transitions between similar states, and how a stack of states lets pause menus and dialogue interrupt play and hand control back.

You are halfway through a conversation with a shopkeeper, you press Escape to check the time, then close the pause menu. The conversation is gone and your character is back on the street. The pause menu did what it was told: "on close, go to Play". Nobody told it where it came from.

Two limits of a flat machine

Yesterday's player controller was a flat finite state machine: one current state, explicit transitions. Two problems appear as it grows.

  • Duplicated transitions. Idle and Run both needed a "jump" arrow and a "down" arrow. Add Walk and Sprint and you write them four times, and one day you forget one.
  • No memory. A flat machine knows only where it is, never where it was. A pause menu that can open from anywhere cannot know where to return.

Hierarchical state machines: states inside states

In a hierarchical state machine, a state can contain other states. The outer one is a superstate and the inner ones are its substates. The current state is still one leaf, such as Run, but Run is also inside Grounded.

The rule: input and updates go to the innermost state first. If it does not handle them, they go up to its superstate, and so on. So "jump" and "down" are written once, on Grounded, and every grounded substate inherits them.

In code, each state gets an optional parent, and the machine walks up the chain until some state returns a transition:

-- Grounded holds the transitions that Idle and Run share.
local grounded = {}
function grounded.update(dt)
  if input.jump then return "jump" end
  if input.down then return "crouch" end
end

states.run = { parent = grounded }
function states.run.update(dt)
  player.x = player.x + input.move * SPEED * dt
  if input.move == 0 then return "idle" end
end

local function updateState(state, dt)
  while state do                        -- innermost first
    local nextState = state.update(dt)
    if nextState then return nextState end
    state = state.parent                -- not handled: ask the superstate
  end
end

Enter and exit follow the nesting. Going from Idle to Run stays inside Grounded, so Grounded neither exits nor enters. Going from Run to Jump exits Run, then Grounded (inside out), then enters Airborne, then Jump (outside in).

Pushdown automata: a stack of states

The memory problem needs a different tool. A stack is a list where you only add or remove at one end, the top. To push is to add a state on top; to pop is to remove the top one, which uncovers whatever was below. A state machine that keeps its states on a stack is called a pushdown automaton.

The pause menu no longer says "go to Play". It says "pop", and whatever was underneath comes back exactly as it was left.

What happens, in what order

With several states alive at once, decide who gets each of the game loop's three jobs. A common set of rules, used by the demo:

  • Input goes to the top state only. When the pause menu is open, Left moves the menu cursor, not the player.
  • Updates run from the top down until a state that pauses the states below it. Dialogue lets the world keep moving; Pause freezes everything under it.
  • Drawing runs from the bottom up, starting at the highest opaque state, one that covers the whole screen. Pause is see-through, so Play and Dialogue are drawn first and Pause darkens them. A full-screen Inventory is opaque, so nothing below it is drawn at all.

Who owns the data

The stack owns the order; only push and pop change it. Each state owns its data, such as Dialogue's current line. Covering a state does not exit it, so the data survives. enter runs on push, exit on pop, and a state that must refresh when uncovered gets a third hook, often called resume.

How the engines express it

Godot 4 gives you much of the stack through the scene tree. An overlay added as the last child is drawn after its siblings, so it appears on top. Input travels in reverse depth-first order, starting at the bottom of the tree, so the newest overlay hears input first and can stop it with get_viewport().set_input_as_handled(). For "pause below", set get_tree().paused = true and give the menu a process_mode of When Paused or Always. In animation, a state inside an AnimationNodeStateMachine can itself be a state machine: a hierarchy.

Unity keeps the three jobs separate. UI draw order comes from the Canvas sort order. Input routing comes from which Input System action maps are enabled, for example with PlayerInput.SwitchCurrentActionMap("UI"). Pausing usually means Time.timeScale = 0, which stops FixedUpdate and zeroes Time.deltaTime while Update keeps running. The Animator Controller has sub-state machines, a hierarchy, and layers, machines running side by side.

The trade-off

Godot ties draw order and input order to one tree, so a pushed overlay gets both right automatically, but moving a node changes both at once. Unity makes you wire draw order, input and pausing separately: more setup, and more freedom to make them disagree on purpose.

The code

A complete LÖVE program with the demo's four states, flags and numbers, in an 800 by 600 window.

-- Left/Right walk, Enter or Space confirms, Escape or Backspace goes back.
local LINES = { "Back again?", "The bridge is out past the mill.",
                "Bring rope and I will fix it." }
local ITEMS = { "rope", "lamp", "key", "bread" }
local ACTIONS = { left = "left", right = "right", ["return"] = "confirm",
                  space = "confirm", escape = "back", backspace = "back" }
local player = { x = 80 }
local playTime = 0
local stack = {}
local states = {}

states.play = { opaque = true }
function states.play:update(dt) playTime = playTime + dt end
function states.play:input(a)
  if a == "left" then player.x = player.x - 24 end
  if a == "right" then player.x = player.x + 24 end
  if a == "confirm" then return "push", "dialogue" end
  if a == "back" then return "push", "pause" end
end
function states.play:draw()
  love.graphics.rectangle("fill", player.x - 11, 466, 22, 34)
  love.graphics.print("play time " .. string.format("%.1f", playTime), 10, 10)
end

states.dialogue = { line = 1, chars = 0 }
function states.dialogue:enter() self.line, self.chars = 1, 0 end
function states.dialogue:update(dt) self.chars = self.chars + 30 * dt end
function states.dialogue:input(a)
  if a == "back" then return "push", "pause" end
  if a == "confirm" then
    self.line, self.chars = self.line + 1, 0
    if self.line > #LINES then return "pop" end
  end
end
function states.dialogue:draw()
  local text = LINES[self.line]:sub(1, math.floor(self.chars))
  love.graphics.rectangle("line", 20, 510, 760, 70)
  love.graphics.print("Shopkeeper: " .. text, 36, 530)
end

states.pause = { pausesBelow = true }
function states.pause:input(a)
  if a == "back" then return "pop" end
  if a == "confirm" then return "push", "inventory" end
end
function states.pause:draw()
  love.graphics.setColor(0, 0, 0, 0.6)
  love.graphics.rectangle("fill", 0, 0, 800, 600)
  love.graphics.setColor(1, 1, 1)
  love.graphics.print("PAUSED", 375, 290)
end

states.inventory = { opaque = true, pausesBelow = true, slot = 1 }
function states.inventory:input(a)
  if a == "back" then return "pop" end
  if a == "left" then self.slot = math.max(1, self.slot - 1) end
  if a == "right" then self.slot = math.min(#ITEMS, self.slot + 1) end
end
function states.inventory:draw()
  for i, item in ipairs(ITEMS) do
    local mode = (i == self.slot) and "fill" or "line"
    love.graphics.rectangle(mode, 100 + i * 120, 260, 100, 60)
    love.graphics.print(item, 120 + i * 120, 330)
  end
end

local function push(name)
  local s = states[name]
  stack[#stack + 1] = s
  if s.enter then s:enter() end
end

local function pop()
  local s = table.remove(stack)
  if s.exit then s:exit() end
end

function love.load() push("play") end

function love.keypressed(key)
  local a = ACTIONS[key]
  if not a then return end
  local verb, name = stack[#stack]:input(a)    -- only the top hears input
  if verb == "push" then push(name) elseif verb == "pop" then pop() end
end

function love.update(dt)
  for i = #stack, 1, -1 do                     -- top down
    if stack[i].update then stack[i]:update(dt) end
    if stack[i].pausesBelow then break end     -- states below freeze
  end
end

function love.draw()
  local first = #stack
  while first > 1 and not stack[first].opaque do first = first - 1 end
  for i = first, #stack do stack[i]:draw() end -- bottom up
end
# game_states.gd. Godot 4. Attach to a Node in a new scene and run.
# Enter or Space is ui_accept, Escape is ui_cancel. Watch the Output panel.
extends Node

const LINES := ["Back again?", "The bridge is out past the mill.", "Bring rope and I will fix it."]
const PAUSES_BELOW := ["pause", "inventory"]

var stack: Array[String] = []
var line := 0

func _ready() -> void:
    process_mode = Node.PROCESS_MODE_ALWAYS   # keep hearing input while the tree is paused
    push("play")

func push(state: String) -> void:
    stack.push_back(state)
    if state == "dialogue":
        line = 0                              # enter Dialogue
        print("Shopkeeper: ", LINES[line])
    _changed()

func pop() -> void:
    stack.pop_back()
    _changed()

func _changed() -> void:
    # Freeze every pausable node while a pausing state is anywhere on the stack.
    get_tree().paused = stack.any(func(s): return s in PAUSES_BELOW)
    print("stack: ", stack)

func _unhandled_input(event: InputEvent) -> void:
    var accept := event.is_action_pressed("ui_accept")
    var cancel := event.is_action_pressed("ui_cancel")
    if not accept and not cancel:
        return
    get_viewport().set_input_as_handled()
    match stack.back():                       # only the top state hears input
        "play":
            if accept:
                push("dialogue")
            else:
                push("pause")
        "dialogue":
            if cancel:
                push("pause")
            else:
                line += 1
                if line >= LINES.size():
                    pop()
                else:
                    print("Shopkeeper: ", LINES[line])
        "pause":
            if cancel:
                pop()
            else:
                push("inventory")
        "inventory":
            if cancel:
                pop()
// GameStates.cs. Unity 6 or 2022 LTS with the Input System package.
// Add to any GameObject and press Play. Enter confirms, Escape goes back. Watch the Console.
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.InputSystem;

public class GameStates : MonoBehaviour
{
    static readonly string[] Lines =
        { "Back again?", "The bridge is out past the mill.", "Bring rope and I will fix it." };

    readonly Stack<string> stack = new Stack<string>();
    int line;

    void Start() { Push("play"); }

    void Push(string state)
    {
        stack.Push(state);
        if (state == "dialogue") { line = 0; Debug.Log("Shopkeeper: " + Lines[line]); }
        Changed();
    }

    void Pop() { stack.Pop(); Changed(); }

    void Changed()
    {
        // Freeze scaled time while a pausing state is anywhere on the stack.
        Time.timeScale = (stack.Contains("pause") || stack.Contains("inventory")) ? 0f : 1f;
        Debug.Log("stack, top first: " + string.Join(", ", stack));
    }

    void Update()   // still called when timeScale is 0
    {
        var kb = Keyboard.current;
        if (kb == null) return;
        bool confirm = kb.enterKey.wasPressedThisFrame;
        bool back = kb.escapeKey.wasPressedThisFrame;
        if (!confirm && !back) return;

        switch (stack.Peek())   // only the top state hears input
        {
            case "play":
                if (confirm) Push("dialogue"); else Push("pause");
                break;
            case "dialogue":
                if (back) Push("pause");
                else if (++line >= Lines.Length) Pop();
                else Debug.Log("Shopkeeper: " + Lines[line]);
                break;
            case "pause":
                if (back) Pop(); else Push("inventory");
                break;
            case "inventory":
                if (back) Pop();
                break;
        }
    }
}

The GDScript and C# versions keep the stack and input routing, print instead of drawing, and use each engine's own pause switch for "pausesBelow".

Pitfalls

  • Moving a check into a parent changes its priority. Innermost first means Run's "stop" check now runs before Grounded's "jump"; yesterday Jump came first. A one-frame press can be lost on the frame the player stops. Decide the order on purpose.
  • Pushing when you meant to replace. Play to Game Over should not leave Play underneath. Add an operation that pops and pushes in one step, often called switch or replace.
  • A stack that only grows. If Pause pushes Options and Options pushes Pause, clicking back and forth builds a tall stack. Pop back instead of pushing the parent again.
  • Paused menus. In Godot, a menu left at the default process mode freezes with the game and never hears the key to close it. In Unity, menu code that animates with Time.deltaTime stops at a time scale of zero; use Time.unscaledDeltaTime, and WaitForSecondsRealtime instead of WaitForSeconds in coroutines.
  • Stale data on resume. A shop screen covered by the inventory may show old prices after a sale. A resume hook that refreshes it fixes this.

In real games

Menus that open over menus, a confirm box over options over the pause screen, are a stack whether or not the code calls it one. Both engines' animation tools nest state machines, as described above. Nested states themselves come from David Harel's statecharts, published in 1987 for describing complex reactive systems.

Takeaways

  • A hierarchical machine nests substates in superstates. Input goes innermost first, then up, so shared transitions are written once.
  • A pushdown automaton keeps states on a stack. Push to interrupt; pop to return to the uncovered state, data intact.
  • Decide each job separately: input to the top, updates down to the first state that pauses the rest, drawing up from the highest opaque state.
  • Godot ties draw and input order to the scene tree; Unity wires them separately.

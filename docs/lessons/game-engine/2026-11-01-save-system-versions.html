Building a save system: stable IDs and versioned saves

What a save file should hold, how stable IDs find the right object in a fresh level, and how version numbers and migrations keep old saves loading.

A player pushes a crate onto a switch and saves. You ship an update that adds a lamp to the start of the level, and the player loads their save. The crate is back where it started, the lamp has turned red and moved onto the switch, or the game refuses to load at all.

The serializer from the last lesson was fine. What was missing is a save system around it: what to store, how to find each object again, and a plan for format changes.

A save is a list of changes to a level

A save system is the code that decides what to write when the player saves, and how to rebuild their game from it later. Two kinds of data are involved:

  • Authored data is what the designer built: the level layout, the meshes, the default colour of every crate. It ships with the game and is loaded from the scene file every time.
  • Run-time state is what the player changed: where the crate is now, which doors are open, what is in the inventory, the play time.

A save holds only the run-time state. Loading a game is therefore two steps in a fixed order: first load the level as authored, exactly as a new game would, then lay the saved state over it. This keeps saves small and means that fixing a typo in the level reaches old saves too. Anything the game can rebuild, such as textures, physics shapes or a cached path, stays out. A reference to an asset is saved as its path or address, never as the asset.

Stable IDs: finding the crate again

When the save says "this crate is at 230, 90", the loader has to find that crate in a freshly loaded level. The IDs from the serialization lesson only lived for one file. Here the save and the level are two different files, often made by different builds of the game.

A stable ID is a name for an object that stays the same across runs and across updates, such as crate_a. It is assigned once, by the designer or by an editor tool when the object is placed, and it is stored in the level file. Some choices that look like IDs are not stable:

  • The position in the scene's list of objects. Insert one object at the top of the level and every saved row lands on the wrong object.
  • Run-time IDs such as Godot's get_instance_id() or Unity's GetInstanceID(). They change every run.
  • The node or GameObject name, unless your team treats renaming as a breaking change.

Objects created while playing, such as a dropped item, have no authored ID. Give each one an ID when it spawns and save its kind (which scene or prefab to create) next to its state. On load, any saved row whose ID is not in the level is spawned from that kind. Authored objects that the player destroyed need a row too, marked as removed, or they will be back after loading.

Version numbers and migrations

The format of the save will change: a field gets renamed, a number changes units, a list becomes a dictionary. Old saves will still exist on players' machines. So every save starts with a version number, the format it was written in, and the loader keeps a chain of migrations: small functions that each turn data of version n into data of version n + 1.

Order and ownership matter here. The migrations run on the plain data, after parsing and before any game object sees it. A version 1 save goes through 1 to 2, then 2 to 3, until it reaches the current version. Each saveable object owns one thing: turning its state into a row and reading the current kind of row back. It never needs to know that older formats existed. The save manager owns the file, the version number and the chain.

Rule of thumb

Write a version number into the very first save you ship. Never edit an old migration after release; add a new one.

Try it

You are running build v1. Drag crate_a somewhere new (or focus the canvas and use the arrow keys), press Recolour, then press Save. The save file appears in the text box. Now switch Build to v2, a newer release that adds lamp_a to the front of the level and stores positions as pos and colours as hex. The level starts fresh. Press Load and watch the five load steps under the scene.

Then repeat with Run migrations off, and again with Match objects by set to list position. Finally, save in v2, switch back to v1 and load. You can also edit the text box by hand before loading.

The code

The Lua version is build v2 of the demo: the same four objects, the same IDs, positions and colours, and the same v1 to v2 migration. It uses json.lua by rxi, a single file you put next to main.lua; key order in its output may differ from the demo. Press the right arrow and C to change crate_a, S to save, L to load, and O to write an old v1 save so you can watch the migration run.

-- main.lua, build v2. Needs json.lua (rxi) in the same folder.
local json = require("json")

local VERSION = 2
local HEX = { red = "#d04040", green = "#3a9a4a", blue = "#3a6fd0", gold = "#d0a020" }

-- The level as authored. Build v2 added lamp_a at the front.
local objects = {
  { id = "lamp_a",   x = 60,  y = 60,  color = HEX.gold },
  { id = "crate_a",  x = 160, y = 120, color = HEX.red },
  { id = "crate_b",  x = 260, y = 120, color = HEX.blue },
  { id = "barrel_a", x = 360, y = 120, color = HEX.green },
}
local byId = {}
for _, o in ipairs(objects) do byId[o.id] = o end

local migrations = {}
migrations[1] = function (data)   -- v1 to v2: x, y became pos; colour names became hex
  for _, row in ipairs(data.objects) do
    row.pos = { row.x, row.y }
    row.x, row.y = nil, nil
    row.color = HEX[row.color] or "#808080"
  end
  data.version = 2
end

local function saveGame()
  local rows = {}
  for i, o in ipairs(objects) do
    rows[i] = { id = o.id, pos = { o.x, o.y }, color = o.color }
  end
  love.filesystem.write("save.json", json.encode({ version = VERSION, objects = rows }))
  return "saved"
end

local function loadGame()
  local text = love.filesystem.read("save.json")
  if not text then return "no save yet" end
  local ok, data = pcall(json.decode, text)
  if not ok or type(data) ~= "table" or type(data.objects) ~= "table" then
    return "unreadable save, nothing changed"
  end
  local v = tonumber(data.version) or 1        -- no number: the oldest format
  if v > VERSION then return "save is from a newer build" end
  for from = v, VERSION - 1 do migrations[from](data) end
  for _, row in ipairs(data.objects) do
    local o = byId[row.id]                     -- match by stable ID
    if o and row.pos then o.x, o.y, o.color = row.pos[1], row.pos[2], row.color end
  end
  return "loaded version " .. v
end

local message = "S save, L load, O write an old v1 save"
function love.keypressed(key)
  if key == "right" then byId.crate_a.x = byId.crate_a.x + 10 end
  if key == "c" then byId.crate_a.color = HEX.gold end   -- the demo cycles colours
  if key == "s" then message = saveGame() end
  if key == "l" then message = loadGame() end
  if key == "o" then
    love.filesystem.write("save.json",
      '{"version":1,"objects":[{"id":"crate_a","x":230,"y":90,"color":"gold"}]}')
    message = "wrote a v1 save"
  end
end

local function rgb(hex)
  return tonumber(hex:sub(2, 3), 16) / 255, tonumber(hex:sub(4, 5), 16) / 255,
         tonumber(hex:sub(6, 7), 16) / 255
end

function love.draw()
  for _, o in ipairs(objects) do
    love.graphics.setColor(rgb(o.color))
    love.graphics.rectangle("fill", o.x - 18, o.y - 18, 36, 36)
    love.graphics.setColor(1, 1, 1)
    love.graphics.print(o.id, o.x - 18, o.y + 24)
  end
  love.graphics.print(message, 10, 10)
end
# saveable.gd. Godot 4. Attach to each Node2D you want saved and set save_id.
extends Node2D

@export var save_id: String = ""

func _ready() -> void:
    add_to_group("saveable")

func save_row() -> Dictionary:
    return {"id": save_id, "pos": [position.x, position.y],
            "color": "#" + modulate.to_html(false)}

func load_row(row: Dictionary) -> void:   # only ever sees the current format
    position = Vector2(row["pos"][0], row["pos"][1])
    modulate = Color.html(row["color"])


# save_manager.gd. Godot 4. Add as an autoload, or any node in the scene.
extends Node

const VERSION := 2
const PATH := "user://save.json"
const HEX := {"red": "#d04040", "green": "#3a9a4a", "blue": "#3a6fd0", "gold": "#d0a020"}

func migrate_1_to_2(data: Dictionary) -> void:
    for row in data["objects"]:
        row["pos"] = [row["x"], row["y"]]
        row.erase("x")
        row.erase("y")
        row["color"] = HEX.get(row["color"], "#808080")
    data["version"] = 2

func save_game() -> void:
    var rows := []
    for node in get_tree().get_nodes_in_group("saveable"):
        rows.append(node.save_row())
    var file := FileAccess.open(PATH, FileAccess.WRITE)
    file.store_string(JSON.stringify({"version": VERSION, "objects": rows}))
    file.close()

func load_game() -> String:   # call after the fresh level has run _ready
    if not FileAccess.file_exists(PATH):
        return "no save yet"
    var data = JSON.parse_string(FileAccess.get_file_as_string(PATH))
    if typeof(data) != TYPE_DICTIONARY or not data.has("objects"):
        return "unreadable save, nothing changed"
    var v := int(data.get("version", 1))   # JSON numbers arrive as floats
    if v > VERSION:
        return "save is from a newer build"
    if v < 2: migrate_1_to_2(data)
    var by_id := {}
    for node in get_tree().get_nodes_in_group("saveable"):
        by_id[node.save_id] = node
    for row in data["objects"]:
        if by_id.has(row["id"]): by_id[row["id"]].load_row(row)
    return "loaded version %d" % v
// SaveManager.cs. Unity 6 or 2022 LTS. Put SaveManager on one GameObject, Saveable on each saved one.
using System.Collections.Generic;
using System.IO;
using UnityEngine;

[System.Serializable] public class SaveRow { public string id; public float x, y; public Vector2 pos; public string color; }
[System.Serializable] public class SaveFile { public int version; public List<SaveRow> objects = new List<SaveRow>(); }

public class SaveManager : MonoBehaviour
{
    const int Version = 2;
    static readonly Dictionary<string, string> Hex = new Dictionary<string, string> {
        { "red", "#d04040" }, { "green", "#3a9a4a" }, { "blue", "#3a6fd0" }, { "gold", "#d0a020" } };
    string PathOnDisk => Path.Combine(Application.persistentDataPath, "save.json");

    static void Migrate1To2(SaveFile data)   // v1 rows have x and y; v2 rows have pos
    {
        foreach (var row in data.objects)
        {
            row.pos = new Vector2(row.x, row.y);
            row.color = Hex.TryGetValue(row.color ?? "", out var h) ? h : "#808080";
        }
        data.version = 2;
    }

    public void SaveGame()
    {
        var file = new SaveFile { version = Version };
        foreach (var s in FindObjectsByType<Saveable>(FindObjectsSortMode.None))
            file.objects.Add(s.ToRow());
        File.WriteAllText(PathOnDisk, JsonUtility.ToJson(file, true));
    }

    public string LoadGame()   // call after the fresh scene has loaded
    {
        if (!File.Exists(PathOnDisk)) return "no save yet";
        SaveFile data;
        try { data = JsonUtility.FromJson<SaveFile>(File.ReadAllText(PathOnDisk)); }
        catch (System.Exception) { return "unreadable save, nothing changed"; }
        if (data == null || data.objects == null) return "unreadable save, nothing changed";
        int v = data.version == 0 ? 1 : data.version;   // a missing int reads as 0
        if (v > Version) return "save is from a newer build";
        if (v < 2) Migrate1To2(data);
        var byId = new Dictionary<string, Saveable>();
        foreach (var s in FindObjectsByType<Saveable>(FindObjectsSortMode.None)) byId[s.saveId] = s;
        foreach (var row in data.objects)
            if (row.id != null && byId.TryGetValue(row.id, out var target)) target.FromRow(row);
        return "loaded version " + v;
    }
}

// Saveable.cs, its own file. Needs a SpriteRenderer on the same GameObject.
using UnityEngine;

public class Saveable : MonoBehaviour
{
    public string saveId;   // set once in the Inspector, never changed

    public SaveRow ToRow() => new SaveRow {
        id = saveId, pos = transform.position,
        color = "#" + ColorUtility.ToHtmlStringRGB(GetComponent<SpriteRenderer>().color) };

    public void FromRow(SaveRow row)
    {
        transform.position = row.pos;
        if (ColorUtility.TryParseHtmlString(row.color, out var c)) GetComponent<SpriteRenderer>().color = c;
    }
}

JsonUtility needs one class holding every field any version used, so the v1 fields x and y stay in SaveRow and are written as zeros in new saves. Fields missing from the text keep their defaults, which is what lets it read a version 1 file at all. Godot gives you plain dictionaries, so its migration can rename keys freely.

Pitfalls

  • Shipping without a version number. The first format change then has to guess which format a file is in. If you forgot, treat "no version" as version 1, as all three tabs do, and start writing a number now.
  • Applying before the level is ready. Load the fresh level, wait until its objects have run their setup code, then apply the save. Otherwise _ready or Start runs after loading and resets the values you just restored. In Godot a parent's _ready runs after its children's, so the scene root's _ready is one safe place.
  • Half-applied loads. Parse, check and migrate the whole file before touching a single object. A loader that fails on row three has already moved rows one and two.
  • Losing the save when the game crashes mid-write. If the power fails while the file is being written, the player is left with half a file. Write the new save to a temporary file first, then replace the old one, and keep the previous save as a backup.
  • Trusting the file. Players edit saves. Clamp values on load and do not use a format that can create arbitrary objects, for the reasons given in the serialization lesson.

In real games

Neither engine ships a complete save system; both leave the format to you. Godot gives you the user:// folder, FileAccess and JSON, and its documentation has a Saving games tutorial in which every saveable node is put in a group and returns a dictionary of its state. Unity gives you Application.persistentDataPath, JsonUtility and PlayerPrefs, which is meant for small settings rather than game progress.

Minecraft: Java Edition writes a data version number into its world data and upgrades old worlds step by step when it loads them. Mojang published the library it uses for this as DataFixerUpper. Factorio lets mods ship migration files that run when a save made with an older version of the mod is loaded.

Your turn (15 minutes)

Pick two objects in your project that the player can change, such as a door that opens and a crate that moves. Give each a stable ID field and set it by hand. Write a save that holds a version number and one row per object, and a load that applies rows by ID after the level has loaded.

Then change the format: rename one field and bump the version to 2. Write the migration from 1 to 2. You are done when a save written before the change loads correctly after it, and a save with version 99 is refused with a message instead of a crash.

Takeaways

  • Save run-time state only. Load the authored level first, then lay the save over it.
  • Match saved rows to objects with stable IDs assigned once, never with list positions or run-time IDs.
  • Put a version number in every save and keep a chain of migrations, each turning one version into the next.
  • Migrate the plain data before any object reads it, so objects only know the current format.
  • Refuse saves from a newer build, and never change anything until the whole file has been read and checked.

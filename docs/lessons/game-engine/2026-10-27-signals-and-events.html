Signals in Godot, events in Unity: connecting and disconnecting safely

How Godot signals, C# events and UnityEvents store connections, what each does when a listener is freed, and where to connect and disconnect.

You go back to the main menu and load the level again. The first hit on the player fills the Unity console with MissingReferenceException, and the hurt sound stops playing. Or, in Godot, the console prints "already connected" every time a menu opens. Both engines are telling you the same thing: a connection outlived its listener.

A connection is a record the subject keeps

In the observer pattern a subject keeps a list of functions and calls them all when something happens. Engines give you that list ready-made. Each entry in it is a connection: a record saying "when this happens, call this method on this object". The record lives in the subject, the object that announces. The listener is only pointed at.

So the question for every engine is the same: when the listener goes away, who removes the record? Godot and Unity answer differently, and Unity has two tools that answer differently from each other.

Godot 4: signals

A signal is declared in a script with signal health_changed(new_health: int) and fired with health_changed.emit(health). You connect a listener in one of two places:

  • In the editor, from the Node dock's Signals tab. The connection is saved in the scene file, and the engine makes it again every time the scene is loaded.
  • In code, usually in the listener's _ready: player.health_changed.connect(_on_health_changed).

The thing you connect is a Callable: a method together with the object it belongs to. Because the record knows that object, Godot can clean up. When an object is freed, the engine walks every connection that points at it and removes it from its subject. Godot also refuses to connect the same Callable to the same signal twice: connect prints an error and returns ERR_INVALID_PARAMETER.

Unity: C# events

A C# event, such as public event Action<int> HealthChanged;, is a language feature, not a Unity one. It holds a delegate: a list of methods, each paired with the object to call it on. += adds an entry and -= removes the last matching one. Adding the same method twice puts it in the list twice, and it is called twice.

C# knows nothing about Destroy. A destroyed component is still an ordinary C# object as far as the delegate is concerned, so it keeps being called. The moment its handler touches anything Unity owns, such as its transform, Unity throws MissingReferenceException. An exception inside a delegate call also stops the rest of the list from running, so every listener after the dead one misses the event too.

Unity: UnityEvent

A UnityEvent<int> is a serialised field, so it appears in the Inspector as a list you can fill by dragging objects in and picking a method. Those persistent listeners are saved with the scene or prefab. Code can add more with AddListener and take them off with RemoveListener, which removes every matching entry added from code. RemoveAllListeners clears only the entries added from code, never the ones from the Inspector.

Before each call, a UnityEvent checks whether the target is a destroyed Unity object and skips it if so. You get no exception, but the entry and its reference stay in the list until you remove them.

What happens, in what order

Neither engine deletes an object the instant you ask. queue_free and Destroy both wait until the end of the current frame. The listener's clean-up runs at that point, so this is where the connection should end.

Rule of thumb

The listener connects itself and disconnects itself, at matching points of its own life. Let the subject stay ignorant of who is listening.

Try it

The code

LÖVE has no signals, so the Lua version builds one that behaves like Godot's: it refuses duplicates, and freeing an object removes every connection that points at it. Space hits, F frees the health bar.

-- A signal is a list of connections: which object, which method.
local function newSignal() return { connections = {} } end

local function find(sig, target, method)
  for i, c in ipairs(sig.connections) do
    if c.target == target and c.method == method then return i end
  end
  return nil
end

local function connect(sig, target, method)
  if find(sig, target, method) then
    print("error: already connected")              -- refuse a duplicate
    return false
  end
  table.insert(sig.connections, { target = target, method = method })
  table.insert(target.incoming, sig)               -- the target remembers who calls it
  return true
end

local function disconnect(sig, target, method)
  local i = find(sig, target, method)
  if i then table.remove(sig.connections, i) else print("error: not connected") end
end

local function emit(sig, ...)
  local copy = {}
  for i, c in ipairs(sig.connections) do copy[i] = c end
  for _, c in ipairs(copy) do c.target[c.method](c.target, ...) end
end

-- Freeing an object removes every connection that points at it.
local function freeObject(obj)
  for _, sig in ipairs(obj.incoming) do
    for i = #sig.connections, 1, -1 do
      if sig.connections[i].target == obj then table.remove(sig.connections, i) end
    end
  end
  obj.incoming = {}
  obj.freed = true
end

local player = { health = 100, health_changed = newSignal() }
local healthBar = { incoming = {}, shown = 100 }
function healthBar:on_health_changed(h) self.shown = h end
local sound = { incoming = {}, plays = 0 }
function sound:on_health_changed(h) self.plays = self.plays + 1 end
local flash = { incoming = {}, time = 0 }
function flash:on_health_changed(h) self.time = 0.5 end

connect(player.health_changed, healthBar, "on_health_changed")
connect(player.health_changed, sound, "on_health_changed")
connect(player.health_changed, sound, "on_health_changed")   -- prints the error
connect(player.health_changed, flash, "on_health_changed")

function love.keypressed(key)
  if key == "space" then
    player.health = math.max(0, player.health - 10)   -- state first
    emit(player.health_changed, player.health)        -- then announce
  elseif key == "f" and not healthBar.freed then
    freeObject(healthBar)
  end
end

function love.update(dt) flash.time = math.max(0, flash.time - dt) end

function love.draw()
  if not healthBar.freed then love.graphics.rectangle("fill", 20, 20, healthBar.shown * 2, 16) end
  love.graphics.print("sounds: " .. sound.plays .. "  listeners: " .. #player.health_changed.connections, 20, 50)
  if flash.time > 0 then love.graphics.print("FLASH", 20, 80) end
end
# main.gd on a Node in a new scene. Godot 4.
# Space or Enter (ui_accept) hits the player. F frees the health bar.
extends Node

signal health_changed(new_health: int)

class HealthBar extends Label:
    func on_health_changed(new_health: int) -> void:
        text = "Health %d" % new_health

var health := 100
var bar: HealthBar

func _ready() -> void:
    bar = HealthBar.new()
    bar.text = "Health 100"
    add_child(bar)
    health_changed.connect(bar.on_health_changed)   # the Callable knows its object: bar
    # Connecting again would print an error, so check first.
    if not health_changed.is_connected(bar.on_health_changed):
        health_changed.connect(bar.on_health_changed)
    health_changed.connect(_on_sound)

func _process(_delta: float) -> void:
    if Input.is_action_just_pressed("ui_accept"):
        health = maxi(0, health - 10)
        health_changed.emit(health)
        print("listeners: ", health_changed.get_connections().size())

func _unhandled_input(event: InputEvent) -> void:
    if event is InputEventKey and event.pressed and event.keycode == KEY_F:
        if is_instance_valid(bar):
            bar.queue_free()   # at the end of the frame Godot drops its connection

func _on_sound(_new_health: int) -> void:
    print("Hurt sound")
// Unity 6 or 2022 LTS with the Input System package. Two files.

// Player.cs: put on any GameObject. Space hits the player.
using System;
using UnityEngine;
using UnityEngine.Events;
using UnityEngine.InputSystem;

public class Player : MonoBehaviour
{
    public event Action<int> HealthChanged;   // code-only listeners
    public UnityEvent<int> onHealthChanged;   // can also be wired in the Inspector
    int health = 100;

    void Update()
    {
        if (Keyboard.current != null && Keyboard.current.spaceKey.wasPressedThisFrame)
        {
            health = Mathf.Max(0, health - 10);
            HealthChanged?.Invoke(health);
            onHealthChanged?.Invoke(health);
        }
    }
}

// HealthBar.cs: put on a Cube or Sprite and drag the Player into its field. F destroys it.
using UnityEngine;
using UnityEngine.InputSystem;

public class HealthBar : MonoBehaviour
{
    public Player player;

    void OnEnable()  { player.HealthChanged += OnHealthChanged; }
    void OnDisable() { if (player != null) player.HealthChanged -= OnHealthChanged; }
    // OnDisable also runs on Destroy. Delete it to see MissingReferenceException.

    void OnHealthChanged(int health)
    {
        transform.localScale = new Vector3(health / 100f, 1f, 1f);   // throws if destroyed
    }

    void Update()
    {
        if (Keyboard.current != null && Keyboard.current.fKey.wasPressedThisFrame)
            Destroy(gameObject);
    }
}

Pitfalls

  • Subscribing in Start, unsubscribing in OnDisable. In Unity, Start runs once but OnDisable runs every time the object is switched off. After one off and on cycle the listener is no longer subscribed. Pair OnEnable with OnDisable, or Awake with OnDestroy.
  • Subscribing twice. A C# event or UnityEvent calls a duplicate twice, and one -= removes only one copy. If a sound plays twice per hit, look for a second +=. In Godot, guard repeated code connections with is_connected.
  • Lambdas you cannot remove. In both engines, removing a handler needs the same function value you added. A lambda written inline creates a new one each time, so -= or disconnect with a fresh lambda removes nothing. Keep it in a variable if you will need to remove it.
  • Removed but not freed. Godot's clean-up only happens when an object is freed. A node taken out of the tree with remove_child, or parked in a pool, still exists and is still called. Disconnect it yourself, or check in the handler.
  • Expecting RemoveAllListeners to clear the Inspector. It removes only listeners added from code. Inspector entries stay.

In real games

Both engines use these tools for their own built-in parts. Godot's Button has a pressed signal and its Timer has timeout, and most projects connect them in the editor. Unity's UI Button exposes onClick, a UnityEvent, which is why button actions can be picked in the Inspector. A common split in Unity projects is C# events between scripts and UnityEvents where designers wire things up without code.

Your turn (15 minutes)

Pick one listener in your project that connects to a signal or event in code. Write down where it connects and where it disconnects. If there is no disconnect, or the two are not a matching pair (OnEnable and OnDisable, or connect in _ready and freed with the node), fix it. You are done when you can free or destroy the listener while the game runs, fire the event, and see no errors and no duplicate calls.

Takeaways

  • A connection is a record kept by the subject. The listener is only pointed at, so ending the connection is someone's job.
  • Godot removes connections to an object when that object is freed, and refuses duplicates.
  • A C# event keeps calling a destroyed component until you remove it with -=; an exception there stops later listeners too.
  • A UnityEvent skips destroyed targets, but keeps their entries; RemoveAllListeners leaves Inspector entries alone.
  • Connect and disconnect from the listener, at matching points of its life.

The observer pattern: announcing without knowing who listens

How a subject announces events through a list of subscribed callbacks, in what order they run, who owns the list, and how Godot and Unity provide it.

The player takes a hit. The health bar must shrink, a sound must play, the screen must flash, and an achievement may unlock. The first version of take_damage calls all four directly. Then you open a test scene without the HUD and the player crashes, because it was holding a reference to a health bar that is not there.

Turn the calls around

In the direct version the player knows every system that cares about damage, so each new reaction means editing the player. The observer pattern reverses who knows whom.

  • The subject is the object something happens to, here the player. It keeps a list of functions to call when the event happens, and nothing else about them.
  • An observer is anything that wants to react. It subscribes by adding one of its functions to the subject's list, and unsubscribes by removing it.
  • To notify is to walk the list and call each function, passing along the facts of the event, such as the new health.

What happens, in what order

Notifying is an ordinary function call that loops. When the player runs notify, each observer's function runs to completion before the next one starts, and all of them finish before notify returns. Nothing is queued for later and no frame passes in between. An event like this is synchronous.

Two rules follow. Change your state, then notify, or the health bar shows the old value. And do not depend on the order: it is just the order in which observers happened to subscribe, which changes when objects load in a different sequence.

Who owns what

The subject owns the list. The list holds references to the observers' functions, and through them to the observers. An observer removed from the game that never unsubscribed still gets called, and in a garbage-collected language it is never freed. This is often called the lapsed listener problem. The rule: whoever subscribes is responsible for unsubscribing.

The list can also change during a notify. An achievement that should fire once unsubscribes itself from inside its own call. If the loop walks the live list by index, removing the current entry slides the next one into its slot, and the loop steps over it. That observer silently misses the event. The fix is the one from deferred deletion: loop over a copy of the list, so changes take effect from the next notify.

How the engines provide it

You rarely write the list yourself in an engine. In Godot 4, a signal declared in a script is a subject: connect subscribes a function, disconnect unsubscribes it, and emit notifies. The CONNECT_ONE_SHOT flag makes a connection remove itself after one emission. In Unity, the usual tool is a plain C# event holding a delegate: += subscribes, -= unsubscribes and invoking it notifies.

Both already loop over a copy. In Godot 4 the engine source copies the connection list before calling anyone, and removes one-shot connections first. C# delegates cannot be changed in place, so -= builds a new delegate while the call in progress keeps the old one. They differ on ownership: Godot drops a connection on its own when the object that owns the target function is freed, while a C# event keeps its reference until you remove it.

The trade-off

Observers make the subject ignorant of its audience, which is the point. The cost is that reading take_damage no longer tells you what happens on a hit. You have to find every place that subscribes.

The code

LÖVE has no built-in events for your own objects, so the subject is a table holding a list of functions. Names and numbers match the demo. Swap the copy loop in notify for a loop over subject.observers to see Screen flash go missing on the first hit.

-- A subject is a list of functions to call.
local function newSubject() return { observers = {} } end

local function subscribe(subject, fn)
  table.insert(subject.observers, fn)
end

local function unsubscribe(subject, fn)
  for i = #subject.observers, 1, -1 do
    if subject.observers[i] == fn then table.remove(subject.observers, i) end
  end
end

local function notify(subject, ...)
  local copy = {}                           -- loop over a copy, so an observer
  for i, fn in ipairs(subject.observers) do  -- can unsubscribe safely
    copy[i] = fn
  end
  for _, fn in ipairs(copy) do fn(...) end
end

local player = { health = 100, damaged = newSubject() }
local shownHealth, flash, message, plays = 100, 0, "", 0

local function healthBar(health) shownHealth = health end
local function achievement(health)
  message = "Unlocked: First hit"
  unsubscribe(player.damaged, achievement)   -- one-shot
end
local function screenFlash(health) flash = 0.5 end
local function hurtSound(health) plays = plays + 1 end

subscribe(player.damaged, healthBar)
subscribe(player.damaged, achievement)
subscribe(player.damaged, screenFlash)
subscribe(player.damaged, hurtSound)

local function takeDamage(amount)
  player.health = math.max(0, player.health - amount)   -- state first
  notify(player.damaged, player.health)                  -- then announce
end

function love.keypressed(key)
  if key == "space" then takeDamage(10) end
end

function love.update(dt)
  flash = math.max(0, flash - dt)
end

function love.draw()
  if flash > 0 then love.graphics.setColor(1, 0.3, 0.3) else love.graphics.setColor(1, 1, 1) end
  love.graphics.rectangle("fill", 20, 20, shownHealth * 2, 16)
  love.graphics.setColor(1, 1, 1)
  love.graphics.print(message .. "  sounds: " .. plays, 20, 50)
end
# player.gd on a Node. Godot 4. Press Space or Enter (ui_accept) to take a hit.
# The handlers live here so the script runs alone; normally a HUD node would call
# player.damaged.connect(_on_player_damaged) from its own _ready.
extends Node

signal damaged(health: int)

var health := 100

func _ready() -> void:
    damaged.connect(_on_health_bar)
    damaged.connect(_on_achievement, CONNECT_ONE_SHOT)   # removed after one emit
    damaged.connect(_on_screen_flash)
    damaged.connect(_on_hurt_sound)

func _process(_delta: float) -> void:
    if Input.is_action_just_pressed("ui_accept"):
        take_damage(10)

func take_damage(amount: int) -> void:
    health = maxi(0, health - amount)   # state first
    damaged.emit(health)                # then announce

func _on_health_bar(new_health: int) -> void:
    print("Health bar shows ", new_health)

func _on_achievement(_new_health: int) -> void:
    print("Unlocked: First hit")

func _on_screen_flash(_new_health: int) -> void:
    print("Screen flash")

func _on_hurt_sound(_new_health: int) -> void:
    print("Hurt sound")
// Player.cs. Unity 6 or 2022 LTS with the Input System package.
// Put it on any GameObject and press Space. Normally each handler would live on
// its own component, subscribing in OnEnable and unsubscribing in OnDisable.
using System;
using UnityEngine;
using UnityEngine.InputSystem;

public class Player : MonoBehaviour
{
    public event Action<int> Damaged;   // the subject's list
    int health = 100;

    void Start()
    {
        Damaged += OnHealthBar;
        Damaged += OnAchievement;
        Damaged += OnScreenFlash;
        Damaged += OnHurtSound;
    }

    void Update()
    {
        if (Keyboard.current != null && Keyboard.current.spaceKey.wasPressedThisFrame)
            TakeDamage(10);
    }

    public void TakeDamage(int amount)
    {
        health = Mathf.Max(0, health - amount);   // state first
        Damaged?.Invoke(health);                  // then announce, in order
    }

    void OnHealthBar(int h) { Debug.Log("Health bar shows " + h); }

    void OnAchievement(int h)
    {
        Debug.Log("Unlocked: First hit");
        Damaged -= OnAchievement;   // safe: this Invoke keeps the old list
    }

    void OnScreenFlash(int h) { Debug.Log("Screen flash"); }
    void OnHurtSound(int h) { Debug.Log("Hurt sound"); }
}

In all three, the player never names a health bar or a sound. Unity also has UnityEvent, which can be wired up in the Inspector; it and Godot's editor connections are the subject of the next lesson.

Pitfalls

  • Forgetting to unsubscribe. In Unity, a destroyed component still in a C# event's list gets called; touching its transform then throws, and the list keeps the object from being collected. Pair every += in OnEnable with a -= in OnDisable. Godot drops connections to freed objects by itself; plain Lua functions have no owner to check, so remove them yourself.
  • Changing the list while walking it. In your own code, loop over a copy, or collect removals and apply them after the loop.
  • Announcing before changing state. Observers that read the subject during the call see stale values.
  • Depending on order. Godot 4 currently calls connections in the order they were made, but its documentation does not promise it. C# delegates do promise it. If one observer must run after another, have the first raise its own event.
  • Feedback loops. An observer that changes the subject in a way that fires the same event again recurses until the stack overflows. Guard it, or let it change something else.
  • One failing observer. In C#, an exception thrown by one handler stops the rest of the list from being called. Keep handlers small and do not let them throw.

In real games

Both engines are built on this idea. Godot's own nodes announce through signals: a Button emits pressed, a Timer emits timeout, an Area2D emits body_entered. In Unity, a UI Button exposes onClick, a UnityEvent you can subscribe to from code or the Inspector. Achievements, tutorials and analytics are classic observers: the gameplay code they watch should not know they exist.

Your turn (15 minutes)

Find one place in your project where gameplay code calls UI or audio directly, such as a player script that updates a health label. Give the player a damaged signal or event that carries the new health, make the label subscribe to it, and remove the direct call. Make sure the label unsubscribes when it goes away. You are done when you can delete the label from the scene, play, take a hit, and get no error.

Takeaways

  • A subject keeps a list of functions and calls them when something happens. It does not know or care what they do.
  • Notifying is synchronous: every observer runs, in list order, before the notify call returns. Change state first, then notify.
  • The subject's list holds the observers, so whoever subscribes must unsubscribe, or the subject keeps calling and holding dead objects.
  • Loop over a copy of the list so observers can unsubscribe during a notify. Godot signals and C# events already do this.

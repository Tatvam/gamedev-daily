The component pattern: composition over inheritance

Why building game objects from small reusable components scales better than deep class trees, and how Godot and Unity let parts find each other.

Your game has a WalkingShooter class and a Flyer class, both children of Enemy. The designer asks for a flying enemy that shoots. The shooting code lives in one branch of the tree and the flying code in the other, and there is no clean place to put the new enemy.

Where inheritance runs out

Inheritance means a class takes all the code of its parent class and adds to it. It answers one question well: what is this thing? A Flyer is an Enemy.

Games do not grow that way. Abilities get mixed, and a class in GDScript or C# has only one parent, so each new mix leaves three bad choices:

  • Copy the shooting code into the flying branch, and fix every bug twice from now on.
  • Move it up into Enemy, so every enemy carries shooting code with a flag to turn it off. Soon the base class is a pile of switches.
  • Add a class per mix. Four independent abilities give 2 × 2 × 2 × 2 = 16 combinations.

Composition: an object made of parts

The component pattern turns this around. An entity is a nearly empty container: a name and a position. A component is a small object that owns one ability, its data and its code: Gravity owns a vertical speed, Health owns hit points. What the entity can do is decided by which components it holds. This is called composition: building an object out of other objects instead of out of parent classes.

The lesson on nodes and components showed the shape of each engine. Today is about why the shape works and the three rules that keep it working: order, ownership and how parts talk.

What happens, in what order

Each frame the entity asks every component it holds to update, then to draw. Order matters when one part writes what another reads. A part that reads the position before the parts that move it sees last frame's value, one frame late. So the parts that move the entity, Gravity and Movement, run first, and Glow, which only reads, runs last. Pick the order on purpose and keep it fixed. The demo and the code use one list:

Who owns the data

The entity owns its components and the shared data, here the position. Each component owns its own data. Remove Health and its hit points go with it; add it back and you get a fresh 3. No other part has to know Health exists.

How parts talk

Sometimes one part needs another. Glow pulses faster when hit points are low, so it asks the entity "do you have a Health?" and uses it only if the answer is yes. An optional dependency like this keeps Glow working on a lamp that has no health at all. The other direction is an announcement: Health says "I died" and whoever cares listens, as in the signals lesson.

-- Glow asks the entity, and copes when the answer is nil.
local h = e.parts.health
local rate = 1
if h then rate = 1 + (h.max - h.hp) end

How the engines express it

Unity is built on this pattern. Every script is a component, a class derived from MonoBehaviour. You add one with AddComponent<T>(), find a neighbour with GetComponent<T>() or TryGetComponent(out T c), and remove one with Destroy(component), which takes effect after the current frame's updates. [RequireComponent(typeof(T))] turns a needed neighbour into a rule the editor enforces. The order of Update across different scripts is not guaranteed unless you set it in the Script Execution Order settings.

Godot 4 has no separate component type. The usual way is a child node with its own script, such as a Health node under the enemy, found with get_node_or_null("Health"). A part that needs a position extends Node2D and follows its parent through the transform hierarchy. Order comes from the tree: a parent is processed before its children, children top to bottom, and a newly added child goes last. Godot's scene organisation guide notes that, strictly, a node tree is aggregation rather than composition, since children can move to another parent; here the effect is the same.

Rule of thumb

Inherit to say what a thing is, one level deep: your script extends CharacterBody2D or MonoBehaviour. Compose to say what it can do. Both engines use inheritance for their built-in types and composition for everything you attach.

The trade-off: Godot's child nodes show every part in the tree with a predictable order, at the cost of a node per part and lookups by path. Unity's components are lighter to add and found by type, but you must set their order when it matters.

Try it

The entity starts with only Movement, floating. Tick Gravity and it drops. Tick Health, then press Hit a few times, then tick Glow and hit again: the pulse speeds up because Glow found Health. Untick Health and the glow slows down, because nothing reports damage any more. Watch the readout name the single class inheritance would need for each mix.

The code

A complete LÖVE program with the demo's four components and numbers: gravity 600 px/s², a patrol of 60 px/s up to 80 px each side of home, 3 hit points, a 1 second respawn and a lift of 120 px above the ground.

-- Keys 1-4 toggle Gravity, Movement, Health, Glow. H hits, L lifts.
local GROUND, GRAVITY = 300, 600
local ORDER = { "gravity", "movement", "health", "glow" }  -- update order
local entity = { x = 200, y = GROUND - 120, homeX = 200, parts = {} }
local make = {}

function make.gravity()
  return { vy = 0, update = function(self, e, dt)
    self.vy = self.vy + GRAVITY * dt
    e.y = e.y + self.vy * dt
    if e.y >= GROUND then e.y, self.vy = GROUND, 0 end
  end }
end

function make.movement()
  return { speed = 60, range = 80, dir = 1, update = function(self, e, dt)
    e.x = e.x + self.speed * self.dir * dt
    if e.x > e.homeX + self.range then e.x, self.dir = e.homeX + self.range, -1 end
    if e.x < e.homeX - self.range then e.x, self.dir = e.homeX - self.range, 1 end
  end }
end

function make.health()
  return { hp = 3, max = 3, respawn = 0,
    update = function(self, e, dt) self.respawn = math.max(0, self.respawn - dt) end,
    hit = function(self)
      if self.respawn > 0 then return end
      self.hp = self.hp - 1
      if self.hp <= 0 then self.hp, self.respawn = self.max, 1 end
    end,
    draw = function(self, e) love.graphics.print("hp " .. self.hp, e.x - 14, e.y - 70) end }
end

function make.glow()
  return { t = 0, update = function(self, e, dt)
    local h = e.parts.health               -- optional neighbour
    local rate = 1
    if h then rate = 1 + (h.max - h.hp) end
    self.t = self.t + rate * dt
  end, draw = function(self, e)
    local a = 0.25 + 0.2 * math.sin(self.t * 2 * math.pi)
    love.graphics.setColor(1, 0.85, 0.3, a)
    love.graphics.circle("fill", e.x, e.y - 18, 34)
    love.graphics.setColor(1, 1, 1)
  end }
end

function love.load() entity.parts.movement = make.movement() end

function love.keypressed(key)
  local name = ORDER[tonumber(key)]
  if name then
    if entity.parts[name] then entity.parts[name] = nil   -- its data goes too
    else entity.parts[name] = make[name]() end
  end
  local h = entity.parts.health
  if key == "h" and h then h:hit() end
  if key == "l" then
    entity.y = GROUND - 120
    if entity.parts.gravity then entity.parts.gravity.vy = 0 end
  end
end

function love.update(dt)
  for _, name in ipairs(ORDER) do
    local c = entity.parts[name]
    if c and c.update then c:update(entity, dt) end
  end
end

function love.draw()
  love.graphics.line(0, GROUND, 800, GROUND)
  local h = entity.parts.health
  if h and h.respawn > 0 then return end   -- dead: draw nothing
  for _, name in ipairs(ORDER) do
    local c = entity.parts[name]
    if c and c.draw then c:draw(entity) end
  end
  love.graphics.setColor(0.3, 0.5, 0.9)
  love.graphics.rectangle("fill", entity.x - 14, entity.y - 36, 28, 36)
  love.graphics.setColor(1, 1, 1)
end
# entity.gd. Godot 4. Attach to a Node2D in a new 2D scene and run.
# Keys 1-4 toggle Gravity, Movement, Health, Glow. H hits, L lifts. Watch Output.
extends Node2D

var home_x := 200.0

class Gravity extends Node:
    var vy := 0.0
    func _process(delta: float) -> void:
        var e := get_parent() as Node2D
        vy += 600.0 * delta
        e.position.y += vy * delta
        if e.position.y >= 300.0:
            e.position.y = 300.0
            vy = 0.0

class Movement extends Node:
    var speed := 60.0
    var range_px := 80.0
    var dir := 1.0
    func _process(delta: float) -> void:
        var e = get_parent()
        e.position.x += speed * dir * delta
        if e.position.x > e.home_x + range_px:
            e.position.x = e.home_x + range_px
            dir = -1.0
        elif e.position.x < e.home_x - range_px:
            e.position.x = e.home_x - range_px
            dir = 1.0

class Health extends Node:
    signal died
    var max_hp := 3
    var hp := 3
    func hit() -> void:
        hp -= 1
        print("Health: hp ", hp)
        if hp <= 0:
            hp = max_hp
            died.emit()

class Glow extends Node2D:   # a Node2D child follows the parent's position
    var t := 0.0
    func _ready() -> void:
        show_behind_parent = true
    func _process(delta: float) -> void:
        var rate := 1.0
        var h = get_parent().get_node_or_null("Health")   # optional neighbour
        if h:
            rate = 1.0 + (h.max_hp - h.hp)
        t += rate * delta
        queue_redraw()
    func _draw() -> void:
        var a := 0.25 + 0.2 * sin(t * TAU)
        draw_circle(Vector2(0, -18), 34.0, Color(1, 0.85, 0.3, a))

func _ready() -> void:
    position = Vector2(home_x, 180.0)
    toggle("Movement", Movement)

func _draw() -> void:
    draw_rect(Rect2(-14, -36, 28, 36), Color(0.3, 0.5, 0.9))

func toggle(part_name: String, part_class) -> void:
    var part = get_node_or_null(part_name)
    if part:
        remove_child(part)          # out of the tree now, freed at the end of the frame
        part.queue_free()
        print(part_name, " removed")
    else:
        part = part_class.new()
        part.name = part_name
        add_child(part)             # goes last, so it is processed last
        if part is Health:
            part.died.connect(func(): print("Health: died and respawned"))
        print(part_name, " added")

func _unhandled_input(event: InputEvent) -> void:
    var key := event as InputEventKey
    if key == null or not key.pressed or key.echo:
        return
    match key.keycode:
        KEY_1: toggle("Gravity", Gravity)
        KEY_2: toggle("Movement", Movement)
        KEY_3: toggle("Health", Health)
        KEY_4: toggle("Glow", Glow)
        KEY_L: position.y = 180.0
        KEY_H:
            var h = get_node_or_null("Health")
            if h:
                h.hit()
            else:
                print("Hit ignored: no Health component")
// Unity 6 or 2022 LTS with the Input System package. One class per file.
// Add a Square sprite from the 2D Object menu, then add Entity to it and press Play.
// Distances are in units: 600 px/s² becomes 6, 60 px/s becomes 0.6, ground is y = 0.

// Entity.cs
using UnityEngine;
using UnityEngine.InputSystem;

public class Entity : MonoBehaviour
{
    public float homeX = 0f;

    void Start() { transform.position = new Vector3(homeX, 1.2f, 0f); Toggle<Movement>(); }

    void Update()
    {
        var kb = Keyboard.current;
        if (kb == null) return;
        if (kb.digit1Key.wasPressedThisFrame) Toggle<Gravity>();
        if (kb.digit2Key.wasPressedThisFrame) Toggle<Movement>();
        if (kb.digit3Key.wasPressedThisFrame) Toggle<Health>();
        if (kb.digit4Key.wasPressedThisFrame) Toggle<Glow>();
        if (kb.lKey.wasPressedThisFrame) transform.position = new Vector3(transform.position.x, 1.2f, 0f);
        if (kb.hKey.wasPressedThisFrame)
        {
            if (TryGetComponent(out Health h)) h.Hit();
            else Debug.Log("Hit ignored: no Health component");
        }
    }

    void Toggle<T>() where T : Component
    {
        bool had = TryGetComponent(out T part);
        if (had) Destroy(part);   // removed after this frame's updates
        else gameObject.AddComponent<T>();
        Debug.Log(typeof(T).Name + (had ? " removed" : " added"));
    }
}

// Gravity.cs
using UnityEngine;

public class Gravity : MonoBehaviour
{
    public float g = 6f;
    float vy;

    void Update()
    {
        vy -= g * Time.deltaTime;
        var p = transform.position;
        p.y += vy * Time.deltaTime;
        if (p.y <= 0f) { p.y = 0f; vy = 0f; }
        transform.position = p;
    }
}

// Movement.cs
using UnityEngine;

public class Movement : MonoBehaviour
{
    public float speed = 0.6f, range = 0.8f;
    float dir = 1f;
    Entity entity;

    void Awake() { entity = GetComponent<Entity>(); }   // look up once, not every frame

    void Update()
    {
        var p = transform.position;
        p.x += speed * dir * Time.deltaTime;
        if (p.x > entity.homeX + range) { p.x = entity.homeX + range; dir = -1f; }
        if (p.x < entity.homeX - range) { p.x = entity.homeX - range; dir = 1f; }
        transform.position = p;
    }
}

// Health.cs
using UnityEngine;

public class Health : MonoBehaviour
{
    public int max = 3, hp = 3;

    public void Hit()
    {
        hp--;
        Debug.Log("Health: hp " + hp);
        if (hp <= 0) { hp = max; Debug.Log("Health: died and respawned"); }
    }
}

// Glow.cs
using UnityEngine;

[RequireComponent(typeof(SpriteRenderer))]
public class Glow : MonoBehaviour
{
    float t;
    SpriteRenderer sr;

    void Awake() { sr = GetComponent<SpriteRenderer>(); }

    void Update()
    {
        float rate = 1f;
        if (TryGetComponent(out Health h)) rate = 1 + (h.max - h.hp);   // optional neighbour
        t += rate * Time.deltaTime;
        float a = 0.5f + 0.5f * Mathf.Sin(t * 2f * Mathf.PI);
        sr.color = Color.Lerp(Color.white, Color.yellow, a);
    }

    void OnDestroy() { if (sr) sr.color = Color.white; }   // clean up when removed
}

The GDScript version keeps every part in one file as inner classes so it runs from a single script; in a real project each would be its own script with a class_name. The Unity version needs one file per class, named after the class. Glow tints the sprite there instead of drawing a halo.

Pitfalls

  • Components that assume a neighbour. If Glow calls Health without checking, a lamp with no Health crashes. Check for nil, or make the need explicit with [RequireComponent] in Unity or a warning in Godot's _ready.
  • Hidden order bugs. Two parts that both write the position give different results depending on who runs last. In Godot, removing and re-adding a child moves it to the end of the tree, so its order changes; use move_child to put it back. In Unity, set the order explicitly when it matters.
  • Looking up neighbours every frame. GetComponent and get_node search for the part each call. Cache the result in Awake or _ready when the neighbour is fixed, as Movement does above. Glow searches every frame only because Health can come and go.
  • Components that are too small. A component per variable, such as Speed, turns every behaviour into a tangle of lookups. One component, one ability.
  • The god component. The opposite mistake: a PlayerController that walks, shoots, takes damage and plays sounds is the old base class with a new name. Split it when two kinds of object want only half of it.

In real games

Unity's whole object model is components on GameObjects, and Godot projects commonly use child nodes as reusable parts, such as a hitbox or health node shared by the player and enemies. Robert Nystrom's Game Programming Patterns describes the pattern with a game object split into input, physics and graphics components.

You are done when two objects that do not inherit from each other, for example a crate and an enemy, both take damage through the same component.

Takeaways

  • Inheritance handles one new ability at a time; mixes of abilities lead to copied code, bloated base classes or a class per combination.
  • With components, an entity is a container and each component owns one ability and its data. Behaviour is the list of parts.
  • Fix the update order on purpose. Godot uses tree order; Unity needs Script Execution Order when it matters.
  • Parts talk by asking the entity for an optional neighbour, or by announcing events. Cache lookups that do not change.
  • Inherit to say what a thing is, one level deep. Compose to say what it can do.

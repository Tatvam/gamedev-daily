Delta time in Godot and Unity

Why speeds written per frame change with the frame rate, and how the delta of _process in Godot and Time.deltaTime in Unity make them per second.

You tune your character's walk speed on a 60 Hz monitor and it feels right. A tester with a 144 Hz monitor says the character races around the level, and someone on an old laptop says it crawls. The code is the same on all three machines.

The speed was written as "pixels per frame", so every machine runs the game at its own speed. This lesson turns it back into "pixels per second".

A frame is not a unit of time

A frame is one pass of the game loop: read input, update, draw. The previous two lessons showed that frames are not a fixed length. How long one takes depends on the monitor, the graphics card, what else the computer is doing, and what is on screen right now.

So this line has a hidden assumption:

x = x + 4   -- 4 pixels every frame

At 60 frames per second it moves 240 pixels per second. At 30 it moves 120, and at 144 it moves 576. The number 4 is a speed in pixels per frame, and a frame is a different length on every machine.

Measure the frame and multiply

Delta time, usually written dt or delta, is the number of seconds since the previous frame. If you write speeds in pixels per second and multiply by delta, the units work out to pixels, and the length of the frame is part of the sum:

x = x + 240 * dt   -- pixels per second times seconds = pixels

Short frames give small steps and long frames give big ones. Over one second they always add up to 240 pixels.

Who measures it, and when

You never measure delta yourself in Godot or Unity. The engine owns the clock, and your scripts only read it. Each frame happens in this order:

  1. The engine reads the system clock and subtracts the time it read at the start of the previous frame.
  2. It may adjust that number: Unity limits how large a single frame's delta can be, and both engines multiply it by a time scale, a global speed factor where 1 is normal and 0.5 is slow motion.
  3. It stores the result, then calls every script's per-frame function. Every script in that frame sees the same value.

In Godot 4 the value arrives as the delta argument of _process(delta), in seconds. You can also ask any node for it with get_process_delta_time(). The time scale is Engine.time_scale.

In Unity there is no argument. Update() reads the static property Time.deltaTime, also in seconds. The time scale is Time.timeScale, and Time.unscaledDeltaTime gives the raw value for things that must ignore slow motion, such as a pause menu.

Both engines also have a fixed-rate callback, _physics_process(delta) in Godot and FixedUpdate() in Unity. There the delta is the fixed step, the same every call. Unity's Time.deltaTime also returns the fixed step when you read it inside FixedUpdate, so the same line works in both places.

Rule of thumb

Anything you change a little every frame is a rate. Write it per second and multiply by delta. Then check the units: a change in position should come out in pixels or metres, never in pixels per frame.

The code

LÖVE passes the frame's duration to love.update(dt). The two squares below use the same names and numbers as the demo, including its 0.1 second cap and its time scale.

local TRACK = 480        -- distance to the finish line, in pixels
local PER_FRAME = 4      -- top square: pixels per frame
local SPEED = 240        -- bottom square: pixels per second
local MAX_DT = 0.1       -- longest frame we are willing to simulate
local timeScale = 1      -- 0.5 is slow motion, 2 is double speed

local frameSquare = { x = 0 }
local deltaSquare = { x = 0 }

function love.update(dt)
  -- dt is the number of seconds since the previous frame
  local step = math.min(dt, MAX_DT) * timeScale

  -- Per frame: the speed depends on the frame rate.
  frameSquare.x = math.min(frameSquare.x + PER_FRAME, TRACK)

  -- Per second: pixels per second times seconds.
  deltaSquare.x = math.min(deltaSquare.x + SPEED * step, TRACK)
end

function love.draw()
  love.graphics.rectangle("fill", frameSquare.x, 60, 18, 18)
  love.graphics.rectangle("fill", deltaSquare.x, 140, 18, 18)
end
# Godot 4. Attach to a Node2D in a new scene and run it.
extends Node2D

const TRACK := 480.0
const PER_FRAME := 4.0
const SPEED := 240.0

var frame_x := 0.0
var delta_x := 0.0

func _ready() -> void:
    Engine.max_fps = 30   # try 30, 60 and 0 (no cap) and compare

# delta: seconds since the previous frame, already multiplied by Engine.time_scale
func _process(delta: float) -> void:
    frame_x = minf(frame_x + PER_FRAME, TRACK)
    delta_x = minf(delta_x + SPEED * delta, TRACK)
    queue_redraw()

func _draw() -> void:
    draw_rect(Rect2(frame_x, 60, 18, 18), Color.WHITE)
    draw_rect(Rect2(delta_x, 140, 18, 18), Color.WHITE)
// Unity 6 or 2022 LTS. Put on an empty GameObject in a new scene and press Play.
using UnityEngine;

public class DeltaRace : MonoBehaviour
{
    // Unity measures in units, not pixels: 2.4 units per second here.
    const float StartX = -2.4f, Track = 4.8f;
    const float PerFrame = 0.04f, Speed = 2.4f;

    Transform frameSquare, deltaSquare;

    void Start()
    {
        QualitySettings.vSyncCount = 0;    // otherwise vsync decides the frame rate
        Application.targetFrameRate = 30;  // try 30, 60 and 144 and compare
        frameSquare = MakeCube(1f);
        deltaSquare = MakeCube(-1f);
    }

    // Time.deltaTime: seconds since the previous frame, scaled by Time.timeScale
    void Update()
    {
        Move(frameSquare, PerFrame);
        Move(deltaSquare, Speed * Time.deltaTime);
    }

    static void Move(Transform t, float amount)
    {
        Vector3 p = t.position;
        p.x = Mathf.Min(p.x + amount, StartX + Track);
        t.position = p;
    }

    static Transform MakeCube(float y)
    {
        Transform t = GameObject.CreatePrimitive(PrimitiveType.Cube).transform;
        t.position = new Vector3(StartX, y, 0f);
        t.localScale = Vector3.one * 0.3f;
        return t;
    }
}

In each version, change the frame rate setting and run again. The top square's arrival time follows the frame rate; the bottom one arrives after two seconds every time. The Godot and Unity versions leave the cap to the engine, which is why they have no MAX_DT.

Pitfalls

  • Multiplying twice. Some engine features already apply delta for you. In Godot 4, CharacterBody2D.velocity is in pixels per second and move_and_slide() uses the frame's delta itself. In Unity, a Rigidbody's velocity is in units per second and the physics step applies it. Multiplying those by delta makes movement tiny and frame-rate dependent again.
  • Multiplying amounts that are not rates. Mouse movement reports how far the mouse moved since last time. That is already a distance, so scaling it by delta makes camera sensitivity change with the frame rate. The same goes for one-off changes such as "jump: set vertical speed to 600".
  • Timers counted in frames. cooldown = cooldown - 1 lasts twice as long at 30 fps. Store seconds and subtract dt.
  • Smoothing with a fixed blend. x = x + (target - x) * 0.1 every frame closes 10 percent of the gap per frame, so it settles faster at high frame rates. Use a blend that depends on delta, for example 1 - math.exp(-6.3 * dt) in place of 0.1, which closes about 10 percent of the gap per frame at 60 fps and the same share per second at any rate.
  • Huge frames. Loading, a breakpoint or dragging the window can produce a frame of half a second or more, and the object jumps that far in one step, possibly through a wall. Cap delta, as the Lua does. Unity caps it for you through Maximum Allowed Timestep in the Time settings, one third of a second by default, which is still large for fast objects.
  • Acceleration still drifts. Delta time makes constant speeds exact. Anything that accelerates, such as a jump under gravity, still lands in slightly different places at different frame rates. That needs a fixed step, the subject of the next lesson.

In real games

Every per-frame callback in both engines is built around this value. Godot hands delta to _process, and Unity exposes Time.deltaTime to Update, LateUpdate and coroutines. Godot's own nodes, such as AnimationPlayer and Tween, advance by the same delta, which is why changing the time scale slows them down together with your scripts.

The time scale is the usual tool for whole-game slow motion and for pausing in Unity: setting Time.timeScale to 0 stops everything that uses scaled time, while menus that read Time.unscaledDeltaTime keep working. That only works if every moving thing multiplies by delta. Code that counts frames ignores the time scale entirely, as the demo shows.

Time three things with a stopwatch at 20 fps and again uncapped: crossing the screen, a weapon cooldown, and how long the camera takes to catch up after a sudden move. Fix every number that changes, using the pitfalls above. You are done when all three times match at both frame rates.

Takeaways

  • A frame is not a fixed amount of time, so a speed written per frame changes from machine to machine.
  • Delta time is the seconds since the previous frame. Speed per second times delta gives distance, at any frame rate.
  • The engine measures delta once per frame, scales it, and gives every script the same value: delta in Godot's _process, Time.deltaTime in Unity's Update.
  • Only multiply rates. Distances, one-off changes and values the engine already scales must not be multiplied again.
  • Cap delta for long frames, and use a fixed step for anything that accelerates.

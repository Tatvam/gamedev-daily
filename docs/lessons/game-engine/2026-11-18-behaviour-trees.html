Behaviour trees: AI that is ticked every frame

How selectors, sequences, conditions and actions combine into readable guard AI, what a tick does in what order, and how Godot and Unity support it.

Your guard's state machine has Patrol, Chase and Attack. Then design asks for "investigate noises", "flee when hurt" and "return to post". Each new state needs transitions to and from most old ones, and the diagram becomes a ball of wool. The question the guard really asks every frame is simpler: what is the most important thing I can do right now?

A tree that is asked a question every tick

A behaviour tree is a tree of small nodes that together decide what an agent does. Many times per second the game ticks the tree: it calls the root node, the root calls some of its children, and so on down. Every node answers its tick with exactly one of three statuses:

  • success: I did it, or the thing I checked is true.
  • failure: I cannot do it, or the thing I checked is false.
  • running: I am still working on it; tick me again next time.

The status is all a parent learns about a child. That small contract is what makes nodes reusable.

Leaves do the work

Leaves, the nodes at the ends of branches, come in two kinds. A condition checks something and answers success or failure at once, for example "can I see the player?". An action changes the world, for example "move towards the player", and may answer running for many ticks before it finishes.

Composites decide the order

The inner nodes are composites. They own a list of children and tick them left to right. Two composites cover most trees:

CompositeTicks children until oneReturnsReads like
Sequence (→)does not succeedthat child's status, or success if all succeeded"do this, then this"
Selector (?)does not failthat child's status, or failure if all failed"try this, else this"

A sequence that starts with a condition works like an if: if the condition fails, the action is never ticked. A selector is a priority list: the first child that does not fail wins, and later children are not ticked at all. Some books call the selector a fallback.

One tick, in order

The player stands just outside the guard's sight. One tick:

  1. The selector ticks Attack. Attack ticks In reach?, which fails, so Attack fails without ticking Strike.
  2. The selector moves on to Chase. Can see? fails, so Chase fails.
  3. The selector ticks Patrol, which steps the guard towards its next waypoint and returns running.
  4. Running is not failure, so the selector stops there and returns running. The tick is over.

Now the player steps into sight. Next tick Can see? succeeds, Move to player runs, and Patrol is never reached. Nobody wrote a "Patrol to Chase" transition: the interruption falls out of the priority order, because the tree is walked from the root every tick. That style is called reactive.

The alternative is a composite with memory: it resumes at the child that was running last tick, skipping the ones before it. That suits scripted steps such as "open door, walk through, close door", but it will not notice a more important branch until the running child ends. Most libraries offer both.

Who owns the data

The tree is structure: which nodes exist and in what order. Changing data, such as the guard's next waypoint or where it last saw the player, belongs to the agent. Many libraries keep it in a blackboard, a per-agent table of named values that conditions read and actions write. Keeping data out of the nodes lets twenty guards share one tree.

Your agent ticks the tree from its per-frame callback: _process or _physics_process in Godot, Update in Unity. Many games tick on a timer instead, a few times per second, because decisions rarely need to change every frame.

What each engine gives you

Godot 4 has no behaviour tree in the core engine. Community plugins fill the gap: LimboAI is a C++ plugin with behaviour trees, state machines, an editor and a visual debugger, and tasks written in GDScript; Beehave builds the tree out of nodes in your scene.

Unity has none in the core engine either, but offers an official package, Unity Behavior, for Unity 6. It edits trees as a visual "behavior graph" with a blackboard, and custom nodes are C# classes. On Unity 2022 LTS, hand-written trees or Asset Store packages are usual. A plugin buys you an editor and a live debugger; hand-written code, as below, is a few dozen lines you fully understand.

Rule of thumb

Put the most urgent branch on the left, start each branch with the condition that guards it, and keep the last child of the root something that always works, such as idle or patrol. Then the tree always has an answer.

Try it

Drag the blue player, or click the field and use the arrow keys. The tree below shows the last tick: green succeeded, red failed, amber is running, dashed grey was not ticked. Press Step one tick to go one tick at a time.

When the guard attacks, notice that everything right of Attack goes grey. Then set Selector order to Patrol first. Patrol never fails, so the guard walks right past you.

The code

The Lua is the demo as a LÖVE 11 program with the same numbers: sight 110, reach 24, speed 60 per second, ten ticks per second of game time, and the mouse as the player. Each node is a function that returns its status; the demo uses tables so it can colour them. To try "Patrol first", swap the first and last children of the selector.

-- main.lua for LÖVE 11. The mouse is the player.
local SUCCESS, FAILURE, RUNNING = "success", "failure", "running"
local TICK = 0.1                     -- seconds of game time per tick
local SIGHT, REACH, SPEED = 110, 24, 60
local waypoints = { {60, 50}, {340, 50}, {340, 150}, {60, 150} }
local guard = { x = 60, y = 50, next = 2, strikes = 0 }
local player = { x = 300, y = 120 }
local timer = 0

-- Composites tick their children left to right.
local function Selector(...)
  local children = { ... }
  return function(dt)
    for i = 1, #children do
      local status = children[i](dt)
      if status ~= FAILURE then return status end   -- first child that did not fail
    end
    return FAILURE
  end
end

local function Sequence(...)
  local children = { ... }
  return function(dt)
    for i = 1, #children do
      local status = children[i](dt)
      if status ~= SUCCESS then return status end   -- first child that did not succeed
    end
    return SUCCESS
  end
end

local function distance(x, y)
  return math.sqrt((x - guard.x) ^ 2 + (y - guard.y) ^ 2)
end

local function stepToward(x, y, dt)  -- returns true on arrival
  local d, step = distance(x, y), SPEED * dt
  if d <= step then
    guard.x, guard.y = x, y
    return true
  end
  guard.x = guard.x + (x - guard.x) / d * step
  guard.y = guard.y + (y - guard.y) / d * step
  return false
end

-- Leaves. Conditions answer at once; actions may keep running.
local function inReach() return distance(player.x, player.y) <= REACH and SUCCESS or FAILURE end
local function canSee() return distance(player.x, player.y) <= SIGHT and SUCCESS or FAILURE end

local function strike()
  guard.strikes = guard.strikes + 1
  return SUCCESS
end

local function moveToPlayer(dt)
  stepToward(player.x, player.y, dt)
  return distance(player.x, player.y) <= REACH and SUCCESS or RUNNING
end

local function patrol(dt)
  local p = waypoints[guard.next]
  if not stepToward(p[1], p[2], dt) then return RUNNING end
  guard.next = guard.next % #waypoints + 1
  return SUCCESS
end

local tree = Selector(
  Sequence(inReach, strike),         -- Attack
  Sequence(canSee, moveToPlayer),    -- Chase
  patrol                             -- Patrol
)

function love.update(dt)
  player.x, player.y = love.mouse.getPosition()
  timer = timer + dt
  while timer >= TICK do
    timer = timer - TICK
    tree(TICK)
  end
end

function love.draw()
  love.graphics.circle("line", guard.x, guard.y, SIGHT)
  love.graphics.circle("fill", guard.x, guard.y, 8)
  love.graphics.circle("line", player.x, player.y, 8)
  love.graphics.print("strikes: " .. guard.strikes, 10, 10)
end
# guard.gd for Godot 4, no plugin. Attach to a Node2D in a new scene and run.
# The mouse is the player.
extends Node2D

enum Status { SUCCESS, FAILURE, RUNNING }
const TICK := 0.1
const SIGHT := 110.0
const REACH := 24.0
const SPEED := 60.0

var waypoints := [Vector2(60, 50), Vector2(340, 50), Vector2(340, 150), Vector2(60, 150)]
var guard := Vector2(60, 50)
var player := Vector2(300, 120)
var next_point := 1
var strikes := 0
var timer := 0.0
var tree: Callable

func _ready() -> void:
    tree = selector([
        sequence([in_reach, strike]),        # Attack
        sequence([can_see, move_to_player]), # Chase
        patrol,                              # Patrol
    ])

func selector(children: Array) -> Callable:
    return func(dt: float):
        for child in children:
            var status: int = child.call(dt)
            if status != Status.FAILURE:
                return status
        return Status.FAILURE

func sequence(children: Array) -> Callable:
    return func(dt: float):
        for child in children:
            var status: int = child.call(dt)
            if status != Status.SUCCESS:
                return status
        return Status.SUCCESS

# Leaves. Every leaf takes dt so the composites can call them all the same way.
func in_reach(_dt: float) -> Status:
    return Status.SUCCESS if guard.distance_to(player) <= REACH else Status.FAILURE

func can_see(_dt: float) -> Status:
    return Status.SUCCESS if guard.distance_to(player) <= SIGHT else Status.FAILURE

func strike(_dt: float) -> Status:
    strikes += 1
    return Status.SUCCESS

func move_to_player(dt: float) -> Status:
    guard = guard.move_toward(player, SPEED * dt)
    return Status.SUCCESS if guard.distance_to(player) <= REACH else Status.RUNNING

func patrol(dt: float) -> Status:
    var target: Vector2 = waypoints[next_point]
    guard = guard.move_toward(target, SPEED * dt)
    if guard != target:
        return Status.RUNNING
    next_point = (next_point + 1) % waypoints.size()
    return Status.SUCCESS

func _process(delta: float) -> void:
    player = get_global_mouse_position()
    timer += delta
    while timer >= TICK:
        timer -= TICK
        tree.call(TICK)
    queue_redraw()

func _draw() -> void:
    draw_arc(guard, SIGHT, 0.0, TAU, 48, Color(1, 1, 1, 0.3))
    draw_circle(guard, 8.0, Color.RED)
    draw_circle(player, 8.0, Color.CYAN)
// Guard.cs. Unity 2022 LTS or Unity 6, no package.
// Distances are the demo's numbers divided by 20, so they fit Unity units.
// Put this on a 2D circle sprite. Make a second circle for the player, drag it
// into Player, and move it in the Scene view while the game runs.
using System;
using UnityEngine;

public class Guard : MonoBehaviour
{
    enum Status { Success, Failure, Running }

    const float Tick = 0.1f, Sight = 5.5f, Reach = 1.2f, Speed = 3f;

    public Transform player;
    [SerializeField] int strikes;   // visible in the Inspector

    readonly Vector2[] waypoints =
    {
        new Vector2(3f, 2.5f), new Vector2(17f, 2.5f),
        new Vector2(17f, 7.5f), new Vector2(3f, 7.5f)
    };
    int next = 1;
    float timer;
    Func<float, Status> tree;

    static Func<float, Status> Selector(params Func<float, Status>[] children) => dt =>
    {
        foreach (var child in children)
        {
            var status = child(dt);
            if (status != Status.Failure) return status;
        }
        return Status.Failure;
    };

    static Func<float, Status> Sequence(params Func<float, Status>[] children) => dt =>
    {
        foreach (var child in children)
        {
            var status = child(dt);
            if (status != Status.Success) return status;
        }
        return Status.Success;
    };

    void Start()
    {
        transform.position = waypoints[0];
        tree = Selector(
            Sequence(InReach, Strike),        // Attack
            Sequence(CanSee, MoveToPlayer),   // Chase
            Patrol);                          // Patrol
    }

    float Distance() => Vector2.Distance(transform.position, player.position);

    bool StepToward(Vector2 target, float dt)
    {
        transform.position = Vector2.MoveTowards(transform.position, target, Speed * dt);
        return (Vector2)transform.position == target;
    }

    Status InReach(float dt) => Distance() <= Reach ? Status.Success : Status.Failure;
    Status CanSee(float dt) => Distance() <= Sight ? Status.Success : Status.Failure;

    Status Strike(float dt)
    {
        strikes++;
        return Status.Success;
    }

    Status MoveToPlayer(float dt)
    {
        StepToward(player.position, dt);
        return Distance() <= Reach ? Status.Success : Status.Running;
    }

    Status Patrol(float dt)
    {
        if (!StepToward(waypoints[next], dt)) return Status.Running;
        next = (next + 1) % waypoints.Length;
        return Status.Success;
    }

    void Update()
    {
        timer += Time.deltaTime;
        while (timer >= Tick)
        {
            timer -= Tick;
            tree(Tick);
        }
    }

    void OnDrawGizmos() => Gizmos.DrawWireSphere(transform.position, Sight);
}

Pitfalls

  • A branch that never fails. An action that never fails blocks every branch to its right, as "Patrol first" shows in the demo. Put catch-all behaviour last, and let long actions fail when they cannot finish, for example when the path is blocked.
  • Mixing up running and success. If "move to player" returns success as soon as it starts, the sequence moves on before the guard has arrived. Return running until the job is done.
  • State hidden inside nodes. If a node keeps a timer in its own fields and twenty guards share the tree, they overwrite each other. Keep per-agent data on the agent or its blackboard, or give each agent its own tree.
  • Interrupted actions that never clean up. When a reactive tree switches branches, the old action is simply not ticked again. If it started an animation or reserved a cover point, nothing stops it. Give actions an abort hook once they hold resources; libraries usually have one.
  • Expensive conditions near the root. In a reactive tree the left-most conditions run every tick for every agent. Put a raycast there and you pay for it constantly. Tick less often, cache results, or put cheap checks first.

In real games

Damian Isla's GDC 2005 talk and paper on the AI of Halo 2 described a hierarchy of behaviours chosen by priority and re-evaluated as the situation changed. It is widely credited with making behaviour trees popular in game development.

Unreal Engine ships behaviour trees with a blackboard as part of the engine. Outside games, behaviour trees also control robots, the focus of Colledanchise and Ögren's book below.

Your turn (15 minutes)

Take the code tab for your engine and add a Flee branch: a sequence of the condition "strikes is at least 20" and an action that moves the guard away from the player and always returns running. Decide where in the selector it belongs, then test it. You are done when the guard backs away after 20 strikes, and you can explain why Flee placed last would never run.

Takeaways

  • Every node answers a tick with success, failure or running, and that status is all its parent sees.
  • A sequence ticks children until one does not succeed; a selector ticks children until one does not fail. Order is priority.
  • A reactive tree is walked from the root every tick, so more important branches interrupt running ones without explicit transitions.
  • The tree is shared structure; positions, targets and running state belong to each agent, often in a blackboard.
  • Neither engine core has one: Godot has plugins such as LimboAI and Beehave, Unity 6 has the Unity Behavior package, and a hand-written tree is a few dozen lines.

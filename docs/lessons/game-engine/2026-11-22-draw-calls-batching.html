Draw calls and batching: why shared textures are cheap

What a draw call is, how engines merge neighbouring sprites that share a texture into one batch, and how draw order and atlases decide the count.

You add a hundred coins to a level and the frame rate does not move. You add a hundred coins, gems and hearts, scattered between each other, and the profiler suddenly shows the CPU busy in rendering. The number of sprites is the same. What changed is how many times the engine had to stop and tell the graphics card something new.

A draw call is a command, and commands have overhead

A draw call is one request from the CPU to the GPU: "draw these triangles, using this texture, this shader and these blend settings". The settings that must be in place for the call are called render state. A sprite is two triangles, so the GPU finishes a single sprite almost instantly. The expensive part is usually on the CPU side: the engine and the graphics driver have to prepare, check and send each call, and changing state between calls (binding another texture, switching shader) adds more work.

How much a call costs depends on the hardware and the graphics API. Newer APIs such as Vulkan, Direct3D 12 and Metal make calls cheaper, but not free. The rule that survives everywhere: a few large calls beat many small ones.

Batching merges neighbours that need the same state

Batching means collecting several sprites into one vertex buffer and drawing them with a single call. The engine can only do that when the sprites need the same render state, because one call has one texture and one shader.

There is a second condition that surprises people: the sprites must be next to each other in draw order. The previous lessons settled who is drawn on top through layers, order numbers and tree order. The batcher may not change that answer. It walks the sorted list from back to front and starts a new batch every time the state differs from the sprite before it. So the number of draw calls is the number of runs of equal state in the draw list, not the number of different textures.

Who owns what

You own the inputs: the draw order, which textures exist, and which materials each sprite uses. The engine owns the merging, which it redoes every frame after sorting. You never call "batch these"; you arrange things so that the batcher finds long runs.

Two ways to get longer runs

Group by state in the draw order. If coins never overlap gems, nothing forces them to interleave. Put each kind on its own layer, or under its own parent, and they become one run each. This is free when overlap does not matter and wrong when it does: a sorted list can put a coin on top of a gem that should cover it.

Remove the state change. A texture atlas packs many images into one texture, and each sprite draws a rectangle of it. Every sprite now has the same texture, so any order forms one run. The price is a bigger texture, a maximum texture size, and a little padding between images so that filtering does not bleed one into the next.

How Godot and Unity express it

Godot 4 batches consecutive 2D canvas items in draw order (tree order, adjusted by z_index and Y sorting) when they share a texture and material. The Compatibility renderer has batched 2D since 4.0. The Forward+ and Mobile renderers gained 2D batching later in the 4.x series; my understanding is that this arrived in 4.4, but check the release notes for your version. To share a texture, use one sprite sheet with Sprite2D's region_enabled and region_rect, or hframes and vframes, or an AtlasTexture resource. A frame capture tool such as RenderDoc shows each draw call the frame actually made.

Unity (2022 LTS and Unity 6) batches consecutive SpriteRenderers that share a material and texture, after sorting by sorting layer, order in layer and the other sort criteria. A Sprite Atlas asset packs sprites into shared textures at build time. The Game view's Stats panel shows a Batches count, and the Frame Debugger (Window > Analysis > Frame Debugger) lists every draw call, often with the reason a call could not be merged with the previous one. Meshes in 3D have further mechanisms (static batching, GPU instancing, the SRP Batcher) that this lesson does not cover.

Try it

The field holds sprites using three textures: stripes, dots and checks. The strip underneath is the draw list from first to last, and the bars below it are the batches. Start in scene order and press Next draw call a few times to watch the frame being built one call at a time. Then switch to "Sorted by texture" and look for sprites outlined in red, then try the atlas. Raise the sprite count and watch the scene order climb towards one call per sprite.

The code

A LÖVE 11 program with the demo's numbers: 500 sprites generated with seed 11, 60 shown at first, three procedural textures, and the same three modes. LÖVE batches consecutive draws that use the same texture by itself, so the program counts runs to predict the number of draw calls and prints LÖVE's own count from love.graphics.getStats() beside it. Press 1, 2 or 3 to switch mode and the arrow keys to change the count. Positions differ from the demo's because the random generators differ.

-- main.lua for LÖVE 11. Keys: 1 scene order, 2 sorted by texture, 3 one atlas.
-- Up and Down change the sprite count.
local MAX, SIZE = 500, 24
local count, mode = 60, "random"
local tints = { {0.2, 0.45, 0.85}, {0.15, 0.55, 0.25}, {0.75, 0.5, 0.05} }
local textures, quads, atlas = {}, {}, nil
local sprites, order, batches = {}, {}, 0

-- kind 1 stripes, 2 dots, 3 checks: true where the pattern is light
local function pattern(kind, x, y)
  if kind == 1 then return x % 12 >= 6 end
  if kind == 2 then return (x - 12) ^ 2 + (y - 12) ^ 2 < 25 end
  return (math.floor(x / 12) + math.floor(y / 12)) % 2 == 0
end

local function shade(light)
  if light then return 1, 1, 1, 1 end
  return 0.55, 0.55, 0.55, 1
end

local function rebuild()
  order = {}
  for i = 1, count do order[i] = sprites[i] end
  if mode == "sorted" then
    table.sort(order, function(a, b)
      if a.kind ~= b.kind then return a.kind < b.kind end
      return a.id < b.id
    end)
  end
  -- each run of the same texture in draw order is one draw call
  batches = 0
  local last = nil
  for i = 1, #order do
    local tex = order[i].kind
    if mode == "atlas" then tex = "atlas" end
    if tex ~= last then
      batches = batches + 1
      last = tex
    end
  end
end

function love.load()
  for kind = 1, 3 do
    local data = love.image.newImageData(SIZE, SIZE)
    data:mapPixel(function(x, y) return shade(pattern(kind, x, y)) end)
    textures[kind] = love.graphics.newImage(data)
  end
  -- the atlas: the same three images side by side in one texture
  local data = love.image.newImageData(SIZE * 3, SIZE)
  data:mapPixel(function(x, y)
    return shade(pattern(math.floor(x / SIZE) + 1, x % SIZE, y))
  end)
  atlas = love.graphics.newImage(data)
  for kind = 1, 3 do
    quads[kind] = love.graphics.newQuad((kind - 1) * SIZE, 0, SIZE, SIZE, SIZE * 3, SIZE)
  end
  local rng = love.math.newRandomGenerator(11)
  for i = 1, MAX do
    sprites[i] = { id = i, x = rng:random() * (800 - SIZE),
                   y = rng:random() * (560 - SIZE), kind = rng:random(1, 3) }
  end
  rebuild()
end

function love.keypressed(key)
  if key == "1" then mode = "random" end
  if key == "2" then mode = "sorted" end
  if key == "3" then mode = "atlas" end
  if key == "up" then count = math.min(count + 10, MAX) end
  if key == "down" then count = math.max(count - 10, 10) end
  rebuild()
end

function love.draw()
  for i = 1, #order do
    local s = order[i]
    love.graphics.setColor(tints[s.kind])   -- a colour change does not break a batch
    if mode == "atlas" then
      love.graphics.draw(atlas, quads[s.kind], s.x, s.y)
    else
      love.graphics.draw(textures[s.kind], s.x, s.y)
    end
  end
  local stats = love.graphics.getStats()   -- read before the text adds its own call
  love.graphics.setColor(1, 1, 1)
  love.graphics.print(mode .. "  sprites " .. count .. "  predicted " .. batches
    .. "  drawcalls " .. stats.drawcalls, 10, 570)
end
# batching_field.gd for Godot 4. Attach to a Node2D in a new scene and run.
# Keys 1, 2, 3 rebuild the field in scene order, sorted by texture, or with one atlas.
# Children of a Node2D draw in tree order, so the order of add_child is the draw order.
extends Node2D

const SIZE := 24
var count := 60
var tints := [Color(0.2, 0.45, 0.85), Color(0.15, 0.55, 0.25), Color(0.75, 0.5, 0.05)]
var textures: Array[ImageTexture] = []
var atlas: ImageTexture
var label := Label.new()

func pattern(kind: int, x: int, y: int) -> bool:
    if kind == 0: return x % 12 >= 6
    if kind == 1: return (x - 12) * (x - 12) + (y - 12) * (y - 12) < 25
    return (x / 12 + y / 12) % 2 == 0

func make_texture(first_kind: int, kinds: int) -> ImageTexture:
    # Image.create works in all of Godot 4; 4.3 and later also offer Image.create_empty.
    var img := Image.create(SIZE * kinds, SIZE, false, Image.FORMAT_RGBA8)
    for x in SIZE * kinds:
        for y in SIZE:
            var light := pattern(first_kind + x / SIZE, x % SIZE, y)
            img.set_pixel(x, y, Color.WHITE if light else Color(0.55, 0.55, 0.55))
    return ImageTexture.create_from_image(img)

func _ready() -> void:
    for kind in 3:
        textures.append(make_texture(kind, 1))
    atlas = make_texture(0, 3)
    var hud := CanvasLayer.new()
    hud.add_child(label)
    add_child(hud)
    build("random")

func build(mode: String) -> void:
    for child in get_children():
        if child is Sprite2D:
            child.queue_free()
    var rng := RandomNumberGenerator.new()
    rng.seed = 11
    var sprites := []
    for i in count:
        sprites.append({"id": i, "kind": rng.randi_range(0, 2),
            "pos": Vector2(rng.randf() * (800 - SIZE), rng.randf() * (560 - SIZE))})
    if mode == "sorted":
        sprites.sort_custom(func(a, b): return a.kind < b.kind or (a.kind == b.kind and a.id < b.id))
    var batches := 0
    var last := -1
    for s in sprites:
        var sprite := Sprite2D.new()
        sprite.centered = false
        sprite.position = s.pos
        sprite.modulate = tints[s.kind]
        var tex: int = s.kind
        if mode == "atlas":
            sprite.texture = atlas                 # every sprite shares one texture
            sprite.region_enabled = true
            sprite.region_rect = Rect2(s.kind * SIZE, 0, SIZE, SIZE)
            tex = 3
        else:
            sprite.texture = textures[s.kind]
        if tex != last:
            batches += 1
            last = tex
        add_child(sprite)
    label.text = "%s  sprites %d  predicted draw calls %d" % [mode, count, batches]

func _unhandled_input(event: InputEvent) -> void:
    if event is InputEventKey and event.pressed and not event.echo:
        match event.keycode:
            KEY_1: build("random")
            KEY_2: build("sorted")
            KEY_3: build("atlas")
// BatchingField.cs. Unity 2022 LTS or Unity 6, 2D template.
// Add it to any GameObject, press Play, press 1, 2 or 3, and compare the Batches
// number in the Game view's Stats panel. Uses the Input Manager; if Active Input
// Handling is set to the Input System package only, switch it to Both.
using System.Collections.Generic;
using UnityEngine;

public class BatchingField : MonoBehaviour
{
    const int Size = 24;
    public int count = 60;
    static readonly Color[] tints = {
        new Color(0.2f, 0.45f, 0.85f), new Color(0.15f, 0.55f, 0.25f), new Color(0.75f, 0.5f, 0.05f) };
    readonly Sprite[] separate = new Sprite[3];
    readonly Sprite[] packed = new Sprite[3];
    readonly List<GameObject> spawned = new List<GameObject>();

    static bool Pattern(int kind, int x, int y)
    {
        if (kind == 0) return x % 12 >= 6;
        if (kind == 1) return (x - 12) * (x - 12) + (y - 12) * (y - 12) < 25;
        return (x / 12 + y / 12) % 2 == 0;
    }

    static Texture2D MakeTexture(int firstKind, int kinds)
    {
        var tex = new Texture2D(Size * kinds, Size);
        tex.filterMode = FilterMode.Point;
        var dark = new Color(0.55f, 0.55f, 0.55f);
        for (int x = 0; x < Size * kinds; x++)
            for (int y = 0; y < Size; y++)
                tex.SetPixel(x, y, Pattern(firstKind + x / Size, x % Size, y) ? Color.white : dark);
        tex.Apply();
        return tex;
    }

    void Start()
    {
        var atlas = MakeTexture(0, 3);
        for (int k = 0; k < 3; k++)
        {
            separate[k] = Sprite.Create(MakeTexture(k, 1), new Rect(0, 0, Size, Size), Vector2.zero, 40f);
            packed[k] = Sprite.Create(atlas, new Rect(k * Size, 0, Size, Size), Vector2.zero, 40f);
        }
        Build("random");
    }

    void Update()
    {
        if (Input.GetKeyDown(KeyCode.Alpha1)) Build("random");
        if (Input.GetKeyDown(KeyCode.Alpha2)) Build("sorted");
        if (Input.GetKeyDown(KeyCode.Alpha3)) Build("atlas");
    }

    void Build(string mode)
    {
        foreach (var go in spawned) Destroy(go);
        spawned.Clear();
        Random.InitState(11);
        for (int i = 0; i < count; i++)
        {
            int kind = Random.Range(0, 3);
            var go = new GameObject("Sprite " + i);
            go.transform.position = new Vector3(Random.Range(-4f, 4f), Random.Range(-2.8f, 2.8f), 0f);
            var r = go.AddComponent<SpriteRenderer>();
            r.sprite = mode == "atlas" ? packed[kind] : separate[kind];
            r.color = tints[kind];
            r.sortingOrder = mode == "sorted" ? kind * count + i : i;   // the draw order
            spawned.Add(go);
        }
    }
}

In all three, the only thing that changes between modes is the draw order or the texture each sprite points at. None of them contains batching code: the engine merges, and the scripts only arrange. The Godot and Unity versions draw the same field with their own random generators, so their counts will not match the Lua program exactly. Unity's Batches number also includes other work in the frame, such as clearing the screen, so compare the modes with each other rather than reading the absolute value.

Pitfalls

  • Sorting for batches and breaking the picture. Grouping by texture changes who covers whom. Only regroup things that do not overlap or whose overlap order does not matter, or use an atlas instead.
  • One odd sprite in the middle. A single sprite with another texture, material or shader, placed between two runs, splits them. A health bar with a custom shader drawn between enemies can double the call count.
  • Unique materials by accident. In Unity, reading renderer.material (rather than sharedMaterial) creates a copy for that renderer, which then cannot batch with the others. In Godot, giving each sprite its own duplicated material, for example by enabling local to scene on a shared ShaderMaterial, has the same effect.
  • Atlas bleeding. With filtering or mipmaps on, the GPU samples pixels next to a region's edge, which belong to the neighbouring image. Pad images in the atlas, or use point filtering for pixel art.
  • Optimising a number nobody measured. A few hundred draw calls are fine on most current hardware. Profile first; if the frame is limited by pixel fill, shaders or game logic, fewer calls will not help.

In real games

Tilemaps are the clearest case. A tileset is one texture, so a whole layer of tiles shares the same state. Godot 4's TileSet is built from atlas sources, and Unity's TilemapRenderer has a Chunk mode that draws tiles in groups.

Text rendering relies on the same idea. Engines rasterise glyphs into a font atlas so that a whole line of text, with many different letters, can be one draw call.

LÖVE batches consecutive draws of the same texture automatically since version 11, and offers SpriteBatch for building a batch by hand, which is how many LÖVE games draw tile layers.

Your turn (15 minutes)

Open a busy scene in your project. In Unity, open the Frame Debugger and count the draw calls for sprites; in Godot, capture a frame with RenderDoc. Find two neighbouring calls that use different textures for sprites that could share one. Either put those images into one sprite sheet (a Sprite Atlas in Unity, one texture with regions in Godot) or move one group to its own layer so it is no longer interleaved. You are done when the capture shows fewer calls and the scene looks exactly the same.

Takeaways

  • A draw call is one command to the GPU with one set of render state. Its cost is mostly on the CPU.
  • The engine merges sprites into one call only when they share state and are next to each other in draw order.
  • The call count is the number of runs of equal state in the draw list, not the number of textures.
  • Regroup draw order where overlap does not matter; use an atlas where it does.
  • Measure with the Frame Debugger in Unity or a frame capture in Godot before and after you change anything.

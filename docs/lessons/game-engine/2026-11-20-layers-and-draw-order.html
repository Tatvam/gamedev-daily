Layers and draw order: who is drawn on top

How 2D engines decide which sprite is drawn on top with layers, order numbers and Y sorting, and how Godot and Unity express the same sort key.

Your hero walks up behind a tree and is drawn on top of its trunk, as if standing in front of it. You raise the tree's order number to fix it, and now the hero walks in front of the tree and vanishes behind it. No single number is right, because the right answer changes as the hero moves.

2D engines paint, they do not measure depth

A 3D renderer can keep a depth value for every pixel and let the nearest surface win. Most 2D sprites are partly transparent, so engines draw them in the simplest possible way: one after another, each painted over what is already there. This is the painter's algorithm. Whatever is drawn last ends up on top.

So "which sprite is on top" is really "in what order does the engine draw them". Every frame the engine builds a draw list of visible sprites and sorts it. The question is only what it sorts by.

The sort key

Both engines, and any engine you write yourself, compare sprites with a sort key: a short list of values checked in order, where the first value that differs decides.

  1. Layer. A coarse bucket such as Ground, Objects or Interface. Everything on a lower layer is drawn before everything on a higher one, no matter what else is true.
  2. Order within the layer. A whole number for fine control inside a bucket. Higher is drawn later, so it is on top.
  3. Y position, only when Y sorting is switched on. A lower y on screen (further up) is drawn first.
  4. Scene order. If everything else ties, the object that comes first in the scene is drawn first. This is the fallback, and it is why ordering "just works" until objects start moving.

Faking depth with Y sorting

In a top-down or three-quarter view, the ground recedes up the screen. Something whose feet are higher on the screen is further away, so it should be drawn first. Y sorting puts that rule into the sort key: compare the y of each sprite's sort point, usually its feet.

The sort point matters as much as the switch. A tree is tall and a character is short. If you compare the centres of their images, a character standing just behind the trunk has a lower centre than the tree, and is drawn in front of it. Put the origin, or pivot, of every sprite at the point where it touches the ground.

In Godot, the scene tree is the draw list. A parent is drawn before its children and siblings are drawn top to bottom, so reordering nodes in the Scene dock changes what is on top. z_index overrides tree order inside one canvas layer, and y sorting reorders the children of the node that has it switched on. A CanvasLayer is a separate canvas with its own transform, which is why a HUD inside one is always on top and ignores the camera. A z_index never lifts a node out of its canvas layer.

In Unity, scene order is not part of the 2D contract. Sprites are sorted by Sorting Layer, then Order in Layer, then, for anything still tied, by their distance along the transparency sort axis. In the Built-in pipeline that axis is in the Graphics project settings; in URP with the 2D Renderer it is on the 2D Renderer Data asset. A SortingGroup component makes a multi-sprite character sort as one unit, so its arm cannot slip between the layers of a tree.

Rule of thumb

Use layers for things that are always above or below each other: ground, world, overhead, interface. Use Y sorting for things that move around each other. Reach for a manual order number only to settle a specific tie.

Try it

Click the scene and walk the blue character with the arrow keys or W A S D, or drag it. The small numbers are the draw list: 1 is painted first. With Y sort off, walk behind a tree, then raise the player's order to 1 and walk in front of one. Then switch Y sort on and walk around again.

Finally, change the sort point to the centre of each image and stand just behind a trunk. Put the player on the Ground layer to see that a layer beats everything else, including Y.

The code

The Lua is a LÖVE 11 program with the demo's scene: a puddle on layer 0, the player and four trees and two rocks on layer 1, the player moving at 120 pixels per second. Everything an engine does is in drawsBefore. Press Y to toggle Y sorting.

-- main.lua for LÖVE 11. Arrow keys move, Y toggles Y sorting.
local SPEED = 120
local ySort = false                  -- off at the start, as in the demo
local sprites = {}                       -- the scene, in scene order

local function add(kind, layer, order, x, y)
  local s = { kind = kind, layer = layer, order = order, x = x, y = y, id = #sprites + 1 }
  table.insert(sprites, s)
  return s
end

add("puddle", 0, 0, 330, 250)            -- layer 0: ground
local player = add("player", 1, 0, 200, 230)
add("tree", 1, 0, 110, 150)              -- x, y is where each one meets the ground
add("tree", 1, 0, 210, 215)
add("tree", 1, 0, 330, 140)
add("tree", 1, 0, 410, 230)
add("rock", 1, 0, 290, 205)
add("rock", 1, 0, 70, 250)

local function drawsBefore(a, b)
  if a.layer ~= b.layer then return a.layer < b.layer end
  if a.order ~= b.order then return a.order < b.order end
  if ySort and a.y ~= b.y then return a.y < b.y end
  return a.id < b.id                     -- scene order breaks every tie
end

function love.update(dt)
  local k = love.keyboard.isDown
  if k("left") then player.x = player.x - SPEED * dt end
  if k("right") then player.x = player.x + SPEED * dt end
  if k("up") then player.y = player.y - SPEED * dt end
  if k("down") then player.y = player.y + SPEED * dt end
end

function love.keypressed(key)
  if key == "y" then ySort = not ySort end
end

local function drawSprite(s)             -- every shape is drawn up from its feet
  if s.kind == "puddle" then
    love.graphics.setColor(0.3, 0.5, 0.9, 0.5)
    love.graphics.ellipse("fill", s.x, s.y, 34, 12)
  elseif s.kind == "player" then
    love.graphics.setColor(0.2, 0.4, 0.9)
    love.graphics.rectangle("fill", s.x - 9, s.y - 26, 18, 26)
    love.graphics.circle("fill", s.x, s.y - 31, 7)
  elseif s.kind == "tree" then
    love.graphics.setColor(0.5, 0.3, 0.1)
    love.graphics.rectangle("fill", s.x - 5, s.y - 14, 10, 14)
    love.graphics.setColor(0.1, 0.5, 0.2)
    love.graphics.polygon("fill", s.x - 24, s.y - 14, s.x, s.y - 70, s.x + 24, s.y - 14)
  else
    love.graphics.setColor(0.5, 0.5, 0.5)
    love.graphics.ellipse("fill", s.x, s.y - 9, 17, 9)
  end
end

function love.draw()
  love.graphics.clear(0.75, 0.85, 0.6)
  local list = {}
  for i = 1, #sprites do list[i] = sprites[i] end
  table.sort(list, drawsBefore)           -- build the draw list
  for i = 1, #list do drawSprite(list[i]) end   -- painter's algorithm
end
# draw_order.gd for Godot 4. Attach to a Node2D in a new scene and run.
# Arrow keys move, Enter (ui_accept) toggles Y sorting.
extends Node2D

const SPEED := 120.0
var world := Node2D.new()
var player := Polygon2D.new()
var label := Label.new()

func make_tree(pos: Vector2) -> Polygon2D:
    var tree := Polygon2D.new()
    # Points are relative to the node's origin, which sits where the trunk meets the ground.
    tree.polygon = PackedVector2Array([Vector2(-5, 0), Vector2(-5, -14), Vector2(-24, -14),
        Vector2(0, -70), Vector2(24, -14), Vector2(5, -14), Vector2(5, 0)])
    tree.color = Color(0.1, 0.5, 0.2)
    tree.position = pos
    return tree

func _ready() -> void:
    world.y_sort_enabled = true      # sort world's children by their origin's y
    add_child(world)

    var puddle := Polygon2D.new()
    puddle.polygon = PackedVector2Array([Vector2(-34, 0), Vector2(0, -12), Vector2(34, 0), Vector2(0, 12)])
    puddle.color = Color(0.3, 0.5, 0.9, 0.5)
    puddle.position = Vector2(330, 250)
    puddle.z_index = -1              # a lower z beats Y sorting: always under everything
    world.add_child(puddle)

    player.polygon = PackedVector2Array([Vector2(-9, 0), Vector2(-9, -38), Vector2(9, -38), Vector2(9, 0)])
    player.color = Color(0.2, 0.4, 0.9)
    player.position = Vector2(200, 230)
    world.add_child(player)
    for pos in [Vector2(110, 150), Vector2(210, 215), Vector2(330, 140), Vector2(410, 230)]:
        world.add_child(make_tree(pos))

    var hud := CanvasLayer.new()     # layer 1 by default: above the main canvas, ignores cameras
    hud.add_child(label)
    add_child(hud)

func _process(delta: float) -> void:
    player.position += Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down") * SPEED * delta
    if Input.is_action_just_pressed("ui_accept"):
        world.y_sort_enabled = not world.y_sort_enabled
    label.text = "Y sort: %s" % world.y_sort_enabled
// SortByY.cs. Unity 2022 LTS or Unity 6, any render pipeline.
// Add it to the player and to every tree sprite. Set each sprite's pivot to Bottom
// in its import settings so transform.position is where it meets the ground.
// Tick Is Player on the player. Uses the Input Manager ("Horizontal" and "Vertical");
// if Active Input Handling is set to the Input System package only, switch it to Both.
using UnityEngine;

[RequireComponent(typeof(SpriteRenderer))]
public class SortByY : MonoBehaviour
{
    public bool isPlayer;
    public float speed = 3f;          // units per second
    public int baseOrder = 0;         // added on top, to settle a specific tie
    SpriteRenderer sr;

    void Awake()
    {
        sr = GetComponent<SpriteRenderer>();
        sr.sortingLayerName = "Default";   // or a layer you made in Tags and Layers
    }

    void Update()
    {
        if (!isPlayer) return;
        var move = new Vector3(Input.GetAxisRaw("Horizontal"), Input.GetAxisRaw("Vertical"), 0f);
        transform.position += move.normalized * speed * Time.deltaTime;
    }

    void LateUpdate()   // after everything has moved this frame
    {
        // Unity's y points up, so a higher y is further away and must get a lower order.
        sr.sortingOrder = baseOrder + Mathf.RoundToInt(-transform.position.y * 100f);
    }
}

The Unity script writes y into Order in Layer, which works in every pipeline and is easy to inspect. The setting-only alternative is Transparency Sort Mode set to Custom Axis with axis (0, 1, 0) and each sprite's Sprite Sort Point set to Pivot; then sprites with equal layer and order are sorted by y with no script at all. In the Godot version, notice there is no sorting code: switching y_sort_enabled on the parent is the whole feature.

Pitfalls

  • Pivot in the middle of the image. Y sorting compares origins. With centred pivots, tall objects sort too early and characters pop in front of trunks. Move the pivot, or the sprite's offset, so the origin is at the feet.
  • Layers that should have been Y sort. Fixing one overlap by raising an order number breaks the opposite overlap. If two things can walk around each other, they belong in the same layer with Y sorting.
  • An unstable tie-break. Two sprites with exactly the same key may swap from frame to frame and flicker. Lua's table.sort is not stable, which is why the Lua adds id as a last key. In Unity, give overlapping props distinct orders.
  • Relative z_index surprises in Godot. With z_as_relative on, a child's final z is its parent's plus its own, so a node set to 1 can still be under a sibling branch whose parent is at 2.
  • Overflowing Order in Layer. In Unity it is stored as a 16-bit number, from −32768 to 32767. Multiplying y by 100 is safe only within about ±327 units of the origin; use a smaller factor for large maps.
  • Sorting cost. Sorting a few hundred sprites per frame is cheap. Sorting changes the order of draws, though, and a draw list that alternates between textures can break batching, which is two lessons away.

In real games

Top-down and three-quarter view games, from farming games to action RPGs, need characters to walk both in front of and behind trees, houses and each other, which is what Y sorting is for. Godot's TileMapLayer can take part in Y sorting too, so tall tiles such as walls and trees sort against characters.

Interfaces are almost always a separate layer drawn last: a CanvasLayer in Godot, a Screen Space canvas in Unity. Parallax backgrounds are the opposite case, layers drawn first and scrolled at a fraction of the camera speed.

Your turn (15 minutes)

Take a scene with a character and at least three tall props. Check where each sprite's origin is and move it to the feet. Then switch on Y sorting (in Godot, y_sort_enabled on the common parent; in Unity, the Custom Axis setting or the script above). You are done when the character can circle every prop and is hidden behind it exactly while its feet are above the prop's base.

Takeaways

  • 2D engines use the painter's algorithm: the draw list is sorted and the last sprite drawn is on top.
  • The sort key is checked in order: layer, order within the layer, y when Y sorting is on, then scene order.
  • Layers are for things that are always above or below; Y sorting is for things that move around each other.
  • Y sorting compares origins, so put each sprite's pivot where it touches the ground.
  • Godot spells the key as CanvasLayer, z_index, y_sort_enabled and tree order; Unity as Sorting Layer, Order in Layer and the transparency sort axis.

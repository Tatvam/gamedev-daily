Animation state machines: choosing and blending clips

How states, transitions, crossfades and a 1D blend tree pick and mix idle, walk, run and jump, and how AnimationTree and the Animator do it.

Your character speeds up and its legs snap from walk to run in one frame. Or it flickers between the two near the threshold. Or a jump pressed in mid-air fires again on landing. All three bugs live in the machinery that decides which animation plays, and how much of it.

Two questions every frame

An animation clip is recorded motion: bone angles or sprite frames over time. Every frame the engine must decide which clips play, and how much of each.

An animation state machine answers the first. It has named states (Idle, Walk, Run, Jump) and transitions between them. Each transition has a condition, such as "speed above 3.5", and a crossfade duration: for that long, both states play while the weight slides from the old to the new.

A blend tree (Godot's 1D and 2D kind is a blend space) answers the second. It is one state, Locomotion, holding clips placed on a number line. With idle at 0, walk at 2 and run at 5 metres per second, a speed of 2.6 gives:

  • f = (2.6 - 2) / (5 - 2) = 0.2
  • walk weight 1 - f = 0.8, run weight f = 0.2, idle 0

The weights add up to 1. The final pose, the bone transforms drawn this frame, is the weighted average of the clips' poses.

What happens, in what order

Each frame:

  1. Your code writes parameters: named values such as a Speed float or a Jump trigger. A trigger is a boolean that stays set until a transition consumes it.
  2. If no transition is running, the animator checks those leaving the current state. The first whose condition holds starts.
  3. It advances the clocks: clip playback times and transition progress.
  4. It samples every clip with non-zero weight, blends them, and writes the pose to the skeleton or sprite.

Gameplay owns the truth: speed, being on the floor. The animator owns the presentation: current state, fade progress. When gameplay asks the animator "am I jumping?", the two drift apart, because the animator may still be fading out of Jump after gameplay has landed.

Syncing cycles

A walk loops every 1.0 seconds, a run every 0.6. On separate clocks, the walk's left foot can be forward while the run's is back, and the average is a shuffle. The fix is normalized time, progress through the loop from 0 to 1. A synced blend advances one shared normalized time, with a loop length that is the weighted average of the clips' lengths. The clips must be authored to match: left foot down at 0, right foot at 0.5.

Godot and Unity

Godot 4 uses an AnimationTree node that reads clips from an AnimationPlayer. Its root can be an AnimationNodeStateMachine whose states are clips, AnimationNodeBlendSpace1D nodes or nested trees. Transitions have an xfade_time, a switch mode (immediate, sync or at end) and an advance mode. You write parameters by path, such as tree.set("parameters/Locomotion/blend_position", speed), and request states through the playback object at parameters/playback, whose travel() finds a path through the graph. As far as we know, Godot's blend spaces do not stretch clips to one shared cycle, so give walk and run the same length and foot timing.

Unity (2022 LTS and Unity 6) uses an Animator component with an Animator Controller asset. You declare Float, Int, Bool and Trigger parameters and set them with SetFloat and SetTrigger. Transitions have conditions, Has Exit Time, a Transition Duration and an Interruption Source (default None, as in the demo). A Blend Tree synchronises its children's normalized time. In the default Normal update mode the Animator evaluates after all Update calls and before LateUpdate, which is why bone tweaks belong in LateUpdate.

The trade-off: Godot's graph is made of resources you can build from GDScript, but parameter paths are strings that break silently when you rename a node. Unity's controller has typed parameters and built-in syncing, but is harder to change at runtime.

Rule of thumb

Blend continuous things (speed, direction, aim). Make discrete things (jump, attack, death) states. Parameters flow one way: gameplay to animator.

Try it

In Blend tree mode, drag Speed slowly from 0 to 6: the weights slide smoothly and the stride grows. In Separate states, each threshold starts a crossfade, and a jump from 0 to 6 passes through Walk on the way to Run. Set Fade to 0 to see the snap. Turn off Sync cycles at 3.5 m/s and the legs lose their rhythm. Press Jump twice quickly: the second press waits as a trigger and fires when the first jump ends. On the focused canvas, Left and Right change speed and Space jumps.

The code

The demo's blend tree mode in LÖVE 11, with the same names and numbers: idle 0, walk 2, run 5, a Jump trigger, exit at 75% of a 0.8 second jump, a 0.25 second fade and one shared phase. The legs are just thighs, enough to see the blend.

-- main.lua for LÖVE 11. Up/Down change speed, Space sets the Jump trigger.
local CYCLE = { idle = 2.0, walk = 1.0, run = 0.6 }            -- seconds per loop
local POINTS = { { "idle", 0 }, { "walk", 2 }, { "run", 5 } }  -- blend space, m/s
local JUMP_LEN, JUMP_EXIT, XFADE = 0.8, 0.75, 0.25

local speed, phase, jumpTime = 0, 0, 0
local jumpTrigger = false
local current = "Locomotion"
local transition = nil                     -- { to = name, elapsed = seconds }

local function blend1D(s)
  local w = { idle = 0, walk = 0, run = 0, jump = 0 }
  for i = 1, #POINTS - 1 do
    local a, b = POINTS[i], POINTS[i + 1]
    if s <= b[2] then
      local f = math.max(0, (s - a[2]) / (b[2] - a[2]))
      w[a[1]] = 1 - f
      w[b[1]] = f
      return w
    end
  end
  w[POINTS[#POINTS][1]] = 1
  return w
end

local function stateWeights(name)
  if name == "Jump" then return { idle = 0, walk = 0, run = 0, jump = 1 } end
  return blend1D(speed)
end

local function weights()
  local a = stateWeights(current)
  if not transition then return a end
  local b = stateWeights(transition.to)
  local p = math.min(1, transition.elapsed / XFADE)   -- crossfade progress
  local w = {}
  for k, v in pairs(a) do w[k] = v + (b[k] - v) * p end
  return w
end

function love.update(dt)
  -- 1. gameplay writes parameters
  if love.keyboard.isDown("up") then speed = math.min(6, speed + 3 * dt) end
  if love.keyboard.isDown("down") then speed = math.max(0, speed - 3 * dt) end
  -- 2. check transitions, only when none is running
  if not transition then
    if current == "Locomotion" and jumpTrigger then
      jumpTrigger = false                  -- the transition consumes the trigger
      jumpTime = 0
      transition = { to = "Jump", elapsed = 0 }
    elseif current == "Jump" and jumpTime / JUMP_LEN >= JUMP_EXIT then
      transition = { to = "Locomotion", elapsed = 0 }
    end
  end
  -- 3. advance the clocks
  if transition then
    transition.elapsed = transition.elapsed + dt
    if transition.elapsed >= XFADE then
      current = transition.to
      transition = nil
    end
  end
  jumpTime = jumpTime + dt
  local w = weights()
  local loco = w.idle + w.walk + w.run
  local cycle = 1
  if loco > 0 then
    cycle = (w.idle * CYCLE.idle + w.walk * CYCLE.walk + w.run * CYCLE.run) / loco
  end
  phase = (phase + dt / cycle) % 1          -- one shared normalized time
end

local function thigh(w, side)              -- side is 1 (front leg) or -1
  local s = math.sin(2 * math.pi * phase) * side
  local a = w.idle * 0.06 * side + w.walk * 0.5 * s + w.run * 0.9 * s
  if side == 1 then return a + w.jump * 1.0 end
  return a + w.jump * 0.5
end

function love.draw()
  local w = weights()
  local lift = w.jump * 45 * math.sin(math.pi * math.min(1, jumpTime / JUMP_LEN))
  local hipX, hipY = 200, 240 - lift
  for _, side in ipairs({ 1, -1 }) do
    local a = thigh(w, side)
    love.graphics.line(hipX, hipY, hipX + 60 * math.sin(a), hipY + 60 * math.cos(a))
  end
  love.graphics.line(hipX, hipY, hipX, hipY - 50)
  local y = 20
  for _, k in ipairs({ "idle", "walk", "run", "jump" }) do
    love.graphics.print(string.format("%-5s %.2f", k, w[k]), 300, y)
    love.graphics.rectangle("fill", 380, y, 150 * w[k], 12)
    y = y + 20
  end
  local label = current
  if transition then label = current .. " -> " .. transition.to end
  love.graphics.print(label, 20, 20)
  love.graphics.print(string.format("speed %.1f m/s", speed), 20, 40)
end

function love.keypressed(key)
  if key == "space" then jumpTrigger = true end
end
# player_anim.gd for Godot 4. Set up in the editor first:
#   AnimationPlayer with clips "idle", "walk", "run" and "jump"
#   AnimationTree: Anim Player set to that player, Active on,
#   Tree Root = AnimationNodeStateMachine with two states:
#     "Locomotion": BlendSpace1D, idle at 0, walk at 2, run at 5 (max 6)
#     "Jump": Animation node playing "jump"
#   Start -> Locomotion. Locomotion -> Jump: advance mode Enabled, Xfade Time 0.25.
#   Jump -> Locomotion: switch mode At End, advance mode Auto, Xfade Time 0.25.
#   (At End waits for the clip to finish, a little later than the demo's 75%.)
extends Node2D

@onready var tree: AnimationTree = $AnimationTree
@onready var playback: AnimationNodeStateMachinePlayback = tree.get("parameters/playback")

var speed := 0.0   # m/s; in a real game this comes from your movement code

func _process(delta: float) -> void:
    speed = clampf(speed + Input.get_axis("ui_down", "ui_up") * 3.0 * delta, 0.0, 6.0)
    tree.set("parameters/Locomotion/blend_position", speed)
    if Input.is_action_just_pressed("ui_accept") and playback.get_current_node() == &"Locomotion":
        playback.travel("Jump")
// PlayerAnim.cs for Unity 2022 LTS or Unity 6. Animator Controller set-up:
//   Parameters: Float "Speed", Trigger "Jump"
//   State "Locomotion" (default): 1D Blend Tree on Speed, Idle 0, Walk 2, Run 5
//   State "Jump": the jump clip
//   Locomotion -> Jump: condition Jump, Has Exit Time off, Fixed Duration on, Duration 0.25
//   Jump -> Locomotion: Has Exit Time on, Exit Time 0.75, Fixed Duration on, Duration 0.25
// Uses the Input Manager; if Active Input Handling is set to the Input System only,
// switch it to Both.
using UnityEngine;

[RequireComponent(typeof(Animator))]
public class PlayerAnim : MonoBehaviour
{
    static readonly int SpeedId = Animator.StringToHash("Speed");
    static readonly int JumpId = Animator.StringToHash("Jump");

    Animator animator;
    float speed;   // m/s; in a real game this comes from your movement code

    void Awake() => animator = GetComponent<Animator>();

    void Update()
    {
        speed = Mathf.Clamp(speed + Input.GetAxisRaw("Vertical") * 3f * Time.deltaTime, 0f, 6f);
        animator.SetFloat(SpeedId, speed);
        if (Input.GetKeyDown(KeyCode.Space))
            animator.SetTrigger(JumpId);   // stays set until a transition uses it
    }
}

Pitfalls

  • Flicker at a threshold. With separate Walk and Run states, a speed wobbling around 3.5 restarts the crossfade again and again. Use a blend tree, or leave a gap between thresholds (run above 3.7, walk below 3.3).
  • Stale triggers. A trigger no transition can use waits and fires later: the demo's double jump. In Unity call ResetTrigger when the moment has passed, or only set it when a jump is allowed. In Godot, check the current state before travel(), as the GDScript tab does.
  • Exit time on locomotion. In Unity, new transitions have Has Exit Time on, so walk-to-run waits for the clip. Turn it off where input should respond at once.
  • Reading the animator for gameplay. "Attack only if the state is Idle" ties rules to a half-finished fade. Keep the truth in gameplay code; use animation events or method tracks for timing, such as the frame a sword hits.
  • Performance. Every clip with non-zero weight is sampled each frame. Unity's Animator has a Culling Mode setting that can skip work off screen; distant crowds are often animated more cheaply than the hero.

In real games

Unity's animation system, Mecanim, arrived with Unity 4. Godot's state machines and blend spaces came with the rewritten AnimationTree in Godot 3.1. Unreal Engine's Animation Blueprints have state machines and Blend Spaces built on the same idea.

Some large productions replace hand-built locomotion graphs with motion matching, which searches a library of motion capture every few frames for the best-fitting clip. Simon Clavet's GDC 2016 talk described its use in Ubisoft's For Honor.

Your turn (15 minutes)

Replace separate Idle, Walk and Run states in your project with one Locomotion blend (a BlendSpace1D in Godot, a 1D Blend Tree in Unity) driven by the character's real horizontal speed, then add a Jump state. You are done when slow acceleration shows no pop between walk and run, and pressing jump twice in the air causes no second jump on landing.

Takeaways

  • States and transitions choose which clips play; blend weights, adding up to 1, decide how much.
  • A crossfade plays both states while the weight slides from old to new.
  • Blend continuous things (speed, direction) in one state; keep discrete actions (jump, attack) as separate states.
  • Gameplay owns the truth and writes parameters; the animator owns states, clocks and weights. Do not reverse that flow.
  • Blended loops need matching normalized timing, or the feet fight each other.

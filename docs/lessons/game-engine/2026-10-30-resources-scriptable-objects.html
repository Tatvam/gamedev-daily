Custom Resources in Godot, ScriptableObjects in Unity

How one data asset can feed many objects at once, when an edit reaches all of them, and how to give one object its own unique copy.

You give the elite guard a stronger sword by raising its damage from 20 to 35. You press play and every guard in the level now hits for 35. Later, one guard fires its crossbow and every other guard's ammo counter drops too. Both bugs have the same cause: the guards are not holding weapons, they are all holding the same weapon.

One data asset, many references

A data asset is a file that holds values and nothing else: no position in the world, no update loop. A weapon's damage, reach and ammo are a good fit. Godot calls these custom Resources: a script that extends Resource, saved as a .tres file. Unity calls them ScriptableObjects: a class that extends ScriptableObject, saved as a .asset file.

The behaviour that matters is what happens when the game loads one. In order:

  1. The first object that refers to sword.tres causes the engine to load it. One object now exists in memory.
  2. The engine remembers it in a cache, keyed by the file. Godot's documentation states this directly: loading a path that is already cached returns the same object.
  3. Every other enemy that refers to the same file gets a reference to that one object: an arrow, not a copy.

So "who owns the data?" has a clear answer. The asset owns it, and the enemies borrow it. Reading through any arrow gives the same values. Writing through any arrow changes the values for everyone.

Why share at all

Sharing is the point, not an accident. Fifty goblins need one copy of their stats, not fifty. A designer can tune the goblin in one file and every goblin in every level follows. Code that needs "the goblin's speed" asks the asset rather than a particular goblin. The engines' own types work the same way: textures, materials and meshes are shared between every object that uses them.

Breaking the link: a unique copy

When one object needs different values, give it a unique copy: a new object with the same values, owned by that one user.

  • Godot. In code, weapon.duplicate() returns a new resource with the exported properties copied. In the Inspector, the resource's drop-down menu has Make Unique. Ticking Local to Scene (the resource_local_to_scene property) tells Godot to duplicate the resource for every instance of a scene that uses it.
  • Unity. In code, Instantiate(weapon) makes a run-time copy of a ScriptableObject, just as it copies a GameObject. In the Editor, you duplicate the asset file itself to make a second asset. Unity's renderers show the same split built in: sharedMaterial is the shared asset, while reading material makes a copy for that renderer.

Both copies are shallow by default: numbers and strings are copied, but a resource or asset referenced inside the data is still shared. A weapon that refers to a projectile asset gets a new weapon pointing at the old projectile.

Design values here, live state there

The crossbow bug from the hook comes from storing run-time state, a value that changes during play for one object, in shared data. Ammo, current health and cooldown timers belong on the enemy. The data asset holds design values: maximum ammo, maximum health, cooldown length. The enemy copies the starting value when it spawns and changes its own copy from then on.

The Unity Play mode surprise

Component values in a scene snap back when you leave Play mode. ScriptableObject assets do not. Code that changes a shared asset while you test leaves those changes in your project. Neither engine is a save system: to keep data between sessions, write a save file, which is a later lesson.

Try it

Five enemies all start with a reference to sword.tres. The sliders edit whatever the selected enemy points at. Move the Damage slider and all five change. Now select E3, press Make unique, and move the slider again: only E3 changes, and the other four lose nothing.

Then press Selected enemy fires on E1. Ammo is stored in the shared data, so every enemy still linked to it loses a round. Tick Ammo lives on the enemy and fire again to see the fix.

The code

LÖVE has no data assets, but a Lua table assigned to several variables behaves exactly like one: every variable holds a reference to the same table. The model uses the demo's names and numbers. Keys 1 to 5 select an enemy, Up adds 5 damage, U makes a unique copy, S relinks to the shared sword, F fires and R reloads.

-- main.lua. Same data and numbers as the demo.
local AMMO_ON_ENEMY = false   -- true is the fix: live state stays on the enemy
local SWORD = { damage = 20, reach = 40, ammo = 6 }   -- the shared asset

local function makeUnique(data)   -- a shallow copy, like duplicate()
  local copy = {}
  for key, value in pairs(data) do copy[key] = value end
  return copy
end

local enemies = {}
for i = 1, 5 do
  enemies[i] = { name = "E" .. i, weapon = SWORD, ammo = SWORD.ammo }   -- a reference
end
local selected = 1

local function ammoOf(e)
  if AMMO_ON_ENEMY then return e.ammo end
  return e.weapon.ammo
end

function love.keypressed(key)
  local e = enemies[selected]
  local n = tonumber(key)
  if n and n >= 1 and n <= 5 then selected = n end
  if key == "up" then e.weapon.damage = e.weapon.damage + 5 end   -- reaches every sharer
  if key == "u" and e.weapon == SWORD then e.weapon = makeUnique(SWORD) end
  if key == "s" then e.weapon = SWORD end   -- the copy is now unreferenced
  if key == "f" and ammoOf(e) > 0 then
    if AMMO_ON_ENEMY then e.ammo = e.ammo - 1
    else e.weapon.ammo = e.weapon.ammo - 1 end   -- the bug: shared ammo
  end
  if key == "r" then
    SWORD.ammo = 6
    for _, other in ipairs(enemies) do other.weapon.ammo = 6; other.ammo = 6 end
  end
end

function love.draw()
  for i, e in ipairs(enemies) do
    local kind = (e.weapon == SWORD) and "sword (shared)" or "own copy"
    local mark = (i == selected) and "> " or "  "
    love.graphics.print(mark .. e.name .. "  " .. kind .. "  damage " .. e.weapon.damage ..
      "  reach " .. e.weapon.reach .. "  ammo " .. ammoOf(e), 10, i * 20)
  end
end
# weapon_data.gd. Godot 4.
# FileSystem dock: right-click, New Resource, WeaponData. Save it as sword.tres.
class_name WeaponData
extends Resource

@export var damage: int = 20
@export var reach: float = 40.0
@export var max_ammo: int = 6   # a design value, not live ammo


# enemy.gd. Drag sword.tres onto Weapon in the Inspector of each enemy.
extends Node2D

@export var weapon: WeaponData        # all enemies using sword.tres share one object
@export var unique_weapon := false    # tick on one enemy to give it its own copy

var ammo: int                         # live state belongs here

func _ready() -> void:
    if unique_weapon:
        weapon = weapon.duplicate()   # new object, unlinked from sword.tres
    ammo = weapon.max_ammo


# level.gd on the parent node of several enemies. Press Enter to test.
extends Node2D

func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed("ui_accept"):
        var first = get_child(0)
        first.weapon.damage += 5      # memory only: sword.tres on disk is untouched
        for enemy in get_children():
            print(enemy.name, " damage ", enemy.weapon.damage)
// WeaponData.cs. Unity 6 or 2022 LTS.
// Assets > Create > Game Dev Daily > Weapon Data, and name it Sword.
using UnityEngine;

[CreateAssetMenu(fileName = "WeaponData", menuName = "Game Dev Daily/Weapon Data")]
public class WeaponData : ScriptableObject
{
    public int damage = 20;
    public float reach = 40f;
    public int maxAmmo = 6;   // a design value, not live ammo
}


// Enemy.cs. Drag Sword onto Weapon on each enemy.
using UnityEngine;

public class Enemy : MonoBehaviour
{
    public WeaponData weapon;   // all enemies using Sword share one object
    public bool uniqueWeapon;   // tick on one enemy to give it its own copy
    int ammo;                   // live state belongs here

    void Awake()
    {
        if (uniqueWeapon)
            weapon = Instantiate(weapon);   // run-time copy; the asset is untouched
        ammo = weapon.maxAmmo;
    }

    void OnDestroy()
    {
        if (uniqueWeapon) Destroy(weapon);  // we made the copy, so we free it
    }

    // In Play mode, open this component's menu (three dots) to run it.
    [ContextMenu("Add 5 damage")]
    void AddDamage()
    {
        weapon.damage += 5;   // on a shared enemy, Sword.asset keeps this after Play mode
        foreach (Enemy e in FindObjectsByType<Enemy>(FindObjectsSortMode.None))
            Debug.Log(e.name + " damage " + e.weapon.damage);
    }
}

Each Unity class goes in its own file named after the class. FindObjectsByType is available in Unity 2022 LTS and Unity 6; older versions use FindObjectsOfType.

Pitfalls

  • Live state in shared data. Current health, ammo or a cooldown timer stored in the asset is shared by every user. Keep the maximum in the asset and the current value on the object.
  • Built-in sub-resources are shared too. In Godot, a material or shape created inside an enemy scene, not saved as its own file, is still one object shared by every instance of that scene. Changing a shader parameter on one enemy changes all of them unless the resource is Local to Scene or duplicated.
  • Shallow copies. duplicate() and Instantiate copy the top level. Nested resources and assets are still shared. In Godot 4, duplicate(true) also copies nested arrays and dictionaries, but resources saved as their own files are still not duplicated.
  • Duplicating in a hot path. Each copy is a new object. Making one per bullet defeats the reason to share. Copy only the objects that really differ.
  • Forgetting Unity's copies. A ScriptableObject made with Instantiate is an engine object. Destroy it when its owner goes away rather than relying on the C# garbage collector.
  • Treating the asset as a save file. In a build, nothing writes the change back. It works in Unity's editor, which makes it worse: it passes every test until you ship.

In real games

The engines use this pattern on themselves. Godot's textures, materials, meshes, themes and packed scenes are all resources, loaded once and shared by every node that refers to them. Unity's materials, meshes and textures are shared assets in the same way, and the material versus sharedMaterial pair on renderers is the "make unique" choice made in code.

Typical uses of custom data assets are item and enemy stat tables, dialogue lines, loot tables, level settings and audio presets. In Unity, ScriptableObjects are also used as shared channels between systems; Ryan Hipple's Unite 2017 talk popularised using them for shared variables and events. Godot's own documentation compares its resource scripts directly to Unity's ScriptableObjects.

Your turn (15 minutes)

Pick one kind of enemy or pickup in your project whose numbers are typed into each instance. Move those numbers into a WeaponData-style data asset and point every instance at it. Then add a unique tick box that duplicates the data in _ready or Awake.

You are done when changing the asset in the editor updates every instance, ticking the box on one instance and changing its copy at run time leaves the others alone, and no field in the asset changes while the game is running.

Takeaways

  • A data asset is loaded once and cached. Every object that refers to it holds a reference to the same object in memory.
  • Writing through any reference changes the data for all users. That is the feature when tuning, and the bug when one object needs to differ.
  • A unique copy (duplicate(), Make Unique or Local to Scene in Godot, Instantiate in Unity) breaks the link. It is shallow by default.
  • Keep design values in the asset and live state on the object.
  • Run-time changes to an asset do not survive a shipped game. In Unity's editor they do survive Play mode, so do not rely on either.

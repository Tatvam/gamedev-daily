The command pattern: undo, redo and replay from one idea

Wrap each player action in a command object that can execute and undo itself, and get undo, redo, replays and key remapping from one history list.

You add undo to a grid puzzle. It works until a player walks into a wall and presses undo: the piece jumps back a square it never left. Then someone asks for a replay, and the game has no record of what the player did.

Turn the action into a value

The usual first version changes the game the moment a key arrives:

if key == "left" then piece.x = piece.x - 1 end

The action happens and is gone. Nothing remembers it, so nothing can take it back or do it again.

A command is a small object that describes one action and knows how to carry it out. Instead of moving the piece, the input code builds a command such as "move by (-1, 0)" and hands it on. Its method execute does the work. Because the action is now a value, you can store it, inspect it and run it again. Everything else in this lesson comes from keeping those values around.

Undo: store what you need, not the reverse

Give each command a second method, undo, that puts the world back the way execute found it. The important question is what undo needs to know. The tempting answer is "do the opposite":

function cmd.undo()          -- tempting, and wrong
  newMove(-dx, -dy).execute()
end

This breaks whenever execute did not do exactly what was asked. A move into a wall changes nothing, but its opposite does. The reliable rule: execute records the state it is about to change, and undo restores that record.

function cmd.execute()
  cmd.fromX, cmd.fromY = piece.x, piece.y   -- remember first
  -- ...then try to move
end
function cmd.undo()
  piece.x, piece.y = cmd.fromX, cmd.fromY
end

This answers the ownership question. The piece still owns its position. The command owns a copy of the old position, and only for as long as the command lives in the history.

The history and the cursor

Commands go into an ordered list, the history, with a number called the cursor: how many commands, counted from the start, are applied right now.

  • Run a new command: execute it, put it just after the cursor, move the cursor forward one.
  • Undo: call undo on the command at the cursor, then move the cursor back one. The command stays in the list.
  • Redo: move the cursor forward one and call execute on that command again.

Commands after the cursor can be redone. If the player undoes twice and then makes a new move, those two no longer describe a possible future, so the new command deletes them first. That is why editors lose your redo steps when you type after undoing.

Replay and remapping come free

A replay is the history played again: reset the world to its starting state, then execute the applied commands in order. It only works if every command is deterministic: given the same state, it does the same thing. A command that rolls a random number inside execute will roll differently on the second run, so store the roll in the command.

Remapping is the other end. Only the key map knows which key makes which command, so changing controls means changing one table. The commands and the history never hear about keys.

What the engines give you

Godot 4 ships a general undo history as the UndoRedo class. You call create_action, register a do step and an undo step with add_do_method and add_undo_method (each takes a Callable, so you bind the values you need), then commit_action, which runs the do step. undo() and redo() move through the history, and the max_steps property limits its length. You still decide what to store: bind the old value when you create the action. It extends Object, not RefCounted, so free it yourself, and it has no replay.

Unity has an Undo class, but it lives in the UnityEditor namespace and only works in the editor, not in a built game. For gameplay you write the command list yourself in plain C#.

The trade-off

The alternative to commands is snapshots: save a copy of the whole state after each action and restore a copy to undo. Snapshots are simple and cannot get undo wrong, but cost memory per step. Commands are tiny and replay well, but every undo must be written correctly. Small states suit snapshots; large worlds suit commands.

The code

The Lua version is the demo with the drawing simplified: the same walls, the same start square, the same 0.3 second replay. A command is a table with two functions that close over dx and dy.

local COLS, ROWS = 7, 5
local START = { x = 1, y = 1 }
local WALLS = { ["3,1"] = true, ["3,2"] = true, ["3,3"] = true,
                ["5,3"] = true, ["5,4"] = true, ["5,5"] = true }
local piece = { x = START.x, y = START.y }
local history = {}   -- every command, in order
local cursor = 0     -- how many of them are applied now

local function blocked(x, y)
  return x < 1 or x > COLS or y < 1 or y > ROWS or WALLS[x .. "," .. y]
end

local function newMove(dx, dy)
  local cmd = {}
  function cmd.execute()
    cmd.fromX, cmd.fromY = piece.x, piece.y   -- what undo will need
    if not blocked(piece.x + dx, piece.y + dy) then
      piece.x, piece.y = piece.x + dx, piece.y + dy
    end
  end
  function cmd.undo()
    piece.x, piece.y = cmd.fromX, cmd.fromY
  end
  return cmd
end

local function run(cmd)
  for i = #history, cursor + 1, -1 do history[i] = nil end   -- drop redo tail
  cmd.execute()
  cursor = cursor + 1
  history[cursor] = cmd
end

local function undo()
  if cursor > 0 then history[cursor].undo(); cursor = cursor - 1 end
end

local function redo()
  if cursor < #history then cursor = cursor + 1; history[cursor].execute() end
end

local replaying, replayIndex, replayTimer = false, 0, 0
local function replay()
  piece.x, piece.y = START.x, START.y
  replaying, replayIndex, replayTimer = cursor > 0, 0, 0
end

-- Remapping means editing this table and nothing else.
local keymap = { up = {0, -1}, down = {0, 1}, left = {-1, 0}, right = {1, 0} }

function love.keypressed(key)
  if replaying then return end
  local dir = keymap[key]
  if dir then run(newMove(dir[1], dir[2]))
  elseif key == "z" then undo()
  elseif key == "y" then redo()
  elseif key == "r" then replay() end
end

function love.update(dt)
  if not replaying then return end
  replayTimer = replayTimer + dt
  if replayTimer >= 0.3 then
    replayTimer = replayTimer - 0.3
    replayIndex = replayIndex + 1
    history[replayIndex].execute()
    replaying = replayIndex < cursor
  end
end

function love.draw()
  local size = 48
  for y = 1, ROWS do
    for x = 1, COLS do
      local mode = WALLS[x .. "," .. y] and "fill" or "line"
      love.graphics.rectangle(mode, x * size, y * size, size - 2, size - 2)
    end
  end
  love.graphics.circle("fill", (piece.x + 0.5) * size - 1, (piece.y + 0.5) * size - 1, size * 0.3)
end
# grid_undo.gd. Godot 4. Attach to a Node2D in a new scene and run.
# Arrows move, Z undoes, Y redoes. Uses the built-in UndoRedo class.
extends Node2D

const CELL := 48
const COLS := 7
const ROWS := 5
const WALLS := [Vector2i(3, 1), Vector2i(3, 2), Vector2i(3, 3),
                Vector2i(5, 3), Vector2i(5, 4), Vector2i(5, 5)]

var piece := Vector2i(1, 1)
var undo_redo := UndoRedo.new()
var keymap := {
    KEY_UP: Vector2i(0, -1), KEY_DOWN: Vector2i(0, 1),
    KEY_LEFT: Vector2i(-1, 0), KEY_RIGHT: Vector2i(1, 0),
}

func _exit_tree() -> void:
    undo_redo.free()   # UndoRedo is an Object, not RefCounted

func set_piece(cell: Vector2i) -> void:
    piece = cell
    queue_redraw()

func blocked(cell: Vector2i) -> bool:
    return cell.x < 1 or cell.x > COLS or cell.y < 1 or cell.y > ROWS or cell in WALLS

func _unhandled_input(event: InputEvent) -> void:
    var key := event as InputEventKey
    if key == null or not key.pressed or key.echo:
        return
    if keymap.has(key.keycode):
        var to: Vector2i = piece + keymap[key.keycode]
        if blocked(to):
            to = piece
        undo_redo.create_action("Move")
        undo_redo.add_do_method(set_piece.bind(to))
        undo_redo.add_undo_method(set_piece.bind(piece))   # old value, bound now
        undo_redo.commit_action()   # runs the do method
    elif key.keycode == KEY_Z:
        undo_redo.undo()
    elif key.keycode == KEY_Y:
        undo_redo.redo()

func _draw() -> void:
    for y in range(1, ROWS + 1):
        for x in range(1, COLS + 1):
            var wall := Vector2i(x, y) in WALLS
            draw_rect(Rect2(x * CELL, y * CELL, CELL - 2, CELL - 2),
                    Color(0.5, 0.5, 0.5) if wall else Color(0.2, 0.2, 0.2))
    draw_rect(Rect2(piece.x * CELL + 8, piece.y * CELL + 8, CELL - 18, CELL - 18),
            Color(0.3, 0.6, 1.0))
// GridPiece.cs. Unity 6 or 2022 LTS with the Input System package.
// Create a Cube, add this script, press Play. Arrows move, Z undoes, Y redoes.
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.InputSystem;

public interface ICommand { void Execute(); void Undo(); }

public class MoveCommand : ICommand
{
    readonly GridPiece piece;
    readonly Vector2Int dir;
    Vector2Int from;

    public MoveCommand(GridPiece piece, Vector2Int dir) { this.piece = piece; this.dir = dir; }
    public void Execute() { from = piece.cell; piece.TryMove(dir); }
    public void Undo() { piece.cell = from; }
}

public class GridPiece : MonoBehaviour
{
    public Vector2Int cell = new Vector2Int(1, 1);
    readonly List<ICommand> history = new List<ICommand>();
    int cursor;   // how many commands are applied now

    static readonly HashSet<Vector2Int> walls = new HashSet<Vector2Int> {
        new Vector2Int(3, 1), new Vector2Int(3, 2), new Vector2Int(3, 3),
        new Vector2Int(5, 3), new Vector2Int(5, 4), new Vector2Int(5, 5) };

    public void TryMove(Vector2Int dir)
    {
        var to = cell + dir;
        if (to.x >= 1 && to.x <= 7 && to.y >= 1 && to.y <= 5 && !walls.Contains(to)) cell = to;
    }

    void Run(ICommand cmd)
    {
        history.RemoveRange(cursor, history.Count - cursor);   // drop redo tail
        cmd.Execute();
        history.Add(cmd);
        cursor++;
    }

    void Update()
    {
        var kb = Keyboard.current;
        if (kb == null) return;
        if (kb.upArrowKey.wasPressedThisFrame) Run(new MoveCommand(this, new Vector2Int(0, -1)));
        if (kb.downArrowKey.wasPressedThisFrame) Run(new MoveCommand(this, new Vector2Int(0, 1)));
        if (kb.leftArrowKey.wasPressedThisFrame) Run(new MoveCommand(this, new Vector2Int(-1, 0)));
        if (kb.rightArrowKey.wasPressedThisFrame) Run(new MoveCommand(this, new Vector2Int(1, 0)));
        if (kb.zKey.wasPressedThisFrame && cursor > 0) { cursor--; history[cursor].Undo(); }
        if (kb.yKey.wasPressedThisFrame && cursor < history.Count) { history[cursor].Execute(); cursor++; }
        transform.position = new Vector3(cell.x, -cell.y, 0f);   // grid y grows downwards
    }
}

The C# list counts from 0, so "the command at the cursor" is history[cursor - 1]; that is why undo decrements first and redo increments last. In Godot the old position is captured by bind at the moment the action is created, which plays the same role as fromX and fromY.

Pitfalls

  • Undoing by reversing the input. Blocked, clamped or random actions do not reverse cleanly. Record the old state in execute and restore it in undo.
  • Commands that hold freed objects. A command referencing an enemy breaks once that enemy is freed. To undo "destroy", keep the object alive while the command can be undone, or store a stable ID and recreate it. Godot's add_do_reference and add_undo_reference exist for this case.
  • Non-deterministic commands. Random numbers, frame time or input read inside execute make replays drift. Decide the value once and store it in the command.
  • History that grows forever. Cap it (Godot's max_steps, or drop the oldest entry yourself). Once old commands are gone, a replay can no longer start from the beginning, so keep a snapshot of the state at the new oldest point.
  • Recording moves that did nothing. The demo records bumps into walls so you can see the bug. Many puzzle games skip them so undo never wastes a press.
  • Input during replay. If new commands can be run while a replay is playing, they land in the middle of the history. Block input or finish the replay first, as the Lua code does.

In real games

Grid puzzle games are the clearest case: Baba Is You lets the player undo every move back to the start of a level. Level editors depend on undo in the same way, and both engines' own editors keep an undo history; in Godot 4, editor plugins add to it through EditorUndoRedoManager.

Real-time strategy games are the large-scale example. The Age of Empires developers described a networking model in which each machine sends player commands rather than the state of every unit, and every machine runs the same commands on the same turn. Command-based replay files follow from the same idea, though how any particular game stores its replays is not something this lesson has checked.

Your turn (15 minutes)

Pick one discrete action in your project, such as placing a tile, moving a unit one square or buying an item. Wrap it in a command with execute and undo, route input through a history with a cursor, and bind undo and redo to two keys. You are done when three actions, three undos and three redos leave the game exactly as it was after the third action, and undoing a blocked action changes nothing.

Takeaways

  • A command turns an action into a value with execute and undo, so it can be stored, undone and run again.
  • execute records the state it changes; undo restores that record. Never undo by running the opposite input.
  • A history list plus a cursor gives undo and redo. A new command deletes everything after the cursor.
  • Replay is "reset, then execute in order", which only works when commands are deterministic. Remapping is just a different key map.
  • Godot 4 provides UndoRedo for runtime use; in Unity the built-in Undo is editor only, so gameplay undo is your own list.

Nodes in Godot, GameObjects and components in Unity

How Godot builds a player from a tree of specialised nodes while Unity stacks components on one GameObject, and who owns the data in each.

You follow a Unity tutorial in Godot and look for the place to "add a component". There is no such button, only Add Child Node. Or you go the other way, open Unity, and wonder why your player's collider is not a child of anything. The two engines answer "what is a game object made of?" in different shapes, and fighting the shape causes most of the friction.

Four parts, two shapes

Forget engines for a moment. A walking player needs four things: a place in the world (position, rotation, scale, together called its transform), something that draws it, a shape for collisions, and behaviour, the code that makes it walk and take damage. Every engine has these parts. The difference is where they live.

Godot: a tree of nodes

In Godot everything in a scene is a node: an object of a specific built-in type that does one job. A Sprite2D draws a texture. A CollisionShape2D holds a shape. A CharacterBody2D is a physics body you move from code. You build an object by arranging nodes in a tree: the root node's type says what the object is, and its children add parts.

A node can carry at most one script, and that script extends the node's type. So player.gd on a CharacterBody2D root is a character body with extra code. A second piece of behaviour, such as health, goes on a child node with its own script.

Unity: one GameObject, many components

In Unity a GameObject is a generic container. On its own it does nothing except hold a Transform, which every GameObject has and cannot remove. Abilities come from components attached to it: a SpriteRenderer draws, a BoxCollider2D provides a shape, a Rigidbody2D makes it a physics body. Your scripts are components too (classes derived from MonoBehaviour), and one GameObject can carry as many as you like.

Written as plain data, the difference is a tree versus a list:

-- Godot: nodes, each with a type, at most one script, and children
local godotPlayer = {
  name = "Player", type = "CharacterBody2D", script = "player.gd",
  children = {
    { name = "Sprite2D", type = "Sprite2D" },
    { name = "CollisionShape2D", type = "CollisionShape2D" },
    { name = "Health", type = "Node", script = "health.gd" },
  },
}
-- Unity: one object, a flat list of components
local unityPlayer = {
  name = "Player",
  components = { "Transform", "Rigidbody2D", "SpriteRenderer",
                 "BoxCollider2D", "PlayerMover", "Health" },
}

Both engines also have the other shape. Unity GameObjects can have child GameObjects when a part needs its own transform, such as a held weapon. Godot has plain Node children with no transform, used only to hold logic. What differs is the default.

Ordering and ownership

QuestionGodotUnity
Where does the position live?On each 2D or 3D node itself. Children are placed relative to their parent.In the one Transform component, shared by every component on the GameObject.
Who owns the parts?The parent owns its children. Freeing a node frees its whole subtree.The GameObject owns its components and child GameObjects. Destroying it destroys all of them.
How does code find a part?By path in the tree: $Sprite2D or get_node("Sprite2D").By type on the object: GetComponent<SpriteRenderer>().
Who is updated first?Nodes are processed in tree order, top to bottom, unless you change a node's process_priority.The order of Update between different scripts is not guaranteed unless you set it in the Script Execution Order settings.

Rule of thumb

In Godot, ask "what is this object?" and choose the root type, then add children for its parts. In Unity, ask "what can this object do?" and add one component per ability.

Neither shape is better. Godot's tree shows an object's structure at a glance and gives every part its own transform, but its paths must stay stable. Unity's list makes abilities cheap to add and lookups independent of layout, but parts that need their own transform become extra GameObjects.

The code

The Lua version builds the idea yourself in LÖVE: an entity is a table with a position and a list of components, and the loop asks each component to update and draw. It uses the same numbers as the demo: 60 pixels per second, 80 pixels each way, a 28 by 36 box and 3 hit points. Press H to hit the player.

local player = { x = 200, y = 160, components = {} }

local function add(entity, c)
  c.entity = entity
  table.insert(entity.components, c)
end

local function get(entity, kind)   -- like GetComponent, by kind
  for _, c in ipairs(entity.components) do
    if c.kind == kind then return c end
  end
end

local function rect(c, mode)       -- a 28 x 36 box standing on y
  local e = c.entity
  love.graphics.rectangle(mode, e.x - 14, e.y - 36, 28, 36)
end

add(player, { kind = "sprite", draw = function(c) rect(c, "fill") end })
add(player, { kind = "collider", draw = function(c) rect(c, "line") end })
add(player, { kind = "mover", speed = 60, range = 80, dir = 1, home = player.x,
  update = function(c, dt)
    local e = c.entity
    e.x = e.x + c.dir * c.speed * dt
    if e.x > c.home + c.range then c.dir = -1
    elseif e.x < c.home - c.range then c.dir = 1 end
  end })
add(player, { kind = "health", hp = 3 })

function love.update(dt)
  for _, c in ipairs(player.components) do
    if c.update then c:update(dt) end
  end
end

function love.draw()
  for _, c in ipairs(player.components) do
    if c.draw then c:draw() end
  end
end

function love.keypressed(key)
  local health = get(player, "health")
  if key == "h" and health then
    health.hp = health.hp - 1
    if health.hp <= 0 then health.hp = 3 end
  end
end
# player.gd (Godot 4). Make a scene whose root is a CharacterBody2D,
# place it in view, attach this script, and save health.gd beside it.
extends CharacterBody2D

const SPEED := 60.0
const RANGE := 80.0
var home_x := 0.0
var dir := 1.0

func _ready() -> void:
    home_x = position.x
    var sprite := Sprite2D.new()            # a child node that draws
    sprite.texture = load("res://icon.svg")
    add_child(sprite)
    var shape := CollisionShape2D.new()     # a child node that gives the body a shape
    var box := RectangleShape2D.new()
    box.size = Vector2(28, 36)
    shape.shape = box
    add_child(shape)
    var health: Node = preload("res://health.gd").new()  # second script, own node
    health.name = "Health"
    add_child(health)

func _physics_process(delta: float) -> void:
    velocity = Vector2(dir * SPEED, 0)
    move_and_slide()
    if position.x > home_x + RANGE: dir = -1.0
    elif position.x < home_x - RANGE: dir = 1.0
    if Input.is_action_just_pressed("ui_accept"):
        $Health.hit()                       # found by path

// PlayerMover.cs (Unity 6 or 2022 LTS). Add it to an empty GameObject and press Play.
// The SpriteRenderer draws nothing until you give it a sprite in the Inspector.
using UnityEngine;

[RequireComponent(typeof(Rigidbody2D))]
public class PlayerMover : MonoBehaviour
{
    const float Speed = 0.6f;   // world units per second: 60 px at 100 pixels per unit
    const float Range = 0.8f;
    Rigidbody2D body;
    float homeX;
    float dir = 1f;

    void Awake()
    {
        body = GetComponent<Rigidbody2D>();        // found by type
        body.bodyType = RigidbodyType2D.Kinematic;
        gameObject.AddComponent<SpriteRenderer>();
        var box = gameObject.AddComponent<BoxCollider2D>();
        box.size = new Vector2(0.28f, 0.36f);
        gameObject.AddComponent<Health>();         // second script, same GameObject
        homeX = body.position.x;
    }

    void FixedUpdate()
    {
        Vector2 p = body.position;
        p.x += dir * Speed * Time.fixedDeltaTime;
        if (p.x > homeX + Range) dir = -1f;
        else if (p.x < homeX - Range) dir = 1f;
        body.MovePosition(p);
    }
}

The highlighted lines are the whole lesson: three add_child calls leave Godot with four nodes, while three AddComponent calls leave Unity with one GameObject. Normally you would build both in the editor; code just makes the structure explicit.

Pitfalls

  • Hard-coded node paths in Godot. $Sprite2D breaks the moment someone renames the node or moves it under another parent. For parts you reach often, export a variable and assign it in the Inspector, or mark the node as a scene unique name and reach it with %Name.
  • A shape in the wrong place in Godot. A CollisionShape2D only gives a shape to its direct parent, which must be a physics body or area. Anywhere else, the editor shows a warning and nothing collides.
  • One giant script in Godot. The root takes one script, so it is tempting to pile everything into it. Split separate concerns into child nodes with their own scripts.
  • Calling GetComponent every frame in Unity. It is a lookup, not a field read. Fetch the component once in Awake and keep it in a field, as PlayerMover does.
  • Assuming a component is there in Unity. GetComponent returns null when the component is missing, and the error appears later, far away. [RequireComponent] makes Unity add the dependency for you.
  • Moving a collider that has no body in Unity. A collider without a Rigidbody2D is treated as static scenery. If it moves, give it a Rigidbody2D (Kinematic is fine) so the physics engine knows to expect motion.

In real games

Every Unity scene is built this way: even an "empty" GameObject has a Transform, and the Inspector is the list of components on the selected object. Unity's separate Entities package works differently and gets its own lesson later.

Godot's editor is itself a Godot application built from the same node types, mostly Control nodes for the interface, so the tree you edit games with is made of the same tree you put in them. Its developers have written about choosing node composition over an entity component system (see Further reading).

Your turn (15 minutes)

Take one object from your project, such as the player, and draw it on paper in the other engine's shape. From Godot: list the Unity components, and mark which child nodes must stay child GameObjects because they need their own transform. From Unity: pick the Godot root type, then place each component as a child node or in the root script.

You are done when every part of the object has a place in both drawings, and you can say for each one where its position lives.

Takeaways

  • Both engines give an object a transform, something that draws, a shape and behaviour. Only the arrangement differs.
  • Godot: a tree of typed nodes. The root type says what the object is, and each node has at most one script.
  • Unity: a generic GameObject with a Transform, plus any number of components, scripts included.
  • Godot code finds parts by path and processes them in tree order. Unity code finds them by type, and update order between scripts is yours to set.
  • In both, destroying the owner destroys everything it holds.

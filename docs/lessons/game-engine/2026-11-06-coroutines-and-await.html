Coroutines in Unity, await in Godot

How a function can pause and continue on a later frame, who resumes it, when in the frame, and what happens when its owner is destroyed.

You pull a lever. A lamp lights, half a second later a door slides open, it waits, then slides shut. Four steps that take three and a half seconds, but update only gets one frame at a time. So the four steps end up spread across a timer variable, a step counter and an if ladder, and nobody can read the sequence any more.

The sequence, chopped into frames

Here is the door written the usual way, as a small state machine inside update:

local step, timer = "idle", 0

function love.update(dt)
  timer = timer + dt
  if step == "lamp" and timer >= 0.5 then
    step, timer = "opening", 0
  elseif step == "opening" then
    door.open = math.min(timer / 1.0, 1)
    if timer >= 1.0 then step, timer = "holding", 0 end
  elseif step == "holding" and timer >= 1.0 then
    step, timer = "closing", 0
  end   -- ...and closing, and turning the lamp off
end

It works, but the order of events is no longer visible from top to bottom.

A function that can pause

A coroutine is a function that can stop part way through, hand control back to whoever called it, and later carry on from the same line. Stopping is called yielding (Godot calls it awaiting); carrying on is resuming. While it is paused, its local variables and its whole call stack are kept, so a loop counter in a helper function is still there next frame.

With that, the door reads like the design note:

local function useSwitch()
  lamp.on = true
  wait(0.5)            -- pause here; resume in half a second
  slide(0, 1, 1.0)     -- this helper pauses once per frame
  wait(1.0)
  slide(1, 0, 1.0)
  lamp.on = false
end

A coroutine cannot resume itself. Something outside it has to keep a list of paused coroutines and, every frame, check what each one is waiting for and resume the ones that are ready. That something is the scheduler. In LÖVE you write it yourself in about fifteen lines (see the code below). Godot and Unity each have one built in.

Who resumes it, and when in the frame

Two ordering facts matter. First, starting a coroutine runs it immediately, inside the call that started it, up to its first pause. Unity's StartCoroutine does this, and so does calling a Godot function that contains await. Second, each engine resumes paused code at a fixed point in its frame, and the two engines chose different points.

This is why "wait one frame" is not quite the same in both. In Unity, code after yield return null sees this frame's Update results. In Godot, code after await get_tree().process_frame runs before this frame's _process.

Who owns a paused coroutine

A paused coroutine holds a call stack, so something must own it and decide when it dies.

Unity ties each coroutine to the MonoBehaviour that called StartCoroutine. It stops when that GameObject is deactivated or destroyed, or when you call StopCoroutine with the returned Coroutine handle, or StopAllCoroutines. Disabling only the component (enabled = false) does not stop it. Unity 6 adds a second style, async methods that await Awaitable.NextFrameAsync() or Awaitable.WaitForSecondsAsync(seconds); these are not tied to the object in the same way, which is what destroyCancellationToken is for. Awaitable is not in 2022 LTS.

Godot 4 gives you no handle. The paused function waits on a signal. If its object is freed before the signal arrives, the rest of the function never runs; when the signal comes from something that outlives the node, such as a scene tree timer, a debug build prints an error saying the instance is gone. To cancel a sequence on purpose, check a flag or a counter after each await.

The trade-off

Unity's coroutines are values you can stop from outside, at the cost of extra bookkeeping (handles, and the enabled versus active difference). Godot's await works on any signal with no extra types, but cancelling is your job.

Try it

This is a tiny scheduler running the useSwitch coroutine at 10 frames per second. Press the switch, then press Next frame and watch the shaded line: that is where the function is paused. During a slide, a hollow marker also stays on the line that called slide, because the whole call stack is kept.

Then try the two ways it breaks. Turn off Ignore presses while the lamp is on and press twice: two coroutines write door.open every frame and the door jumps. Or press Destroy switch while the door is moving: its coroutine dies with it and the door is left half open.

The code

Lua has coroutines built into the language: coroutine.create, coroutine.resume and coroutine.yield. A value passed to yield comes out of resume, and the other way round. Here a coroutine yields how many seconds it wants to sleep, and the scheduler passes dt back in. This is a complete LÖVE program; Space presses the switch.

local door = { open = 0 }        -- 0 closed, 1 fully open
local lamp = { on = false }
local tasks = {}                 -- paused coroutines

local function wait(secs) coroutine.yield(secs) end
local function nextFrame() return coroutine.yield(0) end   -- returns dt

local function slide(a, b, secs)
  local t = 0
  while t < secs do
    t = t + nextFrame()
    local k = math.min(t / secs, 1)
    door.open = a + (b - a) * k
  end
end

local function useSwitch()
  lamp.on = true
  wait(0.5)
  slide(0, 1, 1.0)
  wait(1.0)
  slide(1, 0, 1.0)
  lamp.on = false
end

local function start(fn)
  local task = { co = coroutine.create(fn), wait = 0 }
  local ok, secs = coroutine.resume(task.co)   -- runs now, up to the first yield
  assert(ok, secs)
  if coroutine.status(task.co) ~= "dead" then
    task.wait = secs
    tasks[#tasks + 1] = task
  end
end

function love.keypressed(key)
  if key == "space" and not lamp.on then start(useSwitch) end
end

function love.update(dt)
  local running = tasks
  tasks = {}                     -- coroutines started this frame land here
  for _, task in ipairs(running) do
    task.wait = task.wait - dt
    if task.wait <= 0 then
      local ok, secs = coroutine.resume(task.co, dt)   -- continue after its yield
      assert(ok, secs)
      task.wait = secs
    end
    if coroutine.status(task.co) ~= "dead" then tasks[#tasks + 1] = task end
  end
end

function love.draw()
  if lamp.on then love.graphics.setColor(1, 0.8, 0.2) else love.graphics.setColor(0.4, 0.4, 0.4) end
  love.graphics.circle("fill", 60, 60, 10)
  love.graphics.setColor(1, 1, 1)
  love.graphics.rectangle("line", 300, 300, 120, 180)
  love.graphics.setColor(0.6, 0.4, 0.2)
  love.graphics.rectangle("fill", 300, 300 - door.open * 180, 120, 180)
end
# switch_door.gd. Godot 4. Attach to a Node2D in a new scene and run.
# Enter or Space (the ui_accept action) presses the switch.
extends Node2D

var door_open := 0.0   # 0 closed, 1 fully open
var lamp_on := false

func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed("ui_accept") and not lamp_on:
        use_switch()   # no await: runs to its first await, then returns here

func use_switch() -> void:
    lamp_on = true
    queue_redraw()
    await get_tree().create_timer(0.5).timeout
    await slide(0.0, 1.0, 1.0)
    await get_tree().create_timer(1.0).timeout
    await slide(1.0, 0.0, 1.0)
    lamp_on = false
    queue_redraw()

func slide(a: float, b: float, secs: float) -> void:
    var t := 0.0
    while t < secs:
        await get_tree().process_frame   # wakes just before _process
        t += get_process_delta_time()
        door_open = a + (b - a) * minf(t / secs, 1.0)
        queue_redraw()

func _draw() -> void:
    draw_circle(Vector2(60, 60), 10, Color(1, 0.8, 0.2) if lamp_on else Color(0.4, 0.4, 0.4))
    draw_rect(Rect2(300, 300, 120, 180), Color(1, 1, 1), false)
    draw_rect(Rect2(300, 300 - door_open * 180, 120, 180), Color(0.6, 0.4, 0.2))
// SwitchDoor.cs. Unity 6 or 2022 LTS with the Input System package.
// Create a Cube, add this script, press Play, then press Space. The cube is the door.
using System.Collections;
using UnityEngine;
using UnityEngine.InputSystem;

public class SwitchDoor : MonoBehaviour
{
    float doorOpen;      // 0 closed, 1 fully open
    Coroutine running;   // null while idle; also lets you StopCoroutine(running)

    void Update()
    {
        var kb = Keyboard.current;
        if (kb != null && kb.spaceKey.wasPressedThisFrame && running == null)
            running = StartCoroutine(UseSwitch());   // runs to the first yield now
    }

    IEnumerator UseSwitch()
    {
        Debug.Log("lamp on");
        yield return new WaitForSeconds(0.5f);
        yield return StartCoroutine(Slide(0f, 1f, 1f));
        yield return new WaitForSeconds(1f);
        yield return StartCoroutine(Slide(1f, 0f, 1f));
        Debug.Log("lamp off");
        running = null;
    }

    IEnumerator Slide(float a, float b, float secs)
    {
        float t = 0f;
        while (t < secs)
        {
            yield return null;   // next frame, after every Update
            t += Time.deltaTime;
            doorOpen = a + (b - a) * Mathf.Min(t / secs, 1f);
            transform.position = new Vector3(0f, doorOpen * 2f, 0f);
        }
    }
}

The Lua scheduler swaps in a fresh list each frame, so a coroutine started during the loop does not also get resumed in the same frame. Both engine versions use a "running" check for the same job as not lamp.on.

Pitfalls

  • Starting the same sequence twice. Each start makes a new, independent coroutine. Two of them write the same field every frame, and the last one to run wins. Guard with a flag, or keep the handle and stop the old one first.
  • Disabled is not deactivated (Unity). enabled = false leaves coroutines running; SetActive(false) and Destroy stop them. Calling StartCoroutine on an inactive GameObject fails with an error.
  • Timers that ignore pause (Godot). create_timer has a process_always parameter that defaults to true, so the timer keeps counting while the tree is paused. Pass false for gameplay waits.
  • Forgetting await (Godot). Calling a function that awaits, without await, returns at its first pause. The lines after the call run before the sequence has finished.
  • Waits round up to a frame. A wait ends on the first frame at or after its time, so each wait can overshoot by up to one frame. Ten chained waits drift. For timing that must be exact, keep one running clock and compare against it.
  • Garbage per wait (Unity). new WaitForSeconds(...) allocates an object each time. In a coroutine that loops forever, create it once and reuse it.

In real games

Coroutines are a common way to script cutscenes, tutorial prompts, dialogue sequences and timed spawns, anywhere a designer thinks in steps rather than in frames. Coroutines have been part of the Lua language itself since version 5.0, so Lua scripts get them without any engine support. Godot 3 offered the same idea with a yield function; Godot 4 replaced it with the await keyword. Unity's coroutines are built on C# iterators (IEnumerator and yield return).

Take one timed sequence in your project that lives in update as a timer and a step variable, for example a spawn wave or a "ready, set, go" countdown, and rewrite it as a single coroutine. Takeaways

  • A coroutine is a function that can pause and later continue from the same line, keeping its locals and call stack.
  • Starting one runs it immediately up to its first pause; after that a scheduler resumes it once per frame when its wait is over.
  • Unity resumes yield return null after every Update; Godot resumes await get_tree().process_frame just before _process.
  • The owner decides the coroutine's life: in Unity the GameObject that started it, in Godot the object whose function is paused. Cancelling is explicit in Unity and up to you in Godot.

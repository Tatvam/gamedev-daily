Lifecycle callbacks: _ready and _process, Awake, Start and Update

The order in which Godot and Unity call your code when an object is created, added, updated and removed, and which data is safe to touch in each call.

You spawn an enemy and set its speed straight after, but the enemy prints the old speed when it starts. Or a parent script reaches for a child and gets null. The code is correct line by line. It just runs at a moment you did not expect.

The engine calls you

A lifecycle callback is a function you write and the engine calls at a particular moment in an object's life. The engine owns the timing; your script owns the data. The question in every callback is which data already exists at that moment: your own fields, your children, other objects, values set by the code that spawned you.

Every engine has the same four moments, under different names:

  1. Create. The object exists in memory but may not be part of the running world yet.
  2. Enter the world. It joins the scene and can find its neighbours.
  3. Tick. It is updated once per frame until it goes away.
  4. Leave. It is removed, and gets one last chance to clean up.

Godot: the tree decides the order

_init runs when the node object is constructed, for example inside instantiate(). The node is not in the scene tree yet, so it cannot look anything up.

When you call add_child on a parent that is already in the running tree, two passes run before add_child returns. First _enter_tree walks the new branch top-down: the parent, then its children. Then _ready walks it bottom-up: every child is ready before its parent. That second rule is deliberate. When a parent's _ready runs, all its children are already set up, so the parent can safely configure them. Variables marked @onready are filled in just before that node's _ready.

Each frame, _process runs in tree order, top to bottom as the editor shows it (a pre-order traversal: a node, then each of its children's branches in turn). You can change this with the node's process_priority: lower values run first, whatever the tree says. When a branch is removed, _exit_tree runs children first and the parent last. The Godot 4 source visits the children last child first.

Weapon (second child)3231

_ready runs once per node. Removing a node and adding it again calls _enter_tree again but not _ready, unless you call request_ready() first.

Unity: two phases instead of a tree

Unity's rules are the same in Unity 6 and 2022 LTS. Awake runs when the script instance is created: when the scene loads, or inside Instantiate before it returns. It runs even if the component itself is disabled, but not while its GameObject is inactive. OnEnable follows straight after, and runs again every time the component is re-enabled.

Start runs later, just before that script's first Update, and only if the component is enabled. Then Update runs every frame, and LateUpdate runs after all the Update calls of that frame.

The big difference from Godot: Unity does not promise an order between GameObjects. Its documentation says you cannot rely on one object's Awake running before another's, and parent and child get no special treatment. What Unity does promise for objects loaded with a scene is that every Awake has run before any Start. That gives the standard rule: set up your own references in Awake, talk to other objects in Start. When you really need an order, the Script Execution Order page in Project Settings sets it per script class, not per object.

When an object is destroyed, each script gets OnDisable and then OnDestroy. Like Godot, Unity delays the removal until later in the frame. The next lesson is about why.

The gap where spawn code runs

In Godot, instantiate(), then your code sets speed, then add_child() runs _ready, which sees your value. In Unity, Instantiate() has already run Awake and OnEnable by the time your next line sets speed, so only Start sees it.

The code

In LÖVE there is no scene tree, so you would build the lifecycle yourself. This small model calls hooks in Godot's order, with the same names and numbers as the demo: create, set speed to 300, enter top-down, ready bottom-up, process two frames, then exit children first.

local log = {}
local function newNode(name)
  return { name = name, children = {}, speed = 100 }
end
local function call(node, hook, ...)
  log[#log + 1] = node.name .. "." .. hook
  if node[hook] then node[hook](node, ...) end
end

local function enterTree(node)    -- parent first, then children
  call(node, "enter_tree")
  for i = 1, #node.children do enterTree(node.children[i]) end
end

local function ready(node)        -- children first, then parent
  for i = 1, #node.children do ready(node.children[i]) end
  call(node, "ready")
end

local function process(node, dt)  -- tree order, every frame
  call(node, "process", dt)
  for i = 1, #node.children do process(node.children[i], dt) end
end

local function exitTree(node)     -- last child first, parent last
  for i = #node.children, 1, -1 do exitTree(node.children[i]) end
  call(node, "exit_tree")
end

local player = newNode("Player")  -- created, not in the tree yet
player.children = { newNode("Sprite"), newNode("Weapon") }
player.speed = 300                -- spawn code runs before ready
function player:ready() log[#log + 1] = "  sees speed " .. self.speed end

local frames = 0
function love.load() enterTree(player); ready(player) end

function love.update(dt)
  if not player then return end
  process(player, dt)
  frames = frames + 1
  if frames == 2 then exitTree(player); player = nil end  -- end of frame
end

function love.draw() love.graphics.print(table.concat(log, "\n"), 10, 10) end
# player.gd on the root of player.tscn (children: Sprite, Weapon). Godot 4.
extends Node2D

@export var speed := 100.0
@onready var weapon := $Weapon     # filled in just before _ready

func _init() -> void:
    print("Player._init")          # not in the tree, Inspector values not applied yet

func _enter_tree() -> void:
    print("Player._enter_tree")    # children have not entered yet

func _ready() -> void:
    print("Player._ready sees speed ", speed)   # 300: children are ready too

func _process(delta: float) -> void:
    position.x += speed * delta

func _exit_tree() -> void:
    print("Player._exit_tree")     # children have already left


# spawner.gd on any node in the main scene.
extends Node2D

const PLAYER := preload("res://player.tscn")

func _ready() -> void:
    var p = PLAYER.instantiate()   # _init runs for each node
    p.speed = 300.0                # _ready has not run yet
    add_child(p)                   # _enter_tree down, then _ready up
// Player.cs on the root of the Player prefab. Unity 6 and 2022 LTS.
using UnityEngine;

public class Player : MonoBehaviour
{
    public float speed = 100f;

    void Awake()     { Debug.Log("Player.Awake sees speed " + speed); }  // 100
    void OnEnable()  { Debug.Log("Player.OnEnable"); }
    void Start()     { Debug.Log("Player.Start sees speed " + speed); }  // 300
    void Update()    { transform.position += Vector3.right * speed * Time.deltaTime; }
    void OnDisable() { Debug.Log("Player.OnDisable"); }
    void OnDestroy() { Debug.Log("Player.OnDestroy"); }
}


// Spawner.cs on any GameObject in the scene. Drag the prefab onto Player Prefab.
using UnityEngine;

public class Spawner : MonoBehaviour
{
    public Player playerPrefab;

    void Start()
    {
        Player p = Instantiate(playerPrefab);  // Awake and OnEnable run in here
        p.speed = 300f;                        // too late for Awake, in time for Start
    }
}

Godot prints _ready sees speed 300. Unity prints Awake sees speed 100, then Start sees speed 300.

Pitfalls

  • A Godot child reaching up to its parent in _ready. The parent is in the tree, but its _ready has not run, so its @onready variables are still null. Let the parent configure its children in its own _ready, or have the child wait for the parent's ready signal.
  • A Unity script reading another object in Awake. That object's Awake may not have run. Find your own components in Awake, and read other objects in Start.
  • Expecting Awake to see values set after Instantiate. It has already run. Read them in Start, or pass them in through a method you call yourself.
  • Reading Inspector values in Godot's _init. Exported values from the scene file are applied after construction. Use _ready.
  • Relying on Update order between objects. Unity does not define it, and in Godot it changes when someone drags a node in the editor. If A must run before B, say so on purpose: process_priority in Godot, Script Execution Order in Unity, or one manager that updates both in a fixed order.
  • Expecting _ready or Start to run again. Both run once per object. Re-entering the tree or re-enabling a component calls _enter_tree or OnEnable again, which is where re-arming code belongs.

In real games

Every Godot and Unity game runs through these callbacks, and the same four moments appear in other engines. LÖVE gives you love.load, love.update, love.draw and love.quit for the whole game and leaves per-object lifecycles to you, which is what the Lua model builds. Unreal Engine actors have BeginPlay, Tick and EndPlay.

Takeaways

  • The engine owns the timing of every callback. Ask what data already exists at that moment.
  • Godot follows the tree: _enter_tree top-down, _ready bottom-up, _process in tree order, _exit_tree children first.
  • Unity uses two phases: every scene object's Awake runs before any Start, but the order between objects is not promised.
  • Values set right after spawning reach Godot's _ready and Unity's Start, but not Unity's Awake.
  • When order matters, set it on purpose instead of relying on what happens to work today.

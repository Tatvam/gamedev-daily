The scene tree and the transform hierarchy

How a child's local position, rotation and scale combine with its parent's to give its place in the world, and which values Godot and Unity store.

You make a gun a child of the player's hand, set its position to (0, 0), and it appears halfway across the level. Or you drop it out of the hand and it teleports. Nothing is broken: you set a value in one coordinate space while thinking in another.

Every node is measured from its parent

A transform is a position, a rotation and a scale together. In a scene tree each node has a local transform: where it sits, how it is turned and how big it is relative to its parent. For a node with no parent, local and global are the same.

The global transform (Unity says world) is where the node really ends up. The engine works it out by applying each local transform in turn from the root down. That is why moving a parent moves its children: their local values did not change, but what they are measured from did.

Combining one step

Take a parent whose global transform is known, and a child with local values. The child's global values are:

  1. Rotation adds. Child global rotation = parent rotation + child rotation.
  2. Scale multiplies. Child global scale = parent scale × child scale.
  3. Position is turned, stretched, then shifted. Rotate the child's local position by the parent's rotation, multiply it by the parent's scale, and add the parent's position.
-- one step down the tree (2D, uniform scale, angles in radians)
local c, s = math.cos(parent.rot), math.sin(parent.rot)
child.gx = parent.gx + parent.gscale * (c * child.x - s * child.y)
child.gy = parent.gy + parent.gscale * (s * child.x + c * child.y)
child.grot = parent.grot + child.rot
child.gscale = parent.gscale * child.scale

Repeat for every level. Engines store each transform as a matrix so one step is a single multiply, but the matrix holds exactly these three ideas.

A worked example

An arm has three nodes: Arm at the root, Forearm under it, and Hand under that. The canvas has y pointing down, so a positive rotation turns clockwise.

Arm has no parent, so its global position is its local (120, 170). Forearm's local (100, 0) is rotated by Arm's 0° and added: (220, 170), turned 30°. Hand's local (80, 0) is rotated by Forearm's 30°, giving (69.3, 40), and added: about (289.3, 210), turned 30° + 20° = 50°.

Now scale Arm to 1.5. Nothing below it changes its stored values, yet Forearm moves to (270, 170) and Hand to about (373.9, 230): every offset under Arm is stretched by 1.5.

Who owns the data, and in what order

The local values are the truth. The global values are derived. Engines cache them and refresh a node's copy when something above it has changed, so reading a global position does not always walk the whole tree; how they do this is internal and differs between Godot and Unity. Writing a global position works backwards: the engine solves for the local values that put the node there.

Reparenting forces a choice: keep the local numbers, so the node jumps to the same offset from its new parent, or keep the global transform, so it stays put while its local numbers are recomputed.

The naming trap

position is local in Godot and world in Unity. Code ported by swapping syntax alone puts children in the wrong place.

The code

The Lua version builds the hierarchy yourself in LÖVE, with the demo's names and numbers. toGlobal walks up to the root and combines on the way back down. reparent keeps the global transform. Left and right arrows rotate Arm; R moves Hand between Forearm and the world.

local function node(name, parent, x, y, deg, length)
  return { name = name, parent = parent, x = x, y = y,
           rot = math.rad(deg), scale = 1, length = length }
end
local arm     = node("Arm", nil, 120, 170, 0, 100)
local forearm = node("Forearm", arm, 100, 0, 30, 80)
local hand    = node("Hand", forearm, 80, 0, 20, 30)

-- Global = the parent's global transform applied to my local one.
local function toGlobal(n)
  if n.parent == nil then return n.x, n.y, n.rot, n.scale end
  local px, py, prot, pscale = toGlobal(n.parent)
  local c, s = math.cos(prot), math.sin(prot)
  return px + pscale * (c * n.x - s * n.y),
         py + pscale * (s * n.x + c * n.y),
         prot + n.rot, pscale * n.scale
end

-- Change parent, then solve for local values that keep n where it was.
local function reparent(n, parent)
  local gx, gy, grot, gscale = toGlobal(n)
  n.parent = parent
  local px, py, prot, pscale = 0, 0, 0, 1      -- the world
  if parent then px, py, prot, pscale = toGlobal(parent) end
  local c, s = math.cos(prot), math.sin(prot)
  local dx, dy = gx - px, gy - py
  n.x = (c * dx + s * dy) / pscale
  n.y = (-s * dx + c * dy) / pscale
  n.rot, n.scale = grot - prot, gscale / pscale
end

function love.update(dt)
  if love.keyboard.isDown("left") then arm.rot = arm.rot - math.rad(60) * dt end
  if love.keyboard.isDown("right") then arm.rot = arm.rot + math.rad(60) * dt end
end

function love.keypressed(key)
  if key == "r" then
    if hand.parent then reparent(hand, nil) else reparent(hand, forearm) end
  end
end

function love.draw()
  for _, n in ipairs({ arm, forearm, hand }) do
    local x, y, rot, scale = toGlobal(n)
    love.graphics.push()
    love.graphics.translate(x, y)
    love.graphics.rotate(rot)
    love.graphics.scale(scale)
    love.graphics.rectangle("line", 0, -6, n.length, 12)
    love.graphics.circle("fill", 0, 0, 5)
    love.graphics.pop()
  end
end
# arm.gd (Godot 4). Attach to a Node2D at (0, 0) in a new scene and run.
# Left and right arrows rotate Arm. Enter or Space (ui_accept) moves Hand.
extends Node2D

var arm := Node2D.new()
var forearm := Node2D.new()
var hand := Node2D.new()

func _ready() -> void:
    add_child(arm)
    arm.add_child(forearm)
    forearm.add_child(hand)
    arm.position = Vector2(120, 170)       # local to this root node
    forearm.position = Vector2(100, 0)     # local to Arm
    forearm.rotation_degrees = 30
    hand.position = Vector2(80, 0)         # local to Forearm
    hand.rotation_degrees = 20
    print(hand.position, " ", hand.global_position)  # local 80, 0 and global about 289.3, 210

func _process(delta: float) -> void:
    arm.rotation += deg_to_rad(60) * Input.get_axis("ui_left", "ui_right") * delta
    if Input.is_action_just_pressed("ui_accept"):
        var target: Node = self if hand.get_parent() == forearm else forearm
        hand.reparent(target)              # keeps the global transform by default
    queue_redraw()

func _draw() -> void:
    # This node sits at the world origin, so global positions can be drawn as they are.
    draw_line(arm.global_position, forearm.global_position, Color.WHITE, 8)
    draw_line(forearm.global_position, hand.global_position, Color.WHITE, 6)
    draw_line(hand.global_position, hand.to_global(Vector2(30, 0)), Color.ORANGE, 4)
// ArmRig.cs (Unity 6 or 2022 LTS). Add to an empty GameObject at (0, 0, 0) and press Play.
// Watch the Scene view. Drag Arm Degrees and tick Detach Hand in the Inspector while playing.
// Unity's y axis points up, so positive rotations turn counter-clockwise here.
using UnityEngine;

public class ArmRig : MonoBehaviour
{
    [Range(-180f, 180f)] public float armDegrees = 0f;
    public float armScale = 1f;
    public bool detachHand;
    Transform arm, forearm, hand;

    void Start()
    {
        arm = new GameObject("Arm").transform;
        forearm = new GameObject("Forearm").transform;
        hand = new GameObject("Hand").transform;
        arm.SetParent(transform, false);
        forearm.SetParent(arm, false);
        hand.SetParent(forearm, false);
        // 1 unit = 100 pixels of the demo.
        arm.localPosition = new Vector3(1.2f, 1.7f, 0f);
        forearm.localPosition = new Vector3(1f, 0f, 0f);
        forearm.localRotation = Quaternion.Euler(0f, 0f, 30f);
        hand.localPosition = new Vector3(0.8f, 0f, 0f);
        hand.localRotation = Quaternion.Euler(0f, 0f, 20f);
        Debug.Log(hand.localPosition + " " + hand.position);  // local 0.8, 0, 0 and world about 2.89, 2.1, 0
    }

    void Update()
    {
        arm.localRotation = Quaternion.Euler(0f, 0f, armDegrees);
        arm.localScale = Vector3.one * armScale;
        Transform wanted = detachHand ? null : forearm;
        if (hand.parent != wanted)
            hand.SetParent(wanted, true);         // true: keep the world transform
        Debug.DrawLine(arm.position, forearm.position, Color.white);
        Debug.DrawLine(forearm.position, hand.position, Color.white);
        Debug.DrawLine(hand.position, hand.TransformPoint(0.3f, 0f, 0f), Color.yellow);
    }
}

The highlighted lines are the lesson: one node, a local and a global position, and a reparent that keeps the global transform. reparent is new in Godot 4; in Godot 3 you removed and re-added the node and restored its global position yourself.

Pitfalls

  • Setting a local value with a world value in mind. The opening gun bug. Use global_position in Godot or position in Unity when you mean "here in the level".
  • Reparenting the wrong way. Godot's remove_child plus add_child keeps local values, so the node jumps; reparent keeps global ones. In Unity, SetParent(parent, false) keeps local values.
  • Non-uniform scale on a parent. Scale a parent by (2, 1) and rotate a child, and the child gets sheared, which position, rotation and scale alone cannot describe. That is why Unity calls world scale lossyScale; Godot 2D nodes have a skew property for it. Keep odd scales on leaf nodes such as sprites.
  • Two owners for one position. A simulated physics body writes its own world position every step. Parenting it to something that moves gives it two owners, with results that depend on engine and body type. Keep simulated bodies near the top of the tree.
  • Rotation direction. Godot 2D has y pointing down, so positive rotation is clockwise. Unity has y up, so positive z rotation is counter-clockwise.
  • Cost of deep trees. Moving a parent makes every descendant's cached global transform stale. Keep the tree flat when objects do not need to move together.

In real games

Skeletal animation is this lesson applied to bones. In Unity, the bones of a skinned mesh are ordinary Transforms in the hierarchy, and Godot's 2D bones (Bone2D) are nodes that inherit from Node2D. A held weapon is a child of a hand bone; a turret is a child of a tank hull.

A common Godot pattern is a Camera2D as a child of the player, so it follows without code. The idea predates both engines: fixed-function OpenGL kept a matrix stack with push and pop, which LÖVE's love.graphics.push and pop mirror.

Your turn (15 minutes)

Make a parent that rotates slowly with a child 100 pixels (or 1 unit) to its right. Every second, print the child's local and global position. Add a key that moves the child to the scene root, once keeping its global transform and once keeping its local values.

You are done when you can predict where the child will appear in each case, and one printed global position matches the formula worked out by hand.

Takeaways

  • Every node stores a local transform measured from its parent. The global transform is computed from the root down.
  • Rotations add, scales multiply, and positions are rotated and scaled by the parent before the parent's position is added.
  • Writing a global value makes the engine solve backwards for local values. Reparenting has to choose which of the two to keep.
  • In Godot position is local; in Unity position is world. Check which one you are writing.
  • Keep non-uniform scale and simulated physics bodies away from the middle of a tree.

Asset references and dependency graphs: hard and soft links

How one reference can pull a chain of textures and sounds into memory, and how path and address references in Godot and Unity break that chain.

The first level takes nine seconds to load and uses 193 MB, yet the player starts in a small corridor. You trace it. The level holds a link to the boss, the boss holds its 64 MB sprite sheet and its music, and the level also holds the shop menu with its own art and music. Two fields in the editor pulled in 135 MB that only the last two rooms use.

Every reference is an arrow

Asset A depends on asset B when A cannot be used until B is loaded. A scene depends on the textures its sprites show; a material depends on its shader. Draw every asset as a box and every dependency as an arrow and you get the dependency graph of your project.

Arrows come in two kinds.

  • A hard reference stores a direct link to the asset. To build the owner, the engine must load the target first. Loading is therefore transitive: load one box and you load everything you can reach from it by following hard arrows.
  • A soft reference stores only a name for the asset: a file path, a UID, an address or a GUID. It is a string. Nothing is loaded until code passes that name to a load function.

What happens, in what order

When you ask either engine to load an asset, it does roughly this:

  1. Read the asset's file and find its list of references.
  2. For each hard reference, load that asset first, using the same steps. If the engine's cache already holds it, skip it: a shared texture is loaded once, however many owners point at it.
  3. Build the asset itself, wiring the loaded objects into it. Soft references are copied in as plain strings and left alone.

Later, when code calls load with one of those strings, the same walk starts from that box, at that moment, with the hitch costs from the previous lesson.

The cache matters for one subtle rule: a soft link only saves memory if no other hard path reaches the target. If the shop and the player both use sword.png, softening the shop link still leaves the sword loaded through the player.

Who owns the data

With a hard reference the owner keeps the target alive: in Godot until the last reference to the resource goes, in Unity until the scene is unloaded. With a soft reference, the code that called load owns the result. In Godot you drop your last variable pointing at it; with Unity's Addressables you release the handle, or the asset stays loaded.

How Godot 4 expresses it

In a .tscn file the hard references are the [ext_resource] lines at the top. A filled PackedScene or Texture2D export becomes one, as does every instanced sub-scene. A script's preload is hard too, wherever the script is attached.

For a soft reference, export a string with @export_file("*.tscn") and call load on it when needed. Since Godot 4.5 the editor stores such a field as a uid:// string when the file has one, so it survives the file being moved; earlier 4.x versions store the res:// path. load accepts both.

There is also a middle ground for instanced scenes: right-click one in the scene tree and choose Load As Placeholder. At run time it becomes an InstancePlaceholder node, and the real scene is loaded only when you call create_instance().

To inspect the graph, right-click a file in the FileSystem dock: Edit Dependencies... lists the arrows going out and View Owners... lists the arrows coming in. In code, ResourceLoader.get_dependencies(path) returns the direct dependencies of one file.

How Unity expresses it

A serialized field of an asset type, such as GameObject, Texture2D or AudioClip, is a hard reference. When a scene loads, everything its objects reference loads with it, transitively.

Resources.Load("Boss") takes a path string, so it is soft at run time. But everything inside a Resources folder ships in the build, used or not.

The Addressables package gives soft references a proper type. An AssetReference field, or a typed one such as AssetReferenceGameObject, looks like a normal object field in the Inspector, but it serializes only the asset's GUID. You load it with LoadAssetAsync or InstantiateAsync and release it with ReleaseAsset or ReleaseInstance.

In editor scripts, AssetDatabase.GetDependencies(path, true) lists every asset path an asset depends on, recursively.

Rule of thumb

Hard-link what every moment of the scene needs. Put a soft link at each boundary where content may never be used: the next room, a menu, a boss, a cosmetic the player might not own.

The code

LÖVE has no asset graph of its own, so the idea is easy to see bare. This model uses the demo's names and sizes. A soft link is just a key in the SOFT table; a real game would call love.graphics.newImage or love.audio.newSource where the model sets loaded[name] = true. Press B or S to request the boss or the shop, R to reset.

-- main.lua. Same graph and sizes (MB) as the demo.
local SIZE = { Level = 1, Player = 1, Shop = 1, HUD = 1, Boss = 1,
  ["tiles.png"] = 8, ["music.ogg"] = 20, ["hero.png"] = 16, ["jump.wav"] = 1,
  ["sword.png"] = 4, ["shop.png"] = 24, ["shop.ogg"] = 18, ["font.ttf"] = 2,
  ["icons.png"] = 4, ["boss.png"] = 64, ["boss.ogg"] = 24, ["roar.wav"] = 3 }

local REFS = {
  Level  = { "Player", "Shop", "HUD", "Boss", "tiles.png", "music.ogg" },
  Player = { "hero.png", "jump.wav", "sword.png" },
  Shop   = { "sword.png", "shop.png", "shop.ogg" },
  HUD    = { "font.ttf", "icons.png" },
  Boss   = { "boss.png", "boss.ogg", "roar.wav" },
}

-- Soft links store a name only. Empty this table to get 193 MB.
local SOFT = { ["Level>Boss"] = true, ["Level>Shop"] = true }

local loaded = {}   -- the cache: name -> true

local function loadAsset(name)
  if loaded[name] then return end           -- shared assets load once
  for _, child in ipairs(REFS[name] or {}) do
    if not SOFT[name .. ">" .. child] then loadAsset(child) end   -- hard: load first
  end
  loaded[name] = true                       -- then build the owner
end

local function memory()
  local total = 0
  for name in pairs(loaded) do total = total + SIZE[name] end
  return total
end

function love.load() loadAsset("Level") end   -- 58 MB with both links soft

function love.keypressed(key)
  if key == "b" then loadAsset("Boss") end      -- +92 MB
  if key == "s" then loadAsset("Shop") end      -- +43 MB, sword already in
  if key == "r" then loaded = {}; loadAsset("Level") end
end

function love.draw()
  local names = {}
  for name in pairs(loaded) do names[#names + 1] = name end
  table.sort(names)
  love.graphics.print("in memory: " .. memory() .. " MB of 128 MB", 10, 10)
  love.graphics.print(table.concat(names, "\n"), 10, 40)
end
# level.gd on the root node of level.tscn. Godot 4.
# Assign a boss scene and pick a shop scene in the Inspector, then run.
extends Node

# Hard: saved as an [ext_resource] line in level.tscn.
# Loading level.tscn loads the boss scene and everything it references.
@export var boss_scene: PackedScene

# Soft: only a string (a uid:// or res:// path). Nothing loads until load().
@export_file("*.tscn") var shop_scene_path: String

var shop: Node

func _ready() -> void:
    print_graph(scene_file_path, 0, {})

func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed("ui_accept") and shop == null and shop_scene_path != "":
        var shop_scene: PackedScene = load(shop_scene_path)   # loads the shop subtree now
        shop = shop_scene.instantiate()
        add_child(shop)

# Print every file a resource pulls in, once each, like the demo's highlight.
func print_graph(path: String, depth: int, seen: Dictionary) -> void:
    if seen.has(path):
        return
    seen[path] = true
    print("  ".repeat(depth) + path)
    for dep in ResourceLoader.get_dependencies(path):
        var dep_path: String = dep.get_slice("::", 2) if dep.contains("::") else dep
        print_graph(dep_path, depth + 1, seen)
// Level.cs. Unity 6 or 2022 LTS with the Addressables package installed.
// Mark the shop prefab as Addressable, then drag it into Shop Prefab.
// In Play mode, use the component's menu (three dots) to open and close the shop.
using UnityEngine;
using UnityEngine.AddressableAssets;

public class Level : MonoBehaviour
{
    // Hard: this prefab and all its textures and sounds load with the scene.
    public GameObject bossPrefab;

    // Soft: serializes only the asset's GUID. Nothing loads until you ask.
    public AssetReferenceGameObject shopPrefab;

    GameObject shop;

    [ContextMenu("Open shop")]
    void OpenShop()
    {
        if (shop != null || !shopPrefab.RuntimeKeyIsValid()) return;
        shopPrefab.InstantiateAsync().Completed += h => shop = h.Result;
    }

    [ContextMenu("Close shop")]
    void CloseShop()
    {
        if (shop == null) return;
        shopPrefab.ReleaseInstance(shop);   // you own it: release, or it stays loaded
        shop = null;
    }
}

// Assets/Editor/ShowDependencies.cs. Select a scene or prefab, then Tools > Show Dependencies.
using UnityEditor;
using UnityEngine;

public static class ShowDependencies
{
    [MenuItem("Tools/Show Dependencies")]
    static void Show()
    {
        if (Selection.activeObject == null) return;
        string path = AssetDatabase.GetAssetPath(Selection.activeObject);
        foreach (string dep in AssetDatabase.GetDependencies(path, true))
            if (dep != path) Debug.Log(dep);
    }
}

Pitfalls

  • A soft link with a hard twin. You soften the level's link to the boss, but a spawner script still has a hard field or a preload pointing at the same scene. Nothing changes. Check the incoming arrows (View Owners in Godot, or a dependency listing in Unity) before you count the savings.
  • Making everything soft. Each soft link is a load your code must start, wait for and release, and a typo in a path shows up only when that line runs. Soften boundaries, not every texture.
  • Loading an AssetReference twice. Its own LoadAssetAsync logs an error if a load through that reference is still held. To load the same reference from several places, pass it as the key to Addressables.LoadAssetAsync and keep one handle per caller.
  • Duplicated dependencies in Addressables. If Addressable assets in two groups both hard-reference a texture that is not itself Addressable, each bundle can get its own copy. The Addressables Analyze window can report such duplicates.

In real games

The split is not special to Godot and Unity: Unreal Engine calls them hard and soft object references, with types such as TSoftObjectPtr for the soft kind. Open-world streaming is built on soft links, with each region naming its neighbours so the game can load what is near the player. Downloadable content needs them too, because the base game must refer to content that may not be installed.

Your turn (15 minutes)

Run the dependency printer from the code section on your main gameplay scene. Add up the file sizes of what it lists, or just note the five biggest files. Find the largest subtree that the first minute of play does not need, such as a menu, a boss or a later room, and replace the hard link to it with a soft one that is loaded when needed. You are done when the printer no longer lists that subtree and the feature still works when you reach it.

Takeaways

  • Assets form a graph. Loading one asset loads everything reachable from it through hard references.
  • A soft reference is a name: a path, UID, address or GUID. Nothing loads until code asks.
  • The cache loads a shared asset once, so softening a link saves memory only if no other hard path reaches the target.
  • Godot: exported resources and preload are hard; @export_file plus load is soft. Unity: serialized asset fields are hard; AssetReference is soft.
  • Whoever loads through a soft link owns the result and must release it.

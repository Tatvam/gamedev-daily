Freeing objects safely: queue_free in Godot, Destroy in Unity

Why queue_free and Destroy wait until the end of the frame, and what breaks when an object is removed in the middle of a loop or while others still point at it.

A grenade goes off in a crowd. Most enemies die, but two standing next to a dying one walk away unhurt, and the console fills with errors about a turret aiming at something that no longer exists. The damage code is fine. The enemies were removed at the wrong moment.

Removing something while someone is looking at it

To free an object means to remove it from the game and give its memory back. The trouble is everyone else still using the object at that moment. Two kinds of user get hurt.

1. A loop walking over a list

The explosion walks over an array of enemies with an index i. Enemy B in slot 2 dies and is removed on the spot, so every enemy after it slides down one slot. C is now in slot 2, but the loop has finished slot 2 and moves on to slot 3. C is never visited.

It gets worse at the end of the list. In Lua, for i = 1, #enemies do reads #enemies once, before the first pass. Remove three enemies and the loop still runs to 8 and crashes on nil. A C# foreach over a List throws an exception instead.

2. Anyone holding a reference

A reference is a stored pointer to an object, such as a turret's target. When the target is freed, the turret's variable still points to where it was. What happens next depends on who owns the memory:

  • Godot frees the node for real. Using the old reference is a runtime error, and is_instance_valid(target) returns false.
  • Unity destroys the engine side of the object, but your C# object stays around until the garbage collector takes it. Unity overrides == so that target == null is true. Touching its engine data, such as target.transform, throws a MissingReferenceException.
  • Plain Lua has no "free". The turret's reference keeps the removed enemy alive, and the turret shoots a zombie: an object the game thinks is gone but is still using.

The engine's answer: free it later

Engines have both problems at a larger scale: they walk lists of nodes, bodies and signals, and any script can point at any object. So neither engine frees an object when you ask. They defer it: the object is marked, stays valid, and is freed at a safe point when no loop is running.

Godot 4

queue_free() marks the node and all its children for deletion "at the end of the current frame", in the words of the documentation. In the Godot 4.5 source the delete queue is emptied after each physics step and after each process step. Until then the node is still in the tree and usable, and is_queued_for_deletion() returns true. Calling queue_free() twice is safe. free() deletes on the spot.

Unity 6 and 2022 LTS

Destroy(obj) does the same job. The Unity scripting reference says the actual destruction is delayed until after the current Update loop and always happens before rendering. Destroying a GameObject also destroys its components and its child objects. Until then it still compares as not null. DestroyImmediate is meant for editor code. We know of no public Unity method like is_queued_for_deletion, so the usual approach is your own flag.

Who owns what

You own the decision that an object should die. The engine owns the moment its memory goes away. Between the two, the object is still valid but dying, and code that might meet it should check.

Try it

An explosion loop deals the same damage to eight enemies in turn; those at 0 hp or below die. Then the turret updates, aiming at the enemy that had the lowest hp when the frame began. Press Next (or tap the canvas, or use the arrow keys on a focused canvas) to step through one frame.

Start with Free now, loop forwards and watch C and F get skipped before the loop runs off the end. Switch to loop backwards: the array is fine now, but the turret's target is gone. Then try Queue, free at end of frame.

The code

LÖVE has no scene tree, so you build the delete queue yourself. Mark during the loop, act on the mark, and remove marked objects in one pass at the end of love.update. Press space to set off the explosion. The names and numbers match the demo's first wave: C dies, and the turret switches to A.

local damage, exploding = 3, false
local hps = { 5, 2, 1, 6, 3, 2, 8, 1 }
local enemies = {}
for i = 1, #hps do
  enemies[i] = { name = string.char(64 + i), hp = hps[i], dead = false }
end

local function lowestHp()               -- lowest hp wins, first on a tie
  local best = nil
  for i = 1, #enemies do
    local e = enemies[i]
    if not e.dead and (best == nil or e.hp < best.hp) then best = e end
  end
  return best
end
local turret = { target = lowestHp() }  -- C

function love.keypressed(key) if key == "space" then exploding = true end end

function love.update(dt)
  if exploding then
    for i = 1, #enemies do              -- nothing moves, every enemy is visited
      local e = enemies[i]
      e.hp = e.hp - damage
      if e.hp <= 0 then e.dead = true end  -- queue it, do not remove it
    end
    exploding = false
  end
  if turret.target == nil or turret.target.dead then
    turret.target = lowestHp()          -- A
  end
  for i = #enemies, 1, -1 do            -- end of frame: flush the queue
    if enemies[i].dead then table.remove(enemies, i) end
  end
end

function love.draw()
  for i = 1, #enemies do
    love.graphics.print(enemies[i].name .. " " .. enemies[i].hp, 10, i * 20)
  end
  if turret.target then love.graphics.print("target " .. turret.target.name, 120, 20) end
end
# enemy.gd on each enemy. Add the node to the "enemies" group. Godot 4.
class_name Enemy
extends Node2D

@export var hp := 5

func take_damage(amount: int) -> void:
    hp -= amount
    if hp <= 0:
        queue_free()        # still in the tree until the frame ends


# explosion.gd
extends Node2D

@export var damage := 3

func explode() -> void:
    # get_nodes_in_group returns a new array, and nothing is freed yet.
    for enemy in get_tree().get_nodes_in_group("enemies"):
        enemy.take_damage(damage)


# turret.gd
extends Node2D

var target: Enemy

func _process(_delta: float) -> void:
    if not is_instance_valid(target) or target.is_queued_for_deletion():
        target = _lowest_hp()

func _lowest_hp() -> Enemy:
    var best: Enemy = null
    for enemy in get_tree().get_nodes_in_group("enemies"):
        if enemy.is_queued_for_deletion():
            continue
        if best == null or enemy.hp < best.hp:
            best = enemy
    return best
// Enemy.cs. Unity 6 and 2022 LTS.
using System.Collections.Generic;
using UnityEngine;

public class Enemy : MonoBehaviour
{
    public static readonly List<Enemy> All = new List<Enemy>();
    public int hp = 5;
    public bool IsDying { get; private set; }

    void OnEnable()  { All.Add(this); }
    void OnDisable() { All.Remove(this); }

    public void TakeDamage(int amount)
    {
        hp -= amount;
        if (hp <= 0 && !IsDying)
        {
            IsDying = true;          // Unity has no public "queued" check
            Destroy(gameObject);     // really destroyed after this Update loop
        }
    }
}


// Explosion.cs
using System.Collections.Generic;
using UnityEngine;

public class Explosion : MonoBehaviour
{
    public int damage = 3;

    public void Explode()
    {
        // Loop over a copy, so no change to Enemy.All can break this loop.
        foreach (Enemy e in new List<Enemy>(Enemy.All)) e.TakeDamage(damage);
    }
}


// Turret.cs
using UnityEngine;

public class Turret : MonoBehaviour
{
    public Enemy target;

    void Update()
    {
        if (target == null || target.IsDying) target = LowestHp();  // == null is true once destroyed
    }

    Enemy LowestHp()
    {
        Enemy best = null;
        foreach (Enemy e in Enemy.All)
            if (!e.IsDying && (best == null || e.hp < best.hp)) best = e;
        return best;
    }
}

The Lua flush loop runs backwards on purpose. Removing slot i only shifts the slots after it, and those have already been checked.

Pitfalls

  • Dying objects still act this frame. A coin queued by one player can be collected by a second player later in the same frame, giving double points. Check is_queued_for_deletion() or your own flag before you act on an object that might be dying.
  • Removing inside a forward loop. If you must remove immediately, loop backwards. Better, mark now and sweep after the loop.
  • Using ?. or is null on Unity objects. These skip Unity's custom ==, so a destroyed object counts as not null. Use == null or plain if (target).
  • Destroy(this) instead of Destroy(gameObject). The first removes only the script component and leaves the enemy standing.
  • remove_child without freeing. In Godot the node leaves the tree but stays in memory. If nothing adds it back, that is a leak.
  • Reaching for free() or DestroyImmediate. They bring back exactly the problems deferral solves.
  • Performance. Creating and freeing hundreds of bullets per second is costly. Object pooling, later in this course, avoids it.

In real games

Every Godot game that calls queue_free and every Unity game that calls Destroy relies on this deferral. Godot's own process loop also guards itself: the 4.5 source copies the node list before processing and skips nodes removed along the way. Unity's Entities package uses the same idea: changes such as destroying an entity are usually recorded in an entity command buffer and played back later, when no system is iterating.

Takeaways

  • Removing from a list while looping over it skips entries or runs past the end.
  • Freeing an object breaks everyone who still holds a reference to it.
  • Engines defer: queue_free and Destroy mark the object now and free it later, after the update and before rendering.
  • Between the call and the actual free, the object is valid but dying. Check for that.
  • Use is_instance_valid in Godot and == null in Unity for references that may outlive their target.

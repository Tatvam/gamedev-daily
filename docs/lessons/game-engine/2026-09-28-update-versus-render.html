Update versus render: two clocks in one loop

Why engines keep simulation and drawing apart, what happens when they run at different rates, and how Godot and Unity give each its own clock.

A physics object in your game moves perfectly, yet on screen it shivers slightly, even at a steady 60 frames per second.

Nothing is wrong with the physics. The game is updating the world at one rate and drawing it at another, and the screen shows exactly what that mismatch produces.

Two jobs, two owners

Yesterday's lesson split a frame into input, update and render. The two big jobs have different owners and different needs.

  • Update owns the world state: positions, velocities, health, timers. It is the game's rules.
  • Render owns nothing in the world. It reads the latest world state and turns it into pixels. How often it can run depends on the player's hardware and monitor.

Because render only reads, it does not care how many updates happened since it last looked, and update does not care whether anyone is watching. That one-way relationship lets the two run at different rates. The world is always correct; the only question is which moments of it the player sees.

Two clocks

Picture two clocks ticking side by side. The update rate is how many times per second the world advances. The render rate, usually called the frame rate, is how many images per second reach the screen. Each time a frame is drawn, it shows the most recent update that has finished. There are three possible relationships.

  1. Equal rates. Every frame shows exactly one new update. Motion is smooth.
  2. Render faster than update. Some frames have no new update to show, so they repeat the previous image. A repeated frame is wasted drawing work: the GPU drew a picture the player has already seen.
  3. Update faster than render. Some updates finish and are overwritten before any frame shows them. They still count for the rules, but the player never sees them.

The catch comes when one rate is not a whole multiple of the other. Then the number of new updates per frame keeps changing, and so does the distance an object appears to move.

That unevenness has a name: judder. The object moves at a constant speed in the world, but on screen it hops by 0, 1, 1, 0, 1 steps, or by 1, 2, 1, 2. Your eye notices the rhythm even though every frame is correct.

Why engines separate them anyway

Tying the two together would avoid judder, but it would make the frame rate part of the game rules. Separating the clocks buys three things:

  • The rules run at a rate you choose, whatever the monitor does.
  • When rendering falls behind, the game drops frames instead of slowing down or changing behaviour.
  • Update can run with no render at all. A dedicated server for a multiplayer game does exactly that.

The price is the judder above. The usual cure is to draw a blend of the last two updates instead of the latest one, which gets its own lesson in this track.

Rule of thumb

If it changes the outcome of the game, it belongs on the update clock. If it only changes what the player sees, it belongs on the render clock. Render reads, update writes.

The code

LÖVE calls love.update and love.draw once per frame, so both run at the render rate, which with vsync on is your monitor's refresh rate. To give update its own clock, keep a running total of time that has not been simulated yet and run as many fixed updates as it pays for. This small loop is called an accumulator. It is shown here only to separate the clocks; the fixed timestep lesson later in this track adds the safety cap and the blending it still lacks.

local UPDATE_RATE = 40          -- updates per second
local STEP = 1 / UPDATE_RATE
local SPEED = 200               -- world units per second
local WORLD = 400               -- the track is 0..400 wide

local square = { x = 0 }
local unsimulated = 0           -- time that has passed but not been updated
local updates, frames = 0, 0

local function updateWorld(step)   -- writes the world, draws nothing
  square.x = (square.x + SPEED * step) % WORLD
  updates = updates + 1
end

function love.update(dt)        -- called once per frame
  unsimulated = unsimulated + dt
  while unsimulated >= STEP do     -- zero, one or several updates
    updateWorld(STEP)
    unsimulated = unsimulated - STEP
  end
end

function love.draw()            -- reads the world, changes nothing in it
  frames = frames + 1
  love.graphics.rectangle("fill", square.x, 100, 22, 22)
  love.graphics.print("updates " .. updates .. "  frames " .. frames, 10, 10)
end
# Godot 4. Attach to a Node2D with a Sprite2D child, then run the scene.
extends Node2D

const SPEED := 200.0
const WORLD := 400.0
var updates := 0
var frames := 0

func _ready() -> void:
    Engine.physics_ticks_per_second = 40   # the update clock (default 60)
    Engine.max_fps = 60                    # cap on the render clock, 0 = no cap

# Called 40 times per second of game time, whatever the frame rate.
func _physics_process(delta: float) -> void:
    position.x = fmod(position.x + SPEED * delta, WORLD)
    updates += 1

# Called once per drawn frame. Godot renders after it returns.
func _process(_delta: float) -> void:
    frames += 1
    if frames % 60 == 0:
        print("updates ", updates, "  frames ", frames)
// Unity 6 or 2022 LTS. Put on a GameObject with a SpriteRenderer.
using UnityEngine;

public class TwoClocks : MonoBehaviour
{
    // 2 units per second is 200 pixels at the default 100 pixels per unit.
    const float Speed = 2f;
    const float World = 4f;
    int updates, frames;

    void Awake()
    {
        Time.fixedDeltaTime = 1f / 40f;    // the update clock (default 0.02 s, 50 per second)
        QualitySettings.vSyncCount = 0;    // otherwise vsync decides the frame rate
        Application.targetFrameRate = 60;  // the render clock
    }

    // Called 40 times per second of game time, whatever the frame rate.
    void FixedUpdate()
    {
        Vector3 p = transform.position;
        p.x = Mathf.Repeat(p.x + Speed * Time.fixedDeltaTime, World);
        transform.position = p;
        updates++;
    }

    // Called once per drawn frame. Unity renders after Update and LateUpdate.
    void Update()
    {
        frames++;
        if (frames % 60 == 0) Debug.Log($"updates {updates}  frames {frames}");
    }
}

All three move the square only on the update clock and count frames on the render clock. Run any of them and the square judders: 40 updates over 60 frames, like diagram A. In Godot and Unity the fixed clock normally drives physics; here it stands in for "the rules". The per-frame callbacks, _process and Update, are update code running on the render clock, which is why they need the frame's duration. That is the next lesson.

Pitfalls

  • Game rules in drawing code. A cooldown counted down in love.draw, Godot's _draw or Unity's OnGUI runs at a rate you do not control. Godot's _draw does not even run every frame.
  • Counting frames as time. "Wait 60 frames" is one second at 60 frames per second and under half a second at 144. Count updates or seconds.
  • Moving the same object on both clocks. If physics moves a body in the fixed step and a script also sets its position every frame, the object jitters. Give each piece of data one owner.
  • Performance. Repeated frames cost GPU time for nothing new, and undrawn updates still cost CPU time. Raise the update rate only when the rules need the precision.

In real games

Both engines ship with separate clocks. Godot runs _physics_process at 60 ticks per second by default and _process once per drawn frame. Unity runs FixedUpdate every 0.02 seconds by default, 50 per second, and Update once per drawn frame.

Unity's default is a live example of the uneven case: 50 updates on a 60 Hz monitor means some frames show no new physics state. That is why Unity's Rigidbody has an interpolation setting, and why Godot 4.3 and later offer physics interpolation in the project settings.

Dedicated multiplayer servers take this to its limit: an update clock and no render at all.

Takeaways

  • Update owns the world state. Render only reads it and draws the most recent update.
  • Because render only reads, the two can run at different rates without changing the game's outcome.
  • Render faster than update gives repeated frames. Update faster than render gives updates nobody sees.
  • When one rate is not a whole multiple of the other, the distance moved per frame varies and motion judders.
  • Godot and Unity each give you both clocks: _physics_process and FixedUpdate for the rules, _process and Update once per drawn frame.

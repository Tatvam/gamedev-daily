The event bus: one channel in the middle

How a central event bus lets senders and listeners meet without references, when listeners run, and what it costs you when debugging.

Your enemy script started small. Now, when an enemy dies, it plays a sound, tells the quest log, tells the achievement tracker and updates the HUD. Each of those is a reference the enemy has to hold, and the enemy scene no longer runs in an empty test level because it expects all four to exist.

One channel in the middle

In the observer lesson, each subject owned its own list of listeners, so a listener had to find the subject first. The HUD would need a reference to every enemy that might ever spawn.

An event bus is one object that holds the listener lists for every kind of event in the game. An event is a name, such as enemy_died, plus data about what happened, called the payload. Code with news publishes an event to the bus; code that cares subscribes to that name. Senders and listeners hold no references to each other, only to the bus.

Who owns what? The bus owns the subscription lists, the sender owns the game state the event describes, and each listener owns its reaction. The payload is shared, so listeners should treat it as read-only. The bus usually lives for the whole game, longer than any scene.

When does a listener run?

Immediate delivery. Publish calls each listener before it returns. The data is fresh and the code is simple, but if a listener publishes a second event, every listener of that event runs inside the delivery of the first. Below, Badges unlocks a badge while handling enemy_died, so HUD and Audio hear about the badge before Quests hears about the death.

Queued delivery. Publish only appends the event to a queue, and at a fixed point in the frame, usually the end, the bus delivers the queue in order. The sender is never interrupted and chains become a straight line. The price is delay: by delivery time the enemy may be freed, so put what listeners need, such as the position, into the payload.

A queue also needs a rule for events published while it is being delivered. This lesson's bus keeps them for the next frame, so two listeners that answer each other cannot lock the game in an endless loop.

The bill comes when debugging

With direct references, "find all references" shows every system the enemy touches. With a bus, the enemy's code says only "publish enemy_died", and who listens is decided at run time. When a sound plays twice, you hunt through every subscriber to that name. If names are strings, a typo such as enemy_dead fails silently. Three habits keep the cost down:

  • Declare every event in one file, with typed parameters, so a misspelt name fails to compile and "find usages" works again.
  • Log inside the bus. It is the one place that sees every event and every listener, so one line of logging there traces the whole game.
  • Use the bus for news that many unrelated systems care about. Keep a direct call or a local signal for a parent talking to its own child.

Rule of thumb

Publish on the bus when the sender genuinely does not care who listens, or whether anyone does. If the sender needs an answer, or exactly one system must act, call that system directly.

The code

The Lua version is a whole LÖVE program with the demo's events, listeners and badge numbers. Keys 1, 2 and 3 publish, and Q switches between immediate and queued delivery. The bus logs every delivery, which is the same list the demo shows.

-- main.lua. Keys: 1 hurt, 2 enemy died, 3 coin, Q toggles queued delivery.
local bus = { listeners = {}, queue = {}, queued = false }
local log = {}

function bus.subscribe(event, name, fn)
  local list = bus.listeners[event]
  if list == nil then
    list = {}
    bus.listeners[event] = list
  end
  list[#list + 1] = { name = name, fn = fn }
end

function bus.unsubscribe(event, name)
  local list = bus.listeners[event] or {}
  for i = #list, 1, -1 do
    if list[i].name == name then table.remove(list, i) end
  end
end

local function deliver(event, data)
  local list = bus.listeners[event] or {}
  local copy = {}                         -- listeners may unsubscribe mid-loop
  for i = 1, #list do copy[i] = list[i] end
  for i = 1, #copy do
    log[#log + 1] = event .. " -> " .. copy[i].name   -- one place sees all
    copy[i].fn(data)
  end
end

function bus.publish(event, data)
  if bus.queued then
    bus.queue[#bus.queue + 1] = { event = event, data = data }
  else
    deliver(event, data)                  -- listeners run before this returns
  end
end

function bus.flush()                      -- call once, at the end of the frame
  local waiting = bus.queue
  bus.queue = {}                          -- events posted during flush wait a frame
  for i = 1, #waiting do deliver(waiting[i].event, waiting[i].data) end
end

-- Listeners. None of them knows who sends.
local hud = { health = 100, coins = 0, badge = "" }
local sounds, kills, questKills = 0, 0, 0
local BADGE_AT = { [1] = "First blood", [3] = "Hunter", [5] = "Veteran" }

bus.subscribe("player_hurt", "HUD", function (d) hud.health = d.health end)
bus.subscribe("player_hurt", "Audio", function (d) sounds = sounds + 1 end)
bus.subscribe("enemy_died", "Audio", function (d) sounds = sounds + 1 end)
bus.subscribe("enemy_died", "Badges", function (d)
  kills = kills + 1
  if BADGE_AT[kills] then bus.publish("badge_unlocked", { name = BADGE_AT[kills] }) end
end)
bus.subscribe("enemy_died", "Quests", function (d) questKills = questKills + 1 end)
bus.subscribe("coin_collected", "HUD", function (d) hud.coins = d.total end)
bus.subscribe("coin_collected", "Audio", function (d) sounds = sounds + 1 end)
bus.subscribe("badge_unlocked", "HUD", function (d) hud.badge = d.name end)
bus.subscribe("badge_unlocked", "Audio", function (d) sounds = sounds + 1 end)

-- Senders. They know only the bus.
local health, coins = 100, 0

function love.keypressed(key)
  if key == "1" then
    health = health - 10
    bus.publish("player_hurt", { health = health })
  elseif key == "2" then
    bus.publish("enemy_died", { x = 200, y = 120 })
  elseif key == "3" then
    coins = coins + 1
    bus.publish("coin_collected", { total = coins })
  elseif key == "q" then
    bus.queued = not bus.queued
  end
end

function love.update(dt)
  -- the rest of the game would update here
  bus.flush()                             -- the end of the frame
end

function love.draw()
  love.graphics.print("health " .. hud.health .. "  coins " .. hud.coins ..
    "  badge " .. hud.badge .. "  sounds " .. sounds .. "  quest kills " .. questKills, 10, 10)
  love.graphics.print(bus.queued and "delivery: queued" or "delivery: immediate", 10, 30)
  local first = math.max(1, #log - 20)
  for i = first, #log do
    love.graphics.print(log[i], 10, 50 + (i - first) * 16)
  end
end
# events.gd. Godot 4. Register it as an autoload named Events in Project Settings.
# The bus is a node that only declares signals. It lives as long as the game.
extends Node

signal player_hurt(health: int)
signal enemy_died(at: Vector2)
signal coin_collected(total: int)
signal badge_unlocked(badge_name: String)


# main.gd, in its own file, on the root Node of a new scene.
# Press Enter or Space (the ui_accept action) and read the Output panel.
extends Node

const BADGE_AT := {1: "First blood", 3: "Hunter", 5: "Veteran"}
var kills := 0

func _ready() -> void:
    Events.enemy_died.connect(_on_enemy_died_audio)
    Events.enemy_died.connect(_on_enemy_died_badges)
    # Deferred: called at the end of the frame, not inside emit().
    Events.enemy_died.connect(_on_enemy_died_quests, CONNECT_DEFERRED)
    Events.badge_unlocked.connect(_on_badge_unlocked)

func _process(_delta: float) -> void:
    if Input.is_action_just_pressed("ui_accept"):
        print("--- Enemy emits enemy_died")
        Events.enemy_died.emit(Vector2(200, 120))
        print("--- emit() has returned")

func _on_enemy_died_audio(_at: Vector2) -> void:
    print("Audio heard enemy_died")

func _on_enemy_died_badges(_at: Vector2) -> void:
    kills += 1
    print("Badges heard enemy_died, kills = ", kills)
    if BADGE_AT.has(kills):
        Events.badge_unlocked.emit(BADGE_AT[kills])

func _on_enemy_died_quests(_at: Vector2) -> void:
    print("Quests heard enemy_died (deferred)")

func _on_badge_unlocked(badge_name: String) -> void:
    print("HUD shows badge: ", badge_name)
// GameEvents.cs. Unity 2022 LTS or Unity 6.
// A static class: no GameObject, and it lives for the whole run.
using System;
using System.Collections.Generic;
using UnityEngine;

public static class GameEvents
{
    public static event Action<Vector3> EnemyDied;
    public static event Action<string> BadgeUnlocked;

    // Only the declaring class may invoke an event, so senders call these.
    public static void RaiseEnemyDied(Vector3 at) => EnemyDied?.Invoke(at);
    public static void RaiseBadgeUnlocked(string name) => BadgeUnlocked?.Invoke(name);

    // Queued delivery: Post now, Flush once near the end of the frame.
    static readonly List<Action> queue = new List<Action>();
    public static void Post(Action raise) => queue.Add(raise);
    public static void Flush()
    {
        var waiting = queue.ToArray();
        queue.Clear();                        // posted during Flush waits a frame
        foreach (var raise in waiting) raise();
    }
}


// EventDemo.cs, in its own file. Add to an empty GameObject and press Play.
// Tick "Queued" in the Inspector while it runs to switch delivery.
using UnityEngine;

public class EventDemo : MonoBehaviour
{
    public bool queued;
    static readonly string[] BadgeAt = { null, "First blood", null, "Hunter", null, "Veteran" };
    int kills;
    float timer;

    void OnEnable()
    {
        GameEvents.EnemyDied += OnEnemyDiedAudio;
        GameEvents.EnemyDied += OnEnemyDiedBadges;
        GameEvents.BadgeUnlocked += OnBadgeUnlocked;
    }

    void OnDisable()   // a static event holds every listener until it is removed
    {
        GameEvents.EnemyDied -= OnEnemyDiedAudio;
        GameEvents.EnemyDied -= OnEnemyDiedBadges;
        GameEvents.BadgeUnlocked -= OnBadgeUnlocked;
    }

    void Update()
    {
        timer += Time.deltaTime;
        if (timer < 2f) return;
        timer = 0f;
        Vector3 at = transform.position;      // copy the data into the payload
        Debug.Log("--- Enemy raises EnemyDied");
        if (queued) GameEvents.Post(() => GameEvents.RaiseEnemyDied(at));
        else GameEvents.RaiseEnemyDied(at);
        Debug.Log("--- Raise has returned");
    }

    void LateUpdate() => GameEvents.Flush();   // after every Update

    void OnEnemyDiedAudio(Vector3 at) => Debug.Log("Audio heard EnemyDied");

    void OnEnemyDiedBadges(Vector3 at)
    {
        kills++;
        Debug.Log("Badges heard EnemyDied, kills = " + kills);
        if (kills < BadgeAt.Length && BadgeAt[kills] != null)
            GameEvents.RaiseBadgeUnlocked(BadgeAt[kills]);
    }

    void OnBadgeUnlocked(string badgeName) => Debug.Log("HUD shows badge: " + badgeName);
}

Neither engine ships an "event bus" class; both give you the pieces. In Godot it is usually an autoload that only declares signals. Connections to an object's methods are removed automatically when that object is freed. Queuing is chosen per connection: CONNECT_DEFERRED makes that listener run at idle time, at the end of the frame, instead of inside emit().

In Unity it is usually a static class of C# events, as above, or ScriptableObject assets you write that each act as one event channel. A static event keeps every subscribed listener alive, even after its GameObject is destroyed, so OnDisable must remove what OnEnable added. The queue is your own, and LateUpdate stands in for the end of the frame; which script's LateUpdate runs first depends on the script execution order.

Pitfalls

  • Listeners that outlive their objects. The bus outlives every scene. A Unity script that never unsubscribes from a static event is still called after its object is destroyed, and throws errors when it touches its GameObject. In Godot, a node that is hidden or removed from the tree but not freed still reacts.
  • Relying on listener order. Order usually follows subscription order, which follows whichever object was enabled first. If Quests must update before the HUD reads it, make that explicit with a second event or a direct call.
  • Stale payloads in queued mode. The sender may be freed before delivery. Copy values such as position and score into the payload instead of sending the node.
  • Feedback loops. Two listeners that answer each other recurse forever with immediate delivery. Holding new events for the next frame turns the hang into a bug you can watch.
  • Everything through the bus. When a request and its reply both travel over the bus, the logic is spread across files that never mention each other. Questions with answers are function calls.

In real games

In Godot projects, an autoload holding only signals, often named Events or EventBus, is a widely shared community pattern for scenes that do not know each other, such as the player and the HUD.

In Unity, Ryan Hipple's Unite 2017 talk on ScriptableObject architecture popularised event channels as assets: senders raise the asset, and listener components respond to it, wired up in the Inspector.

Robert Nystrom's Game Programming Patterns describes the queued form as the Event Queue pattern, with audio as the example: game code posts sound requests, and the audio system works through them later.

Your turn (15 minutes)

Pick one event in your project that at least three systems care about, such as an enemy dying. Create a bus that declares only that event: an autoload with one signal in Godot, or a static class with one event in Unity. Replace the sender's direct calls with one publish, and make each listener subscribe, with a matching unsubscribe in Unity's OnDisable.

Log the event name and listener count inside the bus. You are done when the enemy scene runs alone in an empty test scene without errors, and the full game logs every death with the right count.

Takeaways

  • An event bus owns the listener lists, so senders and listeners only need a reference to the bus, not to each other.
  • Immediate delivery runs listeners inside publish, so events published by listeners nest. Queued delivery runs them later, in order, at a point in the frame you choose.
  • Queued events arrive late: put copied values in the payload, not references to objects that may be gone.
  • The cost is visibility. Declare events in one typed file, log inside the bus, and unsubscribe when a listener goes away.
  • Use the bus for news many systems care about. Use direct calls for questions that need an answer.

Loading assets: preload, load, and loading in the background

When an asset is loaded up front, on demand or in the background, who pays for it, and how Godot and Unity let you choose each one.

The hero walks through the boss door and the whole game freezes for half a second. Nothing moves. Then the boss is suddenly there, and the hero has jumped a few steps forward. Nothing is wrong with the boss code. The game loaded the boss's art at the moment it needed it, on the same thread that draws the frames.

Loading is work, and someone has to do it

An asset is a file in your project: a texture, a sound, a scene. A resource is that asset turned into a live object in memory that the engine can draw or play. Getting there means reading bytes from disk, decoding them, building objects and often handing data to the GPU. Bigger assets take longer.

Your game code runs on the main thread, which also prepares each frame. Anything it does that takes 300 ms makes that frame 300 ms long: a hitch.

So the choice is when to pay for loading, and which thread pays.

  1. Up front. Load everything before the level starts. Play is smooth, but the player waits at a loading screen, and the boss sits in memory all level.
  2. On demand. Load the boss when code first asks for it. No memory is used early, but the main thread stops until the load is done: the freeze in the hook.
  3. In the background. Ask early, let a worker thread read and decode the boss while the game runs, and collect it when ready. Play stays smooth if you asked early enough, though the main thread still does a small share each frame.

Who owns a loaded asset

Both engines keep a cache from asset path to the resource already in memory, so asking twice gives the same object almost for free. The cache does not decide when memory is freed, though.

  • Godot resources are reference counted: one stays while anything points at it and is freed when the last reference goes.
  • Unity assets loaded through a scene or Resources stay in memory until Unity unloads unused assets, which happens when a scene is loaded in single mode or when you call Resources.UnloadUnusedAssets. Addressables are explicit: each load gives you a handle, and you call Addressables.Release on it when done.

How Godot 4 expresses it

preload("res://boss.png") is a keyword that needs a constant path. The resource loads when the script loads, so its cost is paid while loading the scene that uses the script. That is up front.

load(path) loads when called and blocks until done, unless the path is cached. That is on demand.

In the background, ResourceLoader.load_threaded_request(path) starts the load on another thread. Poll load_threaded_get_status(path) each frame until it returns THREAD_LOAD_LOADED, then load_threaded_get(path) hands you the resource. Call that early and it blocks until the load finishes.

How Unity expresses it

An Inspector field that points at the boss texture is a direct reference: the texture loads with the scene or prefab holding the field. That is up front, and the usual Unity default.

Resources.Load<Texture2D>("Boss") loads from a folder named Resources, by path without extension, and blocks. Resources.LoadAsync returns a ResourceRequest with isDone and progress. Reading its asset early finishes the load at once, on the main thread.

The Addressables package is the more modern route: Addressables.LoadAssetAsync<T>(key) returns a handle with a Completed event, and WaitForCompletion() is its blocking escape hatch. Unity steers larger projects away from Resources, partly because everything in those folders ships in the build, used or not.

Unity's asynchronous loads read on a background thread, then integrate the result on the main thread, for example uploading a texture to the GPU. Application.backgroundLoadingPriority caps the milliseconds per frame integration may take: low for smooth play, high behind a loading screen.

Rule of thumb

Load up front what every moment of the level needs. Load in the background what you can predict a few seconds ahead. Load on demand only what is small, or what you need behind a screen that is already still.

The code

LÖVE gives you the parts to build all three yourself. A thread reads and decodes the image, because decoding is allowed off the main thread. Creating the GPU image with love.graphics.newImage is only allowed on the main thread, so the last step always happens there, just like Unity's integration step. Put any large PNG named boss.png next to main.lua.

-- main.lua. Change MODE to compare. Same numbers as the demo.
local MODE = "background"   -- "preload", "blocking" or "background"
local LEVEL_TIME = 5        -- seconds to cross the level
local REQUEST = 0.3         -- background load starts at 30%
local DOOR = 0.8            -- the boss is needed at 80%

-- Runs on a worker. Threads start with only love.thread and love.filesystem.
local LOADER = [[
require("love.image")
local path = ...
local data = love.image.newImageData(path)   -- read and decode, off the main thread
love.thread.getChannel("boss"):push(data)
]]

local t, boss, thread = 0, nil, nil

local function finish(data)
  boss = love.graphics.newImage(data)        -- GPU upload: main thread only
end

function love.load()
  if MODE == "preload" then finish(love.image.newImageData("boss.png")) end
end

function love.update(dt)
  t = t + dt
  local progress = t / LEVEL_TIME
  if MODE == "background" and not thread and progress >= REQUEST then
    thread = love.thread.newThread(LOADER)
    thread:start("boss.png")
  end
  if not boss and thread then
    local data = love.thread.getChannel("boss"):pop()   -- nil until ready
    if data then finish(data) end
  end
  if not boss and progress >= DOOR then
    if MODE == "blocking" then
      finish(love.image.newImageData("boss.png"))         -- the hitch
    else
      if thread:getError() then error(thread:getError()) end
      finish(love.thread.getChannel("boss"):demand())     -- wait for the rest
    end
  end
end

function love.draw()
  local x = math.min(t / LEVEL_TIME, 1) * 700
  love.graphics.rectangle("fill", 50 + x, 300, 20, 40)
  if boss and t / LEVEL_TIME >= DOOR then love.graphics.draw(boss, 600, 60, 0, 0.25) end
  love.graphics.print("last frame: " .. math.floor(love.timer.getDelta() * 1000) .. " ms", 10, 10)
end
# level.gd on a Node2D in a new scene. Godot 4. Put a large texture at res://boss.png.
extends Node2D

enum Mode { PRELOAD, BLOCKING, BACKGROUND }
@export var mode := Mode.BACKGROUND

const LEVEL_TIME := 5.0
const REQUEST := 0.3
const DOOR := 0.8
const BOSS_PATH := "res://boss.png"

# Loaded when this script loads. While this line exists the boss is in the cache,
# so load() is instant too. Comment it out to test the other two modes.
const BOSS_PRELOADED := preload("res://boss.png")

var t := 0.0
var requested := false
var boss: Texture2D

func _process(delta: float) -> void:
    t += delta
    var progress := t / LEVEL_TIME
    if mode == Mode.BACKGROUND and not requested and progress >= REQUEST:
        ResourceLoader.load_threaded_request(BOSS_PATH)
        requested = true
    if requested and boss == null:
        if ResourceLoader.load_threaded_get_status(BOSS_PATH) == ResourceLoader.THREAD_LOAD_LOADED:
            boss = ResourceLoader.load_threaded_get(BOSS_PATH)
    if boss == null and progress >= DOOR:
        var start := Time.get_ticks_usec()
        match mode:
            Mode.PRELOAD:
                boss = BOSS_PRELOADED
            Mode.BLOCKING:
                boss = load(BOSS_PATH)   # the hitch
            Mode.BACKGROUND:
                boss = ResourceLoader.load_threaded_get(BOSS_PATH)   # blocks for the rest
        print("getting the boss took %.1f ms" % ((Time.get_ticks_usec() - start) / 1000.0))
    queue_redraw()

func _draw() -> void:
    var x := minf(t / LEVEL_TIME, 1.0) * 700.0
    draw_rect(Rect2(50.0 + x, 300.0, 20.0, 40.0), Color.WHITE)
    if boss != null and t / LEVEL_TIME >= DOOR:
        draw_texture(boss, Vector2(600, 60))
// Level.cs. Unity 6 or 2022 LTS. Put a large texture at Assets/Resources/Boss.png.
// Reference mode: also drag that texture into the Boss Reference field.
// While that field is filled, the texture is already loaded, so Resources.Load is instant.
using UnityEngine;

public class Level : MonoBehaviour
{
    public enum Mode { Reference, Blocking, Background }
    public Mode mode = Mode.Background;
    public Texture2D bossReference;   // loads with the scene: up front

    const float LevelTime = 5f, Request = 0.3f, Door = 0.8f;
    float t;
    ResourceRequest request;
    Texture2D boss;

    void Update()
    {
        t += Time.deltaTime;
        float progress = t / LevelTime;
        if (mode == Mode.Background && request == null && progress >= Request)
            request = Resources.LoadAsync<Texture2D>("Boss");

        if (boss == null && progress >= Door)
        {
            float start = Time.realtimeSinceStartup;
            if (mode == Mode.Reference) boss = bossReference;
            else if (mode == Mode.Blocking) boss = Resources.Load<Texture2D>("Boss");   // the hitch
            else boss = (Texture2D)request.asset;   // finishes the load now if not done
            Debug.Log($"Getting the boss took {(Time.realtimeSinceStartup - start) * 1000f:F1} ms");
        }
    }

    void OnGUI()
    {
        if (boss != null) GUI.DrawTexture(new Rect(600, 60, 256, 256), boss);
    }
}

// BossAddressable.cs. Needs the Addressables package.
// Mark the texture as Addressable with the address "Boss".
using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

public class BossAddressable : MonoBehaviour
{
    AsyncOperationHandle<Texture2D> handle;

    void Start()
    {
        handle = Addressables.LoadAssetAsync<Texture2D>("Boss");
        handle.Completed += h => Debug.Log("Boss loaded: " + h.Result.name);
    }

    void OnDestroy()
    {
        if (handle.IsValid()) Addressables.Release(handle);   // you own the handle
    }
}

Pitfalls

  • Collecting a background load too early. load_threaded_get, ResourceRequest.asset and WaitForCompletion all turn a background load back into a blocking one if it is not finished. Check the status first, or start the request earlier.
  • Testing with a warm cache. If something else already references the asset, such as a preload, an Inspector field or an earlier load, the "slow" load is instant in your test and slow for players who reach it by another route. Measure from a fresh start.
  • Forgetting the step after loading. A loaded PackedScene or prefab must still be instantiated on the main thread, and a huge one can hitch on instantiate() or Instantiate even after a background load.
  • Preloading everything. Every preloaded asset stays in memory as long as its script or scene. On phones and consoles, memory runs out first.
  • Leaking Addressables handles. An Addressables asset stays loaded until every handle to it is released. A load with no matching Release is a slow memory leak.

In real games

Loading screens are the up-front strategy made visible. Long elevator rides, tight corridors and doors that open slowly are a common way to hide background loading: the game asks for the next area while you walk somewhere that needs little memory. Open-world games stream nearby areas in the background all the time and unload those behind you. In both engines, the blocking functions are fine behind a loading screen, because nothing on screen needs to move smoothly while they run.

Your turn (15 minutes)

Find one place in your project where a large asset or scene is loaded during play, such as a load, a Resources.Load or a spawn of a big prefab. Wrap it with a timer like the one in the code and print the milliseconds. If it is over about 5 ms, switch it to a background load that starts a few seconds earlier, at a moment you can predict. You are done when the printed time at the point of use drops near zero and the frame graph in your engine's profiler shows no spike there.

Takeaways

  • Loading always costs time. You choose when it happens and which thread pays.
  • Up front means a wait before play and memory held all level; on demand means a hitch at first use; background means smooth play if you ask early enough.
  • Godot: preload, load, and ResourceLoader.load_threaded_request. Unity: Inspector references, Resources.Load, and LoadAsync or Addressables.
  • Collecting a background load before it finishes blocks, just like a normal load.
  • Godot frees a resource when its last reference goes; Addressables free when you release every handle.

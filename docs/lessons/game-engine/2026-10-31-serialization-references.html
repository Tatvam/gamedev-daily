Serialization: turning objects into bytes and back

How engines write live objects out as text or bytes and read them back, and why references and cycles need IDs instead of copies.

You save the game with two enemies chasing the player. You load it, hit one enemy's target, and the other enemy's target is still at full health. After loading there are three players, and only one of them is on screen.

Or the save button freezes the game and then crashes it, because the player targets an enemy that targets the player. Both bugs have the same cause: the save code treated a reference as if it were a value.

Live objects, flat files

Serialization is turning objects in memory into a flat sequence of text or bytes that can be written to a file or sent over a network. Deserialization is the reverse: reading that sequence and building equal objects again. Engines do it constantly: a Godot .tscn scene, a Unity .prefab and the values in the Inspector are all serialized objects.

Plain values are easy. A number, a string or a boolean is copied out and copied back. The choice there is the format:

  • Text, such as JSON, writes field names next to values. People and version control can read it, and a new field does not break old files. It is larger and slower to parse.
  • Binary writes only the values, in an agreed order and size. It is small and fast, but both sides must know the exact layout, called the schema, and a missing byte shifts every value after it.

References are the hard part

A reference is how one object points at another, for example an enemy's target field. In memory a reference is an address, and an address means nothing in a file: the next run puts the object somewhere else. So the serializer has to turn it into something that survives.

The obvious approach is to follow the reference and write the target object inline, inside the object that points at it:

local function naive(obj)
  local target = "null"
  if obj.target then target = naive(obj.target) end   -- follow the reference
  return string.format('{"name":"%s","hp":%d,"x":%d,"target":%s}',
    obj.name, obj.hp, obj.x, target)
end

That code has two bugs, one for each way objects share references:

  • Shared references become copies. If Grub and Mox both target Ada, Ada is written once at the top level and once more inside each enemy. Loading builds three separate Adas. The file looks fine and the game is silently wrong.
  • Cycles never end. If Ada also targets Grub, writing Ada writes Grub, which writes Ada, which writes Grub. The function calls itself until the call stack runs out. A cycle is any loop of references that leads back to its start, and games are full of them: a parent and its children, a weapon and its owner.

The fix: give every object an ID

Instead of writing the target, write a number that stands for it. Saving takes two passes:

  1. Walk all the objects and give each one an ID, a number unique within this file.
  2. Write each object once, in a flat list. Where a field holds a reference, write the target's ID.

Loading also takes two passes, and the order matters. First create every object and fill in its plain values, keeping a table from ID to the new object. Only then go back and turn each stored ID into a reference by looking it up in that table. Linking in the first pass would fail, because an object may refer to one that has not been created yet.

Who owns the IDs? The serializer, for the length of one save or one load, and then it throws its lookup table away. The objects never learn their IDs. IDs that stay the same across many saves are a save system problem, and the next lesson.

Rule of thumb

Each object is written exactly once. Everything else that mentions it writes its ID.

The code

The Lua version saves the demo's three objects with IDs, writes the text to a file with LÖVE, reads it back, and checks that Grub and Mox share one Ada. The text it writes is the same as the demo's IDs view. Press Space to damage Ada and save again. Godot and Unity already serialize their own scenes this way, so their tabs show the same pattern for your own save data.

-- main.lua. The demo's three objects, saved with IDs and loaded back.
local ada  = { name = "Ada",  hp = 100, x = 40 }
local grub = { name = "Grub", hp = 30,  x = 200, target = ada }
local mox  = { name = "Mox",  hp = 30,  x = 320, target = ada }
ada.target = grub                                   -- the cycle
local world = { ada, grub, mox }

local function saveWorld(objects)
  local idOf = {}
  for i, obj in ipairs(objects) do idOf[obj] = i end   -- pass 1: number every object
  local lines = {}
  for i, obj in ipairs(objects) do                       -- pass 2: write each once
    local target = "null"
    if obj.target then target = tostring(idOf[obj.target]) end   -- reference as ID
    lines[i] = string.format('{"id":%d,"name":"%s","hp":%d,"x":%d,"target":%s}',
      i, obj.name, obj.hp, obj.x, target)
  end
  return '{"objects":[\n  ' .. table.concat(lines, ",\n  ") .. "\n]}"
end

local PATTERN = '{"id":(%d+),"name":"(%a+)","hp":(%d+),"x":(%d+),"target":(%w+)}'

local function loadWorld(text)
  local byId, targetId, list = {}, {}, {}
  for id, name, hp, x, target in text:gmatch(PATTERN) do   -- pass 1: create
    local obj = { name = name, hp = tonumber(hp), x = tonumber(x) }
    byId[tonumber(id)] = obj
    targetId[obj] = tonumber(target)                        -- nil when "null"
    list[#list + 1] = obj
  end
  for _, obj in ipairs(list) do                             -- pass 2: link
    if targetId[obj] then obj.target = byId[targetId[obj]] end
  end
  return list
end

local saved, loaded = "", {}
local function saveAndLoad()
  saved = saveWorld(world)
  love.filesystem.write("save.json", saved)
  loaded = loadWorld(love.filesystem.read("save.json"))
end

function love.load() saveAndLoad() end

function love.keypressed(key)
  if key == "space" then ada.hp = math.max(0, ada.hp - 10); saveAndLoad() end
end

function love.draw()
  love.graphics.print(saved, 10, 10)
  local shared = loaded[2].target == loaded[3].target
  love.graphics.print("After loading, Grub and Mox share one Ada: " .. tostring(shared), 10, 110)
end
# save_demo.gd. Godot 4. Attach to any Node and run the scene.
extends Node

class Unit:   # a plain RefCounted object, not a node
    var name: String
    var hp: int
    var x: int
    var target: Unit

func make(n: String, h: int, px: int) -> Unit:
    var u := Unit.new()
    u.name = n
    u.hp = h
    u.x = px
    return u

func save_world(units: Array) -> String:
    var rows := []
    for i in units.size():
        var u: Unit = units[i]
        var target = null
        if u.target: target = units.find(u.target) + 1   # reference as ID
        rows.append({"id": i + 1, "name": u.name, "hp": u.hp, "x": u.x, "target": target})
    return JSON.stringify({"objects": rows}, "  ")

func load_world(text: String) -> Array:
    var data = JSON.parse_string(text)
    var by_id := {}
    var units := []
    for row in data["objects"]:                         # pass 1: create
        var u := make(row["name"], int(row["hp"]), int(row["x"]))   # JSON numbers are floats
        by_id[int(row["id"])] = u
        units.append(u)
    for i in units.size():                              # pass 2: link
        var t = data["objects"][i]["target"]
        if t != null: units[i].target = by_id[int(t)]
    return units

func _ready() -> void:
    var ada := make("Ada", 100, 40)
    var grub := make("Grub", 30, 200)
    var mox := make("Mox", 30, 320)
    grub.target = ada
    mox.target = ada
    ada.target = grub   # the cycle (it also keeps both alive: reference counting)
    var file := FileAccess.open("user://save.json", FileAccess.WRITE)
    file.store_string(save_world([ada, grub, mox]))
    file.close()
    var loaded := load_world(FileAccess.get_file_as_string("user://save.json"))
    print(loaded[1].target == loaded[2].target)   # true: one shared Ada
// SaveDemo.cs. Unity 6 or 2022 LTS. Add to any GameObject and press Play.
using System;
using System.Collections.Generic;
using System.IO;
using UnityEngine;

public class Unit { public string name; public int hp, x; public Unit target; }

[Serializable] public class UnitRow { public int id; public string name; public int hp; public int x; public int target; }
[Serializable] public class SaveFile { public List<UnitRow> objects = new List<UnitRow>(); }

public class SaveDemo : MonoBehaviour
{
    void Start()
    {
        var ada  = new Unit { name = "Ada",  hp = 100, x = 40 };
        var grub = new Unit { name = "Grub", hp = 30,  x = 200, target = ada };
        var mox  = new Unit { name = "Mox",  hp = 30,  x = 320, target = ada };
        ada.target = grub;                                     // the cycle
        var units = new List<Unit> { ada, grub, mox };

        var file = new SaveFile();
        foreach (var u in units)
            file.objects.Add(new UnitRow {
                id = units.IndexOf(u) + 1, name = u.name, hp = u.hp, x = u.x,
                target = u.target == null ? 0 : units.IndexOf(u.target) + 1 });   // 0 means none
        string path = Path.Combine(Application.persistentDataPath, "save.json");
        File.WriteAllText(path, JsonUtility.ToJson(file, true));

        var data = JsonUtility.FromJson<SaveFile>(File.ReadAllText(path));
        var byId = new Dictionary<int, Unit>();
        foreach (var r in data.objects)                         // pass 1: create
            byId[r.id] = new Unit { name = r.name, hp = r.hp, x = r.x };
        foreach (var r in data.objects)                         // pass 2: link
            if (r.target != 0) byId[r.id].target = byId[r.target];
        Debug.Log(byId[2].target == byId[3].target);            // True: one shared Ada
    }
}

Godot's JSON.stringify sorts keys by default, so its file lists fields alphabetically. Unity's JsonUtility cannot write a bare list or a null int, which is why the rows sit inside a SaveFile class and 0 stands for "no target". The binary view in the demo uses 0 for the same reason.

Pitfalls

  • Saving run-time identities. Memory addresses, Godot's get_instance_id() and Unity's GetInstanceID() identify an object only while the game runs. A new run hands out different ones. Use IDs that the save file itself assigns, or stable IDs you store on the object.
  • Unity stores plain classes by value. A field whose type is a [Serializable] C# class is written inline, exactly like the nested serializer. Two fields pointing at one object come back as two objects, and Unity stops nested data at a depth limit with a warning instead of following a cycle forever. References to engine objects (GameObjects, components, assets) are different: those are stored as IDs. For plain classes that must stay shared, Unity 2019.3 and later have the [SerializeReference] attribute.
  • Godot saves only stored properties. In a scene, Godot writes properties marked for storage, such as @export variables. A plain var on your script is not saved with the scene. Unity likewise skips private fields without [SerializeField], static fields and C# properties.
  • JSON loses types. Godot's JSON parser returns every number as a float, and dictionary keys come back as strings. Convert them with int() on load.
  • Loading files you did not write. Formats that can create any type of object, such as Godot resource files or .NET's old BinaryFormatter, can be made to run code. Microsoft has marked BinaryFormatter obsolete for this reason. For player saves and downloaded content, prefer plain data formats like JSON and build the objects yourself.

In real games

Both engines use the ID approach for their own files. A Godot 4 .tscn or .tres file lists each embedded resource once with an ID and refers to it with SubResource("id"), and refers to other files with ExtResource("id"). Nodes in a scene refer to each other by node path. Unity's text scene and prefab files are YAML documents, each object tagged with a file ID, and a reference to another object is written as a fileID, plus a guid when the target lives in another asset file. Unity's Asset Serialization Mode setting chooses text or binary for these files, and text is the usual choice for version control.

Order matters in the engines too. Unity restores a component's serialized fields before it calls Awake. Godot calls _init before it applies the values saved in the scene, so exported values are not ready until _enter_tree or _ready.

Many games use their own binary formats. Minecraft stores world data in NBT, a binary format that writes a type and a name before each value, a middle ground between raw bytes and JSON.

Your turn (15 minutes)

Take two objects in your project where one refers to the other, such as an enemy and its target or a door and the switch that opens it. Write them to a JSON file with an ID for each object and the reference stored as an ID. Load the file into fresh objects using the two passes.

You are done when, after loading, changing a value through the reference changes the same object you get from the loaded list: the link is a reference, not a copy. For a stretch, make the two objects refer to each other and check that it still saves.

Takeaways

  • Serialization flattens objects into text or bytes. Values copy across easily; references do not, because an address means nothing in the next run.
  • Writing a referenced object inline turns shared references into copies and makes cycles loop forever.
  • Give every object an ID, write each object once, and store references as IDs.
  • Load in two passes: create everything, then link IDs back to the new objects.
  • Text is readable and tolerant of change. Binary is small and fast but needs an exact schema.

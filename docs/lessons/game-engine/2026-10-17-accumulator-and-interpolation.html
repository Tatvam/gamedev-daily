The fixed timestep accumulator and interpolation

How an engine turns uneven frames into equal physics steps with an accumulator, and how interpolating with the leftover time removes stutter.

You move a platform in _physics_process or FixedUpdate, exactly as the manual says. On a 144 Hz monitor it twitches: it glides for a few frames, then seems to stand still for one. The physics is correct. What you see is the gap between the physics clock and the screen clock, and the engine has a number that tells you how wide that gap is.

Two clocks, one bucket of time

Delta time fixes constant speeds, but anything that accelerates or collides still depends on the step size. So both engines run physics with a fixed timestep: every physics step simulates exactly the same amount of time. Godot calls the fixed step 60 times per second by default, Unity 50 times.

Frames, however, still arrive whenever the monitor and the graphics card allow. The engine has to turn uneven frames into equal steps. It does that with an accumulator: one number holding real time that has passed but has not been simulated yet. Think of it as a bucket. Each frame pours its duration in, and each physics step scoops exactly one step out.

What happens, in what order

  1. The engine measures how long the last frame took and adds it to the accumulator.
  2. While the accumulator holds at least one step, it runs a physics step and subtracts one step. In Godot a step calls every _physics_process(delta), then moves the physics bodies. In Unity it calls every FixedUpdate(), then runs the physics simulation.
  3. It calls the per-frame callbacks once: _process(delta) in Godot, Update() and LateUpdate() in Unity.
  4. It draws the frame. Whatever is left in the accumulator waits for the next frame.

The engine owns the accumulator and decides how many steps run. You own the state your callbacks change. Since a frame may run zero, one or several steps, per-frame code must never assume a step just happened.

The leftover is the stutter

The first frame in the diagram runs no step, so the screen shows the same picture twice, while the other frames each move a full step. That pause, once every six frames, is the twitch from the opening.

The leftover tells you exactly how far the drawn moment is past the last step. Divided by the step size it becomes the interpolation fraction, usually called alpha, a number from 0 up to almost 1. If you keep the state from before the last step, you can draw a blend between the two:

local alpha = accumulator / STEP
local x = previous.x + (ball.x - previous.x) * alpha

This is interpolation. Every drawn frame now lands at the right point in time, so motion is even. The price is that you always draw up to one step in the past: about 17 ms at 60 steps per second, 50 ms at 20.

When the bucket overflows

A half second frame puts 30 steps in the bucket at 60 per second. If running them takes longer than the time they cover, the next frame is longer still, and the game locks up: the spiral of death. Engines cap it in one of two ways, and both let the game briefly fall behind real time instead.

  • Cap the time. Unity limits how much time a single frame may add, through Maximum Allowed Timestep in the Time settings (Time.maximumDeltaTime, one third of a second by default).
  • Cap the steps. Godot 4 limits how many physics steps one frame may run, through a maximum steps per frame setting in the Physics section of the project settings. It is 8 by default as far as we know; check the value in your version.

The code

LÖVE gives you the frame time in love.update(dt) and nothing else, so the Lua builds the whole loop with the demo's names and numbers. Press I to toggle interpolation. The Godot and Unity versions only write the step and the blend, because the engine already owns the accumulator.

local STEP = 1 / 20      -- seconds per physics step
local MAX_STEPS = 8      -- most steps one frame may run
local GRAVITY = 900      -- pixels per second squared
local BOUNCE = 420       -- upward speed after touching the floor
local WIDTH, FLOOR, RADIUS = 400, 140, 10

local ball = { x = 40, y = 40, vx = 240, vy = 0 }
local previous = { x = ball.x, y = ball.y }
local accumulator = 0
local interpolate = true

local function physicsStep(b, dt)
  b.vy = b.vy + GRAVITY * dt
  b.x = b.x + b.vx * dt
  b.y = b.y + b.vy * dt
  if b.y > FLOOR - RADIUS then b.y = FLOOR - RADIUS; b.vy = -BOUNCE end
  if b.x < RADIUS then b.x = RADIUS; b.vx = math.abs(b.vx) end
  if b.x > WIDTH - RADIUS then b.x = WIDTH - RADIUS; b.vx = -math.abs(b.vx) end
end

function love.update(dt)
  accumulator = accumulator + dt
  local steps = 0
  while accumulator >= STEP and steps < MAX_STEPS do
    previous.x, previous.y = ball.x, ball.y
    physicsStep(ball, STEP)
    accumulator = accumulator - STEP
    steps = steps + 1
  end
  -- Hit the cap: throw away whole steps we could not afford.
  if accumulator >= STEP then accumulator = accumulator % STEP end
end

function love.draw()
  local alpha = accumulator / STEP
  local x, y = ball.x, ball.y
  if interpolate then
    x = previous.x + (ball.x - previous.x) * alpha
    y = previous.y + (ball.y - previous.y) * alpha
  end
  love.graphics.circle("fill", x, y, RADIUS)
end

function love.keypressed(key)
  if key == "i" then interpolate = not interpolate end
end
# Godot 4. Attach to a Node2D in a new scene and run it.
# Untick "Interpolate" in the Inspector to compare.
extends Node2D

const GRAVITY := 900.0
const BOUNCE := 420.0
const WIDTH := 400.0
const FLOOR := 140.0
const RADIUS := 10.0

@export var interpolate := true
var ball_pos := Vector2(40, 40)
var ball_vel := Vector2(240, 0)
var previous: Vector2

func _ready() -> void:
    previous = ball_pos
    Engine.physics_ticks_per_second = 20   # default 60; low to exaggerate

# Called by the engine's accumulator, 0 or more times per frame.
func _physics_process(delta: float) -> void:
    previous = ball_pos
    ball_vel.y += GRAVITY * delta
    ball_pos += ball_vel * delta
    if ball_pos.y > FLOOR - RADIUS:
        ball_pos.y = FLOOR - RADIUS
        ball_vel.y = -BOUNCE
    if ball_pos.x < RADIUS:
        ball_pos.x = RADIUS
        ball_vel.x = absf(ball_vel.x)
    if ball_pos.x > WIDTH - RADIUS:
        ball_pos.x = WIDTH - RADIUS
        ball_vel.x = -absf(ball_vel.x)

# Called once per drawn frame.
func _process(_delta: float) -> void:
    queue_redraw()

func _draw() -> void:
    var p := ball_pos
    if interpolate:
        p = previous.lerp(ball_pos, Engine.get_physics_interpolation_fraction())
    draw_circle(p, RADIUS, Color.WHITE)
// Unity 6 or 2022 LTS. Put on an empty GameObject in a new scene and press Play.
// Untick "Interpolate" in the Inspector to compare.
using UnityEngine;

public class AccumulatorBall : MonoBehaviour
{
    // Unity works in units, so the demo's pixels are divided by 100.
    const float Gravity = 9f, Bounce = 4.2f;
    const float Width = 4f, Radius = 0.1f;

    public bool interpolate = true;
    Vector2 pos = new Vector2(0.4f, 1f), vel = new Vector2(2.4f, 0f), previous;
    Transform view;

    void Start()
    {
        Time.fixedDeltaTime = 1f / 20f;   // default 0.02; low to exaggerate
        previous = pos;
        view = GameObject.CreatePrimitive(PrimitiveType.Sphere).transform;
        view.localScale = Vector3.one * Radius * 2f;
    }

    // Called by the engine's accumulator, 0 or more times per frame.
    void FixedUpdate()
    {
        previous = pos;
        vel.y -= Gravity * Time.fixedDeltaTime;
        pos += vel * Time.fixedDeltaTime;
        if (pos.y < Radius) { pos.y = Radius; vel.y = Bounce; }
        if (pos.x < Radius) { pos.x = Radius; vel.x = Mathf.Abs(vel.x); }
        if (pos.x > Width - Radius) { pos.x = Width - Radius; vel.x = -Mathf.Abs(vel.x); }
    }

    // Called once per drawn frame.
    void Update()
    {
        float alpha = (Time.time - Time.fixedTime) / Time.fixedDeltaTime;
        view.position = interpolate ? Vector2.Lerp(previous, pos, alpha) : pos;
    }
}

Unity's y axis points up, so its floor is at 0 and gravity subtracts. For real physics bodies you would not write the blend at all: tick Interpolate on the Rigidbody in Unity, or enable Physics Interpolation in Godot 4.3 or later. Godot added it for 2D in 4.3; check the documentation for 3D support in your version.

Pitfalls

  • Moving bodies in the per-frame callback. Setting a physics body's position in _process or Update fights the step. The physics engine only sees the change on the next step, and built-in interpolation blends towards a value you overwrite. Move bodies in the fixed callback.
  • Interpolating a teleport. Respawning a player blends them across the map for one frame. Set the previous state equal to the new state when you teleport. Godot's built-in interpolation has a node method for this, reset_physics_interpolation().
  • Reading one-frame input in the step. At 144 frames per second most frames run no step, so a "just pressed" check in the fixed callback is often missed. Read input per frame, store it, and let the next step use it.
  • Raising the step rate to hide stutter. 120 steps per second makes the twitch smaller but doubles the physics cost, and still does not match every monitor. Interpolation fixes the cause; a higher rate only reduces its latency.

In real games

Every game built on Godot or Unity runs this accumulator, whether its developers know it or not, because it is how the engines call _physics_process and FixedUpdate. Unity's Rigidbody interpolation exists for exactly the stutter in the demo, and Godot 4.3 brought the same idea into the engine for 2D with its physics interpolation setting.

Networked games lean on the same fixed steps when every player must simulate in identical increments.

Take an object in your project that moves in the fixed callback, such as a moving platform. Set the physics rate to 20 per second and watch it twitch. Add a previous position, update it at the start of each step, and draw the object at the blended position using the engine's alpha. You are done when the platform moves smoothly at 20 steps per second, and you can explain why it is now drawn slightly behind its physics position.

Takeaways

  • The engine owns an accumulator: each frame adds its duration, each fixed step removes exactly one step.
  • A frame can run zero, one or several steps, so per-frame code must not assume a step just happened.
  • The leftover divided by the step is alpha. Drawing a blend of the last two states at alpha removes stutter, at the cost of up to one step of latency.
  • Engines stop the spiral of death by capping time per frame (Unity) or steps per frame (Godot).
  • For physics bodies, prefer the built-in interpolation: Rigidbody Interpolate in Unity, Physics Interpolation in Godot 4.3 and later.

Finite state machines: one state at a time

How named states with enter, update and exit, and explicit transitions, replace tangled boolean flags, and how to write one in Godot and Unity.

You hold Down to crouch, tap Jump, and your character flies into the air still squashed flat. Or you press Down at the top of a jump and it crouches on thin air. Nobody wrote "crouch in mid-air" on purpose. It came out of two booleans that were never told about each other.

Flags multiply

A first player controller usually tracks what the character is doing with booleans, called flags:

-- One flag per behaviour. Each block looks reasonable alone.
if jumpPressed and not isJumping then
  isJumping = true
  vy = -JUMP_SPEED
end
isCrouching = love.keyboard.isDown("down")
if not isCrouching then x = x + move * SPEED * dt end

Three flags (isRunning, isJumping, isCrouching) allow eight combinations. Only some of them make sense, but nothing in the code says which. Each bug is fixed by adding a condition, such as and not isCrouching on the jump, and the rules end up spread across every if in the file. Each new flag doubles the combinations.

One state at a time

A finite state machine (FSM) replaces the flags with one variable. The character is always in exactly one of a short, fixed list of states: Idle, Run, Jump, Fall or Crouch. The variable that holds the name of the active one is the current state.

The machine moves from one state to another only along a transition: an arrow from one named state to another, labelled with what causes it. If there is no arrow, the change cannot happen. That is the whole trick. "Jump while crouching" is not a bug you remember to guard against; Crouch simply has no jump arrow.

Each state is a small object

Each state gets up to three functions. update(dt) runs every frame while the state is current: it does that state's work and returns the name of the next state, or nothing to stay. enter() runs once when the state becomes current, and exit() runs once when it stops being current. Jump's enter sets the upward speed. Crouch's enter shrinks the hitbox and its exit restores it, so no path out of Crouch can forget to stand up.

What happens, in what order

Three rules follow.

  • Exit before enter. The old state cleans up before the new one sets up, so the new state never sees leftovers.
  • One transition per update. The decision is made once, then applied. Letting enter trigger another change can bounce through states nobody sees.
  • The order of checks is the priority. If Jump and Down are both pressed on the same frame in Idle, the first check wins. In our code that is Jump. With flags this priority is accidental; here it is one line.

Who owns the data

The machine owns the current state, and only change writes to it. The player owns the shared data every state needs: position and vertical speed. Each state owns its side effects: whatever it sets in enter, it undoes in exit.

How the engines express it

Both engines ship a visual state machine, but for animation. In Godot 4, an AnimationTree can use an AnimationNodeStateMachine as its root, and code asks it to move with travel() on its playback object. In Unity, an Animator Controller is a graph of animation states and transitions, and a script derived from StateMachineBehaviour can receive OnStateEnter, OnStateUpdate and OnStateExit for a state.

For gameplay logic, neither engine's scripting API gives you a general state machine class, so you write it. The two common shapes are the same in both engines:

  • An enum and a match or switch. All states in one script, as in the code below. Easy to follow up to about six states.
  • One object per state. In Godot, often one child node per state under a "StateMachine" node. In Unity, often one plain C# class per state. More files, but each state keeps its own code and data.

The trade-off

Driving gameplay from the animation graph gives you the diagram for free, but the rules of play then wait on animation blending and transition timing. Keeping gameplay in code and letting the animation graph follow it avoids that.

Try it

Click the game area (or tab to it) and use the arrow keys and Space, or the on-screen buttons. One state is always lit, and the arrow that fired last stays highlighted. Hold Down and press Jump: nothing happens, because Crouch has no jump arrow.

Then switch to Boolean flags, try the same, and press Down at the top of a jump. Two flags turn on together and the character crouches in mid-air.

The code

A complete LÖVE program with the same states, numbers and check order as the demo. The floor sits at y = 300 instead of the demo's own height. Each state is a table of functions, and change is the only place that writes current.

-- Arrow keys move, Down crouches, Space jumps.
local SPEED, JUMP_SPEED, GRAVITY = 160, 380, 1200
local FLOOR_Y, STAND_H, CROUCH_H = 300, 36, 20

local player = { x = 200, y = FLOOR_Y, vy = 0, h = STAND_H }
local input = { move = 0, down = false, jump = false }

local function moveAndFall(dt)
  player.x = player.x + input.move * SPEED * dt
  player.vy = player.vy + GRAVITY * dt
  player.y = player.y + player.vy * dt
end

local states = {}
states.idle = { update = function(dt)
  if input.jump then return "jump" end          -- first check wins
  if input.down then return "crouch" end
  if input.move ~= 0 then return "run" end
end }
states.run = { update = function(dt)
  player.x = player.x + input.move * SPEED * dt
  if input.jump then return "jump" end
  if input.down then return "crouch" end
  if input.move == 0 then return "idle" end
end }
states.crouch = {
  enter = function() player.h = CROUCH_H end,
  exit = function() player.h = STAND_H end,
  update = function(dt)
    if not input.down then return "idle" end     -- no jump arrow
  end }
states.jump = {
  enter = function() player.vy = -JUMP_SPEED end,
  update = function(dt)
    moveAndFall(dt)
    if player.vy >= 0 then return "fall" end
  end }
states.fall = { update = function(dt)
  moveAndFall(dt)
  if player.y >= FLOOR_Y then
    player.y, player.vy = FLOOR_Y, 0
    return "idle"
  end
end }

local current = "idle"

local function change(name)
  if states[current].exit then states[current].exit() end   -- exit first
  current = name
  if states[current].enter then states[current].enter() end -- then enter
end

function love.keypressed(key)
  if key == "space" then input.jump = true end
end

function love.update(dt)
  input.move = 0
  if love.keyboard.isDown("left") then input.move = input.move - 1 end
  if love.keyboard.isDown("right") then input.move = input.move + 1 end
  input.down = love.keyboard.isDown("down")
  local nextState = states[current].update(dt)
  if nextState then change(nextState) end
  input.jump = false
end

function love.draw()
  love.graphics.rectangle("fill", player.x - 12, player.y - player.h, 24, player.h)
  love.graphics.print("state: " .. current, 10, 10)
end
# player.gd on a Node2D. Godot 4. Arrows move, Down crouches, Space jumps.
# No physics nodes needed: the floor is the line y = 300.
extends Node2D

enum State { IDLE, RUN, JUMP, FALL, CROUCH }

const SPEED := 160.0
const JUMP_SPEED := 380.0
const GRAVITY := 1200.0
const FLOOR_Y := 300.0
const STAND_H := 36.0
const CROUCH_H := 20.0

var state := State.IDLE
var vy := 0.0
var h := STAND_H

func _ready() -> void:
    position = Vector2(200, FLOOR_Y)

func _process(delta: float) -> void:
    var move := Input.get_axis("ui_left", "ui_right")
    var down := Input.is_action_pressed("ui_down")
    var jump := Input.is_action_just_pressed("ui_accept")
    var new_state := state
    match state:
        State.IDLE:
            if jump:
                new_state = State.JUMP
            elif down:
                new_state = State.CROUCH
            elif move != 0.0:
                new_state = State.RUN
        State.RUN:
            position.x += move * SPEED * delta
            if jump:
                new_state = State.JUMP
            elif down:
                new_state = State.CROUCH
            elif move == 0.0:
                new_state = State.IDLE
        State.CROUCH:
            if not down:
                new_state = State.IDLE
        State.JUMP, State.FALL:
            position.x += move * SPEED * delta
            vy += GRAVITY * delta
            position.y += vy * delta
            if state == State.JUMP and vy >= 0.0:
                new_state = State.FALL
            elif state == State.FALL and position.y >= FLOOR_Y:
                position.y = FLOOR_Y
                vy = 0.0
                new_state = State.IDLE
    if new_state != state:
        change_state(new_state)
    queue_redraw()

func change_state(new_state: State) -> void:
    if state == State.CROUCH:
        h = STAND_H              # exit Crouch
    state = new_state
    if state == State.CROUCH:
        h = CROUCH_H             # enter Crouch
    elif state == State.JUMP:
        vy = -JUMP_SPEED         # enter Jump

func _draw() -> void:
    draw_rect(Rect2(-12, -h, 24, h), Color.WHITE)
// PlayerStates.cs. Unity 6 or 2022 LTS with the Input System package.
// Put it on a Cube at the origin. 1 unit = 100 demo pixels, and y points up,
// so gravity is subtracted. The cube scales around its centre when crouching.
using UnityEngine;
using UnityEngine.InputSystem;

public class PlayerStates : MonoBehaviour
{
    enum State { Idle, Run, Jump, Fall, Crouch }

    const float Speed = 1.6f, JumpSpeed = 3.8f, Gravity = 12f;
    const float StandH = 0.36f, CrouchH = 0.20f;

    State state = State.Idle;
    float vy;

    void Start() { transform.localScale = new Vector3(0.24f, StandH, 0.24f); }

    void Update()
    {
        var kb = Keyboard.current;
        if (kb == null) return;
        float move = (kb.rightArrowKey.isPressed ? 1f : 0f) - (kb.leftArrowKey.isPressed ? 1f : 0f);
        bool down = kb.downArrowKey.isPressed;
        bool jump = kb.spaceKey.wasPressedThisFrame;
        float dt = Time.deltaTime;
        Vector3 p = transform.position;
        State next = state;

        switch (state)
        {
            case State.Idle:
                if (jump) next = State.Jump;
                else if (down) next = State.Crouch;
                else if (move != 0f) next = State.Run;
                break;
            case State.Run:
                p.x += move * Speed * dt;
                if (jump) next = State.Jump;
                else if (down) next = State.Crouch;
                else if (move == 0f) next = State.Idle;
                break;
            case State.Crouch:
                if (!down) next = State.Idle;
                break;
            case State.Jump:
            case State.Fall:
                p.x += move * Speed * dt;
                vy -= Gravity * dt;
                p.y += vy * dt;
                if (state == State.Jump && vy <= 0f) next = State.Fall;
                else if (state == State.Fall && p.y <= 0f) { p.y = 0f; vy = 0f; next = State.Idle; }
                break;
        }
        transform.position = p;
        if (next != state) ChangeState(next);
    }

    void ChangeState(State next)
    {
        if (state == State.Crouch) SetHeight(StandH);    // exit Crouch
        state = next;
        if (state == State.Crouch) SetHeight(CrouchH);   // enter Crouch
        else if (state == State.Jump) vy = JumpSpeed;    // enter Jump
    }

    void SetHeight(float h)
    {
        Vector3 s = transform.localScale;
        s.y = h;
        transform.localScale = s;
    }
}

The GDScript and C# versions use the enum shape, so enter and exit become branches inside one change function. The rule is the same: one place changes the state, and exit runs before enter.

Pitfalls

  • Writing the state variable from anywhere. If other scripts set state = JUMP directly, exit and enter are skipped and the crouch hitbox stays small. Route every change through one function.
  • Changing state inside enter. An enter that immediately calls change runs the next state's enter before the first one has finished. Return the next state from update instead, and let the following frame decide.
  • Per-state data that is never reset. A timer for "how long have I been dashing" must be set to zero in Dash's enter, or the second dash starts half finished.
  • Losing a button press across a change. A jump pressed on the frame Fall lands is consumed by Fall, which ignores it. Players feel an eaten jump. An input buffer, which keeps a press alive for a few frames, fixes it.
  • State explosion. Shooting while running, jumping or falling turns five states into ten. That calls for nested states or two machines side by side, the next lesson's subject.

In real games

The animation graphs of both engines are state machines you can open and inspect. Godot's AnimationNodeStateMachine even finds a path through several states when you call travel(). Outside animation, the same idea runs player controllers, enemy behaviour, menus and the flow of a match (waiting, countdown, playing, results).

Takeaways

  • A finite state machine keeps exactly one current state, so impossible combinations of flags cannot exist.
  • Transitions are explicit arrows. If there is no arrow, the change cannot happen.
  • Each state has enter, update and exit. Whatever enter sets up, exit undoes.
  • In one frame: the old state's update decides, the old state exits, the current state changes, the new state enters. Its update runs next frame.
  • Godot and Unity provide visual state machines for animation. Gameplay machines are usually an enum and a match or switch, or one object per state.
